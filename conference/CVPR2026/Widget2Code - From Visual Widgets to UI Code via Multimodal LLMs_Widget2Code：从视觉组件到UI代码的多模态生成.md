> 导读

UI2Code旨在将视觉设计转化为可执行前端代码，但现有方法严重依赖Web或移动端丰富的结构化元数据，无法处理缺乏DOM树且空间极度紧凑的App Widget。本文指出通用多模态大语言模型（MLLMs）虽优于专用UI2Code模型，但仍存在布局错乱与几何失真，其切入点在于将“端到端生成”解耦为“感知分解-检索-编译”流水线。通过构建首个纯图像Widget基准及模块化基线WidgetFactory，本文确立了该细分领域的评估标准。其价值在于填补了微界面代码生成的空白，但受限于自建数据集规模及缺乏跨平台泛化验证，其结论的普适性存疑。

## 研究背景

UI2Code任务的核心挑战在于视觉感知与代码生成的耦合。Web页面天然伴随HTML/CSS真值，移动端可通过Accessibility API获取视图层级，这使得基于监督学习的方法能够建立像素到代码的映射。然而，App Widget作为紧凑、无上下文的微界面，既无公开源码，也缺乏布局元数据，且包含密集图标与微型图表，导致传统基于结构化元数据的方法完全失效。这种“无监督信号”与“高视觉复杂度”的矛盾，构成了Widget代码生成的根本障碍。

主流UI2Code路线分为两类：一类是依赖真值代码的专用模型（如Design2Code、UI-UG），另一类是通用MLLM直接生成。实验表明，专用模型在Widget上性能显著退化，因其训练数据偏向Web/移动端的长文本与宽松布局，缺乏对紧凑结构的归纳偏置。通用MLLM虽具备更强的视觉泛化能力，但直接生成HTML时易产生冗长代码、图标幻觉及边界溢出，无法保证几何一致性。现有方法均未能解决“从纯视觉输入到几何精确代码”的映射问题，亟需一种不依赖真值代码、且能显式控制布局结构的生成范式。

## 核心方法

### 方法参照系

本文问题属于UI2Code中的“视觉-代码映射”范畴，但区别于主流端到端生成流程。标准流程通常由MLLM直接输出HTML字符串，而本文的关键差异在于引入中间结构化表示（WidgetDSL）与外部检索模块，将生成过程拆解为感知、检索、编译与渲染四个阶段，以解决直接生成导致的几何失控问题。

### 原子组件感知与图标检索

针对MLLM直接生成图标易产生语义幻觉及视觉不一致的问题，本文在感知阶段引入基于检索的图标替换策略。设计动机在于利用确定性检索替代概率性生成，确保图标的语义正确性与视觉保真度。首先，MLLM将输入图像 $I$ 分解为原子组件 $e = [r, b, t, c]$，其中 $r$ 为裁剪区域，$t$ 为文本描述。对于图标类组件，系统计算其视觉嵌入 $f_v^{[e]} = F_v(r)$ 与文本嵌入 $f_t^{[e]} = F_t(t)$。在包含 $N$ 个SVG图标的库中，通过余弦相似度进行粗检索：

$$ \text{Cand} = \text{TopK}_{n} \left( \cos(f_v^{[e]}, f_v^{[n]}) \right) $$

随后利用文本嵌入对候选集进行重排序，最终选取最匹配图标。该机制将图标生成转化为检索问题，消除了MLLM在细粒度视觉符号上的生成噪声。

### WidgetDSL编译与自适应渲染

针对直接生成HTML导致的布局错乱与边界溢出，本文设计了框架无关的领域特定语言（WidgetDSL）及自适应渲染模块。设计动机在于通过中间表示解耦视觉理解与代码实现，并通过反馈机制修正几何误差。Perceptual Agent将组件组装为WidgetDSL抽象语法树，编译器将其映射为React或HTML。关键在于自适应渲染模块，它利用Web引擎反馈渲染结果，若检测到内容溢出或比例失真，则动态调整容器尺寸与内边距。这一闭环机制确保了生成代码在严格空间约束下的几何一致性，解决了通用MLLM缺乏空间感知导致的布局失效问题。

## 实验评估

实验在自建Widget2Code基准上进行，包含2,825个高质量Widget，其中1,000个用于测试。基线覆盖通用MLLM（GPT-4o, Gemini2.5-Pro, Qwen3-VL）与专用UI2Code模型（ScreenCoder, UI-UG, Design2Code）。结果显示，专用模型在Widget上表现极差，如UI-UG的Layout Margin仅为52.97，而通用MLLM GPT-4o达到63.48。本文提出的Widget2Code框架在Layout Margin（72.15）、Content（66.08）及Geometry（100.00）上均显著优于所有基线，验证了模块化流水线在几何一致性上的优势。

| 方法 | Layout Margin | Layout Content | Geometry |
| :--- | :--- | :--- | :--- |
| GPT-4o | 63.48 | 59.04 | 91.93 |
| UI-UG | 52.97 | 47.90 | 23.35 |
| Widget2Code (Ours) | 72.15 | 66.08 | 100.00 |

消融实验表明，各模块均有正向贡献。加入WidgetFactory后，Layout Margin从基线Qwen3-VL的64.75提升至69.97；进一步加入Color analysis模块后，Style Palette从47.44提升至57.56。然而，加入Components模块后，Perceptual SSIM从0.683微降至0.676，显示组件分解可能在局部细节上引入轻微失真。整体而言，模块化设计在结构保真度上收益显著，但在像素级感知指标上存在边际冲突。

评估指标基于Apple Widget设计原则，涵盖Layout、Legibility、Style、Perceptual及Geometry五个维度，比传统CLIP Score更细粒度。局限在于数据集规模较小（1,000测试样本），且仅评估静态Widget，未涉及动态交互。代码与超参数未完全公开，复现性依赖项目页面提供的部分资源。

## 关联研究分析

从问题动机看，本文与Design2Code同属UI2Code，但Design2Code依赖Web页面的HTML真值进行监督，而本文针对无代码对的Widget场景。这一差异源于任务特性：Web页面结构规整且数据丰富，适合端到端监督；Widget结构紧凑且数据稀缺，迫使本文采用检索与编译的解耦策略。Design2Code在Web上有效，但在Widget上因缺乏归纳偏置而失效，这印证了专用模型在跨域迁移时的局限性。

从方法设计看，本文与UI-UG同属MLLM驱动，但UI-UG采用端到端生成，本文引入WidgetDSL中间表示。UI-UG在Web/移动端表现良好，但在Widget上Layout Margin仅52.97，远低于本文的72.15。根源在于UI-UG缺乏显式的几何约束机制，而本文通过自适应渲染反馈闭环解决了边界溢出问题。这种差异表明，在空间约束极强的微界面任务中，中间结构化表示比直接生成更具鲁棒性。

## 总结

本文核心矛盾在于无结构化元数据的紧凑微界面代码生成。现有方法因缺乏归纳偏置或几何控制而失效，本文凭借“感知-检索-编译”解耦架构及自适应渲染反馈，实现了几何一致的重建。实验证明其在Layout Margin（72.15）与Geometry（100.00）上优于GPT-4o等通用模型。边界在于数据集规模有限且仅覆盖静态Widget，未验证动态交互场景。当Widget包含实时数据更新或复杂动画时，静态DSL编译能否保持几何一致性，论文未给出回答。
