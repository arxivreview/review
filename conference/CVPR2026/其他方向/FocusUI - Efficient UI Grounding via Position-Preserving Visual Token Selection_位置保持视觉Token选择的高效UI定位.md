# CVPR2026最新论文 ｜FocusUI: Efficient UI Grounding via Position-Preserving Visual Token Selection ｜位置保持视觉Token选择的高效UI定位

研究机构：新加坡国立大学、英国牛津大学

作者：Mingyu Ouyang、Kevin Qinghong Lin、Mike Zheng Shou 等 4 人

论文原文见 [arXiv](https://arxiv.org/abs/2601.03928)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2601.03928)

> 高分辨率UI截图导致视觉Token序列极度冗长，直接压缩会破坏空间位置连续性，致使定位精度崩塌。现有通用剪枝方法忽略多模态旋转位置编码对序列连续性的依赖，无法在UI任务中平衡效率与精度。FOCUSUI通过指令引导的显著性评分筛选关键Patch，并引入POSPAD机制将丢弃的连续序列压缩为单一位置标记，在保留30%视觉Token时仅损失3.2%精度，实现1.44倍推理加速。该方法验证了位置保持策略对细粒度定位的关键作用，但其绝对精度仍低于未压缩的SOTA大模型，且未探索多步交互中的时序Token压缩。

## 研究背景

UI定位任务要求模型从高分辨率截图中精准定位指令所指元素，但2K或4K分辨率截图被切分为数千个视觉Token，占据序列预算的85%以上，造成巨大的计算开销与注意力稀释。多模态大语言模型（MLLMs）依赖多模态旋转位置编码（M-RoPE）建模空间关系，其高度、宽度维度与视觉Patch的二维布局严格对应。当直接丢弃视觉Token时，M-RoPE序列出现位置跳跃，导致模型对细粒度目标的空间感知失效，定位偏移显著。

GUI定位领域已确立纯视觉驱动范式，主流方法通过大规模数据微调提升定位精度，但效率问题长期被忽视。通用视觉Token剪枝方法（如Fast-V、HiPrune）在自然图像理解中有效，但在UI定位任务中因破坏位置连续性导致精度大幅下滑。例如，Jedi-3B在ScreenSpot-Pro上应用HiPrune后，准确率从36.1%降至26.2%。FOCUSUI的切入点在于识别UI任务对位置敏感性的特殊需求，通过位置保持的Token选择策略，在压缩冗余视觉信息的同时维持空间结构完整性，解决通用剪枝方法在细粒度定位场景下的失效问题。

## 核心方法

### 方法参照系

通用视觉Token剪枝流程通常基于Token重要性评分，在预填充阶段筛选Top-K Token以缩短序列长度。该流程假设Token间位置关系可被忽略，适用于自然图像分类等任务。但UI定位要求像素级精度，视觉Patch的二维空间布局与M-RoPE位置编码紧密耦合，直接丢弃Token会破坏(h, w)维度的连续性，导致定位偏移。本文问题与该通用流程的关键差异在于：必须在选择Token的同时，显式保留被丢弃序列的位置信息，以维持模型的空间感知能力。

### 指令引导的显著性评分

通用剪枝方法基于视觉冗余度或注意力权重选择Token，忽略指令语义对目标区域的约束。FOCUSUI引入轻量级查询引导显著性评分器，通过指令文本嵌入与视觉Patch嵌入的相似度计算，筛选指令相关的关键Patch。该评分器采用自注意力层增强跨模态交互，并通过KL散度优化训练，其核心公式为：

$$s_i = \text{mean}(P_i)$$

其中$P_i$为第$i$个Patch与所有指令Token的余弦相似度矩阵。该公式的物理含义是：将指令语义聚合为单一查询向量，通过均值池化计算每个Patch与指令的整体相关性，从而区分目标区域与背景区域。这一设计解决了通用剪枝方法在模糊指令下误删关键元素的问题，确保保留的Token与指令语义高度对齐。

### 位置保持序列变换（POSPAD）

通用剪枝方法直接删除低重要性Token，导致M-RoPE序列出现位置跳跃，破坏空间连续性。FOCUSUI引入POSPAD策略，将每个被丢弃的连续视觉Token序列压缩为单一可学习标记，置于该序列的最后一个索引位置。该变换的核心公式为：

$$S = K \cup E_{\text{seq-end}}$$

其中$K$为保留的Token索引集，$E_{\text{seq-end}}$为每个被丢弃连续序列的末尾索引集。该公式的物理含义是：仅保留序列末尾的位置信息，通过单一标记继承该位置的(h, w)坐标，从而在压缩序列长度的同时，维持M-RoPE在空间维度上的连续性。这一设计解决了直接丢弃Token导致的定位偏移问题，在保留30%视觉Token时，ScreenSpot-Pro准确率仅从43.8%降至40.6%，而通用剪枝方法在相同压缩率下精度损失超过20%。

## 实验评估

实验在ScreenSpot-V2、ScreenSpot-Pro、OSWorld-G和UI-Vision四个基准上进行，基线覆盖GUI-Actor、Jedi、Qwen2.5-VL等主流模型，但缺少GUI-Spotlight等迭代聚焦类方法的对比。FOCUSUI-7B在ScreenSpot-Pro上以48.3%的准确率超越GUI-Actor-7B的44.6%，且在30% Token保留率下，准确率仅降至45.1%，而Jedi-3B+HiPrune在相同压缩率下仅为26.2%。

| 模型 | ScreenSpot-V2 | ScreenSpot-Pro | OSWorld-G |
| :--- | :--- | :--- | :--- |
| Jedi-3B (100%) | 88.9 | 36.1 | 48.8 |
| Jedi-3B + HiPrune (30%) | 80.9 | 26.2 | 40.4 |
| FOCUSUI-3B (100%) | 91.5 | 43.8 | 53.4 |
| FOCUSUI-3B (30%) | 91.0 | 40.6 | 51.8 |

消融实验表明，UI-Graph先验与Bounding-box重叠信号的融合监督是关键，单独使用UI-Graph标签时准确率为41.1%，单独使用Bounding-box标签时为39.8%，融合后达到42.3%。保留率从100%降至30%时，准确率平滑下降，但降至10%时出现显著下滑（36.6%），表明存在精度保持的临界压缩率。

评估协议未报告置信区间，且训练数据规模（约1M截图）与基线GUI-Actor对齐，但不同模型的预训练数据分布差异未被控制。代码已开源，超参数包括融合权重$\lambda=0.8$，训练使用8×NVIDIA H200 GPU，1个epoch。

## 关联研究分析

从问题动机看，FOCUSUI与GUI-Spotlight均针对高分辨率UI定位的效率与精度矛盾，但解决路径截然不同。GUI-Spotlight通过迭代裁剪增加推理次数，以多次前向传播换取局部视野的精度提升，其代价是推理延迟显著增加。FOCUSUI则通过单次前向的Token压缩，在预填充阶段消除冗余，推理延迟仅增加1.44倍。这一差异源于任务特性：GUI-Spotlight假设目标区域需动态探索，而FOCUSUI假设指令语义足以引导全局定位，无需迭代搜索。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

从方法设计看，FOCUSUI与ZonUI-3B同属高效轻量模型路线，但优化阶段不同。ZonUI-3B通过单卡训练流水线降低训练成本，侧重模型部署的门槛；FOCUSUI通过推理时Token选择降低计算开销，侧重实时交互的延迟。两者共同构成从训练到部署的全链路轻量化方案，但FOCUSUI的POSPAD机制具有任务特异性，其位置保持策略依赖M-RoPE的空间编码特性，是否可迁移至非UI的通用VLM任务，如文档理解或视频定位，论文未进行验证。

## 总结

FOCUSUI解决的核心矛盾是高分辨率UI截图导致的视觉Token冗余与细粒度定位对空间连续性的依赖。通用剪枝方法因破坏M-RoPE位置编码而失效，FOCUSUI通过指令引导的显著性评分与POSPAD位置保持策略，在压缩70%视觉Token时仅损失3.2%精度，实现1.44倍推理加速。其边界在于绝对精度仍低于未压缩的SOTA大模型（如GUI-AIMA-3B的61.5%），且仅处理单步定位，未涉及多步交互中的时序Token压缩。当支持集增大到5-shot时，查询侧增强的边际收益是否递减，论文未给出回答。
