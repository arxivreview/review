# ICLR2026最新论文 ｜HOW MANY CODE AND TEST CASES ARE ENOUGH? EVALUATING TEST CASES GENERATION FROM A BINARY-MATRIX PERSPECTIVE ｜从二进制矩阵视角评估测试用例生成

研究机构：哈尔滨工业大学、中南大学

作者：Xianzhen Luo、JinYang Huang、Wenzhen Zheng 等 8 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_77641761)

> 导读 测试用例生成（Test Case Generation, TCG）的质量直接决定代码评估的可靠性，但现有基准在评估TCG方法时面临计算成本高昂与分数膨胀的双重困境。主流方法依赖未过滤的错误代码集合，导致常见错误淹没关键故障，使得评估失去区分度。本文切入点在于将错误代码与测试用例的执行结果形式化为二进制矩阵，利用矩阵秩理论构建最小且最具区分度的诊断基。通过提出WrongSelect算法筛选错误代码，本文构建了TC-Bench基准，揭示了当前SOTA方法在复杂错误模式下的显著缺陷。该工作为TCG评估提供了防膨胀的理论框架，但其对非线性错误模式的覆盖能力仍存疑。

## 研究背景

代码评估依赖黄金测试用例（Golden Tests, GTs）作为正确解的边界条件集，但私有测试用例稀缺且构建成本高。当大语言模型（LLM）用于自动生成测试用例（ATs）时，评估其有效性需验证其能否排除错误代码（Wrong Codes, WCs）。然而，WCs集合中存在大量重复或琐碎错误，仅能识别常见错误的平庸方法可能获得与识别罕见关键故障的优越方法相似的分数，这种统计淹没效应削弱了基准的诊断力。

现有TCG评估路线主要分为随机采样与启发式选择两类。随机采样方法如TestCase-Eval（Cao et al., 2025）虽简单但评估过于稀疏，无法连续反映模型能力；启发式方法如TCG（Yang et al., 2025）选择通过率高错误代码，但缺乏理论依据。未过滤的全量WCs集合导致评估成本呈二次方增长，且分数膨胀严重。本文切入点在于将WCs的执行结果映射为二进制向量，通过线性代数工具量化错误模式多样性，从而在理论上确定最小诊断基的大小与构成。

## 核心方法

### 二进制矩阵与诊断基形式化

TCG评估的标准流程是统计生成测试用例排除WCs的比例，但本文指出该流程忽略了WCs内部的冗余性。本文将每个WC在GTs上的执行结果（AC=0, WA=1）表示为二进制向量，所有WC构成$n \times d$矩阵$M$。矩阵秩$rank(M)$量化了独立错误模式的最大数量，同时提供了区分这些模式所需测试用例数的上界。设计动机在于解决未过滤集合中常见错误淹没关键故障的问题，通过线性无关约束确保选出的WCs集合既完整又无冗余。

### WrongSelect贪心近似算法

在确定矩阵秩后，需从多个可能的基中选择多样性最大的基。本文定义目标函数为最小化基内所有WCs对的平均Jaccard相似度：

$$ F(I) = \frac{1}{\binom{|I|}{2}} \sum_{i<j \in I} \frac{\mathbf{r}_i \cdot \mathbf{r}_j}{\|\mathbf{r}_i\|_1 + \|\mathbf{r}_j\|_1 - \mathbf{r}_i \cdot \mathbf{r}_j} $$

其中$\mathbf{r}_i \cdot \mathbf{r}_j$计算共同失败的测试用例数。由于寻找最优基是NP-hard问题，本文提出WrongSelect算法，采用随机重启局部搜索策略。算法从随机初始基开始，通过交换基内与基外向量迭代优化，直至收敛至局部最优。设计动机在于平衡计算效率与诊断广度，避免启发式选择导致的评估稀疏性，同时通过预过滤（移除全1列与高失败率行）消除噪声，确保基的诊断价值。

## 实验评估

实验在TC-Bench（877题，9347 WCs）上评估5种TCG方法（CRUX, PSEUDO, ALGO, LCB, HT）与13个LLM。基线覆盖主流方法，但缺失基于变异测试的TCG方法，限制了与经典软件工程方法的对比。主结果显示，即使最强组合Claude4+HT的HackRate仅为62.96%，表明当前技术存在显著性能上限。

| LLM | Method | PR | HR |
|---|---|---|---|
| Claude4 | HT | 71.56 | 62.96 |
| Qwen2.5-Coder-32B | LCB | 59.65 | 58.10 |
| Deepseek-V3 | LCB | 46.58 | 58.83 |
| Qwen-Coder-Plus | LCB | 77.73 | 61.46 |

消融实验揭示方法选择对性能的影响远超模型规模。在Qwen2.5-Coder-32B上，LCB的HackRate比CRUX高近40%，而不同规模模型使用相同方法时HackRate差异仅1%。这表明TCG是专业化任务，模型缩放带来的收益有限，方法论改进更为关键。

评估边界方面，HackRate与Precision定义不同，不可直接跨基准比较。代码已开源，但预过滤阈值$\tau=80\%$与秩阈值5的敏感性分析未在正文详细展开，可能影响基准的泛化性。

## 关联研究分析

从问题动机看，本文与SWE-bench等仓库级评估基准形成互补。SWE-bench关注模型在真实GitHub Issue中的代理式编码能力，而TC-Bench聚焦评估工具本身的诊断力。二者差异源于任务特性：仓库级评估需处理跨文件依赖，而TCG评估需处理错误模式多样性。本文未探索矩阵秩理论在仓库级代码错误空间中的适用性，查询侧增强在数据充足时是否仍有增益，论文未给出回答。

从方法设计看，本文与HardTestGen（HT）等RL验证器生成方法存在路线差异。HT通过强化学习优化测试用例质量，而TC-Bench通过线性代数筛选评估基准。二者冲突暗示了TCG评估的两个维度：生成质量与评估可靠性。本文未对比HT在TC-Bench上的表现与在其他基准上的差异，可能掩盖了方法在不同评估协议下的鲁棒性差异。

## 总结

本文要解决的核心矛盾是TCG评估中计算成本与分数膨胀的冲突。现有方法因未过滤WCs集合导致常见错误淹没关键故障，而本文通过矩阵秩理论确定最小诊断基，利用WrongSelect算法高效筛选多样性最大的WCs。实验证明即使SOTA方法在TC-Bench上HackRate仅62.96%，揭示了当前TCG方法在复杂错误模式下的显著缺陷。本文的边界在于预过滤阈值与秩阈值的敏感性未充分验证，且未探索矩阵秩理论在非算法类代码中的适用性。当支持集增大到5-shot时，查询侧增强的边际收益是否递减，论文未给出回答。
