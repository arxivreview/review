# ICLR2026最新论文 ｜SPARTA: Scalable and Principled Benchmark of Tree-Structured Multi-hop QA over Text and Tables ｜基于溯源修复的表格-文本多跳问答基准构建

作者：Sungho Park、Jueun Kim、Wook-Shin Han

论文原文见 [arXiv](https://arxiv.org/abs/2602.23286)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2602.23286)

> 现有表格-文本问答（Table-Text QA）基准因人工标注导致噪声高、推理浅、规模小，无法真实评估模型在异构数据上的深层推理能力。SPARTA 通过构建统一的关系事实数据库，利用大语言模型（LLM）生成嵌套 SQL 查询，并引入数据库溯源技术修复空结果查询，实现了大规模、低噪声、可控跳数的自动化基准生成。该方法将标注成本降低至 HybridQA 的四分之一，并暴露了当前 SOTA 模型在复杂跨模态推理上的显著性能崩塌。其价值在于提供了更严谨的评测标尺，但生成查询的自然度与真实用户意图的匹配度仍存疑。

## 研究背景

当模型需要回答“哪些球员身高超过控球后卫平均值且篮板数大于 8”这类问题时，答案分散在球员属性表、比赛记录文本和位置统计表中。这种跨模态、多跳的推理需求构成了表格-文本问答的核心挑战。然而，传统基准如 HybridQA 和 OTT-QA 依赖人工标注，导致数据规模受限且存在系统性噪声。审计显示，HybridQA 中 21% 的样本包含错误，其中 52.4% 为冗余模态，即表格和文本编码了相同事实却标记为跨模态问题。

现有基准的推理深度普遍较浅，极少涉及超过两跳的链式推理或 GROUP BY、HAVING 等高级分析操作，且多采用线性链结构而非树状结构。这种设计缺陷使得模型在简单提取任务上表现良好，却在真实世界的复杂查询中失效。SPARTA 的切入点在于摒弃全量人工标注，转而利用 LLM 在统一的关系数据库中生成可执行的嵌套 SQL 查询，通过程序化保证逻辑正确性，从而解决标注噪声与规模瓶颈。

## 核心方法

### 方法参照系

SPARTA 属于自动化基准生成框架，其参照系是传统的“检索-生成”或“程序合成”范式。关键差异在于，SPARTA 不直接生成自然语言问题，而是先生成结构化 SQL 查询，再通过 SQL-to-NL 转换生成问题，确保了答案的绝对可执行性和逻辑一致性。

### 参考事实数据库构建

设计动机在于解决文本与表格数据异构导致的检索与对齐困难。SPARTA 将源表格（Source Tables, ST）和从文本中提取的原子事实构成的接地表格（Grounding Tables, GT）合并为参考事实数据库 $D$。

$$ D = ST \cup GT $$

其中 $ST$ 包含结构化数据（如薪资、奖项），$GT$ 包含从非结构化文本（如比赛报道）中提取的原子命题。通过强制共享实体属性（如 PLAYER_NAME）作为主外键，确保 $D$ 中所有元组均可通过 SQL 连接，实现了文本与表格的统一寻址。

### 溯源引导的查询生成

设计动机在于解决 LLM 一次性生成复杂嵌套 SQL 时频繁出现空结果或语义空洞的问题。SPARTA 采用后序遍历（Post-Order）策略构建查询图 $G=(V, E)$，其中节点 $v_i$ 对应子查询，边 $e_{ij}$ 表示嵌套谓词。

$$ Q_{final} = \text{Compose}(Q_{leaf}, \text{Predicate}(Q_{child}, T_{join})) $$

当生成的查询返回空结果时，系统触发溯源修复（Provenance-based Refinement）。该过程剥离谓词直至获得非空结果，利用 why-not 溯源工具定位导致特定元组被过滤的阻塞谓词，并将此反馈提供给 LLM 重写特定子句。例如，若 `salary > 800,000` 导致空结果，溯源报告指出该谓词过滤了关键元组，LLM 随后将其放宽为 `salary > 600,000`。这一机制确保了生成的查询既符合逻辑结构又具备实际数据支撑。

## 实验评估

实验在 NBA、Movie 和 Medical 三个领域进行，使用 Llama-3.1-70B-Instruct 生成数据，评估模型包括 ODYSSEY 和 HProPro，分别搭配 GPT-5 和 GPT-3.5-turbo。基线覆盖了图遍历（ODYSSEY）和程序生成（HProPro）两条主流路线，但缺失了知识库中提到的迭代检索智能体如 PRISM 或 STRIDE，这可能限制了跨模态推理能力的全面评估。

| 方法 | 骨干 | SPARTA (Oracle) Avg F1 | HybridQA F1 | 性能降幅 |
| :--- | :--- | :--- | :--- | :--- |
| ODYSSEY | GPT-5 | 35.6 | 69.5 | 33.9 |
| HProPro | GPT-5 | 40.4 | 70.5 | 30.1 |
| ODYSSEY | GPT-3.5-turbo | 20.6 | — | — |
| HProPro | GPT-3.5-turbo | 20.3 | — | — |

在 SPARTA (Oracle) 设置下，HProPro 在 NBA 和 Movie 领域优于 ODYSSEY，归因于其程序生成能力在处理千行级大表时的优势。然而，在 SPARTA (Retrieval) 设置下，最佳组合 HELIOS + HProPro (GPT-5) 仅获得 22.6 F1，较 Oracle 设置大幅下降，揭示了检索与推理耦合带来的复合挑战。

消融实验显示，对于嵌套查询，Post-Order+Prov 策略比 One-Shot-k 减少了 66.2% 的 LLM 调用次数，比无溯源的 Post-Order 减少了 42.8%。这表明溯源修复不仅提高了查询成功率，还显著降低了生成成本。FiE Reader 在 OTT-QA 上比 HELIOS + HProPro 高 9.2 点，但在 SPARTA 上低 11.0 点，证明微调模型难以泛化到 SPARTA 的复杂域外设置。

评估边界方面，SPARTA 依赖 LLM 生成查询的自然度，虽然经过轻量级人工验证，但可能仍保留模板化痕迹。代码已开源，但生成过程依赖特定的 LLM 版本和硬件配置（4 RTX A6000），复现成本较高。

## 关联研究分析

从问题动机看，SPARTA 与知识库中的 RAG-MHQA 方法（如 PRISM、STRIDE）存在根本差异。RAG-MHQA 关注在线推理时的证据检索与迭代策略，旨在解决长上下文注意力稀释问题；而 SPARTA 关注离线基准构建，旨在解决评测数据的质量与规模问题。SPARTA 的“参考事实数据库”概念类似于知识库中提到的结构化知识表示（如 HippoRAG 的超图），但 SPARTA 将其作为生成引擎而非推理引擎。这种差异源于任务特性：基准构建需要绝对的可执行性保证，而在线推理允许一定的模糊性。

从方法设计看，SPARTA 的溯源修复机制与知识库中的强化学习策略优化（如 GTA-RAG）有异曲同工之妙，均通过过程反馈优化中间步骤。然而，GTA-RAG 使用轨迹级奖励优化检索行为，SPARTA 使用数据库溯源优化 SQL 谓词。SPARTA 未探索将溯源机制应用于非结构化文本检索的可能性，这是否限制了其在纯文本多跳问答中的应用，论文未给出回答。

## 总结

SPARTA 解决了现有表格-文本问答基准噪声高、推理浅、规模小的核心矛盾，通过统一关系数据库和溯源引导的 SQL 生成，实现了低成本、高保真的自动化基准构建。该方法证明了当前 SOTA 模型在复杂跨模态推理上的脆弱性，ODYSSEY 和 HProPro 在 SPARTA 上的 F1 分数较 HybridQA 下降超过 30 点。其边界在于生成查询的自然度依赖 LLM 能力，且评估仅覆盖表格-文本模态，未涉及图像等多模态数据。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
