# ICLR2026最新论文 ｜OMNICVR: A BENCHMARK FOR OMNI-COMPOSED VIDEO RETRIEVAL WITH VISION, AUDIO, AND TEXT ｜全模态组合视频检索基准与音频语义注入

研究机构：清华大学、快手

作者：Junyang Ji、Shengjun Zhang、Da Li 等 11 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_75588353)

> 组合视频检索（Composed Video Retrieval, CoVR）要求模型根据源视频和文本修改指令定位目标视频，但现有基准仅覆盖视觉模态，无法评估音频语义在检索中的决定性作用。本文提出 OmniCVR 基准，将视觉、音频、文本确立为一等模态，并设计 AudioVLM2Vec 模型，通过音频转文本机制注入声学语义。该工作揭示了当前多模态模型在音频组合推理上的严重缺陷，但 AudioVLM2Vec 的推理延迟增加与音频时序信息损失问题仍存疑。

## 研究背景

当检索指令要求“保持画面不变，仅将背景音乐替换为快节奏流行乐”时，传统视觉-文本对齐模型面临根本性失效。这种失效源于跨模态语义粒度不匹配：文本指令中的音频修改意图无法在纯视觉特征空间中找到对应表示，导致模型无法区分视觉相似但声学迥异的候选视频。为弥合这一鸿沟，组合视频检索（CoVR）被提出，它要求模型执行细粒度的组合推理，而非简单的语义相似度匹配。然而，现有 CoVR 基准如 WebVid-CoVR 和 EgoCVR 均将视频视为纯视觉-文本介质，完全忽略了音频流。

视频检索领域的主流路线已从基于手工特征的浅层模型演进至依赖大规模图文对比预训练（如 CLIP）的范式，这解决了零样本泛化问题，但未能触及多模态融合的深层逻辑。时刻检索（Moment Retrieval, MR）与组合检索（CoVR）作为高级任务，依赖基础跨模态对齐能力，但现有方法在处理需要同时修改视觉与音频的复杂指令时，缺乏显式推理能力。本文的切入点在于指出音频往往携带与视觉同等甚至更高的语义权重（如语音传达意图、音乐建立情绪），现有基准因忽略音频而无法评估模型在听觉信息决定性场景下的表现，且缺乏系统性处理视觉与音频同时修改的框架。

## 核心方法

### 方法参照系

本文问题置于组合视频检索（CoVR）通用流程下，其标准范式为：给定源视频 $v_s$ 和修改文本 $t_m$，在候选池 $\mathcal{V}$ 中检索目标视频 $v_t$，即最大化相似度 $S(v_s, t_m, v_t)$。与仅关注视觉变化的现有 CoVR 流程不同，本文要求模型同时处理视觉与音频模态的联合变换，且音频修改指令需具备细粒度的声学语义解析能力。

### 全模态组合检索基准构建

OmniCVR 基准通过三阶段自动化流水线构建，核心创新在于引入双验证协议与模态解耦的三元组挖掘策略。设计动机是解决现有合成数据质量低、缺乏音频维度标注的问题。三元组挖掘采用严格的模态相似度约束：对于音频中心（Audio-Centric）查询，要求源视频与目标视频的视觉 CLIP 余弦相似度 $> 0.9$，同时音频 CLAP 余弦相似度 $< 0.3$，确保视觉场景恒定而音频显著变化。

$$
\text{Triplet}_{\text{audio}} = \{(v_s, v_t) \mid \text{sim}_{\text{CLIP}}(v_s, v_t) > 0.9 \land \text{sim}_{\text{CLAP}}(v_s, v_t) < 0.3\}
$$

该公式物理含义为：在视觉特征空间高度重合的约束下，筛选出声学特征空间差异巨大的视频对，从而强制模型依赖音频语义进行区分。测试集采用 Gemini 2.5 Pro 与人类专家的 AND-gated 双重验证，仅当两者均通过时保留，确保语义保真度。

### 音频转文本嵌入机制

AudioVLM2Vec 在 VLM2Vec 框架基础上，将音频处理从原生 Token 输入改为文本描述注入。设计动机是解决原生音频 Token 在 LLM 中难以与视觉 Token 建立细粒度因果关联的问题。模型使用 Qwen2-Audio-7B-Instruct 生成音频的细粒度自然语言描述 $d_a$，将其与修改查询 $t_m$ 拼接后输入 LLM 骨干。

$$
\mathbf{e}_{\text{final}} = \text{LLM}(\mathbf{e}_{\text{vis}} \oplus \text{Enc}(t_m \oplus d_a))
$$

其中 $\mathbf{e}_{\text{vis}}$ 为视觉编码器输出的投影特征，$\oplus$ 表示序列拼接。该公式表明，音频语义被转化为文本模态，与视觉 Token 在 LLM 的多头自注意力机制中联合处理，使模型能学习如“嘴唇移动”文本与对应视觉 Token 之间的协同关系。最终嵌入通过对比学习优化，实现视觉与音频线索在共享语义空间的对齐。

## 实验评估

实验在 OmniCVR 基准上进行，包含 5,000 个金标准测试实例。基线覆盖轻量级模型（CLIP, BLIP, ImageBind）与大型多模态嵌入模型（VLM2Vec, OmniEmbed-v0.1-multivent）。值得注意的是，基线中缺失了知识库中提到的专门针对 CoVR 优化的 X-Aligner 和 FDCA，这可能影响对组合检索专用架构的对比完整性。

| 模型 | 骨干 | R@1 | R@5 | R@10 |
| :--- | :--- | :--- | :--- | :--- |
| CLIP | CLIP | 27.54 | 56.70 | 62.62 |
| VLM2Vec | Qwen2-VL | 38.44 | 60.44 | 66.60 |
| OmniEmbed | Qwen2.5-Omni | 31.90 | 57.04 | 64.00 |
| AudioVLM2Vec | Qwen2-Audio + Qwen2-VL | **66.98** | **80.86** | **84.40** |

AudioVLM2Vec 在整体 R@1 上达到 66.98，较次优的 VLM2Vec（38.44）提升 28.54 个点。在音频中心子任务上，VLM2Vec 的 R@1 从整体的 38.44 骤降至 12.4，而 AudioVLM2Vec 保持 77.2，揭示了现有模型在音频组合推理上的灾难性失效。

| 消融设置 | R@1 | 变化幅度 |
| :--- | :--- | :--- |
| AudioVLM2Vec (完整) | 77.20 | - |
| 移除源视频 (Blind) | 28.10 | -49.10 |
| OmniEmbed (原生音频) | 13.6 | - |
| OmniEmbed (Audio-as-Text) | 32.7 | +19.1 |

消融实验显示，移除源视频导致 R@1 下降 49.1 个点，证明修改文本是相对指令而非独立描述，源视频提供必要的上下文过滤干扰项。在 OmniEmbed 骨干上，将原生音频 Token 替换为 Audio-as-Text 机制，R@1 从 13.6 提升至 32.7，验证了文本化音频语义在 LLM 嵌入空间中的有效性优于原生音频 Token。

评估协议采用 5 次候选池洗牌取平均，以缓解候选集组成带来的方差。对于音频中心任务，强制包含视觉相似但声学不同的干扰项，确保公平性。局限在于未报告计算效率的 FLOPs 标准化指标，且 AudioVLM2Vec 的推理延迟从 1.72s 增至 4.77s（约 1.77 倍），虽然 RTF 为 0.5 仍快于实时，但在移动端部署中可能构成瓶颈。代码未公开，仅提供 HuggingFace 数据集链接，限制了可复现性。

## 关联研究分析

从问题动机看，OmniCVR 与 WebVid-CoVR 同属组合检索范畴，但后者仅关注视觉修改（如“将海变成湖”），而 OmniCVR 引入了音频修改维度。这一差异源于任务特性：WebVid-CoVR 基于 WebVid10M 合成数据，其视觉多样性足以支撑组合推理，但音频信息在原始数据中未被结构化标注，导致无法构建音频中心查询。OmniCVR 通过 Qwen2.5-Omni 进行全模态标注，解决了数据层面的缺失，但这也引入了对生成模型质量的依赖。

从方法设计看，AudioVLM2Vec 与 OmniEmbed-v0.1-multivent 均基于 Qwen 系列骨干，但前者采用 Audio-as-Text 机制，后者使用原生音频 Token。这一设计选择与领域共识中“对比学习是有效范式”略有冲突，因为 AudioVLM2Vec 更依赖 LLM 的推理能力而非纯对比学习。根源在于组合检索需要细粒度的语义转换推理，原生音频 Token 在 LLM 中难以建立与视觉 Token 的因果关联，而文本化音频能利用 LLM 的语言理解能力。然而，Audio-as-Text 是否牺牲了音频的时序动态信息（如节奏、音调变化），论文未给出定量分析，这可能在处理音乐类查询时成为盲区。

## 总结

本文核心矛盾在于现有组合视频检索基准忽略音频模态，导致无法评估模型在听觉信息决定性场景下的推理能力。切入点在于将音频确立为一等模态，并通过 AudioVLM2Vec 验证音频语义注入的有效性。方法上，OmniCVR 构建了包含 50K 三元组的全模态基准，AudioVLM2Vec 通过 Qwen2-Audio 生成音频文本描述注入 LLM。实验证明 AudioVLM2Vec 在整体 R@1 达 66.98，音频中心 R@1 达 77.2，显著优于基线。边界在于推理延迟增加 1.77 倍，且 Audio-as-Text 机制可能丢失音频时序动态信息。当处理包含复杂节奏变化的音乐类查询时，文本化音频描述能否保留足够的时序细节以支持精确检索，论文未给出回答。
