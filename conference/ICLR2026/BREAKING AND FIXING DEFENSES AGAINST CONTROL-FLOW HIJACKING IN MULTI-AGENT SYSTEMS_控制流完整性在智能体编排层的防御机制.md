# ICLR2026最新论文 ｜BREAKING AND FIXING DEFENSES AGAINST CONTROL-FLOW HIJACKING IN MULTI-AGENT SYSTEMS ｜控制流完整性在智能体编排层的防御机制

研究机构：美国康奈尔大学

作者：Rishi Jha、Harold Triedman、Justin Wagle 等 4 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_62346465)

> 多智能体系统（MAS）在委托执行任务时，编排器依赖子智能体返回的文本进行重规划，这为攻击者提供了通过伪装错误指令劫持控制流的机会。现有基于语义对齐检查的防御手段因定义模糊且缺乏全局上下文，极易被重述攻击绕过。本文提出 ControlValve，在任务规划阶段生成静态控制流图与边缘规则，在执行阶段进行结构化校验而非语义判断。该方法在控制流劫持攻击中实现了 0% 的攻击成功率，但其静态约束机制在应对动态环境中的合法重规划需求时存在潜在的功能性限制。

## 研究背景

当 MAS 处理包含不可信内容（如网页、邮件）的任务时，子智能体可能遭遇间接提示注入（IPI）。若攻击者将恶意指令伪装为“错误修复建议”，编排器在重规划时可能将其视为合法操作，从而执行危险动作，这一现象称为控制流劫持（CFH）。CFH 利用了委托架构中的“混淆代理人”漏洞，即编排器信任子智能体返回的状态信息，却无法区分真实故障与攻击载荷。

MAS 安全防御的主流路线分为两类：一是针对单智能体的对齐检查，如 LlamaFirewall，通过判断智能体行为是否“相关且可能推进目标”来拦截异常；二是基于最小权限原则的资源限制。然而，对齐检查依赖 LLM 对模糊语义的判断，在攻击者将恶意行为包装为“完成任务的必要步骤”时，安全与功能性的冲突导致防御失效。最小权限原则则无法阻止智能体在合法权限内执行恶意操作。

本文的切入点在于将防御层级从语义判断提升至结构验证。借鉴编程语言中的控制流完整性（CFI）原则，ControlValve 不依赖对智能体内部状态或工具调用的观测，而是在编排层建立显式的控制流约束。这种设计避免了 LLM 在运行时进行复杂语义推理的不确定性，转而通过预生成的图结构来硬性限制智能体间的交互路径，从而在不可信内容进入系统前建立安全边界。

## 核心方法

### 方法参照系

MAS 安全防御通常遵循“检测-拦截”流程，即在智能体执行动作前，由守卫模型判断该动作是否符合用户意图。本文问题与该通用流程的关键差异在于：守卫模型缺乏全局执行上下文，且攻击者可通过语义混淆使恶意动作在局部看来是“合理”的。因此，本文放弃了基于语义相似度的动态判断，转向基于预定义结构的静态校验。

### 控制流图生成与约束

设计动机在于解决对齐检查中“恶意行为被伪装为必要步骤”导致的判断失效。ControlValve 在任务规划阶段，利用 LLM 生成一个上下文无关文法，定义智能体调用的合法序列。该过程不依赖攻击样本，而是基于任务逻辑推导。生成的控制流图（CFG）规定了哪些智能体可以在何时被调用，例如“代码执行器只能在编码智能体之后运行”。

$$
G = (V, E, \Sigma, P, S)
$$

其中 $V$ 为智能体集合，$E$ 为允许的转移边，$\Sigma$ 为调用标记，$P$ 为文法产生式，$S$ 为起始符号。该公式的物理含义是：系统仅允许符合文法 $P$ 定义的智能体调用轨迹，任何偏离该轨迹的调用请求将被直接拒绝，无需进行语义层面的“是否安全”辩论。

### 边缘规则与执行时校验

设计动机在于 CFG 仅约束调用顺序，无法约束调用时的具体参数或上下文条件，攻击者可能利用合法路径传递恶意数据。为此，ControlValve 为每条边 $A \to B$ 生成零样本的自然语言规则，定义 $B$ 在何种条件下可被 $A$ 调用。这些规则在规划阶段生成，早于不可信内容的摄入，确保了规则的纯净性。

$$
\text{Permit}(A \to B) = \mathbb{1}[(A, B) \in E] \land \text{Judge}(\text{Trace}, R_{A \to B})
$$

其中 $\mathbb{1}$ 为指示函数，$R_{A \to B}$ 为边缘规则，$\text{Judge}$ 为 LLM 裁判。该公式的含义是：只有当调用对存在于 CFG 中，且 LLM 裁判确认当前执行轨迹满足特定边缘规则时，调用才被允许。与对齐检查不同，裁判仅判断是否满足既定规则，而非判断动作是否“对齐”原始目标，从而避免了语义模糊性带来的误判。

## 实验评估

实验在 AutoGen 平台上进行，使用 Magentic-One 配置，编排器使用 o4-mini，子智能体使用 GPT-4o。基线包括无防御、最小权限（LP）、LlamaFirewall（LF，使用 Llama、GPT-4o、GPT-4o-mini、o4-mini 作为后端）及 Azure Content Filters（ACF）。评估数据集包括新构建的 CFH-Hard（16 个任务，14 种攻击）及修改版的 AgentDojo。

| 防御方法 | CFH-Hard (Coding) ASR (%) | CFH-Hard (Comp. Use) ASR (%) | AgentDojo (Slack) ASR (%) |
| :--- | :--- | :--- | :--- |
| Undefended | 100% | 67% | 10% |
| LlamaFirewall (Llama) | 80% | 67% | 10% |
| LlamaFirewall (o4-mini) | 7% | 6% | 10% |
| ControlValve | 0% | 0% | 0% |

ControlValve 在所有测试场景中均实现了 0% 的攻击成功率，显著优于 LlamaFirewall 在复杂攻击下的表现（最高 ASR 达 80%）。在良性任务性能上，ControlValve 在单答案任务中准确率为 97%，开放任务中至少与基线同等优秀的比例为 56%（编码）和 89%（计算机使用），表明其未显著损害系统功能性。

消融分析显示，LlamaFirewall 的失效主要源于攻击载荷的重述。例如，在计算机使用场景中，攻击者将恶意指令包装为“解决初始任务”的步骤，导致对齐检查通过。ControlValve 通过静态 CFG 阻断了此类路径，即使攻击者试图通过合法智能体传递恶意指令，也会因违反边缘规则而被拦截。此外，实验首次揭示了非对抗性模糊输入导致的意外控制流违规，ControlValve 在此类场景下同样表现出 0% 的违规率，验证了其结构约束的鲁棒性。

评估边界方面，实验仅覆盖了 AutoGen 平台的特定配置，未测试其他 MAS 框架。代码未公开，但基于开源 AutoGen 和 Lark 解析器，复现门槛较低。指标上，ASR 为二值指标，未量化防御带来的延迟开销，尽管论文提及运行时开销与 LlamaFirewall 相当，但未提供具体毫秒级数据。

## 关联研究分析

从问题动机看，ControlValve 与 SentinelAgent 均关注委托链中的信任问题，但路径截然不同。SentinelAgent 侧重于意图验证，通过委托链机制确保子任务符合用户原始意图，属于语义层面的对齐；而 ControlValve 侧重于控制流结构，通过 CFG 限制智能体交互路径，属于结构层面的约束。这种差异源于对“安全”定义的不同：前者认为安全是意图的一致性，后者认为安全是行为的合法性。ControlValve 的优势在于其确定性，不受 LLM 语义理解波动影响，但代价是灵活性降低，难以适应需要动态调整智能体组合的任务。

从方法设计看，ControlValve 与 LlamaFirewall 代表了 MAS 防御的两个极端：动态语义判断 vs. 静态结构约束。LlamaFirewall 依赖 LLM 的推理能力，能够处理未预见的攻击变体，但易被语义混淆绕过；ControlValve 依赖预生成的规则，对已知攻击模式具有强防御力，但对超出 CFG 范围的合法操作可能产生误报。这种设计选择反映了 MAS 安全中“安全性”与“功能性”的根本权衡：ControlValve 通过牺牲部分适应性换取了更高的确定性，这在安全关键场景中是合理的，但在开放域任务中可能成为瓶颈。

## 总结

本文解决的核心矛盾是 MAS 中语义对齐检查的脆弱性与控制流劫持攻击的隐蔽性之间的冲突。现有方法依赖 LLM 对模糊语义的判断，易被重述攻击绕过，而 ControlValve 通过引入静态控制流图与边缘规则，将防御从语义层提升至结构层，实现了在 CFH 攻击下的 0% 攻击成功率。其边界在于静态 CFG 的生成依赖 LLM 的规划能力，若规划阶段出错，防御即失效；且过度约束可能限制智能体在真实故障中的自适应重规划能力。当任务复杂度增加导致 CFG 规模指数级增长时，规划阶段的 LLM 能否准确生成无冗余且无遗漏的控制流图，论文未给出回答。
