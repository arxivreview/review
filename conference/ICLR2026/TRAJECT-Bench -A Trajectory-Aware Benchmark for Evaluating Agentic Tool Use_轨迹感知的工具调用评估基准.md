# ICLR2026最新论文 ｜TRAJECT-Bench:A Trajectory-Aware Benchmark for Evaluating Agentic Tool Use ｜轨迹感知的工具调用评估基准

研究机构：美国密歇根州立大学、美国宾夕法尼亚州立大学

作者：Pengfei He、Zhenwei Dai、Bing He 等 13 人

论文原文见 [arXiv](https://arxiv.org/abs/2510.04550)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2510.04550)

> 现有智能体评估多聚焦于最终答案的正确性，导致无法区分模型是真正掌握了工具调用逻辑，还是仅凭内部知识“猜”出了结果。TRAJECT-Bench 通过构建包含 1228 个高保真生产级 API 的工具集，并引入轨迹结构（并行/串行）与查询难度（直接/隐含）的双维度控制变量，将评估重心从结果导向转向过程审计。该基准通过精确匹配、包含率及参数校验等细粒度指标，量化了模型在复杂依赖链中的执行偏差。其核心价值在于揭示了从短轨迹向中长轨迹过渡时的性能瓶颈，但在动态环境适应性与多智能体协作归因方面仍存在局限。

## 研究背景

当智能体面对包含数百个 API 的工具库时，上下文窗口的限制迫使系统必须从海量选项中筛选出正确的工具并填充参数。这一过程不仅要求模型理解自然语言指令，更需精确解析工具的 Schema 约束与依赖关系。若仅评估最终输出，模型可能通过调用错误的工具但利用内部知识修正结果，从而掩盖了工具选择与参数化能力的缺陷。这种“结果正确但过程错误”的现象，使得传统基准无法有效诊断智能体在真实部署中的可靠性。

工具调用评估领域长期存在三个核心瓶颈：一是工具集规模小且多为模拟数据，缺乏生产级 API 的复杂性；二是查询指令过于直接，往往在提示词中直接包含 API 名称，未考察模型从隐含线索中推断工具的能力；三是评估指标单一，过度依赖最终准确率，忽略了中间步骤的工具选择错误、参数格式违规及依赖链断裂。ToolBench 等早期工作虽引入了多步工具调用，但轨迹深度有限且缺乏对查询难度的解耦。TRAJECT-Bench 的切入点在于将工具调用视为一种独立的、可分解的技能，通过控制轨迹结构与查询语义的复杂度，实现对模型工具使用能力的细粒度诊断。

## 核心方法

### 方法参照系

本文问题属于工具增强智能体评估范畴，与 ToolBench 和 Gorilla 等基准共享“工具选择-参数填充-执行”的基本流程。关键差异在于，现有基准通常将工具集视为静态背景，仅关注最终任务成功率；而本文将工具调用轨迹本身作为评估对象，引入了轨迹结构（并行/串行）与查询难度（简单/困难）作为显式控制变量，旨在解耦模型的工具选择能力与通用推理能力。

### 轨迹结构与查询难度的解耦设计

在数据构建阶段，本文首先从 RapidAPI 筛选出 1228 个高保真工具，覆盖旅行、金融、教育等 10 个领域。针对轨迹结构，本文定义了两种基本拓扑：并行结构（Parallel）中工具调用相互独立，输入参数预先固定；串行结构（Sequential）中工具形成依赖链，后续工具的输入依赖于前序工具的输出。为量化这种依赖关系，本文构建了有向工具图 $G_T = (V, E)$，其中节点 $v \in V$ 代表工具，边 $e_{ij} \in E$ 表示工具 $t_i$ 的输出可作为工具 $t_j$ 的输入参数。

$$
\text{Trajectory}_{seq} = \{ t_1(\text{params}_1) \rightarrow t_2(\text{params}_2) \rightarrow \dots \rightarrow t_n(\text{params}_n) \}
$$

该公式定义了串行轨迹的形式化表示，其中 $\text{params}_k$ 的取值依赖于 $t_{k-1}$ 的执行结果。设计动机在于，现有基准多采用短轨迹，无法捕捉长依赖链中的状态漂移与错误累积。通过手动设计轨迹模板并让 LLM 填充具体参数，本文确保了串行轨迹的逻辑连贯性，使得评估能够区分模型是“无法规划依赖顺序”还是“无法正确传递中间状态”。

### 查询难度分级与轨迹感知指标

在查询生成阶段，针对同一轨迹，本文生成了两个语义对齐但难度不同的查询版本：简单版本（Simple）直接指明工具需求与关键参数；困难版本（Hard）使用自然语言中的隐含线索，要求模型推断工具选择与参数映射。例如，将“按评分排序酒店”转化为“寻找口碑好的住宿”。这种设计使得模型在 Hard 查询下的性能退化可直接归因于语义推断能力的不足，而非工具执行能力的缺陷。

在评估指标上，本文引入了轨迹感知指标以替代单一的最终准确率。其中，轨迹精确匹配（Trajectory ExactMatch, EM）计算预测轨迹与金标准轨迹的工具名称集合是否完全一致：

$$
\text{EM} = \mathbb{I}(\{t_i\}_{pred} = \{t_i\}_{gold})
$$

该公式通过指示函数判断预测工具集合与金标准工具集合的等价性，严格考察了模型是否选择了正确的工具组合。此外，还包含轨迹包含率（Inclusion）、工具使用正确性（Usage，校验参数 Schema 与值）以及轨迹满足度（Traj-Satisfy，由 LLM 评判器在无金标准时评估轨迹能否解决查询）。这些指标共同构成了对工具调用过程的多维诊断，解决了仅关注最终答案时无法定位错误根源的问题。

## 实验评估

实验在 TRAJECT-Bench 上进行，涵盖 1228 个工具和 5670 个查询。基线模型包括 Claude-3.7、Claude-4、Gemini-2.5-pro、GPT-5-mini、DeepSeek-V3.1 等 SOTA 模型。评估协议分为直接查询（Direct Query）和智能体模式（Agentic，基于 ReAct），并对比了全量工具、领域内工具和检索增强（Retrieval-based）三种工具选择策略。

| 模型 | 查询难度 | 轨迹结构 | EM | Inclusion | Usage | Acc |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Claude-4 | Simple | Parallel | 0.846 | 0.855 | 0.839 | 0.905 |
| Claude-4 | Hard | Parallel | 0.445 | 0.668 | 0.794 | 0.517 |
| Gemini-2.5-pro | Simple | Parallel | 0.851 | 0.854 | 0.835 | 0.911 |
| Gemini-2.5-pro | Hard | Parallel | 0.442 | 0.652 | 0.785 | 0.498 |
| Claude-4 | Simple | Sequential | 0.819 | 0.832 | 0.775 | 0.813 |
| Claude-4 | Hard | Sequential | 0.445 | 0.668 | 0.794 | 0.517 |

数据显示，模型在 Simple 查询下的表现显著优于 Hard 查询。以 Claude-4 为例，在并行结构下，Acc 从 0.905 骤降至 0.517，降幅接近 43%。这一差距在串行结构中同样存在，表明模型在从隐含线索推断工具及参数时存在系统性弱点。此外，串行结构的整体性能低于并行结构（Claude-4 Simple Acc: 0.813 vs 0.905），揭示了依赖链管理是工具调用的另一瓶颈。

在检索增强策略的消融实验中，引入检索机制对 Hard 查询的性能提升有限，甚至在某些情况下导致性能下降。例如，Claude-4 在 Hard 并行查询中，使用 bge-large 检索时 Acc 为 0.189，而直接提供领域工具时 Acc 为 0.517。这表明，当查询语义模糊时，基于嵌入相似度的检索策略容易召回错误工具，反而干扰了模型的决策。相比之下，在 Simple 查询中，检索策略能显著降低上下文长度，提升效率，但对准确率的提升幅度小于直接提供全量工具。

评估边界方面，本文主要依赖 LLM 评判器（Claude-4）进行 Traj-Satisfy 和 Acc 的评估，可能存在评判器偏差。此外，工具集虽为生产级 API，但静态的依赖图构建限制了动态环境适应性评估。代码与数据已开源，但检索模型的超参数（如 Top-K=20）固定，未探索不同 K 值对性能的影响。

## 关联研究分析

从问题动机看，TRAJECT-Bench 与 ToolBench 的核心差异在于对“工具使用能力”的定义。ToolBench 侧重于多步任务完成率，将工具调用视为达成最终目标的手段；而 TRAJECT-Bench 将工具调用本身视为被评估的技能，强调过程的正确性。这种差异源于任务特性的不同：ToolBench 的任务多为端到端的信息检索，最终答案往往唯一且明确；而 TRAJECT-Bench 的任务涉及复杂的参数依赖与语义推断，中间步骤的错误可能导致多种失败模式。TRAJECT-Bench 通过解耦查询难度，更清晰地隔离了语义理解与工具执行的贡献，这是 ToolBench 等早期基准未能实现的。

从方法设计看，与 CORE 等通用智能体轨迹评估框架相比，TRAJECT-Bench 的轨迹定义更为具体且结构化。CORE 使用确定性有限自动机（DFA）对通用动作路径进行标注，适用于多种环境交互；而 TRAJECT-Bench 聚焦于工具调用这一特定子集，利用有向工具图 $G_T$ 显式建模依赖关系。这种设计使得 TRAJECT-Bench 能够进行更细粒度的参数校验（Usage 指标），但牺牲了通用性。CORE 的优势在于可迁移至网页导航、代码编辑等非工具调用场景，而 TRAJECT-Bench 的静态依赖图假设限制了其在动态工具接口变化场景下的适用性。

## 总结

TRAJECT-Bench 旨在解决工具调用评估中“结果正确但过程错误”的盲区，通过构建大规模生产级工具集与双维度控制变量（轨迹结构、查询难度），实现了对模型工具使用能力的细粒度诊断。实验证明，模型在隐含语义推断（Hard 查询）和长依赖链管理（Sequential 结构）上存在显著性能瓶颈，Claude-4 在 Hard 并行查询下的 Acc 仅为 0.517，远低于 Simple 查询的 0.905。该基准的边界在于其静态依赖图假设与对 LLM 评判器的依赖，未能覆盖动态工具接口变化及多智能体协作场景。当工具依赖关系在运行时动态变化时，基于静态有向图的轨迹评估是否仍能准确捕捉模型的规划能力，论文未给出回答。
