# ICLR2026最新论文 ｜Process-Level Trajectory Evaluation for Environment Configuration in Software Engineering Agents ｜环境配置过程级诊断基准

研究机构：中山大学、香港理工大学

作者：Jiayi Kuang、Yinghui Li、Xin Zhang 等 8 人

论文原文见 [arXiv](https://arxiv.org/abs/2510.25694)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2510.25694)

> 软件工程智能体在真实仓库中常因环境配置失败而中断，但现有基准仅报告端到端构建成功率，无法定位智能体在规划、感知、反馈或行动哪个环节失效。本文通过向高质量仓库的 README 注入受控错误并验证其有效性，构建了首个支持过程级轨迹评估的环境配置基准。该框架填补了配置能力诊断的空白，但其合成错误分布与真实长尾依赖冲突的覆盖度存疑。

## 研究背景

当智能体尝试在 Docker 容器中复现 GitHub 仓库的运行环境时，它首先面临的是依赖解析与版本兼容性的不确定性。这种不确定性导致构建脚本频繁报错，而错误往往隐藏在多轮交互的中间状态中，而非最终输出。为量化智能体处理此类错误的细粒度能力，需将“环境配置”从黑盒任务拆解为可观测的认知阶段：规划（Planning）、感知（Perception）、反馈（Feedback）与行动（Action）。

现有环境配置基准如 INSTALLAMATIC 和 EnvBench 仅以“构建成功且测试通过”作为唯一指标，这种端到端评估掩盖了智能体在轨迹中的具体失效点。例如，智能体可能正确识别了版本冲突，却未能生成有效的修复命令，最终导致构建失败，但传统指标无法区分这是感知缺陷还是行动缺陷。这种诊断盲区阻碍了针对特定能力短板的优化。本文切入点在于通过受控错误注入，将环境配置任务转化为可定位、可归因的过程级评估问题，从而揭示智能体在配置轨迹中的真实能力边界。

## 核心方法

### 方法参照系

通用软件工程智能体通常遵循“读取 Issue-生成补丁-执行测试”的流程，其评估核心是补丁的正确性。本文问题与该通用流程的关键差异在于：任务前置为“环境配置”，且输入是包含人为错误的 README 而非 Issue，评估对象从代码补丁扩展为包含错误诊断与修复策略的执行轨迹。

### 受控错误注入与有效性验证

传统基准依赖真实仓库中自然存在的配置错误，但此类数据稀缺且标注成本高。本文创新在于将原本正确的 README 作为真值，利用 LLM 注入特定类型的错误，并通过自动化管道验证错误的“有效性”。有效性定义为：遵循错误 README 会导致构建失败，而修复该错误后构建能继续推进。这一设计解决了真实数据不可控的问题，确保了每个任务实例都有明确的错误标签和修复路径。

$$
\text{Valid}(e) = \begin{cases}
1 & \text{if } \text{Build}(\text{README}_e) = \text{Fail} \land \text{Build}(\text{README}_{e \to \text{fix}}) = \text{Pass} \\
0 & \text{otherwise}
\end{cases}
$$

该公式表明，只有当错误确实阻断构建且修复后能恢复构建时，该错误实例才被保留，从而过滤掉无效或自修复的错误。

### 过程级轨迹评估协议

在智能体执行配置任务后，本文从轨迹中提取错误类型判断、错误描述、修复建议及最终 Shell 脚本。评估分为两部分：一是过程级诊断，将预测的错误类型与描述与黄金答案 JSON 对比，计算精确率、召回率和 F1 值；二是端到端可执行性，在 Docker 中运行最终脚本，检查构建与测试是否通过。这种双轨评估使得研究者能区分“诊断正确但修复失败”与“诊断错误”两种不同的失效模式，为智能体优化提供细粒度反馈。

## 实验评估

实验在自建 EnConda-Bench 上进行，包含 4,201 个 README 实例，覆盖 323 个仓库。基线涵盖 Zero-shot LLMs（如 GPT-4.1）、通用智能体（OpenHands + DeepSeek-V3）及专用配置智能体（Repo2Run + Claude-4）。

| 方法 | F1 Score | Description Acc. | Fix Acc. | Pass@1 |
|---|---|---|---|---|
| GPT-4.1 (Zero-shot) | 48.8 | - | - | - |
| OpenHands + DeepSeek-V3 | 58.7 | 51.9 | 33.8 | 9.1 |
| Repo2Run + Claude-4 | 60.6 | 52.2 | 47.3 | 22.9 |

Repo2Run + Claude-4 在 F1 和 Pass@1 上均领先，但其 Fix Acc.（47.3%）与 Pass@1（22.9%）之间存在显著差距，表明即使诊断正确，智能体仍难以将反馈转化为有效的执行动作。这一发现揭示了当前智能体在“反馈-行动”转换环节的瓶颈，而非单纯的感知能力不足。

消融分析显示，Zero-shot LLMs 具有高召回率但低精确率（GPT-4.1 召回率 90.6%，精确率 33.4%），说明模型倾向于过度报告错误。相比之下，智能体框架通过迭代交互提升了精确率，但牺牲了部分召回率。这种权衡表明，过程级评估能揭示不同架构在错误定位策略上的差异，而端到端指标无法捕捉此细节。

评估边界方面，本文未报告计算效率指标，且合成错误分布可能偏离真实长尾依赖冲突。代码与数据已开源，但 Docker 镜像的固定版本可能限制跨平台复现性。

## 关联研究分析

从问题动机看，本文与 MEnvAgent 等基于检索增强的配置方法形成互补。MEnvAgent 聚焦于通过检索历史配置解决依赖解析问题，而 EnConda-Bench 聚焦于评估智能体在已知错误下的诊断与修复能力。两者差异源于任务定义：前者是“从零构建”，后者是“纠错构建”。这种差异暗示，检索增强可能提升构建成功率，但未必能提升智能体对错误类型的细粒度分类能力，因为检索提供的是解决方案而非诊断逻辑。

从方法设计看，本文与 SWE-agent 等通用 SWE 智能体存在框架差异。SWE-agent 依赖 Agent-Computer Interface 进行多轮交互，其评估核心是 Issue 解决率；而 EnConda-Bench 将交互限制在环境配置子任务中，并引入过程级指标。这种差异源于评估目标：SWE-agent 追求端到端任务完成，而 EnConda-Bench 追求能力诊断。若将 EnConda-Bench 的过程级指标应用于 SWE-agent，可能揭示其在环境配置阶段的特定短板，但论文未进行此类交叉评估，导致无法判断过程级优化是否直接提升整体 SWE 任务性能。

## 总结

本文核心矛盾在于环境配置基准缺乏过程级诊断能力，导致无法定位智能体失效环节。其切入点是通过受控错误注入与自动化验证，构建可归因的评估框架。实验证明，专用智能体 Repo2Run + Claude-4 虽在 F1 上达到 60.6%，但 Pass@1 仅 22.9%，暴露了反馈到行动转换的瓶颈。本文边界在于合成错误分布可能未覆盖真实长尾依赖冲突，且未评估过程级优化对整体 SWE 任务的影响。当智能体在过程级指标上表现优异但端到端成功率仍低时，是否意味着存在未被现有指标捕捉的隐性失效模式？
