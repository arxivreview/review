作者：Jialin Lu、Kye Emond、Kaiyu Yang 等 6 人

> 自动形式化领域长期面临“编译通过但语义错误”的困境，而检索增强生成（Retrieval-Augmented Generation, RAG）作为缓解手段，其核心瓶颈在于现有引擎优化的是机器生成的中立描述，而非数学家带有特定视角的真实提问。本文指出这种“领域差距”导致检索结果与用户意图错位，提出通过反向合成模拟用户意图的查询来对齐分布。Lean Finder 采用对比学习与直接偏好优化（Direct Preference Optimization, DPO）两阶段训练，在真实用户查询上实现了 81.6% 的偏好率，显著优于基线，但其对复杂证明生成的增益有限，揭示了检索与推理能力的解耦边界。

## 研究背景

交互式定理证明器 Lean 及其社区库 mathlib4 包含超过 230k 个定理和 110k 个定义，其规模远超 Python（89 个内置函数）或 C++ 标准库（105 个头文件）。在如此庞大的代码库中定位正确的引理是形式化工作的首要痛点，现有工具如 `#find` 或 Loogle 依赖精确名称匹配，在命名约定漂移或示例稀疏时频繁失效。尽管基于大语言模型（Large Language Model, LLM）的检索引擎通过嵌入非形式化陈述来改进搜索，但它们假设查询来自“中立视角”，忽略了数学家在实际编码中携带的特定动机、抽象层级和上下文偏差。

现有 Lean 检索引擎的核心缺陷在于训练数据分布与真实用户查询分布的不匹配。主流方法如 Lean Search 使用 LLM 对形式化代码进行“非形式化”（Informalization），生成看似中立的自然语言描述，但 PCA 分析显示，这些机器生成的查询在嵌入空间中仅覆盖真实用户查询（来自 Zulip 和 GitHub）的一个子空间。这种分布偏差导致检索系统过度拟合于偏离的分布，无法捕捉数学家“从自身特定视角寻求解释”的真实意图。本文的切入点在于识别并弥合这一领域差距，通过构建基于真实社区讨论语义聚类的合成查询数据集，使检索引擎能够理解并响应用户潜在的意图结构，而非仅进行表面语义匹配。

## 核心方法

### 方法参照系

标准 Lean 检索流程通常将形式化代码转换为自然语言描述，训练嵌入模型以最小化查询与代码间的距离。本文问题与该通用流程的关键差异在于：输入不再是机器生成的中立描述，而是模拟数学家真实提问意图的多样化查询，且训练目标从单纯的语义对齐扩展至用户偏好对齐。

### 用户意图驱动的查询合成

传统检索引擎使用 LLM 直接翻译代码，导致查询分布偏离真实用户行为。本文首先从 Zulip 和 GitHub 收集 693 个真实用户讨论，利用 OpenAI o3 迭代聚类出 5 类语义意图（如“寻找现有代码”、“元编程问题”等）。随后，采用“反向工程”策略：给定一个形式化 Lean 陈述，先由 GPT-4o 判断其适用的意图簇，再针对每个簇合成模拟该意图的自然语言查询。这一设计解决了真实用户查询数据稀缺（仅 693 条）且难以标注精确答案的瓶颈，生成了 582,102 条合成查询，使训练数据分布与真实用户查询在嵌入空间中高度对齐。

### 两阶段训练：对比学习与偏好对齐

第一阶段采用对比学习建立基础检索能力。基于 DeepSeek-Prover-V1.5-RL 7B 模型，提取最后解码层最后隐藏状态作为嵌入，优化对比损失以拉近匹配查询-代码对的距离：

$$ \mathcal{L}_{\text{contrastive}} = -\log \frac{\exp(\text{Sim}(q_i, c_i^+)/\tau)}{\sum_{j \in \mathcal{C}_b} \exp(\text{Sim}(q_i, c_j)/\tau)} $$

其中 $\text{Sim}$ 为余弦相似度，$\tau$ 为温度参数，$\mathcal{C}_b$ 为包含正样本和负样本的批次候选集。该损失函数确保模型在共享嵌入空间中区分相关与不相关的 Lean 陈述。

第二阶段引入直接偏好优化（DPO）以对齐用户偏好。收集 1,154 个偏好三元组 $(q, c^+, c^-)$，其中 $c^+$ 和 $c^-$ 分别为用户或 LLM 判定为“更优”和“较差”的检索结果。DPO 目标函数被适配至检索任务，通过调整相似度分数差值来优化排序：

$$ \mathcal{L}_{\text{DPO}} = -\mathbb{E}_{(q,c^+,c^-) \sim P} \left[ \log \sigma \left( \beta \left( \text{Sim}_\theta(q, c^+) - \text{Sim}_\theta(q, c^-) \right) - \left( \text{Sim}_{\theta_{\text{ref}}}(q, c^+) - \text{Sim}_{\theta_{\text{ref}}}(q, c^-) \right) \right) \right] $$

其中 $\sigma$ 为 sigmoid 函数，$\beta$ 控制模型偏离参考策略的程度。此阶段将检索从“语义相似”提升至“用户有用”，解决了纯对比学习无法捕捉细微偏好差异的问题。

## 实验评估

实验在 MiniF2F、ProofNet 和 PutnamBench 上进行，基线包括 Lean Search、GPT-4o、Qwen3-Embedding-8B 和 Lean Explore。Lean Finder 在检索性能上全面领先，尤其在用户意图对齐方面表现突出。

| 模型 | Informalized Statement R@1 | Synthetic User Query R@1 | Augmented Statement R@1 | User Study Top-3 (%) |
| :--- | :--- | :--- | :--- | :--- |
| **Lean Finder** | **64.2** | **54.4** | **82.7** | **81.6** |
| Lean Search | 49.2 | 47.1 | 59.2 | 56.9 |
| GPT-4o (full name) | 14.8 | 13.6 | 39.7 | 54.1 |
| Qwen3-Embedding-8B | 57.7 | 41.2 | 76.2 | — |

在真实用户查询的 LMArena 风格测试中，Lean Finder 获得 81.6% 的 Top-3 偏好率，显著高于 Lean Search 的 56.9% 和 GPT-4o 的 54.1%。消融实验显示，移除 DPO 后，Top-3 偏好率从 81.6% 降至 76.7%，而移除合成用户查询数据则降至 62.9%，表明用户意图合成数据对偏好对齐的贡献大于 DPO 本身。然而，在集成至 Goedel Prover 等证明生成器时，MiniF2F 准确率仅从 57.7% 提升至 58.2%，PutnamBench 上无显著提升（7 vs 7），表明检索增益在复杂推理任务中边际化。

评估边界方面，用户研究仅涉及 5 名参与者和 128 个查询，样本量较小可能影响统计显著性。此外，GPT-4o 基线被限制为仅生成完整名称以避免幻觉，这可能低估了其作为生成式检索器的潜在能力。代码已开源，但训练数据中的合成查询生成依赖 GPT-4o，存在对特定 LLM 分布的依赖风险。

## 关联研究分析

从问题动机看，Lean Finder 与 DRIFT（Zhang et al., 2025）同属检索增强路线，但 DRIFT 聚焦于分解复杂陈述以定位依赖前提，而 Lean Finder 聚焦于模拟用户视角以对齐查询分布。DRIFT 的分解策略旨在解决“隐式前提识别”问题，而 Lean Finder 的意图聚类旨在解决“查询-代码语义错位”问题。两者在依赖解析策略上互补：DRIFT 通过子查询分解扩大检索范围，Lean Finder 通过意图模拟提高检索精度。然而，DRIFT 未考虑用户查询的分布偏差，其检索结果可能仍受限于机器生成的中立描述，这在处理带有特定上下文的真实用户查询时可能失效。

从方法设计看，Lean Finder 与 MathlibLemma（Liu et al., 2026）均涉及 Mathlib 挖掘，但 MathlibLemma 侧重合成新引理以填补库中结构缺口，而 Lean Finder 侧重检索现有引理以辅助证明。MathlibLemma 的“民间挖掘”任务假设库中存在未形式化的引理，而 Lean Finder 假设库中已有足够多的引理，问题在于如何找到它们。这一差异源于任务特性：MathlibLemma 针对库的完整性，Lean Finder 针对库的可访问性。若库中缺乏所需引理，Lean Finder 的检索能力将受限，而 MathlibLemma 的合成能力可能更关键。论文未探讨两者结合的可能性，即通过合成新引理来扩展检索空间，这可能是未来提升复杂证明检索成功率的方向。

## 总结

Lean Finder 旨在解决 Lean 检索引擎中机器生成查询与真实用户意图之间的分布偏差问题。现有方法如 Lean Search 依赖中立非形式化描述，无法捕捉数学家特定视角的提问方式，导致检索结果与用户偏好错位。本文通过反向合成模拟用户意图的查询，并结合对比学习与 DPO 两阶段训练，实现了检索与用户偏好的对齐。实验表明，Lean Finder 在真实用户查询上获得 81.6% 的偏好率，显著优于基线，但在复杂证明生成任务中增益有限，仅提升 0.5% 的准确率。这一结果揭示了检索增强在复杂推理任务中的局限性：当证明生成器本身能力不足时，更精准的检索无法弥补推理能力的缺陷。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
