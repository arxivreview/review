# ICLR2026最新论文 ｜Towards Reliable Benchmarking: A Contamination Free, Controllable Evaluation Framework for Multi Step LLM Function Calling ｜函数调用基准的污染规避与难度正交控制

作者：Seiji Maekawa、Jackson Hassell、Pouya Pezeshkpour 等 5 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_8735413)

> 工具增强大语言模型（Tool-Augmented LLMs, TaLMs）的评估长期受困于静态基准的数据污染与难度维度混杂，导致无法区分模型的真实推理能力与记忆效应。现有基准如 BFCLv4 和 ToolBench 缺乏对函数依赖深度及无关函数干扰的细粒度控制，且公开问答对易被预训练语料覆盖。FuncBenchGen 通过将多步函数调用形式化为有向无环图（DAG）遍历问题，在评估时实时生成合成任务，实现了难度因子的正交解耦。该框架揭示了长序列推理与状态追踪的脆弱性，但其合成任务与真实 API 分布的保真度尚未得到验证。

## 研究背景

当 LLM 执行多步函数调用时，它必须从函数签名中推断依赖关系并维护中间变量状态。这一过程涉及两个核心概念：函数依赖深度（Dependency Depth），即从输入变量到目标变量所需的最长调用链长度；以及无关函数干扰（Irrelevant Function Interference），指那些类型兼容但不参与最终解的函数对模型决策的负面影响。依赖深度决定了规划的前瞻性要求，而无关函数干扰则考验模型在噪声中筛选有效路径的能力。

工具调用评估领域的主流路线是构建静态 API 集合，如 API-Bank 和 BFCLv4。这些基准面临双重瓶颈：一是数据污染，公开的任务-答案对可能出现在预训练数据或测试时网络搜索中，导致模型通过记忆而非推理得分；二是难度混杂，现有基准仅能控制所需函数数量，无法独立调节依赖深度和无关函数的拓扑连接方式。这使得实验结果难以归因于特定能力缺陷。FuncBenchGen 的切入点在于将任务生成与评估解耦，通过图结构参数化实现污染-free 与难度可控的统一。

## 核心方法

### 方法参照系

动态基准生成框架（如 LiveBench）通常通过从最新来源提取或改写文本任务来规避污染，但缺乏对任务内部结构的细粒度控制。FuncBenchGen 的关键差异在于将任务结构显式建模为图论对象，而非仅处理文本表面形式，从而实现了难度维度的正交控制。

### DAG 形式化与图结构生成

传统基准将函数调用视为序列预测，无法独立控制依赖深度。FuncBenchGen 将多步函数调用形式化为 DAG 遍历问题，其中节点代表函数，边代表依赖关系。设计动机是解决静态基准中难度维度混杂的问题，使研究者能单独隔离依赖深度对性能的影响。框架通过两阶段生成图结构：首先创建长度为 $d$ 的核心节点序列以确保存在从输入到目标的有效路径，然后随机添加剩余核心节点并保证无环性。

$$
G = (F, E), \quad (f_i, f_j) \in E \iff f_j \text{ consumes output of } f_i
$$

该公式定义了函数依赖图，其中边 $(f_i, f_j)$ 表示函数 $f_j$ 的输入依赖于函数 $f_i$ 的输出。这种形式化允许通过调整 $d$ 和核心节点数 $n_{core}$ 独立控制任务复杂度，而无需修改函数逻辑本身。

### 无关函数拓扑控制与污染规避

现有基准无法区分无关函数是“连接”还是“断开”于解路径，导致干扰效应不可控。FuncBenchGen 引入连接无关节点（CINs）和断开无关节点（DINs）的概念，CINs 与核心节点共享类型兼容变量，DINs 则完全隔离。设计动机是量化不同类型干扰对模型状态追踪的影响，同时通过随机生成函数名和变量类型确保评估时生成，从源头切断预训练数据泄露路径。

$$
\text{CIN}_k \sim \text{Uniform}(\{f \in F_{core} \mid \text{type}(f_{out}) = \text{type}(f_{in})\})
$$

该过程随机选择核心节点作为 CIN 的父节点，确保无关函数在类型上与解路径兼容，从而模拟真实场景中“看似相关实则无关”的 API 干扰。这种拓扑控制使得实验能精确分离“类型匹配”与“逻辑依赖”对模型决策的影响。

## 实验评估

实验在 7 个 SOTA 模型上进行，核心节点数设为 {5, 10, 20}，无关节点数设为 {0, 10, 20, 40}，每种配置生成 5 个随机图。基线覆盖推理优化模型（GPT-5, Gemini-2.5-Pro）和通用模型（GPT-4.1），但未对比其他动态基准生成框架（如 LiveBench）在相同任务上的表现，限制了跨框架的可比性。

| 模型 | 5 核心节点成功率 | 10 核心节点成功率 | 20 核心节点成功率 |
|---|---|---|---|
| GPT-5 | 72.5% | 38.2% | 15.0% |
| Gemini-2.5-Pro | 46.5% | 14.4% | 6.0% |
| GPT-4.1 | 12.0% | 2.2% | 0.0% |

GPT-5 在 5 核心节点下达到 72.5% 成功率，但随序列长度增加急剧下降至 15.0%，表明长序列规划是主要瓶颈。无关函数分析显示，CINs 对所有模型性能造成最严重损害，而 DINs 对 GPT-5 反而有轻微正向影响，暗示其可能通过增加决策复杂度促使模型更谨慎。

消融实验聚焦于依赖深度与无关函数类型。当依赖深度从 1 增加到 8 时，GPT-5 成功率从近 90% 降至不足 30%，验证了深度对规划能力的决定性影响。失败类型分析显示，“值未知”（Value Not Yet Known）占 GPT-5 错误的 79.6%，表明模型主要失败于状态追踪而非函数选择。提出的缓解策略——在每步重新陈述先前变量值——将 GPT-5 成功率从 62.5% 提升至 81.3%，证实了状态追踪脆弱性是可修复的。

评估边界方面，指标仅包含成功率和平均调用数，缺乏对调用效率的细粒度分析（如冗余调用比例）。协议局限在于合成函数逻辑过于简单（仅返回正确值或随机错误），未模拟真实 API 的复杂错误处理。可复现性方面，代码已开源，但随机种子和具体图生成算法细节未在正文中完全披露，可能影响结果复现。

## 关联研究分析

从问题动机看，FuncBenchGen 与 LiveBench 同属动态基准生成路线，但 LiveBench 侧重多领域文本任务的实时刷新，而 FuncBenchGen 聚焦工具调用垂直领域的结构化控制。差异根源在于任务特性：文本任务的污染主要源于表面形式记忆，可通过改写规避；而工具调用任务的污染源于逻辑依赖记忆，需通过图结构随机化规避。FuncBenchGen 的 DAG 形式化是否限制了任务对非结构化、模糊依赖关系的覆盖能力，论文未给出回答。

从方法设计看，FuncBenchGen 与 CoreEval 均强调抗污染，但 CoreEval 依赖真实数据重写，FuncBenchGen 依赖纯合成生成。CoreEval 的优势在于保真度高，但成本高昂且难以控制难度；FuncBenchGen 的优势在于可控性强，但缺乏真实 API 分布的统计特性。合成任务上的模型排名是否与真实 API 调用基准（如 BFCL）排名一致，是验证该框架实用性的关键问题。

## 总结

FuncBenchGen 解决了工具调用评估中污染与难度混杂的核心矛盾，通过 DAG 形式化实现了难度因子的正交控制。该框架证明了推理优化模型在长序列规划上的显著瓶颈，GPT-5 在 20 核心节点下成功率仅 15.0%，且状态追踪失败占错误的 79.6%。其边界在于合成函数逻辑的简化假设，未模拟真实 API 的复杂错误处理与异步调用特性。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
