# ICLR2026最新论文 ｜EDITBENCH: EVALUATING LLM ABILITIES TO PERFORM REAL-WORLD INSTRUCTED CODE EDITS ｜真实场景指令式代码编辑基准

研究机构：美国卡内基梅隆大学

作者：Wayne Chi、Valerie Chen、Ryan Shar 等 11 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_58490788)

> 现有代码生成基准多依赖静态、人工编写的题目，无法反映开发者在IDE中通过自然语言指令修改局部代码的真实交互模式，且缺乏对高亮代码、光标位置等上下文信息的评估。本文通过开发VS Code插件收集近500名用户的真实编辑日志，构建了包含540道题目的EditBench，首次将指令、代码上下文、高亮区域和光标位置作为联合输入进行评测。该基准揭示了当前模型在真实编辑任务上的显著短板，但仅覆盖Python和JavaScript两种编程语言，且依赖人工构建的测试用例，其泛化边界尚存疑。

## 研究背景

当开发者在IDE中选中一段代码并输入“修复这个错误”时，模型需要解析模糊的自然语言指令，同时理解被高亮的代码片段、光标位置以及整个文件的上下文。这种交互模式被称为指令式代码编辑（Instructed Code Editing），它不同于从零生成代码，也不同于简单的自动补全，而是要求模型在复杂、多模态的IDE上下文中执行局部修改。

主流代码评估基准如HumanEval和MBPP主要关注函数级代码生成，其题目多为面试风格或竞赛题，存在数据污染和任务简化问题。针对代码编辑的现有基准如CanItEdit和Aider Polyglot，虽然引入了编辑任务，但数据源仍依赖标注者编写或LeetCode题目，指令格式模板化，且缺乏对真实开发环境中上下文依赖性的捕捉。SWE-bench虽引入了仓库级真实Issue，但侧重于多文件代理式工作流，未聚焦于单文件内基于IDE交互的细粒度编辑。本文的切入点在于利用真实用户行为数据，构建一个包含多语言、多上下文特征且指令多样化的编辑基准，以填补静态基准与仓库级基准之间的空白。

## 核心方法

### 方法参照系

代码编辑评估的通用流程通常包括：定义编辑任务、提供代码上下文、生成修改后的代码、通过单元测试验证正确性。本文问题与该通用流程的关键差异在于，输入不再是单一的代码片段和明确指令，而是包含用户模糊指令、完整文件上下文、高亮代码区域和光标位置的复合信息，且数据源来自真实IDE交互而非人工构造。

### 基于IDE日志的数据采集与筛选

传统基准的数据采集依赖标注者编写题目，导致指令格式单一且缺乏真实噪声。本文通过开发一个开源VS Code插件，模拟GitHub Copilot和Cursor的指令式编辑功能，收集用户在实际开发中的编辑请求。对于每次编辑，系统记录用户指令、代码上下文（包括高亮片段、光标位置、前缀和后缀）以及模型响应。设计动机在于解决现有基准指令模板化、缺乏真实用户意图多样性的问题。数据采集后，通过筛选仅保留Python和JavaScript题目，去除相似、琐碎或模糊的问题，最终从2672条响应中提炼出470个有趣且具挑战性的问题。这一过程确保了基准反映真实开发场景中的复杂性和多样性，而非理想化的测试环境。

### 多上下文感知的测试框架构建

原始IDE数据不包含测试用例，直接用于评估不可行。本文构建了一个包含环境设置和测试用例的测试框架（Test Harness）。设计动机在于解决真实数据中用户意图模糊、难以直接验证的问题。测试框架的构建由五名经验丰富的程序员完成，他们根据用户指令、代码文件、高亮片段和光标位置设计测试用例，确保测试既符合用户意图又具有泛化性。对于仍过于模糊的问题，标注者将其移除。此外，使用GPT-4o和Sonnet 3.7生成示例解决方案以辅助标注，并利用编码代理设置测试环境。这一创新使得基准能够评估模型在整合多源上下文信息时的意图解析能力，而非仅依赖指令文本。

$$
\text{Pass@1} = \frac{1}{N} \sum_{i=1}^{N} \mathbb{1}[\text{Code}_i \text{ passes all tests}]
$$

该公式定义了评估指标，即模型生成的代码通过所有单元测试的比例，确保了评估的客观性和可复现性。

## 实验评估

实验在EditBench上评估了40个开源和闭源大语言模型，包括GPT、Qwen、Llama、Mistral等家族。基线覆盖广泛，但缺少针对编辑任务专用微调模型的对比。主结果显示，仅claude-sonnet-4一个模型的pass@1超过60%，达到66.67%，表明EditBench对当前SOTA模型仍具挑战性。闭源模型普遍优于开源模型，前15名中仅4个为开源模型，其中glm-4.6表现最佳，pass@1为56.48%。

| 模型 | Pass@1 (%) |
| :--- | :--- |
| claude-sonnet-4 | 66.67 |
| glm-4.6 | 56.48 |
| deepseek-chat-v3.1 | 64.81 |
| kimi-k2-0905 | 54.26 |
| o3-mini | 51.48 |

消融实验揭示了上下文信息对性能的影响。添加高亮代码使5/7的模型任务成功率提升，平均提升约2.4%；而添加光标位置导致结果混合，部分模型性能下降。例如，qwen3-coder在添加光标后性能下降2.59%。这一发现表明，高亮代码是关键的意图线索，而光标位置可能引入噪声或干扰。此外，模型在不同编辑类别上表现差异显著，bug fixing平均52.2%，而feature addition仅39.6%，显示模型在创造性修改任务上更弱。

评估边界方面，EditBench仅覆盖Python和JavaScript，未涉及知识库强调的低资源语言泛化。测试用例由人工构建，可能存在主观偏差。代码已开源，但插件数据采集的隐私控制和IRB审批细节未在正文中完全展开。

## 关联研究分析

从问题动机看，EditBench与SWE-bench同属真实数据驱动，但SWE-bench聚焦多文件代理式工作流，而EditBench聚焦单文件IDE交互。根源在于任务特性：SWE-bench需要全局上下文和多步推理，而EditBench需要局部上下文和意图解析。EditBench未探索跨文件依赖，这是否是真实编辑场景的盲区，论文未给出回答。

从方法设计看，EditBench与Aider Polyglot均评估代码编辑，但Aider Polyglot依赖LeetCode题目，指令模板化，而EditBench使用真实用户指令，包含高亮和光标。差异源于数据源：Aider Polyglot追求标准化，EditBench追求真实性。EditBench与Aider Polyglot弱相关，证明真实数据捕捉了独特任务分布。然而，EditBench的多语言支持通过GPT-4o翻译实现，可能引入翻译偏差，论文未量化这一影响。

## 总结

本文要解决的核心矛盾是静态基准无法反映真实IDE交互中的指令模糊性和上下文依赖性。本文抓住的切入点是利用VS Code插件收集真实用户编辑日志，构建包含多上下文特征的基准。本文做了什么：开发了EditBench，包含540道题目，评估40个模型。证明了什么：仅claude-sonnet-4超过60% pass@1，高亮代码显著提升性能。本文的边界在于仅覆盖Python和JavaScript，测试用例依赖人工构建，且多语言翻译可能引入偏差。当支持集增大到更多编程语言时，真实用户指令的多样性是否足以支撑跨语言泛化，论文未给出回答。
