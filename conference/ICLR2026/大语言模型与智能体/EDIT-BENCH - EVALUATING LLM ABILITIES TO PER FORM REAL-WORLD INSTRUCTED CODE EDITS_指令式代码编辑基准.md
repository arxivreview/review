# ICLR2026最新论文 ｜EDIT-BENCH: EVALUATING LLM ABILITIES TO PER FORM REAL-WORLD INSTRUCTED CODE EDITS ｜指令式代码编辑基准

研究机构：美国卡内基梅隆大学

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_839682)

> 指令式代码编辑要求模型根据自然语言指令修改现有代码片段，但现有基准多依赖人工标注或竞赛题，无法反映真实IDE交互中的模糊指令与长上下文依赖。EDIT-Bench通过VSCode扩展收集500名开发者的真实编辑日志，构建了包含540个多语言、多上下文维度的测试集。该基准揭示了模型在整合高亮代码与光标位置时的性能波动，以及闭源与开源模型在真实编辑任务上的显著差距。其价值在于填补了真实交互模式评估的空白，但测试用例由人工构建，可能引入主观偏差，且仅覆盖Python与Javascript。

## 研究背景

当开发者在IDE中选中一段代码并输入“修复这个错误”时，模型需要同时解析模糊的自然语言指令、理解高亮区域的代码语义、定位光标位置以推断修改范围。这种多模态上下文整合能力是传统代码生成任务所不具备的，因为后者通常假设输入是完整的函数签名或明确的算法描述。指令式代码编辑的核心难点在于指令的歧义性：同一句“优化性能”可能指向算法复杂度降低、内存占用减少或I/O操作合并，模型必须依赖代码上下文中的注释、变量命名和结构线索来消解歧义。

现有代码评估体系主要围绕功能正确性构建，HumanEval和MBPP等静态基准因数据污染和任务简化已无法区分前沿模型性能。针对代码编辑的早期工作如CanItEdit和Aider Polyglot虽引入了编辑任务，但数据源仍局限于标注者编写的模板化问题或LeetCode竞赛题，缺乏真实开发场景中的多样性与复杂性。SWE-bench虽采用真实GitHub Issue，但聚焦于多文件仓库级修复，未覆盖单文件、短交互的IDE编辑场景。EDIT-Bench的切入点在于利用真实用户日志构建基准，将评估对象从“生成正确代码”转向“在真实IDE约束下执行精准编辑”，从而捕捉模型在上下文整合与指令消解上的真实能力。

## 核心方法

### 方法参照系

代码编辑评估的通用流程通常包括：定义编辑任务、构建测试用例、执行模型生成并验证功能正确性。本文问题与该通用流程的关键差异在于输入的多模态性：传统基准仅提供指令与代码文本，而EDIT-Bench要求模型同时处理指令、完整代码文件、高亮区域和光标位置四个维度的信息，且数据源为真实用户而非人工构造。

### 真实数据收集与筛选

数据收集环节通常依赖标注者编写任务，本文改为开发VSCode扩展采集真实用户编辑日志。用户高亮代码片段并输入自然语言指令，系统记录指令、代码上下文（含高亮区域、光标位置、前后缀）及模型响应。从458名用户收集的2672条响应中，筛选出Python和Javascript任务，剔除相似、琐碎或风格化问题，最终保留470个有效问题。这一设计解决了人工标注数据缺乏真实交互模式的问题，使指令分布更贴近实际开发场景，如直接粘贴错误堆栈或简短描述“fix this”。

$$
P_{\text{filtered}} = \{ p \in P_{\text{raw}} \mid \text{lang}(p) \in \{\text{Python, JS}\} \land \text{sim}(p, P_{\text{raw}}) < \tau \land \text{complexity}(p) > \epsilon \}
$$

该公式表示筛选后的问题集，其中$\text{sim}$衡量问题相似度，$\text{complexity}$排除琐碎任务，确保保留具有挑战性的真实编辑场景。

### 多语言扩展与测试构建

多语言扩展环节通常通过机器翻译实现，本文采用GPT-4o将核心问题翻译为5种自然语言，并由母语者验证。测试构建环节通常由人工编写单元测试，本文组建5人团队，基于指令、代码、高亮区域和光标位置设计可泛化的测试用例，并使用编码代理自动配置环境。这一设计解决了真实数据缺乏测试用例的问题，同时通过人工审核确保测试符合用户意图，避免代理生成的模式匹配式测试。

$$
T_{\text{final}} = \{ t \in T_{\text{gen}} \mid \text{intent}(t, i) = \text{true} \land \text{pii}(t) = \text{false} \land \text{review}(t) = \text{pass} \}
$$

该公式表示最终测试集，其中$\text{intent}$验证测试是否符合用户指令意图，$\text{pii}$排除个人身份信息，$\text{review}$确保通过二次人工审核。

## 实验评估

实验在540个EDIT-Bench问题上评估40个LLM，采用pass@1指标，将问题分为易（≤20个模型解决）和难（>20个模型解决）两组。基线覆盖GPT、Qwen、Llama、Mistral、Sonnet等主流模型家族，但未包含针对编辑任务微调的专用模型。主结果显示，仅claude-sonnet-4的pass@1超过60%（66.67%），闭源模型整体优于开源模型，其中glm-4.6以56.48%位列开源模型第一。

| 模型 | Pass@1 (%) |
|---|---|
| claude-sonnet-4 | 66.67 |
| glm-4.6 | 56.48 |
| deepseek-chat-v3.1 | 56.48 |
| kimi-k2-0905 | 56.48 |

消融实验显示，添加高亮代码使5/7模型性能提升（最大+3.71%），但添加光标位置导致混合结果（最大-8.15%）。这表明高亮代码是消解指令歧义的关键线索，而光标位置可能引入噪声或干扰模型对代码结构的理解。

| 模型 | Code Only | +Highlight | +Cursor |
|---|---|---|---|
| claude-sonnet-4 | 62.41 | 64.81 (+2.40) | 64.26 (+1.85) |
| o3-mini | 52.59 | 52.96 (+0.37) | 52.41 (-0.18) |
| qwen3-coder | 56.48 | 53.89 (-2.59) | 53.89 (-2.59) |

评估边界方面，pass@1指标未考虑代码质量或可维护性，仅验证功能正确性。测试用例由人工构建，可能引入主观偏差，且仅覆盖Python和Javascript，未评估其他编程语言。代码开源，但测试用例生成过程未完全自动化，复现性受限于人工审核环节。

## 关联研究分析

从问题动机看，EDIT-Bench与SWE-bench均基于真实数据，但SWE-bench聚焦多文件仓库级修复，强调代理式工作流，而EDIT-Bench聚焦单文件IDE编辑，强调上下文整合。这一差异源于任务粒度：SWE-bench的Issue通常涉及跨文件依赖，需全局理解；EDIT-Bench的编辑任务局部性强，需精准定位。SWE-bench未覆盖IDE特有的高亮与光标信息，导致其无法评估模型在短交互场景下的消歧能力。

从方法设计看，EDIT-Bench与Aider Polyglot同为编辑基准，但Aider Polyglot使用LeetCode式题目，指令明确且上下文短，而EDIT-Bench使用真实用户日志，指令模糊且上下文长。两者相关性弱（r=0.24），表明EDIT-Bench捕捉了Aider Polyglot未覆盖的能力维度。Aider Polyglot的测试用例由人工编写，可能更偏向算法优化，而EDIT-Bench的测试用例基于真实用户意图，更贴近实际开发需求。

## 总结

EDIT-Bench要解决的核心矛盾是真实IDE编辑场景的评估缺失，现有基准因数据源人工化或任务简化无法反映模型在模糊指令与长上下文下的真实能力。本文通过VSCode扩展收集真实用户日志，构建了包含多语言、多上下文维度的测试集，证明了模型在整合高亮代码与光标位置时的性能波动。核心数字显示，最佳模型claude-sonnet-4的pass@1为66.67%，仅1/40模型超过60%。本文的边界在于测试用例由人工构建，可能引入主观偏差，且仅覆盖Python和Javascript。当测试用例由自动化代理生成时，其质量与人工构建的测试用例相比是否一致，论文未给出回答。
