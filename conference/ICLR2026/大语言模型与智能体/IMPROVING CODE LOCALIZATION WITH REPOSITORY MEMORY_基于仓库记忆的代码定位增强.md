# ICLR2026最新论文 ｜IMPROVING CODE LOCALIZATION WITH REPOSITORY MEMORY ｜基于仓库记忆的代码定位增强

研究机构：美国俄亥俄州立大学

作者：Boshi Wang、Weijian Xu、Yunsheng Li 等 7 人

论文原文见 [arXiv](https://arxiv.org/abs/2510.01003)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_63260925)

> 仓库级软件工程的代码定位任务要求智能体在海量代码中精准锁定需修改的文件与函数，但现有代理框架普遍将每个问题视为独立谜题，缺乏对仓库历史演化的长期记忆，导致在复杂依赖场景下推理链断裂。本文切入点在于利用仓库提交历史（Commit History）构建非参数化记忆库，通过检索历史补丁与活跃模块摘要为定位提供先验知识。具体做法是扩展LocAgent的工具集，引入基于BM25的提交检索与LLM生成的文件功能摘要查询接口。该方案在SWE-bench-verified上将定位准确率从54.3%提升至76.5%，但其在稀疏历史仓库上的性能退化揭示了记忆机制对数据密度的强依赖，其能否转化为最终问题解决率的提升仍存疑。

## 研究背景

代码定位是仓库级智能体执行Bug修复的首要步骤，其本质是在代码库的有向异构图上进行多跳搜索，以识别与Issue描述相关的实体。这一过程高度依赖对代码结构（如导入、调用、继承关系）的实时解析，但LLM在长轨迹中易陷入循环或丢失关键上下文，导致搜索过早终止。为缓解此问题，智能体需具备类似人类开发者的“专家知识”，即对核心模块功能的缓存理解及对常见Bug模式与修复位置关联的记忆。

现有主流路线分为检索式、代理式与程序式。检索式方法依赖代码嵌入相似度，难以捕捉深层依赖；程序式方法如Agentless（Xia et al., 2025）通过静态提示简化流程，但缺乏动态探索能力；代理式框架如LocAgent（Chen et al., 2025b）通过图导航工具实现迭代交互，是当前SOTA，但其核心局限在于“无状态”——每次任务均从零开始，无法利用仓库的历史演化信息。人类开发者通过长期维护积累了对代码库的语义记忆（如“该模块负责序列化”）和情景记忆（如“上次类似Bug修在writer.py”），这种记忆能显著缩小搜索空间。本文旨在通过挖掘仓库提交历史这一天然结构化数据源，为代理智能体注入此类长期记忆，以突破静态图导航在长程推理中的瓶颈。

## 核心方法

### 方法参照系

本文基于LocAgent的ReAct范式，该框架通过Thought-Act-Observation循环调用图导航工具（SearchEntity, TraverseGraph, RetrieveEntity）进行代码探索。与标准流程的关键差异在于，LocAgent仅依赖实时代码解析，而本文引入离线预计算的仓库记忆模块，将历史提交数据转化为可检索的外部知识库，扩展了智能体的动作空间。

### 情景记忆构建与检索

情景记忆旨在捕获具体历史变更的叙事，解决代理在缺乏先验知识时盲目遍历代码图的问题。构建阶段，系统爬取Issue发生前的提交历史，存储补丁、提交信息及关联Issue，并过滤与当前测试实例文本重叠的数据以防泄漏。检索阶段，智能体通过$SearchCommit(q, k)$工具查询历史，其匹配分数定义为：

$$ Score(c, q) = \sum_{t \in q} IDF(t) \cdot TF(t, c) $$

其中$c$为提交，$q$为查询，$TF$与$IDF$分别为词频与逆文档频率。该公式利用BM25算法处理提交信息的关键词特性，使智能体能通过“migration”、“import”等关键词直接定位相关历史补丁，从而将搜索从全图遍历转向基于历史先验的假设驱动探索。

### 语义记忆构建与检索

语义记忆提供代码库活跃区域的高层功能上下文，弥补情景记忆在抽象层级上的不足。构建阶段，系统分析提交频率识别“热点文件”（Top-k most edited files），利用LLM生成其功能摘要。检索阶段，智能体通过$ViewSummary(f)$获取特定文件摘要，或通过$SearchSummary(q, k)$进行关键词搜索。摘要生成可形式化为：

$$ S_f = LLM(\text{Code}(f), \text{Prompt}_{\text{summary}}) $$

其中$S_f$为文件$f$的功能摘要。这一设计将高频修改文件作为缺陷易发区（基于JiT-SDP领域的代码churn理论），使智能体在探索初期即获得架构级指引，避免在无关或稳定模块中浪费推理步数。

## 实验评估

实验在SWE-bench-verified与SWE-bench-live上进行，基线包括LocAgent、Agentless及CodeRankEmbed。RepoMem在SWE-bench-verified上取得76.5%的Acc@5，较LocAgent的54.3%提升22.2个百分点；在SWE-bench-live上取得66.2%的Acc@5，较LocAgent的71.6%有所下降，但优于Agentless的62.3%。

| 方法 | SWE-bench-verified Acc@5 | SWE-bench-live Acc@5 |
| :--- | :--- | :--- |
| LocAgent | 54.3 | 71.6 |
| Agentless | 45.1 | 67.8 |
| RepoMem | 76.5 | 66.2 |

消融实验显示，仅使用情景记忆（episodic-only）在SWE-bench-verified上达到74.3% Acc@5，仅使用语义记忆（semantic-only）达到72.4%，两者结合达到76.5%，表明两类记忆提供互补信息。检索方法对比中，BM25（LLM tokenizer）在django仓库上取得79.7% Acc@5，显著优于密集检索模型GritLM-7B的73.6%，证实稀疏检索在处理代码实体刚性词汇时的优势。

评估边界方面，本文仅报告定位准确率（Acc@k），未报告最终问题解决率（Resolution Rate），无法直接推断定位提升对端到端修复的贡献。此外，实验未提供代码开源链接，且未报告计算成本的具体分布细节，仅通过散点图定性展示成本方差，可复现性受限。

## 关联研究分析

从问题动机看，RepoMem与SWE-MeM（Gao et al., 2026）同属记忆增强路线，但SWE-MeM侧重小模型在长程任务中的上下文压缩与检索，而RepoMem侧重仓库级静态历史知识的注入。差异根源在于任务粒度：SWE-MeM关注单次任务内的状态维持，RepoMem关注跨任务的历史经验复用。这种差异暗示，当仓库历史稀疏时，RepoMem的性能退化（如“others”组下降13.1%）可能比SWE-MeM更严重，因为前者依赖外部数据密度，后者依赖内部状态管理。

从方法设计看，RepoMem与LocAgent（Chen et al., 2025b）共享图导航框架，但RepoMem引入了非参数化检索接口，而LocAgent依赖参数化LLM进行实时推理。这一设计选择解决了LocAgent在长轨迹中推理链断裂的问题，但引入了检索噪声风险。当检索返回无关信息时，可能污染LLM的上下文，导致性能低于基线。论文未探索动态记忆更新机制，即智能体能否在任务过程中将新发现的修复模式写入记忆，这限制了其在持续演化仓库中的适应性。

## 总结

本文核心矛盾在于代理智能体缺乏长期仓库记忆，导致在复杂依赖场景下定位失败。切入点在于利用提交历史这一天然结构化数据源，构建情景与语义双重记忆库，通过非参数化检索为定位提供先验。方法上扩展LocAgent工具集，引入BM25提交检索与LLM文件摘要查询。实验证明在SWE-bench-verified上Acc@5从54.3%提升至76.5%，但在稀疏历史仓库上性能下降13.1%。边界在于仅评估定位准确率，未验证对最终解决率的贡献，且记忆机制对数据密度敏感。当仓库历史极度稀疏或Issue高度新颖时，记忆检索是否仍能提供有效先验，而非引入噪声干扰，论文未给出回答。
