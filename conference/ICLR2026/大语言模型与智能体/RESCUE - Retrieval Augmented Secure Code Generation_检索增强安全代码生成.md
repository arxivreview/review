# ICLR2026最新论文 ｜RESCUE: Retrieval Augmented Secure Code Generation ｜检索增强安全代码生成

研究机构：美国普渡大学

作者：Jiahao Shi、Tianyi Zhang

论文原文见 [arXiv](https://arxiv.org/abs/2510.18204)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2510.18204)

> 大语言模型（LLM）生成的代码普遍存在安全漏洞，而现有微调或静态分析工具反馈方法存在数据泄露风险或僵化局限，难以灵活注入新知识。RESCUE 提出了一种训练无关的检索增强生成（RAG）框架，通过构建分层安全知识库与多面检索机制，在提升安全性的同时保留模型功能正确性。该方法在四个基准上实现了 SecurePass@1 平均 4.8% 的绝对提升，但其性能高度依赖离线构建的高质量补丁数据，对无明确修复实例的场景适用性存疑。

## 研究背景

当 LLM 生成代码时，安全漏洞往往源于对特定 API 误用或逻辑缺陷，这些风险隐含在任务描述中而非显式给出。传统检索增强生成（RAG）将安全文档视为通用文本进行相似度匹配，无法捕捉这种隐含的安全语义，导致检索结果包含大量无关逻辑，干扰代码生成。为解决此问题，需要一种能主动解析任务安全需求并精准定位修复策略的机制。

LLM 代码安全领域已从单纯的功能正确性评估转向安全-功能联合评估。主流解决路径包括微调（如 SafeCoder）和静态工具反馈（如 Codexity），但前者训练成本高且易牺牲功能性，后者依赖预定义规则且存在评估数据泄露风险。RESCUE 切入 RAG 路线，指出传统 RAG 在安全领域的两大失效点：原始文档噪声大，以及检索器缺乏对 API 模式、漏洞成因等安全维度的感知。

## 核心方法

### 方法参照系

标准 RAG 流程包含离线索引与在线检索两阶段。本文问题与通用 RAG 的关键差异在于：安全代码生成需要同时满足功能约束与安全约束，且安全知识具有层级结构（从通用指南到具体代码片段），单一文本相似度检索无法有效处理这种层级与多面性。

### 混合蒸馏知识库构建

传统 RAG 直接索引原始安全文档，导致无关代码逻辑干扰生成。RESCUE 在离线阶段引入混合蒸馏，结合 LLM 摘要与静态程序分析。首先，利用 LLM 对原始漏洞-修复实例进行自下而上的聚类摘要，提取高层安全指南（Security Guidelines）与漏洞成因（Vulnerability Causes）。其次，针对代码示例，构建程序依赖图（PDG），以补丁修改点为兴趣点执行双向切片，剔除无关逻辑，仅保留与安全修复相关的语句。该设计解决了原始文档中“示例任务逻辑”与“目标任务逻辑”不匹配导致的生成干扰问题。

$$
\text{SlicedCode} = \text{Slice}(\text{PDG}, \text{PointsOfInterest}_{\text{vuln}}, \text{PointsOfInterest}_{\text{secure}})
$$

此公式表示通过程序依赖图切片，基于漏洞与修复代码的兴趣点提取精简的安全代码片段。

### 分层多面检索

传统检索仅基于文本相似度，无法区分 API 误用与逻辑漏洞。RESCUE 设计了两步分层检索。第一步在 CWE（通用弱点枚举）层级，利用漏洞成因分析（VCA）的稠密检索分数与 API 模式的稀疏检索分数（BM25），通过修改的倒数排名融合（RRF）筛选相关漏洞类型。第二步在代码层级，增加代码相似度维度，融合三个维度的分数以定位具体安全代码示例。这种多面融合机制确保了检索结果在语义、API 调用和代码结构上的一致性。

$$
\text{Score}_{\text{RRF}}(d) = \sum_{i \in \{VCA, API, Code\}} \frac{1}{\alpha + r_i(d)} \cdot \mathbb{I}(s_i(d) > \tau_i)
$$

其中 $r_i(d)$ 为文档 $d$ 在第 $i$ 个维度的排名，$s_i(d)$ 为分数，$\tau_i$ 为置信度阈值，$\alpha$ 为平滑参数。该公式通过阈值过滤与排名融合，仅保留高置信度的多面匹配结果。

## 实验评估

实验在 CodeGuard+、HumanEval+、BigCodeBench 和 LiveCodeBench 上进行，对比了 SecCoder、Codexity、SafeCoder、CoSec 和 INDICT 五种基线。基线覆盖了 RAG、工具反馈、微调和约束解码路线，但缺失了近期流行的强化学习（RL）路线方法（如 SecCoderX）。

| 模型 | 方法 | CodeGuard+ SP@1 | CodeGuard+ SR | CodeGuard+ Pass@1 |
| :--- | :--- | :--- | :--- | :--- |
| DeepSeek-Coder-V2-Lite | RESCUE | 65.6 | 72.8 | 87.9 |
| DeepSeek-Coder-V2-Lite | LLM alone | 59.7 | 65.1 | 86.8 |
| Qwen2.5-Coder-7B | RESCUE | 64.8 | 72.1 | 86.2 |
| Qwen2.5-Coder-7B | SafeCoder | 56.5 | 74.0 | 67.7 |
| Llama3.1-8B | RESCUE | 56.2 | 69.7 | 77.6 |
| Llama3.1-8B | INDICT | 52.4 | 69.4 | 54.6 |

RESCUE 在 SecurePass@1（SP@1）上平均提升 4.8%，且保留了 98.7% 的功能正确性。相比之下，INDICT 虽然 SecureRate 较高，但 Pass@1 显著下降，印证了功能-安全权衡的存在。

| 消融设置 | DSC-V2-Lite SP@1 | Qwen-7B SP@1 | Llama-8B SP@1 |
| :--- | :--- | :--- | :--- |
| RESCUE | 65.6 | 64.8 | 56.2 |
| w/o construction | 55.6 | 53.9 | 45.3 |
| w/o slicing | 63.3 | 62.6 | 52.7 |
| w/o guideline | 61.0 | 63.9 | 51.4 |

消融实验表明，移除知识库构建（w/o construction）导致性能大幅下降，证明原始数据噪声的负面影响。程序切片（w/o slicing）的移除也导致 SP@1 下降，且显著减少了输入 Token 数（如 DSC-V2-Lite 从 503 降至 435），验证了切片在提升检索精度与降低计算成本上的双重作用。

评估边界方面，CodeGuard+ 仅包含 94 个场景，样本量较小，统计显著性有限。此外，RESCUE 依赖 SafeCoder 的训练数据构建知识库，存在潜在的数据重叠风险，尽管论文声称通过切片和摘要降低了泄露影响，但未提供严格的去重验证。代码已开源，但超参数（如 RRF 的 $\alpha=60$）的敏感性分析未在正文中详细展开。

## 关联研究分析

从方法设计看，RESCUE 与 SecCoder 同属 RAG 路线，但 SecCoder 仅检索最相似的单一安全代码示例，而 RESCUE 引入了分层结构与多面检索。差异根源在于对“安全相关性”的定义：SecCoder 假设文本相似度等价于安全相关性，而 RESCUE 认为 API 模式与漏洞成因是独立于文本语义的安全维度。这种设计使得 RESCUE 能更精准地定位修复策略，但也增加了离线构建的复杂度。

从问题动机看，RESCUE 与 SafeCoder 等微调方法形成对比。SafeCoder 通过参数更新内化安全知识，而 RESCUE 通过外部检索动态注入。RESCUE 的优势在于零训练成本与知识更新灵活性，但其性能上限受限于知识库的质量与覆盖度。若知识库中缺乏特定漏洞类型的修复实例，RESCUE 的检索将失效，而微调模型可能通过泛化能力应对未见过的漏洞模式。这种依赖外部数据的特性，使得 RESCUE 在长尾漏洞场景下的鲁棒性弱于参数化方法。

## 总结

RESCUE 旨在解决 LLM 代码生成中安全性与功能性的权衡难题，特别是传统 RAG 方法因噪声和语义缺失导致的性能瓶颈。其切入点在于将安全知识结构化，并通过多面检索精准匹配任务需求。方法上，它结合了 LLM 摘要与程序切片构建分层知识库，并设计了基于 RRF 的多面检索机制。实验证明，该方法在 CodeGuard+ 上实现了 SP@1 平均 4.8% 的提升，同时保持了高功能正确性。然而，其性能高度依赖离线构建的高质量补丁数据，且评估基准规模较小。当面对知识库中未覆盖的长尾漏洞类型时，RESCUE 的检索机制是否仍能保持有效的安全引导，论文未给出回答。
