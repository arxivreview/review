# ICLR2026最新论文 ｜HARDTESTGEN: A HIGH-QUALITY RL VERIFIER GENERATION PIPELINE FOR LLM ALGORITHMIC CODING ｜高质量RL验证器生成管道

研究机构：美国卡内基梅隆大学

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_19448995)

> 算法竞赛代码生成中的强化学习（RL）训练依赖结果验证器（Outcome Verifier）提供准确的奖励信号，但现有合成测试用例存在大量假阳性，导致模型学到错误策略。本文指出直接由大语言模型（LLM）生成测试输入难以保证有效性与覆盖度，提出HARDTESTGEN管道，通过LLM生成“生成器程序”而非直接生成输入，结合共识过滤机制合成高质量测试集HARDTESTS。该方法在竞赛编程任务上显著提升了验证精度，并实证了测试质量对RL及拒绝采样（Rejection Sampling）下游性能的决定性影响，但其依赖Oracle程序的前提限制了在无参考解场景下的泛化能力。

## 研究背景

在基于结果的强化学习（RLVR）中，验证器负责判定模型生成的代码是否通过所有测试用例，从而赋予奖励。对于算法竞赛类任务，代码的“正确性”不仅指逻辑无误，更要求时间复杂度满足约束。一个语义正确但算法低效的解（如用 $O(n^2)$ 暴力法解决 $O(n \log n)$ 问题），在随机小数据上可能通过，但在精心构造的边界数据上会超时或错误。这种“伪装错误的解”（well-disguised wrong solution）是静态基准和简单合成测试难以捕捉的盲区。

现有测试合成方法如TACO和CodeT主要依赖LLM直接生成测试输入，导致输入有效性低且分布单一。研究数据显示，APPS基准中60%通过测试的程序实际是错误的，CodeContests中46%的程序语义正确但效率不足。由于人工测试用例多为专有数据无法爬取，合成测试成为必然选择，但其质量直接决定了RL训练信号的信噪比。本文切入点在于：测试用例的有效性不应由LLM直接生成输入来保证，而应通过LLM生成“生成器程序”来间接保证，同时利用多个Oracle程序的一致性来过滤无效输出。

## 核心方法

### 基于生成器程序的测试输入合成

传统LLM测试合成直接提示模型输出测试数据，但模型难以生成大规模、符合复杂约束（如凸多边形坐标）的有效输入。HARDTESTGEN将任务解耦：LLM不直接生成输入，而是生成一个Python函数（生成器），该函数根据问题的数据类型、范围及内在约束返回随机有效输入。这种“生成生成器”的策略确保了输入在格式和逻辑上的有效性。

对于输出类别不平衡的问题（如Yes/No判断），引入分层生成（SPGen）。LLM首先识别输出类别，然后为每个类别生成独立的生成器函数，确保测试集覆盖所有可能的输出分支。其核心逻辑可形式化为：

$$
\mathcal{I}_{SP} = \bigcup_{c \in C} \{ g_c(x) \mid x \sim \mathcal{U} \}
$$

其中 $C$ 为LLM推断的输出类别集合，$g_c$ 为针对类别 $c$ 生成的函数，$\mathcal{U}$ 为均匀分布。这解决了随机生成导致测试集偏向单一输出类别、无法全面验证代码逻辑的失效问题。

### 针对算法复杂度的Hacking测试与共识过滤

针对“伪装错误解”，HARDTESTGEN引入HackGen模块。LLM首先描述几种典型的低效或错误算法（如暴力枚举、忽略边界条件的DFS），然后推导这些算法失效的场景（如链状树导致深度 $d=n$），最后为每个失效场景生成对应的输入生成器。这一过程显式地将“最坏情况”纳入测试分布。

测试输出的正确性通过共识过滤（Consensus Filtering）保证。对于每个问题，收集最多 $n_{oracle}=8$ 个人工编写的Oracle程序。若两个Oracle程序在超过90%的输入上产生等价输出，则视为一致。最终测试集仅保留所有Oracle程序输出一致的输入-输出对。其过滤条件为：

$$
\text{Valid}(x) \iff \frac{|\{ (y_i, y_j) \mid y_i(x) \equiv y_j(x) \}|}{\binom{n_{oracle}}{2}} > 0.9
$$

其中 $\equiv$ 表示语义等价（如集合比较或字符串匹配）。该机制消除了因单个Oracle程序潜在Bug或LLM生成输入无效导致的错误标签，显著提升了验证器的精度。

## 实验评估

实验在AtCoder和Codeforces的1253道问题上进行，候选程序来自Qwen2.5-Coder-7B/14B、GPT-4o及人类提交。基线包括TACO和CodeContests。HARDTESTS在平均精度（Precision）上达到79.21%，较TACO的61%提升18.21个百分点；召回率（Recall）为91.69%，较TACO的78.97%提升12.72个百分点。

| 方法 | Precision (Avg) | Recall (Avg) |
| :--- | :--- | :--- |
| TACO | 61 | 78.97 |
| CodeContests | 51.64 | 85.98 |
| HARDTESTS | 79.21 | 91.69 |

消融实验显示，仅使用LLMGen（HT-L）时精度降至42.42%，加入RPGen/SPGen（HT-L+R/S）后升至64.67%，完整HARDTESTS达到79.21%。这表明基于生成器的输入合成（RPGen/SPGen）和Hacking测试（HackGen）对精度的提升是累积且显著的，其中HackGen对高难度问题（Difficulty 4+）的精度贡献尤为关键，从47.73%提升至55.88%。

在下游任务中，使用HARDTESTS进行RL训练的Qwen3-4B在LiveCodeBench-105上pass@1达到39.42%，pass@10达到64.76%；而使用TACO测试训练的模型pass@1仅为36.95%，pass@10为57.14%。拒绝采样实验同样表明，使用高质量测试过滤的“good 5k”数据集训练后，模型pass@10从56.19%提升至60.00%，而随机采样或错误采样导致性能下降。

评估边界方面，实验仅覆盖C++和Python，且依赖68%问题拥有Oracle程序。每问题测试生成成本为0.23 USD，规模化部署时需考虑API调用开销。代码与数据已开源，但RL训练的具体超参数（如学习率、批大小）未在正文中详细列出，需查阅附录以复现。

## 关联研究分析

从问题动机看，HARDTESTGEN与STGen（Peng et al., 2025）均关注代码效率，但STGen侧重于生成“压力测试”以评估时间复杂度，而HARDTESTGEN侧重于生成“Hacking测试”以区分正确算法与低效算法。STGen的测试可能无法捕捉逻辑错误，而HARDTESTGEN通过结合功能正确性（LLMGen）和效率边界（HackGen），构建了更全面的验证器。这种差异源于任务目标的不同：STGen用于评估，HARDTESTGEN用于RL奖励信号，后者对假阳性（False Positive）的容忍度更低，因为错误的奖励会直接误导策略更新。

从方法设计看，HARDTESTGEN与TACO（Li et al., 2023）的核心区别在于输入生成机制。TACO直接由LLM生成输入，而HARDTESTGEN由LLM生成生成器程序。这一设计解决了LLM直接生成大规模复杂输入时有效性低的问题，但引入了生成器程序本身的正确性风险。虽然通过Oracle共识过滤缓解了输出错误，但生成器程序的逻辑Bug仍可能导致输入分布偏差。相比之下，CodeContests通过变异现有输入来生成测试，避免了LLM生成的不确定性，但受限于原始输入的覆盖度，难以生成全新的边界场景。

## 总结

本文核心矛盾在于RL训练需要高信噪比的奖励信号，而现有合成测试假阳性率高。HARDTESTGEN通过“生成生成器”策略和共识过滤机制，将测试精度提升至79.21%，并实证了高质量测试对RL和拒绝采样的显著增益（pass@10提升7.62个百分点）。其边界在于强依赖Oracle程序的存在，且仅针对算法竞赛类任务。当问题缺乏人工参考解时，共识过滤机制失效，此时如何保证合成测试的可靠性，论文未给出回答。
