# ICLR2026最新论文 ｜RedCodeAgent: AUTOMATIC RED TEAMING AGENT AGAINST DIVERSE CODE AGENTS ｜代码代理自动化红队测试

研究机构：美国芝加哥大学、美国伊利诺伊大学厄巴纳-香槟分校

作者：Chengquan Guo、Chulin Xie、Yu Yang 等 9 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_43583852)

> 代码代理在集成解释器执行代码时，面临静态基准无法覆盖的动态边界风险。现有红队工具依赖人工设计或固定提示优化，难以适应代理的实时演化与执行反馈。本文提出 RedCodeAgent，通过自适应记忆模块与动态工具组合实现自动化漏洞挖掘。该方法在多个代理上显著提升了攻击成功率，但其对底层大语言模型推理能力的依赖及防御机制的局限性仍存疑。

## 研究背景

代码代理（Code Agents）通过集成 Python 解释器等外部工具，实现了从代码生成到环境交互的闭环。这种执行能力使得安全评估不能仅停留在静态代码审查层面，必须验证代码执行后的实际后果。然而，传统红队测试（Red-teaming）多依赖静态基准或人工设计的越狱（Jailbreaking）算法，如 GCG 和 AutoDAN，这些方法针对自然语言任务优化，缺乏对代码执行环境的动态适应性。当代理引入新的防护机制或工具调用逻辑时，静态攻击模式往往失效，导致大量潜在漏洞未被发现。

当前领域共识认为，仅关注功能正确性的评估是不充分的，安全性需作为独立维度。然而，现有安全基准如 CodeLMSec 主要依赖静态分析器，存在高误报率，且无法模拟多轮交互中的安全退化。RedCodeAgent 的切入点在于将红队测试从“静态提示优化”转变为“动态代理决策”，通过模拟真实攻击者的迭代过程，利用执行反馈调整攻击策略，从而揭示静态方法无法捕捉的边界条件漏洞。

## 核心方法

### 动态代理决策框架

RedCodeAgent 基于 ReAct 逻辑构建，将红队测试视为一个序贯决策过程。与静态基准不同，该框架允许代理在每次交互后根据目标代理的响应动态调整下一步动作。核心差异在于引入了执行结果评估模块，该模块在 Docker 沙箱中运行代码并检查文件系统状态，而非仅依赖 LLM 判断代码文本的安全性。这一设计解决了静态评估无法确证漏洞可利用性的问题，确保攻击成功定义为“代码执行且产生预期风险后果”。

### 自适应记忆检索机制

记忆模块是 RedCodeAgent 的核心创新，用于积累并复用成功攻击经验。每个记忆条目包含风险场景、风险描述、攻击轨迹及评估结果。检索过程通过嵌入模型计算语义相似度，并引入轨迹长度惩罚项以偏好高效攻击路径。

$$ S = S_r + S_t - P $$

其中 $S_r$ 和 $S_t$ 分别为风险场景和描述的余弦相似度，$P = \text{Length}(m.\text{trajectory}) \times \rho$ 为轨迹长度惩罚。该公式确保检索到的经验不仅语义相关，且具备时间效率，避免冗长无效的攻击尝试。

### 代码专用工具组合

工具箱集成了 GCG、AmpleGCG 等通用越狱工具，以及专为代码任务设计的 Code Substitution 工具。Code Substitution 通过调用多个候选 LLM 生成替代实现（如用 `pathlib.unlink` 替代 `os.remove`），绕过代理内置的命令黑名单。这种工具组合策略允许 RedCodeAgent 根据目标代理的拒绝原因动态选择最合适的优化手段，解决了单一越狱算法在代码特定场景下泛化性不足的问题。

## 实验评估

实验在 RedCode-Exec、RedCode-Gen 和 RMCbench 三个基准上进行，目标代理包括 OpenCodeInterpreter (OCI)、ReAct (RA)、Cursor 和 Codeium。基线覆盖 GCG、AmpleGCG、Advprompter、AutoDAN 及 FlipAttack。RedCodeAgent 在 OCI 代理的 RedCode-Exec 基准上取得 72.47% 的攻击成功率（ASR），显著高于最佳基线 GCG 的 54.69%。在 RA 代理上，ASR 达到 75.93%，同样优于所有静态基线。

| 目标代理 | 基准 | No Jailbreak ASR | GCG ASR | RedCodeAgent ASR |
| :--- | :--- | :--- | :--- | :--- |
| OCI | RedCode-Exec | 55.46% | 54.69% | 72.47% |
| RA | RedCode-Exec | 56.67% | 57.53% | 75.93% |
| OCI | RedCode-Gen | 14.70% | 12.84% | 59.11% |
| RA | RedCode-Gen | 11.36% | 15.31% | 81.52% |

消融实验显示，记忆模块对性能至关重要。移除记忆模块后，OCI 上的 ASR 从 72.47% 降至 61.23%。工具数量增加至 5 个时 ASR 达到峰值 72.47%，继续增加至 8 个时 ASR 微降至 69.04%，表明工具冗余可能引入干扰。惩罚因子 $\rho$ 设为 0.02 时平衡了效率与成功率，$\rho=1$ 时 ASR 提升至 73.70% 但轨迹长度缩短至 3.29，显示更严格的效率约束有助于发现更直接的攻击路径。

评估边界方面，LLM-as-judge 在 RedCode-Gen 上的判断与人审一致性为 90.5%，主要错误源于不完整代码片段的误判。实验未报告计算成本的具体 GPU 资源消耗，仅提供了平均时间成本（121.17 秒），未与基线进行严格的算力归一化对比。代码未公开，复现需依赖 LangChain 框架及特定 LLM API。

## 关联研究分析

从问题动机看，RedCodeAgent 与 GCG 等静态越狱方法的核心差异在于评估闭环的引入。GCG 优化提示以最大化 LLM 生成恶意文本的概率，而 RedCodeAgent 优化提示以最大化代码执行后的风险后果。这一差异源于代码代理的执行特性：仅生成恶意代码而不执行，或执行失败，均不构成有效攻击。RedCodeAgent 通过沙箱执行反馈，将攻击目标从“文本生成”转向“状态改变”，解决了静态方法在代码场景下的评估失真问题。

从方法设计看，RedCodeAgent 借鉴了 ReAct 框架的工具调用逻辑，但将“行动”替换为“攻击工具组合”。与通用 LLM 代理不同，RedCodeAgent 的记忆模块专门针对攻击经验优化，引入轨迹长度惩罚以偏好高效路径。这一设计在数据充足时是否仍具优势，论文未给出回答。此外，RedCodeAgent 依赖 GPT-4o-mini 作为基础模型，其 72.47% 的 ASR 可能部分归因于该模型的强推理能力，而非框架本身的通用性。Llama-3.3-70B 在相同设置下 ASR 仅为 58.02%，且工具调用失败率高达 35.92%，表明框架对底层模型的工具调用能力有强依赖。

## 总结

RedCodeAgent 解决了代码代理安全评估中静态基准无法覆盖动态执行风险的核心矛盾。通过引入自适应记忆模块与代码专用工具组合，该框架实现了从静态提示优化到动态代理决策的范式转移。实验证明，该方法在 OCI 和 RA 代理上分别达到 72.47% 和 75.93% 的 ASR，显著优于静态基线。然而，框架对底层 LLM 工具调用能力的强依赖，以及现有防御机制（如 LlamaFirewall）对其攻击成功率几乎无影响（ASR 保持 72.47%），暴露了当前防御体系的脆弱性。当防御机制针对特定攻击模式进行优化时，RedCodeAgent 的记忆模块能否快速适应并发现新的绕过路径，论文未给出回答。
