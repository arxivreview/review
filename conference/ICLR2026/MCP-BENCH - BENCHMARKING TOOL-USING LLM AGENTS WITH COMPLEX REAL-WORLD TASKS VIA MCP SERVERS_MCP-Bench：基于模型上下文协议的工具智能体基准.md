作者：Zhenting Wang、Qi Chang、Hemani Patel 等 11 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_23639478)

> 现有工具使用基准多依赖孤立API或显式步骤指令，无法评估智能体在真实生态中处理模糊指令与跨域依赖链的能力。MCP-Bench 通过连接 28 个生产级 MCP 服务器，构建了包含 250 个工具的评测环境，并引入模糊化任务生成机制，迫使智能体自主推断执行路径。该基准揭示了当前前沿大语言模型在依赖感知与并行规划上的显著短板，但其仅评测通用模型而未纳入专用智能体框架，限制了其对架构优化贡献的区分能力。

## 研究背景

当智能体面对包含数百个异构工具的生态系统时，传统的“检索-调用”模式失效，因为工具间存在复杂的输入输出依赖，且用户指令往往缺乏显式步骤指引。这种场景要求智能体具备从模糊指令中推断隐含依赖链的能力，即规划能力。然而，现有基准如 ToolBench 和 BFCL v3 主要聚合孤立 API，任务多为少步调用，无法测试长程规划；而早期的 MCP 基准如 MCP-RADER 虽使用标准化协议，但覆盖范围狭窄，且任务描述过于具体，未挑战智能体在信息缺失下的决策鲁棒性。

工具使用评测的核心矛盾在于“真实性”与“可控性”的平衡。早期基准通过人工构造任务保证可控性，但牺牲了真实世界的复杂性；近期基于 MCP 的尝试提升了真实性，却因任务规模小或指令过于明确，未能充分暴露智能体在复杂依赖链中的规划弱点。MCP-Bench 的切入点在于利用 MCP 生态中服务器内工具天然互补的特性，结合自动化的模糊指令生成，构建了一个既具备真实依赖结构，又要求智能体进行深层推理的评测平台。

## 核心方法

### 方法参照系

本文问题属于工具使用智能体评测，其通用流程为“任务定义-智能体执行-结果评估”。与标准流程的关键差异在于，本文不预设显式执行步骤，而是通过依赖链分析生成模糊指令，将评测重心从“工具调用准确性”转移至“规划与依赖推理能力”。

### 模糊化任务合成

任务合成阶段的核心改动在于从“显式步骤”到“模糊指令”的转换。传统基准直接给出工具名或步骤，而本文首先通过 LLM 分析工具 I/O 签名发现依赖链，生成包含具体步骤的任务，随后将其重写为仅保留核心目标、省略工具引用和执行步骤的模糊变体。这一设计解决了现有基准中智能体可通过模式匹配而非真正规划完成任务的问题，迫使模型在信息缺失下推断隐含的执行顺序。

$$
\text{Task}_{fuzzy} = \text{Rewrite}(\text{Task}_{explicit}, \text{Constraint}_{minimal})
$$

该公式表示模糊任务由显式任务经最小化约束重写生成，确保核心目标保留而执行细节被移除。

### 双层评估框架

评估阶段采用规则检查与 LLM 评判结合的双层框架。规则层计算工具名称有效率、模式合规率和执行成功率，公式如下：

$$
R_{valid} = \frac{|\{e \in E : tool(e) \in T_{available}\}|}{|E|}
$$

其中 $E$ 为所有工具调用事件，$T_{available}$ 为可用工具集。该指标量化了智能体对工具可用性的基础理解。LLM 评判层则通过结构化评分标准评估任务完成质量、工具使用合理性和规划有效性，并引入提示洗牌与分数平均策略以消除评判偏差。这一设计弥补了纯规则检查无法评估策略质量的缺陷，同时通过多次独立评判提高了评估的稳定性。

## 实验评估

实验在 104 个任务上评估 20 个前沿 LLM，基线覆盖 OpenAI、Anthropic、Google 等主流厂商模型，但缺失 ToolVerse 等专用工具调用框架，导致无法区分模型能力与架构优化的贡献。

| 模型 | 整体得分 | 依赖感知 | 并行效率 |
| :--- | :--- | :--- | :--- |
| gpt-5 | 0.749 | 0.339 | 0.749 |
| o3 | 0.715 | 0.329 | 0.715 |
| gpt-oss-120b | 0.692 | 0.329 | 0.692 |
| llama-3-1-8b-instruct | 0.428 | 0.221 | 0.428 |

gpt-5 以 0.749 的整体得分领先，但所有模型在依赖感知维度得分均低于 0.35，表明长程依赖推理仍是普遍瓶颈。

消融分析显示，从单服务器到多服务器设置，弱模型性能显著下降。例如，llama-3-1-8b-instruct 的整体得分从 0.438 降至 0.415，主要源于依赖感知和并行效率的恶化。这一发现揭示了模型在分布式工作流中的泛化能力不足，且性能波动与服务器数量无平滑关系，暗示混合依赖结构对模型构成非均匀压力。

评估边界方面，基准未报告置信区间，且 LLM 评判依赖 o4-mini 模型，可能存在评判者偏差。代码已开源，但任务合成依赖 o4-mini，不同合成模型可能导致任务分布差异，影响结果可比性。

## 关联研究分析

从问题动机看，MCP-Bench 与 BFCL v3 均关注工具调用，但 BFCL 侧重单轮/多轮 API 调用的语法正确性，而 MCP-Bench 强调生态级多跳工作流的规划能力。这一差异源于任务复杂度：BFCL 的工具集孤立，无法形成依赖链，而 MCP 服务器的工具天然互补，使得依赖推理成为必要能力。

从方法设计看，MCP-Bench 与 MCP-RADER 均基于 MCP 协议，但 MCP-RADER 的任务生成依赖人工配置，而 MCP-Bench 采用自动化模糊化合成。这一设计选择解决了人工任务难以规模化且易过拟合特定模式的问题，但也引入了合成任务与真实用户意图分布可能不一致的风险。

## 总结

MCP-Bench 旨在解决现有工具基准无法评估复杂依赖链规划的问题，通过 MCP 生态与模糊指令结合，构建了高保真评测环境。实验显示 gpt-5 整体得分 0.749，但依赖感知得分仅 0.339，揭示了前沿模型在长程推理上的短板。其边界在于仅评测通用 LLM，未纳入专用智能体框架，无法区分模型能力与架构优化的贡献。当引入 ToolVerse 等框架时，依赖感知得分是否显著提升，论文未给出回答。
