# ICLR2026最新论文 ｜FeatureBench: Benchmarking Agentic Coding for Complex Feature Development ｜功能级智能体编码基准

研究机构：中国科学院、华为

作者：Qixing Zhou、Jiacheng Zhang、Haiyang Wang 等 12 人

论文原文见 [arXiv](https://arxiv.org/abs/2602.10975)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2602.10975)

> 现有智能体编码基准主要聚焦于单Pull Request（PR）内的Bug修复，难以评估模型在跨文件、长周期功能开发中的真实能力，且缺乏自动化更新机制以规避数据污染。本文通过测试驱动的动态依赖图追踪，从真实仓库中自动提取功能级任务，构建了包含200个实例的FeatureBench。该基准揭示了当前SOTA模型在功能开发上的显著能力缺口，但任务复杂度的极端性可能掩盖了模型在中等难度功能迭代上的实际进展。

## 研究背景

当智能体面对“实现GPT-2模型”这类需求时，其输出必须是一个可直接调用的模块，而非零散的代码片段。这要求任务定义包含明确的接口签名与输入输出规范，否则执行接地验证（Execution-Grounded Verification）将因接口歧义失效——同一功能可能有多种合法实现，导致单元测试无法唯一判定正确性。为消除歧义，基准必须提供显式的接口定义，这构成了功能级任务与Bug修复任务在评估协议上的根本差异。

仓库级软件工程智能体的评估长期依赖SWE-bench，其核心假设是Bug修复可通过单个PR的补丁与测试对进行闭环验证。然而，真实软件工程中约18-22%的需求属于功能开发，这类任务往往跨越多个PR与时间线，传统基于PR反转的数据收集方法无法完整捕获功能边界，且人工构建的基准（如PaperBench、GitTaskBench）规模有限且难以持续更新。FeatureBench的切入点在于：将任务粒度从“修复错误”扩展至“构建功能”，并通过自动化管道解决功能边界模糊与数据稀缺问题。

## 核心方法

### 测试驱动的任务提取范式

功能级编码任务的标准流程通常依赖人工标注或PR历史回溯，但本文将其置于“测试驱动的代码提取”框架下。关键差异在于：不依赖PR标签或提交历史，而是以单元测试为锚点，通过运行时行为反向推导功能边界。这一设计解决了PR方法中功能补丁分散、标签缺失导致的任务碎片化问题。

### 动态依赖图追踪与节点分类

传统代码提取依赖静态分析或LLM生成，易误删支撑功能。本文在参照系中引入动态追踪机制：执行F2P（Fail-to-Pass）与P2P（Pass-to-Pass）测试时，利用Python内置追踪设施捕获函数调用事件，构建对象依赖图。图中每个节点代表一个函数，并标记其在P2P测试中是否被触发。

$$
\text{Node}_{i} = \begin{cases} \text{Extracted} & \text{if } \text{Triggered}_{P2P}(i) = \text{False} \\ \text{Remained} & \text{if } \text{Triggered}_{P2P}(i) = \text{True} \end{cases}
$$

该公式定义了节点分类规则：仅在F2P测试中触发、未在P2P测试中出现的函数被标记为“提取”，其余保留。这一设计动机在于：P2P测试代表了代码库中已稳定运行的功能，任何被其依赖的函数必须保留，以确保提取目标功能后剩余代码库的完整性。通过广度优先遍历从F2P测试导入的顶层对象出发，系统自动隔离出目标功能的代码片段，避免了人工界定功能边界的模糊性。

### 后验证与问题陈述合成

提取后的代码补丁需通过严格后验证：修改后的代码库必须通过所有P2P测试（确保未破坏现有功能）且失败所有F2P测试（确保目标功能已移除）。验证通过后，系统基于提取的代码片段、预修改代码库与单元测试，自动生成包含接口签名、功能描述与Docker环境定义的问题陈述。这一流程将人工干预限制在仓库安装命令指定（每仓库约3分钟），实现了200个实例与3825个可执行环境的自动化构建。

## 实验评估

实验采用OpenHands、Claude Code等主流智能体框架，搭配GPT-5.1-Codex、Claude Opus 4.5等前沿模型，在FeatureBench的Lite（30实例）与Full（200实例）集上评估。基线覆盖了当前SWE-bench上的SOTA配置，但缺乏专门针对功能开发的专用智能体对比。

| 模型 | 框架 | Lite % Resolved | Full % Resolved | Full Token I/O |
|---|---|---|---|---|
| Claude Opus 4.5 | Claude Code | 11.0 | 20.0 | 9.0M / 35k |
| GPT-5.1-Codex | Codex | 12.5 | 20.0 | 6.6M / 39k |
| Gemini-3-Pro-Preview | OpenHands | 10.0 | 10.0 | 6.0M / 41k |

Claude Opus 4.5在SWE-bench Verified上解决率为74.4%，但在FeatureBench子集上仅5.2%，凸显功能级任务的挑战性。消融实验显示，提供可见单元测试使GPT-5.1-Codex的解决率从25.3%提升至63.3%，表明测试可见性是关键性能因子；而增加执行步数从50到100仅带来边际收益，暗示当前瓶颈不在迭代次数而在推理质量。

评估边界方面，基准仅覆盖Python仓库，且任务复杂度极端（平均15.7文件、29.2函数），可能高估了模型在中等难度功能迭代上的能力缺口。代码与数据已开源，但3825个环境的构建依赖人工指定的安装命令，限制了向非Python生态的扩展。

## 关联研究分析

从问题动机看，SWE-bench聚焦Bug修复，其执行接地验证假设任务可通过单PR闭环；FeatureBench将任务扩展至功能开发，但继承了SWE-bench的F2P/P2P测试协议。关键差异在于：功能开发涉及跨文件依赖与长程规划，而SWE-bench的Bug修复多为局部修改。这一差异导致FeatureBench中模型解决率骤降，但论文未量化“功能复杂度”与“解决率”的非线性关系，5.2%的低解决率是否主要源于任务难度还是评估协议过严，缺乏对照实验。

从方法设计看，SWE-Gym依赖PR反转生成训练数据，而FeatureBench采用测试驱动的动态依赖图追踪。SWE-Gym的局限在于PR标签缺失导致功能边界模糊，FeatureBench通过P2P测试约束解决了这一问题，但引入了对测试覆盖率的依赖——若仓库测试不完整，依赖图追踪可能遗漏关键函数。论文未讨论测试覆盖率对提取准确性的影响，这在测试稀疏的开源项目中可能成为瓶颈。

## 总结

FeatureBench要解决的核心矛盾是：现有基准无法评估智能体在功能级开发中的真实能力，且缺乏自动化更新机制。其切入点在于以单元测试为锚点，通过动态依赖图追踪自动提取功能边界，解决了PR方法中任务碎片化与人工构建的规模瓶颈。该基准证明了当前SOTA模型在功能开发上的显著能力缺口（Claude Opus 4.5解决率仅11.0%），但任务复杂度的极端性（平均15.7文件）可能掩盖了模型在中等难度功能迭代上的实际进展。当仓库测试覆盖率低于阈值时，依赖图追踪的准确性是否退化，论文未给出回答。
