# ICLR2026最新论文 ｜GISTIFY! CODEBASE-LEVEL UNDERSTANDING VIA RUNTIME EXECUTION ｜代码库级执行流理解评估

研究机构：美国北卡罗来纳大学教堂山分校、微软研究院

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_38274923)

> 现有仓库级基准依赖GitHub Issue文本，且允许模型通过检索局部补丁绕过全局执行逻辑，导致无法区分模型是真正理解了代码库结构还是仅在进行模式匹配。GISTIFY任务通过要求模型生成一个最小化、自包含且能复现特定命令运行时行为的单文件，强制模型追踪完整的跨文件执行路径。该方法利用程序化验证而非LLM裁判，解决了动态基准构建成本高且易受污染的问题。尽管该方法在理论上填补了自动化代码库级评估的空白，但当前SOTA模型在长执行轨迹下的失败率依然极高，其评估结果是否足以证明深层语义理解仍存疑。

## 研究背景

当代理式编码模型（Agentic Coding Model）被部署在大型真实代码库中时，其面临的挑战不再是单函数生成，而是如何在缺乏完整上下文窗口的情况下，理解复杂的文件间依赖关系。这种理解要求模型不仅识别静态代码结构，还需模拟动态执行流，即追踪数据和控制流在多个模块间的传递。然而，现有的评估体系大多基于静态快照或简化的Issue修复任务，难以捕捉这种动态的、全局性的执行逻辑。

主流仓库级基准如SWE-bench和RepoBench虽然引入了真实GitHub Issue，但其任务定义允许模型通过启发式捷径或检索局部补丁来解决问题，而不必真正推理整个执行过程。此外，这些基准严重依赖Issue日志和Pull Request文本，导致其无法泛化到没有此类元数据的私有或任意代码库。GISTIFY任务的切入点在于剥离对Issue文本的依赖，仅利用测试套件和入口命令，要求模型通过“执行流重构”来证明其对代码库结构的理解，从而构建一个可自动化、防污染且更严苛的评估协议。

## 核心方法

### 任务定义与参照系

GISTIFY任务置于仓库级软件工程评估的范畴，但其核心差异在于目标输出的性质。传统SWE-bench要求模型修改代码以修复Bug，而GISTIFY要求模型生成一个“Gistified File”，即一个最小化、自包含的单文件，该文件必须能独立执行并复现原代码库在特定命令下的运行时行为。这一设计强制模型从“解题者”转变为“结构解析者”，必须识别哪些代码是执行必需的，哪些是冗余的。

### 执行忠实度与最小化度量

为量化模型对执行流的理解，GISTIFY引入了三个核心指标，其中执行忠实度（Execution Fidelity）是二元指标，定义为生成文件与原代码库在给定命令下输出的一致性。其形式化定义如下：

$$
\text{Fidelity}(c, C, G) = \mathbb{1}[\text{runs}(c, G) \land \text{out}(c, G) = \text{out}(c, C)]
$$

该公式表明，只有当生成文件 $G$ 能成功运行且其标准输出/错误流与原代码库 $C$ 完全一致时，才计为成功。这排除了仅靠静态代码相似度得分的可能性，强制要求动态行为的一致性。

### 行存在率与执行率

为了评估生成文件的最小化和忠实性，GISTIFY引入了行存在率（Line Existence Rate）和行执行率（Line Execution Rate）。行存在率衡量生成文件中的代码块是否直接来源于原代码库，防止模型幻觉出新的代码逻辑。其计算公式为：

$$
\text{Existence}(G, C) = \frac{\sum_{b \in B_G} \mathbb{1}[\exists b' \in B_C, L(b) \subseteq L(b')]}{|B_G|}
$$

其中 $B_G$ 和 $B_C$ 分别为生成文件和原代码库的代码块集合，$L(b)$ 表示块内的行集合。该指标确保模型是在“提取”而非“重写”代码，从而隔离了代码生成能力与代码理解能力。行执行率则衡量生成文件中实际被执行行的比例，高执行率意味着文件精简且无冗余，反映了模型对执行路径的精准把握。

## 实验评估

实验在SWE-bench中的5个仓库（requests, pylint等）及debug-gym上进行，使用SWE-agent、mini-SWE-agent和Copilot三种框架，对比GPT-5、Claude-4等模型。基线覆盖审计显示，论文未对比专门针对代码重构或压缩的专用工具，仅对比了通用代理框架，这可能低估了专用方法在代码提取任务上的潜力。

| 框架 | 模型 | 执行忠实度 (无执行/有执行) | 行存在率 | 行执行率 |
| :--- | :--- | :--- | :--- | :--- |
| SWE-agent | Claude-4 | 56.7 / 57.3 | 66.3 | 72.9 |
| Copilot | Claude-4 | 58.7 / 61.3 | 69.6 | 80.3 |
| SWE-agent | GPT-5 | 30.7 / 46.0 | 48.3 | 81.7 |
| mini-SWE-agent | GPT-5 | 51.0 / 54.0 | 56.8 | 83.1 |

数据显示，Claude-4在Copilot框架下取得了最高的执行忠实度（61.3%），但整体成功率仍低于65%。GPT-5在SWE-agent框架下表现显著下降（30.7%），而在mini-SWE-agent下表现较好（51.0%），表明框架的工具支持对模型性能有显著影响。

消融实验揭示了测试函数保真度的关键作用。当在提示中显式提供正确的测试函数体时，Test F1 Score从68.4提升至85.3，执行忠实度从42.0%提升至60.0%。这一发现表明，模型失败的主要瓶颈在于初始步骤中定位和复制测试函数的能力，而非后续的代码提取逻辑。此外，启用执行工具（如bash）仅带来微小的性能提升（如SWE-agent中Claude-4从56.7%到57.3%），说明当前模型未能有效利用运行时反馈来修正推理错误。

评估边界方面，GISTIFY依赖测试套件的存在，对于无测试覆盖的代码库无法直接应用。此外，行存在率的计算依赖于代码块的分块策略，可能对不同编程风格敏感。代码已开源，但实验仅使用了25个测试实例，样本量较小，统计显著性有限。

## 关联研究分析

从问题动机看，GISTIFY与SWE-bench的核心差异在于任务目标的本质。SWE-bench关注“修复”，允许模型通过局部补丁解决Issue，而GISTIFY关注“理解”，要求模型复现全局执行行为。这种差异源于SWE-bench对Issue文本的依赖，使得模型可以利用文本线索进行检索，而GISTIFY剥离了这些线索，强制模型通过执行流推理来定位关键代码。这一设计使得GISTIFY更能区分模型的深层理解能力与表面模式匹配能力，但也可能导致任务难度高于真实SWE场景，因为真实开发中开发者往往能利用Issue上下文。

从方法设计看，GISTIFY与CoRE（Code Reasoning Evaluation）均关注代码推理，但CoRE侧重于静态分析任务（如数据流分析），而GISTIFY侧重于动态执行验证。CoRE的评估基于静态代码属性，而GISTIFY的评估基于运行时输出一致性。这种差异表明，静态推理能力并不完全等价于动态执行理解能力。GISTIFY通过引入执行忠实度指标，填补了动态执行理解评估的空白，但其评估协议依赖于测试套件，而CoRE可以应用于任意代码片段。这种依赖关系限制了GISTIFY的泛化性，但也使其评估结果更具确定性，避免了LLM-as-a-Judge的主观偏差。

## 总结

GISTIFY旨在解决现有仓库级基准无法区分模型是真正理解代码库结构还是仅进行模式匹配的核心矛盾。通过要求模型生成最小化、自包含且能复现运行时行为的单文件，GISTIFY强制模型追踪完整的跨文件执行路径，从而构建了一个可自动化、防污染的评估协议。实验表明，即使是最强的Claude-4模型，在Copilot框架下的执行忠实度也仅为61.3%，且测试函数的保真度对最终成功率有决定性影响。然而，该方法的边界在于其依赖测试套件的存在，且当前模型在长执行轨迹下的失败率依然极高，这可能反映了模型在动态执行流推理上的根本局限。当代码库规模进一步扩大，执行轨迹长度超过模型上下文窗口时，GISTIFY的评估结果是否仍能准确反映模型的代码库级理解能力，而非受限于上下文截断导致的推理中断，论文未给出回答。
