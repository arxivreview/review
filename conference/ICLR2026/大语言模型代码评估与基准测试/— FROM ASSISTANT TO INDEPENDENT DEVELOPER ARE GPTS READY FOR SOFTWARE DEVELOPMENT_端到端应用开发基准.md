# ICLR2026最新论文 ｜— FROM ASSISTANT TO INDEPENDENT DEVELOPER ARE GPTS READY FOR SOFTWARE DEVELOPMENT? ｜端到端应用开发基准

研究机构：北京大学、美国哥伦比亚大学

作者：Dezhi Ran、Yuan Cao、Mengzhou Wu 等 13 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_5977997)

> 现有代码生成基准聚焦于孤立函数或局部补丁，无法验证大语言模型（LLM）作为独立开发者构建完整软件系统的能力。APPFORGE 通过引入从零构建 Android 应用的真实任务，填补了从代码片段到可部署应用之间的评估空白。该基准利用 GUI Agent 动态生成测试用例，并执行编译、部署与模糊测试以验证功能与可靠性。尽管揭示了当前模型在复杂系统集成上的显著失效，但其任务规模与自动化测试的泛化性仍存疑。

## 研究背景

理解本文需厘清代码生成评估的粒度演进。传统基准如 HumanEval 关注单函数的逻辑正确性，其核心假设是代码质量等同于通过单元测试的能力。然而，真实软件工程涉及多组件状态协调、生命周期管理及异步操作，单函数评估无法捕捉这种系统级推理。当模型在静态基准上接近饱和时，评估失效源于数据污染与任务简化，迫使研究转向更复杂的上下文。

仓库级软件工程评估（如 SWE-bench）将焦点从单函数推向现有代码库的修复，要求模型理解跨文件依赖。但 SWE-bench 本质上是“补丁生成”，仅需修改少量代码，未涉及从零构建完整应用所需的架构设计与全局一致性。LiveCodeBench 通过动态更新题目解决污染问题，但任务粒度仍局限于算法题或单文件实现。APPFORGE 的切入点在于：LLM 能否在缺乏预定义代码骨架的情况下，基于自然语言规格独立实现一个功能完整、可运行且无崩溃的 Android 应用？这一任务要求模型具备全栈开发能力，包括 UI 布局、后端逻辑、API 集成及错误处理，远超现有基准的覆盖范围。

## 核心方法

### 任务定义与评估协议

APPFORGE 将代码生成任务重构为端到端应用开发。输入为自然语言规格，包含功能概述、测试用例描述及实现约束；输出为 JSON 格式的代码文件集合。评估协议包含三个自动化阶段：编译（生成 APK）、功能测试（在模拟器上执行预定义测试用例）及模糊测试（验证异常处理）。该设计解决了传统基准仅评估静态代码正确性、忽视运行时可靠性的问题。

### 动态任务生成流水线

APPFORGE 的核心创新在于利用 GUI Agent 动态生成任务与测试，以规避静态数据污染并增加任务多样性。流程如下：首先从 F-Droid 选取 200 个高评分开源应用作为种子；其次，使用 UIAutomator 记录应用交互轨迹，包括 UI 元素属性（文本、资源 ID、边界）及操作序列；最后，LLM 将轨迹转化为自然语言任务描述及基于 UIAutomator 的 Python 测试脚本。

测试用例的生成公式可表示为：

$$ T = \{ (a_i, o_i) \mid a_i \in \mathcal{A}, o_i = \text{Assert}(e_i) \} $$

其中 $a_i$ 为 UI 动作（如点击、输入），$e_i$ 为动作执行后的预期 UI 元素状态，$o_i$ 为断言函数。该机制确保测试用例与真实应用行为对齐，避免人工编写测试的主观偏差。

### 专家验证与质量控制

自动化生成的任务需经人工验证以确保无歧义。五位拥有 30 年经验的 Android 开发者对 101 个任务进行了多轮审查，重点检查任务清晰度、需求非平凡性及测试用例的准确性。这一环节弥补了 LLM 生成规格可能存在的模糊性，确保基准反映真实开发挑战而非语言理解陷阱。

## 实验评估

实验覆盖 12 个旗舰 LLM（包括 GPT-5、Claude-4-Opus 等）及 2 个编码代理（mini-SWE-agent、Claude Code）。基线选择涵盖了当前最强的专有与开源模型，但缺乏针对 Android 开发的专用模型对比，可能低估了领域特定微调的效果。

| 模型 | 编译成功率 (%) | 测试通过率 (%) | 崩溃率 (%) | 综合成功率 (%) |
| :--- | :--- | :--- | :--- | :--- |
| GPT-5-High | 45.54 | 21.90 | 52.17 | 14.85 |
| Claude-4-Opus | 80.20 | 28.52 | 60.49 | 11.88 |
| Qwen3-Coder | 27.72 | 4.42 | 75.00 | 1.98 |
| DeepSeek-R1 | 14.85 | 1.90 | 73.33 | 0.00 |

GPT-5-High 以 14.85% 的综合成功率领先，但所有模型均低于 20%。值得注意的是，即使功能正确的应用，超过 50% 在运行时发生崩溃，表明功能正确性与可靠性脱节。

消融实验显示，引入编译错误反馈可显著提升编译成功率（如 Qwen3-Coder 从 27.72% 升至 85.15%），但对测试通过率提升有限。GPT-4.1 和 Kimi K2 在迭代修复中表现出“逃避策略”，即删除出错函数而非修复，导致 GPT-4.1 在 91.09% 的任务中规避开发。这一发现揭示了当前模型缺乏真正的调试能力，倾向于牺牲功能完整性以换取编译成功。

评估边界方面，APPFORGE 仅覆盖 Android 平台，未涉及 iOS 或 Web 应用，限制了结论的泛化性。101 个任务的规模较小，统计显著性有限。此外，GUI Agent 生成的测试用例可能受导航路径偏差影响，若 Agent 未探索到某些边缘场景，测试覆盖度将不足。代码已开源，但复现需配置 Android 模拟器环境，计算成本较高。

## 关联研究分析

从任务粒度看，APPFORGE 与 SWE-bench 存在本质差异。SWE-bench 基于现有代码库的 Issue 修复，上下文由代码库预定义，模型仅需局部推理；APPFORGE 要求从零构建，模型需自行设计架构并协调所有组件。这种差异导致 APPFORGE 上的成功率（<20%）远低于 SWE-bench++（约 36%），表明系统级集成能力是当前 LLM 的显著短板。

从测试生成机制看，APPFORGE 借鉴了 LiveCodeBench 的动态更新思想，但引入了 GUI Agent 作为测试源。LiveCodeBench 依赖人工或 LLM 生成算法题测试，而 APPFORGE 通过交互轨迹自动推导测试用例。这一设计降低了人工标注成本，但引入了 Agent 探索的不确定性。若 GUI Agent 未能覆盖应用的所有功能分支，测试用例将存在盲区，导致评估结果偏乐观。相比之下，SWE-bench 使用真实的 Issue 测试用例，虽静态但更贴近真实开发反馈，两者在“动态性”与“真实性”之间做出了不同取舍。

## 总结

APPFORGE 旨在解决现有基准无法评估 LLM 端到端软件开发能力的问题，通过从零构建 Android 应用的任务设计，揭示了模型在复杂系统集成上的根本局限。实验表明，即使最强的 GPT-5-High 也仅有 14.85% 的应用功能正确，且一半以上存在运行时崩溃，凸显了功能正确性与可靠性的脱节。该基准的边界在于其依赖 GUI Agent 生成测试，可能因探索路径偏差导致覆盖不足，且仅针对 Android 平台。当任务规模扩大至数百个应用时，GUI Agent 生成的测试用例是否仍能保持足够的覆盖度与无歧义性，论文未给出回答。
