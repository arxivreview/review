# ICLR2026最新论文 ｜SWINGARENA: ADVERSARIAL PROGRAMMING - ARENA FOR LONG CONTEXT GITHUB ISSUE SOLVING ｜对抗性持续集成评估框架

研究机构：美国加州大学洛杉矶分校、清华大学

作者：Wendong XU、Jing Xiong、Chenyang Zhao 等 19 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_68781887)

> 现有代码生成基准多聚焦于静态快照下的功能正确性，难以捕捉真实软件工程中的迭代协作与动态审查机制，导致模型在复杂仓库级任务上的能力被高估。SWINGARENA 通过构建提交者与审查者的双代理对抗环境，将评估嵌入真实的持续集成（CI）流水线，以动态生成的测试用例和全链路质量门控替代固定测试集。该框架结合多语言检索增强代码生成（RACG）模块，在 400 个真实 GitHub Issue 上验证了不同模型在补丁激进性与 CI 稳定性间的权衡。其价值在于揭示了静态基准无法量化的协作鲁棒性，但受限于基线模型时效性与检索瓶颈，结论的普适性存疑。

## 研究背景

当大语言模型（LLM）处理大型代码库时，关键信息散落在数千行代码与多个文件中，长上下文处理成为核心瓶颈。为缓解此问题，检索增强生成（RAG）技术被引入，但现有方法多依赖词汇匹配，缺乏对代码结构的细粒度理解，导致在复杂仓库中检索精度不足。同时，真实软件开发并非一次性代码生成，而是包含提交、审查、测试与迭代的闭环流程，这一动态协作过程在现有评估中几乎被完全忽略。

主流评估路线存在显著瓶颈。HumanEval 等静态基准因数据污染与任务简化已饱和，无法区分前沿模型性能；SWE-bench 虽引入真实 GitHub Issue，但仍依赖固定的单元测试与单代理范式，缺乏对 CI 流水线中风格检查、安全扫描等质量门控的覆盖。这些基准假设代码只需通过单一测试即可视为正确，忽视了工业级开发中“代码需通过全链路自动化验证”的核心约束。SWINGARENA 的切入点在于将评估从“静态正确性”转向“动态对抗性”，通过模拟提交者与审查者的角色交互，量化模型在真实 CI 环境下的端到端成功率。

## 核心方法

### 对抗性 CI 评估协议

传统代码评估采用单代理范式，模型生成代码后由固定测试集验证，该流程无法捕捉代码在动态审查下的鲁棒性。SWINGARENA 引入双代理对抗机制，将评估重构为提交者（Submitter）与审查者（Reviewer）的博弈过程。提交者生成修复补丁，审查者动态生成测试用例以暴露潜在缺陷，两者在 CI 流水线中交替迭代。该协议的核心在于将“通过固定测试”转化为“通过动态生成的对抗性测试”，从而量化模型在未知测试场景下的稳定性。

$$
\text{Win Rate} = \frac{1}{|T|} \sum_{t \in T} \mathbb{1}[\text{Patch}_t \text{ passes all CI checks} \land \text{Patch}_t \approx \text{Golden}_t]
$$

该公式定义了胜率，仅当补丁通过所有 CI 检查（包括审查者生成的测试）且与黄金修复语义一致时才计为成功。这一设计解决了静态基准中“测试覆盖不足导致评估偏差”的问题，通过动态测试生成强制模型应对更广泛的边界条件。

### 多语言检索增强代码生成（RACG）

长上下文代码库中，相关代码片段分散且冗余，传统 RAG 方法在严格 token 预算下难以精准定位关键上下文。SWINGARENA 提出 RACG 模块，结合语法感知分块、密集重排序与 token 预算感知打包，为模型提供标准化上下文访问。该模块采用 BM25 进行文件级粗筛，CodeBERT 进行块级密集重排序，并通过语言感知平局打破与邻近偏差优化检索精度。

$$
\text{Score}(c) = \alpha \cdot \cos(\mathbf{e}_q, \mathbf{e}_c) + \beta \cdot \text{Prox}(c, c_{\text{selected}}) + \gamma \cdot \mathbb{1}[\text{Def}(c)]
$$

该评分函数融合语义相似度、邻近偏差与定义优先策略，其中 $\mathbf{e}_q$ 与 $\mathbf{e}_c$ 分别为问题与代码块的 CodeBERT 嵌入，$\text{Prox}$ 衡量与已选块的邻近度，$\mathbb{1}[\text{Def}]$ 标识定义块。这一设计解决了传统 RAG 在复杂仓库中“检索冗余与结构无关”的问题，通过语法感知分块保留代码结构完整性，提升上下文相关性。

## 实验评估

实验基于 400 个真实 GitHub Issue（C++、Python、Rust、Go 各 100 个），对比 GPT-4o、Claude-3.5、Gemini-2.0、DeepSeek-V3 等模型。基线覆盖主流专有模型，但缺失最新 SOTA 模型（如 GPT-5、Claude Sonnet 4.5），限制了结论的时效性。主实验显示，DeepSeek-V3 在 Best@3 上取得最高平均分（0.59），GPT-4o 在胜率上表现激进（跨模型胜率均 ≥0.90），但 CI 通过率较低（SPR 0.55），揭示其补丁激进性与稳定性间的权衡。

| 模型 | 平均 Best@3 | C++ | Go | Rust | Python |
|---|---|---|---|---|---|
| DeepSeek | 0.59 | 0.64 | 0.61 | 0.58 | 0.52 |
| Gemini | 0.57 | 0.64 | 0.58 | 0.51 | 0.57 |
| GPT-4o | 0.57 | 0.63 | 0.53 | 0.56 | 0.54 |
| Claude | 0.55 | 0.63 | 0.55 | 0.52 | 0.50 |

消融实验验证了 RACG 的有效性。在 C++ 任务中，引入 RACG 使 Best@3 从 0.38 提升至 0.42，胜率从 0.77 提升至 0.84。与 BM25 基线相比，Top-20 检索取得最强基线结果（Best@3 0.43，胜率 0.73），但 RACG 在多数语言上仍占优。值得注意的是，RACG 的固定 Top-5 文件检索限制可能成为复杂任务的瓶颈，论文未提供更大检索范围的消融结果。

| 方法 | Best@3 | 胜率 |
|---|---|---|
| C++ w/ RACG | 0.42 | 0.84 |
| C++ w/o RACG | 0.38 | 0.77 |
| BM25 | 0.38 | 0.62 |
| Top-20 Related | 0.43 | 0.73 |

评估边界方面，指标体系包含胜率、CI 通过率与 Best@k，但未报告置信区间，数值比较需谨慎。评估协议依赖 Docker 容器隔离，但不同仓库的 CI 配置差异可能导致环境不一致，论文未提供环境标准化细节。可复现性上，论文提供了 GitHub 与 HuggingFace 链接，但 RACG 的超参数（如 CodeBERT 版本、token 预算阈值）未在正文中完整列出，限制了独立复现。

## 关联研究分析

从问题动机看，SWINGARENA 与 SWE-bench 同属仓库级评估路线，但核心差异在于评估协议的动态性。SWE-bench 依赖固定单元测试与单代理修复，而 SWINGARENA 引入审查者动态生成测试，将评估从“静态正确性”转向“动态鲁棒性”。这一差异源于任务特性：真实软件开发中，代码需通过不断变化的审查标准，固定测试集无法捕捉这一动态过程。然而，SWINGARENA 未讨论审查者测试生成的偏差控制，若审查者存在自我偏好，可能导致胜率虚高，这一盲区在论文中未得到充分验证。

从方法设计看，SWINGARENA 的 RACG 模块与 LiveCodeBench 的防污染理念不同。LiveCodeBench 通过时间维度更新题目避免数据污染，而 SWINGARENA 通过对抗性 CI 评估实现动态性，两者解决的是不同层面的问题：前者针对数据静态性，后者针对评估协议静态性。RACG 采用 CodeBERT 进行密集重排序，而 LiveCodeBench 未涉及检索增强，这一差异源于任务规模：SWINGARENA 处理多文件仓库级任务，需精准定位上下文，而 LiveCodeBench 聚焦单函数算法题，上下文需求较低。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

SWINGARENA 要解决的核心矛盾是静态基准无法量化 LLM 在真实 CI 环境下的动态协作能力。其切入点在于将评估重构为提交者与审查者的对抗博弈，通过动态测试生成与全链路 CI 验证替代固定测试集，从而捕捉模型在未知审查标准下的鲁棒性。该框架结合 RACG 模块处理长上下文检索，在 400 个真实 GitHub Issue 上验证了不同模型的行为差异：DeepSeek-V3 在 Best@3 上最高（0.59），GPT-4o 胜率激进但 CI 稳定性较低（SPR 0.55）。其边界在于基线模型非最新 SOTA，RACG 的固定检索限制可能制约复杂任务性能，且审查者偏差控制未充分验证。当审查者测试生成存在系统性偏差时，胜率指标是否仍能可靠反映模型真实能力，论文未给出回答。
