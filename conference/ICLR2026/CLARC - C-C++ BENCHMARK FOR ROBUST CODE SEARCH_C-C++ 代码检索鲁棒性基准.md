# ICLR2026最新论文 ｜CLARC: C/C++ BENCHMARK FOR ROBUST CODE SEARCH ｜C/C++ 代码检索鲁棒性基准

研究机构：美国南加州大学

作者：Kaicheng Wang、Liyan Huang、Weike Fang 等 4 人

论文原文见 [arXiv](https://arxiv.org/abs/2603.04484)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ICLR_2026_17069754)

> 代码检索模型在标准基准上表现优异，但这一高分往往源于对标识符名称等表面词汇特征的依赖，而非对代码深层语义的理解。现有基准多聚焦 Python 且缺乏对文本扰动的压力测试，导致无法区分模型的语义理解能力与词汇匹配能力。本文提出 CLARC，一个基于真实 C/C++ 仓库构建的基准，通过标识符匿名化和编译至低层语言来剥离表面特征，暴露模型鲁棒性缺陷。该工作揭示了当前 SOTA 检索模型在语义泛化上的脆弱性，但其结论受限于仅评估了少数支持 C/C++ 的嵌入模型，且未探索通过微调彻底解决该问题的路径。

## 研究背景

代码检索是大规模代码库导航的核心组件，其主流范式是基于嵌入的密集检索。模型将代码片段和自然语言查询编码为向量，通过计算相似度进行排序。这一范式依赖于模型能够捕捉代码的语义结构，但在实际部署中，代码往往经过混淆、重命名或编译，导致表面词汇特征与底层语义发生解耦。若模型仅依赖标识符名称进行匹配，其在真实工程场景中的可靠性将大打折扣。

当前代码检索基准存在显著局限。多数数据集（如 CodeSearchNet, CoSQA）优先覆盖 Python 等研究友好型语言，忽视 C/C++ 等系统编程语言，且代码片段常因缺失依赖而无法编译。更关键的是，现有基准极少评估模型对文本扰动的鲁棒性，例如变量重命名或编译至汇编语言。这种缺失掩盖了模型高分是否源于真正的语义理解，还是仅仅利用了浅层词汇线索。CLARC 的切入点在于构建一个完全可编译的 C/C++ 基准，并引入匿名化与低层语言编译设置，以隔离表面特征对检索性能的影响。

## 核心方法

### 方法参照系

代码检索评估的标准流程通常包括：收集代码-查询对、训练/微调嵌入模型、在标准设置下计算 NDCG、MRR 等指标。本文的关键差异在于，它不将“标准设置”视为评估终点，而是将其作为基线，通过引入“中性化”、“随机化”及“低层语言编译”三种对抗性设置，构建一个鲁棒性评估框架。

### 依赖复杂度分类与查询生成

为量化上下文对检索的影响，CLARC 将代码片段按依赖复杂度分为三组：Group 1 仅依赖标准库；Group 2 依赖自定义类型；Group 3 依赖用户定义的辅助函数。对于 Group 3，进一步细分为 Short（主函数与辅助函数分离）和 Long（合并为单一片段）。查询生成采用 LLM（o3-mini 和 grok-4）自动描述函数功能，并明确指令 LLM 避免使用标识符名称，仅基于代码目的生成描述。为确保查询质量，论文采用假设检验框架，由三名博士级标注者对 LLM 生成与人类专家生成的描述进行双盲评分。评分公式定义为：若描述存在事实错误，得 -1.0；若两者均正确且质量相当，各得 +0.5；若一方明显更优，优者得 +1.0，劣者得 +0.5。通过 Bootstrap 分析（10,000 次迭代），验证 LLM 生成查询的质量与人类专家无显著差异（p-value > 0.76），从而确保查询侧不引入词汇偏差。

### 鲁棒性设置与嵌入评估

在标准设置之外，CLARC 引入三种鲁棒性设置以剥离表面特征。Neutralized 设置将标识符替换为中性占位符（如 `func_a`, `var_b`），保留结构角色但去除语义名称；Randomized 设置将标识符替换为随机名称，彻底消除词汇信息；Assembly/Wasm 设置将代码编译为 x86 汇编或 WebAssembly，通过编译过程自然消除大部分标识符。检索模型（如 Voyage-code-3, OASIS）在这些设置下计算嵌入相似度。核心评估指标为 MRR（Mean Reciprocal Rank），其定义为：

$$ MRR = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{rank_i} $$

其中 $rank_i$ 是第 $i$ 个查询中第一个相关结果在排序列表中的位置。该公式直接衡量模型在剥离表面特征后，能否快速定位语义正确的代码片段。

## 实验评估

实验在 CLARC 评估集（1,245 对）上进行，对比 BM25、CodeT5+、OASIS、Nomic-emb-code、OpenAI-text-embedding-large 和 Voyage-code-3 六种模型。基线覆盖从经典 TF-IDF 到最新 SOTA 嵌入模型，但缺失专用 C/C++ 检索模型。在标准设置下，Voyage-code-3 在 Group 2 的 MRR 达到 92.10，显著高于 CodeT5+ 的 46.67，表明现代嵌入模型在完整上下文下具有强大语义理解能力。

| 模型 | Group 1 MRR (Std) | Group 2 MRR (Std) | Group 3 Long MRR (Std) |
|---|---|---|---|
| Voyage-code-3 | 86.93 | 92.10 | 85.43 |
| OASIS | 86.54 | 88.30 | 63.53 |
| Nomic-emb-code | 86.23 | 91.61 | 64.93 |
| CodeT5+ | 58.84 | 46.67 | 17.78 |

在 Neutralized 和 Randomized 设置下，所有模型性能均大幅下降。Voyage-code-3 在 Group 2 的 MRR 从 92.10 降至 77.18（Neutralized）和 69.43（Randomized），降幅分别为 16.2% 和 24.7%。OASIS 在 Group 1 的 MRR 从 86.54 降至 83.66（Neutralized）和 78.74（Randomized），降幅最小，表明其基于顺序增强策略的训练方法对词汇扰动具有一定鲁棒性。值得注意的是，在 Randomized 设置下，Group 1 的性能普遍高于 Group 2，这与标准设置下的趋势相反，暗示模型对自定义类型的理解高度依赖类型名称的语义线索。

| 模型 | Group 2 MRR (Neu) | Group 2 MRR (Ran) | Group 3 Long MRR (Ran) |
|---|---|---|---|
| Voyage-code-3 | 77.18 | 69.43 | 61.15 |
| OASIS | 68.91 | 60.19 | 30.51 |
| Nomic-emb-code | 67.65 | 48.23 | 26.06 |
| CodeT5+ | 15.67 | 11.27 | 5.18 |

在 Assembly 和 Wasm 设置下，仅评估了 OpenAI 和 Voyage 两个通用嵌入模型。Voyage-code-3 在 Group 1 的 MRR 为 29.02（Asm）和 27.19（Wasm），远低于标准设置的 86.93，降幅超过 68%。OpenAI 在 Group 1 的 MRR 仅为 8.61（Asm）和 6.60（Wasm），表现更差。这表明当前模型在低层语言上的语义理解能力极为有限，且通用嵌入模型在剥离标识符后，其性能退化程度远超匿名化设置。

评估边界方面，论文未报告置信区间，且仅评估了六个模型，缺乏对专用 C/C++ 检索模型的对比。微调实验显示，CodeT5+ 在标准设置微调后 MRR 提升，但在 Neutralized 设置下仍显著低于标准设置，证实标准监督微调无法解决鲁棒性缺陷。OASIS 微调后在目标设置性能提升，但在其他设置性能下降，出现过拟合现象。

## 关联研究分析

从问题动机看，CLARC 与 LiveCodeBench 等动态基准共享“防污染”和“真实性”目标，但 CLARC 聚焦于 C/C++ 系统编程语言，而 LiveCodeBench 主要覆盖 Python 和竞赛编程。CLARC 的核心创新在于引入“匿名化”和“编译”设置，这不同于 LiveCodeBench 的时间维度更新，而是从语义层面剥离表面特征。这一差异源于 C/C++ 在系统编程中的重要性及其代码混淆的普遍性，而 Python 代码较少经历此类变换。

从方法设计看，CLARC 的查询生成采用 LLM 并辅以假设检验，这与 PACIFIC 等确定性规则评估框架形成对比。PACIFIC 强调规则评估的无歧义性，而 CLARC 依赖 LLM 生成查询并通过统计检验验证质量。这种差异反映了代码检索任务中自然语言查询的开放性，难以用确定性规则完全约束。CLARC 的假设检验框架（Bootstrap + Krippendorff’s α）为 LLM 生成基准提供了质量保障，但其有效性依赖于标注者的一致性和样本量，对于大规模自动化生成场景，其可扩展性仍存疑。

## 总结

CLARC 旨在解决代码检索模型对表面词汇特征的过度依赖问题，通过构建可编译的 C/C++ 基准并引入匿名化与低层语言编译设置，暴露了当前 SOTA 模型在语义鲁棒性上的缺陷。实验表明，Voyage-code-3 在标准设置下 Group 2 MRR 达 92.10，但在 Randomized 设置下降至 69.43，降幅 24.7%；在 Assembly 设置下进一步降至 29.02，降幅 66.7%。该工作证明了标准监督微调无法克服这些鲁棒性缺陷，OASIS 微调后虽在目标设置提升，但在其他设置性能下降。其边界在于仅评估了少数通用嵌入模型，未探索专用 C/C++ 模型或更复杂的鲁棒性训练策略。当模型在低层语言上的性能退化是否可通过大规模低层语言数据微调缓解，论文未给出回答。
