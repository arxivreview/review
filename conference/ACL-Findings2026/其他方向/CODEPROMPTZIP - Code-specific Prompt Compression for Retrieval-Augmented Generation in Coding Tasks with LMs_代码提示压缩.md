作者：Pengfei He、Shaowei Wang、Tse-Hsun Chen

论文原文见 [arXiv](https://arxiv.org/abs/2502.14925)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_c07d2f7d9ca8)

> 检索增强生成（RAG）在代码任务中常因引入大量示例导致提示词长度激增，超出模型上下文窗口或产生高额API成本。现有通用压缩方法缺乏对代码语法结构的感知，盲目剔除Token易破坏代码逻辑。本文提出CodePromptZip，一种基于程序分析类型优先级与复制机制的硬压缩框架，旨在保留关键代码语义的同时实现可控比率压缩。该方法在三个代码任务上显著优于熵基与蒸馏基线，但其依赖静态分析工具的特性限制了在不可解析代码上的泛化能力。

## 研究背景

RAG通过检索相关代码示例注入提示词以提升生成质量，但示例往往包含数万Token，直接输入导致计算成本激增且受限于模型上下文窗口。解决此问题的核心在于提示压缩，即在不损失关键语义的前提下减少Token数量。然而，代码与自然语言存在本质差异：代码中的标识符、符号与结构具有严格的语法依赖，通用压缩方法若忽略这种类型差异，极易导致编译错误或逻辑断裂。

现有提示压缩路线主要分为软压缩与硬压缩。软压缩（如GIST）将文本映射为连续向量，虽压缩比高但缺乏可解释性，且需访问模型梯度，无法兼容黑盒API服务。硬压缩（如LLMLingua）通过启发式指标（如熵）筛选Token，保留了人类可读性，但通用启发式指标未能区分代码中不同语法元素对生成质量的具体影响。LLMLingua-2等蒸馏方法虽提升了压缩效果，但依赖大模型生成摘要，成本高且难以精确控制压缩比率。CodePromptZip的切入点在于利用程序分析工具量化代码Token类型的差异化贡献，构建任务特定的移除优先级，从而在硬压缩框架内实现结构感知的精准压缩。

## 核心方法

### 方法参照系

CodePromptZip属于显式抽取式压缩路线，其基础流程为：接收原始代码与目标压缩比率，通过某种准则筛选保留Token，输出压缩后的代码片段。与通用硬压缩的关键差异在于，本文不依赖单一的统计指标（如困惑度），而是引入程序分析（PA）工具对Token进行类型分类，并基于消融实验建立类型级的移除优先级队列。

### 类型感知优先级构建

传统压缩方法假设所有Token的信息量可通过单一标量（如熵）衡量，但在代码中，标识符（Identifier）承载开发者意图，而符号（Symbol）仅定义边界，二者对生成质量的贡献度存在显著差异。CodePromptZip通过消融分析量化这种差异：移除特定类型Token后，测量下游任务性能下降幅度$d_T$与压缩比率$\tau_{code/T}$的比值，定义优先级函数：

$$
Priority(T) = \frac{\tau_{code/T}}{d_T}
$$

该公式表明，移除某类型Token能带来高压缩率且性能损失小，则该类型优先级高，应优先剔除。实验发现优先级具有任务特异性（如Assertion Generation中Invocation优先级高于Symbol，而在Code Suggestion中反之），但跨模型一致，这解决了通用启发式指标无法适配不同代码任务语义重心的问题。

### 复制增强压缩器架构

基于优先级构建数据集后，需训练一个能精确控制压缩比率的压缩器。CodeT5等编码器-解码器模型在生成压缩代码时，常因词表限制或生成随机性导致实际压缩比率偏离目标。CodePromptZip在CodeT5架构中引入复制机制（Copy Mechanism），允许解码器直接从源序列复制Token，而非从全词表生成。同时，扩展词表加入`<Ratio>`等特殊Token，使模型能条件化地学习不同压缩比率下的映射关系。复制机制的引入使得压缩过程变为“抽取式”而非“生成式”，确保输出代码完全源自输入，避免了生成式压缩可能引入的幻觉代码，同时通过优先级队列指导的贪心算法（Algorithm 1）在训练阶段预剔除高优先级Token，使压缩器只需学习如何在保留Token中维持语法完整性，从而实现了比率的精确控制与代码结构的鲁棒性。

## 实验评估

实验在Assertion Generation、Bugs2Fix和Code Suggestion三个RAG代码任务上进行，基线包括熵基方法（LLMLingua, LongLLMLingua）和蒸馏方法（LLMLingua-2, RECOMP），未包含软压缩基线（如GIST），这限制了与高保真软压缩路线的直接对比。主实验结果显示，CodePromptZip在三个任务上分别较最佳基线提升23.4%、28.7%和8.7%，表明类型感知策略在代码特定任务上显著优于通用压缩。

| 方法 | Assertion Gen (EM%) | Bugs2Fix (CodeBleu%) | Code Suggestion (CodeBleu%) |
| :--- | :--- | :--- | :--- |
| LLMLingua | 20.9 | 25.1 | 21.8 |
| RECOMP | 25.9 | 20.9 | 21.0 |
| CodePromptZip | 26.2 | 21.7 | 20.5 |

*注：表中CodePromptZip数值取自论文Table 2中“Ours, Setting τcode-0.3, 1-shot”行，其中Assertion Gen为Exact Match，其余为CodeBleu。基线数值对应同一表格中相应列。*

消融实验验证了复制机制的关键作用：移除复制机制后，Assertion Generation的Exact Match下降1.2%，Bugs2Fix的CodeBleu下降5.2%，Code Suggestion下降3.2%。这表明复制机制不仅提升了性能，更确保了压缩代码的语法正确性。此外，在不可解析代码测试中，CodePromptZip在移除1%和3%尾部Token后，性能仅轻微下降（42.1%至42.0%和41.7%），而依赖AST的Oracle方法失效，证明了基于概率关系的压缩器对代码完整性的鲁棒性。

评估边界方面，论文未报告计算效率指标（如压缩延迟、显存占用），且仅在GPT-3.5-turbo、CodeLlama-13B和Gemini-1.0-pro三个模型上验证泛化性，缺乏在更小参数量模型或不同编程语言上的测试。代码未开源，超参数细节（如优先级队列的具体阈值）未在正文中完全披露，限制了可复现性。

## 关联研究分析

从问题动机看，CodePromptZip与LLMLingua-2同属硬压缩路线，但LLMLingua-2依赖大模型蒸馏生成摘要，其压缩决策由外部大模型的黑盒判断驱动，缺乏对代码内部结构的显式建模。CodePromptZip则通过程序分析工具显式提取Token类型，将压缩决策建立在代码语法结构的先验知识上。这种差异源于任务特性：代码的语法约束比自然语言更严格，通用蒸馏方法难以保证压缩后的代码可编译，而类型感知策略通过保留关键结构Token（如Signature）确保了语法完整性。

从方法设计看，CodePromptZip与GIST等软压缩方法形成鲜明对比。GIST通过微调模型将提示压缩为连续向量，实现了极高的压缩比，但牺牲了可解释性且需访问模型梯度。CodePromptZip选择硬压缩路线，核心动机是兼容黑盒API服务（如GPT-4），这在工业部署中至关重要。然而，硬压缩的离散Token剔除本质决定了其压缩比上限低于软压缩，且在高压缩比下易出现语义断裂。CodePromptZip通过复制机制缓解了这一问题，但并未解决硬压缩在高压缩比下信息保真度骤降的根本局限，这是否是代码任务特有的容忍度较高，还是方法本身的边界，论文未给出明确回答。

## 总结

CodePromptZip旨在解决代码RAG场景中提示词过长导致的成本与上下文限制问题，其切入点在于利用程序分析量化代码Token类型的差异化贡献，克服了通用压缩方法忽略代码语法结构的缺陷。通过类型感知优先级构建与复制增强压缩器，该方法在三个代码任务上实现了较最佳基线23.4%至28.7%的性能提升，证明了结构感知硬压缩的有效性。然而，其依赖静态分析工具的特性限制了在不可解析代码上的应用，且未评估高压缩比下的语义保真度极限。当压缩比率进一步降低至0.1以下时，类型优先级策略是否仍能维持代码的逻辑连贯性，论文未提供实验证据。
