# ACL-Findings2026最新论文 ｜Text2Mem: A Unified Memory Operation Language for Memory Operating System ｜统一记忆操作语言

作者：Leo Wang、Lihai Yang、Boyu Chen 等 9 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_fa768cf74138)

> 大语言模型智能体在长程交互中面临记忆管理碎片化问题，现有系统仅暴露编码、检索等基础原语，缺乏对优先级调整、合并、锁定等高级治理操作的形式化定义，导致跨系统行为不一致且难以审计。本文切入点在于将自然语言指令映射为具有显式字段与语义不变量的模式化操作契约，通过验证-解析-适配流水线实现确定性执行。Text2Mem定义了12个覆盖记忆全生命周期的动词，并构建了分离规划与执行评估的双层基准。该工作确立了记忆操作接口的标准化范式，但其端到端任务性能优势及在复杂动态环境下的泛化能力尚未得到充分验证。

## 研究背景

当智能体接收“暂时不要提及午餐”这类模糊指令时，不同系统可能执行删除、隐藏或忽略操作，这种歧义源于自然语言指令在作用域、持续时间与动作类型上的欠定。解决此问题需引入模式化约束，将模糊指令规范化为包含目标、参数与元数据的结构化对象，这构成了类型化解析的基础。类型化解析进一步要求执行环境具备状态转换的可验证性，即操作执行后的记忆状态变化必须能通过数据库断言进行审计，从而确保行为的可复现性。

现有记忆框架如MemGPT、Mem0和Letta虽实现了外部存储与检索，但主要依赖CRUD式原语或临时扩展，缺乏统一的操作语言来支持优先级治理、记忆巩固与生命周期管理。这种碎片化导致记忆管理无法组合成复杂工作流，且不同后端对同一指令的解释存在差异，削弱了系统的可移植性与安全性。Text2Mem借鉴Text-to-SQL中从自然语言到精确可执行操作的映射思路，将记忆控制视为一种需要模式约束与类型检查的语言任务，旨在通过显式接口消除底层实现的歧义。

## 核心方法

### 操作集与模式架构

Text2Mem将记忆操作定义为12个动词，分为编码、存储与检索三个阶段，其中存储阶段包含Promote、Demote、Merge、Split、Lock、Expire等高级治理操作。每个操作被表示为包含stage、op、target、args、meta五个字段的JSON对象，其中target支持ID、过滤器、语义搜索或全局范围四种模式。该设计动机在于解决现有系统缺乏统一语义边界的问题，通过显式字段强制规范化欠定指令，使同一操作规格能跨异构后端执行。

$$
\mathcal{S} = \langle \sigma, \omega, \tau, \alpha, \mu \rangle
$$

其中 $\sigma \in \{\text{ENC}, \text{STO}, \text{RET}\}$ 为阶段，$\omega$ 为操作动词，$\tau$ 为目标范围，$\alpha$ 为归一化参数，$\mu$ 为元数据。该公式定义了操作的完整契约，确保执行前所有必要信息均已显式指定。

### 验证-解析-适配流水线

流水线分为验证器、解析器与适配器三阶段。验证器检查结构完整性与跨字段不变量，如禁止删除锁定项或更新过期项，将安全检查前移至执行前。解析器将验证后的模式转换为类型化操作对象，将时间范围、优先级等参数归一化为具体表示。适配器将类型化对象映射到特定后端的可执行动作，本文使用SQL参考后端作为受控执行环境。该设计解决了运行时安全与参数歧义问题，通过前置验证确保后续阶段操作于良构实例，提升了执行的可预测性与可审计性。

$$
\mathcal{E}(\mathcal{S}, \mathcal{M}) \rightarrow \mathcal{M}'
$$

其中 $\mathcal{M}$ 为当前记忆状态，$\mathcal{M}'$ 为执行后的状态。该函数表示操作对记忆状态的确定性转换，执行结果记录受影响项及状态变化，支持通过SQL断言进行数据库级验证。

## 实验评估

实验在自建Text2Mem Benchmark上进行，该基准包含从场景到自然语言请求、模式生成、预期结果定义的三层结构，评估分为规划层（模式生成准确率）与执行层（执行保真度）。基线对比包括MemOS、Mem0和Letta，但缺乏HippoRAG、SwiftMem等检索优化方法的横向对比，且未报告LoCoMo、LongMemEval等标准长程记忆基准成绩，限制了与领域SOTA的直接比较。

| MemOS | ✓ | ✓ | ✓ | – | – | – | – | – |
| Mem0 | ✓ | ✓ | ✓ | – | – | – | – | – |

| Text2Mem | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

表格显示Text2Mem是唯一完整支持所有12个操作的框架，现有系统仅覆盖基础CRUD操作，高级治理操作普遍缺失。该对比验证了操作集完整性的必要性，但未提供性能数值，仅证明功能覆盖差异。

评估边界方面，基准依赖SQL原型后端，虽提供可审计性，但可能简化了真实生产环境的复杂性，如并发访问、分布式同步等。代码已开源，但超参数与GPU配置未在材料中详细披露，且缺乏多后端大规模实证比较，限制了结论的泛化性。

## 关联研究分析

从问题动机看，Text2Mem与MemGPT等系统共享外部记忆必要性共识，但MemGPT聚焦虚拟内存分页机制，将记忆视为辅助推理的工具，而Text2Mem聚焦操作接口的标准化，将记忆视为可治理的第一类组件。这一差异源于任务特性：MemGPT解决上下文窗口限制，Text2Mem解决指令歧义与行为不一致。Text2Mem未探索记忆内容的语义质量，仅关注操作执行的正确性，这与Mem0等强调事实提取与冲突解决的方法形成互补而非竞争。

从方法设计看，Text2Mem借鉴Text-to-SQL的模式约束思路，但记忆操作比SQL查询更具动态性与治理性，如Lock与Expire涉及生命周期管理，这在SQL中无直接对应。与SuperLocalMemory V3的信息几何遗忘机制相比，Text2Mem将遗忘简化为Expire操作，缺乏基于统计结构的自适应调整，这可能牺牲了遗忘的认知合理性。Text2Mem的Retrieve操作引入权限感知与字段白名单，区别于纯语义相似度检索，但缺乏多信号融合机制，在大规模噪声记忆中的鲁棒性未经验证。

## 总结

Text2Mem解决的核心矛盾是自然语言指令的欠定性与记忆操作执行确定性之间的冲突，现有系统因缺乏统一操作语言导致行为碎片化，而Text2Mem通过模式化契约与类型化解析实现了跨后端的一致性执行。该工作定义了12个覆盖全生命周期的操作动词，并构建了分离规划与执行评估的双层基准，证明了高级治理操作在现有框架中的缺失。其边界在于仅验证了操作规范性，未提供端到端任务性能数据，且SQL参考后端可能简化了真实环境的复杂性。当记忆操作涉及多模态内容或分布式同步时，该模式化契约是否仍能保持确定性与可审计性，论文未给出回答。
