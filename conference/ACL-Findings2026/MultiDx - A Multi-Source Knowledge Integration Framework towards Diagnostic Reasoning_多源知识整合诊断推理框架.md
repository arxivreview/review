# ACL-Findings2026最新论文 ｜MultiDx: A Multi-Source Knowledge Integration Framework towards Diagnostic Reasoning ｜多源知识整合诊断推理框架

研究机构：香港城市大学、西湖大学

作者：Yimin Deng、Zhenxi Lin、Yejing Wang 等 12 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.24186)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.24186)

> 临床诊断推理要求模型不仅给出正确病名，还需生成符合医学逻辑的可验证推理链，但现有大语言模型（LLM）依赖内部参数化知识或静态知识库，导致在罕见病或知识更新场景下出现推理断裂与幻觉。本文切入点在于将诊断过程解耦为“多源证据生成”与“跨源鉴别诊断”两个阶段，通过并行检索网络、结构化病例及数据库，弥补单一知识源的时效性与覆盖度缺陷。MultiDx 采用两阶段流水线，先由 SOAP 格式化、BM25 检索及 Web 搜索生成候选病列表，再通过投票与鉴别诊断整合出最终预测。该方法在 MedCaseReasoning 基准上实现了 H@1 0.420 的准确率，优于基线模型，但其性能高度依赖外部检索质量，且未验证在纯离线或高噪声环境下的鲁棒性。

## 研究背景

临床诊断推理的核心困境在于信息的不完整性与知识的动态性。当模型面对复杂病例时，仅靠参数化知识往往无法覆盖长尾疾病，此时需要引入外部知识。检索增强生成（RAG）通过注入外部文档缓解知识过时问题，但传统 RAG 通常依赖单一静态知识库，难以应对实时变化的医学指南或罕见病例。为提升推理的可解释性，思维链（CoT）技术被引入以显式化推理步骤，然而若缺乏高质量的结构化证据支撑，CoT 易陷入“右答错因”的陷阱，即结论正确但逻辑链条断裂，导致临床医生无法验证其合理性。

医疗 LLM 领域的主流路线正从静态知识召回转向动态推理对齐。早期工作如 MedAgents 通过多智能体协作模拟会诊，但缺乏对实时外部知识的整合；OpenAI-DR 等深度研究代理虽具备动态检索能力，却未针对临床诊断的标准工作流进行结构化约束。现有方法普遍存在两个瓶颈：一是知识源单一，无法同时利用实时网络数据、结构化病例报告与历史诊断轨迹；二是评估指标侧重最终答案正确性，忽视推理路径的临床符合度。MultiDx 针对这一缺口，提出将诊断过程对齐至临床标准的“疑似病列表生成”与“鉴别诊断”两步，通过多源知识并行整合，确保推理轨迹既具备事实准确性，又符合医学逻辑规范。

## 核心方法

### 多源知识引导的诊断生成

本文方法置于检索增强生成（RAG）与多智能体协作的交叉参照系中。与标准 RAG 仅从单一向量库检索不同，MultiDx 的关键差异在于并行整合异构知识源，并将输入预处理为临床标准的 SOAP 格式。设计动机在于解决非结构化病例报告导致的上下文噪声问题，以及单一知识源在罕见病场景下的覆盖盲区。

在 Stage 1 中，模型首先将原始病例 $C$ 转换为 SOAP 格式 $C_{SOAP}$，其中包含主观症状（S）、客观检查（O）、评估（A）与计划（P）。由于输入仅含症状与检查，A 与 P 被标记为缺失，以此强制模型基于证据进行推理。随后，系统并行执行三个检索模块：

1. **SOAP 推理**：基于结构化输入生成候选病列表 $H_{SOAP}$。

2. **病例库检索**：利用 BM25 算法从标注病例库 $\mathcal{G}$ 中检索相似病例，并基于实体重叠度检索细粒度推理轨迹。实体相似度通过 Jaccard 系数计算：

$$
J(E_{i,j}, E_C) = \frac{|E_{i,j} \cap E_C|}{|E_{i,j} \cup E_C|}
$$

该公式衡量检索到的推理片段 $R_{i,j}$ 与当前病例 $C$ 在生物医学实体上的重合度，确保检索到的推理步骤与当前病例在病理机制上高度相关。

3. **Web 搜索**：模型生成搜索计划 $P = (Q, T, N)$，其中 $Q$ 为查询词，$T$ 为工具类型，$N$ 为步数。通过迭代调用搜索、导航与提取工具，累积记忆状态 $m_i$，最终生成基于实时网络信息的候选病列表 $H_{web}$。

### 证据整合与鉴别诊断

Stage 2 承接 Stage 1 输出的四个候选病列表 $\{H_{web}, H_{SOAP}, H_{case}, H_{trace}\}$，解决多源证据冲突与冗余问题。设计动机在于单一来源的候选列表可能存在偏差，需通过跨源一致性验证提升诊断可靠性。

模型执行四步整合流程：

1. **疾病匹配**：统一不同来源中的同义术语（如“心肌梗死”与“心脏病发作”）。

2. **投票聚合**：统计每个候选病在四个列表中的出现频次与排名，量化跨源支持度。

3. **鉴别诊断**：对高排名候选病进行逻辑比对，基于病例特征排除不匹配项。

4. **最终重排**：输出最终诊断 $D$ 及推理路径 $R$。该过程形式化为：

$$
(R, D) = \text{LLM}(I_{multi}, C, H_{web}, H_{SOAP}, H_{case}, H_{trace})
$$

其中 $I_{multi}$ 为指令提示，引导模型综合多源证据进行最终决策。这一机制将诊断过程从“单点预测”转化为“多视角证据收敛”，显著提升了推理路径的临床可解释性。

## 实验评估

实验在 MedCaseReasoning（14,489 例）与 DiReCT 数据集上进行，基线包括 DeepSeek-R1、MedAgents、Self-refinement 及 OpenAI-DR。所有方法均基于 DeepSeek-R1 骨干，确保公平对比。

| 方法 | H@1 | H@5 | H@10 | Recall |
| :--- | :--- | :--- | :--- | :--- |
| DeepSeek-R1 | 0.360 | 0.419 | 0.442 | 0.648 |
| w/ SOAP | 0.379 | 0.467 | 0.502 | 0.638 |
| w/ web search | 0.416 | 0.553 | 0.602 | 0.460 |
| MultiDx | **0.420** | **0.577** | **0.617** | **0.662** |

MultiDx 在 H@1 上达到 0.420，较基线 DeepSeek-R1 提升 16.7%，在 H@5 与 H@10 上分别提升 8.4% 与 17.5%。消融实验显示，Web 搜索模块对 H@1 贡献最大（0.416 vs 0.360），但导致 Recall 下降至 0.460，表明实时知识虽提升精准度，却可能引入噪声或分散注意力。SOAP 结构化与病例库检索则主要提升 Recall，验证了结构化输入对推理完整性的贡献。

评估边界方面，论文仅在 300 个测试样本上评估，样本量较小，统计显著性受限。此外，Web 搜索模块的延迟与 Token 消耗未完全报告，且未对比纯 RLVR 方法（如 CRPO），无法量化训练式方法与非训练式框架在推理质量上的差异。代码已开源，但 Web 搜索模块依赖实时网络环境，复现性受外部条件影响。

## 关联研究分析

从问题动机看，MultiDx 与 MedAgents 均旨在提升诊断推理的可解释性，但 MedAgents 依赖多智能体内部知识协作，缺乏外部知识注入，导致在罕见病场景下知识覆盖不足。MultiDx 通过引入 Web 搜索与病例库，解决了知识时效性与覆盖度问题，但其代价是引入了外部噪声风险。相比之下，OpenAI-DR 虽具备动态检索能力，但未针对临床诊断的 SOAP 结构化与鉴别诊断流程进行优化，导致其推理路径缺乏临床标准约束。MultiDx 的 SOAP 预处理与鉴别诊断步骤，使其推理轨迹更符合临床工作流，这是其区别于通用深度研究代理的关键。

从方法设计看，MultiDx 的投票机制与 ConfAgents 的置信度过滤类似，但 ConfAgents 基于单一模型的置信度，而 MultiDx 基于多源一致性。这一差异源于任务特性：诊断推理需要多视角证据收敛，而非单一模型的自我校准。然而，MultiDx 未探索多源知识冲突时的权重分配策略，当 Web 搜索与病例库给出矛盾结果时，模型仅通过 LLM 提示进行定性判断，缺乏量化机制。这种定性整合在复杂病例中可能引入主观偏差，论文未给出在知识冲突场景下的鲁棒性分析。

## 总结

MultiDx 针对临床诊断推理中知识不足与推理不可验证的矛盾，通过多源知识并行整合与 SOAP 结构化，实现了 H@1 0.420 与 Recall 0.662 的性能提升。其核心贡献在于将诊断过程对齐至临床标准，确保推理路径的可解释性。然而，实验仅在 300 个样本上进行，且 Web 搜索模块的噪声影响未充分量化。当外部知识源与内部知识发生冲突时，MultiDx 的投票机制是否仍能保持诊断稳定性，论文未给出回答。
