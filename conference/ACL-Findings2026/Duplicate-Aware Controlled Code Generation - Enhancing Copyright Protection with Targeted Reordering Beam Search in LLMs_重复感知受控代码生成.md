# ACL-Findings2026最新论文 ｜Duplicate-Aware Controlled Code Generation: Enhancing Copyright Protection with Targeted Reordering Beam Search in LLMs ｜重复感知受控代码生成

作者：Junbo Fu、Guoshuai Zhao、Linkang Yang 等 5 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_6274b366a671)

> 大语言模型在代码生成中倾向于逐字复现训练数据片段，直接触发版权侵权风险，而现有评估体系仅关注功能正确性，忽视了输出内容的法律合规性。传统的数据清洗或后处理去重方法要么破坏模型能力，要么无法实时控制重复长度，导致在保持代码功能完整性的同时消除逐字重复成为技术难点。本文提出重复感知受控代码生成（DACCG）任务，并设计目标重排束搜索（TRBS）算法，在解码阶段通过动态重排候选束来实时抑制重复序列。该方法在8B参数模型上实现了重复率与准确率的灵活权衡，但受限于单函数场景与小模型规模，其在真实仓库级工程环境中的有效性尚未得到验证。

## 研究背景

当模型在推理阶段生成代码时，若输出片段与训练数据中的受版权保护代码高度相似，即构成法律意义上的侵权。这种逐字复现（Verbatim Repetition）现象在参数小于60B的模型中尤为显著，平均可复现50个单词的文学片段（Karamolegkou et al., 2023）。由于源代码在法律上被视为文学作品，GitHub Copilot等工具因生成未署名的复制代码已引发诉讼。解决此问题需引入最长公共子序列（LCS）作为侵权度量，但直接约束LCS长度往往导致代码语法错误或功能失效，因此需要在解码过程中同时监控重复度与语义完整性。

代码生成评估领域长期聚焦于Pass@k等功能正确性指标，静态基准如HumanEval已饱和且存在数据污染，动态基准如LiveCodeBench虽解决了污染问题，但均未将版权合规纳入评估维度。现有受控生成方法主要解决语法或安全约束，缺乏针对版权去重的实时干预机制。本文切入点在于将数据污染从“评估失效”转化为“法律风险”，提出在解码阶段通过束搜索干预实现去重，填补了模型用户视角下版权保护的技术空白。

## 核心方法

### 解码干预参照系

受控生成通常通过分类器引导或能量模型调整Logits以约束输出属性。本文问题与通用流程的关键差异在于约束目标为外部参照系（私有代码库）的序列相似度，而非内部概率分布的属性，且要求实时性以避免生成无效代码。

### 基于FM-Index的重复检测与束重排

标准束搜索仅按累积概率排序，无法感知输出与私有代码的重复。TRBS在解码每步引入FM-Index，利用其线性空间复杂度高效检测当前束候选与私有代码序列$S$的尾部最长公共子序列（TLCS）。当检测到非零TLCS时，算法寻找同一父束下TLCS为零且语义可替换的候选束进行交换。语义可替换性通过Token级概率比$p_m/p_n$判定，若比值超过阈值$\alpha$则拒绝替换，确保替换不显著降低生成质量。

$$
TLCS(b_i, S) = \arg \max_{t_{ik}} \{k \mid t_{ik} \sqsubseteq S\}
$$

该公式计算束$b_i$后缀与私有代码$S$的最长匹配长度，$t_{ik}$为$k$长度后缀子序列，$\sqsubseteq$表示子序列关系。

### 基于尖峰熵的结构锚点保护

单纯替换Token可能破坏代码结构完整性，导致后续生成陷入语法无效区域。TRBS引入尖峰熵（Spike Entropy）识别结构锚点，即低熵的关键节点。在锚点位置禁止替换操作，防止局部修改引发级联错误。尖峰熵基于Logits概率分布$P_i(m)$计算，阈值$\beta$控制保护强度。

$$
SpikeEntropy = \sum_{m=1}^{D} \frac{P_i(m)}{1 + z \cdot P_i(m)}
$$

其中$z$为缩放常数，$D$为词表大小。低尖峰熵区域被视为上下文依赖放大器，微小修改在此处会产生非线性影响，保护机制确保代码结构连贯性。

## 实验评估

实验在HumanEval-X和MultiCodeBench上验证TRBS，使用Qwen3-8B作为骨干，LoRA微调。基线包括训练数据重写（预处理）和输出再生成（后处理）。TRBS在Python、Java、Go等语言上，于相同LCS长度下实现了高于基线的执行准确率，或在相同准确率下实现了更低的LCS长度。

| 语言 | α | β | LCS | ACC |
|---|---|---|---|---|
| Python | 2 | 0.55 | 53.91 | 77.44 |
| Java | 2 | 0.55 | 73.70 | 67.68 |
| JavaScript | 2 | 0.55 | 27.53 | 67.68 |
| Go | 2 | 0.55 | 39.76 | 54.88 |
| CPP | 2 | 0.55 | 39.09 | 52.44 |

消融实验显示，移除结构锚点保护导致准确率显著下降，而LCS仅轻微增加，证明保护机制对维持功能正确性至关重要。参数分析表明，$\alpha$和$\beta$在0.50-0.60区间内对结果敏感，需联合调优以平衡去重与质量。

评估边界受限于8B小模型与单函数任务，未涉及仓库级跨文件依赖。代码开源，超参数$\alpha, \beta$可灵活调整，但FM-Index构建开销随代码库规模线性增长，限制了其在大规模私有代码库中的实时性。

## 关联研究分析

从问题动机看，本文与SWE-bench等仓库级评估框架存在根本差异。SWE-bench关注解决真实GitHub Issue的代理能力，而DACCG聚焦于生成内容的法律合规性。前者假设代码正确性即质量，后者指出正确代码若包含侵权片段仍不可用。这种差异源于任务特性：仓库级任务需全局上下文理解，而版权去重是局部序列匹配问题，FM-Index的局部检测机制在此更具优势，但无法捕捉跨文件依赖导致的间接侵权。

从方法设计看，TRBS与Classifier Guidance等解码干预方法同属Logits调整范式，但TRBS使用外部索引而非内部分类器。Classifier Guidance依赖预训练奖励模型，存在自我偏好偏差；TRBS基于规则化的LCS检测，无歧义且可复现，但缺乏语义灵活性。在低资源语言或复杂控制流中，规则化替换可能失效，而基于学习的引导可能更鲁棒。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

本文核心矛盾在于代码生成的功能正确性与版权合规性之间的冲突，现有方法无法在解码阶段实时平衡两者。TRBS通过FM-Index检测重复并基于尖峰熵保护结构锚点，实现了无需额外训练的去重控制。实验证明在Qwen3-8B上，TRBS在Python数据集上以53.91的LCS长度维持了77.44%的执行准确率，优于基线。其边界在于单函数场景与8B模型规模，未验证在大规模私有代码库或仓库级任务中的扩展性。当私有代码库规模扩大至百万行级别时，FM-Index的构建与查询开销是否仍能满足实时解码要求，论文未给出回答。
