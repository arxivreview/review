# ACL-Findings2026最新论文 ｜Idea First, Code Later: Disentangling Problem Solving from Code Generation in Evaluating LLMs for Competitive Programming ｜先想后写：编辑式解耦竞赛编程中的推理与实现

作者：Sama Hadhoud、Alaa Elsetohy、Frederikus Hudi 等 6 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_2164c4884be7)

> 竞赛编程（Competitive Programming, CP）评估长期将算法规划与代码实现混同为单一端到端任务，导致模型失败时无法区分是“想错了”还是“写错了”。现有基准如LiveCodeBench虽解决了数据污染，但仍无法定位推理瓶颈。本文切入点是将自然语言编辑式（Editorial）作为显式中间产物，通过对比模型自生成编辑式与专家金标编辑式下的代码通过率，量化“解题”与“实现”的独立贡献。其价值在于首次提供了可操作的解耦评估协议，但83题的小样本规模限制了统计稳健性，且仅覆盖C++/Python两种语言。

## 研究背景

竞赛编程的核心交付物并非代码本身，而是约束下的算法规划：关键观察、数据结构选择、不变量证明及复杂度论证。代码仅是这一规划向可执行程序的下游翻译。然而，当前主流评估范式（如HumanEval、LiveCodeBench）仅记录最终程序的通过/失败状态，这种端到端映射混淆了两种截然不同的能力：推导正确高效算法的“解题”能力，与将计划转化为正确高效代码的“实现”能力。当提交失败时，标准指标无法区分失败源于规划错误还是编码错误，导致模型优化方向模糊。

该领域正从静态快照向动态生态重构，LiveCodeBench等基准通过时间维度换取抗污染能力，SWE-bench则引入仓库级上下文。然而，这些进展均未触及CP内部的认知结构：模型在竞赛题上的表现提升，究竟源于算法洞察力的增强，还是代码模板记忆的强化？现有方案卡在“黑盒”评估上，无法提供细粒度的诊断信号。本文的切入点在于借鉴人类选手的工作流——先写解题思路（编辑式），再写代码——将编辑式确立为评估的显式中间态，从而在数学上隔离推理与实现两个环节。

## 核心方法

### 编辑式中心评估管线

标准CP评估流程为 $C = f_{code}(P, \emptyset)$，即直接从题目 $P$ 生成代码。本文将其扩展为三阶段管线，引入编辑式 $E$ 作为中间变量。设计动机在于：端到端评估中，若模型生成错误代码，无法判断是 $f_{code}$ 的实现缺陷还是 $f_{ed}$ 的规划缺陷。通过控制 $E$ 的来源，可分别量化两个环节的贡献。

### 双源编辑式对比与解耦

本文定义两个生成算子：$E = f_{ed}(P)$ 生成模型自产编辑式，$C = f_{code}(P, E)$ 生成条件代码。核心创新在于引入“金标编辑式”（Gold Editorial）作为参照系。设 $E^*$ 为专家编写的验证过的解题计划，则定义三种条件：

$$
\begin{aligned}
\text{w/oEd: } & C_0 = f_{code}(P, \emptyset) \\
\text{w/GenEd: } & C_1 = f_{code}(P, f_{ed}(P)) \\
\text{w/GoldEd: } & C_2 = f_{code}(P, E^*)
\end{aligned}
$$

通过比较 $C_2$ 与 $C_1$ 的通过率差异，可分离“实现瓶颈”（$C_2$ 仍失败的部分）与“解题瓶颈”（$C_2$ 通过但 $C_1$ 失败的部分）。这一设计解决了此前方法中“失败归因不明”的失效，使得模型在给定正确计划下的表现成为实现能力的纯度量，而自生成编辑式与金标编辑式的差距则直接反映模型算法规划的可靠性。

### 专家标注与LLM-as-a-Judge验证

为诊断编辑式质量，本文构建了三维标注体系：问题理解（PU）、算法描述（ALG）及算法正确性（ALG-COR）。设计动机在于量化“为什么”自生成编辑式会误导代码生成。标注由IOI奖牌获得者执行，并验证了LLM-as-a-Judge协议与专家判断的一致性。该机制将定性分析转化为可复现的标签，使得“推理错误”不再是黑盒，而是可分类（如“错误算法”、“次要编辑需求”）的实体。

## 实验评估

实验在83道ICPC风格题目上进行，覆盖19个前沿模型，使用C++作为主语言。基线覆盖闭源推理模型（GPT-5, O3, Gemini 2.5 Pro）与开源模型（DeepSeek-R1, Qwen3-Coder等），但缺失早期基线如AlphaCode，且未包含仓库级基准如SWE-bench的对比，限制了跨范式比较。

| 模型组 | 条件 | 整体 Pass@1 (%) | T1 (易) | T2 (中) | T3 (难) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 闭源平均 | w/oEd | 32.5 | 52.4 | 32.6 | 14.7 |
| 闭源平均 | w/GoldEd | 52.0 | 75.0 | 56.2 | 27.2 |
| 开源平均 | w/oEd | 16.4 | 33.2 | 14.6 | 3.1 |
| 开源平均 | w/GoldEd | 27.4 | 49.0 | 26.6 | 8.8 |
| 整体平均 | w/GenEd | 23.1 | 43.1 | 21.6 | 6.5 |

金标编辑式带来显著增益：整体平均Pass@1从23.2%升至37.7%（+14.5pp），其中T1提升18.6pp，T3提升8.5pp。相比之下，自生成编辑式（w/GenEd）整体仅-0.1pp，且在T3上为-1.5pp，表明模型自产推理常具误导性。统计检验显示，金标编辑式增益的95%置信区间为[+12.30, +16.80]，稳健排除零；而自生成编辑式区间为[-1.90, +1.71]，跨越零，证实其效果不可靠。

消融分析揭示，DeepSeek-R1是唯一自生成编辑式增益显著（+16.9pp）的模型，暗示其推理链与代码生成高度对齐。失败模式分析显示，即使提供金标编辑式，WA（错误答案）仍占主导，TLE（超时）在强模型中占比上升，表明“实现瓶颈”主要源于效率优化而非逻辑错误。

评估边界方面，83题样本量导致T3子集统计功效有限，部分模型间微小差异（<5pp）可能不具显著性。代码未公开完整复现脚本，仅提供项目页面，且Python与C++性能差异未深入归因，可能受训练数据偏差影响。

## 关联研究分析

从问题动机看，本文与Coding Triangle（Zhang et al., 2025）同属“解耦评估”路线，但后者侧重通用代码生成中的编辑式-代码-测试三角验证，而本文聚焦CP特有的时限与内存约束。关键差异在于：Coding Triangle假设编辑式是通用中间态，而本文证明在CP中，编辑式的质量直接决定代码的可行性，且“金标”与“自生成”编辑式的差距是模型能力差异的核心来源。这一差异源于CP任务的强约束性：算法复杂度必须严格匹配时限，使得“正确但低效”的编辑式在CP中无效，而在通用代码生成中可能仍可通过测试。

从方法设计看，本文与LiveCodeBench（Jain et al., 2025）共享防污染目标，但LiveCodeBench通过动态更新题目解决数据污染，本文则通过选用非主流平台（NUS/ICPC Regional）题目实现静态防污染。然而，本文未采用LiveCodeBench的时间维度评估，导致无法衡量模型在“新题”上的泛化能力，仅能反映在“旧题”上的推理-实现解耦效果。这种取舍使得本文结果更适用于诊断模型内部机制，而非评估其持续学习能力。

## 总结

本文要解决的核心矛盾是CP评估中推理与实现的混淆，导致失败归因不明。其切入点是引入编辑式作为显式中间态，通过金标与自生成编辑式的对比，数学上隔离两个环节。实验证明，金标编辑式使整体Pass@1提升14.5pp，而自生成编辑式无显著增益，揭示了模型“解题”能力的普遍短板。本文的边界在于83题的小样本规模限制了统计稳健性，且仅覆盖C++/Python，未探索多语言泛化。当支持集扩展到数千题时，金标编辑式增益的边际收益是否递减，论文未给出回答。
