# ACL-Findings2026最新论文 ｜Train in Vain: Functionality-Preserving Poisoning to Prevent Unauthorized Use of Code Datasets ｜功能性保持的代码数据集投毒

作者：Yuan Xiao、Jiaming Wang、Yuchen Chen 等 11 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.22291)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_e595236c6d67)

> 代码大语言模型（CodeLLMs）的预训练依赖海量公开代码，但数据所有者缺乏阻止未授权微调的技术手段。现有投毒方法如 CoProtector 通过破坏语法或语义来降低模型效用，导致代码无法编译或功能失效，无法在真实发布场景中部署。本文提出 FUNPOISON，通过向执行路径注入可编译、无副作用的弱用代码片段，在保持 100% 功能正确性的前提下，仅污染 10% 数据集即可显著抑制未授权微调收益。该方法在隐蔽性和鲁棒性上优于基线，但其对语义级异常检测的抵抗能力及跨语言泛化性仍存疑。

## 研究背景

代码数据集的版权保护面临“可用性”与“安全性”的冲突。若直接修改代码以阻止训练，会破坏开发者的正常使用体验；若仅依赖许可证声明，则缺乏技术强制力。数据集投毒（Dataset Poisoning）作为一种主动防御机制，旨在通过扰动数据降低未授权模型的训练收益，但其核心挑战在于如何在不破坏代码可编译性（Compilability）和功能正确性（Functional Correctness）的前提下，有效干扰模型的自回归学习过程。

现有主流投毒路线以 CoProtector（Sun et al., 2022）为代表，其采用代码损坏（CC）、拼接（CS）、重命名（CR）及注释反转（CSR）四种变换。然而，CC、CS 和 CR 直接破坏语法结构，导致编译失败，仅适用于内部测试而非公开数据集；CSR 虽保持可编译性，但仅改变注释语义，对基于代码逻辑的微调影响微弱，且在部分投毒（Partial Poisoning）场景下无法有效抑制性能增益。CoProtector 的局限性在于其假设“全量投毒”且容忍代码质量下降，这与实际场景中“部分污染”且“必须保持可用”的需求相悖。本文切入点在于设计一种“功能性保持”的投毒机制，即注入的代码片段在运行时完全惰性（Execution-inert），但在训练时通过占用执行路径的 token 监督信号，干扰模型对正确代码模式的拟合。

## 核心方法

### 方法参照系

代码数据集投毒的通用流程包含模板生成、安全过滤与受控注入。与文本领域投毒不同，代码投毒必须满足严格的编译约束和类型安全约束。本文的关键差异在于引入“弱用合成”（Weak-use Synthesis）机制，将传统的破坏性变换转化为语义中性的变量消费操作，从而在保留代码结构完整性的同时实现训练干扰。

### 编译驱动模板生成

传统投毒直接使用原始代码片段，往往因依赖缺失或上下文耦合导致注入后编译失败。本文在模板生成阶段引入编译修复（Compilation Repair）机制，将语句级片段重构为独立可编译单元。对于引用类型，JDK 类通过显式导入解决，非 JDK 类替换为轻量级桩（Stub）；裸分配（Bare Allocation）重写为赋值语句以消除静态分析警告。该过程确保每个模板 $t$ 满足独立编译约束：

$$
\text{Compile}(t) = \text{True} \land \text{SideEffect}(t) = \emptyset
$$

这一设计解决了 CoProtector 中 CC/CS 变换导致编译率趋近于零的问题，使得投毒后的数据集在静态检查下与干净数据无异，提升了隐蔽性。

### 弱用合成与执行路径注入

模板生成后，直接注入可能因变量冲突或副作用破坏宿主程序。本文通过弱用合成模块，为模板中的每个变量生成类型匹配的“弱用表达式”（如装箱、身份哈希、守卫大小检查），这些表达式消耗变量但不改变程序状态。注入位置选择执行路径上的“惰性接缝”（Inert Seams），即前驱语句为纯声明或无副作用表达式的代码位置。注入后的代码 $c'$ 满足：

$$
\text{Behavior}(c') = \text{Behavior}(c) \land \text{Tokens}(c') \supset \text{Tokens}(c)
$$

其中 $\text{Behavior}$ 指运行时输出与副作用，$\text{Tokens}$ 指自回归训练时的 token 序列。该机制确保运行时行为不变，但训练时模型需拟合额外的弱用 token，从而稀释正确代码的监督信号。相比 CoProtector 的 CSR 仅修改注释（不参与代码逻辑训练），FUNPOISON 直接干扰代码逻辑区域的 token 分布，因此在部分投毒下具有更强的抑制效果。

## 实验评估

实验在 HumanEval-X 和 MBPP 上评估 DeepSeek-Coder（1.3B/6.7B）、StarCoderBase（1B）及 CodeLlama-7B。基线包括 CoProtector 的四种变换及 DeadBranchInsertion 消融实验。主结果显示，在 10% 投毒率下，FUNPOISON 使 DeepSeek-Coder-1.3B 的 Pass@1 从 0.38 降至 0.20（$\Delta$-0.18），而 CoProtector 的 CSR 在相同条件下无显著下降，CC/CS/CR 因编译失败无法评估。

| 方法 | 投毒率 | Pass@1 (T=0.0) | 编译率 |
| :--- | :--- | :--- | :--- |
| Base Model | - | 0.31 | 100% |
| Clean Fine-tuned | 0% | 0.38 | 100% |
| FUNPOISON | 10% | 0.20 | 100% |
| CoProtector (CSR) | 10% | 0.38 | 100% |
| CoProtector (CC) | 100% | 0.00 | <1% |

消融实验表明，DeadBranchInsertion（将模板置于恒假分支）在 10% 投毒下 Pass@1 为 0.38，与干净微调无差异，证明性能下降源于执行路径上的 token 监督，而非模板本身的暴露。鲁棒性测试中，FUNPOISON 在 CodeQL 静态分析下误报率为 4.3%，在 GPT-4 重写攻击下 CodeBLEU 仅为 0.06，表明其能抵抗常见的净化与重写防御。

评估边界方面，实验仅覆盖 Java 语言，未验证跨语言泛化性；投毒率上限为 100%，但未探讨极低投毒率（<1%）下的阈值效应。代码已开源，但超参数（如模板池大小、注入密度）对效果的敏感性分析未在正文中详细展开。

## 关联研究分析

从问题动机看，本文与代码水印（Code Watermarking）形成互补而非竞争关系。水印（如 Sun et al., 2023）依赖事后归因，需保留水印检测器且易被微调抹除；FUNPOISON 提供事前威慑，通过降低数据效用直接阻止未授权训练，无需事后检测。然而，水印可定位具体侵权者，而投毒无法区分未授权用户与授权用户，若授权用户也使用投毒数据，其模型性能同样受损，这是投毒方案在部署上的固有局限。

从方法设计看，本文与文本领域投毒（如 TextFooler）的核心差异在于约束强度。文本投毒仅需保持语义相似，而代码投毒必须满足编译与类型安全。本文通过“编译修复”和“弱用合成”解决了这一约束，但引入了新的隐蔽性挑战：弱用表达式（如 `Integer.valueOf(x)`）在真实代码中虽常见，但在特定上下文中可能显得冗余。论文未评估基于语义异常检测（如检测冗余变量消费）的防御效果，仅测试了基于规则的重写和静态分析。若攻击者使用 LLM 进行语义级净化，识别并移除这些“无意义”的弱用语句，FUNPOISON 的鲁棒性可能下降，这一点在现有实验中未得到验证。

## 总结

本文解决的核心矛盾是代码数据集保护中“可用性”与“安全性”的冲突。现有方法如 CoProtector 因破坏编译性或功能正确性而无法在公开场景部署，本文通过弱用合成与执行路径注入，在保持 100% 编译率和功能正确性的前提下，实现了 10% 投毒率下的有效性能抑制（Pass@1 从 0.38 降至 0.20）。其边界在于实验仅覆盖 Java 语言，且未验证对语义级异常检测的抵抗能力。当攻击者使用具备代码理解能力的 LLM 进行净化时，弱用表达式的隐蔽性是否足以维持投毒效果，论文未给出回答。
