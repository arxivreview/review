# ACL-Findings2026最新论文 ｜What Prompts Don’t Say: Understanding and Managing Underspecification in LLM Prompts ｜提示词欠定：需求感知优化与稳定性治理

研究机构：美国卡内基梅隆大学

作者：Chenyang Yang、Yike Shi、Qianou Ma 等 6 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_4054c1974d7b)

> 提示词工程面临的核心矛盾在于，开发者难以穷尽所有业务需求，而大语言模型（LLM）对未明确指定的行为表现出高度不稳定性。现有自动优化方法（如 APE、TextGrad）仅关注整体性能指标，缺乏对单一需求满足率的细粒度反馈，导致优化结果在模型更新后极易回归。本文切入点在于将传统软件工程中的“需求工程”引入提示词优化，通过需求感知优化器（Requirements-Aware Optimizers）显式管理“指定”与“未指定”需求的边界。其价值在于揭示了“全量指定”的反模式，但其在通用推理基准上的泛化能力仍存疑。

## 研究背景

当开发者构建 LLM 应用时，提示词往往仅覆盖部分显式需求，而大量隐性需求（如天气预警、签证提醒）处于未指定状态。这种遗漏被称为提示词欠定（Prompt Underspecification），即提示词中缺少关键需求，导致多种有效但不一致的行为成为可能。欠定并非简单的信息缺失，而是引发了模型行为的不可预测性：LLM 可能默认遵循某些需求，也可能完全忽略，且这种默认行为随模型版本更新剧烈波动。

传统提示词优化路线（如 APE、TextGrad）将提示词视为黑盒变量，通过迭代搜索最大化整体任务准确率。然而，这种“需求无关”（Requirement-Agnostic）的优化忽略了需求的独立性：当模型更新时，未指定需求的满足率可能大幅下降，而整体准确率因其他指定需求的提升而掩盖了这一回归。现有方法缺乏对“哪些需求必须显式指定”以及“哪些需求可依赖模型默认行为”的区分机制，导致开发者在部署后面临持续的行为漂移风险，无法建立稳定的用户心智模型。

## 核心方法

### 需求感知优化框架

本文方法置于自动提示优化（Automatic Prompt Optimization, APO）范畴，但关键差异在于优化目标的分解。传统 APO 优化单一标量指标（如准确率），而本文引入需求特定验证器（Requirement-Specific Validators），将优化目标分解为每个需求的满足率。这一设计解决了传统方法无法区分“指定需求失效”与“未指定需求回归”的问题，使得优化器能够针对具体需求进行反馈。

### 需求子集选择与指定策略

传统做法倾向于在提示词中罗列所有需求，但本文发现这会导致指令遵循能力过载。为此，本文提出两种需求感知优化器：COPRO-R 与 Bayesian Optimizer。COPRO-R 增强现有优化器，利用需求特定验证器提供细粒度反馈，优化“如何指定”需求（如重排序、合并）。Bayesian Optimizer 则优化“指定哪些”需求，通过贝叶斯搜索确定最优需求子集，移除模型能默认遵循的需求。

COPRO-R 的优化过程可形式化为：

$$
\theta^* = \arg\max_{\theta} \frac{1}{|R|} \sum_{r \in R} \mathbb{E}_{x \sim D} [V_r(f_\theta(x))]
$$

其中 $R$ 为需求集合，$V_r$ 为需求 $r$ 的验证器，$f_\theta$ 为提示词策略。该公式表明，优化目标不再是单一任务得分，而是所有需求（无论是否显式指定）满足率的均值，从而强制优化器关注被遗漏的需求。

Bayesian Optimizer 的核心在于需求子集选择。设 $S \subseteq R$ 为选定的指定需求子集，优化目标为：

$$
S^* = \arg\max_{S \subseteq R} \left( \text{Acc}(S) - \lambda \cdot |S| \right)
$$

其中 $\text{Acc}(S)$ 为指定子集 $S$ 后的平均准确率，$|S|$ 为需求数量，$\lambda$ 为正则化系数。该公式体现了“选择性指定”策略：通过惩罚需求数量，优化器倾向于移除那些模型能默认满足的需求，从而在保持性能的同时缩短提示词长度，缓解指令遵循过载。

## 实验评估

实验在三个任务（代码解释、旅行顾问、产品生成）上进行，使用 Llama-3.3-70B-Instruct、gpt-4o-2024-08-06 和 o3-mini 三个模型。基线包括 OpenAI Prompt Optimizer 和 COPRO。本文未对比 TextGrad 或 GEPA 等前沿优化器，但指出传统优化器在旅行顾问任务上性能下降 1.1%，而在其他任务上仅提升 2.8%，缺乏一致性。

| 优化器 | 平均准确率提升 (%) | Token 使用变化 (%) | 备注 |
| :--- | :--- | :--- | :--- |
| COPRO-R | +5.8 | - | 重排序与合并需求 |
| Bayesian Optimizer | +3.8 | -41 to -45 | 移除默认满足的需求 |
| OpenAI Optimizer | +2.8 (avg) | - | 旅行顾问任务 -1.1 |
| COPRO | +2.8 (avg) | - | 旅行顾问任务 -1.1 |

Bayesian Optimizer 在提升准确率 3.8% 的同时，将 Token 使用减少 41-45%，验证了“选择性指定”的有效性。消融实验显示，全局、格式和开发者编写的需求被移除的比例最高（分别为 56.5%、77.0%、57.9%），这与 LLM 能默认遵循这些需求的观察一致。

评估边界方面，本文使用自建数据集，缺乏 GSM8K 等通用推理基准的验证。LLM 验证器与人工标注的一致率为 95.6%，但需求列表的构建依赖人工筛选，可能存在偏差。代码已开源，但超参数（如贝叶斯优化的迭代次数）未在正文中详细披露，复现性依赖附录。

## 关联研究分析

从问题动机看，本文与 DSPy 的声明式编程思想同源，但 DSPy 侧重于模块化的提示词合成与测试，而本文聚焦于需求粒度的稳定性治理。DSPy 假设提示词结构可通过编译优化，但未显式处理“未指定需求”的回归风险；本文则通过需求验证器量化了这种风险，并证明“全量指定”反而导致性能下降 19%，这与 DSPy 追求完整指令遵循的隐含假设形成冲突。这一差异源于任务特性：DSPy 多用于结构化输出任务，而本文针对开放域应用，其中隐性需求对用户体验至关重要。

从方法设计看，本文的 Bayesian Optimizer 与 TextGrad 的梯度驱动优化形成对比。TextGrad 通过文本梯度迭代修订提示词，但缺乏需求特定反馈，导致优化方向模糊；本文通过需求验证器提供细粒度信号，使得优化器能够区分“需求冲突”与“指令过载”。然而，本文未探索 TextGrad 与需求感知的结合，即是否可以通过需求特定的文本梯度加速收敛。这一盲区可能源于计算成本：需求验证器需要多次 LLM 调用，而 TextGrad 的梯度计算已较昂贵，两者结合可能面临效率瓶颈。

## 总结

本文解决的核心矛盾是 LLM 应用开发中“需求遗漏”与“模型行为不稳定”之间的耦合问题。现有方法因缺乏需求粒度反馈，无法区分指定与未指定需求的回归，导致优化结果脆弱。本文通过引入需求感知优化器，显式管理需求指定边界，证明了“选择性指定”优于“全量指定”。实验表明，Bayesian Optimizer 在提升准确率 3.8% 的同时减少 41-45% 的 Token 使用，验证了该策略的有效性。然而，本文的局限在于仅在三个自建任务上验证，且未对比 TextGrad 等前沿优化器，其方法在通用推理任务上的泛化能力未知。当任务复杂度增加至多跳推理时，需求子集选择的贝叶斯搜索空间是否呈指数增长，论文未给出回答。
