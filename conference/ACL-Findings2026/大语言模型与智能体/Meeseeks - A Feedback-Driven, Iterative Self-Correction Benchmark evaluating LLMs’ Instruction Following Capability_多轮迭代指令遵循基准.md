# ACL-Findings2026最新论文 ｜Meeseeks: A Feedback-Driven, Iterative Self-Correction Benchmark evaluating LLMs’ Instruction Following Capability ｜多轮迭代指令遵循基准

研究机构：美团

作者：Jiaming Wang、Yunke Zhao、Peng Ding 等 10 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_8021b9dbd77d)

> 大语言模型在单次响应中难以同时满足复杂多约束指令，而现有评估基准仅关注单轮静态表现，无法量化模型在反馈驱动下的自我修正上限。Meeseeks 通过引入 20 轮迭代反馈机制，将评估从“单次成功率”转向“能力上限探测”，并采用代码引导的规则增强评估框架解决长文本提取的准确性与成本瓶颈。该基准揭示了模型单次表现与最终能力上限的巨大差距，但受限于自建数据集分布，其结论在跨基准泛化性上仍存疑。

## 研究背景

当用户要求 LLM 生成一篇包含特定关键词、字数限制及格式规范的报告时，模型往往在单次生成中遗漏部分约束。这种失败源于指令遵循任务中约束间的逻辑依赖与冲突，传统单轮评估基准（如 IFEval）仅记录首次响应是否满足所有条件，无法区分“模型完全不会”与“模型能学会但首次失误”。为量化后者，需引入迭代反馈机制，使模型在接收到具体违规反馈后尝试修正，从而逼近其真实能力边界。

指令遵循评估领域长期聚焦于单轮交互的静态验证，IFEval 确立了规则可验证指令的范式，FollowBench 扩展至多约束层级，但均假设模型仅有一次作答机会。随着应用场景复杂化，多轮对话中的指令稳定性成为新瓶颈，现有基准缺乏对模型自我修正能力的系统评估。Meeseeks 的切入点在于将评估过程重构为“响应-评估-反馈-修正”的闭环循环，通过 20 轮迭代探测模型在持续反馈下的性能上限，而非仅记录单次表现。

## 核心方法

### 迭代反馈评估框架

Meeseeks 的核心流程包含响应收集、约束评估与反馈提示三个环节。给定含多重约束的指令，每轮迭代首先收集模型响应，随后通过规则脚本与 LLM 评估器联合判断各约束满足情况，最后将违规原因作为反馈注入下一轮提示。该框架的关键差异在于允许模型在同一指令下多次修正，而非每轮引入新指令。

### 代码引导的规则增强评估

传统方法依赖 LLM 重新生成清理后的文本以提取关键信息，这在长文本或多元素场景下导致高计算成本与准确性下降。Meeseeks 提出代码引导评估，让 LLM 生成 Python 函数直接从原始响应中提取目标内容，避免文本再生成。设原始响应为 $R$，提取函数为 $f_{extract}$，则评估输入为 $C = f_{extract}(R)$，其中 $C$ 为结构化数据（如列表）。该设计将提取过程从语义生成转为程序执行，显著降低 token 消耗并提升边界情况处理的鲁棒性。

### 认知维度能力标签体系

Meeseeks 将指令遵循分解为意图识别、细粒度内容验证与输出结构验证三个认知维度，下设 32 个能力标签。每个标签对应特定约束类型（如字数范围、关键词包含），并定义依赖关系。例如，子问题 2 依赖子问题 0，若模型在子问题 0 失败，则自动判定子问题 2 失败。该层级结构实现了约束间的错误传播建模，使评估结果能反映模型在不同认知层面的具体缺陷，而非仅给出整体通过率。

## 实验评估

实验在 Meeseeks 自建数据集（700+ 实例，中英双语）上进行，对比 17 个 SOTA 模型在 20 轮迭代中的表现。基线覆盖商业 API（GPT-4.1, Claude Sonnet 4）与开源模型（DeepSeek-V3.1, Qwen3-235B），但未对比其他多轮评估框架（如 Parrot, Multi-IF）。

| 模型 | Turn 1 Utility Rate | Turn 20 Utility Rate | 提升幅度 |
|---|---|---|---|
| Claude Sonnet 4 Thinking | .438 | .905 | +0.467 |
| o3-mini (high) | .567 | .846 | +0.279 |
| DeepSeek-V3.1 | .371 | .791 | +0.420 |
| Qwen3-14B | .348 | .465 | +0.117 |

代码引导评估在大规模多元素场景下将端到端准确率从 0.684 提升至 0.994，token 消耗从 874.65 降至 252.94，降幅 71.08%。在长单元素场景下，准确率从 0.5 提升至 0.998，验证了代码引导方法在复杂文本处理中的有效性。

消融实验显示，推理模型在多轮修正中表现优于非推理模型，尤其在字数约束任务中，推理模型通过内部计算预确定内容长度，缓解了非推理模型的“灾难性过度修正”现象。例如，当要求 400 词时，非推理模型从 300 词反馈后可能跳至 600 词，而推理模型能逐步收敛。

评估边界方面，Meeseeks 未报告置信区间，且数据集源自业务日志，可能存在领域偏差。代码开源（GitHub），但超参数与 GPU 需求未详细披露，复现性依赖商业 API 或 Qwen2.5-32B 部署（约 80GB 显存）。

## 关联研究分析

从问题动机看，Meeseeks 与 IFEval 的根本差异在于评估目标：IFEval 关注单次响应的约束满足率，而 Meeseeks 关注模型在反馈下的修正能力上限。这一差异源于任务特性——实际应用中用户常需多轮交互，单次失败可接受，但无法自我修正则不可用。Meeseeks 通过迭代机制揭示了模型单次表现与能力上限的差距，这是单轮基准无法捕捉的维度。

从方法设计看，Meeseeks 与 Complexbench 均采用规则增强 LLM 评估，但 Meeseeks 引入代码引导提取替代文本再生成。这一改进解决了长文本场景下 LLM 提取的准确性瓶颈，但可能引入新的偏差：代码生成错误可能导致提取失败，进而影响评估准确性。论文未量化代码生成错误的频率及其对最终评估结果的影响，这一盲区在复杂约束场景下可能放大评估误差。

## 总结

Meeseeks 要解决的核心矛盾是现有基准无法区分模型“不会”与“能学会但首次失误”，其切入点在于引入 20 轮迭代反馈机制，将评估从静态单次表现转向动态能力上限探测。通过代码引导评估框架，Meeseeks 将评估准确率从 78.7% 提升至 98.4%，并揭示即使经过 20 轮修正，所有模型准确率均未超过 91%。本文的边界在于数据集源自业务日志，缺乏跨基准泛化验证，且代码引导提取的潜在偏差未被量化。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
