# ACL-Findings2026最新论文 ｜ContractEval: A Benchmark for Evaluating Contract-Satisfying Assertions in Code Generation ｜契约满足评估基准

研究机构：韩国延世大学

作者：Soohan Lim、Joonghyuk Hahn、Hyunwoo Park 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2510.12047)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2510.12047)

> 现有代码生成基准仅验证良构输入下的功能正确性，导致模型在拒绝非法输入这一关键防御机制上存在盲区。HumanEval+等基准虽标注了契约字段，却将其用于过滤违规测试而非评估拒绝行为，使得“契约满足”这一维度长期不可测。本文通过神经符号流水线生成精准违规测试，将契约满足率确立为独立评估轴。该工作揭示了当前大语言模型在边界防御上的系统性缺失，但其评估范围仍局限于函数级输入验证，未触及跨文件依赖或复杂类型系统的深层契约。

## 研究背景

代码生成模型在通过单元测试时，往往忽略了输入参数的合法性约束。这种“功能正确但边界脆弱”的现象源于评估范式的局限：传统基准如HumanEval和MBPP仅执行满足所有前置条件的良构输入，测试用例由构造保证合法，因此无法暴露模型对非法输入的静默接受行为。在真实软件开发中，开发者普遍使用断言语句在函数入口执行输入验证，这种基于设计契约（Design by Contract, DbC）的防御机制是软件鲁棒性的基石。然而，现有评估体系将契约视为过滤条件而非评估目标，导致模型生成的代码即使通过所有测试，也可能在遇到违反契约的输入时崩溃或产生错误结果。

该领域长期面临功能正确性与非功能质量脱节的问题。主流路线如SWE-bench聚焦仓库级Issue修复，TREAT框架关注鲁棒性波动，但均未专门针对“输入验证契约”这一细粒度维度。HumanEval+和MBPP+虽然引入了契约字段，但其评估逻辑是剔除违规输入，而非验证模型是否主动拒绝这些输入。这种设计使得契约满足成为评估盲区，模型无需实现任何断言检查即可获得高分。ContractEval的切入点在于反转这一逻辑：不再过滤违规输入，而是将其作为测试用例，直接执行以检验生成代码的拒绝能力。这一转变将契约满足从隐含假设转化为可量化的评估指标，填补了现有基准在边界防御评估上的空白。

## 核心方法

### 方法参照系

本文问题置于代码质量与非功能评估路线下。标准流程通常依赖静态分析或通用鲁棒性测试，但缺乏对特定契约条款的精准定位。本文的关键差异在于引入神经符号流水线，将自然语言契约转化为形式化约束，并通过求解器生成逻辑一致的违规测试，从而实现对契约满足率的确定性评估。

### 神经符号违规测试生成

CVT（Contract-Violating Tests）的生成是本文的核心创新，旨在解决人工构造测试用例可能存在的语义偏差和逻辑不一致问题。传统方法依赖LLM直接生成违规输入，但LLM可能触发非目标断言或产生逻辑冲突。本文采用两阶段流水线：首先，LLM将参考断言翻译为SMT-LIB约束，基于代数数据类型（ADT）模板统一表示整数、浮点数、字符串及嵌套容器；其次，SMT求解器枚举所有非空契约子集，对目标子集取反并强制满足其余约束，求解满足赋值。该过程确保生成的CVT仅违反指定契约，且在其他约束下保持功能可行。

$$
\text{SMT Query} = \neg (\bigwedge_{a_i \in V_t} a_i) \land (\bigwedge_{a_j \in A \setminus V_t} a_j)
$$

其中 $V_t$ 为目标违反子集，$A$ 为全部断言集合。该公式的物理含义是：构造一个输入，使其恰好违反 $V_t$ 中的所有断言，同时满足其余所有断言，从而精准定位特定契约的缺失。

### 契约满足率度量

为量化生成代码的契约执行能力，本文提出契约满足率（CSR）。CSR通过执行验证后的CVT集合，计算生成代码成功拒绝违规输入的比例。该指标直接反映代码是否实现了预期的断言检查，而非依赖文本相似度或LLM主观判断。

$$
\text{CSR} = \frac{|T_{\text{rej}}|}{|T_{\text{ver}}|}
$$

其中 $T_{\text{ver}}$ 为经过可行性过滤的验证CVT集合，$T_{\text{rej}}$ 为生成代码 $C$ 通过抛出断言错误或显式拒绝而成功拦截的输入子集。该公式表明，CSR越高，生成代码对契约的强制执行越可靠。此外，本文还引入断言违反捕获率（AVC）和目标特异性（TS）验证CVT质量，确保测试用例本身的有效性。

## 实验评估

实验基于HumanEval+和MBPP+构建的364个任务，平均每个任务包含2.29个断言和13.48个验证CVT。基线覆盖五个开源模型（DeepSeek-R1, gemma-3, Phi-4, Phi-4-plus, Qwen-3）及两个商业模型（GPT-4o, Gemini-3-flash），但未对比专用代码编辑模型或仓库级评估框架。主实验结果显示，标准提示下所有模型CSR均为0.00%，而pass@1在75%-82%之间，揭示了功能正确性与契约满足的严重脱节。

| 模型 | 提示条件 | pass@1 (%) | CSR (%) |
|---|---|---|---|
| DeepSeek-R1 | Standard | 80.81 | 0.00 |
| DeepSeek-R1 | EAS | 70.87 | 53.05 |
| gemma-3 | Standard | 81.76 | 0.00 |
| gemma-3 | EAS | 69.56 | 41.74 |
| Phi-4 | Standard | 75.39 | 0.00 |
| Phi-4 | EAS | 72.99 | 69.33 |
| GPT-4o | Standard | 90.04 | 0.00 |
| GPT-4o | EAS | 75.45 | 56.51 |

消融实验表明，示例增强规范（EAS）相比契约规范（CS）平均提升50.94%p的CSR，同时保留92%的原始pass@1。这一发现表明契约检查对功能主体具有加性而非替代性，轻微的pass@1下降源于干扰效应而非结构性权衡。然而，思维链（CoT）策略在Phi-4和Phi-4-plus上导致pass@1和CSR双双崩溃至0-4%，说明CoT在需要同时保持可执行性和拒绝行为的场景中不适用。多轮策略则稳定提升pass@1约1.8%p，但伴随2-7%p的CSR下降，反映优化过程倾向于优先保留功能行为。

评估边界方面，CSR指标依赖SMT求解器的逻辑一致性，但ADT模板对复杂嵌套类型的可扩展性未充分验证。评估协议局限于函数级输入验证，未涵盖跨文件依赖或全局状态契约。可复现性方面，代码已开源，但SMT求解器的具体配置和ADT模板细节仅在附录中简要描述，缺乏完整的超参数列表。

## 关联研究分析

从问题动机看，ContractEval与TREAT框架均关注代码非功能质量，但TREAT侧重鲁棒性波动和专业化程度，采用通用编码任务和多模态任务，而ContractEval聚焦输入验证契约，采用确定性SMT求解生成精准违规测试。这一差异源于任务特性：鲁棒性评估需覆盖多种故障模式，而契约评估需精准定位特定约束的违反。ContractEval的神经符号流水线解决了TREAT中LLM生成测试可能存在的逻辑不一致问题，但牺牲了对复杂类型系统的泛化能力。

从方法设计看，ContractEval与SWE-bench同属执行导向评估，但SWE-bench聚焦仓库级Issue修复，依赖多文件上下文和代理式工作流，而ContractEval局限于函数级输入验证，依赖单文件断言检查。这一差异反映了评估粒度的不同：SWE-bench评估模型在复杂工程环境中的综合能力，而ContractEval评估模型在边界防御上的细粒度能力。ContractEval的契约-规范对齐过滤机制确保了测试用例与任务描述的语义一致性，这是SWE-bench中未明确强调的环节。然而，ContractEval未探索跨文件契约或全局状态验证，这在真实软件工程中更为常见。

## 总结

ContractEval解决了功能正确性与契约满足脱节的核心矛盾，通过神经符号流水线生成精准违规测试，将契约满足率确立为独立评估轴。实验证明，标准提示下模型CSR为0.00%，而EAS提示下提升至49-53%，揭示了当前模型在边界防御上的系统性缺失。本文的边界在于评估范围局限于函数级输入验证，未触及跨文件依赖或复杂类型系统的深层契约。当支持集增大到多文件仓库级任务时，契约满足率的评估是否仍能有效区分模型能力，论文未给出回答。
