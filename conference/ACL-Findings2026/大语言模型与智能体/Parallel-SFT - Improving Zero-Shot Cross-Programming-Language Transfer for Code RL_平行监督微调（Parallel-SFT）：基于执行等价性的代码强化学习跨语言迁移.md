研究机构：美国麻省理工学院

作者：Zhaofeng Wu、Shiqi Wang、Boya Peng 等 8 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_e95b94477403)

> 导读 代码强化学习（RL）在源编程语言上获得的策略增益，往往无法零样本迁移至目标语言，甚至导致性能退化。现有方法依赖自然语言中天然存在的平行文本对齐表示空间，但代码语料缺乏此类信号，导致模型陷入语法中心而非功能中心的表示陷阱。本文提出 Parallel-SFT，通过合成跨语言功能等价程序构建平行语料，在监督微调阶段对齐表示空间，从而提升后续 RL 阶段的跨语言迁移能力。该方法在 Llama-3.1-8B 上验证了有效性，但其对大规模模型及非执行等价语义迁移的适用性尚存疑。

## 研究背景

当模型在 Python 上通过 RL 优化了算法解题策略后，直接将其应用于 Go 或 Ruby 时，性能不仅未提升，反而可能下降。这一现象源于代码表示空间的碎片化：模型将不同编程语言的语法结构映射到独立的子空间，而非共享的语义空间。解决此问题的关键在于建立跨语言的语义对齐，即让模型理解“二分查找”在 Python 和 Java 中是同一逻辑的不同实现，而非两种独立的语法模式。

代码生成领域的主流路线聚焦于数据合成与推理增强，旨在提升单语言下的正确率与鲁棒性。然而，这些方法通常假设训练与测试语言一致，忽略了低资源语言的性能瓶颈。多语言自然语言处理（NLP）研究表明，平行文本是构建语言通用表示的关键，但代码文件几乎 exclusively 为单语言，且不同语言常服务于不同领域（如 Python 用于 AI，C++ 用于系统），导致自然平行信号缺失。本文切入点在于：既然自然平行信号缺失，是否可以通过合成“平行程序”——即同一自然语言指令在不同语言下的功能等价实现——来人工构建对齐信号，从而修复 RL 阶段的跨语言迁移失效？

## 核心方法

### 方法参照系

标准代码后训练流程包含预训练、监督微调（SFT）与 RL 三个阶段。SFT 阶段通常使用单一语言或混合语言数据，但缺乏显式的跨语言对齐机制。本文问题与该通用流程的关键差异在于：SFT 数据不再仅关注指令-代码对的多样性，而是强制要求同一指令在不同语言下的代码实现构成“平行组”，以诱导功能中心表示。

### 平行程序合成与数据构造

设计动机在于解决代码语料中“局部”与“全局”平行信号的双重缺失。自然语言语料中，0.34% 的数据包含平行句对（Briakou et al., 2023），而代码文件几乎不含跨语言平行内容。本文通过合成翻译构建平行程序：利用 Llama-4-Maverick 将 Python 代码翻译为 C++、Java 等 8 种语言，并过滤未通过测试用例的翻译，确保功能等价性。SFT 数据格式定义为：

$$
\mathcal{D}_{SFT} = \left\{ \left( q_i, c_i^{Python}, c_i^{C++}, \dots, c_i^{Lang_k} \right) \right\}_{i=1}^{N}
$$

其中 $q_i$ 为自然语言指令，$c_i^{Lang}$ 为语言 $Lang$ 下通过测试的代码实现。该公式的物理含义是：模型被强制学习将同一语义 $q$ 映射到不同语法实现 $c^{Lang}$，从而在潜在空间中拉近功能等价程序的表示距离。

### 执行等价性锚定与表示对齐

设计动机在于区分“语法相似”与“功能等价”。传统多语言 SFT 仅增加语言多样性，但未显式对齐语义。Parallel-SFT 通过执行测试用例验证代码正确性，确保平行程序在功能上严格等价，而非仅表面相似。这种执行等价性锚定使得模型在 SFT 阶段即建立“功能中心”表示，而非“语法中心”表示。分析表明，Parallel-SFT 在中间层（语义推理层）显著提升了平行程序间的余弦相似度，而在首尾层（语法映射层）保持与基线相近的水平，证实了语义对齐发生在抽象推理层。

## 实验评估

实验基于 Llama-3.1-8B-Instruct，SFT 数据包含 3,111 个唯一问题，每问题平均 181 个实例，总计约 620 万实例。基线包括单语言 SFT、8 语言非平行 SFT 及 Oracle（目标语言直接训练）。RL 阶段使用 CodeForces 数据，评估 Go、PHP、Ruby 三种低资源语言的零样本迁移性能。

| 方法 | SFT 语言策略 | Go Pass@1 (%) | PHP Pass@1 (%) | Ruby Pass@1 (%) |
|---|---|---|---|---|
| 1 Language (Source) | 单语言 | 55.0 | 52.5 | 50.0 |
| 8 Languages (Non-parallel) | 多语言非平行 | 60.0 | 57.5 | 55.0 |
| 8 Languages (Parallel) | 多语言平行 | 65.0 | 62.5 | 57.5 |
| Oracle (Target) | 目标语言直接训练 | 62.5 | 60.0 | 55.0 |

Parallel-SFT 在 Go 上达到 65.0%，超越 Oracle 的 62.5%，表明平行程序对齐不仅优于单语言基线，甚至超越了目标语言直接训练的“数据丰富”场景。这一反直觉结果暗示，高质量的功能对齐可能比单纯增加目标语言数据量更有效，因为后者可能引入噪声，而前者提供了更清晰的语义结构。

消融实验显示，8 语言非平行 SFT 已优于单语言 SFT，证实多语言训练本身具有元学习效应。但 Parallel-SFT 进一步提升了 5-7.5 个百分点，证明显式平行对齐的边际收益显著。值得注意的是，当源语言为 Python 时，Parallel-SFT 在目标语言上的性能甚至超过 Oracle，这可能源于高资源语言（Python）提供了更高质量的语义锚点，使模型能更有效地利用源语言 RL 数据。

评估边界方面，实验仅在 Llama-3.1-8B 上验证，缺乏大规模模型（如 70B+）的测试，无法确认方法在更大参数下的可扩展性。此外，评估语言限于 Go、PHP、Ruby 三种，未覆盖 C、Java 等高资源语言，可能高估了迁移难度。代码未公开，超参数（如 RL 学习率、SFT 学习率）未详细报告，限制了可复现性。

## 关联研究分析

从问题动机看，本文与 SCoGen 均使用合成数据，但 SCoGen 侧重场景语境的高保真度，旨在提升单语言下的复杂任务泛化；而 Parallel-SFT 侧重跨语言功能等价性，旨在解决 RL 迁移失效。这一差异源于任务特性：SCoGen 面对的是单语言内的语境缺失，而 Parallel-SFT 面对的是跨语言的表示碎片化。若 SCoGen 引入平行程序，是否能在单语言任务上进一步提升性能？论文未给出回答。

从方法设计看，本文与 IFCodeEvolve 均关注指令遵循，但 IFCodeEvolve 通过生成器-审计器协同进化解决单语言合规问题，而 Parallel-SFT 通过执行等价性解决跨语言对齐问题。IFCodeEvolve 的审计器机制可视为一种隐式执行验证，但缺乏跨语言维度。若将 IFCodeEvolve 的协同进化机制扩展至多语言，是否能自动发现平行程序？这或许是数据合成路线的一个潜在改进方向，但本文未探索。

## 总结

本文要解决的核心矛盾是代码 RL 阶段源语言策略增益无法零样本迁移至目标语言。现有方法依赖自然语言中的平行文本对齐表示，但代码语料缺乏此类信号，导致模型陷入语法中心表示陷阱。本文抓住的切入点是：通过合成跨语言功能等价程序，人工构建平行信号，在 SFT 阶段对齐表示空间。Parallel-SFT 在 Llama-3.1-8B 上验证了有效性，Go 语言 Pass@1 达 65.0%，超越 Oracle 的 62.5%。本文的边界在于：仅在 8B 模型上验证，未覆盖高资源语言，且依赖 Llama-4-Maverick 的翻译质量。当模型规模扩大至 70B 以上时，平行程序的边际收益是否递减，还是会被更强的预训练表示所掩盖？论文未给出回答。
