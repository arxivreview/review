> 导读 代码生成模型在静态基准上接近满分，但“能写出正确代码”与“真正理解执行逻辑”之间存在断层。现有推理基准仅依赖单一标准实现和最终输出，无法区分深层语义推理与表面模式匹配。CoRE 通过构建功能等价但语法多样的多实现集合，并引入中间状态探针，联合评估实现不变性与过程透明度。该基准揭示了前沿模型的风格过拟合与表面执行现象，但其评估协议对探针难度的控制及跨语言泛化能力仍存疑。

## 研究背景

当模型在 HumanEval 上得分超过 80% 时，评估体系面临的核心困境是数据污染与任务饱和。此时，功能正确性（Pass@k）不再具备区分度，研究者需转向更深层的能力维度。代码推理（Code Reasoning）旨在验证模型是否具备模拟程序执行过程的能力，而非仅仅记忆输入-输出映射。然而，传统推理基准如 CruxEval 和 REval 存在两个结构性缺陷：一是依赖单一标准实现（Canonical Implementation），导致模型可能通过识别特定代码风格而非理解逻辑来作答；二是仅评估最终输出，将推理过程视为黑盒，无法捕捉中间状态的幻觉。

这一缺陷在模型能力跃升后变得尤为紧迫。随着 GPT-5、Claude-4.5 等模型在静态任务上表现优异，领域共识认为必须引入动态、细粒度的评估以区分“记忆”与“推理”。然而，现有方案在鲁棒性评估上存在盲区：它们未量化模型在功能等价但语法不同的代码间的一致性，也未验证模型对中间执行状态的忠实度。CoRE 的切入点正是填补这一空白，通过强制模型在多样化实现上保持一致，并深入检查中间状态，从而暴露模型推理的脆弱性。

## 核心方法

### 方法参照系

传统代码推理评估遵循“单实现-输出预测”范式，即给定一个标准代码实现 $c$ 和输入 $x$，模型预测输出 $\hat{y}$。该流程的关键差异在于，CoRE 将评估对象从单一 $c$ 扩展为功能等价实现集合 $S_P$，并将评估目标从终端输出 $\hat{y}$ 扩展至中间状态 $\hat{a}$，从而引入实现不变性与过程透明度两个新维度。

### 实现不变性评估

针对单实现评估易受风格过拟合影响的失效，CoRE 构建了由 7 个不同 LLM 生成的 255 个多样化代码实现。设计动机在于，若模型仅依赖表面语法特征，其在不同风格代码上的表现将出现显著波动。实现不变性通过严格输出一致性指标 $I$ 量化，定义为模型在所有候选实现上均正确预测输出的二元指示器：

$$
I(P) = \begin{cases} 1, & \forall c_i \in S_P, M(c_i, T_P^x) = T_P^y \\ 0, & \text{otherwise} \end{cases}
$$

该公式意味着，只要模型在任何一个功能等价实现上出错，该问题的不变性得分即为 0，从而严格惩罚风格依赖行为。

### 过程透明度与 RCS 分数

在实现不变性基础上，CoRE 进一步引入过程透明度评估，以解决“输出正确但过程错误”的表面执行问题。通过 Python 执行追踪获取中间状态真值，并利用 LLM 生成覆盖算术、逻辑、状态、边界四个维度的探针。过程保真度权重 $W_s$ 定义为正确回答的探针比例：

$$
W_s(P) = \frac{\sum_{(q_i, a_i) \in Q_P} \mathbb{1}(M(q_i, P) = a_i)}{|Q_P|}
$$

最终，推理一致性分数（Reasoning Consistency Score, RCS）定义为 $RCS(P) = I \times W_s$。这一乘积结构确保任何实现不变性的失败都会使最终分数归零，而过程保真度则对分数进行缩放，从而有效过滤出仅靠捷径推理的模型，区分真正的执行理解与表面启发式。

## 实验评估

实验在 8 个前沿 LLM 上进行，包括 GPT-5、o3、Claude-4.5 等，采用 IO、CoT、CoC 及 RHDA 提示策略。基线覆盖主流推理框架，但缺乏针对特定代码编辑或安全性的对比。CoRE 包含 60 个问题、255 个实现、1978 个样本，平均循环复杂度 5.0，每问题 7.8 个测试用例。

| 模型 | 自身代码得分 (%) | 跨模型最低得分 (%) | 鲁棒性差距 |
|---|---|---|---|
| OpenAI | 98.18 | 71.96 | 26.22 |
| DeepSeek | 88.50 | 71.96 | 16.54 |
| Gemini | 91.95 | 71.96 | 19.99 |
| Claude | 91.15 | 71.96 | 19.19 |
| Qwen | 76.23 | 71.96 | 4.27 |

数据显示，OpenAI 系模型在自身生成的代码上得分最高（98.18%），而在其他模型代码上显著下降，证实了风格过拟合的存在。Qwen 的鲁棒性差距最小（4.27%），表明其推理对代码风格的依赖较低。

消融分析显示，RCS 分数在 CoT 提示下普遍高于 IO 提示，但提升幅度有限，表明提示策略无法根本解决过程幻觉问题。设计决策上，将测试用例从 24.1 个精简至 7.8 个并未降低覆盖完整性，验证了最小覆盖子集策略的有效性。

评估边界方面，CoRE 仅覆盖 Python 语言，未涉及多语言泛化；探针由 LLM 生成并经人工验证，但探针难度分布未公开，可能影响 RCS 分数的可比性。代码已开源（https://github.com/ZJUSig/CoRE），但超参数与执行环境配置细节有限，复现成本较高。

## 关联研究分析

从问题动机看，CoRE 与 CruxEval 的核心差异在于对“理解”的定义。CruxEval 假设正确输出即代表正确推理，而 CoRE 指出输出正确性可能是表面启发式的结果。这一差异源于任务特性：CruxEval 侧重算法题的输入-输出映射，而 CoRE 关注执行过程的忠实度。CoRE 的多实现设计直接回应了 CruxEval 未解决的风格过拟合问题，但两者均未探讨模型在低资源语言上的推理一致性，这是否是语言无关的通用能力，论文未给出回答。

从方法设计看，CoRE 与 REval 在中间状态评估上存在路线分歧。REval 采用刚性模板生成探针，而 CoRE 利用 LLM 生成多样化探针并覆盖四个维度。这一差异导致 CoRE 的探针更具挑战性，但也引入了生成偏差风险。REval 的模板化设计虽缺乏灵活性，但确保了探针的确定性，而 CoRE 的 LLM 生成探针可能包含逻辑错误，尽管有人工验证，其可靠性仍低于模板方法。此外，CoRE 未对比基于变异测试的探针生成方法，这可能是一种更鲁棒的替代方案，但论文未探索此方向。

## 总结

CoRE 旨在解决代码推理评估中“输出正确但过程错误”的矛盾，通过实现不变性与过程透明度的联合评估，暴露了前沿模型的风格过拟合与表面执行现象。其核心贡献在于构建了 255 个多样化实现与 1978 个中间状态探针，并定义了 RCS 分数以量化推理忠实度。实验表明，OpenAI 系模型在自身代码上得分 98.18%，但跨模型得分降至 71.96%，证实了鲁棒性差距的存在。然而，CoRE 的边界在于其仅覆盖 Python 语言，且探针难度分布未公开，导致 RCS 分数的跨基准可比性受限。当探针难度从当前水平提升至更复杂的嵌套逻辑时，模型的过程保真度是否会出现非线性下降，论文未给出回答。
