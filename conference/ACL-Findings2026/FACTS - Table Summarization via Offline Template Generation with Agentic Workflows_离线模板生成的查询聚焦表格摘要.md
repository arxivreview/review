# ACL-Findings2026最新论文 ｜FACTS: Table Summarization via Offline Template Generation with Agentic Workflows ｜离线模板生成的查询聚焦表格摘要

作者：Ye Yuan、Mohammad Amin Shabani、Siqi Liu

论文原文见 [arXiv](https://arxiv.org/abs/2510.13920)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_4f1a9c4805b1)

> 查询聚焦表格摘要旨在根据用户意图从表格中生成叙事性洞察，而非仅返回事实值。现有方法要么暴露敏感数据，要么因缺乏可复用性导致计算冗余，且难以保证数值准确性。FACTS 通过生成可复用的离线模板（SQL查询+Jinja2渲染）解决这一矛盾，实现了隐私合规与高效推理。其价值在于将一次性推理转化为可执行资产，但模板对模式漂移的鲁棒性仍存疑。

## 研究背景

当金融分析师需要连续十年每年的总收入摘要时，传统方法面临双重困境：直接调用大语言模型（LLM）处理全表数据不仅消耗大量Token，更将敏感记录暴露给外部服务，违反HIPAA等隐私法规；而微调专用模型虽能保护数据，却需为每个新表格重新训练，无法应对同模式下的批量查询。这一矛盾源于表格摘要任务对“可复用性”与“隐私合规”的刚性需求，而现有LLM范式将推理过程与数据绑定，导致每次查询都需重复昂贵的模型调用。

表格理解领域的主流路线分为专用预训练模型、提示工程与智能体框架。TaPas等专用模型受限于泛化能力，难以适应多样化表格结构；DirectSumm等提示方法虽能直接利用LLM，但存在Token限制与幻觉风险；Binder等智能体框架通过SQL执行接地提升了准确性，却仍依赖即时规划，无法跨表格复用。FACTS的切入点在于将智能体框架的输出从“即时答案”转化为“离线模板”，通过解耦推理逻辑与数据执行，使同一模板可应用于任意同模式表格，从而在隐私约束下实现规模化摘要生成。

## 核心方法

### 方法参照系

本文问题属于智能体推理框架范畴，但与传统“规划-执行-反思”循环的关键差异在于：执行器为SQL引擎而非通用代码解释器，输出为可复用的离线模板而非即时答案。传统框架如Binder将查询即时翻译为SQL并执行，每次查询均需重新生成代码；FACTS则生成绑定于模式（Schema）的模板，将推理逻辑固化为可重复执行的资产。

### 离线模板生成机制

设计动机：解决传统智能体框架中“每次查询均需重新规划”导致的计算冗余与隐私泄露问题。FACTS将离线模板定义为复合工件，包含模式感知的SQL查询与Jinja2渲染模板。形式化地，离线模板 $\mathcal{T} = \langle \mathcal{Q}, \mathcal{R} \rangle$，其中 $\mathcal{Q}$ 为SQL查询集合，$\mathcal{R}$ 为Jinja2模板。SQL查询 $\mathcal{Q}$ 从底层表格中检索相关事实，Jinja2模板 $\mathcal{R}$ 将检索结果转化为自然语言摘要。该公式的物理含义是：模板将“数据检索”与“语言生成”解耦，SQL负责精确数值提取，Jinja2负责叙事渲染，二者共同构成可复用的推理资产。

### LLM Council验证机制

设计动机：解决单模型生成SQL与模板时的幻觉与不一致性问题。FACTS引入LLM Council，即多个异构LLM组成的验证集合，在每个阶段独立产生结构化判断（YES/NO）与反馈。形式化地，Council的接受决策 $D$ 由多数投票决定：

$$
D = \text{MajorityVote}\left( \{ d_i \}_{i=1}^{N} \right), \quad d_i \in \{\text{YES}, \text{NO}\}
$$

其中 $d_i$ 为第 $i$ 个LLM的判断，$N$ 为Council规模。该公式的物理含义是：通过多模型共识降低单模型偏差，聚合反馈指导迭代修正，确保SQL与模板的对齐性。Council在四个位置提供反馈：评估引导问题与过滤规则、验证SQL查询、检查SQL结果与模板对齐、评估最终摘要是否满足用户查询。

## 实验评估

实验在FeTaQA、QTSumm与QFMTS三个基准上进行，覆盖单表与多表场景。基线包括提示方法（CoT、DirectSumm、ReFactor、Reason-then-Summ）与智能体框架（Binder、Dater、TaPERA、SPaGe），但缺失Table-to-text微调模型（如TAPEX、OmniTab），可能低估微调方法的竞争力。论文声称FACTS在所有数据集上取得最佳或次佳结果，但未提供具体准确率数值，仅定性描述“consistently outperforms”。据领域综述，FeTaQA上现有SOTA为Weaver的52.1%与MATA的52.8%，FACTS是否超越这些数值无法从论文中确认。

消融实验显示，FACTS工作流平均每个样本需2.47个接受的引导问题或过滤规则、1.36轮SQL修正、1.84轮模板修正，最大耐心设为3轮。Token效率方面，整个工作流平均消耗9,922输入Token与1,045输出Token。这些数字表明，尽管FACTS实现了模板复用，但生成阶段的计算成本仍显著高于单次LLM调用，复用收益需跨多个表格才能体现。

评估边界存在明显局限：论文未报告置信区间，数值比较需谨慎；未评估模式漂移（如列名变更）下的模板鲁棒性；未对比隐私合规性指标（如数据泄露率）。代码已开源（https://github.com/BorealisAI/FACTS），但超参数与GPU配置未详细披露，可复现性受限。

## 关联研究分析

从问题动机看，FACTS与Binder共享SQL接地思想，但Binder聚焦即时查询执行，FACTS转向离线模板生成。这一差异源于任务特性：Binder处理一次性查询，而FACTS针对重复性、同模式查询场景。Binder的即时规划无法跨表格复用，每次查询均需重新生成SQL；FACTS的模板生成将推理逻辑固化，使同一模板可应用于任意同模式表格。然而，Binder未探索模板复用，FACTS未评估模式漂移下的鲁棒性，二者在“可复用性”与“适应性”之间做出了不同取舍。

从方法设计看，FACTS与SPaGe同属智能体框架，但SPaGe采用图执行处理多表场景，FACTS用Jinja2渲染简化多表处理。SPaGe的图执行能处理复杂表间关系，但规划开销大；FACTS的Jinja2模板仅支持简单迭代与条件渲染，无法处理复杂嵌套逻辑。这一差异暗示：当表格结构复杂、表间关系密集时，FACTS的模板机制可能失效，而SPaGe的图执行更具优势。论文未对比二者在多表复杂场景下的性能，Jinja2模板的表达力边界未得到充分验证。

## 总结

FACTS要解决的核心矛盾是隐私合规与计算效率的冲突：传统LLM方法暴露敏感数据且无法复用，微调模型则缺乏灵活性。FACTS抓住的切入点是“离线模板生成”，通过将推理逻辑固化为SQL+Jinja2模板，使同一模板可应用于任意同模式表格，从而在数据不出域前提下实现规模化摘要。该方法证明了模板复用能降低重复查询的计算成本，但论文未提供具体准确率数值，仅定性声称优于基线。其边界在于：模板绑定于固定模式，未评估模式漂移下的鲁棒性；Jinja2模板的表达力有限，无法处理复杂嵌套逻辑。当表格模式发生细微变更（如列名重命名）时，离线模板是否仍能正确执行，论文未给出回答。
