# ACL-Findings2026最新论文 ｜Beyond Single-Shot: Multi-step Tool Retrieval via Query Planning ｜工具查询规划器

研究机构：美国麻省理工学院

作者：Wei Fang、James Glass

论文原文见 [arXiv](https://arxiv.org/abs/2601.07782)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2601.07782)

> 大规模动态工具库中，静态单次检索无法弥合用户抽象意图与工具技术文档间的语义鸿沟，且难以处理多工具组合依赖。现有密集检索器在复杂组合任务上失效，本文切入点是将检索重构为交互式规划过程。TOOLQP 通过轻量模型分解子任务并迭代生成查询，结合 RLVR 优化策略。其价值在于以极低参数量实现了跨检索器的鲁棒泛化，但迭代查询带来的推理延迟在实时场景下的权衡尚存疑。

## 研究背景

当智能体面对包含数万 API 的动态工具库时，上下文窗口无法容纳所有工具文档，必须依赖检索模块筛选候选工具。然而，用户查询常使用“提升音质”等抽象词汇，而工具定义多为 `scipy.signal.lfilter` 等数学参数描述，这种语义错位导致标准密集检索器（Dense Retriever）在组合任务中失效。更严重的是，单一固定维度向量无法编码多工具的 combinatorial diversity，且静态索引无法感知工具间的依赖关系（如预测工具需先获取区域 ID）。

工具检索是决定智能体性能上限的关键瓶颈，主流路线分为基于提示的查询扩展与基于微调的检索器优化。前者如 HyDE 和 Q2E 依赖大模型生成假设文档，计算成本高且缺乏交互性；后者如 ContrastiveFT 虽提升表示能力，但受限于训练域分布，在零样本场景下泛化不足。现有方法均将检索视为静态匹配，忽略了环境反馈对解决动态依赖的价值。TOOLQP 的切入点在于将检索器视为可交互的动态环境，通过规划-查询-聚合三阶段循环，在推理时动态调整策略以弥合语义鸿沟并发现隐含依赖。

## 核心方法

### 方法参照系

标准工具检索流程为：嵌入用户查询 $q$ 与工具集 $D$，计算相似度后返回 Top-K 结果。该流程假设查询与工具存在直接语义对齐，且工具间无依赖。本文的关键差异在于引入“规划”与“交互”机制，将单次匹配转化为序列决策过程，以处理组合意图与动态反馈。

### 规划与交互式查询生成

设计动机：直接查询复杂指令时，用户措辞中常缺失工具关键词，导致检索失败。TOOLQP 首先生成自然语言计划 $P$，将查询 $q$ 分解为子任务序列 $\{s_n\}$。随后，针对每个子任务，模型迭代生成查询 $q_t$，并观察检索反馈 $O_t = E(q_t; D)$。这一反馈循环允许模型根据已检索工具的需求（如特定输入参数）动态生成后续查询，从而发现单向量无法捕获的依赖关系。

### 峰值排名聚合与 RLVR 优化

设计动机：不同子任务生成的查询数量不一，传统倒数排名融合（RRF）会偏向查询次数多的子任务，导致结果失衡。TOOLQP 采用峰值排名（Peak-rank）策略，对每个唯一工具 $d$，其最终排名严格基于其在任何单次检索中达到的最高排名。

$$
\text{Rank}_{final}(d) = \min_{t \in \{1, \dots, T\}} \text{Rank}_t(d)
$$

该公式确保各子任务对最终结果的贡献均衡，避免频率偏差。在训练阶段，TOOLQP 采用 SFT 初始化后，通过 RLVR 优化查询策略。奖励函数 $R_{retrieval}$ 定义为最终聚合检索与基线检索在 nDCG@5 和 Recall@5 上的差值加权：

$$
R_{retrieval} = \beta_{1,n} \Delta N + \beta_{1,r} \Delta R
$$

其中 $\Delta N$ 和 $\Delta R$ 分别为 nDCG@5 和 Recall@5 的提升量。此设计将检索质量直接转化为可验证奖励，引导模型生成更精准的查询序列，而非仅模仿教师轨迹。

## 实验评估

实验在 TOOLRET（35 个数据集）、API-Bank 和 StableToolBench (STB) 上进行。基线覆盖提示扩展（Q2E, HyDE）、微调检索器（ContrastiveFT）及交互式方法（Re-Invoke）。TOOLQP 使用 Qwen3-1.7B 作为规划器，gte-Qwen 作为底层检索器。

| 方法 | In-Domain $\Delta$N@10 | In-Domain $\Delta$C@10 | 0-Shot $\Delta$N@10 | 0-Shot $\Delta$C@10 |
| :--- | :--- | :--- | :--- | :--- |
| Q2E | +1.6 | +1.9 | +2.2 | +2.8 |
| Re-Invoke | +5.2 | +7.5 | +5.2 | +5.4 |
| TOOLQP-FORMAT | +9.4 | +9.6 | +1.6 | +4.2 |
| TOOLQP | +5.6 | +6.8 | +5.4 | +7.1 |

TOOLQP 在零样本场景下表现最优，N@10 提升 5.4%，C@10 提升 7.1%，显著优于 Re-Invoke。在域内场景，TOOLQP-FORMAT 通过显式建模工具格式，N@10 提升 9.4%，验证了格式信息对特定任务的增益。

| 方法 | API-Bank Level-1 | STB I2Category | STB I3-Instruction |
| :--- | :--- | :--- | :--- |
| Base Retriever | 47.6 | - | - |
| TOOLQP | 53.2 | - | - |

在端到端任务中，TOOLQP 在 API-Bank Level-1 上准确率从 47.6% 提升至 53.2%。在更复杂的 STB 上，TOOLQP 较基线提升 8-9% 的 Solvable Pass Rate。消融实验显示，SFT 阶段贡献了主要的域内性能增益，而 RLVR 对零样本泛化至关重要。移除用户查询作为锚点会导致性能下降，表明分解过程需原始查询校正。

评估边界方面，论文未报告迭代查询的平均延迟，仅定性提及“高效”。代码未开源，但提供了详细超参数（如 RLVR 的 KL 正则化 0.02，Group size 4）。STB 评估使用 Qwen-30B 作为裁判，可能存在裁判偏差。

## 关联研究分析

从问题动机看，TOOLQP 与 CoHyDE 均关注检索与训练的协同，但 CoHyDE 侧重迭代协同训练以优化检索器本身，而 TOOLQP 聚焦推理时的规划策略，不修改底层索引。这一差异源于任务特性：CoHyDE 假设工具库静态，可承受离线训练成本；TOOLQP 面向动态工具库，需在线适应。TOOLQP 的规划机制在工具频繁更新场景下更具优势，但 CoHyDE 的协同训练可能在固定工具集上获得更优的表示对齐。

从方法设计看，TOOLQP 与 Tool-R1 均使用 RLVR，但 Tool-R1 优化工具调用策略（何时调用、调用哪个），TOOLQP 优化检索查询策略（如何查询以找到工具）。Tool-R1 的奖励基于最终任务成功，TOOLQP 的奖励基于检索质量（nDCG/Recall）。这种差异导致 TOOLQP 更关注中间步骤的准确性，而 Tool-R1 更关注端到端结果。在长程任务中，TOOLQP 的细粒度检索奖励可能提供更稳定的梯度信号，但 Tool-R1 的全局奖励可能更好地对齐最终目标。

## 总结

TOOLQP 解决了大规模动态工具库中静态检索无法处理语义错位与组合依赖的核心矛盾。其切入点是将检索器视为可交互环境，通过轻量规划模型迭代生成查询，并利用 RLVR 优化策略。实验证明，1.7B 模型在零样本场景下 N@10 提升 5.4%，端到端任务提升 8-9%，验证了规划机制的有效性。边界在于迭代查询带来的推理延迟未量化，且依赖底层检索器的质量。当工具库规模进一步扩大至百万级时，规划模型的查询生成效率与检索器响应速度的匹配性，论文未给出回答。
