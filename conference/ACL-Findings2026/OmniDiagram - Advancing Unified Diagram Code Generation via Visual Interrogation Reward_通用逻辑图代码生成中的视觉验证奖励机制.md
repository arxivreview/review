# ACL-Findings2026最新论文 ｜OmniDiagram: Advancing Unified Diagram Code Generation via Visual Interrogation Reward ｜通用逻辑图代码生成中的视觉验证奖励机制

研究机构：中国科学院、中国科学院大学

作者：Haoyue Yang、Xuanle Zhao、Xuexin Liu 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.05514)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.05514)

> 多模态大语言模型在将视觉图表转化为可执行代码时，常面临语法正确性与视觉保真度脱节的困境。现有方法多依赖单一任务或固定语言，且强化学习中的二元奖励信号难以捕捉细粒度结构差异。本文提出VIVA机制，通过生成实例特定的视觉问题来评估渲染结果，实现细粒度反馈。该框架在通用逻辑图生成上超越了专用代码模型，但其对VQA评估模型的依赖及离线问题生成的泛化边界尚存疑。

## 研究背景

当模型尝试将流程图或UML图转化为Mermaid或LaTeX代码时，仅靠语法检查无法确保生成的图表在视觉上还原了原始拓扑结构。这种“代码正确但视觉失真”的现象源于传统奖励机制的粗粒度，通常仅判断代码是否可编译，而忽略了节点连接、布局比例等语义细节。为了解决这一对齐难题，研究者引入了可验证奖励强化学习（RLVR），试图通过环境反馈优化策略，但现有的视觉反馈多采用全局相似度计算，容易陷入表面结构模仿而丢失关键属性。

图表代码生成领域长期存在任务碎片化问题，StarFlow等早期工作仅支持JSON输出，JanusCoder虽尝试统一文本到代码与图表到代码，但受限于监督微调（SFT）范式，缺乏对视觉对齐的深层优化。与此同时，MoCA和REChart等最新方法虽在特定图表基准上表现优异，但多聚焦于单语言或特定类型的图表编辑，缺乏对LaTeX、Mermaid、PlantUML等多语言逻辑图的统一支持。本文的切入点在于构建一个覆盖3×3任务-语言矩阵的统一框架，并设计一种基于视觉问答（VQA）的细粒度奖励机制，以解决多模态代码生成中视觉保真度验证的难题。

## 核心方法

### 多模态代码生成参照系

本文任务属于结构化代码生成路线，其标准流程通常包含数据合成、SFT建立基础语法能力，以及RL优化执行与视觉一致性。与仅针对单一图表类型（如ChartQA中的柱状图）的方法不同，本文需处理LaTeX、Mermaid和PlantUML三种异构语言，且任务涵盖图表到代码、图表编辑及文本到代码，这要求奖励机制具备跨语言和跨任务的通用性，而非依赖特定领域的固定模板。

### VIVA视觉验证奖励机制

针对SFT后模型在RL阶段易出现模式坍塌及视觉细节丢失的问题，本文提出Visual Interrogation Verifies All (VIVA) 机制。该机制摒弃了全局像素相似度计算，转而采用“提问-回答”的验证范式。对于每个训练样本，离线生成一组针对该实例特定结构的关键问题（如“实体A是否包含属性B？”），在线训练时，将候选代码渲染为图像，由VQA模型回答这些问题。最终奖励 $R_i$ 定义为VIVA得分与格式奖励的加权和：

$$ R_i = \alpha R_{VIVA} + (1-\alpha) R_{fmt} $$

其中 $R_{VIVA}$ 是 $N$ 个实例特定问题的平均得分，$R_{fmt}$ 为代码结构合规的二元奖励。若代码无法渲染，$R_{VIVA}$ 直接置为0。这种设计将粗粒度的执行成功信号转化为细粒度的语义验证信号，使得模型在优化过程中能够区分“语法正确但结构错误”与“完全正确”的输出，从而有效缓解RL中的奖励稀疏与噪声问题。

### 基于GRPO的策略优化

在获得细粒度奖励后，本文采用组相对策略优化（GRPO）更新策略模型 $\pi_\theta$。对于输入 $x$，生成 $G$ 个候选代码，计算其组内归一化优势 $\hat{A}_{i,t}$：

$$ \hat{A}_{i,t} = \frac{R_i - \text{mean}(R)}{\text{std}(R)} $$

该公式通过组内标准化消除了绝对奖励值的偏差，仅保留相对优劣信息。结合VIVA的低方差特性，GRPO能够更稳定地引导策略向高视觉保真度方向收敛，避免了传统PPO中价值函数估计不准带来的训练不稳定。

## 实验评估

| 模型 | M3[2] Bench Exec (%) | M3[2] Bench Svis | VisPlotBench Exec (%) | VisPlotBench Svis |
| :--- | :--- | :--- | :--- | :--- |
| Qwen2.5-VL-7B | 46.1 | 28.1 | 57.3 | 25.6 |
| OmniDia-7B (SFT) | 88.7 | 70.6 | 84.0 | 45.3 |
| OmniDia-7B (RL) | 89.2 | 71.8 | 86.3 | 51.0 |
| VisCoder2-7B | 83.6 | 63.0 | 78.6 | 43.0 |
| GPT-5-mini | 87.3 | 65.1 | 57.5 | 34.2 |

实验在M3[2] Bench（1.7k样本）和VisPlotBench上进行，基线包括Qwen2.5-VL、InternVL3.5、VisCoder2及GPT-5-mini。OmniDia-7B (RL)在M3[2] Bench上执行率（Exec）达89.2%，视觉保真度（Svis）达71.8，显著优于基线Qwen2.5-VL-7B（46.1% / 28.1%）及专用代码模型VisCoder2-7B（83.6% / 63.0%）。在VisPlotBench上，OmniDia-7B (RL)的执行率（86.3%）也高于VisCoder2-7B（78.6%），表明通用多模态骨干经VIVA-RL优化后，在逻辑图代码生成上具备超越专用Coder骨干的潜力。

消融实验显示，SFT阶段将执行率从46.1%提升至88.7%，而RL阶段进一步将其提升至89.2%，同时Svis从70.6%提升至71.8%。这表明SFT主要解决了语法合法性问题，而VIVA驱动的RL主要优化了视觉语义对齐。值得注意的是，RL阶段对执行率的提升幅度（0.5%）远小于SFT阶段（42.6%），说明在SFT已建立良好语法基础的前提下，RL的核心价值在于细粒度的视觉保真度优化，而非单纯的语法纠错。

评估协议依赖GPT-4.1作为裁判模型进行多维评分，可能存在裁判模型自身的偏见。代码与数据集已开源，训练使用8张H800 GPU，SFT全局批大小32，RL全局批大小128，超参数 $\alpha=0.9, G=4$。由于VIVA问题由GPT-4.1-mini离线生成，其质量上限受限于该模型的能力，且未报告VQA评估模型的推理延迟，这在大规模部署中可能成为瓶颈。

## 关联研究分析

从方法设计看，本文与Chart-RL同属RLVR路线，但奖励信号的性质截然不同。Chart-RL依赖数值匹配的二元奖励，适用于数据提取任务；而VIVA采用VQA生成的细粒度语义奖励，适用于结构复杂的逻辑图生成。这种差异源于任务特性：数值推理只需关注最终结果的正确性，而逻辑图生成需验证中间结构的拓扑一致性。VIVA的“提问”机制本质上是将结构验证转化为语义问答，这在处理非双射映射（即不同代码可生成相同视觉结果）时更具鲁棒性，但引入了对VQA模型语义理解能力的依赖。

从问题动机看，MoCA和REChart聚焦于特定图表类型的编辑与生成，强调模态仲裁或推理效率；而OmniDiagram追求多语言、多任务的统一性。MoCA在ChartMimic上的执行率（95.66%）高于OmniDiagram在VisPlotBench上的表现（86.3%），但这并非直接可比，因为MoCA针对的是特定图表基准，而OmniDiagram覆盖更广泛的逻辑图类型。本文未对比MoCA，可能是因为任务定义（通用逻辑图 vs 特定图表）存在差异，这也暗示了当前领域缺乏统一的跨类型评估基准，导致不同方法间的性能难以直接横向比较。

## 总结

OmniDiagram旨在解决多模态代码生成中语法正确性与视觉保真度脱节的核心矛盾。其切入点在于利用VQA机制将粗粒度的执行奖励转化为细粒度的语义验证奖励，从而在RL阶段有效优化视觉对齐。通过构建3×3任务-语言矩阵数据集M3[2] Diagram，并采用SFT+VIVA-RL两阶段训练，模型在M3[2] Bench上实现了89.2%的执行率和71.8%的视觉保真度，超越了专用代码模型VisCoder2。然而，VIVA机制依赖离线生成的问题集，其泛化能力受限于问题生成模型的质量，且未评估VQA评估带来的计算开销。当逻辑图类型超出训练分布时，离线生成的问题是否仍能准确捕捉关键结构差异，论文未给出回答。
