# ACL-Findings2026最新论文 ｜SQLAgent: Learning to Explore Before Generating as a Data Engineer ｜SQLAgent: 基于自主探索的双智能体文本到SQL框架

研究机构：西湖大学、美国加州大学默塞德分校

作者：Wenjia Jiang、Yiwei Wang、Boyan Han 等 5 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_2688e00dcffb)

> 导读 企业级数据库的文本到SQL（Text-to-SQL）任务面临模式链接与跨域泛化的双重瓶颈，现有提示工程方法依赖静态示例或单次生成，难以应对未见过的复杂模式结构。SQLAgent 提出“探索-部署”两阶段框架，通过蒙特卡洛树搜索（MCTS）驱动的自主探索构建数据库特定知识库，再由双智能体协作完成查询生成。该设计将一次性生成转化为主动熟悉数据库的过程，显著提升了复杂查询的执行准确率。然而，探索阶段的高昂计算成本与对实时性场景的适用性限制，使其在通用基准上的表现未达领域最优，其价值边界需结合具体部署场景评估。

## 研究背景

当用户以自然语言查询包含数百张表的企业数据库时，模型需准确识别相关列并推断隐含的连接键。这一过程称为模式链接（Schema Linking），其准确性直接决定SQL生成的成败。由于自然语言的口语化表达与数据库抽象命名（如缩写、代码）存在语义鸿沟，传统关键词匹配常遗漏关键连接键或误判相关列，导致生成的查询在执行时失败或返回错误结果。

文本到SQL领域的主流路线已从早期序列到序列模型转向大语言模型（LLM）提示工程。DAIL-SQL 等检索增强方法通过动态选择相似示例提升泛化能力，但示例库是静态的，无法适应未见过的模式结构；ReFoRCE 等迭代精炼方法依赖执行反馈修正查询，但在缺乏先验知识时，冗余反馈易导致模型将正确查询修改为错误结果。SQLAgent 的切入点在于：人类专家在查询陌生数据库前会先熟悉其结构，因此系统应在查询前主动探索数据库，构建包含可执行查询与模式片段的动态知识库，为后续生成提供验证过的先验知识。

## 核心方法

### 方法参照系

本文问题与标准LLM提示工程流程的关键差异在于：标准流程假设示例库已存在且静态，而本文需在无标注数据下自主构建数据库特定的动态知识库。参照系为检索增强生成（RAG）范式，其核心是检索相关示例作为上下文，但本文将检索源从静态语料替换为通过执行验证的动态三元组库。

### 探索阶段：MCTS驱动的动态知识库构建

探索阶段在查询前自主构建知识库，解决静态示例库无法适应未见模式的问题。传统MCTS依赖标量奖励通过树状置信上限（UCT）传播，但SQL查询的有效性在执行时是二元的，而语义质量是连续且上下文相关的，标量奖励无法区分语法无效与语义低效的路径。SQLAgent 用LLM作为策略与评估器替代UCT策略，LLM编码错误轨迹与模式语义，输出区分语法无效与语义低效的自然语言反馈。知识库以三元组 $(S, Q, U)$ 形式存储，其中 $S$ 是模式子结构，$Q$ 是可执行SQL查询，$U$ 是对齐的自然语言描述。三元组生成过程遵循树状搜索，每个节点代表一个候选模式子结构，LLM从离散动作空间（如选择列、添加约束、应用聚合）中选择下一动作，扩展树节点。生成的查询需通过两阶段验证：SQL解析器检查语法正确性，执行引擎验证运行时有效性，仅当查询语法有效、执行无错误且返回非空非平凡结果集时，LLM才生成自然语言描述 $U$，完成三元组。该设计确保每个示例都基于真实模式子结构并经执行验证，保证 $S$、$Q$、$U$ 间的高语义对齐。

### 部署阶段：双智能体协作与迭代精炼

部署阶段利用探索阶段构建的知识库，解决单次生成在复杂查询中因上下文不完整或连接依赖未检测而失效的问题。InfoAgent 负责模式接地与上下文管理，GenAgent 负责知识驱动的SQL合成。InfoAgent 通过两步构建精确的模式上下文：首先，将每列序列化为包含名称、数据类型与文档注释的描述字符串，用句子嵌入模型编码为高维向量，构建预计算的嵌入索引；查询时，从用户查询中提取语义关键词，通过相似度搜索检索 top-k 最相关列。其次，由于初始 top-k 集常遗漏连接键，InfoAgent 提示LLM作为数据库专家，推理检索组件间的关系依赖，推断逻辑上必要的添加。例如，若初始检索返回 users 表的 user_name 列与 orders 表的 order_amount 列，LLM 识别并添加连接两表所需的 user_id 与 customer_id 键。GenAgent 通过联合编码用户自然语言问题与 InfoAgent 提供的模式上下文，生成检索嵌入，对知识库中每个三元组的 SQL 组件 $Q$ 的预计算嵌入进行相似度搜索，检索 top-k 语义最相似的三元组作为数据库特定的少样本示例。生成的查询执行失败时，InfoAgent 执行两个并发修正动作：剪枝模式上下文，移除上下文中存在但生成查询中不存在的组件，缩小候选集；重新分析用户查询，提取初始接地步骤可能遗漏的次要语义关键词，召回额外候选表与列。该迭代循环持续至查询执行成功且语义保真度检查通过，或达到迭代上限。

## 实验评估

实验在 Spider 2.0-Snow 与 BIRD 基准上进行，对比 Spider-Agent、ReFoRCE、AlphaSQL、MARS-SQL 等基线。Spider 2.0-Snow 包含高度分片的企业模式，BIRD 覆盖更广泛的真实世界数据库，两者结构复杂度互补。基线覆盖多智能体、强化学习、无训练推理等路线，但缺失 DIN-SQL 等传统微调基线，可能高估本文方法的相对优势。

SQLAgent 全方法在 Spider 2.0-Snow 上达到 25.78% 的整体执行准确率，超越 ReFoRCE 的 20.84% 与 Spider-Agent 的 12.98%，Hard 子集上 12.21% 的准确率显著高于基线的 5.23% 与 6.94%。消融实验显示，仅添加探索阶段（w/ Exp. Stage）将整体准确率从 14.26% 提升至 20.10%，Hard 子集从 0.00% 提升至 5.81%，验证了动态知识库对复杂查询的关键作用。全方法在 BIRD 上达到 70.53% 的执行准确率，高于 ReFoRCE 的 57.0%、MARS-SQL 的 66.8% 与 AlphaSQL 的 69.7%，但低于领域综述中 EXPO-SQL 的 72.9%，表明其在通用基准上未达最优，优势集中于高复杂度企业场景。

评估边界方面，论文未报告置信区间，数值比较需谨慎；BIRD 基准引入的有效效率分数（VES）未被报告，效率维度评估缺失；代码已开源（https://github.com/Westlake-AGI-Lab/SQLAgent），但探索阶段的计算成本（初始 467k tokens）未提供 GPU 时间或硬件配置，可复现性受限于计算资源。

## 关联研究分析

从问题动机看，SQLAgent 与 DAIL-SQL 均解决模式链接的语义鸿沟，但 DAIL-SQL 依赖静态示例库的相似度匹配，示例与目标模式的结构性兼容性无法保证；SQLAgent 的三元组库通过执行验证确保示例与模式子结构的语义对齐，且联合编码查询与模式上下文的检索策略直接针对结构性兼容性优化。这一差异源于任务特性：企业级数据库的模式冗余（如时间分片）使静态示例易引入噪声，而动态探索通过执行反馈过滤无效组合，是应对结构复杂性的必要设计。

从方法设计看，SQLAgent 与 ReFoRCE 同属迭代精炼框架，但 ReFoRCE 的迭代依赖执行反馈直接修正查询，缺乏先验知识时反馈噪声易导致正确查询被错误修改；SQLAgent 的探索阶段提供验证过的先验知识，使迭代精炼在稳定基础上进行，避免了无引导精炼的不稳定性。这一差异源于对执行反馈利用效率的处理：ReFoRCE 将执行反馈作为唯一修正信号，SQLAgent 将其分为探索阶段的验证信号与部署阶段的修正信号，前者构建知识库，后者驱动精炼，形成更鲁棒的闭环。

## 总结

SQLAgent 要解决的核心矛盾是：LLM 在未见过的企业级数据库上缺乏模式熟悉度，导致模式链接错误与复杂推理失败。现有方法依赖静态示例或单次生成，无法主动适应新数据库的结构特性；SQLAgent 通过 MCTS 驱动的自主探索构建动态知识库，将“熟悉数据库”这一人类专家行为转化为系统化的预查询过程，解决了冷启动泛化难题。实验证明，该框架在 Spider 2.0-Snow 上达到 25.78% 的整体执行准确率，Hard 子集 12.21% 的准确率显著超越基线，验证了动态知识库对复杂查询的有效性。然而，探索阶段的高昂计算成本（初始 467k tokens）与对实时性场景的适用性限制，使其在 BIRD 通用基准上未达领域最优。当探索阶段的计算成本降低至可接受范围时，该框架在实时企业查询系统中的部署可行性如何，论文未给出回答。
