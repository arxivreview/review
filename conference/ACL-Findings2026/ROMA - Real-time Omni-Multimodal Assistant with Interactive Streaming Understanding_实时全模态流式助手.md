# ACL-Findings2026最新论文 ｜ROMA: Real-time Omni-Multimodal Assistant with Interactive Streaming Understanding ｜实时全模态流式助手

研究机构：中国科学院、中科院计算所

作者：Xueyun Tian、Wei Li、Bingbing Xu 等 6 人

论文原文见 [arXiv](https://arxiv.org/abs/2601.10323)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2601.10323)

> 流式视频理解的核心矛盾在于无限输入流与有限上下文窗口的冲突，以及被动响应无法适应实时交互的痛点。现有方法要么仅处理视频而忽略音频，要么将时机决策与内容生成耦合导致语义冲突。ROMA 通过构建同步多模态单元与解耦的 Speak Head，统一了主动与被动交互范式。该框架在主动任务上取得显著优势，但其依赖长上下文 KV 缓存的设计在超长流场景下的显存效率存疑。

## 研究背景

实时交互应用要求模型在严格因果约束下处理连续音视频流，这涉及两个核心概念：流式因果性（Streaming Causality）规定模型仅能访问当前及过去观测，而主动响应（Proactive Response）则要求模型自主决定何时基于证据触发响应。因果性确立了实时交互的底层逻辑，但仅解决“看什么”的问题；主动响应进一步解决“何时说”的决策问题，两者共同构成了流式理解区别于离线理解的范式边界。

流式视频理解的主流路线在 2024-2025 年聚焦于视频模态的内存管理与架构标准化，如 StreamingVLM 通过注意力沉没解决无限流输入，VideoLLM-Online 通过 EOS 机制确立主动交互基础。然而，这些方法存在两个瓶颈：一是模态单一，忽略了音频信号在实时场景中的密集连续特性，导致跨模态对齐缺失；二是时机决策机制粗糙，EOS 预测与文本生成耦合，易产生任务干扰。ROMA 的切入点在于将音频与视频统一为同步的多模态单元，并引入独立的 Speak Head 解耦时机与内容，旨在解决全模态流式交互中的粒度不匹配与决策干扰问题。

## 核心方法

### 方法参照系

ROMA 属于全模态流式交互路线，其基础架构继承自 Qwen2.5-Omni 的多模态大语言模型（MLLM）骨干。与标准离线 MLLM 处理完整视频不同，ROMA 需处理无限流输入，关键差异在于必须维护持久化 KV 缓存以累积历史上下文，并引入显式的时机决策模块以支持主动交互，而非仅被动回答查询。

### 同步多模态单元与分块 TMRoPE

为解决音频密集连续与视频稀疏离散的时间粒度不匹配，ROMA 将连续音频切分为 1 秒间隔，与同区间视频帧对齐形成多模态单元。设计动机在于消除异步信号融合时的时间漂移，确保跨模态语义在时间轴上的精确对应。ROMA 采用分块时间对齐多模态旋转位置编码（Chunked TMRoPE），为每个单元内的视觉与听觉 Token 分配共享的时间 ID。视觉 Token 在单元内共享常量时间 ID，而音频 Token 保留 40ms 分辨率的细粒度时间 ID。位置编码公式如下：

$$
\text{PosID}_{t+1} = \text{MaxPosID}_t + \Delta
$$

其中 $\Delta$ 为单元间隔，该机制通过累积位置 ID 无缝扩展全局时间线，使模型在增量编码时能感知跨单元的时间连续性，避免了传统滑动窗口导致的上下文断裂。

### 解耦 Speak Head 与两阶段训练

针对 EOS 机制中时机与内容生成的耦合干扰，ROMA 引入轻量级 Speak Head，作为并行于语言建模（LM）头的二元分类器。设计动机在于将“何时说话”的决策从文本生成中剥离，防止生成偏差影响触发准确性。Speak Head 输入为最后 $K=4$ 层隐藏状态的加权组合，输出响应概率 $p_t$。训练采用两阶段课程：第一阶段适配流式格式，第二阶段学习时机决策。时机损失采用加权二元交叉熵（BCE）以缓解触发稀疏性：

$$
\mathcal{L}_{timing} = -\frac{1}{T}\sum_{t=1}^{T} [w_{pos} z_t \log p_t + (1-z_t) \log(1-p_t)]
$$

其中 $w_{pos}$ 为正样本权重，$z_t$ 为真实标签。该解耦架构使模型在静默时不消耗生成算力，仅在概率超过阈值时激活 LM 头，实现了低延迟的主动响应。

## 实验评估

ROMA 在 12 个基准上评估，基线覆盖 VideoLLM-Online、MMDuet、Dispider 等流式视频模型，以及 Qwen2.5-Omni 等全模态模型。在主动任务上，ROMA 表现显著优于基线：

| 基准 | 指标 | ROMA | MMDuet | VideoLLM-Online |
| :--- | :--- | :--- | :--- | :--- |
| QVHighlights | mAP | 53.7 | 31.4 | – |
| Charades-STA | R@0.5 | 44.3 | 31.2 | – |
| YouCook2 Narration | F1 | 35.21 | 17.81 | 18.82 |
| OVO-Bench (SSR) | F1 | 14.54 | 9.02 | 10.24 |

ROMA 在 QVHighlights 上 mAP 达 53.7，较 MMDuet 的 31.4 提升 22.3 个百分点，验证了全模态对齐对时序定位的增益。在被动问答任务上，ROMA 在 OVO-Bench 的 Real-Time Visual Perception 子任务取得 76.96，高于 Flash-VStream 的 62.91，但在 Video-MME 上仅得 33.30，低于 Qwen2.5-Omni 的 20.50 之外的其他全模态模型，主要因使用语音查询而非文本查询，协议差异导致数值不可直接对比。

消融实验显示，移除 Speak Head 导致 QVHighlights mAP 从 53.7 降至 16.5，YouCook2 F1 从 35.21 降至 9.25，证实解耦机制对主动任务的关键作用。两阶段训练优于混合训练，后者在动态决策任务（REC）上性能显著下降，表明渐进式学习对时序决策校准的重要性。$w_{pos}=3$ 时性能最平衡，$w_{pos}=2$ 或 4 均导致主动任务指标波动，而被动任务对 $w_{pos}$ 不敏感。

评估边界方面，ROMA 未报告 TTFT 或 MaxFPS 等系统级延迟指标，仅给出单单元编码耗时 0.3697 秒。代码未开源，仅提供项目页面，可复现性受限。评估协议中语音查询的设置虽贴近真实交互，但缺乏与纯文本查询的对照实验，难以分离音频编码噪声与模型能力的影响。

## 关联研究分析

从方法设计看，ROMA 的 Speak Head 与 VideoLLM-Online 的 EOS 机制形成鲜明对比。VideoLLM-Online 将时机决策嵌入文本生成序列，依赖特殊 Token 预测，易受生成偏差干扰；ROMA 通过独立分类头解耦，避免了任务冲突。这一差异源于任务特性：VideoLLM-Online 聚焦视频单模态，生成序列较短，耦合干扰较小；ROMA 处理全模态长流，生成内容复杂，解耦成为必要。然而，ROMA 未探索 Speak Head 在音频密集场景下的触发延迟是否高于纯视频场景，这可能源于音频 Token 数量远多于视频 Token，导致计算开销增加。

从问题动机看，ROMA 与 StreamingVLM 在记忆管理上存在路线分歧。StreamingVLM 采用注意力沉没与连续 RoPE 解决无限流显存溢出，强调计算效率；ROMA 依赖持久化 KV 缓存，未引入压缩机制，强调语义完整性。这一差异反映了全模态交互对细节保留的高要求：音频的 40ms 粒度信息若被压缩，可能丢失关键时序线索。ROMA 未验证超长视频流中 KV 缓存的显存增长曲线，其设计在分钟级视频上有效，但在小时级流中可能面临显存瓶颈，这是其未探索的盲区。

## 总结

ROMA 旨在解决全模态流式交互中音视频粒度不匹配与时机决策耦合的矛盾。其切入点在于将音频切分为 1 秒单元与视频对齐，并引入独立 Speak Head 解耦时机与内容，从而在统一框架下支持主动与被动交互。实验证明，该设计在 QVHighlights 上取得 53.7 mAP，YouCook2 叙述 F1 达 35.21，显著优于纯视频基线。然而，ROMA 依赖持久化 KV 缓存而未引入压缩机制，在超长视频流中的显存效率未经验证。当视频时长从分钟级扩展至小时级时，未压缩 KV 缓存的显存占用是否会导致系统崩溃，论文未给出回答。
