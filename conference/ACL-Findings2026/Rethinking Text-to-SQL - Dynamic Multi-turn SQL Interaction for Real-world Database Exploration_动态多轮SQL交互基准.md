# ACL-Findings2026最新论文 ｜Rethinking Text-to-SQL: Dynamic Multi-turn SQL Interaction for Real-world Database Exploration ｜动态多轮SQL交互基准

研究机构：中国科学院大学、北京大学

作者：Linzhuang Sun、Tianyu Guo、Hao Liang 等 12 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_f3178f68c7fe)

> 现有文本到SQL（Text-to-SQL）基准将任务简化为静态单轮翻译，忽略了真实场景中用户意图的动态演化与数据库状态的持续变更。本文指出，静态评估无法捕捉多轮对话中的状态维护与错误恢复能力，因此构建了首个支持完整CRUD操作的动态交互基准。通过两阶段自动合成管线与三元交互框架，DySQL-Bench揭示了前沿大语言模型在动态SQL推理上的显著脆弱性。该基准填补了动态评估空白，但模拟用户的保真度与评估协议的封闭性仍存疑。

## 研究背景

文本到SQL的核心挑战在于弥合自然语言口语化表达与数据库抽象模式间的语义鸿沟。在静态单轮场景中，模式链接（Schema Linking）错误直接导致生成失败，而多轮对话引入了更复杂的上下文依赖：用户指令随交互动态调整，Agent需维护长程状态一致性并处理指代消解。传统基准如CoSQL和SPIDER假设对话历史静态且无噪声，仅评估SELECT查询的生成准确性，忽略了INSERT、UPDATE、DELETE等状态改变操作对后续查询的影响。

主流方法路线在静态基准上取得了较高执行准确率，但无法应对真实工作流中的动态状态变更。例如，金融分析师不仅读取账本，还需更新交易记录并插入审计日志，这种状态依赖性要求模型具备交互式错误恢复能力。现有评估范式将任务视为“翻译考试”，缺乏对意图漂移与执行反馈闭环的测试。DySQL-Bench的切入点在于构建一个动态交互环境，通过模拟用户与可执行数据库的实时交互，评估Agent在状态演化中的推理稳定性与适应性。

## 核心方法

### 方法参照系

多轮文本到SQL的标准流程通常依赖静态历史拼接与单轮解析模型，如CoE-SQL通过AST差异比较生成编辑链，Track-SQL利用动态模式链接更新上下文。本文的关键差异在于摒弃静态历史，引入实时三元交互框架，将评估从“SQL匹配”转向“状态等价性验证”。

### 两阶段自动任务合成管线

直接生成多轮任务常面临语义不匹配与SQL语法错误。本文首先将原始关系表转换为分层逻辑树（Hierarchical Logic Tree），使LLM在单一提示窗口内可视化完整关系上下文，从而合成包含复杂依赖的指令与动作序列。这一设计解决了在线采样方法因执行复杂JOIN导致的高延迟与高成本问题，将生成时间减少约90%。随后，通过验证委员会（Verifier Committee）进行多轮自动过滤，确保指令与动作的语义对齐。

$$
\text{Tree}(T) = \{ \text{Root}(T_{primary}), \text{Children}(T_{related}) \}
$$

该公式表示以主表为根节点，通过外键递归检索关联表记录，形成预取子图结构，供LLM一次性生成连贯任务。

### 三元交互与状态哈希评估

传统评估依赖静态金标准SQL匹配，无法捕捉动态状态变化。本文提出三元交互框架，由LLM模拟用户、被测Agent与可执行数据库组成。Agent生成SQL操作序列 $A = (a_1, ..., a_n)$ 改变初始状态 $S_1$ 至 $S_2$，而金标准动作序列 $A_g$ 产生目标状态 $S_3$。成功判定基于状态哈希：

$$
\text{Success} \iff \text{hash}(S_2) = \text{hash}(S_3)
$$

此公式通过序列化数据库内容（排除易变时间戳）计算哈希值，确保模型执行结果与金标准功能等价，而非表面形式匹配。该机制解决了静态匹配无法验证状态变更正确性的问题，特别是针对UPDATE/DELETE操作。

## 实验评估

实验在DySQL-Bench上进行，包含1,072个任务，覆盖13个数据库，其中49.64%为UPDATE操作。基线涵盖GPT-4o、Qwen2.5-Max、DeepSeek-V3等主流LLM，但缺失专门的Text-to-SQL微调模型如RAT-SQL或DIN-SQL，限制了与静态基准SOTA的直接对比。

| 模型 | Short Tasks (Overall) | Long Tasks (Overall) | Overall Tasks |
| :--- | :--- | :--- | :--- |
| GPT-4o | 62.79 | 59.68 | 58.34 |
| Qwen2.5-Max | 76.74 | 75.41 | 76.74 |
| Qwen2.5-72B-Instruct | 73.49 | 75.81 | 73.49 |
| DeepSeek-V3 | 48.84 | 34.43 | 48.84 |

Qwen2.5-Max在Pass^1指标下取得76.74的最高整体准确率，但在Pass^5严格一致性指标下，GPT-4o仅达23.81%，显示模型在多次独立试验中保持正确性的能力不足。

消融分析显示，模型规模在70B以下时性能随参数增加而提升，但超过此阈值后增益递减。DeepSeek-V3在Pass^k指标下性能急剧下降，部分任务准确率为零，表明其推理稳定性较差。幻觉率分析揭示，DeepSeek-V3和OmniSQL-32B的幻觉率分别为44.28%和26.15%，而GPT-4o仅为0.09%，暗示后训练中的逐步推理模式可能导致模型过早生成“答案”而非等待环境反馈。

评估边界方面，DySQL-Bench采用Pass^k指标量化稳定性，但缺乏与静态基准（如Spider）的对照实验，无法排除性能下降仅源于任务复杂度而非方法缺陷。模拟用户由Qwen2.5-72B-Instruct扮演，其指令生成可能引入额外噪声，干扰对Agent能力的纯粹评估。代码已开源，但超参数设置（如温度0.6）固定，未探索不同推理策略对稳定性的影响。

## 关联研究分析

从问题动机看，DySQL-Bench与CoE-SQL均关注多轮对话，但CoE-SQL依赖静态历史AST比较，而本文引入实时状态哈希验证。这一差异源于任务特性：CoE-SQL假设对话历史固定，而真实场景中用户意图随Agent反馈动态调整。CoE-SQL未测试状态变更操作，导致其无法评估Agent在数据分布动态变化下的鲁棒性。

从方法设计看，DySQL-Bench与Track-SQL都采用动态模式链接，但Track-SQL聚焦于指代消解，而本文扩展至全CRUD操作。Track-SQL的静态历史更新机制无法处理INSERT/DELETE引起的模式结构变化，而本文的三元交互框架通过实时数据库执行反馈，迫使Agent适应状态演化。然而，本文未单独报告模式链接准确率，可能掩盖了链接错误对最终状态哈希的影响。

## 总结

DySQL-Bench旨在解决静态文本到SQL基准无法捕捉动态多轮交互与状态变更的核心矛盾。通过两阶段自动合成管线与三元交互框架，本文构建了首个支持完整CRUD操作的动态基准，揭示了前沿模型在动态SQL推理上的显著脆弱性。实验显示，Qwen2.5-Max在Pass^1下取得76.74的最高准确率，但GPT-4o在Pass^5下仅达23.81%，表明模型在多次独立试验中保持正确性的能力不足。本文的边界在于模拟用户的保真度未经验证，且缺乏与静态基准的对照实验。当模拟用户的行为分布偏离真实人类意图时，基准的评估效度是否受损，论文未给出回答。
