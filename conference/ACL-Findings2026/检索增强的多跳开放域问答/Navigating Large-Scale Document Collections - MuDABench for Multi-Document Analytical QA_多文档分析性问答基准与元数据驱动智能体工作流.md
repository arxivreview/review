作者：Zhanli Li、Yixuan Cao、Lvzhou Luo 等 4 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.22239)

> 现有检索增强生成（RAG）范式在处理跨文档多跳推理时，常因证据分散和中间实体缺失导致推理链断裂，但这类任务通常仅涉及少量文档的语义关联。当面对由数百份半结构化文档组成的大规模集合时，传统单次或迭代检索模式因上下文窗口限制和缺乏全局聚合能力而彻底失效，且现有基准未覆盖此类需要跨大量文档进行定量分析的场景。本文切入点在于将文档集合视为半结构化数据库，提出 MuDABench 基准及元数据感知的多智能体工作流，通过并行单文档提取与代码执行实现信息聚合。该工作填补了大规模文档分析性问答的评测空白，但所有方法在绝对性能上仍显著低于人类专家，暴露出单文档提取精度与领域知识规划的瓶颈。

## 研究背景

当大语言模型（LLM）处理知识密集型任务时，静态参数化知识导致的幻觉与长上下文注意力稀释是固有局限。在需要跨越多个文档进行链式逻辑推导的多跳推理场景中，单次检索模式因证据分散而失效，这催生了检索增强生成（RAG）范式。然而，RAG 通常将文档视为松散关联的片段，旨在检索少量段落以适配单一上下文窗口，这种交互模式在文档数量极少时有效，但无法应对文档集合行为类似半结构化数据库的场景。

主流的多跳问答研究聚焦于 Wikipedia 式短文本，如 HotpotQA 和 MuSiQue，其核心假设是“单次或迭代检索即可获取所有必要证据”。长上下文基准如 LongBench 和 RULER 虽扩展了输入长度，但假设所有相关内容能装入单一窗口，且缺乏对文档元数据的利用。金融领域基准如 FinanceBench 和 FinAgentBench 关注单文档检索精度，而非下游的大规模聚合分析。本文针对这一空白，提出多文档分析性问答（Multi-Document Analytical QA）任务，要求从超过 LLM 上下文窗口的大规模文档集合中提取、综合信息并进行定量分析，现有基准均未覆盖此场景。

## 核心方法

### 方法参照系

本文任务属于智能体架构路线，但偏离了迭代检索-推理的标准流程。通用流程依赖迭代检索积累证据，而本文采用“并行单文档提取+代码聚合”，无迭代检索环节。关键差异在于：本文利用文档元数据（如年份、类型）约束检索范围，将非结构化文档提取结果规范化为扁平 JSON，作为代码代理的输入，实现了从文本到结构化数据的转换，而非依赖 LLM 直接进行长程语义推理。

### 元数据感知的规划与提取

规划代理（Planning Agent）不立即检索文档，而是将全局查询 $Q$ 分解为问题模板 $T$，模板可包含元数据限制。对于每个文档 $D_i$ 及其元数据 $M_i$，若满足限制条件，则实例化模板生成子查询 $q_{i,j}$，并通过标准 RAG 系统执行单文档定向提取。这一设计解决了此前方法中查询分解不准确导致的错误传播问题，通过元数据过滤降低了规划错误，确保方法可扩展至任意大小的文档集合。

$$
q_{i,j} = \text{FILLTEMPLATE}(T_j, M_i) \quad \text{if} \quad \text{SATISFYRESTRICTION}(M_i, T_j)
$$

该公式表示仅当文档元数据满足模板限制时，才用元数据填充模板生成子查询，从而避免对无关文档的无效检索。

### 批量规范化与代码执行

规范化代理（Norm Agent）将非结构化提取转录转换为结构化 JSON 记录。为避免处理数千文档时的上下文溢出，采用批量迭代策略：从少量样本定义 schema $S_{json}$，后续记录在该统一 schema 下分批规范化。代码代理（Code Agent）接收 schema 和示例，合成程序对完整结构化数据集 $J$ 执行分析，生成最终答案 $A$。这一设计解决了 LLM 在数值计算和逻辑过滤上的固有缺陷，通过代码执行确保聚合过程的确定性，同时通过批量策略控制了计算成本。

$$
J = \bigcup_{k=1}^{K} \text{NORMAGENT}(B_k, S_{json}) \quad \text{where} \quad K = \lceil |Q_{pairs}| / B \rceil
$$

该公式表示将提取结果对 $Q_{pairs}$ 分批处理，每批 $B_k$ 在统一 schema 下规范化，最终合并为完整结构化数据集 $J$，供代码代理执行分析。

## 实验评估

实验在 MuDABench 上进行，该基准包含 80,000 页以上文档和 332 个分析性问答实例，平均每个问题涉及 14.8 份文档。基线仅对比标准 RAG 系统，缺失迭代检索（如 PRISM）或图结构方法（如 HippoRAG）等强基线，导致无法全面评估不同路线的优劣。

| :--- | :--- | :--- | :--- | :--- |
| A股年报 (CN) | 499k | 0.4696 / 0.4555 | 0.6537 / 0.6674 | 0.6447 / 0.6570 |
| A股ESG报告 (CN) | 72k | 0.3998 / 0.3898 | 0.6067 / 0.4813 | 0.5865 / 0.4992 |
| A股公告 (CN) | 144k | 0.3903 / 0.3786 | 0.5222 / 0.4976 | 0.5542 / 0.5575 |
| 美股年报 (EN) | 120k | 0.4472 / 0.3955 | 0.3167 / 0.5374 | 0.4643 / 0.7375 |

主实验显示，标准 RAG 在 MuDABench 上表现不佳，即使使用 GPT-4o 也受限于结构。多智能体工作流显著提升了最终答案准确率，但所有方法仍远低于人类专家。消融实验表明，提取步骤的独立准确率最低（Simple 40.0%, Complex 20.0%），是主要瓶颈；规划、规范化和代码步骤准确率较高（均 >90%），表明单文档信息提取精度是限制整体性能的关键。

评估协议采用 LLM-as-judge，包括最终答案准确率、过程准确率和完整准确率。过程准确率通过中间事实覆盖或单元格级评估计算，手动审计显示单元格级一致性为 81.93%。可复现性方面，论文提供代码 URL，但未报告 GPU 资源或超参数细节，且依赖商业 PDF 处理工具 ChatDOC，可能影响结果的可复现性。

## 关联研究分析

从问题动机看，本文与 FinAgentBench 同属金融文档领域，但 FinAgentBench 侧重检索精度，评估智能体能否定位正确文档类型和段落，而本文侧重下游聚合分析，要求从大规模文档集合中提取并综合信息。这一差异源于任务特性：FinAgentBench 关注单文档定位，本文关注跨文档定量分析，因此本文引入代码代理执行数值计算，而 FinAgentBench 未涉及此环节。

从方法设计看，本文与 PRISM 同属智能体架构，但 PRISM 依赖迭代检索积累证据，通过问题分析器、选择器和添加器逐步精炼证据集，而本文采用并行单文档提取+代码聚合，无迭代检索环节。这一差异源于文档规模：PRISM 适用于少量文档的多跳推理，本文适用于大规模文档集合的聚合分析，因此本文利用元数据过滤和批量规范化策略，确保可扩展性。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

本文要解决的核心矛盾是大规模半结构化文档集合中的元数据驱动聚合分析，现有方法因上下文窗口限制和缺乏全局聚合能力而失效。本文抓住的切入点是利用文档元数据约束检索范围，并通过代码执行实现确定性聚合，从而避免 LLM 在数值计算上的固有缺陷。本文提出了 MuDABench 基准及元数据感知的多智能体工作流，证明了标准 RAG 在此任务上表现不佳，而多智能体工作流显著提升了最终答案准确率，但所有方法仍远低于人类专家。本文的边界在于单文档信息提取精度不足（Complex 任务仅 20.0%）和领域特定知识规划能力有限，导致整体成功率低。当文档结构噪声增大或元数据缺失时，该工作流的泛化能力如何，论文未给出回答。
