# ACL-Findings2026最新论文 ｜Speculative Decoding with a Speculative Vocabulary ｜词表推测（SpecVocab）：动态子集选择缓解草稿模型输出分布计算瓶颈

作者：Miles Williams、Young D. Kwon、Rui Li 等 5 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_4eed40cc58bb)

> 导读 投机解码（Speculative Decoding, SD）通过草稿模型并行预测与目标模型单次验证实现无损加速，但大词表投影导致草稿阶段延迟高企，成为加速比的主要限制因素。现有静态词表裁剪方法（如 FR-Spec、VocabTrim）虽降低计算量，却因上下文无关性导致目标 token 落在子集外时接受率骤降，抵消加速收益。本文提出 SpecVocab，通过上下文感知的动态词表子集预测，在保持无损性的同时提升接受长度与吞吐量。该方法在 EAGLE-3 框架内实现最高 8.1% 的吞吐量提升，但其绝对加速比仍低于领域内特征对齐路线的 SOTA，且未验证长上下文与多模态场景下的泛化能力。

## 研究背景

自回归解码的串行特性与硬件内存带宽限制构成 LLM 推理效率的核心矛盾，投机解码通过“草稿-验证”范式将串行生成转化为并行验证，在不改变输出分布的前提下提升吞吐量。草稿模型的质量（接受率）是决定加速比的关键，而输出分布计算开销随词表规模线性增长，成为草稿阶段的延迟瓶颈。

早期研究聚焦于独立草稿模型与目标模型的分布对齐，EAGLE 系列通过特征对齐显著提升接受率，但全词表投影的计算成本随词表扩大（如 Qwen3 的 152K 词表）而急剧增加。FR-Spec 和 VocabTrim 利用自然语言的 Zipf 分布特性，通过静态裁剪词表至 32K 子集来降低投影延迟，但固定子集无法适应上下文变化，当目标 token 落在子集外时，当前及后续草稿 token 均被拒绝，导致加速比归零。本文切入点在于：将词表选择从静态后处理改为动态前向预测，使草稿模型在每步解码时仅计算上下文相关子集的输出分布，从而在降低计算量的同时维持接受率。

## 核心方法

### 方法参照系

本文问题属于“草稿模型训练优化”路线，标准流程为：草稿模型利用目标模型隐藏状态生成候选 token，通过全词表或静态裁剪词表计算输出分布。本文关键差异在于引入“词表推测模块”，动态预测每步相关子集，替代静态裁剪的上下文无关性。

### 词表排名与子集选择

静态裁剪方法（如 FR-Spec）基于全局 token 频率选择固定子集，忽略上下文依赖性，导致目标 token 落在子集外时接受率损失。本文在草稿模型最终隐藏状态 $h_t$ 上引入降维投影 $W_{down} \in \mathbb{R}^{d' \times d}$（$d' \ll d$），计算近似 logits $s_t = W_{vocab} h'_t$，其中 $W_{vocab} \in \mathbb{R}^{|V| \times d'}$，$h'_t = W_{down} h_t$。通过 top-k 选择 $k_t = \text{top-k}(s_t, k)$ 得到候选词表 $K_t$，其规模通常 $k=2048$，远小于静态方法的 32K。该设计动机在于：动态子集选择使草稿模型仅计算上下文相关 token 的输出分布，避免静态裁剪因上下文无关性导致的接受率损失，同时通过降维投影降低排名计算开销。

### 融合内核与训练策略

计算候选词表 logits 需对 $h_t$ 与 $K_t$ 中每个 embedding 做点积，朴素实现需多次内存读写。本文实现融合内核，仅从内存读取每个 embedding 一次，避免中间矩阵 $U'_t$ 的物化，加速 logits 计算达 5 倍。训练时，词表推测模块与草稿模型联合优化，损失函数为 $L = L_{TTT}(p, q) + \lambda L_{TTT}(p, q_{aux})$，其中 $q_{aux}$ 为词表推测模块的输出分布，$\lambda$ 调节其贡献。该设计动机在于：通过蒸馏目标模型分布，使词表推测模块学习上下文相关的子集选择策略，同时避免草稿模型因词表压缩而损失表示能力，确保接受长度不下降。

## 实验评估

实验基于 Spec-Bench 基准（含 MT-Bench、GSM8K 等六类任务），使用 Qwen3 4B/8B 和 OLMo 2 1B/7B 四个模型，基线覆盖 EAGLE-3、FR-Spec、VocabTrim，但缺失独立小模型（如 DistillSpec）及树状验证对比（如 SpecInfer）。

| 方法 | 平均接受长度 (Qwen3 8B) | 平均吞吐量 (tokens/s, Qwen3 8B) | 加速比 (Qwen3 8B) |
| :--- | :--- | :--- | :--- |
| EAGLE-3 | 4.33 | 212.7 | 2.19× |
| EAGLE-3 + VocabTrim | 4.84 | 237.6 | 2.45× |
| EAGLE-3 + SpecVocab | 5.01 | 245.2 | 2.53× |

SpecVocab 在 Qwen3 8B 上平均接受长度较 EAGLE-3 提升 4.8%（+0.23 tokens/步），吞吐量提升 4.3%；在 OLMo 2 7B 上吞吐量提升达 8.1%。消融显示，VocabTrim 在多数任务上优于 EAGLE-3 的静态裁剪训练，证明后训练裁剪优于从头训练小词表；但 SpecVocab 在 24 个任务-模型组合中 23 个优于所有基线，唯一例外是 Qwen3 8B 摘要任务，较 FR-Spec 低 0.8%（1.7 tokens/s）。

评估边界：指标仅覆盖接受长度与吞吐量，未报告置信区间或计算效率维度；实验使用 SGLang 框架消除 CPU 开销，但单 GPU 设置限制了高并发场景的验证；代码开源（github.com/SamsungLabs/SpecVocab），训练超参数完整披露，可复现性良好。

## 关联研究分析

从问题动机看，SpecVocab 与 EAGLE-3 同属特征对齐路线，但 EAGLE-3 聚焦于树状草稿架构与全词表投影，而 SpecVocab 针对输出分布计算瓶颈，通过动态子集选择解决静态裁剪的上下文无关性缺陷。这一差异源于任务特性：大词表模型（如 Qwen3 152K）中，全词表投影延迟占比显著，静态裁剪虽降低计算量，但接受率损失抵消收益；而小词表模型（如 BERT 30K）中，投影延迟占比低，动态选择的边际收益可能不足。

从方法设计看，SpecVocab 与 FR-Spec/VocabTrim 同属词表裁剪路线，但 FR-Spec 基于外部语料（SlimPajama）计算 token 频率，VocabTrim 基于目标模型生成数据，而 SpecVocab 通过上下文感知的动态预测替代静态频率统计。这一差异源于数据分布假设：静态方法假设 token 频率全局稳定，但实际生成中 token 分布高度依赖上下文，动态选择能更精确地覆盖高概率 token。然而，SpecVocab 未验证动态选择在长上下文（>8K tokens）下的稳定性，当上下文长度增加时，词表推测模块的排名准确性是否下降，论文未给出回答。

## 总结

本文要解决的核心矛盾是：大词表投影导致草稿阶段延迟高企，而静态词表裁剪因上下文无关性导致接受率损失，两者共同限制投机解码的加速比。本文抓住的切入点是：词表选择应从静态后处理改为动态前向预测，使草稿模型在每步解码时仅计算上下文相关子集的输出分布，从而在降低计算量的同时维持接受率。本文通过词表推测模块与融合内核实现这一目标，在 EAGLE-3 框架内实现最高 8.1% 的吞吐量提升，接受长度较 EAGLE-3 提升 4.8%。本文的边界在于：实验仅覆盖单 GPU 与短上下文场景，未验证长上下文与多模态输入下的泛化能力，且绝对加速比（2.53×）低于领域内特征对齐路线的 SOTA（~3.5×），表明其优化空间受限于 EAGLE 框架本身。当上下文长度超过 8K tokens 时，词表推测模块的排名准确性是否因上下文稀释而下降，论文未给出回答。
