# 中大南洋理工阿里联合发布RealSec-bench：基于真实Java仓库评估LLM安全代码生成，揭示跨过程漏洞短板

研究机构：中山大学、新加坡南洋理工大学

作者：Yanlin Wang、Ziyao Zhang、Chong Wang 等 8 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_217605fc06c1)

RealSec-bench (RealSec-bench)

> 现有安全代码生成基准多依赖合成片段或孤立函数，无法捕捉真实软件中跨过程数据流引发的漏洞，导致对模型安全能力的评估存在系统性高估。本文切入点在于构建基于真实高风险 Java 仓库的基准，通过 SAST 筛选与多 LLM 裁决机制解决静态分析高误报与上下文缺失的双重难题。其核心做法是构建包含 105 个实例的 RealSec-bench，并引入联合指标 SecurePass@k 同时评估功能与安全性。该基准揭示了当前主流 LLM 在仓库级安全生成上的显著短板，但其仅覆盖 Java 语言且实例规模有限，跨语言泛化性存疑。

## 研究背景

当 LLM 生成的代码从孤立函数扩展至完整仓库时，安全漏洞往往不再局限于单一函数内部，而是源于跨函数、跨模块的数据流交互。这种复杂性要求评估基准必须提供完整的仓库上下文，而非简化的代码片段。然而，静态应用安全测试（SAST）工具在扫描真实代码时存在极高的误报率，若直接将其输出作为基准的“真值”，会严重扭曲对模型安全能力的评估。为平衡上下文真实性与标注准确性，基准构建需在 SAST 的广度与人工审计的精度之间建立自动化过滤机制。

安全代码生成领域的核心矛盾在于功能正确性与安全性的权衡。早期基准如 CodeLMSec 聚焦于孤立片段，虽便于自动化测试，但忽略了漏洞在大型系统中的传播路径，导致模型在简单场景下的表现被过度泛化。随着 SWEbench 等仓库级基准的出现，研究重心转向真实项目，但安全维度的引入面临新挑战：如何在保证代码可编译、可测试的前提下，准确识别并标注跨过程漏洞。现有方法多依赖单一 SAST 工具或纯人工标注，前者误报率高，后者成本巨大且难以规模化。

RealSec-bench 的切入点在于利用多 LLM 裁决机制替代部分人工审计，以解决 SAST 误报与人工成本之间的冲突。该基准从真实 Java 仓库中提取漏洞，通过执行过滤确保可复现性，并利用 GPT-4.1 与专家协作进行二次验证。这一设计旨在构建一个既具备真实仓库复杂度，又拥有高置信度安全标签的评估环境，从而更准确地量化 LLM 在复杂依赖场景下的安全生成能力。

## 核心方法

### 方法参照系

安全代码生成基准的构建通常遵循“数据收集-漏洞标注-任务标准化”流程。本文问题与通用流程的关键差异在于：传统基准多基于合成数据或孤立函数，而 RealSec-bench 要求从真实仓库中提取具备跨过程依赖的漏洞，并解决 SAST 高误报导致的标签噪声问题。

### 多阶段漏洞筛选与实例构建

基准构建始于高风险仓库的选择与漏洞提取。设计动机在于解决孤立片段基准无法反映真实软件复杂性的问题。首先，从 GitHub 上筛选出 4,000 个高星 Java 仓库，经 Maven 构建过滤后保留 929 个可编译项目。随后，使用 CodeQL 进行高召回率扫描，从 532 个高风险仓库中提取约 20,000 个原始漏洞警报。为确保可复现性，实施两阶段执行过滤：验证 Maven 构建完整性，并解析覆盖率报告确认候选函数被至少一个可运行单元测试覆盖，将候选集缩减至 160 个可执行实例。

$$
\text{ExecutableInstances} = \{ f \in \text{SASTAlerts} \mid \text{BuildOK}(f) \land \exists t \in \text{Tests}, \text{Covers}(t, f) \}
$$

该公式表示仅保留构建成功且被测试覆盖的 SAST 警报，确保每个实例都具备 fail-to-pass 评估的基础。

### 多 LLM 裁决与安全指标定义

为解决 SAST 高误报问题，引入多 LLM 裁决机制。设计动机在于单一 SAST 工具缺乏语义理解，易将安全代码误判为漏洞。该机制包含两个阶段：首先，三个 Voter LLM 独立分析代码与漏洞报告，提供初步推理；随后，Final-Judge 综合 Voter 理由、仓库上下文及数据流证据，判定警报是否为假阳性。若 Judge 判定为假阳性（置信度 > 0.5），样本重新分类为安全。

$$
\text{Secure@k} = P\left( \bigcup_{i=1}^{k} \left[ \text{SASTPass}(c_i) \lor \text{JudgeAcquit}(c_i) \right] \right)
$$

该公式定义 Secure@k 为 k 个生成样本中至少一个通过 SAST 扫描或被 Judge 判为安全的概率。在此基础上，定义联合指标 SecurePass@k，要求样本同时通过功能单元测试与安全裁决：

$$
\text{SecurePass@k} = P\left( \bigcup_{i=1}^{k} \left[ \text{PassTest}(c_i) \land \text{Secure}(c_i) \right] \right)
$$

这一设计将功能正确性与安全性绑定，避免了单独评估某一维度时的片面性，更贴近实际部署需求。

## 实验评估

实验在 RealSec-bench 上进行，评估五个主流 LLM：GPT-4.1、GPT-4.1-mini、Claude-3.7-Sonnet、Deepseek-V3 和 Qwen3-235B。基线覆盖通用大模型，但未包含专用安全微调模型（如 SafeCoder、SecCoderX），这可能限制了与特定安全优化方法的直接对比。生成参数统一为 temperature 0.7，top-p 1.0，上下文窗口 4096 tokens。

| 模型 | Pass@1 | Secure@1 | SecurePass@1 |
| :--- | :--- | :--- | :--- |
| Claude-3.7-Sonnet | 16.19% | 4.76% | 4.76% |
| GPT-4.1 | 15.24% | 8.57% | 5.71% |
| Qwen3-235B | 11.43% | 6.67% | 5.71% |
| Deepseek-V3 | 8.57% | 5.71% | 3.81% |
| GPT-4.1-mini | 13.33% | 5.71% | 5.71% |

主结果显示，所有模型的 SecurePass@1 均低于 8%，表明在仓库级复杂场景下，功能正确性与安全性难以兼顾。Claude-3.7-Sonnet 在功能正确性上表现最佳（16.19%），但其安全性能并未同步提升，SecurePass@1 仅为 4.76%。

消融实验验证了多 LLM 裁决机制的有效性。原始 SAST 基线的精确率仅为 44.9%，引入三个 Voter LLM 后精确率提升至 63.0%，但召回率下降至 85.0%。加入 Final-Judge 后，精确率进一步升至 81.7%，召回率恢复至 98.0%，F1 分数达到 89.1%，假阳性减少 77.6%。这一结果证实了分层裁决在平衡精确率与召回率上的优势。

| 组件 | 精确率 | 召回率 | F1 分数 | 假阳性减少 |
| :--- | :--- | :--- | :--- | :--- |
| SAST Baseline | 44.9% | 100.0% | 62.0% | - |
| + Three Voter | 63.0% | 85.0% | 72.3% | ↓59.2% |
| + Final Judger | 81.7% | 98.0% | 89.1% | ↓77.6% |

评估边界方面，基准仅覆盖 Java 语言，且实例数量为 105，规模较小，可能影响统计显著性。代码与数据已开源，但多 LLM 裁决的具体模型版本与提示词细节未完全公开，可能影响复现性。此外，SecurePass@1 极低值是否因基准难度过高导致区分度不足，仍需进一步验证。

## 关联研究分析

从问题动机看，RealSec-bench 与 DUALGAUGE 均关注功能-安全联合评估，但 DUALGAUGE 侧重自动化测试生成以验证功能行为，而 RealSec-bench 侧重真实仓库上下文中的跨过程依赖。这一差异源于任务特性：DUALGAUGE 假设漏洞可通过局部测试检测，而 RealSec-bench 指出许多漏洞源于全局数据流，局部测试无法捕捉。RealSec-bench 引入多 LLM 裁决以解决 SAST 误报，而 DUALGAUGE 依赖动态执行验证，两者在解决评估失真问题上采取了不同路径。

从方法设计看，RealSec-bench 与 SecCodeBench-V2 均强调隔离环境与 PoC 验证，但 RealSec-bench 进一步引入多 LLM 裁决以处理 SAST 的语义局限。SecCodeBench-V2 依赖专用 PoC 测试，而 RealSec-bench 利用 LLM 的推理能力辅助判定，这一设计选择挑战了“人工审计是金标准”的隐含假设。然而，LLM 裁决的可靠性是否足以替代部分人工审计，尤其是在处理复杂逻辑漏洞时，论文未给出充分回答。

## 总结

RealSec-bench 旨在解决安全代码生成基准中上下文缺失与 SAST 高误报的双重矛盾。现有方法因依赖孤立片段或单一 SAST 工具，无法准确评估模型在真实仓库中的安全能力。本文通过构建基于真实 Java 仓库的基准，并引入多 LLM 裁决机制，实现了功能与安全性的联合评估。实验证明，当前主流 LLM 的 SecurePass@1 均低于 8%，揭示了其在复杂依赖场景下的显著短板。然而，基准仅覆盖 Java 语言且实例规模有限，跨语言泛化性与大规模仓库扩展性未得到验证。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
