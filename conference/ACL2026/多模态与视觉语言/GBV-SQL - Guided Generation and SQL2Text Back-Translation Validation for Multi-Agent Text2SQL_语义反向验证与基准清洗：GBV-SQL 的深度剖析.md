> 导读

文本到SQL（Text-to-SQL）的核心挑战在于自然语言意图与结构化查询之间的语义鸿沟，现有基于大语言模型（LLM）的生成方法虽能产出语法正确的SQL，却常因逻辑偏差导致执行结果错误。本文指出当前主流方法缺乏对最终查询语义一致性的显式验证机制，且现有基准存在严重的标注噪声。GBV-SQL 提出一种多智能体框架，通过SQL到自然语言的反向翻译验证语义对齐，并引入“Gold Error”分类法清洗基准数据。该工作揭示了评估失真问题，但在复杂推理场景下的泛化能力仍受限于骨干模型能力。

## 研究背景

当用户询问“平均写作分数为499的学校章程号”时，模型可能生成包含 `HAVING AVG(...)` 的聚合查询，而非直接过滤 `WHERE AvgScrWrite = 499` 的简单查询。这种语法正确但语义错误的现象源于自然语言问题（NLQ）与SQL结构间的语义鸿沟。解决此问题需依赖模式链接（Schema Linking）准确识别相关表列，并通过上下文学习（In-Context Learning, ICL）利用LLM的先验知识生成查询。然而，ICL生成的SQL往往缺乏对原始意图的逆向校验，导致逻辑偏差难以被检测。

早期研究聚焦于序列到序列架构与图神经网络，通过显式编码模式结构解决单轮翻译，但受制于跨域泛化能力。随着LLM引入，研究重心转向提示工程，DIN-SQL 和 DAIL-SQL 通过分解式上下文学习提升了复杂查询性能，但推理过程仍缺乏显式逻辑验证。MAC-SQL 和 MAG-SQL 引入多智能体协作管理分解与生成，但现有智能体仅负责生成，未对最终SQL进行语义验证。本文切入点在于填补这一验证空白，并指出当前基准（如Spider）中普遍存在的“Gold Error”导致模型性能被低估。

## 核心方法

### 方法参照系

GBV-SQL 属于LLM提示工程路线，其标准流程为：Schema剪枝 → 问题分解 → SQL生成 → 后处理。与MAC-SQL等基线相比，关键差异在于引入了独立的语义验证智能体（SQL2TextValidator），将单向生成流程转变为“生成-验证-修正”的闭环，以解决语法正确但语义偏离的问题。

### 语义反向验证机制

SQL2TextValidator 位于SQL生成之后、最终输出之前，其设计动机是解决现有方法缺乏显式逻辑验证导致的语义偏差。该模块提示LLM将生成的初始SQL翻译回自然语言描述，并与原始NLQ进行对比。若发现逻辑不一致，LLM被提示修正SQL以对齐用户意图。为最大化验证效果，引入二元选择器（Binary Selector），基于执行结果评估初始SQL与验证后SQL的语义一致性，选择最优版本作为最终SQL。该机制通过逆向视角挑战查询的语义保真度，提供了此前协作模型中缺失的反馈回路。

### 迭代执行修复与Schema精炼

SQLChecker 模块处理格式错误与执行异常，其设计动机是解决LLM幻觉导致的格式冗余或执行失败。该模块采用最小化原则消除冗余字段，并通过多轮迭代检查可执行性。若执行结果为空、0或包含NULL，则触发修复循环。修复过程检索数据库中top-k相关值，结合部分执行结果作为上下文提示LLM修正。此外，Planner 模块通过“反向链接”操作提取每个子SQL所需的表列对，合并为核心Schema $S_{core}$，定义如下：

$$ S_{core} = \bigcup_{i=1}^{N} S_i $$

其中 $S_i$ 为第 $i$ 个子SQL所需的表列集合。该精炼过程确保后续生成聚焦于高度相关的模式信息，减少无关干扰。

## 实验评估

实验在 Spider 和 BIRD 基准上进行，使用 Deepseek-v3 和 GPT-4o 作为骨干，温度设为0。基线覆盖 DIN-SQL、DAIL-SQL、MAC-SQL、MAG-SQL 等 ICL 主流方法，但缺失 SQL-R1 等强化学习路线及 EXPO-SQL 等最新 SOTA 方法。

| 方法 | Spider Dev EX | Spider Test EX | BIRD Dev EX |
| :--- | :--- | :--- | :--- |
| MAC-SQL + Deepseek-v3 | 80.1 | 77.6 | 57.43 |
| GBV-SQL + Deepseek-v3 | 79.6 | 82.8 | 63.23 |
| GBV-SQL + GPT-4o | 79.7 | 83.9 | – |
| GBV-SQL + No Gold Errors | 96.5 | 97.6 | – |

在 BIRD 基准上，GBV-SQL 使用 Deepseek-v3 取得 63.23% 的执行准确率（EX），较同骨干 MAC-SQL 提升 5.8%。在 Spider 测试集上，GBV-SQL 达到 82.8%，优于 MAC-SQL 的 77.6%。然而，Spider 开发集性能（79.6%）低于预期，经分析发现主要源于基准中的“Gold Error”。

| 消融配置 | Simple | Moderate | Challenging | Total |
| :--- | :--- | :--- | :--- | :--- |
| GBV-SQL (Full) | 69.51 | 54.62 | 50.69 | 63.23 |
| w/o SQLChecker | 66.49 | 49.89 | 47.22 | 59.65 |
| w/o SQL2TextValidator | 68.54 | 52.69 | 47.92 | 61.80 |
| w/o Human-like CoT | 66.70 | 52.90 | 51.39 | 61.08 |

消融实验显示，移除 SQLChecker 导致性能下降最大（63.23% 降至 59.65%），表明可执行性检查对当前基于执行的评估范式至关重要。移除 SQL2TextValidator 导致中等难度查询性能显著下降（54.62% 降至 52.69%），验证了语义验证对复杂逻辑处理的贡献。

评估边界方面，论文未报告置信区间，数值比较需谨慎。代码未公开，但提供了详细的提示模板与算法伪代码。超参数包括最大修复迭代次数为3，温度设为0。指标完备性上，论文同时报告了执行准确率（EX）和有效效率分数（VES），但 VES 仅在结果匹配时计算，可能低估了效率差异。

## 关联研究分析

从方法设计看，GBV-SQL 与 MAC-SQL 共享多智能体架构，但核心差异在于验证机制。MAC-SQL 的智能体协作聚焦于分解与生成的分工，而 GBV-SQL 引入 SQL2TextValidator 作为独立的语义验证者。这一差异源于任务特性：复杂查询的逻辑错误往往难以通过前向生成检测，需逆向翻译才能暴露意图偏差。相比之下，CHESS 采用多智能体协作解决大规模 Schema 下的链接噪声，但未涉及语义验证，其优势在于模式链接的准确性，而 GBV-SQL 的优势在于生成后的逻辑保真度。

从问题动机看，GBV-SQL 与 EXPO-SQL 均关注鲁棒性，但路径不同。EXPO-SQL 通过强化学习（RL）利用执行反馈优化策略，依赖参数更新提升小模型性能；GBV-SQL 则通过提示工程中的反向验证提升鲁棒性，无需微调。这一差异反映了领域内“提示工程 vs. 训练优化”的核心分歧。GBV-SQL 的验证机制依赖于 LLM 的语义理解能力，若骨干模型能力不足，验证效果可能受限；而 EXPO-SQL 的 RL 方法依赖执行环境的稳定性，若反馈噪声大，优化可能不稳定。

## 总结

GBV-SQL 旨在解决 Text-to-SQL 中语法正确但语义偏离的核心矛盾，通过引入 SQL2Text 反向验证机制填补了现有方法缺乏显式逻辑验证的空白。该框架在 BIRD 基准上取得 63.23% 的 EX，较基线提升 5.8%，并在清洗后的 Spider 基准上达到 96.5% 和 97.6% 的 EX，揭示了基准噪声对评估的干扰。然而，论文实验显示 Spider 开发集性能低于测试集，且消融实验表明 SQLChecker 对性能影响最大，暗示当前评估范式对可执行性的过度依赖。当骨干模型从 Deepseek-v3 更换为 GPT-4o 时，Spider 测试集性能仅提升 1.1%（82.8% 至 83.9%），这是否意味着语义验证机制的增益已接近饱和，还是受限于基准本身的噪声上限，论文未给出明确回答。
