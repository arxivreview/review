# ACL2026最新论文 ｜ReEx-SQL: Reasoning with Execution-Aware Reinforcement Learning for Text-to-SQL ｜执行感知强化学习文本到SQL生成

研究机构：复旦大学、中国科学院大学

作者：Yaxun Dai、Wenxuan Xie、Xialie Zhuang 等 10 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ef7ba813e7b8)

> 文本到SQL的核心矛盾在于自然语言的模糊性与SQL执行的确定性之间的鸿沟，传统思维链推理缺乏外部验证导致错误累积。现有强化学习方法虽能优化推理路径，但将执行反馈隔离在解码之外，无法实时修正语义偏差。ReEx-SQL将SQL执行器嵌入强化学习的Rollout过程，通过生成-验证-修正闭环实现端到端交互。该方法在7B规模下实现了鲁棒性基准的领先，但其性能上限受限于骨干模型能力，且执行反馈的延迟开销在复杂查询中是否可接受仍存疑。

## 研究背景

当大语言模型面对包含歧义列名和复杂表间关系的数据库模式时，静态上下文中的语义鸿沟导致生成的SQL频繁出现语法错误或语义偏差。这种错误累积源于思维链（Chain-of-Thought, CoT）推理的封闭性：模型仅依赖自身参数和输入上下文进行单步生成，缺乏对中间SQL执行结果的即时感知。为打破这一局限，执行反馈被视为关键的外部监督信号，但现有方法多将其作为后处理步骤，导致修正过程可能破坏原本正确的SQL结构。

文本到SQL领域的主流路线已从序列翻译转向基于大语言模型的推理优化。早期工作如DIN-SQL通过分解任务提升复杂查询性能，但缺乏显式逻辑验证；近期SQL-R1等采用组相对策略优化（Grouped Reinforcement Policy Optimization, GRPO）增强推理能力，却仍未在执行阶段引入实时反馈。这种分离式设计使得模型无法在生成过程中动态调整策略，尤其在面对模糊问题或分布偏移时，语义对齐能力显著下降。ReEx-SQL的切入点在于将执行反馈直接整合到强化学习的策略更新过程中，使模型能够基于数据库的实际响应进行迭代修正，从而在解码阶段实现语义与语法的同步验证。

## 核心方法

### 执行感知强化学习框架

ReEx-SQL基于GRPO算法构建，其核心差异在于Rollout过程中引入了SQL执行器 $E$。标准GRPO仅基于最终输出计算奖励，而ReEx-SQL将执行反馈 $E$ 嵌入策略 $\pi_\theta$ 的采样过程，形成 $\pi_\theta(\cdot|x) \otimes E$ 的交错结构。这一设计解决了传统RL中奖励稀疏且无法定位具体错误环节的问题，使模型能够针对中间SQL的执行结果进行细粒度策略调整。

### 复合奖励与反馈掩码机制

为应对执行反馈带来的训练不稳定性和奖励黑客风险，ReEx-SQL设计了包含格式、执行、精确匹配、实体匹配和探索五个维度的复合奖励函数 $R = \sum_{i \in C} w_i R_i$。其中，执行奖励 $R_{exec}$ 由语法有效性和结果一致性两部分组成，直接约束SQL的可执行性与语义正确性。关键创新在于对执行反馈Token进行掩码处理，确保策略梯度仅基于模型自身生成的Token计算，避免外部噪声干扰参数更新。该机制的物理含义是：模型学习的是“如何根据反馈调整推理”，而非“如何记忆反馈内容”，从而提升了泛化能力。

### 树结构解码策略

针对多轮交互导致的推理延迟问题，ReEx-SQL采用树结构解码替代线性解码。每个节点包含推理上下文、候选SQL及其执行结果，通过执行结果剪枝错误分支，减少冗余探索。相比线性解码，树结构解码在16个候选下将推理时间降低51.9%，同时通过执行投票机制选择最可靠的输出。这一设计平衡了探索广度与计算效率，使模型能够在有限预算内最大化正确SQL的生成概率。

## 实验评估

ReEx-SQL在BIRD和Spider基准上进行了全面评估，基线覆盖了RL类（SQL-R1, Reasoning-SQL）和SFT类（CodeS, OmniSQL）方法，但缺失GBV-SQL等最新SOTA。主实验结果显示，ReEx-SQL在BIRD Dev上取得65.3%的执行准确率（EX）和73.3%的有效效率分数（VES），在Spider Dev上达到89.1% EX，优于同规模RL基线SQL-R1（63.1% EX）和Reasoning-SQL（64.0% EX）。

| 方法 | BIRD Dev EX | BIRD Dev VES | Spider Dev EX | Spider Test EX |
| :--- | :--- | :--- | :--- | :--- |
| SQL-R1-7B | 63.1 | - | 84.5 | 86.1 |
| Reasoning-SQL | 64.0 | - | - | 78.72 |
| ReEx-SQL-7B | 65.3 | 73.3 | 89.1 | 86.9 |

消融实验揭示了奖励权重对性能的关键影响。MaxTune配置（$w_{format}=2.0, w_{em}=1.0, w_{exec}=3.0, w_{entity}=1.0, w_{expl}=2.0$）在BIRD Dev上取得63.4% EX，显著优于均匀权重配置（62.3% EX）和仅增加探索权重的配置（62.0% EX）。执行奖励 $R_{exec}$ 的权重最高，表明执行反馈是驱动性能提升的核心因素。此外，树结构解码相比线性解码在BIRD Dev上提升了1.2% EX，同时降低了51.9%的推理延迟，验证了效率与准确性权衡的有效性。

评估边界方面，ReEx-SQL仅使用Qwen2.5-Coder-7B作为骨干，未报告置信区间，且未覆盖GBV-SQL等最新SOTA方法。可复现性方面，论文提供了详细的超参数设置（batch size 64, learning rate 2e-6, temperature 1.0）和硬件配置（8 NVIDIA A800 GPUs），但未公开代码仓库，限制了独立复现的可能性。

## 关联研究分析

从问题动机看，ReEx-SQL与SQL-R1同属RL路线，但前者将执行反馈嵌入Rollout过程，而后者仅基于最终结果计算奖励。这一差异源于对“语义对齐”实现路径的不同理解：SQL-R1假设推理能力的提升能间接改善SQL正确性，而ReEx-SQL认为直接验证执行结果是更可靠的监督信号。根源在于任务特性：SQL的正确性不仅取决于逻辑推理，还依赖于数据库的具体内容，后者无法通过参数化推理完全捕获。

从方法设计看，ReEx-SQL与DIN-SQL代表了两种截然不同的错误修正范式。DIN-SQL采用后处理修正，通过独立的修正模块调整初始SQL，但可能引入新错误（如DIN-SQL在BIRD上引入113个额外错误）；ReEx-SQL则通过端到端交互实现实时修正，避免了模块间的信息损失。这一差异反映了领域对“验证时机”的共识转变：从解码后验证转向解码中验证。然而，ReEx-SQL的执行反馈依赖数据库的可执行性，若执行成本高或数据库只读，该方法的适用性将受到限制，论文未对此场景进行探讨。

## 总结

ReEx-SQL旨在解决文本到SQL中推理过程缺乏实时验证导致的错误累积问题，其切入点在于将执行反馈直接整合到强化学习的策略更新过程中，使模型能够基于数据库的实际响应进行迭代修正。通过扩展GRPO算法并设计复合奖励与树结构解码，ReEx-SQL在7B规模下实现了BIRD Dev 65.3% EX和Spider Dev 89.1% EX的性能，优于同规模RL基线。其边界在于依赖数据库的可执行性，且执行反馈的延迟开销在复杂查询中可能成为瓶颈。当数据库执行时间超过模型推理时间时，执行感知推理的效率优势是否仍能保持，论文未给出回答。
