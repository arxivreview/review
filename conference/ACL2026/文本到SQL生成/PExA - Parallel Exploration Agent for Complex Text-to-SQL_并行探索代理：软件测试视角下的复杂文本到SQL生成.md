# ACL2026最新论文 ｜PExA: Parallel Exploration Agent for Complex Text-to-SQL ｜并行探索代理：软件测试视角下的复杂文本到SQL生成

研究机构：美国加州大学洛杉矶分校

作者：Tanmay Parekh、Ella Hofmann-Coyle、Shuyi Wang 等 6 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.22934)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.22934)

> 复杂企业数据库中的自然语言查询往往涉及嵌套数据类型与超长SQL，现有串行推理代理虽能提升准确率，但延迟随推理步骤线性增长，难以满足交互式分析需求。PEXA将文本到SQL重构为软件测试覆盖问题，通过并行生成并执行一组简化的“测试用例”SQL，在获取充分语义证据后合成最终查询。该框架在Spider 2.0基准上取得了70.2%的执行准确率，同时保持了与串行基线相当的低延迟。其价值在于打破了性能与延迟的帕累托约束，但测试用例的“过度生成”策略是否会在极端复杂场景下导致计算成本失控，仍需进一步验证。

## 研究背景

当企业分析师面对包含数百张表、嵌套JSON字段的Snowflake数据库时，直接让大语言模型（LLM）生成完整SQL往往因上下文窗口限制和逻辑复杂度而失败。这种困境源于两个核心概念的冲突：一是模式链接（Schema Linking），即从海量列名中准确识别与用户意图相关的字段；二是推理时扩展（Inference-time Scaling），即通过多次调用LLM或工具来弥补单次生成的逻辑缺陷。传统方法将这两者串行处理，先压缩Schema，再逐步推理，导致延迟随推理深度累积。

文本到SQL领域的主流路线已从早期的序列到序列微调转向基于LLM的提示工程与代理工作流。DIN-SQL和DAIL-SQL等通过分解任务和检索增强提升了复杂查询性能，但均依赖串行思维链（Chain-of-Thought, CoT），其延迟与推理步数成正比。Spider 2.0基准的引入加剧了这一矛盾，其平均800列的数据库规模和长SQL要求迫使模型进行更深的探索，而串行探索的延迟瓶颈使得交互式应用变得不切实际。PEXA的切入点在于利用软件测试中“测试用例天然可并行”的特性，将串行推理转化为并行覆盖，从而在保持搜索广度的同时压低延迟上限。

## 核心方法

### 软件测试范式重构

PEXA将文本到SQL任务映射为软件测试中的测试覆盖问题。与传统的查询分解不同，后者仅关注原查询内部的子句逻辑，PEXA生成的测试用例旨在覆盖用户查询的语义表面，包括目标信息与非目标信息的探索。这种“过度生成”策略允许代理在最终生成前，通过执行简单的原子SQL获取表结构、值分布等上下文证据，从而降低最终长SQL生成的幻觉风险。

### 并行多路径搜索机制

PEXA的核心创新在于将规划、执行与合成三个阶段解耦并并行化。Planner在单次前向传播中生成一组独立的测试用例，Test Case Generator并行执行这些SQL，Proposer则基于执行结果合成最终查询。这种设计将延迟复杂度从所有路径之和 $T_{seq} = \sum_{i=1}^{k} \sum_{j=1}^{k_i} t_{ij}$ 降低为最慢路径的时间 $T_{par} = \max_{i,j} (t_{ij})$。

$$ T_{par} = \max_{i \in \{1..k\}, j \in \{1..k_i\}} (t_{plan}^{(i)} + t_{gen}^{(ij)}) $$

该公式表明，通过限制分支因子，PEXA能在性能与效率间实现细粒度权衡。实验显示，将分支因子从无限限制为1时，执行准确率仅下降4.5%，但延迟显著降低。这种单步多路径搜索（Single-step Multi-path Search）避免了串行迭代中的累积误差，使代理能在有限步数内快速剪除错误假设。

## 实验评估

PEXA在Spider 2.0-Snow（547个样本，150+数据库）和Lite*子集上进行了评估，使用GPT-o3作为骨干模型。基线包括Spider-Agent、ReFoRCE、Chat2DB和AgenticData，均为开源代理框架。PEXA在Snow子集上取得45.7%的执行准确率（EX），优于AgenticData的44.11%；在Lite*子集上取得46.6% EX，优于基线的44.51%。值得注意的是，PEXA在更新后的评估数据上达到了70.2%的SOTA，但消融实验基于旧数据，存在版本差异。

| 方法 | Snow EX | Snow EX@4 | Lite* EX | Lite* Wall Time (min) |
| :--- | :--- | :--- | :--- | :--- |
| Spider-Agent | 25.2 | 26.2 | - | - |
| ReFoRCE | 27.4 | 28.7 | - | - |
| AgenticData | 39.7 | 44.1 | - | - |
| PEXA | 45.7 | 49.5 | 46.6 | 5.55 |

消融实验揭示了并行化对性能的关键贡献。移除规划时并行化导致EX下降2.9%，移除测试时并行化下降3.0%，而移除语义验证器仅下降0.6%。这表明并行探索带来的语义广度增益远大于单一验证机制。此外，混合模型实验显示，GPT-o3在生成和提议阶段表现最佳，而Sonnet-4在规划阶段略优，但整体性能低于纯GPT-o3配置，暗示长上下文推理能力对最终SQL质量至关重要。

评估边界方面，论文未报告计算成本（Token消耗）的详细对比，仅指出错误运行比正确运行多消耗50%的Token。代码未公开，且基线数据部分引自旧排行榜，可能影响可比性。Spider 2.0的评估协议在2025年10月更新，导致部分数值与先前工作不可直接比较。

## 关联研究分析

从问题动机看，PEXA与CHESS等基于多智能体协作的方法均旨在解决复杂Schema下的链接噪声，但CHESS依赖迭代优化和串行验证，而PEXA通过并行测试用例实现一次性覆盖。这种差异源于对“鲁棒性”的不同定义：CHESS追求通过多次修正消除错误，PEXA则通过广泛探索确保信息完备。PEXA的“过度生成”策略在Schema已预压缩（如ReFoRCE模块）的场景下效果显著，但在Schema极度庞大且未压缩时，测试用例的生成成本可能成为瓶颈。

从方法设计看，PEXA与DIN-SQL等分解式提示工程方法共享任务分解思想，但DIN-SQL的分解是逻辑子句层面的串行依赖，而PEXA的分解是语义覆盖层面的并行独立。DIN-SQL依赖LLM的上下文学习能力处理子任务间依赖，PEXA则通过执行反馈解耦依赖，使子任务可独立验证。这种设计使得PEXA对LLM的长上下文推理能力要求降低，但对执行环境的稳定性要求更高。若数据库执行延迟高，并行优势将被抵消，论文未对此进行量化分析。

## 总结

PEXA针对复杂文本到SQL中性能与延迟的帕累托冲突，利用软件测试的并行覆盖范式，将串行推理转化为并行探索，在Spider 2.0上实现了70.2%的执行准确率与5.55分钟的平均延迟。其核心贡献在于证明了并行测试用例生成能有效提升语义覆盖广度，且性能对分支因子的敏感度较低。然而，论文未深入探讨测试用例“过度生成”在极端复杂查询下的计算成本边界，也未验证该范式在跨方言（如BigQuery与Snowflake混合）场景下的泛化能力。当数据库Schema规模进一步增大时，并行测试用例的生成与执行开销是否会抵消其延迟优势，仍是该框架实用化的关键未知数。
