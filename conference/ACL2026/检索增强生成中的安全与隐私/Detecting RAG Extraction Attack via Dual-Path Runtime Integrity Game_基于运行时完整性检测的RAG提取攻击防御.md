# ACL2026最新论文 ｜Detecting RAG Extraction Attack via Dual-Path Runtime Integrity Game ｜基于运行时完整性检测的RAG提取攻击防御

研究机构：中国科学院、中国科学院大学

作者：Yuanbo Xie、Yingjie Zhang、Yulin Li 等 8 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.10717)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.10717)

> 检索增强生成（RAG）系统面临的核心威胁是攻击者通过黑盒查询重构私有知识库，现有防御手段多依赖语义过滤或索引重构，难以在保持系统效用同时提供实时检测能力。本文切入点在于将泄露问题从“内容保密”重构为“运行时完整性违规”，借鉴软件安全中的栈金丝雀机制，通过注入非语义标记并监控双路径输出行为来识别攻击。该方法以极低的计算开销实现了接近零的知识库恢复率，但其检测机制缺乏形式化隐私保证，且对完全抑制标记输出的自适应攻击依赖额外的Oracle路径进行兜底，鲁棒性边界尚待更严苛的对抗场景验证。

## 研究背景

RAG系统通过检索外部知识库缓解大语言模型（LLM）的知识滞后，但其开放性使得私有数据成为主要攻击面。攻击者无需访问内部参数，仅通过API交互即可实施提取攻击（Extraction Attack），即诱导模型复述检索到的敏感文档以重构知识库。传统防御如重排序（Reranker）或摘要（Summarize）旨在降低泄露概率，但属于被动过滤，无法主动识别恶意意图，且往往需要修改检索或生成管线，难以即插即用。

该领域的主流防御路线分为两类：一是基于语义边界的隔离，如RAGFort通过对比重索引强化主题间边界；二是基于内容替换的混淆，如使用合成摘要替代原始文档。这些方法的共同瓶颈在于缺乏对“攻击行为”本身的实时感知能力，且在面对自适应攻击时，防御效果显著衰减。本文针对这一缺口，提出一种无需修改底层架构、不依赖语义匹配的检测型防御机制，将安全边界从“内容相似度”转移至“运行时行为一致性”。

## 核心方法

### 方法参照系

现有RAG防御通常遵循“检索-过滤-生成”流程，在检索后或生成前对文档进行语义清洗或替换。本文的关键差异在于不改变文档内容，而是在生成阶段引入行为监控，将防御从“数据预处理”移至“运行时检测”。

### 金丝雀注入与完整性定义

设计动机在于解决语义相似度无法区分合法引用与恶意泄露的问题。本文在检索到的文档块中注入非语义金丝雀令牌（Canary Tokens），定义为 $\tau = \{\kappa_1, \dots, \kappa_m\}$。注入函数 $\Phi$ 将原始块 $c$ 增强为 $c' = \Phi(c, \tau)$，使得金丝雀令牌在正常任务中不应出现。

$$
c' = \Phi(c, \tau) = c \oplus \kappa_i
$$

该公式表示将随机生成的非语义字符串拼接至文档块，作为完整性锚点。若模型输出中出现这些令牌，即表明检索内容被不当暴露，从而将模糊的泄露判定转化为明确的完整性违规信号。

### 双路径并发监控机制

设计动机在于应对自适应攻击者抑制金丝雀输出的行为。本文构建目标路径（Target Path）与Oracle路径（Oracle Path）并发执行。目标路径处理用户查询，预期不输出任何金丝雀；Oracle路径使用修改后的查询，预期必须输出金丝雀。

$$
\text{Violation} = \mathbb{1}[\text{Canary} \in Y_{target}] \lor \mathbb{1}[\text{Canary} \notin Y_{oracle}]
$$

该公式定义了违规条件：目标路径出现金丝雀，或Oracle路径未出现金丝雀，均判定为攻击。通过这种互斥的行为预期，系统能够同时检测直接泄露和针对检测机制的规避行为，实现了从被动过滤到主动行为监控的范式转变。

## 实验评估

实验在ChatDoctor、Mini-Wikipedia和Mini-BioASQ三个RAG智能体上进行，对比了无防御、Reranker、Summarize、RAGFort及CanaryRAG。基线覆盖了语义过滤和结构重构路线，但缺失差分隐私（如Private-RAG）和加密检索（如p2RAG）等强隐私保证方法，导致无法直接对比隐私-效用权衡下的性能差异。

| 防御方法 | 相对平均CRR | 相对平均FLOPs |
| :--- | :--- | :--- |
| No Defense | 1.00× | 1.00× |
| Reranker | 0.98× | 1.06× |
| Summarize | 0.67× | 4.80× |
| RAGFort | 0.60× | 3.25× |
| CanaryRAG | 0.04× | 1.90× |

CanaryRAG将相对平均块恢复率（CRR）降至0.04×，相比RAGFort的0.60×有数量级优势，且计算开销（FLOPs）仅为Summarize的40%。在良性查询下，BERTScore几乎无损（如ChatDoctor从0.517降至0.515），误报率（FPR）低于0.15%，表明该机制对正常服务影响极小。

消融实验显示，Oracle路径对自适应攻击的鲁棒性至关重要。在非自适应攻击下，无Oracle路径的检测真阳性率（TPR）为98.2%，但在自适应攻击（A1+A3）下骤降至51.8%；启用Oracle路径后，TPR恢复至94.1%。这表明仅依赖目标路径无法有效应对试图抑制金丝雀输出的攻击者，双路径设计是应对自适应威胁的关键。

评估边界方面，论文未报告置信区间，且数据集规模较小（每智能体500个块），缺乏大规模动态知识库下的长期稳定性验证。代码未公开，超参数如金丝雀长度和缓冲区大小未详细披露，限制了可复现性。此外，CRR指标基于ROUGE-L和余弦相似度，可能无法捕捉细粒度的语义泄露，且未与形式化隐私保证方法（如DP）进行横向对比，难以评估其在合规场景下的适用性。

## 关联研究分析

从问题动机看，本文与RAGFort均针对RAG提取攻击，但RAGFort侧重于通过对比重索引强化语义边界，属于预防型防御，而CanaryRAG侧重于运行时行为检测，属于检测型防御。RAGFort需要重构索引，部署成本高，且对自适应攻击的鲁棒性有限（CRR 0.60×）；CanaryRAG无需修改架构，通过行为监控实现更低泄露率（CRR 0.04×），但缺乏形式化保证。这一差异源于任务特性：预防型方法依赖数据分布假设，而检测型方法依赖行为异常，后者在动态攻击场景下更具适应性，但前者在静态合规场景下提供更强的理论保障。

从方法设计看，本文借鉴软件安全中的栈金丝雀，与差分隐私（DP）路线形成互补。DP通过添加噪声保护数据，提供形式化隐私预算，但导致精度损失且计算开销大；CanaryRAG通过注入标记检测泄露，计算开销低且精度无损，但无法提供隐私预算保证。两者在技术路线上存在根本分歧：DP追求“不可知”，CanaryRAG追求“可检测”。在医疗、金融等高敏感场景，DP可能更优；在通用企业助手场景，CanaryRAG的即插即用特性更具实用价值。

## 总结

本文解决的核心矛盾是RAG提取攻击防御中实时检测与系统效用的冲突。现有方法如RAGFort依赖语义重构，难以即插即用且对自适应攻击鲁棒性不足；本文通过引入非语义金丝雀令牌和双路径监控，将泄露检测转化为运行时完整性违规判定，实现了无需重训练、低开销的防御。实验表明，CanaryRAG将相对平均CRR降至0.04×，且对良性查询的BERTScore影响小于0.005，误报率低于0.15%。其边界在于缺乏形式化隐私保证，且对完全抑制金丝雀输出的攻击依赖Oracle路径，若攻击者能同时规避双路径预期，检测机制可能失效。当攻击者具备更强的自适应能力，能够同时抑制目标路径泄露并伪造Oracle路径输出时，该双路径监控机制的鲁棒性是否仍能维持，论文未给出回答。
