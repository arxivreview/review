# ACL2026最新论文 ｜LoPT: Lossless Parallel Tokenization Acceleration for Long Context Inference of Large Language Model ｜无损并行分词加速框架

作者：Wei Shao、Zheng Lingchao、Pengyu Wang 等 6 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_bd92996b71f9)

> 长上下文推理中，分词预处理常成为延迟瓶颈，而现有并行分词方法因边界处理缺陷导致输出与串行结果不一致。LoPT 通过引入字符位置对齐机制与动态块长调整，解决了并行分词的无损性问题。该框架在保持输出完全一致的前提下实现了显著加速，但其加速上限受限于多进程通信开销，且在动态分词器场景下的适用性尚未验证。

## 研究背景

长上下文大语言模型（LLM）推理面临的核心挑战之一是输入预处理延迟。分词器将原始文本映射为离散 Token ID 序列，这一过程在 CPU 端执行，且计算复杂度随文本长度线性增长。当上下文长度达到百万级 Token 时，分词时间占比显著上升，成为制约 GPU 利用率的关键因素。为解决此问题，并行分词策略被提出，其核心思想是将长文本切分为多个重叠片段，利用多进程并行处理后再合并结果。然而，现有方法在合并阶段存在根本性缺陷：基于分隔符切分的方法忽略了边界变化对子词合并的影响，而基于重叠 Token 序列匹配的方法则因重复文本导致的序列歧义产生错误。这些缺陷使得并行分词无法保证输出与标准串行分词完全一致，限制了其在生产环境中的应用。

分词加速研究此前主要聚焦于算法优化（如 BPE、WordPiece 的工程实现）或硬件加速（如 GPU 内核），但针对长上下文单样本推理的 CPU 侧并行加速研究较少。ParallelTokenizer 是首个尝试多进程并行分词的开源库，但其合并策略依赖最长重叠 Token 序列匹配，在包含连续重复文本的场景下失效。LoPT 的切入点在于识别出“字符位置一致性”是保证无损合并的必要条件，并通过动态调整切分策略确保该条件始终满足，从而在加速与正确性之间取得平衡。

## 核心方法

### 方法参照系

LoPT 遵循“切分-并行分词-合并”的通用并行处理范式，与 ParallelTokenizer 架构相同。关键差异在于合并阶段：ParallelTokenizer 依赖 Token ID 序列比对，而 LoPT 引入字符位置信息作为对齐基准，并增加动态块长重试机制以处理边界失效情况。

### 基于字符位置的重叠匹配

传统重叠匹配方法通过比对相邻片段分词结果的 Token ID 序列寻找重叠区，但在文本包含重复子串时，不同位置的相同 Token 序列会导致匹配歧义。LoPT 要求分词器输出每个 Token 在片段内的字符级位置，匹配时仅接受满足“全局字符位置一致”条件的 Token 序列。具体而言，对于相邻片段 $s_i$ 和 $s_{i+1}$，其重叠 Token 序列中每个 Token 在 $s_i$ 中的字符位置与在 $s_{i+1}$ 中的字符位置之差必须恒等于块长 $L_c$。该约束确保匹配到的 Token 在原始长文本中占据唯一确定的位置，消除了重复文本引发的歧义。

$$
\text{pos}_{global}(t) = \text{pos}_{s_i}(t) + L_c \cdot (i-1) = \text{pos}_{s_{i+1}}(t) + L_c \cdot i
$$

此公式表明，只有当 Token 在两个相邻片段中的局部位置差严格等于块长时，才被视为有效重叠 Token。该设计将匹配复杂度从序列比对降低为位置校验，同时保证了无损性。

### 动态块长调整机制

固定块长可能导致重叠区过短，使得有效重叠 Token 数量不足，进而引发匹配失败。LoPT 引入动态调整机制：若某对相邻片段的有效重叠 Token 数 $n_{o_i}$ 小于预设阈值 $T$，则判定当前块长不适配，将块长加倍并重新执行整个切分-分词-合并流程。该机制通过牺牲少量重试开销换取无损保证，避免了因边界失效导致的输出错误。

$$
\text{if } n_{o_i} < T \text{ for any } i, \text{ then } L_c \leftarrow 2L_c \text{ and restart}
$$

此公式描述了动态调整触发条件。阈值 $T$ 设为 2，确保重叠区至少包含两个有效 Token，以覆盖大多数边界情况。该机制解决了固定块长在特定文本分布下失效的问题，但最坏情况下重试次数可能增加延迟。

## 实验评估

实验在 LongBenchV2、LEval 和 ClongEval 三个长文本数据集上进行，覆盖英文与中文场景。基线包括 HuggingFace TokenizerFast（串行基准）、三种分隔符并行方法（空格、逗号、句号）及 ParallelTokenizer（原始版与优化版）。LoPT 在所有数据集和分词器组合下均实现 Accuracy 1.0，即输出与串行分词完全一致。在 LongBenchV2 上，LoPT 延迟为 106.7ms，而 HuggingFace TokenizerFast 为 509.2ms，加速比约 4.8 倍。分隔符方法延迟更低（约 86-93ms），但 Accuracy 显著低于 1.0，尤其在 BERT-Base-Uncased 分词器下最低仅 0.247。ParallelTokenizer 优化版延迟为 479.5ms，加速效果微弱且 Accuracy 为 0.982，未达无损标准。

消融实验表明，LoPT 的加速性能受并行进程数影响。在 32 进程下，实际加速比为 7.27，远低于 Amdahl 定律理论值 29.85，主要受限于进程间通信与同步开销。序列长度对加速效果有正向影响：在 128k Token 长度下，LoPT 相对 HuggingFace TokenizerFast 的加速比高于 4k Token 长度下的比值，表明长文本场景下并行收益更显著。

评估边界方面，实验仅覆盖 CPU 环境，未对比 GPU 加速方案（如 GPUTOK）。Accuracy 指标定义为“与串行结果完全匹配的样本比例”，但未报告置信区间或样本量分布。代码未开源，超参数（如阈值 $T$、初始块长）未在正文中明确列出，可复现性受限。

## 关联研究分析

从问题动机看，LoPT 与 GPUTOK 均针对长上下文分词延迟，但技术路线截然不同。GPUTOK 通过 CUDA 内核并行化 BPE 合并操作，利用 GPU 高带宽内存优势加速单样本分词；LoPT 则依赖 CPU 多进程并行，通过任务级并行降低延迟。二者差异源于硬件假设：GPUTOK 假设分词计算密集且适合 GPU 并行，而 LoPT 假设分词 I/O 密集且 CPU 多核更经济。LoPT 未探索 GPU 加速路径，可能因其目标场景为小 Batch 单样本推理，GPU 启动开销占比过高。

从方法设计看，LoPT 与 ParallelTokenizer 同属多进程并行框架，但合并策略存在本质差异。ParallelTokenizer 依赖 Token ID 序列比对，其正确性依赖于文本无重复子串；LoPT 引入字符位置约束，将正确性保证从文本内容特性转移至位置一致性，从而在重复文本场景下仍保持无损。这一改进源于对边界失效根因的深入分析：Token ID 歧义源于位置信息缺失，而非序列比对算法本身。LoPT 未讨论该机制对动态分词器（如 RL Tokenization）的适用性，因动态分词器的 Token 边界随上下文变化，字符位置一致性假设可能失效。

## 总结

LoPT 解决了长上下文推理中并行分词的无损性问题，其核心在于通过字符位置对齐消除边界歧义，并辅以动态块长调整确保重叠区有效性。实验证明其在 CPU 单样本场景下实现 4.8 倍加速且输出完全一致，优于现有并行方法。然而，其加速上限受限于多进程通信开销，实际加速比远低于理论值，且未验证在动态分词器或 GPU 加速场景下的适用性。当分词器引入上下文依赖的动态边界时，字符位置一致性假设是否仍成立，论文未给出回答。
