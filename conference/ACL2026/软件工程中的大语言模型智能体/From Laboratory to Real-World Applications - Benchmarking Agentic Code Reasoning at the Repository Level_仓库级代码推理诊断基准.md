# ACL2026最新论文 ｜From Laboratory to Real-World Applications: Benchmarking Agentic Code Reasoning at the Repository Level ｜仓库级代码推理诊断基准

研究机构：香港中文大学、中山大学

作者：Jia Li、Yuxin Su、Michael R. Lyu

论文原文见 [arXiv](https://arxiv.org/abs/2601.03731)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2601.03731)

> 现有软件工程智能体评估多聚焦于“能否修复Issue”的黑盒结果，缺乏对模型在复杂依赖中“为何失败”的白盒诊断能力。RepoReason 通过执行驱动变异与动态程序切片，构建了首个量化认知瓶颈的仓库级推理基准。其核心价值在于将模糊的长程推理拆解为可读性、模拟深度与集成宽度三个正交维度，但仅测试读取推理能力，未验证与端到端修复性能的关联。

## 研究背景

当智能体面对包含数万行代码的仓库时，其核心挑战不再是生成单行代码，而是维持跨文件逻辑一致性，即仓库级推理（Repository-Level Reasoning）。这种能力要求模型在探索庞大上下文时，精准定位目标定义、聚合多源依赖信息，并追踪长链状态突变。然而，当前评估体系存在两极分化：函数级基准如 CRUXEval 虽具分析严谨性，却缺乏真实仓库的跨文件依赖；SWE-bench 虽基于真实 GitHub Issue，但仅报告解决率，无法揭示失败的具体认知根源。

主流路线在“生成正确代码”与“诊断推理缺陷”之间陷入僵局。SWE-bench 确立了执行接地验证的黄金标准，但其黑盒特性导致无法区分是逻辑错误还是语法噪声导致的失败。与此同时，数据污染问题使得直接复用开源仓库测试用例面临预训练记忆泄露风险。RepoReason 的切入点在于构建一个白盒诊断工具，通过验证断言而非生成补丁，隔离核心逻辑推理与表面语法错误，从而量化智能体在上下文过载、状态追踪与信息聚合上的具体瓶颈。

## 核心方法

### 方法参照系

RepoReason 属于代码推理基准构建范畴，但偏离了传统的“输入-输出预测”范式。标准流程通常要求模型生成代码或预测运行时变量值，而本文将其重构为“断言验证”任务：给定仓库执行历史，推导满足特定断言的系统状态。这一差异旨在消除原始轨迹查询中的捷径学习（Spurious Correlation），即模型通过局部静态分析而非真实执行模拟获取答案。

### 执行驱动变异与语义锚点

为对抗预训练数据记忆，RepoReason 引入执行驱动变异（Execution-Driven Mutation）机制。该设计动机在于切断模型对原始 GitHub 代码的记忆检索路径，同时保留逻辑复杂度。具体而言，系统利用教师大语言模型对代码进行视觉与逻辑双重变异（如重命名变量、修改常量），随后将代码执行环境作为语义预言机（Semantic Oracle）。通过探针注入（Probe Injection）将断言转换为打印语句，执行变异后的代码以捕获真实运行时状态作为新的地面真值（Ground Truth）。这一过程确保了任务逻辑的真实性，同时使具体状态值不可被记忆。

$$
\text{Score} = 0.5 \times \frac{N_{calls}}{N_{calls}^{base}} + 0.2 \times \frac{D}{D^{base}} + 0.2 \times \frac{N_{funcs}}{N_{funcs}^{base}} + 0.1 \times \frac{N_{files}}{N_{files}^{base}}
$$

该公式用于结构过滤，通过加权计算调用次数、堆栈深度、函数数与文件数，筛选出复杂度评分 $\ge 3.0$ 的高密度测试用例，确保任务具备足够的逻辑深度。

### 动态程序切片与认知指标

基于变异后的执行轨迹，RepoReason 执行动态程序切片（Dynamic Program Slicing），从断言沿数据与控制依赖反向追踪，提取最小因果计算子图。在此基础上，定义三个正交认知指标以量化推理强度：有效切片体积（ESV）衡量因果相关源码量，反映上下文过载导致的理解失败；变异链长度（MCL）衡量动态状态更新步数，反映状态追踪缺陷；依赖扇入（DFI）衡量独立上游逻辑输入数量，反映信息聚合缺陷。

$$
\text{DFI} = |\{ x \in \text{Inputs} \mid x \notin \text{Slice}(A) \land x \text{ influences } A \}|
$$

DFI 公式量化了执行子图外部生成但被其消费的逻辑输入数量，显式过滤语言关键字等结构噪声。这一指标直接映射到智能体的信息聚合能力，揭示了模型在合成多源逻辑源时的瓶颈。

## 实验评估

实验采用 OpenHands 0.60.0 的 ReadOnlyAgent 作为评估平台，限制智能体仅能读取代码，隔离编辑与规划能力。对比模型包括 Claude-Sonnet-4.5、GPT-5.2、DeepSeek-v3.1-Terminus、Kimi-K2 及 Qwen3-Coder-480B。所有模型在 Hard 难度任务上均出现显著性能下降，其中 Claude-Sonnet-4.5 在 Easy 任务中准确率为 80.27%，而在 Hard 任务中降至 47.39%，显示出明显的性能悬崖。

| 模型 | Overall (%) | Easy (%) | Medium (%) | Hard (%) |
|---|---|---|---|---|
| Claude-Sonnet-4.5 | 66.98 | 80.27 | 66.79 | 47.39 |
| DeepSeek-v3.1-Terminus | 60.96 | 74.03 | 60.02 | 41.71 |
| GPT-5.2 | 56.86 | 75.92 | 53.94 | 30.85 |
| Kimi-K2 | 54.74 | 69.38 | 51.79 | 35.66 |
| Qwen3-Coder-480B | 50.56 | 61.35 | 49.16 | 35.50 |

相关性分析表明，DFI 与准确率的负相关系数最强，GPT-5.2 的 DFI 相关系数达 -0.234，证实集成宽度是主要认知瓶颈。ESV 与 MCL 的相关性较弱，表明上下文长度与模拟深度并非首要限制因素。

| 模型 | ESV | MCL | DFI |
|---|---|---|---|
| GPT-5.2 | -0.188 | -0.158 | -0.234 |
| Claude-Sonnet-4.5 | -0.161 | -0.122 | -0.225 |
| DeepSeek-v3.1-Terminus | -0.152 | -0.122 | -0.157 |
| Kimi-K2 | -0.130 | -0.117 | -0.195 |
| Qwen3-Coder-480B | -0.148 | -0.154 | -0.196 |

评估边界方面，RepoReason 仅覆盖 Python 纯代码仓库，排除 C/C++ 扩展库，限制了跨语言泛化验证。代码未开源，且未报告置信区间，数值比较需谨慎。此外，ReadOnlyAgent 的设置剥离了编辑能力，可能低估智能体在真实 SWE 任务中通过试错修正推理的能力。

## 关联研究分析

从问题动机看，RepoReason 与 SWE-bench 形成互补而非替代关系。SWE-bench 关注端到端解决率，而 RepoReason 聚焦于失败归因。然而，SWE-bench 的执行接地验证已隐含了部分推理能力测试，RepoReason 的断言验证是否提供了 SWE-bench 无法捕捉的额外诊断信息，论文未通过相关性分析证明两者间的映射关系。

从方法设计看，RepoReason 的动态程序切片依赖完整执行轨迹，这在依赖复杂或无法运行的仓库中覆盖率受限。相比之下，CRUXEval 等静态分析基准虽缺乏仓库级深度，但无需执行环境，部署成本更低。RepoReason 的执行驱动变异虽解决了数据污染，但引入了对教师 LLM 的依赖，变异质量可能影响基准的稳定性。

## 总结

RepoReason 旨在解决仓库级推理评估中“黑盒结果”与“白盒诊断”的矛盾，通过执行驱动变异与动态程序切片，构建了首个量化认知瓶颈的基准。其核心贡献在于揭示 DFI（集成宽度）是前沿模型的主要瓶颈，GPT-5.2 在 Hard 任务中准确率仅 30.85%，且 DFI 相关系数达 -0.234。然而，该基准仅测试读取推理能力，未验证与端到端修复性能的关联，且依赖 Python 纯代码环境。当智能体在真实 SWE 任务中通过编辑代码修正推理错误时，RepoReason 所揭示的聚合缺陷是否仍具决定性影响，论文未给出回答。
