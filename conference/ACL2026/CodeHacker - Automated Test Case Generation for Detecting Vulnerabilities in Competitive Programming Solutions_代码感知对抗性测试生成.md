# ACL2026最新论文 ｜CodeHacker: Automated Test Case Generation for Detecting Vulnerabilities in Competitive Programming Solutions ｜代码感知对抗性测试生成

研究机构：西北工业大学、美团

作者：Jingwei Shi、Xinxiang Yin、Jing Huang 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2602.20213)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2602.20213)

> 竞赛编程评估长期受困于测试用例覆盖不足导致的“假阳性”，即错误代码因未触及边界而通过测试。现有自动化生成方法多依赖概率性输入变异或基于问题描述的提示生成，本质上是黑盒模糊测试，缺乏对具体代码逻辑漏洞的针对性。本文提出 CodeHacker，将竞赛编程中的“Hack”机制形式化为对抗性测试生成任务，通过代码感知策略主动搜索能触发特定提交失败的输入。该方法显著提升了基准测试的真阴性率，验证了自动化对抗生成在纠正评估偏差上的有效性，但其结论局限于 C++ 竞赛场景，向仓库级工程的迁移性尚存疑。

## 研究背景

竞赛编程评估的核心困境在于测试集与代码实现的耦合性。传统评估依赖静态测试用例，其有效性取决于测试输入是否恰好覆盖了代码的逻辑缺陷。当测试集稀疏时，许多包含潜在 Bug 的提交会因未触发错误路径而被误判为正确，这种现象称为假阳性。为降低假阳性，研究者引入了自动化测试生成，试图通过扩大输入空间覆盖来暴露错误。然而，单纯增加测试数量或进行随机变异，本质上是在输入空间中进行概率性探索，其成功与否取决于“碰巧”命中漏洞，而非对程序语义的深层理解。

主流自动化测试生成路线存在明显的瓶颈。基于变异的方法（如 EvalPlus）通过重组现有输入提高覆盖率，但可能违反复杂约束导致无效测试；基于 LLM 的方法（如 TACO）根据问题描述生成测试，但受限于上下文长度且无法保证满足 intricate 约束，难以处理大规模结构化实例。这些方法共同的问题是“代码盲视”，即生成过程不依赖目标代码的具体实现，导致生成的测试缺乏针对性。CodeHacker 的切入点在于引入“代码感知”视角，将目标代码作为一等公民，通过执行反馈和逻辑分析，主动搜索能触发特定失败模式的对抗样本，从而将评估从“统计覆盖”转向“逻辑验证”。

## 核心方法

### 方法参照系

本文问题属于自动化测试生成范畴，但区别于传统的基于问题描述的生成范式。传统流程是“问题描述 → 测试输入”，而 CodeHacker 采用“代码实现 + 问题描述 → 对抗输入”的双向耦合流程。关键差异在于，CodeHacker 不生成期望输出，而是通过执行标准解（Standard Solution）获取真值，仅由 LLM 生成输入，从而避免了 LLM 在复杂约束下生成错误期望输出导致的幻觉问题。

### 评估工具校准与自我攻击

在生成对抗样本前，CodeHacker 首先执行 Phase I 校准，确保评估基础设施（Validator 和 Checker）的可靠性。设计动机在于，若评估工具本身存在漏洞（如 Validator 过松或 Checker 过严），后续的对抗生成将基于错误的反馈信号，导致无效攻击。CodeHacker 引入“自我攻击”机制，LLM Agent 主动生成两类探针：一是“绕过攻击”，生成显式无效输入以测试 Validator 是否过松；二是“拒绝攻击”，生成有效但边缘的输入以测试 Validator 是否过严。对于 Checker，Agent 构造结构正确但数值错误的输出（Deception Attack）和有效但非标准的输出（Rejection Attack）来探测判定逻辑的偏差。

校准过程通过迭代反馈实现，其核心判定逻辑可形式化为：

$$
\text{Flaw} = \begin{cases}
\text{False Positive} & \text{if } J_{tool}(x_{invalid}) = \text{Accepted} \\
\text{False Negative} & \text{if } J_{tool}(x_{valid}) = \text{Rejected}
\end{cases}
$$

其中 $J_{tool}$ 为待校准的评估工具，$x_{invalid}$ 和 $x_{valid}$ 分别为 Agent 生成的无效和有效探针。该公式明确了工具漏洞的判定标准：若无效输入被接受或有效输入被拒绝，则工具存在缺陷，需触发更新。通过这种对抗性校准，CodeHacker 确保了后续生成的对抗样本是在一个“无偏”的评估环境中被验证的，从而消除了因评估工具错误导致的假阳性或假阴性。

### 代码感知对抗生成

Phase II 是核心创新环节，CodeHacker 通过 Code Analyst 模块实现代码感知。设计动机在于，静态文本分析易产生关于复杂度或边界条件的幻觉，而动态执行能提供确凿的行为证据。Code Analyst 配备“双执行接口”：一是 C++ 沙箱，用于行为探测，Agent 生成小规模探针输入执行目标代码，观察崩溃或错误输出以确认 Bug 存在；二是 Python 解释器，用于精确计算，验证复杂度边界（如调和级数操作数）和整数溢出风险。

基于 Analyst 的漏洞假设，Generator 模块采用三种策略生成对抗样本：Stress Test 针对渐近行为（如栈溢出、TLE）；LLM 生成针对语义逻辑错误（如 WA）；Anti-Hash 针对哈希碰撞。其中，Anti-Hash 策略将碰撞搜索形式化为最短向量问题（SVP），利用格基约简算法（LLL）确定性构造碰撞，解决了随机模糊测试难以命中特定哈希漏洞的问题。

对抗生成的成功判定依赖于严格的三条件约束：

$$
\text{Hack Success} = \mathbb{I}[x \in X_{valid}] \cdot \mathbb{I}[J_p(S_{std}, \{x\}) = AC] \cdot \mathbb{I}[J_p(s, \{x\}) \neq AC]
$$

该公式定义了有效 Hack 的充要条件：输入必须有效（通过 Validator），标准解必须通过（Oracle Confirmation），且目标提交必须失败（Target Failure）。这一形式化定义确保了生成的测试用例不仅是“能报错”，更是“能证明错误”，从而将评估信号从模糊的执行异常提升为精确的逻辑证伪。

## 实验评估

实验基于 CodeContest+ 数据集的 2000 道题目（1000 道传统判题，1000 道特殊判题），对比基线包括 CodeContests、HardTests、TACO 和 CodeContest+。基线覆盖了手动、变异和 LLM 生成三种主流路线，但缺乏与最新 SOTA LLM 直接生成测试方法的对比。

| 数据集 | VPR (%) | TPR (Traditional) (%) | TNR (Traditional) (%) | TPR (Special) (%) | TNR (Special) (%) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| CodeContests | 71.41 | 98.96 | 84.73 | 96.46 | 82.67 |
| HardTests | 97.32 | 76.33 | 77.69 | 83.70 | 85.48 |
| TACO | 81.84 | 98.33 | 86.56 | 96.02 | 84.04 |
| CodeContest+ | 99.66 | 79.25 | 75.37 | 85.72 | 84.04 |
| CodeContest++ (Ours) | 100.00 | 95.86 | 96.31 | 96.38 | 96.05 |

CodeHacker 生成的 CodeContest++ 在特殊判题上的 TNR 达到 96.05%，显著高于 CodeContest+ 的 84.04% 和 TACO 的 84.04%。TNR 的提升表明该框架能有效识别并拒绝原本被误判为正确的错误代码，而 TPR 的轻微下降（96.62% 至 96.38%）符合“更严格评估”的预期，即减少了假阳性。

| 变体 | Hack Success Rate (%) |
| :--- | :--- |
| CodeHacker (Full) | 51.40 |
| w/o Code Analyst | 49.86 |
| w/o Stress Test | 50.12 |
| w/o Anti-Hash Generator | 51.00 |
| w/o Refinement Loop | 46.60 |

消融实验显示，Refinement Loop 是最关键组件，移除后 HSR 从 51.40% 降至 46.60%，表明单次生成难以满足严格约束，迭代反馈对修正无效输入至关重要。Code Analyst 的贡献次之（49.86%），验证了代码感知对定位逻辑漏洞的价值。Anti-Hash Generator 虽触发率低（约 0.4%），但在触发时成功率为 100%，证明针对特定算法捷径（如滚动哈希）的领域专用模块对实现全覆盖不可或缺。

评估边界方面，实验仅聚焦 C++ 语言，未验证 Python 等动态语言或仓库级任务的迁移性。可复现性上，论文提供了详细的超参数（如温度 0.7）和工具链配置（MinGW），但未公开完整代码库，且人工干预（<5% 案例）虽声称无偏，但其具体分布未披露，可能影响极端难度题目的评估公平性。

## 关联研究分析

从问题动机看，CodeHacker 与 HardTests 和 TACO 存在根本差异。HardTests 侧重规则驱动的变异，旨在提高覆盖率，但其生成的测试可能违反复杂约束，导致假阴性；TACO 基于 LLM 生成，但受限于上下文长度，难以处理大规模结构化实例。CodeHacker 的差异在于引入“代码感知”和“执行反馈”，将测试生成从“基于问题的概率探索”转变为“基于代码的逻辑证伪”。这一差异的根源在于任务特性：竞赛编程题目往往具有复杂的边界条件和算法假设，仅靠问题描述无法充分约束测试空间，必须结合代码实现的具体行为才能定位漏洞。

从方法设计看，CodeHacker 与 LiveCodeBench 等动态基准形成互补。LiveCodeBench 通过时间维度更新题目来规避污染，但题目本身仍是静态的；CodeHacker 则在静态题目上增加动态的对抗测试层，针对特定代码实现生成测试。这种“静态题目 + 动态测试”的组合，解决了 LiveCodeBench 无法区分“模型记忆”与“模型推理”的问题。然而，CodeHacker 的对抗生成依赖于标准解（Standard Solution）的正确性，若标准解本身存在 Bug，则 Oracle Confirmation 条件失效，导致整个评估链条崩溃。这一局限性在 LiveCodeBench 等依赖人工验证的基准中同样存在，但 CodeHacker 的自动化程度更高，使得标准解错误的风险被放大。

## 总结

CodeHacker 解决了竞赛编程评估中测试用例覆盖不足导致的假阳性问题，其核心矛盾在于传统自动化生成方法缺乏对具体代码逻辑漏洞的针对性。本文通过引入代码感知对抗生成，将评估从统计覆盖转向逻辑证伪，利用 Self-Hacking 机制校准评估工具，并通过 Anti-Hash 等专用模块覆盖特定算法漏洞。实验证明，该方法将特殊判题的 TNR 从 84.04% 提升至 96.05%，显著增强了评估的区分度。然而，其结论局限于 C++ 竞赛场景，且依赖标准解的正确性。当目标代码库规模扩大至仓库级，且缺乏单一标准解时，CodeHacker 的 Oracle Confirmation 机制是否仍能保持有效性，论文未给出回答。
