# ACL2026最新论文 ｜From Completion to Editing: Unlocking Context-Aware Code Infilling via Search-and-Replace Instruction Tuning ｜搜索替换填充

作者：Jiajun Zhang、Zeyu Cui、Jiaxi Yang 等 12 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_3eebdc943577)

> 代码补全领域长期依赖 Fill-in-the-Middle (FIM) 范式，但该范式强制使用未对齐的 Base 模型，导致系统在面对代码注入攻击时缺乏防御能力，且无法修正上下文中的既有错误。现有方案要么牺牲安全性以维持补全性能，要么引入多步代理工作流导致延迟过高，无法满足实时交互需求。本文提出 Search-and-Replace Infilling (SRI)，通过结构化指令微调将代理验证机制内化为单次推理过程，使 Chat 模型在保持低延迟的同时继承安全对齐能力。SRI 在安全基准上将攻击成功率从接近 100% 降至 5.5%-20.0%，但其在通用编码任务上的性能保持机制仍需更严格的跨域验证。

## 研究背景

代码补全任务要求模型基于前缀和后缀上下文生成缺失代码段，这一能力由 FIM 预训练策略支撑。FIM 通过数据变换技术克服 Decoder-only 架构无法进行中间填充的局限，成为 CodeX、StarCoder 等代码模型的标准范式。然而，FIM 推理依赖特殊 Token，无法直接应用于经过指令微调的 Chat 模型；若采用自然语言提示模拟 FIM，会导致补全性能显著退化，最高降幅达 59.0%。

代码补全工具面临的核心矛盾是安全性与实时性的权衡。传统 FIM 范式依赖未对齐的 Base 模型，SAL 基准显示其攻击成功率超过 99%，暴露出严重的安全漏洞。直接调用 Chat 模型虽具备安全对齐能力，但 FIM 技能无法有效迁移至对话设置，导致性能大幅下降。多步代理工作流虽能提升灵活性，但其延迟开销与实时补全场景不兼容。现有方法在表示质量、适应效率与计算成本之间未能找到平衡点，导致安全对齐与补全性能难以兼得。

本文切入点在于重构补全任务的底层范式。通过引入 Search-and-Replace (S&R) 格式，将静态填充转化为动态上下文感知编辑，使 Chat 模型能够利用其指令跟随先验完成补全任务。这一转变不仅解决了 FIM 对 Base 模型的依赖，还通过显式搜索阶段实现了对上下文错误的修正能力，为下一代交互式开发工具提供了安全且高效的对齐路径。

## 核心方法

### 方法参照系

代码补全的标准流程基于 FIM 范式，模型接收前缀和后缀上下文，直接生成中间缺失代码。该流程假设上下文无错误且模型具备安全对齐能力。本文问题与该通用流程的关键差异在于：FIM 无法处理含噪上下文，且强制使用未对齐 Base 模型，导致安全缺陷与功能局限并存。

### 结构化搜索替换机制

SRI 将补全任务重构为上下文感知微编辑，核心创新在于引入显式搜索阶段作为 Grounding 机制。模型首先生成 SEARCH 块，精确复现待修改代码段，随后生成 REPLACE 块提供修正后代码。这一过程类似视觉 Chain-of-Thought，强制模型在提交更改前验证上下文。

$$
\text{Output} = \text{SEARCH}(\text{Context}_{target}) \oplus \text{REPLACE}(\text{Context}_{corrected})
$$

该公式表示输出由目标上下文的精确复现与修正后上下文的替换组成，$\oplus$ 表示结构化拼接。设计动机在于解决标准 Diff 补丁依赖行号导致的失效问题，S&R 格式基于语义内容锚定编辑，即使模型内部计数不精确也能可靠执行。这一机制使 Chat 模型能够动态修正语法错误或遗留模式，突破了 FIM 冻结上下文的刚性假设。

### 安全对齐桥接策略

SRI 通过格式重构实现安全对齐能力的继承，无需额外安全数据。模型在 SRI 框架下利用 Chat 骨干的指令跟随先验，将安全约束内化于生成过程。与直接提示 Chat 模型执行 FIM 不同，SRI 的结构化输出格式与预训练语料中的 Diff 格式高度对齐，最小化分布偏移。

$$
\text{Safety}_{SRI} = \text{Safety}_{Chat} \times \text{Alignment}_{Format}
$$

该公式表示 SRI 的安全性能由 Chat 模型固有安全能力与格式对齐程度共同决定。设计动机在于解决 NL-FIM 策略导致的性能退化问题，SRI 通过匹配预训练数据分布，使 Chat 模型在补全任务中保持通用编码能力。实验表明，SRI 微调后的模型在通用编码基准上无性能回归，而 NL-FIM 策略导致显著退化，验证了格式对齐的关键作用。

## 实验评估

实验在五个主流补全基准（CrossCodeEval、RepoEval、CrossCodeLongEval、SAFIM、ExecRepoBench）和 SAL 安全基准上进行，对比 20+ 领先模型。基线覆盖 Base 模型（FIM）、Chat 模型（NL-FIM）及 SRI 微调模型，但缺失专门安全代码生成模型（如 SafeCoder）的直接对比。

| 模型 | SAL Level 1 (%) | SAL Level 2 (%) | CrossCodeEval-Flex EM | CrossCodeEval-Flex ES |
|---|---|---|---|---|
| Qwen-Base (FIM) | 100.0 | 97.5 | 0.0 | 35.6 |
| Qwen-Instruct (SRI) | 13.8 | 20.0 | 14.0 | 53.8 |
| SRI-Coder | — | — | 33.0 | 71.5 |
| DeepSeek-Base (FIM) | 98.2 | 95.4 | 0.0 | 38.2 |
| DeepSeek-Instruct (SRI) | 5.5 | 7.1 | 24.5 | 67.4 |

SAL 基准显示 SRI 将攻击成功率从接近 100% 降至 5.5%-20.0%，显著优于 FIM 基线。CrossCodeEval-Flex 上，FIM 模型在含噪环境中 EM 得分为 0.0，而 SRI-Coder 达到 33.0，验证了上下文修正能力。

消融实验比较 SRI 与三种 NL-FIM 微调策略（标准填充、对话重建、模板填充），使用相同 20k 数据集。SRI-Coder 在代码补全基准上平均得分 56.1，显著优于 NL-FIM 变体；在通用编码基准（MBPP、HumanEval 等）上，SRI 保持模型原有能力，而 NL-FIM 导致可测量的性能回归。这一发现表明 SRI 的优势源于其与预训练 Diff 格式的对齐，而非单纯数据量增加。

评估边界方面，SAL 基准仅覆盖 Level 1 和 Level 2 攻击，未测试更复杂的自适应攻击；CrossCodeEval-Flex 的噪声注入限于 5 行窗口，未验证长上下文仓库级编辑的鲁棒性。可复现性上，论文提供 16 块 A100 GPU 训练细节（32k 上下文、256 批大小、853 步），但 SRI-200K 数据集仅使用 20k 子集，完整数据分布未公开。

## 关联研究分析

从问题动机看，SRI 与 SafeCoder 等安全微调方法解决同一安全对齐问题，但路径截然不同。SafeCoder 通过指令调优注入安全知识，依赖高质量数据策展，而 SRI 通过格式重构继承 Chat 模型固有安全能力，无需额外安全数据。这一差异源于任务特性：代码补全要求低延迟实时响应，SafeCoder 的额外推理开销可能不兼容，而 SRI 的单次推理机制天然适配。然而，SRI 的安全性能是否完全源于 Chat 模型通用对齐，还是 SRI 格式本身提供了额外防御，论文未通过控制变量实验分离这两者贡献。

从方法设计看，SRI 与 CodeEditor 共享编辑范式，但去除了多步交互，将代理验证内化为单次推理。CodeEditor 通过多轮对话实现复杂编辑，但延迟高；SRI 通过 SEARCH-REPLACE 结构化输出在单次前向传播中完成验证与编辑，平衡了灵活性与效率。这一设计选择解决了多步代理在实时补全场景中的延迟瓶颈，但可能牺牲了复杂多文件编辑的能力。SRI 在仓库级基准（RepoEval）上的性能提升幅度（↑49.3）小于文件级基准（CrossCodeEval，↑46.3），暗示长上下文编辑中搜索阶段的 Grounding 效果可能受限，这一局限在论文中未深入探讨。

## 总结

本文核心矛盾是代码补全中安全性与实时性的不可兼得，FIM 范式强制使用未对齐 Base 模型导致安全漏洞，而 Chat 模型直接应用 FIM 又面临性能退化。SRI 抓住格式重构这一切入点，通过 SEARCH-REPLACE 结构化输出将代理验证机制内化为单次推理，使 Chat 模型在保持低延迟的同时继承安全对齐能力。实验证明 SRI 将 SAL 攻击成功率从 100.0% 降至 5.5%-20.0%，并在含噪环境中实现 33.0 EM 的修正能力。边界在于 SRI 的安全性能可能部分源于 Chat 模型通用对齐而非格式本身，且长上下文仓库级编辑的鲁棒性未充分验证。当支持集从 20k 扩展至完整 200k 时，SRI 在复杂多文件编辑任务上的性能增益是否持续，论文未给出回答。
