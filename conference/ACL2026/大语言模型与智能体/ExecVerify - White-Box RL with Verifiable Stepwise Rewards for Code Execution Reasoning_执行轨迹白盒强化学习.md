# ACL2026最新论文 ｜ExecVerify: White-Box RL with Verifiable Stepwise Rewards for Code Execution Reasoning ｜执行轨迹白盒强化学习

研究机构：浙江大学、英国伦敦大学学院

作者：Lingxiao Tang、He Ye、Zhaoyang Chu 等 7 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_ba49c258edf5)

> 代码大语言模型（LLM）在生成代码时往往缺乏对程序具体执行过程的语义理解，导致下游代码生成与修复性能受限。现有方法多依赖监督微调（SFT）模仿教师模型生成的文本解释，但SFT无法显式验证中间执行步骤的正确性，且训练数据缺乏难度控制。本文提出ExecVerify，通过约束式数据合成构建可控难度数据集，并引入基于解释器执行轨迹的白盒强化学习（RL），将训练目标从文本模仿转向逐步语义正确性验证。该方法显著提升了小模型在执行推理任务上的表现，但其奖励机制仅覆盖局部状态，对全局逻辑一致性的保证仍存疑。

## 研究背景

当LLM面对复杂程序时，其预训练数据多为静态文本，缺乏动态执行反馈，导致模型难以准确预测变量状态与控制流走向。这种执行语义理解的缺失直接削弱了模型在代码生成中的逻辑推理能力。为弥补这一缺陷，研究者尝试将执行信号融入训练，主要形成两条路线：一是I/O中心方法，如SemCoder和CodeI/O，利用执行结果验证教师生成的输入-输出推理链；二是轨迹中心方法，如TracePile，将执行轨迹转化为自然语言解释。然而，这两类方法均依赖SFT，在token级交叉熵目标下，中间执行步骤未被显式验证，模型可能过拟合教师文本而非真正理解执行过程。此外，被动收集的训练数据缺乏难度结构，包含大量平凡或不可解样本，阻碍了小模型的有效学习。ExecVerify的切入点在于，利用解释器提供的确定性执行轨迹构建可验证的白盒问题，通过RL奖励机制直接优化中间步骤的语义正确性，并配合约束式合成解决数据难度分布问题。

## 核心方法

### 约束式数据合成

ExecVerify的数据构建旨在解决被动采集数据缺乏结构多样性与难度控制的问题。该方法通过迭代Python内置类型与方法，在提示中施加两类结构约束：方法调用约束要求嵌套调用与多方法组合，控制结构约束强制特定嵌套控制流模式。这种从简单到复杂的渐进式约束生成，确保了程序覆盖广泛的数据类型与执行路径。随后，通过类型感知变异生成多样输入，并执行过滤以剔除运行失败或输出异常的实例。最后，利用Qwen2.5-Coder-7B-Instruct在I/O预测任务上进行难度筛选，仅保留通过率≤3/10的实例，形成具有课程学习特性的数据集。这一设计动机在于，通过显式控制结构复杂度与求解难度，使训练数据既具挑战性又可解，避免SFT中常见的数据分布偏差。

### 白盒强化学习

传统I/O奖励仅评估最终输出，无法捕捉中间执行状态的错误。ExecVerify在Stage I引入白盒奖励，将解释器执行轨迹 $\tau = (l_t, \sigma_t)_{t=1}^T$ 转化为两类可验证问题：控制流问题预测下一执行语句 $l_{t+1}$，数据流问题预测更新后的变量值与类型 $\sigma_{t+1}$。奖励函数定义为：

$$ R_{\text{white-box}} = 2 \cdot \left( (1-\alpha) R_{I \to O} + \alpha R_{\text{white}} \right) $$

其中 $R_{I \to O}$ 为最终I/O正确性的二元奖励，$R_{\text{white}}$ 为采样白盒问题集合 $Q_s$ 上的平均准确率，$\alpha=0.5$ 平衡终端与步级奖励。该公式的物理含义是，模型不仅需预测正确输出，还需准确解释每一步的控制流与数据流变化，从而将训练目标从文本匹配转向执行语义的逐步验证。Stage II则通过单元测试通过率 $R_{\text{gen}}$ 将执行推理能力迁移至代码生成任务，形成从推理到生成的两阶段训练闭环。

## 实验评估

在CRUXEval、LiveCodeBench-Exec与REval基准上，ExecVerify-7B在代码推理任务上显著优于同规模基线，平均得分从基线的60.8提升至80.8，接近Qwen2.5-Coder-32B-Instruct的77.9。基线覆盖SemCoder、CodeI/O等SFT方法，但缺乏与最新形式化验证方法的对比。

| 模型 | 规模 | CRUXEval-O | LiveCodeBench-Exec | REval | 平均 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Qwen2.5-Coder-Instruct | 7B | 61.0 | 78.6 | 60.3 | 60.8 |
| + SFT + white-box RL | 7B | 85.6 | 85.8 | 83.2 | 80.8 |
| Qwen2.5-Coder-Instruct | 32B | 78.2 | 84.6 | 83.3 | 77.9 |

消融实验显示，仅使用Stage II无法提升代码推理性能，而Stage I与Stage II结合在代码生成任务上取得最佳平均得分57.1，较纯GRPO基线提升5.9点。控制流与数据流奖励的互补性验证了白盒问题的细粒度设计价值：仅控制流奖励提升控制流指标但降低状态准确率，仅数据流奖励则相反，两者结合取得最高平均分80.8。

| 设置 | CRUXEval-O | LiveCodeBench-Exec | REval | 平均 |
| :--- | :--- | :--- | :--- | :--- |
| Stage I only | 85.6 | 85.8 | 83.2 | 80.8 |
| Stage II only | 61.6 | 77.4 | 60.2 | 60.8 |
| Stage I + II | 84.6 | 89.1 | 84.2 | 80.8 |

评估边界方面，实验仅覆盖Python及CRUXEval-X中的六种语言，未涉及形式化验证语言如Dafny或Verus。代码与超参数已开源，但RL训练需500步与8次rollout，计算成本较高。指标以pass@1为主，未报告置信区间，数值比较需谨慎。

## 关联研究分析

从问题动机看，ExecVerify与SemCoder、CodeI/O同属执行信号融入训练路线，但核心差异在于训练范式。SemCoder与CodeI/O依赖SFT模仿教师文本，其奖励信号稀疏且无法验证中间步骤；ExecVerify通过RL直接优化可验证的步级奖励，解决了SFT中“过拟合教师解释而非理解执行过程”的失效。这一差异源于任务特性：执行推理需要逐步语义正确性，而SFT的token级损失无法提供这种细粒度监督。

从方法设计看，ExecVerify与TracePile同属轨迹利用路线，但TracePile将轨迹翻译为自然语言进行SFT，而ExecVerify直接构建结构化白盒问题用于RL。这一设计选择源于对轨迹信息利用效率的考量：自然语言翻译引入额外噪声且难以验证，而结构化问题可直接从解释器提取，确保奖励信号的确定性与可验证性。然而，ExecVerify的白盒奖励仅覆盖局部状态变化，对跨过程依赖与全局逻辑一致性的建模能力有限，这与形式化验证方法如AlphaVerus在系统级验证上的优势形成对比。

## 总结

ExecVerify旨在解决LLM代码执行推理中SFT无法验证中间步骤且数据缺乏难度控制的核心矛盾。其切入点在于利用解释器轨迹构建可验证白盒问题，通过RL奖励机制直接优化步级语义正确性，并配合约束式合成解决数据分布问题。实验表明，7B模型在代码推理任务上平均得分达80.8，代码生成pass@1提升5.9点，接近32B模型性能。然而，白盒奖励仅覆盖局部状态变化，对全局逻辑一致性的保证不足，且实验未涉及形式化验证语言。当程序涉及深层跨过程依赖时，仅靠局部状态预测是否足以确保全局正确性，论文未给出回答。
