# ACL2026最新论文 ｜QiMeng-PRepair: Precise Code Repair via Edit-Aware Reward Optimization ｜编辑感知强化学习下的精确代码修复

研究机构：中科院计算所、中国科学院大学

作者：Changxin Ke、Rui Zhang、Jiaming Guo 等 13 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.05963)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.05963)

> 代码修复旨在自动纠正故障程序并保留其预期语义，但现有基于大语言模型（LLM）的方法往往陷入“过度编辑”陷阱，即通过重写大量正确代码来掩盖错误，导致可维护性下降且难以定位真实缺陷。本文指出，仅优化修复正确性的强化学习范式忽略了编辑幅度，导致模型无法区分“精准修复”与“暴力重写”。PRepair 框架通过自破坏数据生成与编辑感知组相对策略优化（EA-GRPO），将编辑成本纳入奖励函数，实现了在保持正确性的同时最小化代码变更。该方法在 Python 和 Verilog 任务上显著提升了修复精度，但受限于单元测试的覆盖范围，其“精确性”是否等同于逻辑正确性仍存疑。

## 研究背景

程序修复的核心困境在于数据分布的不对称性：真实软件缺陷通常表现为局部逻辑错误，而现有训练数据多为完全错误的代码或人工注入的简单 Bug。这种数据稀缺性迫使模型在缺乏“局部故障”样本的情况下学习修复策略。与此同时，强化学习（RL）在代码生成中的应用通常采用二元奖励机制，即仅当代码通过测试时给予正向反馈。这种“正确性唯一”的目标函数存在根本缺陷：它无法区分“修改一行代码修复 Bug”与“重写整个函数重写逻辑”这两种截然不同的行为，导致模型倾向于通过大规模重写来“碰运气”通过测试，而非理解并定位错误。

传统代码修复研究多采用多阶段流水线（如错误定位、修正、验证）或代理系统，这些方法虽然有效但推理成本高且难以端到端部署。随着 Copilot 等编码助手的普及，对快速、端到端修复模型的需求日益迫切。然而，现有端到端方法（如基于 SFT 或标准 GRPO 的模型）普遍存在过度编辑现象。本文切入点在于揭示过度编辑的双重危害：它不仅增加了开发者的审查负担，更因破坏了原有代码结构而削弱了模型的错误定位能力。因此，研究重点从“如何修对”转向“如何修得少且对”，即定义并优化“精确修复”这一新目标。

## 核心方法

### 方法参照系

本文问题属于基于强化学习的代码修复范式，其标准流程为：给定故障代码，模型生成候选修复，验证器（单元测试）评估正确性，策略梯度更新模型参数。与标准流程的关键差异在于，本文引入了编辑成本作为负向约束，将优化目标从单一的“功能正确”扩展为“功能正确且编辑最小”，从而改变了奖励信号的构成。

### 自破坏数据生成 (Self-Breaking)

针对真实局部故障数据稀缺的问题，本文提出自破坏策略。设计动机是解决训练数据中“正确逻辑占比高、故障点局部化”样本缺失导致的模型泛化能力不足。具体做法是提示 LLM 向黄金代码 $Y$ 注入 Bug，生成故障代码集 $X = \{X_1, ..., X_m\}$。为避免 Bug 模式集中，采用最小-最大采样策略，通过最小化样本间最大相似度（定义为 $1 - D_{EC}(X_i, X_j)$）来选取子集 $X_s$。该公式的物理含义是强制选出的故障代码在编辑距离上尽可能分散，从而覆盖多样化的错误类型，确保模型在训练时接触到足够丰富的局部故障模式。

### 编辑感知组相对策略优化 (EA-GRPO)

在自破坏数据基础上，本文改进 GRPO 的奖励机制以抑制过度编辑。设计动机是解决二元奖励无法惩罚“正确但冗长”的修复方案这一失效。EA-GRPO 引入动态编辑感知奖励，仅当组内平均准确率超过阈值 $\alpha$ 时，才对正确样本施加编辑惩罚。对于正确样本 $o_i$，其编辑惩罚项定义为：

$$ r_{edit}(o_i) = -\beta \cdot \sigma \left( \frac{D_{EC}(X, o_i) - \mu_{G_c}}{\sigma_{G_c}} \right) $$

其中 $D_{EC}$ 为归一化 Levenshtein 距离，$\mu_{G_c}$ 和 $\sigma_{G_c}$ 为组内正确样本编辑成本的均值与标准差，$\beta$ 为惩罚系数，$\sigma$ 为 Sigmoid 函数。该公式通过标准化编辑成本并施加 Sigmoid 边界，既保留了组内编辑幅度的相对排序，又避免了过度惩罚。最终奖励 $r_i = r_{acc} + r_{edit}$ 平衡了正确性与最小化编辑，使模型学会在确保通过测试的前提下，复用原有正确逻辑，仅修改故障行。

## 实验评估

实验在 Python (LeetCode) 和 Verilog (QiMeng-CodeV-R1) 数据集上进行，基线包括 Prompt Engineering、标准 GRPO 及 GPT4、Gemini2.0-Flash。基线覆盖较全面，但缺乏与 SFT 基线的直接对比，且未包含形式化验证基线。

| 语言 | 方法 | pass@1 | fix1@1 | fix2@1 |
| :--- | :--- | :--- | :--- | :--- |
| Python | Qwen2.5-Coder-7B + GRPO | 92.37 | 66.52 | 77.41 |
| Python | Qwen2.5-Coder-7B + EA-GRPO | 91.19 | 81.62 | 89.54 |
| Verilog | Qwen2.5-Coder-7B + GRPO | 68.63 | 38.00 | 49.59 |
| Verilog | Qwen2.5-Coder-7B + EA-GRPO | 68.37 | 68.11 | 68.59 |

EA-GRPO 在 Python 和 Verilog 上均显著提升了 fix1@1 指标，其中 Verilog 的 fix1@1 从 38.00% 提升至 68.11%，表明编辑约束有效抑制了过度编辑。

| $\alpha$ | $\beta$ | pass@1 | fix1@1 | fix2@1 |
| :--- | :--- | :--- | :--- | :--- |
| 0 | 0.05 | 90.73 | 81.74 | 88.93 |
| 0.8 | 0.05 | 91.19 | 81.62 | 89.54 |
| 1.1 | / | 89.82 | 47.44 | 60.88 |

消融实验显示，$\alpha=0$（始终惩罚）与 $\alpha=1.1$（仅正确性奖励）均导致性能下降。$\alpha=0$ 时模型忽视正确性，$\alpha=1.1$ 时 fix1@1 骤降至 47.44%，证明动态阈值对平衡正确性与编辑幅度至关重要。

评估边界方面，fix_p@k 指标虽兼顾正确性与编辑量，但依赖单元测试，无法检测逻辑错误。可复现性上，论文提供了超参数细节，但未公开代码库，且 Verilog 数据集依赖特定工具链，复现门槛较高。

## 关联研究分析

从问题动机看，本文与 Loong (Huang et al., 2025) 同属验证器引导优化路线，但 Loong 利用形式化验证器筛选高质量推理轨迹以进行后训练，而 PRepair 利用单元测试与编辑距离进行在线策略优化。差异根源在于任务特性：形式化验证提供确定性逻辑证据，适合证明生成；而代码修复需兼顾可维护性，编辑距离作为连续信号更贴合“最小变更”的工程需求。然而，单元测试的覆盖不足可能导致 PRepair 学习到“通过测试但逻辑错误”的修复策略，这是其相对于形式化验证方法的潜在盲区。

从方法设计看，本文与 MIST-RL (Zhu et al., 2026) 均采用 RL 优化代码生成，但 MIST-RL 关注测试生成的边际效用，而 PRepair 关注修复的编辑成本。MIST-RL 通过变异体杀死率驱动测试生成，属于测试驱动开发；PRepair 通过 Levenshtein 距离驱动代码修改，属于代码驱动修复。两者在奖励信号设计上存在互补性：MIST-RL 的测试生成能力可作为 PRepair 的验证器增强，但论文未探索这种组合，仅依赖现有测试套件。

## 总结

本文核心矛盾在于 LLM 代码修复中“正确性”与“最小化编辑”的目标冲突，现有方法因忽略编辑幅度导致过度编辑。PRepair 通过自破坏数据生成解决局部故障样本稀缺问题，并利用 EA-GRPO 将编辑成本动态融入奖励函数，实现了精确修复。实验表明，EA-GRPO 在 Verilog 上将 fix1@1 从 38.00% 提升至 68.11%，证明了编辑约束的有效性。然而，其边界在于依赖单元测试作为正确性判据，无法保证修复后的代码无深层逻辑错误。当单元测试覆盖率不足时，模型是否会将“通过测试”误判为“逻辑正确”，从而产生看似精确实则错误的修复，论文未给出回答。
