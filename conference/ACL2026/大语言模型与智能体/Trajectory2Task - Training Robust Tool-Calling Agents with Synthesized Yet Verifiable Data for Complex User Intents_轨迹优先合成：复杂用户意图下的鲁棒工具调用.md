# ACL2026最新论文 ｜Trajectory2Task: Training Robust Tool-Calling Agents with Synthesized Yet Verifiable Data for Complex User Intents ｜轨迹优先合成：复杂用户意图下的鲁棒工具调用

作者：Ziyi Wang、Yuxuan Lu、Yimeng Zhang 等 15 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_6517e5e3091c)

> 工具调用智能体在真实客服场景中常面临用户意图模糊、中途变更或根本不可行的情况，而现有基准多假设目标固定且明确，导致模型在动态交互中频繁失效。Trajectory2Task 通过“先执行后生成任务”的逆向合成管线，解决了传统“任务优先”合成中因求解器能力不足导致的轨迹不可验证问题。该方法构建了包含三类复杂意图的可验证数据集 Retail-3I，并证明基于成功轨迹的监督微调（SFT）能显著提升小模型在未见领域的泛化能力。尽管其在 SFT 范式内表现稳健，但缺乏与强化学习（RL）路线的横向对比，其性能上限是否受限于模仿学习的固有瓶颈尚存疑。

## 研究背景

在部分可观测马尔可夫决策过程（POMDP）中，智能体需基于内部信念状态 $b_t$ 选择动作，而真实用户意图 $u_t$ 是非平稳的潜在变量，会随智能体输出 $o^U_t$ 发生漂移。这种非平稳性使得静态规划失效，智能体必须在信息不全时决定何时询问、何时行动以及何时修正计划。

现有工具调用基准如 ToolBench 和 BFCL 主要评估静态目标下的 API 规划与参数填充，缺乏对意图动态性的系统控制。虽然 τ-bench 引入了多轮交互，但未将模糊性、意图漂移和不可行性作为独立的压力因子进行解耦评估。主流合成数据管线（如 APIGen-MT）采用“任务优先”策略，依赖 LLM 裁判保证质量，但无法提供确定性的执行验证，且在复杂多步场景中易产生逻辑不一致的轨迹。

本文切入点在于将数据生成的因果链反转：不先生成任务再求解，而是先让强模型在环境中执行出有效轨迹，再逆向推导任务描述。这种“轨迹优先”设计确保了每个任务都对应一个可达的环境状态和黄金标签轨迹，从而在模糊、变更和不可行意图下实现了闭环验证与训练。

## 核心方法

### 方法参照系

标准合成管线遵循“任务生成→轨迹求解→质量过滤”流程，其质量上限受限于求解器的推理能力。本文的关键差异在于将“轨迹探索”置于“任务生成”之前，利用执行结果作为真值锚点，而非依赖 LLM 对任务描述的逻辑一致性判断。

### 轨迹优先合成管线

该设计解决了传统管线中“错误轨迹被误标为真值”的失效问题。管线首先构建 API 依赖有向无环图（DAG），通过随机游走采样工具子集，确保轨迹的工具链在功能上可达。随后，探索器 LLM 在模拟环境中执行交互，生成包含推理 token 和工具调用的完整轨迹 $\zeta = \{(o_t, y_t)\}_{t=0}^T$。仅当轨迹通过数据库状态变更和通信完整性验证后，才进入任务生成阶段。

任务生成阶段通过修改摘要提示词，将轨迹逆向映射为三类复杂意图任务：

1.  **模糊意图**：指令中省略关键槽位，用户仅在智能体明确询问时提供信息。

2.  **变更意图**：对话中途目标漂移或分支，要求智能体动态调整计划。

3.  **不可行意图**：请求违反策略或工具约束，智能体需执行诊断动作并避免禁止动作。

$$
\mathcal{L}_{SFT}(\theta) = -\mathbb{E}_{(\tau, \zeta)} \sum_{t=0}^{T} \log P_\theta(y_t \mid \tau, o_{\le t})
$$

该损失函数最大化成功轨迹中智能体输出的似然，其中 $y_t$ 包含推理 token 和动作，$\tau$ 为任务描述。通过仅使用通过自动验证器的轨迹进行训练，模型习得的是在部分可观测环境下“何时问、如何改、如何拒”的决策行为，而非单纯的工具调用格式。

### 非平稳意图建模

针对意图漂移，本文将用户意图转移函数 $T_U$ 显式建模为 $u_{t+1} \sim T_U(u_{t+1} \mid u_t, o^U_t)$。在不可行意图场景中，奖励函数 $R$ 不再基于最终任务完成度，而是基于约束合规性：智能体成功当且仅当完成所有必需的诊断/响应动作且未执行任何禁止动作。这一设计将“失败”转化为可学习的“正确拒绝”行为，解决了传统 SFT 中缺乏负样本或错误恢复示范的问题。

## 实验评估

实验在自建 Retail-3I 基准上进行，该基准包含 473 个模糊意图任务及相应数量的变更与不可行任务，基于 Tau2-Bench 环境构建。基线仅涵盖 Qwen3 系列不同尺寸模型（4B, 8B, 14B, 32B, 235B），未对比 Tool-R1 等 RLVR 方法或检索增强方法，导致无法评估 SFT 相对于 RL 的相对优势。

| 模型 | 场景 | Pass^1 | Pass^2 | Pass^3 |
| :--- | :--- | :--- | :--- | :--- |
| Qwen3-235B | General | 0.775 | 0.746 | 0.727 |
| Qwen3-235B | Infeasible | 0.557 | 0.480 | 0.410 |
| Qwen3-8B (SFT) | General | 0.736 | 0.709 | 0.691 |
| Qwen3-8B (SFT) | Infeasible | 0.576 | 0.504 | 0.463 |
| Qwen3-4B (SFT) | Infeasible | 0.578 | 0.499 | 0.463 |

SFT 后的 Qwen3-8B 在不可行意图场景下 Pass^1 达到 0.576，略高于未微调的 Qwen3-4B (0.578 为 4B SFT 值，此处对比需谨慎，原文 4B SFT Infeasible Pass^1 为 0.578，8B SFT 为 0.576，两者接近，但 8B 在 General 场景下 0.736 显著高于 4B 的 0.720)。值得注意的是，Qwen3-235B 在不可行场景下 Pass^1 仅为 0.557，低于 SFT 后的 8B 模型，表明大模型在缺乏特定意图训练时，其通用推理能力未必能转化为对复杂约束的精确遵守。

消融实验显示，随着 Pass^k 中 k 值增加，所有模型性能均下降，其中不可行意图场景下降幅度最大（Qwen3-235B 从 0.557 降至 0.410），反映出模型在多次独立试验中保持一致性拒绝策略的难度。评估协议采用 Pass^k 指标，强调鲁棒性而非单次成功率。代码未公开，但提供了详细的提示词附录和人工验证样本，可复现性中等。

## 关联研究分析

从数据生成机制看，Trajectory2Task 与 APIGen-MT 的核心差异在于验证锚点。APIGen-MT 依赖 LLM 裁判判断轨迹与任务蓝图的一致性，属于“逻辑一致性”验证；而本文依赖数据库状态变更和工具执行结果，属于“物理可达性”验证。这一差异源于任务复杂度：在不可行意图场景中，逻辑一致性难以界定“正确拒绝”的边界，而执行验证能明确区分“尝试违规”与“正确诊断”。然而，轨迹优先设计可能牺牲任务分布的多样性，因为任务是由有限工具子集的随机游走生成的，其覆盖范围受限于 API DAG 的结构，是否足以代表真实世界中长尾意图分布，论文未给出回答。

从训练范式看，本文坚持 SFT 路线，与当前领域向 RLVR 转型的趋势形成对比。Tool-R1 等方法通过环境反馈优化策略，理论上能探索更优的拒绝或澄清策略；而 SFT 仅模仿强模型的既有行为。本文实验显示 SFT 后的 8B 模型在不可行场景下性能接近 235B 基线，暗示在数据质量足够高（即轨迹经过严格执行验证）的情况下，模仿学习可能已触及该任务的性能上限，或者 RL 的额外探索成本在此类约束明确的任务中收益有限。

## 总结

本文核心矛盾在于真实用户意图的非平稳性与现有基准静态假设之间的错位。Trajectory2Task 通过轨迹优先合成，将验证锚点从 LLM 裁判转移至环境执行结果，解决了复杂意图下数据不可验证的问题。实验证明，基于此数据的 SFT 能使 8B 模型在不可行意图场景下达到 0.576 的 Pass^1，超越 235B 基线的 0.557。其边界在于仅验证了 SFT 范式内的有效性，且任务分布受限于 API DAG 的随机游走覆盖。当 API 库规模扩大至数万级时，轨迹优先合成的计算成本是否呈线性增长，以及 SFT 模型在面对未见过的工具组合时是否会出现灾难性遗忘，论文未给出回答。
