# ACL2026最新论文 ｜RExBench: Can coding agents autonomously implement AI research extensions? ｜科研扩展基准：从复现到假设驱动的代码实现

研究机构：奥地利维也纳大学、美国波士顿大学

作者：Nicholas Edwards、Yukyung Lee、Yujun Audrey Mao 等 6 人

论文原文见 [arXiv](https://arxiv.org/abs/2506.22598)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_8aad2d7b217f)

> 深度研究智能体领域长期聚焦于信息检索与报告生成，而科研自动化闭环中“基于假设修改现有代码库”这一关键环节缺乏标准化评估。现有基准如 PaperBench 侧重从零复现，无法衡量智能体在特定研究语境下执行增量创新的能力。REXBENCH 通过构建 12 个抗数据污染的私有化扩展任务，利用容器化执行与数值比对机制，首次量化了 LLM 智能体自主实现科研扩展的边界。尽管最佳智能体成功率仅 33%，该基准揭示了当前通用智能体在精细代码逻辑理解上的显著短板，但其样本量限制了对统计显著性的判断。

## 研究背景

当智能体试图在现有代码库上实现新的研究假设时，它必须同时理解论文中的理论逻辑、代码库的工程结构以及扩展指令中的隐含约束。这种多源信息的整合要求智能体具备超越简单代码补全的推理能力，即需要在不破坏原有功能的前提下，精准定位修改点并验证数值结果的正确性。这一过程区别于传统的检索增强生成，后者仅依赖静态文本匹配，而科研扩展要求智能体在动态执行环境中进行闭环验证。

科研自动化领域的主流路线分为“复现派”与“扩展派”。复现派以 PaperBench 为代表，评估智能体从零构建实验代码的能力，但忽略了真实科研中基于已有成果进行迭代的核心特征。扩展派则关注假设驱动的代码修改，但此前缺乏统一的评估标准，导致不同研究间的结果不可比。REXBENCH 的切入点在于将“扩展”定义为独立的基准任务，通过私有化 Gold Solution 规避数据污染，并引入执行成功率与文件召回率作为细粒度过程指标，填补了从“能跑通”到“结果对”的评估空白。

## 核心方法

### 任务定义与抗污染设计

REXBENCH 将科研扩展任务形式化为代码实现问题，输入包含研究论文、原始代码库及专家撰写的扩展指令。该设计的关键差异在于其抗污染机制：所有 Gold Solution 存储于私有 Bitbucket 仓库，且扩展任务本身为新颖假设，确保 LLM 无法通过记忆获取答案。任务约束包括：原始论文的关键趋势必须可复现、Gold 实现必须在 12 小时内完成、且所有依赖包版本固定。这种设计确保了评估的公平性与可复现性，同时保持了任务的现实复杂度。

### 数值范围匹配评估机制

针对开放式任务难以自动评估的难题，REXBENCH 采用数值范围匹配作为核心成功标准。对于确定性任务，要求智能体输出与 Gold 实现完全一致；对于存在随机性的任务，通过五次独立运行 Gold 实现，计算均值 $\mu$ 与标准差 $\sigma$，定义成功区间为：

$$
[\mu - 2\sigma, \mu + 2\sigma]
$$

该公式的物理含义是：只要智能体的实现结果落在 Gold 实现的统计波动范围内，即视为成功。这一设计解决了传统精确匹配在随机环境下的失效问题，同时通过窄区间（实践中观察无假阳性/假阴性）保证了评估的严格性。此外，引入文件召回率 $FR = \frac{|Files_{agent} \cap Files_{gold}|}{|Files_{gold}|}$ 作为辅助指标，量化智能体定位核心修改文件的能力，弥补仅看最终结果的不足。

### 受控执行基础设施

为确保数值比对的可靠性，REXBENCH 构建了基于 OpenStack 的容器化执行环境。每个任务在独立的 Apptainer 容器中运行，预加载原始代码库与评估脚本，并固定所有随机种子与硬件配置。智能体提交的 Git Patch 文件在容器内应用并执行，超时限制设为 12 小时（约为最长 Gold 运行时间的两倍）。该基础设施实现了任务级并行化，确保了不同智能体在完全相同的环境条件下接受评估，消除了硬件差异与依赖冲突对结果的干扰。

## 实验评估

实验设置涵盖 12 个 NLP/ML 领域的扩展任务，基线包括 aider 与 OpenHands 两种框架，结合 GPT-5、Claude 4/3.7 Sonnet、o1、o4-mini 及 DeepSeek-R1 等骨干模型。基线覆盖审计显示，本文未包含基于强化学习训练的专用智能体（如 ASearcher），这可能限制了性能上限的探索。主实验结果表明，所有智能体在多数任务上表现挣扎，最佳组合 OpenHands + Claude 4 Sonnet 的平均最终成功率为 33%，执行成功率为 68%。DeepSeek-R1 的执行成功率为 0，表明其代码生成能力在该任务上完全失效。

| 智能体组合 | 最终成功率 (%) | 执行成功率 (%) | 备注 |
| :--- | :--- | :--- | :--- |
| OpenHands + Claude 4 Sonnet | 33 | 68 | 最佳表现 |
| OpenHands + Claude 3.7 Sonnet | 8 | - | 显著低于 Claude 4 |
| Aider + GPT-5 | 2 | - | 非迭代设计导致低效 |
| DeepSeek-R1 (任意框架) | 0 | 0 | 完全失败 |

消融实验显示，提供信息定位提示（Level 1）可提升成功率，但即使提供逐步实现指导（Level 2），最佳性能仍低于 44%。这一发现表明，瓶颈不仅在于信息获取，更在于智能体将高层指令转化为具体代码逻辑的能力。文件召回率普遍较高，说明智能体能定位修改文件，但无法正确实现逻辑，揭示了“定位”与“实现”之间的能力断层。

评估边界方面，12 个任务的样本量限制了统计显著性，且任务局限于 NLP/ML 领域，未覆盖生物、物理等其他科学领域。可复现性上，代码与数据已开源，但 Gold Solution 私有化可能限制社区复现细节。指标完备性上，缺乏对代码逻辑非等价性的细粒度分析，数值匹配可能掩盖实现路径的差异。

## 关联研究分析

从问题动机看，REXBENCH 与 PaperBench 的核心差异在于任务形态。PaperBench 评估从零复现，侧重代码生成的完整性；REXBENCH 评估增量扩展，侧重对现有代码库的理解与修改。这一差异源于真实科研流程中，研究者更多是在已有工作基础上迭代，而非从头构建。REXBENCH 的抗污染设计（私有 Gold Solution）比 PaperBench 更严格，因为扩展任务的新颖性使其更容易被 LLM 记忆，而 PaperBench 的复现任务可能已在公开数据中存在。

从方法设计看，REXBENCH 与 MLE-bench 共享容器化执行范式，但任务粒度不同。MLE-bench 聚焦竞赛解题，强调算法优化；REXBENCH 聚焦科研扩展，强调假设验证与代码逻辑的对应。REXBENCH 未采用 HiRAS 等层级多智能体框架，而是使用通用智能体，这可能限制了性能上限。HiRAS 在 PaperBench 上取得 66.6% 的成绩，暗示专用架构在复杂代码任务上可能优于通用框架。REXBENCH 的数值范围匹配机制比 MLE-bench 的精确匹配更灵活，但可能掩盖实现逻辑的非等价性，这一权衡在论文中未深入讨论。

## 总结

REXBENCH 要解决的核心矛盾是科研扩展任务的开放性与自动评估可行性之间的冲突。其切入点在于通过私有化 Gold Solution 与数值范围匹配机制，在保持任务现实复杂度的同时实现自动评估。该基准证明了当前 LLM 智能体在自主实现科研扩展上的显著局限，最佳成功率仅 33%，且即使提供逐步指导，性能仍低于 44%。本文的边界在于样本量小、领域局限及未探索专用架构的潜力。当智能体在文件召回率较高但最终成功率较低时，如何量化“定位”与“实现”之间的能力断层，论文未给出回答。
