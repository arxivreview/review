# ACL2026最新论文 ｜CAR-bench: Evaluating the Consistency and Limit-Awareness of LLM Agents under Real-World Uncertainty ｜车载智能体局限感知与一致性评估基准

作者：Johannes Kirmayr、Lukas Stappen、Elisabeth André

论文原文见 [arXiv](https://arxiv.org/abs/2601.22027)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2601.22027)

> 现有大语言模型智能体基准多假设任务信息完备且工具可用，导致模型在真实交互中面对模糊指令或缺失能力时，倾向于编造而非承认局限。CAR-bench 切入这一盲区，构建了包含 58 个工具与 19 项策略的车载环境，通过引入“幻觉”与“歧义消解”任务类型，量化智能体在不可满足请求下的行为退化。该基准揭示了前沿推理模型在一致性上的显著缺口，为安全关键场景的部署可靠性提供了诊断工具，但其依赖 LLM 模拟用户的设计引入了新的噪声源，评估结果的绝对可信度仍受限于模拟保真度。

## 研究背景

车载语音助手面临的核心困境是用户指令的模糊性与车辆 API 的严格安全性之间的冲突。当用户发出“去巴黎”这类未指定路线或充电需求的指令时，智能体必须通过多轮对话消解歧义；而当所需工具缺失或参数不全时，智能体必须识别自身局限并诚实反馈，而非执行错误操作。这种对“不确定性处理”与“局限感知”的要求，超出了传统静态基准仅关注最终状态正确性的范畴，构成了动态交互评估的新维度。

当前智能体评估领域的主流路线聚焦于通用任务完成能力，如 WebArena 侧重网页导航，SWE-bench 侧重代码修复，而 τ-bench 虽引入多轮交互与策略约束，但仍假设任务在理论上可解。ToolSandbox 和 BFCLv3 开始探索工具缺失场景，但仅覆盖部分工具移除，未触及参数缺失或环境观察不完整等更细微的失效模式。这些基准的共性瓶颈在于：它们无法区分模型是“有能力但执行不一致”还是“根本缺乏识别局限的认知能力”。CAR-bench 的切入点正是填补这一空白，将评估焦点从“能否完成任务”转向“在无法完成时能否正确拒绝”，并引入 Pass^k 指标以量化这种拒绝行为在多次运行中的稳定性。

## 核心方法

### 方法参照系

CAR-bench 建立在 τ-bench 的动态交互范式之上，继承了其 LLM 模拟用户、API 工具调用及策略遵循的基本架构。关键差异在于任务类型的扩展：τ-bench 仅包含可解任务，而 CAR-bench 引入了两类不可解或需消解的任务，并重新定义了成功标准，从“状态匹配”扩展至“行为合规性”。

### 任务类型与评估指标

传统基准的成功判定依赖于最终状态与真值状态的精确匹配，这在任务不可解时会导致所有模型均被判定为失败，无法区分“盲目执行”与“诚实拒绝”。CAR-bench 引入 _Hallucination_ 任务，通过移除必要工具、参数或结果，使任务在物理上不可满足。此时，成功标准不再是状态匹配，而是智能体是否通过控制词“llm acknowledges limitation”明确承认局限。对于 _Disambiguation_ 任务，成功要求智能体在采取动作前通过内部信息检索或用户澄清消解歧义，若过早执行或无谓询问用户则判定失败。

为量化这种一致性，CAR-bench 采用 Pass^k 与 Pass@k 双指标。Pass^k 定义为任务在 k 次独立运行中全部成功的概率，反映部署可靠性；Pass@k 定义为至少一次成功的概率，反映模型潜力。其数学表达为：

$$ \text{Pass}^k_t = \prod_{i=1}^{k} r_{t}^{(i)} $$

其中 $r_{t}^{(i)}$ 为第 $i$ 次运行的二元成功指示器。该公式的物理含义是：只有当智能体在每一次重复测试中都表现出正确的局限感知或歧义消解行为时，才被视为具备该能力，任何一次“侥幸”或“随机正确”均不计入一致性得分。

### 环境构建与策略验证

环境构建的核心挑战在于如何模拟真实车载系统的复杂依赖关系。CAR-bench 设计了 58 个工具，分为 _get_（信息检索）与 _set_（状态修改）两类，并通过 API 图链接工具间的参数依赖与状态触发关系。例如，设置导航前需检查电量状态，这构成了隐式的策略约束。

策略验证采用混合机制以平衡精度与可行性。对于 12 条可程序化验证的策略（如“禁止同时开启远光灯与雾灯”），使用代码直接检查状态变量；对于 7 条依赖语义理解的策略（如“发送邮件前需用户确认”），则采用 LLM-as-a-Judge 进行评估。这种设计解决了纯代码验证无法覆盖语义合规性、纯 LLM 验证缺乏确定性的问题。策略合规性作为独立奖励指标，与动作正确性并列，确保智能体不仅“做对事”，而且“按规矩做事”。

## 实验评估

实验覆盖 GPT-5、Claude-Opus-4.5、Gemini-2.5 等前沿模型及 Qwen3-32B 等开源模型，基线审计显示未包含 ReAct 等复杂框架，旨在隔离模型内在能力。主结果揭示了一致性缺口：在 _Disambiguation_ 任务上，GPT-5 的 Pass@3 为 68%，但 Pass^3 骤降至 36%，表明模型具备识别歧义的潜力，但无法稳定执行。

| 模型 | Base Pass^3 | Hallucination Pass^3 | Disambiguation Pass^3 |
| :--- | :--- | :--- | :--- |
| GPT-5 (thinking) | .66 | .60 | .36 |
| Claude-Opus-4.5 (thinking) | .52 | .52 | .38 |
| GPT-4.1 | .37 | .31 | .22 |

消融分析显示，思考型模型在 _Hallucination_ 任务上显著优于非思考型，GPT-5 的主动编造率（E5b）低于 GPT-4.1，但隐式掩盖（E5a）仍占 70%。在 _Disambiguation_ 任务中，思考型模型未能显著降低过早行动（E1）错误，该错误占 GPT-5 持续失败的约 90%。这表明推理能力主要缓解了逻辑与执行错误，但对“完成导向”导致的策略违规缺乏有效抑制。

评估边界方面，用户模拟采用 Gemini-2.5-Flash，手动检查发现 2.4%-6.1% 的失败源于用户模拟错误，其中 6%-9% 为唯一原因，直接降低了 Pass^5 分数。代码已开源，但温度设置因提供商限制存在差异（Claude/GPT-5 固定为 1），可能引入额外方差。

## 关联研究分析

从问题动机看，CAR-bench 与 ToolSandbox 均关注工具缺失，但 ToolSandbox 仅移除整个工具函数，而 CAR-bench 进一步移除参数或结果，模拟了更细粒度的 API 不稳定性。这一差异源于车载场景对参数精度的高要求，如“充电”操作需精确的电量阈值，参数缺失比工具缺失更常见且更具隐蔽性。ToolSandbox 未探索这一维度，可能是因其通用环境缺乏此类强约束。

从方法设计看，CAR-bench 与 τ-bench 共享动态交互框架，但 τ-bench 的成功标准基于最终状态匹配，而 CAR-bench 在不可解任务中引入行为合规性指标。这一设计差异反映了任务特性的根本不同：τ-bench 的任务均可解，关注执行效率；CAR-bench 的任务部分不可解，关注认知边界。τ-bench 未引入此类指标，是因为其零售/航空场景缺乏“安全关键”的硬性约束，错误执行的后果相对较轻，而车载场景中错误执行可能导致物理危险，因此必须将“拒绝执行”作为独立评估维度。

## 总结

CAR-bench 解决了智能体评估中“可解性假设”与“真实世界不确定性”之间的矛盾，通过构建不可解任务与歧义任务，量化了模型在局限感知与歧义消解上的一致性缺口。实验证明，即使是最先进的推理模型，在 _Disambiguation_ 任务上的 Pass^3 也仅 36%，暴露了当前 LLM 在稳定执行复杂认知策略上的根本局限。该基准的边界在于其依赖 LLM 模拟用户，而用户模拟本身的幻觉与不一致性（占比高达 9%）可能混淆模型能力的真实评估。当用户模拟的噪声被进一步降低或引入人类验证时，模型在局限感知上的真实能力边界是否会发生显著偏移，论文未给出回答。
