# ACL2026最新论文 ｜Programming over Thinking: Efficient and Robust Multi-Constraint Planning ｜可复用代码规划引擎

研究机构：新加坡南洋理工大学

作者：Derrick Goh Xin Deik、Quanyu Long、Zhengyuan Liu 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2601.09097)

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2601.09097)

> 多约束规划要求智能体在组合爆炸的解空间中同时满足多个相互依赖的硬性条件，现有大语言模型（LLM）方法要么依赖长链自然语言推理导致错误累积与成本指数增长，要么为每个查询独立生成求解代码而无法复用。SCOPE 将查询特定的语义解析与通用的代码执行逻辑解耦，通过从单一样例中归纳出可复用的求解器函数，使同域内的后续查询仅需更新参数即可求解。该框架在弱骨干模型上实现了接近强模型基线的性能并大幅降低推理成本，但其跨域泛化能力与代码执行的形式化完备性仍存疑。

## 研究背景

多约束规划的核心难点在于解空间的组合爆炸与约束间的逻辑耦合。当任务涉及时间、空间、资源等多重限制时，LLM 的自回归生成机制难以在长序列中同时维持所有约束的满足，导致“短视”行为与逻辑断裂。为应对此问题，领域内形成了两条主要技术路线：一是基于自然语言的推理增强，如思维树（Tree-of-Thought, ToT）或进化代理（EvoAgent），通过显式枚举或迭代优化中间状态来探索解空间；二是基于代码生成的求解器集成，如思维搜索（Thought of Search, ToS），将规划问题转化为可执行的搜索代码，利用代码的确定性来保证逻辑正确性。

然而，这两条路线均存在显著瓶颈。自然语言推理路线随着任务复杂度增加，推理链长度呈指数级增长，不仅计算成本高昂，且中间步骤的错误会迅速累积，导致最终方案无效。代码生成路线虽然保证了逻辑的确定性，但现有方法（如 ToS）通常为每个新查询从头生成独立的求解代码，缺乏对底层规划逻辑的抽象与复用，导致在相同领域内重复计算，效率低下。SCOPE 的切入点在于识别出“查询特定推理”与“通用执行逻辑”的可分离性，通过构建域级可复用的求解器函数，将 LLM 的角色从“每次重新推导逻辑”转变为“提取参数并调用固定逻辑”，从而在保持灵活性的同时获得代码执行的鲁棒性与效率。

## 核心方法

### 方法参照系

本文问题可置于“代码增强推理”框架下，其标准流程为：LLM 解析自然语言查询 → 生成针对该查询的特定求解代码 → 执行代码获得答案。SCOPE 与该通用流程的关键差异在于，它不生成查询特定的代码，而是生成一组与具体查询解耦的、可复用的求解器函数（Solver Functions），后续查询仅需生成参数值并调用这些函数。

### 查询特定问题推理

在标准代码生成流程中，LLM 直接输出包含具体数值的代码。SCOPE 在此环节引入“问题形式化”与“问题优化”两个子步骤，旨在从单一样例中提取出结构化的组合参数（Combinations）与约束参数（Constraints）。设计动机是解决直接生成代码时参数与逻辑纠缠、难以复用的问题。形式化阶段由规划代理（Planning Agent）和解决方案代理（Solution Agent）协作，将查询转化为 JSON 结构，其中组合参数定义候选计划的生成空间，约束参数定义过滤条件。优化阶段通过多个优化代理（Optimization Agents）迭代去除冗余与歧义，确保参数结构的完备性与一致性。该过程可形式化为：

$$
(C, K) \leftarrow \mathcal{O}(\mathcal{P}(Q_{ex}), \mathcal{S}(Q_{ex}))
$$

其中 $\mathcal{P}$ 为规划代理，$\mathcal{S}$ 为解决方案代理，$\mathcal{O}$ 为优化代理集合，$Q_{ex}$ 为示例查询。此公式表明，结构化表示 $(C, K)$ 是通过多代理迭代优化从示例中提取的，而非直接映射。

### 通用求解器生成与推理

在获得结构化表示后，SCOPE 进入通用求解器生成阶段，构建组合函数（Combination Function）、过滤函数（Filter Function）和交付函数（Deliver Function）。设计动机是确保执行逻辑的确定性与复用性，避免每次查询都重新生成代码。求解器构建阶段由三个专用代理分别生成这三个函数，并通过“求解器精炼”步骤，利用示例查询的答案作为监督信号，迭代修正函数直至输出匹配。推理阶段，输入代理（Input Agent）仅负责从新查询中提取参数值 $(C_i, K_i)$，随后调用预生成的求解器函数：

$$
S_i \leftarrow F_{deliver}(F_{filter}(F_{comb}(C_i), K_i))
$$

其中 $F_{comb}$ 生成候选计划，$F_{filter}$ 根据约束过滤，$F_{deliver}$ 转换为自然语言。该公式体现了 SCOPE 的核心机制：推理过程被简化为参数提取与固定函数的组合调用，逻辑执行完全由代码保证，LLM 仅负责语义到参数的映射。

## 实验评估

实验在 TravelPlanner 和 Natural Plan（含 Trip Planning 与 Meeting Planning）基准上进行，对比了 Direct、CoT、ToT、EvoAgent、HTP 和 ToS 六种基线，使用 GPT-4o、GPT-o3、GPT-5、Gemini-1.5-Pro 和 Gemini-2.5-Pro 五种模型。基线覆盖了文本推理与代码求解两条主要路线，但缺失 PDDL 形式化方法（如 NL2PDDL）的对比，这可能影响对“代码 vs. 符号逻辑”效率差异的全面评估。

| 模型 | 方法 | TravelPlanner SR (%) | Trip Planning SR (%) | Meeting Planning SR (%) |
| :--- | :--- | :--- | :--- | :--- |
| GPT-4o | CoT | 31.5 | 64.8 | 59.8 |
| GPT-4o | ToS | 12.5 | 31.5 | 59.8 |
| GPT-4o | SCOPE | 93.1 | 87.1 | 100 |
| GPT-5 | CoT | 91.4 | 91.8 | 93.2 |
| GPT-5 | SCOPE | 93.9 | 89.5 | 100 |

在 GPT-4o 上，SCOPE 在 Trip Planning 中达到 87.1% 的成功率，显著优于 CoT 的 64.8% 和 ToS 的 31.5%，甚至超过了 GPT-5 使用 CoT 的 91.8%（接近值）。这表明 SCOPE 通过确定性逻辑弥补了弱骨干模型的推理能力不足。消融实验显示，移除“问题优化”或“求解器精炼”会导致性能大幅下降，例如在 Trip Planning 中，移除问题优化后成功率降至 0.0%，移除求解器精炼后降至 0.0%，证明这两个环节对确保求解器通用性与正确性至关重要。

评估边界方面，SCOPE 仅在同域内复用求解器，跨域需重新生成，限制了其泛化范围。此外，实验主要依赖闭源模型，未评估开源模型对代码生成能力的依赖。可复现性上，论文提供了 GitHub 链接，但未详细报告超参数与计算资源消耗，仅提供了 API 成本与时间数据。

## 关联研究分析

从方法设计看，SCOPE 与 ToS 的核心差异在于代码的复用粒度。ToS 为每个查询生成独立的搜索代码，其逻辑与具体查询绑定，无法跨查询复用；而 SCOPE 将逻辑抽象为域级函数，仅参数随查询变化。这一差异源于对“规划逻辑”与“查询实例”解耦程度的不同理解：ToS 视每个查询为独立的搜索问题，而 SCOPE 视同域查询为同一逻辑结构下的不同参数实例。这种解耦使得 SCOPE 在推理阶段仅需一次 LLM 调用提取参数，而 ToS 需多次调用生成代码，从而在成本上获得显著优势。然而，SCOPE 的解耦依赖于查询间逻辑结构的一致性，若同域内存在逻辑变体，其复用性将受限，论文未对此进行量化评估。

从问题动机看，SCOPE 与 NL2PDDL 等符号规划方法均旨在解决 LLM 逻辑幻觉问题，但路径不同。NL2PDDL 依赖外部 PDDL 规划器进行形式化验证，强调逻辑的完备性与可验证性；SCOPE 则依赖代码执行，强调效率与灵活性。代码执行虽快，但缺乏 PDDL 那样的形式化完备性保证，即代码可能执行错误但无语法错误，而 PDDL 规划器能证明无解。SCOPE 的“求解器精炼”步骤通过示例验证部分弥补了这一缺陷，但仅针对单一样例，未提供全局逻辑正确性的证明。这种取舍使得 SCOPE 在效率上优于符号方法，但在安全关键应用中可能面临风险。

## 总结

SCOPE 旨在解决多约束规划中 LLM 推理成本高与逻辑不稳定的矛盾，其切入点是将查询特定推理与通用执行逻辑解耦，通过从单一样例归纳可复用求解器函数，使同域查询仅需参数更新即可求解。实验证明，在 GPT-4o 上，SCOPE 在 Trip Planning 中达到 87.1% 的成功率，较 CoT 基线提升 22.3 个百分点，且推理成本降低 1.4 倍。其边界在于求解器仅限同域复用，跨域需重新生成，且代码执行缺乏形式化完备性保证。当同域内查询的逻辑结构出现细微变体时，预生成的求解器函数是否仍能正确过滤候选计划，论文未给出回答。
