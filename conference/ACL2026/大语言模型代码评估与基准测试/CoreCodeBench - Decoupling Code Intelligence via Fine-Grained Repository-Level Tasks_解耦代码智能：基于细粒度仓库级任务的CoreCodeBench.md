# ACL2026最新论文 ｜CoreCodeBench: Decoupling Code Intelligence via Fine-Grained Repository-Level Tasks ｜解耦代码智能：基于细粒度仓库级任务的CoreCodeBench

研究机构：上海交通大学、美团

作者：Lingyue Fu、Hao Guan、Bolun Zhang 等 12 人

分析报告见 [ArxivReview](https://www.arxivreview.com/papers/conf_a0cd090642bc)

> 现有代码评估基准将编程能力视为单一整体，通过粗粒度通过率掩盖了模型在不同工程场景下的认知瓶颈。静态基准面临数据污染与性能饱和的双重失效，而端到端仓库级任务又因复杂度过高难以定位具体缺陷。CoreCodeBench通过COREPIPE管道将同一代码上下文拆解为开发、修复与测试驱动三类原子任务，实现认知维度的隔离评估。该框架揭示了模型能力的非单调性，但原子任务解耦是否削弱了真实工程中的耦合效应，仍存疑。

## 研究背景

当模型在HumanEval上接近满分时，评估体系陷入两难：静态基准因数据污染失去区分度，而SWE-bench等仓库级基准虽具真实性，却将生成、调试与规划能力混同于单一指标。这种“单体化”评估无法回答模型究竟擅长代码生成还是逻辑推理，导致优化方向模糊。

仓库级软件工程评估的主流路线是端到端解决GitHub Issue，如SWE-bench强调跨文件依赖与执行验证。然而，该范式下模型性能下降归因困难，无法区分是上下文理解不足还是特定认知环节失效。LiveCodeBench通过时间维度动态更新解决污染问题，但仍未触及能力结构的内部解耦。CoreCodeBench的切入点在于：在保持仓库级上下文真实性的前提下，将单一任务拆解为具有不同认知需求的原子单元，从而诊断具体的认知瓶颈。

## 核心方法

### 方法参照系

仓库级评估的标准流程是从真实仓库提取Issue，构建包含完整依赖关系的执行环境，以端到端解决率为指标。本文的关键差异在于放弃端到端求解，转而通过函数调用树（Function Call Tree）将任务原子化，并在相同上下文中生成多类型任务以隔离认知维度。

### 原子任务生成与认知隔离

原子任务生成阶段的核心改动在于引入级联合成策略与信息增益过滤。传统BugFix基准多采用语法扰动或对抗注入，导致错误缺乏语义连贯性。本文采用“高级模型设计逻辑谬误+小模型实现噪声”的两阶段策略，确保Bug符合真实开发者失误特征。对于TDD任务，通过函数调用树映射单元测试至核心代码块，以测试通过作为功能正确性的代理指标。

$$
\text{IoU}(A, B) = \frac{|S_A \cap S_B|}{|S_A \cup S_B|}
$$

该公式量化模型在任务A与B上成功实例集合的重叠度，用于检测能力一致性。低IoU值表明模型在不同认知维度上存在显著的能力错位，而非整体性能波动。

### 复合任务缩放与难度控制

复合任务生成阶段通过子图采样实现难度动态调节。给定全局函数调用树 $G=(V,E)$，通过超参数依赖深度 $d$ 与任务数量 $\nu$ 采样连通子图 $G' \subseteq G$。

$$
G' \subseteq G, \quad |V(G')| \le \nu, \quad \text{depth}(G') \le d
$$

该约束确保任务复杂度可控。当 $d=3$ 时，Multi-Dev任务平均AC@All从12.9%降至8.7%，Multi-TDD从19.4%降至2.8%，证明依赖深度增加显著提升了推理范围，有效缓解了性能饱和。

## 实验评估

实验在12个Python仓库上构建1,524个任务，评估GPT-5.2、Claude-4.5、Gemini-3-Pro等SOTA模型。基线覆盖闭源与开源主流模型，但缺失早期开源基线如DeepSeek-V3.1，且未与SWE-bench等标准基准进行跨基准相关性验证。

| 模型 | Dev AC@1 | BugFix AC@1 | TDD AC@1 |
|---|---|---|---|
| Gemini-3-Pro | 87.72 | 78.58 | 89.33 |
| Claude-4.5 | 86.56 | 63.25 | 83.92 |
| GPT-5.2 | 81.80 | 70.92 | 83.27 |

Gemini-3-Pro在开发任务上领先，但BugFix任务上Claude-4.5与GPT-5.2差距缩小，揭示能力错位。消融实验显示，低信息增益（IG≤0）任务上模型性能差距压缩，证明IG过滤对区分度的必要性。

评估边界方面，指标仅包含AC@1与AC Rate，缺乏计算效率维度；评估协议为零样本贪心解码，未探索多轮交互；代码开源但COREPIPE管道超参数（如掩码长度分布）未完全公开，可复现性受限。

## 关联研究分析

从问题动机看，SWE-bench强调端到端真实性，而CoreCodeBench主张原子解耦更能揭示认知瓶颈。这一差异源于任务特性：SWE-bench关注“能否解决”，CoreCodeBench关注“为何失败”。若原子任务解耦导致评估偏离真实工程工作流，则其诊断价值需重新审视。

从方法设计看，LiveCodeBench通过时间维度防污染，CoreCodeBench通过代码变换防污染。前者依赖持续收集新问题，后者依赖自动化管道生成变体。CoreCodeBench的78.55%有效率远超SWE-bench-Verified的31.7%，但自动化生成的任务是否覆盖所有边缘案例，论文未给出回答。

## 总结

CoreCodeBench解决的核心矛盾是粗粒度评估掩盖认知瓶颈与静态基准失效。其切入点在于利用函数调用树将仓库级任务原子化，通过级联合成与难度缩放实现认知隔离与防污染。实验证明模型在开发、修复与测试维度上存在显著能力错位，如Kimi-K2开发任务通过率比BugFix高35%以上。边界在于原子任务解耦可能削弱真实工程中的耦合效应，且缺乏与标准基准的跨基准验证。当支持集增大到5-shot时，查询侧增强的边际收益是否递减，论文未给出回答。
