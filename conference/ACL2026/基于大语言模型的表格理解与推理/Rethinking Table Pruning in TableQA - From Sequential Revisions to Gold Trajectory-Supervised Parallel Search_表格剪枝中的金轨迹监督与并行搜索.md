> 表格问答（Table Question Answering, TableQA）常因原始表格中大量无关行列干扰推理而失效，表格剪枝旨在提取紧凑子表以简化下游任务。现有剪枝方法依赖不可靠的批评信号进行顺序修订，易陷入局部最优且无法检测关键数据丢失。本文提出 TabTrim，利用 SQL 执行生成的金轨迹监督训练剪枝器与验证器，并通过并行搜索探索最优子表。该方法在 WikiTQ 上取得 79.4% 准确率，但依赖 SQL 可表达性，对非结构化表格的泛化能力存疑。

## 研究背景

表格剪枝的核心困境在于如何在移除冗余单元格的同时保留答案关键数据（Answer-critical data）。这一过程涉及两个核心概念：一是剪枝轨迹，即从原始表到最终子表的中间状态序列；二是批评信号，用于判断每一步剪枝是否合理。传统方法将剪枝视为顺序修订过程，每一步基于前一步的反思进行微调，这种线性路径缺乏回溯机制，一旦早期步骤错误删除关键数据，后续步骤无法恢复。

表格剪枝是 TableQA 的前置预处理环节，旨在解决长上下文瓶颈与注意力稀释问题。主流路线分为程序基（Program-based）与 LLM 基（LLM-based）两类：前者通过执行 SQL 或 Python 代码过滤行列，后者利用思维链或多智能体规划进行推理。程序基方法虽能捕捉语法错误，但无法识别语义错误，即程序执行成功却删除了关键数据；LLM 基方法使用 LLM-as-a-Judge 评估冗余性，但模型自我反思易产生主观偏差，导致判断不一致。TabTrim 的切入点在于引入基于 SQL 执行的金轨迹作为客观监督信号，并结合并行搜索机制，将剪枝从顺序修订转化为多路径探索，以解决局部最优与关键数据丢失问题。

## 核心方法

### 方法参照系

表格剪枝的标准流程通常包含子表生成与质量评估两个环节。程序基方法依赖代码执行反馈，LLM 基方法依赖模型自评估。本文的关键差异在于引入外部金轨迹作为监督源，并将单路径顺序修订扩展为多路径并行搜索，通过验证器对中间子表进行损失感知评分，从而在生成与评估之间建立更可靠的闭环。

### 金轨迹构建与剪枝器训练

剪枝器（Pruner）的训练基于从 Text-to-SQL 数据中构建的金轨迹。具体而言，将金 SQL 查询分解为子句级操作序列，按逻辑执行顺序逐步生成中间子表，形成金轨迹 $\tau^+ = (T_0, T_1^+, \dots, T_n^+)$。为提升鲁棒性，还通过修改金操作构建离轨迹负样本 $T_t^-$。剪枝器采用两阶段训练：第一阶段监督微调（SFT），损失函数为：

$$
\mathcal{L}_{SFT}(\theta) = -\sum_{(Q, T_0, T_{t-1}^+, T_t^+) \in D^+} \log P_\theta(T_t^+ | Q, T_0, T_{t-1}^+) - \lambda \sum_{(Q, T_0, T_{t-1}^-, T_t^+) \in D^-} \log P_\theta(T_t^+ | Q, T_0, T_{t-1}^-)
$$

该公式迫使模型既遵循金轨迹，又能从错误状态恢复至正确目标。第二阶段直接偏好优化（DPO），通过对比金子表与错误子表的似然比，强化模型对正确剪枝路径的偏好，减少细微语义错误。

### 损失感知验证器与并行搜索

验证器（Verifier）用于评估中间子表的质量，其评分基于与金轨迹最终子表 $T_n^+$ 的单元格集合重叠度。定义精确率（Precision）与召回率（Recall）：

$$
\text{Precision} = \frac{|E(T_t) \cap E(T_n^+)|}{|E(T_t)|}, \quad \text{Recall} = \frac{|E(T_t) \cap E(T_n^+)|}{|E(T_n^+)|}
$$

损失感知评分函数为：

$$
S(T_t) = \frac{(1 + \alpha^2) \cdot \text{Precision} \cdot \text{Recall}}{(\alpha^2 \cdot \text{Precision}) + \text{Recall}}
$$

其中 $\alpha > 1$ 时强调召回率，即惩罚关键数据丢失。推理阶段采用束搜索（Beam Search），每步生成多个候选子表，由验证器评分后保留 Top-k 候选，最终输出最高分数的子表。这一设计通过并行探索避免单路径顺序修订的局部最优，确保关键数据在剪枝过程中得到保留。

## 实验评估

实验在 WikiTQ、TabFact 和 TableBench 三个基准上进行，基线覆盖直接问答、程序基、LLM 基及批评方法四类。TabTrim-8B 在 WikiTQ 上取得 79.4% 准确率，较最强基线 Table-Critic（72.6%）提升 6.8 个百分点；在 TabFact 上达到 91.2%，在 TableBench 上平均提升 2.9 个百分点。

| 方法 | WikiTQ | TabFact | TableBench (Avg) |
|---|---|---|---|
| Table-Critic | 72.6 | 90.6 | 70.3 |
| TabTrim-4B | 76.8 | 89.4 | 70.8 |
| TabTrim-8B | 79.4 | 91.2 | 73.5 |

消融实验显示，移除 DPO 导致 WikiTQ 准确率下降 1.3 个百分点，移除校正样本下降 4.6 个百分点，完全移除训练则下降 24.7 个百分点，表明过程监督轨迹对剪枝行为至关重要。验证器评分中，使用平衡评分（$\alpha=1$）相比损失感知评分（$\alpha=1.5$）在 WikiTQ 上下降 1.6 个百分点，证实强调召回率对保留关键数据更有效。并行搜索相比顺序修订在 WikiTQ 上提升 6.5 个百分点，验证了多路径探索对避免局部最优的贡献。

评估边界方面，论文未报告置信区间，且所有基线均使用 GPT-4o-mini 作为最终答案生成器，可能引入额外变量。代码未公开，超参数（如 $\alpha=1.5$、束宽 $k=2$）的敏感性分析有限，可复现性依赖附录中的细节。

## 关联研究分析

从问题动机看，TabTrim 与 Table-Critic 同属 LLM 基剪枝路线，但 Table-Critic 依赖 LLM-as-a-Judge 的主观评估，而 TabTrim 引入基于 SQL 执行的金轨迹作为客观监督。这一差异源于 Table-Critic 未解决自我反思偏差问题，而 TabTrim 通过外部验证信号规避了模型自评估的不可靠性。然而，TabTrim 依赖 SQL 可表达性，对于非 SQL 可表达的复杂表格（如含合并单元格、多级表头），其金轨迹构建可能失效，而 Table-Critic 的通用 LLM 评估虽不准确但适用范围更广。

从方法设计看，TabTrim 的并行搜索机制与智能体框架中的多路径探索有相似之处，但 TabTrim 聚焦于剪枝路径而非最终答案生成。相比之下，MATA 等多智能体框架通过调度器协调多种推理路径，适用于复杂多步任务，但协调开销大。TabTrim 的并行搜索仅针对剪枝步骤，计算开销较低，但缺乏对推理过程的动态调整能力。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

TabTrim 旨在解决表格剪枝中关键数据丢失与局部最优问题，其切入点在于利用 SQL 执行生成的金轨迹作为客观监督信号，并通过并行搜索扩展探索空间。该方法在 WikiTQ 上取得 79.4% 准确率，较最强基线提升 6.8 个百分点，验证了金轨迹监督与并行搜索的有效性。然而，其依赖 SQL 可表达性，对非结构化表格的泛化能力受限，且验证器评分对 $\alpha$ 参数的敏感性未充分探讨。当表格结构无法通过 SQL 子句分解时，金轨迹构建是否仍能提供有效监督，论文未给出回答。
