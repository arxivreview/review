# HuggingFace最新推荐论文 ｜CooperBench: Why Coding Agents Cannot be Your Teammates Yet ｜协调诅咒：多智能体代码协作基准

研究机构：美国斯坦福大学

论文原文见 [arXiv](https://arxiv.org/abs/2601.13295)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2601.13295)

> 多智能体系统旨在解决个体能力与集体产出之间的转化效率问题，但现有评估多依赖结构化脚手架，掩盖了底层协调能力的缺失。本文指出当前大语言模型（LLM）在自由协作中存在“协调诅咒”，即双人协作表现显著劣于单人处理同等工作量。通过构建基于真实代码库的可验证协作基准 CooperBench，本文量化了这一缺陷并归因于通信、承诺与预期三大能力缺口。该工作揭示了社会智能而非代码能力是当前瓶颈，但其结论受限于特定框架与任务类型，泛化性存疑。

## 研究背景

当两个智能体异步修改同一代码库时，一方对文件的变更会实时改变另一方的环境状态，这种由策略同步更新引发的非平稳性（Non-stationarity）是协作失败的核心根源。由于智能体仅能观测自身任务需求，无法直接访问对方分支，部分可观测性迫使它们依赖自然语言通信来同步状态。然而，通信本身存在噪声与延迟，若智能体无法准确建模对方的动态意图，信息不对称将导致代码合并冲突，使得协作产出低于个体独立产出的总和。

主流多智能体强化学习（MARL）研究聚焦于博弈论环境下的策略优化，通过奖励函数设计诱导合作均衡，如公平性建模或自适应惩罚机制。然而，这些方法假设智能体具备可微的策略梯度或明确的奖励信号，难以直接迁移至基于离散文本交互的 LLM 协作场景。现有 LLM 多智能体框架如 CAMEL 和 AutoGen 依赖外部编排器或严格工作流来规避协调难题，这导致评估结果反映的是脚手架的有效性而非模型内在的社会智能。本文的切入点在于剥离外部脚手架，在部分可观测且无显式奖励信号的真实软件工程场景中，直接测量 LLM 智能体在自由协作下的表现，从而暴露其基础协调能力的缺失。

## 核心方法

### 方法参照系

本文问题属于多智能体协作评估，但不同于 MARL 中基于奖励最大化的策略学习，其核心差异在于评估对象的离散性与不可微性。传统 MARL 通过梯度更新优化连续策略空间，而 LLM 协作依赖离散文本生成，无法直接应用策略梯度。因此，本文采用基于结果验证的基准测试范式，而非过程优化范式，将协作成功定义为代码合并后的功能正确性，而非累积奖励值。

### 可验证协作评估管道

设计动机在于解决传统多智能体评估中“过程不可观测”与“结果不可验证”的矛盾，即无法区分失败源于代码能力不足还是协调失败。CooperBench 引入双重评估标准：解决方案兼容性与实现正确性。兼容性通过 $git\ merge-file$ 检查两个补丁的结构冲突，若标准合并失败，则调用小模型（Qwen 3 Coder 1.5B）解决表面格式冲突，仅当语义冲突无法解决时判定失败。正确性则在合并后的代码库上运行双方单元测试。该管道将协作成功形式化为：

$$
S_{coop} = \mathbb{1}[\text{Merge}(P_1, P_2) \neq \emptyset] \cdot \mathbb{1}[\text{Test}(P_1 \cup P_2) = \text{Pass}]
$$

其中 $P_1, P_2$ 为两个智能体生成的补丁，$\mathbb{1}[\cdot]$ 为指示函数。这一设计确保了评估结果反映的是智能体间语义对齐的能力，而非代码生成的绝对水平，从而隔离了协调变量。

### 异步通信与任务构造

设计动机在于模拟真实开发中的非平稳性与信息不对称，避免同步回合制带来的理想化假设。任务构造基于真实开源仓库的 Pull Request（PR），每个任务池包含 $n$ 个兼容但潜在冲突的功能，智能体仅能查看自身功能描述。通信通过 SQL 数据库实现异步消息传递，智能体可随时发送自然语言消息，接收方在下一步提示中立即获取。这种机制允许智能体在修改代码的同时进行实时协商，但缺乏强制同步点，迫使智能体主动管理信息流。任务难度通过功能重叠度控制，77.3% 的任务存在真值代码冲突，确保协调是成功的必要条件而非充分条件。

## 实验评估

实验在 CooperBench 上进行，包含 652 个任务，覆盖 Python、TypeScript、Go 和 Rust 四种语言的 12 个开源库。基线包括 Solo（单智能体处理双任务）和 Coop（双智能体协作），对比模型涵盖 GPT-5、Claude 4.5 Sonnet、MiniMax-M2 及两个 Qwen 变体。未对比 MARL 方法，因任务域与奖励机制不兼容；未对比其他 LLM 协作框架，因本文旨在测量模型内在能力而非框架有效性。

| 模型 | Solo 成功率 | Coop 成功率 | 协调差距 |
| :--- | :--- | :--- | :--- |
| GPT-5 | 0.48 | 0.22 | 54.2% |
| Claude 4.5 Sonnet | 0.47 | 0.22 | 53.2% |
| MiniMax-M2 | 0.36 | 0.14 | 61.1% |
| Qwen3-Coder | 0.28 | 0.13 | 53.6% |
| Qwen3-30B | 0.26 | 0.06 | 76.9% |

数据显示，所有模型在 Coop 设置下的成功率均显著低于 Solo 设置，GPT-5 和 Claude 4.5 的协调差距约为 50%，证实了“协调诅咒”的存在。值得注意的是，中等难度任务的协调差距最大，表明简单任务可通过独立工作规避冲突，而复杂任务因信息需求高且通信噪声大，导致协作收益被协调成本抵消。

消融分析显示，通信并非万能解药。成功轨迹中 Plan:Question 比为 2.04，而冲突轨迹为 1.31，表明提问是协调问题的症状而非解药。首轮规划消息将冲突率从 51.5% 降至 29.4%，且具体行号引用（32.6 次 vs 22.5 次）显著降低重叠修改。失败原因中，预期错误（42%）和承诺违背（32%）占比最高，表明智能体缺乏对伙伴状态的动态建模能力，而非单纯的通信带宽不足。

评估边界受限于 OpenHands 框架与 SQL 通信工具，未测试屏幕共享等更高带宽通信方式。代码已开源，但超参数与 GPU 配置未详细披露，复现性依赖特定版本依赖。指标仅关注最终合并结果，未量化中间协调过程的效率或语义稳定性，可能掩盖了长期协作中的协议退化问题。

## 关联研究分析

从问题动机看，本文与 MARL 中的公平合作机制（如 FEN/SOTO）形成鲜明对比。MARL 方法通过修改奖励函数（如广义基尼福利函数）来诱导公平分配，假设智能体能感知他人奖励并据此调整策略。而 CooperBench 中的 LLM 智能体无法直接感知对方奖励，仅能通过自然语言推断意图，这导致公平性无法通过奖励塑形实现，而必须依赖显式协商。这种差异源于任务特性：MARL 环境通常具有可观测的状态空间或共享奖励信号，而代码协作环境具有强部分可观测性且奖励稀疏。LLM 的“社会智能”缺失是否源于缺乏强化学习训练，还是源于预训练数据中缺乏协作语料，论文未给出回答。

从方法设计看，本文与 CAMEL 等对话编程框架存在根本分歧。CAMEL 通过预设角色与对话模板来约束交互结构，从而规避协调难题；CooperBench 则剥离这些脚手架，测试自由形式下的协调能力。这种设计选择揭示了外部协议可能掩盖底层缺陷：CAMEL 的高成功率可能反映模板的有效性，而非模型的协调能力。相比之下，CooperBench 的低成功率暴露了 LLM 在缺乏结构约束时的脆弱性。然而，这种自由形式评估是否过于严苛，以至于忽略了实际应用中脚手架的必要性，论文未进行对比实验验证。

## 总结

本文要解决的核心矛盾是 LLM 个体能力与多智能体协作产出之间的巨大落差，现有方法通过外部脚手架掩盖了这一缺陷，而本文通过剥离脚手架直接测量内在协调能力。CooperBench 通过可验证的代码合并管道，证明了 GPT-5 等前沿模型在协作中成功率仅 25%，比单人处理低约 50%，揭示了通信、承诺与预期三大能力缺口。本文的边界在于其结论依赖于特定的异步通信机制与任务类型，未探索更高带宽通信或结构化协议对协调差距的缓解作用。当引入屏幕共享等实时视觉反馈时，协调诅咒是否会消失，还是仅从语言模态转移至视觉模态，论文未给出回答。
