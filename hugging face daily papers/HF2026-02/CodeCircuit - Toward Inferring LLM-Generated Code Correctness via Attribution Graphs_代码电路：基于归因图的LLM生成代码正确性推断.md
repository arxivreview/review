> 现有代码验证依赖执行测试或LLM裁判，存在成本高、覆盖不全及评估者自身能力受限的问题。本文提出从模型内部计算结构推断代码正确性，无需外部执行或监督。通过构建行级归因图并提取拓扑特征，CodeCircuit在Python、Java和C++上显著优于黑盒与灰盒基线。该方法揭示了代码正确性在模型内部表征中的可解码性，但其对复杂逻辑错误的覆盖能力及实时部署成本仍存疑。

## 研究背景

当LLM生成代码时，其内部残差流中的激活状态包含了算法执行的完整轨迹，但传统评估仅关注最终输出。这种黑盒视角导致无法区分“幸运猜对”与“真正理解”，且执行测试难以覆盖所有边界情况。归因图（Attribution Graph, AG）提供了一种因果线性分解机制，通过替换多层感知机（MLP）为逐层转码器（Per-Layer Transcoder, PLT），将复杂的非线性计算转化为可解释的特征流动网络，使得信息流追踪成为可能。

代码验证领域长期面临外部机制的局限性：执行测试依赖人工设计且稀疏，LLM裁判引入推理开销且受限于评估者自身先验。主流路线如Temperature Scaling或Chain-of-Embedding仅捕捉表面置信度或嵌入一致性，无法触及逻辑错误的根本原因。CodeCircuit的切入点在于假设代码具有刚性拓扑结构（如控制流、变量绑定），模型在生成正确代码时会实例化特定的神经回路，而错误则表现为这些回路中的结构性坍塌。通过解码这些内在电路，框架实现了从输出观察到内部过程审计的范式转移。

## 核心方法

### 方法参照系

本文问题属于代码验证中的机制解释路线，与Zhao et al. (2025)的机制验证范式一致，但关键差异在于将分析粒度从整体推理轨迹细化至代码行级，并引入因果干预以验证信号的功能性。

### 行级归因图构建

通常做法是将整个生成序列视为单一计算单元，但CodeCircuit将代码分解为$N$个离散逻辑步骤$C = \{s_1, s_2, ..., s_N\}$，为每步构建独立的归因图$G_i = (V_i, E_i)$。这一设计解决了长序列中错误定位模糊的问题，使得诊断能精确到具体代码行。PLT通过编码器$W_{enc}^{[l]}$和非线性函数$\sigma$从残差流$x^{[l]}$提取稀疏特征向量$f^{[l]}$，并通过解码器$W_{dec}^{[l]}$重构MLP输出。局部替换模型用误差校正的PLT输出$\hat{m}^{[adj_l]} = \hat{m}^{[l]} + (m^{[l]} - \hat{m}^{[l]})$替代真实MLP输出，其中误差项充当偏置节点，确保下游计算在冻结前向传播下保持线性。

$$
w_{ij} = a_i \cdot v_{out,i}^T J_{ij} v_{in,j}
$$

该公式定义了从源节点$i$到目标节点$j$的边权重，其中$J_{ij}$是冻结残差流变换的雅可比矩阵，stop-gradient应用于所有非线性部分。这确保了归因通过残差流而非直接特征依赖进行，从而捕捉了算法原语间的因果贡献。

### 拓扑特征提取与病理诊断

在获得行级归因图后，CodeCircuit通过结构编码函数$\Phi$将变规模拓扑蒸馏为固定尺寸特征向量$\mathbf{x}_i \in \mathbb{R}^d$。这一设计解决了原始图结构无法直接输入分类器的问题，同时保留了关键的病理信号。特征提取涵盖三个维度：机械组成（如误差-特征影响比$\eta_i$）、全局结构（如图密度$\rho_i$、聚类系数$C_i$）以及信息瓶颈（如介数中心性$C_B(v)$）。

$$
\eta_i = \frac{\sum_{u \in V_{err}} \sum_{v \in V_{feat}} w_{uv}}{\sum_{u \in V_{feat}} \sum_{v \in V_{feat}} w_{uv}}
$$

该公式量化了模型对不可解释组件的依赖程度，高$\eta_i$值表明计算由不透明启发式驱动，暗示逻辑脆弱性。随后，梯度提升决策树（GBDT）分类器$h_\phi$将$\mathbf{x}_i$映射为正确性概率$y_i$，最小化交叉熵损失。GBDT的特征重要性排名进一步实现了结构性缺陷诊断，例如高$\eta_i$结合低介数中心性指向状态维护缺失。

## 实验评估

实验在MBPP数据集上进行，覆盖Python、Java和C++三种语言，基线包括黑盒方法（MaxProb、PPL、Entropy、Temperature Scaling、Energy）和灰盒方法（CoE-R、CoE-C、CoT-Kinetics）。评估指标采用AUROC、AUPR和FPR@95，其中错误步骤被视为正类。

| 方法 | Python AUROC | Java AUROC | C++ AUROC |
|---|---|---|---|
| MaxProb | 51.25 | 56.29 | 54.06 |
| CoT-Kinetics | 51.41 | 56.57 | 53.16 |
| CodeCircuit | 79.89 | 68.06 | 72.21 |

CodeCircuit在Python上AUROC达79.89，较最佳基线51.42提升28.47个百分点，显著优于所有表面启发式方法。跨语言迁移实验中，Java训练的探针在C++上达到59.33 AUROC，仍高于C++特定的MaxProb基线54.06，表明结构信号具有语言无关性。

消融分析显示，随着代码复杂度增加（行数从10增至30），CodeCircuit的AUROC从约80升至近92，而基线保持停滞。这一反直觉发现表明内部激活在长序列中提供了更丰富的病理信号，而非噪声累积。然而，论文未报告计算开销，行级归因图的构建涉及多次前向传播和雅可比计算，实时部署可行性存疑。

评估边界方面，真值标签由GPT-4o生成，可能引入评估者偏差；实验仅覆盖MBPP级别的入门任务，未涉及仓库级复杂工程场景。代码已开源（github.com/bruno686/CodeCircuit），但超参数和GPU配置未在正文中详述，可复现性依赖附录细节。

## 关联研究分析

从问题动机看，CodeCircuit与CoRE同属内部机制分析路线，但CoRE侧重细粒度推理忠实度，而CodeCircuit聚焦拓扑结构完整性。这一差异源于任务特性：代码的刚性拓扑使得结构坍塌比推理偏差更易检测，但论文未验证在模糊逻辑错误（如边界条件遗漏）上，结构信号是否仍优于CoRE的推理追踪。

从方法设计看，CodeCircuit与Gistify均利用执行理解，但Gistify依赖外部执行轨迹，而CodeCircuit纯内部推断。这一选择规避了执行环境复杂性，但牺牲了对运行时错误的捕捉能力。当代码逻辑正确但执行失败（如内存泄漏）时，CodeCircuit的归因图可能无法区分，因为其信号源自生成过程而非执行结果。这种内部-外部信号的互补性，论文未通过混合评估协议进行量化。

## 总结

CodeCircuit旨在解决外部验证成本高且覆盖不全的矛盾，通过假设代码正确性编码于模型内部拓扑，利用行级归因图提取结构特征实现无监督验证。在Python上AUROC 79.89的结果证明了内部信号的有效性，且跨语言迁移能力表明其捕捉了通用逻辑病理。然而，实验仅覆盖MBPP级任务，且未报告计算开销，限制了其在复杂工程场景和实时系统中的适用性。当代码逻辑正确但执行失败时，纯内部信号是否仍能准确区分，论文未给出回答。
