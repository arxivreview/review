# HuggingFace最新推荐论文 ｜Generative Visual Code Mobile World Models ｜基于可渲染代码的移动端GUI世界模型

研究机构：韩国科学技术院

论文原文见 [arXiv](https://arxiv.org/abs/2602.01576)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2602.01576)

> 移动端GUI智能体在训练与推理时面临状态预测精度与视觉保真度的矛盾：文本世界模型丢失像素细节，图像生成模型无法精确渲染文本。本文提出以“可渲染Web代码”作为中间表示，由单一VLM直接生成下一状态代码，而非像素或纯文本。该范式在6个基准上确立了新的精度-参数量帕累托前沿，但代码表示的语义歧义及向下游定位任务的增益转化机制尚存疑。

## 研究背景

移动端GUI智能体依赖世界模型（World Model, WM）预测动作后的界面状态，以辅助策略优化。传统WM将状态抽象为文本，虽便于语言模型处理，却丢弃了图标、排版等细粒度视觉信息，导致基于视觉语言模型（VLM）的策略无法充分利用视觉线索。VIMO（Luo et al., 2025）率先提出视觉WM，通过扩散模型生成下一帧图像，但依赖OCR、掩码、外部VLM等多阶段流水线，计算开销大且权重未开源，难以复现与部署。

现有视觉WM的核心瓶颈在于直接生成像素时，模型难以保证文本的可读性与布局的结构准确性。图像生成模型倾向于学习恒等映射（复制当前状态），而非建模语义状态转移，这在移动GUI高视觉冗余的场景下尤为明显。gWorld的切入点在于利用VLM预训练中蕴含的结构化Web代码先验，将状态预测转化为代码生成任务，从而在保持视觉保真度的同时，利用语言先验确保文本精确渲染。

## 核心方法

### 方法参照系

本文问题属于生成式世界模型范畴，标准流程为学习转移分布 $p_\theta(S_{t+1} | S_t, A_t)$。与通用WM不同，GUI WM需处理高维像素空间，且动作空间包含坐标点击等离散操作。本文的关键差异在于将输出空间从像素或自然语言映射至可执行Web代码，利用代码的结构化特性约束视觉生成。

### 可渲染代码表示

设计动机在于解决图像生成模型在GUI文本渲染上的失效。通常做法是直接回归像素值，但VLM在预训练中已掌握HTML/CSS结构，具备生成精确文本与布局的内在能力。gWorld将下一状态 $S_{t+1}$ 表示为可渲染Web代码 $S_{t+1}^{code}$，训练目标定义为：

$$
\mathcal{L}_{SFT} = -\sum_{t=1}^{T-1} \log p_\theta(R_t, S_{t+1}^{code} | S_t^{image}, A_t)
$$

其中 $R_t$ 为推理轨迹。该公式表明模型需同时预测状态变化的自然语言描述与对应的代码实现，将复杂的视觉预测分解为语义推理与结构生成两个子任务，利用语言先验弥补像素生成的随机性。

### 跨模态数据合成

设计动机在于缺乏现成的代码形式GUI轨迹数据。通常做法是人工标注或合成像素对，但成本高且难以覆盖长尾场景。gWorld提出三步数据合成框架：首先复用离线策略轨迹 $(S_t^{image}, A_t, S_{t+1}^{image})$；其次利用前沿模型 $\pi^*$ 将 $S_{t+1}^{image}$ 重标注为 $S_{t+1}^{code}$；最后通过自由前瞻（Free Look-ahead）生成对齐的推理轨迹 $R_t$。

$$
S_{t+1}^{code} \leftarrow \pi^*(S_{t+1}^{image}, P_{img-to-code}), \quad R_t \leftarrow \pi^*(S_t^{image}, A_t, S_{t+1}^{image}, P_{look-ahead})
$$

此过程将像素监督信号转化为代码监督信号，并通过前瞻机制确保推理轨迹与目标状态的一致性，解决了数据稀缺与推理对齐问题。

## 实验评估

实验在4个分布内（AitW, GUIO, AC, AMEX）和2个分布外（AndroidWorld, KApps）基准上进行，基线包括Qwen3-VL、Llama 4、GLM-4.6V等通用VLM及Emu3.5、Qwen-Image-Edit等图像生成模型。gWorld 32B在IAcc指标上全面领先，例如在MWMBench-AitW上达到79.9%，显著优于GLM-4.6V的74.1%和Llama 4的67.4%。

| 基准 | gWorld 32B (IAcc %) | GLM-4.6V 106B (IAcc %) | Llama 4 402B (IAcc %) | Emu3.5 34B (IAcc %) |
| :--- | :--- | :--- | :--- | :--- |
| MWMBench-AitW | 79.9 | 74.1 | 67.4 | 17.8 |
| MWMBench-GUIO | 87.2 | 79.0 | 65.6 | 37.5 |
| MWMBench-AC | 86.8 | 81.2 | 74.6 | 33.4 |
| MWMBench-AMEX | 86.1 | 82.6 | 69.5 | 21.7 |

消融实验显示，代码表示优于纯图像生成，gWorld 32B的渲染失败率仅为0.6%，而Qwen-Image-Edit为9.4%。数据规模从37K增至240K时，IAcc遵循幂律增长，$R^2 \ge 0.94$，表明数据管道尚未饱和。

评估边界方面，IAcc依赖VLM-as-a-Judge，虽展示了跨裁判一致性，但缺乏与真实环境交互的端到端验证。代码开源，训练使用4节点H200集群，超参数公开，可复现性良好。

## 关联研究分析

从问题动机看，gWorld与SeeClick等定位工作同属GUI智能体核心组件，但任务定义不同：定位是 $S \to A$ 的映射，gWorld是 $S, A \to S'$ 的预测。SeeClick通过大规模截图-文本-坐标数据微调提升定位精度，而gWorld通过预测下一状态为策略提供“想象”能力。两者的差异根源在于任务特性：定位需精确坐标回归，而状态预测需全局布局重构。gWorld未直接对比UI-TARS等定位SOTA，因其输出为代码而非坐标，这暗示了世界模型与定位模块在架构上的解耦。

从方法设计看，gWorld与VIMO同属视觉WM路线，但VIMO依赖多阶段流水线（OCR+Diffusion+VLM），gWorld采用单模型代码生成。VIMO的复杂流水线导致延迟高且权重封闭，而gWorld利用VLM的代码先验简化了流程。这种差异源于对“视觉保真度”的实现路径选择：VIMO通过像素级生成追求视觉相似，gWorld通过代码级生成追求结构准确。gWorld在KApps（韩语界面）上的表现验证了其跨语言泛化能力，但代码表示是否引入新的语义歧义（如CSS渲染差异），论文未深入探讨。

## 总结

本文核心矛盾在于视觉WM的保真度与效率权衡，切入点在于利用VLM的代码先验替代像素生成。gWorld通过可渲染代码表示与跨模态数据合成，在6个基准上确立了新的帕累托前沿，32B模型IAcc最高达87.2%。其边界在于代码表示的渲染误差未量化，且未验证对下游定位任务的直接增益。当支持集增大时，代码生成的边际收益是否递减，论文未给出回答。
