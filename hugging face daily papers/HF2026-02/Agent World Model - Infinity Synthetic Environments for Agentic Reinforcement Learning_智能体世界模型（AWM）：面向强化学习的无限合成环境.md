> 导读 智能体强化学习（RL）训练长期受制于真实环境稀缺、API 不可用及 LLM 模拟环境的状态幻觉问题，导致策略优化缺乏稳定且可扩展的交互底座。现有方案或依赖人工构建的小规模基准，或采用 LLM 模拟状态转换，均无法支撑大规模并行 RL 所需的可靠状态一致性。本文提出智能体世界模型（Agent World Model, AWM），通过代码驱动与 SQL 数据库支持的流水线，从场景描述逆向合成 1,000 个可执行环境。该工作验证了合成环境在分布外基准上的泛化能力，但其奖励机制对 LLM 裁判的依赖及骨干模型规模限制，仍制约着绝对性能上限。

## 研究背景

智能体在复杂任务中需通过工具调用改变环境状态，这一过程可形式化为部分可观测马尔可夫决策过程（POMDP），其中状态空间由数据库定义，动作空间由工具接口界定。传统 LLM 模拟环境通过提示生成状态转换，但存在幻觉与高延迟缺陷，无法提供 RL 训练所需的确定性反馈。为突破此瓶颈，研究界转向代码驱动的环境合成，利用程序逻辑保证状态转换的可靠性，但早期工作多依赖人工任务集或 API 文档，规模受限且缺乏通用性。

环境合成路线的演进揭示了从“任务驱动”到“场景驱动”的范式转变。EnvScaler 等并发工作通过代码生成构建 191 个环境，但依赖预定义任务集，限制了多样性扩展。AWM 的切入点在于摒弃人工先验，从高层场景描述逆向推导任务、数据库模式与工具接口，实现了从“小规模 SFT 环境”到“大规模 RL 环境”的跨越。这一设计直接回应了 RL 训练对高保真、可并行、易重置环境的迫切需求，解决了长程任务中因环境状态不一致导致的信用分配难题。

## 核心方法

### 方法参照系

环境合成通常遵循“任务定义-接口实现-状态管理”流程，但现有方法多将环境视为给定，或通过 LLM 模拟状态转换。AWM 的关键差异在于将环境合成解耦为场景、任务、数据库、接口与验证五个独立阶段，每个阶段引入自动化执行与自纠错机制，确保生成代码的可执行性与状态一致性。

### 逆向合成流水线

AWM 从 100 个种子场景名称出发，利用 LLM 生成 1,000 个唯一场景描述，每个场景包含 10 个 API 可解任务，共计 10,000 个任务。任务生成遵循“API 可解性”与“后认证上下文”原则，排除 UI 依赖操作，聚焦深层功能。数据库模式由任务集逆向推导，LLM 推断实体、属性与关系，生成 SQLite 模式并填充样本数据，确保每个任务从初始状态 $s_0$ 可执行。接口层通过 MCP 协议暴露 Python 工具，工具执行触发数据库读写，实现状态转换函数 $T_{E_i}: S_{E_i} \times A_{E_i} \rightarrow S_{E_i} \times O_{E_i}$。该设计动机在于解决 LLM 模拟环境中状态转换的随机性与不可复现性，通过代码逻辑强制状态一致性，为 RL 提供稳定训练信号。

### 代码增强验证机制

验证模块定义任务特定奖励函数 $R_\tau$，通过比较代理执行前后的数据库状态提取成功信号。鉴于合成环境可能存在状态更新不完整或基础设施故障，AWM 引入代码增强 LLM-as-a-Judge，结合结构化验证信号与轨迹上下文，输出 $\{Completed, Partially Completed, Agent Error, Environment Error\}$ 四类结果。该机制解决了纯代码验证在环境缺陷下的脆弱性，避免误判导致的奖励噪声。公式上，奖励信号 $r_t$ 由状态差异 $\Delta s = s_{t+1} - s_t$ 与 LLM 裁判置信度 $c$ 共同决定，确保奖励既 grounded 于具体证据，又具备容错能力。

## 实验评估

实验在 BFCLv3、$\tau_2$-bench 与 MCP-Universe 三个分布外基准上进行，基线包括 Base（原始 LLM）、Simulator（LLM 模拟环境）与 EnvScaler（并发代码合成方法）。AWM 在 BFCLv3 上显著提升 8B 模型整体得分至 65.94%，超越 Simulator 与 EnvScaler；在 $\tau_2$-bench 上 8B 模型 Pass@1 达 39.39%，一致优于 Simulator；在 MCP-Universe 上取得最佳整体结果，尤其在金融与位置导航任务中增益显著。

| 基准 | 模型 | Base | Simulator | EnvScaler | AWM |
| :--- | :--- | :--- | :--- | :--- | :--- |
| BFCLv3 (Overall) | 8B | 53.83 | 74.06 | 52.53 | 65.94 |
| $\tau_2$-bench (Pass@1) | 8B | 26.44 | 50.72 | 31.30 | 39.39 |
| MCP-Universe (Overall) | 8B | 6.70 | 6.15 | 5.59 | 11.17 |

消融实验表明，代码增强 LLM-as-a-Judge 优于纯 LLM 或纯代码验证，尤其在环境缺陷场景下表现稳健。环境规模分析显示，10 个环境导致性能严重退化，100 个环境带来显著提升，526 个环境继续改善，验证了环境多样性对 RL 的关键作用。

评估边界方面，AWM 未报告计算效率指标（如 Token 消耗、延迟），且骨干模型限于 Qwen3 4B/8B/14B，可能限制绝对性能上限。代码开源（https://github.com/Snowflake-Labs/agent-world-model）确保了可复现性，但合成环境与真实世界的分布距离未量化，OOD 泛化结论需结合更多真实场景验证。

## 关联研究分析

从问题动机看，AWM 与 EnvScaler 同属代码合成路线，但 EnvScaler 依赖人工任务集，规模仅 191 个环境，而 AWM 从场景逆向合成，规模达 1,000 个，且引入数据库状态一致性。这一差异源于任务特性：EnvScaler 侧重 SFT 与 RL 的通用性，而 AWM 专为大规模 RL 设计，需高保真状态转换。AWM 的逆向合成是否导致任务分布与真实世界偏差，论文未给出回答，但 OOD 基准上的泛化结果间接支持其有效性。

从方法设计看，AWM 与 Tool-R0 同用 RL 进行策略优化，但 Tool-R0 侧重工具调用策略优化，依赖合成环境提供训练信号，而 AWM 侧重环境基础设施，提供可执行底座。AWM 的 MCP 接口标准化与 Tool-R0 的工具检索机制形成互补，前者解决“环境可用性”，后者解决“工具选择效率”。AWM 未采用 Tool-R0 的难度奖励机制，可能因环境合成阶段已隐含任务难度梯度，但两者结合是否提升长程任务性能，论文未探索。

## 总结

AWM 解决的核心矛盾是 RL 训练对大规模可靠环境的依赖与环境稀缺之间的冲突。其切入点在于从场景逆向合成代码驱动环境，通过数据库强制状态一致性，避免了 LLM 模拟的幻觉与延迟。方法上，AWM 实现了 1,000 个环境与 10,000 个任务的自动化生成，并在 OOD 基准上验证了泛化能力，8B 模型在 BFCLv3 上达 65.94%，在 MCP-Universe 上达 11.17%。边界在于奖励机制对 LLM 裁判的依赖及骨干模型规模限制，合成环境与真实世界的分布距离未量化。当环境规模从 526 扩展至 1,000 时，RL 性能的边际收益是否递减，论文未给出回答。
