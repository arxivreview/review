# HuggingFace最新推荐论文 ｜Automating Database-Native Function Code Synthesis with LLMs ｜数据库原生函数代码合成

研究机构：上海交通大学、清华大学

作者：Wei Zhou、Xuanhe Zhou、Qikang He 等 7 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.06231)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.06231)

> 数据库内核原生函数（Database Native Function）的自动化合成旨在解决遗留系统迁移中代码重构成本高、人工开发依赖专家知识的瓶颈。现有通用代码智能体因缺乏对数据库内部依赖结构的感知，常出现函数单元遗漏或引用错误，导致合成失败。DBCooker 通过静态依赖图分析函数单元并引入三级渐进验证机制，实现了从声明到可执行内核代码的端到端生成。该系统在三个主流数据库上显著优于通用智能体，但其对复杂跨文件动态链接场景的泛化能力仍受限于静态分析边界。

## 研究背景

数据库原生函数是嵌入数据库内核的底层 C/C++ 代码，其开发涉及函数声明注册、多输入类型对应的函数单元实现以及内部宏与库函数的引用链接。与用户定义函数（UDF）不同，原生函数直接参与查询执行计划，其正确性依赖于对数据库内部数据结构（如 `pg_proc` 目录、内部数据类型）的精确操控。这种紧密耦合的特性使得传统基于提示工程的代码生成方法难以直接适用，因为 LLM 无法仅凭自然语言描述推断出正确的内部引用路径。

随着 PostgreSQL 函数数量从 v11 的 237 个增长至 v18 的 630 个，以及 DuckDB 从 60 个增长至 666 个，数据库厂商面临巨大的函数扩展压力。在 Oracle 到 PostgreSQL 等遗留系统迁移场景中，专有函数实现占据迁移预算的 30%–60%，每 1,000 行代码需耗费 40–80 小时人工重构。现有通用代码智能体（如 Claude Code、Qwen Code）在处理此类任务时，往往陷入低效的文件搜索循环，且无法识别特定输入类型所需的独立函数单元（如 `date_trunc()` 需分别处理 `timestamp` 和 `interval` 类型），导致合成结果编译失败或逻辑错误。

DBCooker 的切入点在于将数据库代码合成视为一个结构化的依赖解析问题，而非单纯的文本生成任务。它通过静态分析预先构建函数单元间的依赖图，将“寻找正确引用”这一模糊过程转化为确定性的图遍历操作，从而弥补了通用 LLM 在数据库内部结构感知上的缺失。

## 核心方法

### 方法参照系

通用代码智能体通常采用“搜索-生成-验证”的迭代循环，依赖 LLM 自主决定文件读取与代码编辑操作。本文问题的关键差异在于：数据库原生函数合成要求精确识别“需实现的新函数单元”与“需引用的已有函数单元”的边界，且引用关系具有严格的类型约束，通用智能体的粗粒度文件搜索无法满足此需求。

### 函数表征与依赖解析

针对通用智能体无法区分新实现单元与引用单元的问题，DBCooker 引入函数表征模块。该模块通过多源声明收集（文档与系统目录）和层级分析，将 SQL 函数分解为独立的函数单元集合。对于每个单元，利用静态依赖图进行上下文感知的跨单元引用分析，并通过类别特定剪枝移除无关引用。这一设计解决了 C1 挑战，即确定哪些单元需要专门编码。其核心逻辑可形式化为：给定函数声明 $S$，识别需实现的单元集合 $\mathcal{F}_{new}$ 和引用单元集合 $\mathcal{F}_{ref}$，其中 $\mathcal{F}_{ref}$ 通过依赖图 $G(V, E)$ 的可达性分析确定，仅保留与 $\mathcal{F}_{new}$ 存在直接调用关系的节点。

### 混合填空与渐进验证

在生成阶段，DBCooker 摒弃了从零开始的代码生成，转而采用基于伪代码计划的混合填空模型。该模型利用概率先验和组件感知机制，将已知的引用单元（如 `PG_GETARG_TEXT_PP`）作为固定锚点，仅对核心逻辑部分进行生成。为解决 C2 挑战（引用复杂且易错），系统设计了三级渐进验证：第一级检查语法，第二级检查标准合规性（如 `pg_proc` 注册条目），第三级由 LLM 引导进行语义验证。验证失败时，错误信息反馈至 LLM 进行迭代修正。这一机制确保了生成代码不仅可编译，还能通过数据库内部的回归测试。其验证过程可表示为：$V(f) = V_{syntax}(f) \land V_{compliance}(f) \land V_{semantic}(f)$，其中 $V_{semantic}$ 依赖于 LLM 对执行轨迹的推理。

## 实验评估

实验在 SQLite、PostgreSQL 和 DuckDB 三个数据库上进行，测试函数涵盖数学、日期、字符串和 JSON 四类，共 348 个函数。基线包括 LLM 直接生成（GPT-5, Claude Opus 4.1）、RAG 增强（CodeRAG）及智能体系统（Claude Code, TRAE）。

| 方法 | SQLite Acc_EXE | PostgreSQL Acc_EXE | DuckDB Acc_EXE |
| :--- | :--- | :--- | :--- |
| Claude Code | 87.1 | 75.0 | 57.14 |
| TRAE | 87.1 | 79.17 | 65.71 |
| DBCooker | 96.77 | 78.62 | 83.67 |

DBCooker 在 SQLite 上以 96.77% 的合规准确率领先，较最强基线 Claude Code 高出 9.67 个百分点；在 DuckDB 上优势更为显著，达到 83.67%，较 Claude Code 提升 26.53 个百分点。这表明领域特定的依赖解析在复杂数据库内核中收益更大。

| 组件移除 | SQLite Acc_RES | PostgreSQL Acc_RES |
| :--- | :--- | :--- |
| 移除三级验证 | 17.33 | 5.52 |
| 移除伪代码计划 | 32.0 | 5.52 |
| DBCooker (完整) | 69.33 | 58.62 |

消融实验显示，移除三级验证导致 PostgreSQL 的结果准确率从 58.62% 骤降至 5.52%，降幅达 53.1 个百分点。这一剧烈波动揭示了 PostgreSQL 内部依赖的复杂性，验证了语义级验证在捕获深层逻辑错误（如负区间处理）中的关键作用。相比之下，SQLite 因结构较简单，移除验证后的性能下降相对平缓。

评估指标采用合规准确率（编译通过）与结果准确率（测试通过）双指标，比单一执行准确率更严格。实验环境为 2 颗 Intel Xeon E5-2678 v3 CPU、256 GB RAM 和 4 块 NVIDIA RTX 4090 Ti GPU，单次合成超时设为 300 秒。代码已开源，但论文未报告不同 LLM 骨干（如 GPT-5 vs Qwen3）对最终性能的独立贡献度，仅展示了组合效果。

## 关联研究分析

从问题动机看，DBCooker 与 GenDB 同属 LLM 驱动数据库内核优化路线，但 GenDB 侧重查询处理代码（如 GPU Kernel）的生成，而 DBCooker 聚焦于函数定义本身的合成。GenDB 利用进化采样优化执行效率，而 DBCooker 依赖静态依赖图保证功能正确性。这种差异源于任务特性：查询优化允许一定的性能波动，而函数合成必须保证语义精确，因此 DBCooker 引入了更严格的合规性验证。

从方法设计看，DBCooker 与 BlendSQL 均涉及 LLM 与数据库系统的混合架构，但 BlendSQL 在查询语言层引入 LLM 函数以处理非结构化数据，属于外部扩展；DBCooker 则深入内核层，生成 C/C++ 代码以扩展原生功能。DBCooker 的静态依赖图分析假设数据库结构在版本间相对稳定，这与 BlendSQL 依赖运行时语义匹配的路径形成对比。当数据库版本迭代导致内部宏或数据结构变更时，静态图的维护成本是否高于动态检索，论文未给出量化回答。

## 总结

DBCooker 解决了数据库原生函数合成中“内部依赖感知缺失”的核心矛盾，通过静态依赖图解析函数单元并引入三级渐进验证，实现了从声明到可执行代码的自动化。实验证明其在 SQLite 和 DuckDB 上的合规准确率分别达到 96.77% 和 83.67%，显著优于通用智能体。然而，其性能高度依赖静态依赖图的准确性，当面对 PostgreSQL 等具有复杂跨文件动态链接机制的数据库时，结果准确率仍低于合规准确率（58.62% vs 78.62%），暴露了语义验证在深层逻辑错误检测上的局限。当数据库内核引入更复杂的运行时动态行为时，静态依赖图能否有效捕获所有必要的引用约束，仍是该方法泛化能力的关键制约。
