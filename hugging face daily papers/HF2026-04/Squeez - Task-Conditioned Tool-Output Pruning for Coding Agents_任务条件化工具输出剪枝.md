# HuggingFace最新推荐论文 ｜Squeez: Task-Conditioned Tool-Output Pruning for Coding Agents ｜任务条件化工具输出剪枝

作者：Ádám Kovács

论文原文见 [arXiv](https://arxiv.org/abs/2604.04979)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.04979)

> 编码智能体在处理文件读取、构建日志等长工具观察时，面临上下文窗口浪费与推理延迟激增的瓶颈。现有提示压缩或文档检索剪枝方法无法处理代码、日志与元数据混合的非结构化工具输出，导致智能体需重复读取大量无关信息。本文提出任务条件化剪枝任务，通过微调轻量级模型提取最小逐字证据块。该方案在自建基准上实现了高召回率与高压缩率，但其对端到端任务解决率的实际增益尚未在真实智能体循环中得到验证。

## 研究背景

编码智能体在解决软件工程问题时，需持续消费由文件读取、`grep` 命中、堆栈跟踪及构建日志组成的观察流。这些观察中仅极小部分 token 对下一步决策有效，但智能体通常被迫重新读取完整输出。这种低效性源于工具输出的混合格式特性：代码片段、非结构化日志与结构化元数据交织在同一工件中，使得基于语义相似度的通用检索或基于文档结构的传统压缩难以直接适用。

工具增强大语言模型（Tool-Augmented LLMs）的研究重心长期聚焦于工具调用策略与强化学习训练，旨在解决“能否正确调用”及“如何规划多步依赖”的问题。然而，随着任务复杂度提升，输入端的效率瓶颈日益凸显。现有提示压缩方法如 LLMLingua 针对长提示进行 token 级移除，而文档级剪枝器如 EXIT 针对检索增强的文本段落进行提取式压缩。这些方法均假设输入为纯文本或结构化文档，未针对编码智能体特有的混合格式工具输出进行优化。SWE-Pruner 虽针对代码智能体，但其聚焦于仓库级代码上下文剪枝，而非单次工具观察的细粒度证据提取。

本文切入点在于将工具输出处理从“通用压缩”细化为“任务条件化提取”。给定一个聚焦查询和单个工具观察，模型需返回智能体下一步应检查的最小逐字证据块。这一任务不要求从单一观察中解决 bug，而是保留相关证据并丢弃其余部分，从而在智能体推理循环中插入一个轻量级预处理步骤，降低后续推理的上下文负担。

## 核心方法

### 任务定义与参照系

本文任务定义为：给定查询 $q$ 和原始工具观察 $o$，输出 $o$ 中一个或多个连续跨度集合 $\mathcal{S}$。与通用提示压缩不同，该任务强调“逐字保留”与“查询条件化”。参照系为提取式问答（Extractive QA），其核心约束是输出必须忠实于源文本，禁止生成式改写。本文的关键差异在于输入并非自然语言文档，而是包含代码、日志、Shell 轨迹的混合格式工具输出，且目标不是生成答案，而是为智能体提供下一步推理所需的证据块。

### 数据构建与标注策略

数据构建采用两阶段教师标注管线，使用 `openai/gpt-oss-120b` 生成查询与标注。首先，教师模型根据背景任务生成聚焦的、工具感知的提取查询，而非完整的 issue 描述；其次，选择回答该查询的最小连续跨度。设计动机在于解决通用摘要方法在工具输出上产生的幻觉问题，通过强制逐字提取确保证据的可追溯性。

$$
\mathcal{L}_{task} = \text{CrossEntropy}(P_{model}(y | q, o), y_{gold})
$$

其中 $y_{gold}$ 为线性化的 XML 包裹提取文本。该损失函数直接优化模型对特定查询下证据块的预测能力，避免了生成式模型在长上下文中的注意力分散。

### 模型微调与部署架构

模型选用 Qwen 3.5 2B，通过 LoRA 进行微调。选择 2B 骨干而非更大模型，是因为该任务旨在学习狭窄的监督提取策略，而非最大化零样本推理深度。小模型在编码智能体栈中可作为轻量级预处理步骤，通过 vLLM 服务或 CLI 过滤器插入，无需修改核心规划逻辑。

$$
\theta_{final} = \theta_{base} + \Delta \theta_{LoRA}
$$

LoRA 适配器合并至基础模型后，以低延迟方式运行。这种架构设计解决了大模型在实时智能体循环中推理延迟过高的问题，使得剪枝操作能在毫秒级完成，不影响智能体的整体响应速度。

## 实验评估

实验在自建基准上进行，该基准包含 11,477 个样本，涵盖 27 种工具类型，其中 618 个测试样本经过人工筛选。基线包括三个零样本生成模型（Qwen 3.5 35B A3B, Kimi K2, Qwen 3.5 2B base）和四个启发式方法（BM25, First-N, Last-N, Random）。

| 模型 | 精确率 | 召回率 | 严格 F1 | 完全匹配 | F1 | 压缩率 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Squeez-2B | 0.80 | 0.86 | 0.79 | 0.49 | 0.80 | 0.92 |
| Qwen 3.5 35B A3B | 0.74 | 0.75 | 0.70 | 0.39 | 0.73 | 0.92 |
| Kimi K2 | 0.61 | 0.53 | 0.53 | 0.30 | 0.68 | 0.94 |
| Qwen 3.5 2B (base) | 0.42 | 0.53 | 0.41 | 0.19 | 0.55 | 0.82 |
| BM25 (10%) | 0.13 | 0.22 | 0.13 | 0.01 | 0.23 | 0.90 |

Squeez-2B 在召回率上以 0.86 领先，比 18 倍大的 Qwen 3.5 35B A3B 高 11 个百分点，比未微调的 2B 基线高 33 个百分点。值得注意的是，Squeez-2B 在显式负样本（即无相关证据的情况）上表现优异，在 59 个负样本测试中，80% 的情况下正确返回空输出，而 Qwen 35B 仅 7%。这表明微调模型学会了工具特定的提取策略，而非通用的指令遵循。启发式基线表现极差，BM25 召回率仅为 0.22，证实了工具输出中相关证据的位置随机性，无法通过词汇重叠或固定位置策略捕捉。

评估边界方面，基准仅评估单次工具观察的剪枝质量，未测量对端到端任务完成率的下游影响。指标使用跨度重叠近似有用性，无法捕捉所有有效的替代剪枝决策。此外，部分工具家族如 `grep` 和 `lint output` 的标注噪声较大，可能影响模型在这些场景下的泛化能力。代码与数据已公开，训练在单张 NVIDIA A100 80GB GPU 上完成，超参数包括学习率 $2 \times 10^{-4}$，最大序列长度 20,000。

## 关联研究分析

从问题动机看，Squeez 与 SWE-Pruner 均针对编码智能体的上下文效率，但 SWE-Pruner 聚焦于仓库级代码上下文，处理的是静态代码库的剪枝，而 Squeez 处理的是动态工具观察的实时提取。SWE-Pruner 的假设是代码上下文中存在大量冗余，可通过静态分析或语义相似度剪枝；Squeez 的假设是工具观察中的相关性高度依赖于当前查询，需动态条件化提取。这一差异源于任务特性：代码库是相对稳定的知识源，而工具输出是瞬时的、查询依赖的状态反馈。

从方法设计看，Squeez 与 EXIT 同属提取式压缩，但 EXIT 针对检索增强的文本段落，假设输入为自然语言文档，使用序列标注或重排序；Squeez 针对混合格式工具输出，使用生成式模型进行跨度提取。EXIT 的局限在于无法处理代码与日志交织的结构，而 Squeez 通过 LoRA 微调小模型，学习了对混合格式的感知能力。然而，Squeez 未采用强化学习，仅依赖监督微调，这限制了其在未见工具类型上的泛化能力，而 EXIT 通过多样化 QA 域训练获得了更强的开箱即用鲁棒性。

## 总结

本文核心矛盾在于编码智能体需处理长工具观察但仅少量信息有效，现有通用压缩方法无法处理混合格式工具输出。Squeez 抓住“任务条件化”与“逐字提取”两个关键点，通过微调 Qwen 3.5 2B 实现最小证据块提取。实验证明其在自建基准上达到 0.86 召回率与 0.92 压缩率，显著优于零样本大模型与启发式基线。其边界在于未验证对端到端任务解决率的增益，且依赖人工标注的跨度，无法捕捉所有有效剪枝决策。当工具类型扩展至未见过的生态系统时，仅靠监督微调的 Squeez 能否保持高召回率，论文未给出回答。
