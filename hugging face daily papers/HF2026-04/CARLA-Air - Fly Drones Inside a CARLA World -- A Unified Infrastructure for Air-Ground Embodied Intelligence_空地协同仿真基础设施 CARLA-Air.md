> 低空经济与具身智能的交叉需求要求仿真平台能同时建模空中与地面智能体，但现有开源工具集在物理一致性或场景丰富度上存在单域局限。传统多进程桥接方案虽能连接异构后端，却引入了不可忽略的同步延迟与渲染管线冗余，无法满足感知与学习对严格时空一致性的要求。本文通过单进程架构将 CARLA 与 AirSim 整合于同一 Unreal Engine 实例中，实现了零修改的 API 兼容与共享物理时钟。该方案填补了空地协同仿真的基础设施空白，但其性能瓶颈是否足以支撑高频闭环控制仍需进一步验证。

## 研究背景

Unreal Engine 4 (UE4) 的架构约束是理解本文设计的关键。UE4 强制规定每个世界实例仅允许存在一个活跃的 GameMode，该模式负责编排场景生命周期、物理更新与 API 接口。当试图在同一场景中运行两个独立的仿真后端时，后加载的 GameMode 会静默覆盖前者的初始化逻辑，导致部分 API 失效。此外，不同仿真器采用异构坐标系：CARLA 继承 UE4 的左手系（X 前、Y 右、Z 上，单位厘米），而 AirSim 采用右手北-东-下 (NED) 系（X 北、Y 东、Z 下，单位米）。这种坐标系的根本差异使得跨模态传感器数据的配准必须依赖显式的几何变换，否则空间推理将产生系统性偏差。

空地协同系统研究面临的核心矛盾在于：地面驾驶仿真器（如 CARLA）提供丰富的交通流与行人交互，但缺乏多旋翼动力学；空中仿真器（如 AirSim）具备物理精确的飞行模型，却缺失真实的城市地面场景。主流解决方案采用基于 ROS 2 或自定义消息传递的多进程桥接架构，如 TranSimHub。然而，这种架构依赖跨进程序列化，导致每帧数据传输时间随传感器数量线性增长，且独立进程无法保证严格的时空同步，这在需要高频状态观测的强化学习或视觉语言导航任务中是致命缺陷。本文的切入点在于利用 UE4 的类继承与组合机制，在引擎层面解决 GameMode 冲突，从而在单一进程内实现物理时钟与渲染管线的共享，从根本上消除跨进程通信开销。

## 核心方法

### 单进程架构与 GameMode 冲突解决

本文方法置于通用仿真器集成框架下，其关键差异在于摒弃了多进程桥接，转而采用引擎内部的类继承与组合策略。通常做法是通过外部中间件连接独立进程，但本文利用 UE4 的架构特性，将 AirSim 的飞行逻辑从 GameMode 解耦为普通 Actor。具体而言，引入 `CARLAAirGameMode` 类，它继承自 CARLA 的 GameMode 基类，占据唯一的 GameMode 槽位，从而自动获取地面仿真子系统（交通、天气、RPC 接口）。AirSim 的飞行 Actor 则在 `BEGINPLAY` 阶段作为普通世界实体被组合（Composition）进场景，而非竞争 GameMode 槽位。这一设计解决了“后加载 GameMode 覆盖前者”的引擎级冲突，使得地面与空中子系统共享同一物理 Tick 与渲染管线，确保了所有传感器视角的严格时空一致性。

### 坐标系映射与传感器配准

在单进程架构基础上，跨模态数据融合依赖于精确的坐标系变换。设 $\mathbf{p} \in \mathbb{R}^3$ 为 UE4 世界系中的点，$\mathbf{o}$ 为共享世界原点，NED 系中的等效位置 $\mathbf{p}_{NED}$ 由下式给出：

$$ \mathbf{p}_{NED} = \mathbf{R} \left( \frac{\mathbf{p} - \mathbf{o}}{100} \right) $$

其中 $\mathbf{R}$ 为旋转矩阵，由于 X 与 Y 轴方向对齐，仅需对 Z 轴进行符号反转以反映坐标系手性改变，除以 100 实现厘米到米的单位换算。该公式的物理含义是：通过刚体变换将异构坐标系的点映射到统一参考系，使得空中 API 返回的无人机姿态与地面 API 返回的车辆航向能够在同一空间框架下进行融合。这一映射消除了因坐标系不一致导致的传感器数据错位，为跨视角感知与联合决策提供了几何基础。

## 实验评估

实验在配备 NVIDIA RTX A4000 (16 GB) 与 AMD Ryzen 7 5800X 的工作站上进行，采用 Town10HD 地图与 Epic 画质。基线对比主要聚焦于架构层面的性能差异，而非算法级 SOTA，因为本文定位为基础设施。主要对比对象为基于桥接的协同仿真方案（如 TranSimHub），评估指标包括帧率、显存占用、CPU 利用率及 API 延迟。

| 配置 | FPS (Harmonic Mean) | VRAM (MiB) | CPU (%) |
| :--- | :--- | :--- | :--- |
| Ground sim only | 28.4 ± 1.2 | 3,821 ± 10 | 31 ± 3 |
| Aerial sim only | 44.7 ± 2.1 | 2,941 ± 8 | 29 ± 3 |
| Moderate joint | 19.8 ± 1.1 | 3,870 ± 13 | 54 ± 5 |
| Traffic surveillance | 20.1 ± 1.8 | 3,874 ± 15 | 61 ± 6 |

数据显示，中等联合配置（3 辆车 + 2 行人 + 1 无人机）的帧率为 19.8 FPS，相比地面基线下降 8.6 FPS（30.3%），其中 6.5 FPS 的开销归因于空中物理引擎，且主要体现为 CPU 利用率从 38% 升至 54%，而显存仅增加 39 MiB。这表明空中动力学计算是 CPU 密集型任务，而非 GPU 显存瓶颈。在 3 小时、357 次 Actor 生灭循环的稳定性测试中，显存回归斜率为 0.49 MiB/cycle，$R^2 = 0.11$，证实无显著内存泄漏；API 错误与崩溃次数均为 0。

| API 调用类型 | 中位延迟 (μs) | IQR (μs) |
| :--- | :--- | :--- |
| Ground: World state snapshot | 320 | 40 |
| Ground: Actor spawn | 1,850 | 210 |
| Aerial: Multirotor state query | 410 | 55 |
| Aerial: Image capture (1 RGB) | 3,200 | 380 |
| Bridge IPC (ref.) | 3,000 | 2,000 |

单进程架构下的 API 延迟显著低于桥接方案。例如，空中图像捕获延迟为 3,200 μs，而桥接方案的状态同步延迟高达 3,000 μs 且 IQR 极大（2,000 μs），表明桥接方案存在严重的通信抖动。CARLA-Air 的每帧数据传输时间保持在 < 0.5 ms，且不随传感器数量线性增长，验证了单进程设计在实时性上的优势。

评估边界方面，本文未提供算法级导航成功率（SR）或路径长度（SPL）等 AVLN 标准指标，仅验证了平台稳定性与低延迟。可复现性良好，代码已开源，但缺乏不同硬件配置下的性能泛化数据。

## 关联研究分析

从问题动机看，本文与 TranSimHub 等桥接方案的根本差异在于对“时空一致性”的实现层级。TranSimHub 依赖多进程消息传递，其同步精度受限于网络栈与序列化开销，导致传感器数据存在时间戳错位，这在视觉语言导航中会导致指令与观测的异步，进而引发决策错误。本文通过共享物理 Tick 从引擎底层保证一致性，消除了这一误差源。然而，这种单进程设计在超大规模场景（如数百个 Agent）下是否会导致 CPU 调度瓶颈，论文未给出压力测试数据，这限制了其在大规模多智能体强化学习中的适用性。

从方法设计看，本文与 AirSim 的关系是继承与扩展，而非替代。AirSim 上游开发已归档，本文通过将其飞行 Actor 嵌入 CARLA 框架，为 AirSim 生态提供了可持续的演进路径。与 Isaac Lab 等具身智能平台相比，本文更侧重场景真实感（交通流、行人）而非并行训练效率。Isaac Lab 利用 GPU 加速实现数千个并行环境，适合大规模策略搜索；而 CARLA-Air 的单进程架构限制了并行度，更适合需要高保真物理交互与跨模态数据配准的任务。这种取舍反映了“场景真实性”与“训练吞吐量”之间的权衡，本文选择了前者，以支持对物理一致性的严格需求。

## 总结

本文解决的核心矛盾是空地协同仿真中物理一致性与基础设施可用性的缺失。现有桥接方案因跨进程通信导致同步延迟与渲染冗余，无法满足具身智能对严格时空一致性的要求；本文凭借 UE4 单进程架构与“继承+组合”的 GameMode 解决方案，实现了零修改的 API 兼容与共享物理时钟。实验证明，该架构在中等负载下维持 19.8 FPS 的帧率，API 延迟稳定在毫秒级，且无内存泄漏。然而，其边界在于单进程架构对 CPU 资源的占用较高，且缺乏算法级导航性能的验证。当场景规模扩大至数百个 Agent 时，单进程 CPU 调度是否成为瓶颈，以及 19.8 FPS 是否足以支撑 10 Hz 以上的高频 VLA 控制，论文未给出回答。
