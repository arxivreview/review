研究机构：浙江大学

作者：Yi Zhong、Buqiang Xu、Yijun Wang 等 7 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.19667)

> 工业级智能体部署依赖显式工作流编排，但人工设计成本高且难以适应需求变更。现有自动化方法多聚焦拓扑搜索优化，缺乏对“自然语言指令到可执行视觉工作流”端到端生成保真度的系统性评估。本文构建了包含多轮交互与真实平台约束的基准，并验证了当前大语言模型在格式合规与执行成功之间的巨大鸿沟。该基准揭示了生成式工作流在工业落地中的核心瓶颈，但受限于节点类型与任务复杂度，其结论向更复杂场景的泛化能力存疑。

## 研究背景

当开发者试图将自然语言需求转化为 Dify 或 Coze 等平台的可视化工作流时，面临的核心困境是控制流推断与工具调用的精确匹配。这一过程要求模型不仅理解语义，还需生成符合特定 YAML 格式的有向无环图（DAG）结构。由于工作流执行具有强依赖性与状态传递性，任何节点参数或连接关系的微小错误都会导致整个流程失效，这使得“格式正确”与“执行成功”成为两个截然不同的评估维度。

当前 LLM 智能体工作流编排研究主要沿两条路线演进：一是基于强化学习或蒙特卡洛树搜索的拓扑自动优化，如 GPTSwarm 和 AFlow，旨在寻找最优代理连接结构；二是基于提示工程的静态模板生成。前者虽能提升任务成功率，但计算开销大且难以直接映射到工业平台的可视化编辑界面；后者虽部署简单，但缺乏对动态需求变更的适应能力。据领域综述，超过 70% 的真实部署依赖显式工作流而非权重微调，然而现有基准如 GSM8K 或 GAIA 仅评估任务解决能力，未考察工作流结构本身的合法性与可部署性。

Chat2Workflow 的切入点在于填补“自然语言指令”与“可执行平台工作流”之间的评估空白。它不追求拓扑的最优性，而是聚焦于生成工作流的格式合规性、变量一致性以及在多轮需求变更下的稳定性。通过引入 Pass Rate（格式通过率）与 Resolve Rate（解决率）的双阶段评估协议，该基准将工作流生成问题从“能否解题”转化为“能否生成一个可被平台直接导入并正确执行的工程制品”，从而更贴近工业级自动化的实际需求。

## 核心方法

### 方法参照系

本文问题属于工作流自动优化中的“生成式”路线，但与传统基于代码或图搜索的方法存在关键差异。传统方法如 AFlow 在代码表示空间中搜索最优结构，目标是最大化任务成功率；而本文任务要求模型直接输出符合特定平台规范（如 Dify 的 YAML 格式）的 JSON 结构，且必须通过多轮对话维持结构一致性。其核心挑战不在于寻找最优拓扑，而在于在强格式约束下实现自然语言到结构化代码的精确翻译。

### 两阶段渐进式评估协议

为区分“格式合法”与“执行有效”，本文设计了 Pass Rate 与 Resolve Rate 两个指标。Pass Rate 衡量生成 JSON 与思维链（CoT）序列及参考变量的一致性，并验证其能否转换为有效 YAML。该过程包含格式检查、转换导入、变量一致性及逻辑有效性四步验证。其计算公式为：

$$
\%Pas. = \frac{N_{success\_subtask}}{N_{total\_subtask}} \times 100\%
$$

其中 $N_{success\_subtask}$ 为通过所有格式检查的子任务数。这一设计动机在于揭示现有模型常陷入“格式正确但逻辑错误”的陷阱，即生成的工作流虽能解析，但无法正确执行。

Resolve Rate 则进一步验证工作流在平台上的实际执行结果是否满足指令要求。该指标通过执行工作流并比对输出与参考答案，计算满足所有指定要求的测试用例比例：

$$
\%Res. = \frac{N_{success\_case}}{N_{total\_case}} \times 100\%
$$

两阶段分离使得研究者能精确定位失败原因：是结构生成错误（Pass Rate 低）还是逻辑推理或工具调用错误（Pass Rate 高但 Resolve Rate 低）。这种评估协议比单一的任务成功率指标更能反映工业部署中的真实瓶颈。

### 错误驱动的智能体基线

针对多轮交互中上下文衰减与结构错误累积问题，本文提出基于 OpenCode 框架的错误驱动智能体基线。该机制在零样本提示基础上引入结构化技能（SKILL）范式，动态提取前序工作流的变量摘要作为补充上下文。核心创新在于构建了一个包含 5 次重试机制的执行循环，当工作流执行失败时，触发自动修复模块针对四类常见错误（代码围栏畸形、JSON 解码失败、拓扑排序违规、节点选择不一致）进行定向修正。这一设计解决了静态生成方法在需求变更时无法自我纠错的问题，通过闭环反馈提升了工作流的鲁棒性。

## 实验评估

实验在 Dify 1.9.2 平台上进行，覆盖 15 个主流大语言模型，包括 GPT-5.1/5.2、Claude-Sonnet-4.5、Gemini-3-Pro-Preview 及 Qwen-3 系列等。基线审计显示，本文仅对比了通用 LLM 的零样本与智能体增强性能，未纳入领域内专用的工作流优化方法如 DAAO 或 AFlow，这限制了其在“优化算法”维度的横向对比能力。

| 模型 | 平均 Pass Rate (%) | 平均 Resolve Rate (%) |
| :--- | :--- | :--- |
| Gemini-3-Pro-Preview | 80.17 | 71.59 |
| GLM-4.7 | 69.20 | 55.98 |
| GPT-5.1 | 47.26 | 39.38 |
| Qwen-3-235B-A22B | 40.93 | 27.71 |

Gemini-3-Pro-Preview 以 71.59% 的 Resolve Rate 领先，但其 Pass Rate 与 Resolve Rate 之间仍存在约 8.58% 的差距，表明即使最强模型也有近 10% 的工作流虽格式合法但执行失败。GLM-4.7 在 Developer 场景下 Resolve Rate 仅为 29.17%，显著低于其 41.67% 的 Pass Rate，揭示了复杂编程任务中格式合规与逻辑正确的巨大鸿沟。

消融实验显示，模型规模与工作流生成能力正相关，Qwen-3 系列从 8B 到 235B 的 Resolve Rate 从 6.89% 提升至 27.71%。然而，后训练对格式合规的提升并不必然转化为执行能力的提升，例如 GLM-4.6 的 Pass Rate（45.83%）高于 GLM-4.7（41.67%），但 Resolve Rate 却大幅落后（6.94% vs 29.17%）。此外，思考型模型（如 Kimi-K2-Thinking）在所有领域均优于指令型模型（Kimi-K2-Instruct），表明推理机制对复杂结构生成的关键作用。

评估边界方面，本文仅使用 20 种高频节点，未覆盖工业场景中更复杂的自定义工具；测试用例主要来源于公开数据集与合成数据，可能低估真实业务逻辑的复杂性。代码已开源，但智能体基线的超参数（如重试次数、修复模块触发条件）未详细披露，限制了完全复现。

## 关联研究分析

从问题动机看，Chat2Workflow 与 RobustFlow 均关注工作流的鲁棒性，但侧重点截然不同。RobustFlow 通过同义变换与噪声注入测试工作流生成对查询变异的稳定性，关注的是“输入扰动下的结构保持”；而 Chat2Workflow 聚焦于“多轮需求变更下的结构演进”，即用户明确修改需求后，模型能否正确更新工作流。这一差异源于任务场景的不同：RobustFlow 模拟的是用户表达的不确定性，而 Chat2Workflow 模拟的是业务逻辑的动态迭代。前者揭示的是模型的语义鲁棒性缺陷，后者暴露的是模型的长程上下文跟踪与结构一致性维护能力不足。

从方法设计看，本文与 DAAO 在“查询自适应”上存在表面相似性，但机制本质不同。DAAO 利用变分自编码器估计查询难度，动态分配代理算子子集与模型路由，属于“运行时资源调度”；而 Chat2Workflow 的自适应体现在“生成时的结构修订”，即根据历史对话调整 JSON 结构。DAAO 假设工作流结构是固定的，仅调整执行路径；本文则假设工作流结构本身是可变对象，需要重新生成或局部修改。这种差异暗示，若将 DAAO 的难度估计机制引入 Chat2Workflow，可能有助于在需求变更时决定是“局部修补”还是“整体重构”，从而降低多轮交互中的错误累积风险。

## 总结

Chat2Workflow 解决了工业级工作流自动化中“自然语言指令到可执行视觉工作流”的评估缺失问题。其切入点在于将工作流生成从“任务解决”视角转向“工程制品生成”视角，通过 Pass Rate 与 Resolve Rate 的双阶段协议量化了格式合规与执行成功之间的差距。实验证明，即使是最先进的 Gemini-3-Pro-Preview，其 Resolve Rate 也仅为 71.59%，且 Pass Rate 与 Resolve Rate 之间存在显著鸿沟，表明当前 LLM 在强格式约束下的结构化生成能力仍远未达到工业部署标准。本文的边界在于仅覆盖 20 种节点与 27 个任务，未涉及更复杂的自定义工具与跨平台迁移。当节点类型扩展至数百种社区插件时，模型对长尾工具接口的理解与调用准确率是否会成为新的瓶颈，论文未给出回答。
