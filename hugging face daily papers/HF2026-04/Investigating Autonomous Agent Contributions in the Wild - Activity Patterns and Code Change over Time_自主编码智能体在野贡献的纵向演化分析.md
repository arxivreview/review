# HuggingFace最新推荐论文 ｜Investigating Autonomous Agent Contributions in the Wild: Activity Patterns and Code Change over Time ｜自主编码智能体在野贡献的纵向演化分析

研究机构：荷兰代尔夫特理工大学、美国加州大学戴维斯分校

作者：Razvan Mihai Popescu、David Gros、Andrei Botocan 等 6 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.00917)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.00917)

> 该方向旨在解决自主编码智能体（Autonomous Coding Agents）在真实开源项目中产生的代码长期稳定性与可维护性评估缺失问题。现有静态基准（如SWE-bench）仅能验证孤立任务的功能正确性，无法捕捉代码在后续维护周期中的存活与重构轨迹，导致对智能体真实工程价值的判断存在系统性偏差。本文通过挖掘11万条真实Pull Request（PR）及其后续提交，构建了基于代码行存活率与变更率的纵向评估框架。这一工作填补了从“即时生成能力”到“长期维护成本”的实证空白，但其结论受限于低星仓库的高占比样本，对高复杂度遗留系统的适用性存疑。

## 研究背景

当开发者将代码生成任务委托给OpenAI Codex或GitHub Copilot等自主智能体时，传统的质量保障流程面临失效风险。这是因为智能体生成的代码往往缺乏对仓库全局架构的深层理解，导致其在功能正确性之外，伴随高复杂度的代码异味与架构不一致性。这种“生成-维护”脱节使得代码在合并后迅速发生重构或废弃，即代码变更率（Code Churn）异常升高，而传统的接受率或短期用户满意度指标无法量化这一长期维护负担。

软件工程领域长期依赖HumanEval、MBPP等静态基准评估大语言模型（LLM）的代码生成能力，但这些基准存在数据污染、真值错误及任务饱和等问题，且仅关注单次生成的正确性，忽略了代码在真实项目生命周期中的演化。随着智能体从辅助补全转向自主执行多步骤任务，其贡献已占GitHub公共PR的10%，但现有研究多局限于高星仓库或单一智能体的小样本分析，缺乏对大规模、多智能体、全仓库分布的纵向追踪。

本文切入点在于利用智能体在GitHub上留下的独特签名（如分支前缀、作者水印），构建一个覆盖5个主流智能体与人类开发者的对照数据集，通过追踪PR合并后代码行的存活状态，量化智能体代码与人类代码在长期维护成本上的差异，从而揭示智能体在真实工程环境中的实际影响。

## 核心方法

### 基于签名过滤的大规模数据策展

本文方法参照系为基于GitHub API的仓库挖掘（Mining Software Repositories, MSR）流程，但关键差异在于针对智能体特有的身份标识进行精细化过滤。常规MSR研究难以区分人类与AI贡献，而本文利用智能体操作环境的确定性特征，通过分支命名规范（如`head:codex/`）、Bot作者标识（如`author:devin-ai-integration[bot]`）及PR描述水印（如`Co-Authored-By: Claude`）三类信号，精准分离智能体PR与人类PR。这一设计解决了此前研究中因身份混淆导致的归因错误，确保了后续演化分析的纯净性。

### 提交级代码存活与变更度量

在获取PR数据后，本文引入提交级（Commit-level）的纵向度量，以捕捉代码在时间维度上的稳定性。对于每个种子提交（Seed Commit），提取其新增代码行，并在定义的时间窗口内追踪这些行在后续提交中的状态。存活率（Survival Rate）定义为在目标提交中内容未发生变化的新增行比例，反映代码的持久性；变更率（Churn Rate）定义为在目标提交中新增或发生语法差异的行数占初始变更总行数的比例，反映代码的重构强度。

$$
\text{Survival Rate} = \frac{\text{Number of surviving lines in target commit}}{\text{Total added lines in seed commit}}
$$

该公式直观地量化了智能体生成的代码在后续开发中未被修改或移除的比例，高存活率意味着代码贡献稳定，低存活率则暗示代码需频繁修正。

$$
\text{Churn Rate} = \frac{\text{Churned LOC (added or modified in target commit)}}{\text{Total LOC (changed in seed commit)}}
$$

变更率公式聚焦于代码行的“流动”程度，高变更率直接关联到维护成本的增加，是衡量代码可维护性的关键负面指标。

### 分层抽样与活跃度均衡

针对智能体PR数量分布极不均衡的问题（如Codex在采样期内产生约110万条PR，而Jules仅数千条），本文采用分层时间间隔抽样策略。对于高活跃度智能体，使用较短的时间间隔（如1小时）进行密集采样；对于低活跃度智能体，使用较长间隔（如5小时）或全量采集。同时，设定每日采样上限并动态调整，以防止高活跃度智能体主导数据集。这一设计动机在于消除因智能体发布时间和用户基数差异带来的采样偏差，确保不同智能体在数据集中的代表性均衡，从而支持跨智能体的公平对比。

## 实验评估

实验设置基于2025年6月至8月的GitHub公共数据，构建了包含111,969条PR的数据集，涵盖OpenAI Codex、Claude Code、GitHub Copilot、Google Jules、Devin及人类开发者。基线审计方面，本文以人类PR作为主要对照基线，但未与SWE-bench等静态基准进行直接数值对比，也未包含Cursor、Cosine等其他新兴智能体的详细对比，这限制了结论的普适性。

| Google Jules | 18,468 | 36,936 | 41,032 | 5,700 | 3,249 | 2,185 | 138,610 |

数据显示，智能体PR在评论与审查数量上普遍低于人类PR，例如Codex的平均评论数远低于人类，表明智能体代码可能较少引发社区讨论或审查。在仓库分布上，40.5%的人类PR来自0星仓库，而Codex和Jules约75%的PR来自0星仓库，显示智能体活动高度集中于低知名度项目。

评估边界方面，本文未报告置信区间，且纵向追踪的时间窗口未明确量化（仅提及“defined time window”），这可能影响Churn率计算的稳定性。此外，数据集未包含代码复杂度（如圈复杂度）或架构一致性指标，仅从行级语法变化评估质量，可能遗漏结构性缺陷。可复现性上，论文提供了HuggingFace数据集链接，但未公开完整的采样脚本与过滤规则细节，限制了第三方复现的精确度。

## 关联研究分析

从问题动机看，本文与AIDev-Pop等前置工作同属“智能体在野行为”研究路线，但关键差异在于评估维度的深化。AIDev-Pop聚焦于PR的解决时间、接受率等短期协作指标，而本文引入Survival Rate和Churn Rate，将评估视角从“合并瞬间”延伸至“合并后数月”。这一差异源于对“代码质量”定义的扩展：前者视质量为“被接受”，后者视质量为“被保留”。这种转变揭示了智能体代码在短期效率与长期稳定性之间的权衡，是静态基准无法捕捉的盲区。

从方法设计看，本文与SWE-bench等静态基准形成互补而非竞争关系。SWE-bench通过隔离环境测试智能体解决特定Issue的能力，强调功能正确性；本文则通过真实仓库的纵向数据，揭示智能体代码在复杂依赖环境中的演化轨迹。两者的根本差异在于任务特性：SWE-bench假设代码是静态交付物，而本文视代码为动态演化实体。这种差异暗示，智能体在SWE-bench上的高分可能无法直接转化为真实项目中的低维护成本，因为后者涉及更复杂的上下文依赖与团队协作。

## 总结

本文核心矛盾在于自主编码智能体的快速生成能力与传统软件工程对代码长期可维护性的刚性需求之间的冲突。现有静态基准无法评估代码在真实项目中的演化，而本文凭借对GitHub大规模PR数据的挖掘与智能体签名的精准过滤，构建了首个纵向评估框架。实验表明，智能体代码的Churn率显著高于人类代码，且活动高度集中于0星仓库，证实了智能体在低复杂度环境中的活跃性与在高复杂度环境中的潜在维护负担。然而，样本中0星仓库的高占比（如Codex 75%）限制了结论向高星、高复杂度遗留系统的推广。当仓库星数增加、架构依赖加深时，智能体代码的Churn率是否会因缺乏全局上下文而进一步恶化，还是因智能体能力的提升而收敛，本文未给出回答。
