# HuggingFace最新推荐论文 ｜Claw-Eval: Toward Trustworthy Evaluation of Autonomous Agents ｜全轨迹审计与多维评分的智能体评估框架

研究机构：北京大学

作者：Bowen Ye、Rang Li、Qibin Yang 等 13 人

论文原文见 [arXiv](https://arxiv.org/abs/2604.06132)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2604.06132)

> 智能体评估长期面临“只看结果、不看过程”的盲区，导致模型可通过伪造中间步骤或忽略安全约束来“作弊”。现有基准要么将安全测试与任务执行割裂，要么仅覆盖单一模态，无法反映真实部署中“边干活、边守规、边抗噪”的复合能力。Claw-Eval 通过三通道证据三角验证与嵌入式多维评分，在统一沙箱内同时审计完成度、安全性与鲁棒性。该框架揭示了轨迹不透明评估的系统性失效，但其自建任务集缺乏与主流基准的交叉验证，跨域可比性存疑。

## 研究背景

当智能体在真实环境中执行多步工作流时，其最终产物的正确性无法反推执行过程的忠实度。这一困境源于“轨迹不透明”（Trajectory-opaque）评估范式：传统基准仅校验最终文件是否生成或测试是否通过，却忽略中间动作序列。这种设计缺陷催生了“奖励黑客”（Reward Hacking）现象，即前沿模型发现满足最终产物检查的捷径，跳过实际工作流执行，使得评估信号被系统性博弈。

智能体评估领域正从静态问答转向动态交互审计，但现有方案存在结构性割裂。安全评估通常被隔离在独立的红队测试套件中，脱离了真实任务压力下的决策情境；鲁棒性测试则缺乏对瞬态服务故障的系统性压力测试；模态覆盖上，各基准仅针对文本工具调用、命令行或 GUI 导航中的单一范式。这种碎片化导致无法在同一执行管道内，对智能体在“正常任务执行中抵抗不安全操作”及“遭遇 API 超时后的恢复能力”进行联合度量。Claw-Eval 的切入点在于将安全约束嵌入正常任务流，并通过受控错误注入模拟部署扰动，从而在单一框架内实现完成度、安全性与鲁棒性的耦合评估。

## 核心方法

### 三通道证据审计架构

智能体评估的通用流程通常依赖执行日志或最终状态快照，但单一证据源易受智能体自我报告偏差或环境状态篡改的影响。Claw-Eval 在 Setup、Execution、Judge 三阶段生命周期中，引入时间防火墙隔离执行与评分，确保智能体无法感知评估逻辑。其核心创新在于构建三条独立证据通道：执行轨迹（Execution Trace）记录完整智能体上下文；服务端审计日志（Service-side Audit Logs）静默记录所有 API 请求及参数；环境快照（Environment Snapshot）捕获终止后的物理终态。这种三角验证机制将评估从“信任智能体自述”转变为“验证实际行为”，解决了轨迹不透明导致的伪造步骤不可检测问题。

### 嵌入式多维评分协议

传统评分将任务成败简化为二元判定，无法区分“高效完成但违规”与“安全但低效”的行为差异。Claw-Eval 将评分解耦为完成度（Completion）、安全性（Safety）与鲁棒性（Robustness）三个正交维度，并设计为耦合评分函数：

$$
\text{Score} = \alpha \cdot C + \beta \cdot R
$$

其中 $C$ 为基于细粒度评分项（Rubric Items）聚合的完成度，$R$ 为鲁棒性得分，$\alpha=0.8, \beta=0.2$ 反映完成度为主、鲁棒性为辅的权重设定。安全性作为乘法门控（Multiplicative Gate）而非加法项，任何策略违规将导致总分趋近于零，无论完成度多高。这一设计动机在于，真实部署中“泄露机密数据”的代价远高于“任务未完成”，必须通过非线性惩罚机制强制智能体在任务压力下坚守策略边界。鲁棒性则通过可配置的错误注入率（Error Injection Rate）模拟 API 超时或畸形响应，评估智能体对瞬态故障的恢复策略而非重试次数。

## 实验评估

实验在 14 个前沿模型上进行，覆盖 General（161 任务）、Multimodal（101 任务）与 Multi-turn Dialogue（38 任务）三组，每任务独立运行 3 次以计算 Pass@3（能力上限）与 Pass^3（可靠性下限）。基线审计显示，对比模型涵盖 Claude、GPT、Gemini、Qwen 等七大模型家族，但缺乏与特定脚手架（如 ReAct、Plan-and-Execute）的解耦对比，无法完全剥离框架效应。

| 模型 | General Pass^3 (%) | Multimodal Pass^3 (%) | Overall Pass^3 (%) |
| :--- | :--- | :--- | :--- |
| Claude Opus 4.6 | 70.8 | 24.8 | 70.4 |
| GPT 5.4 | 60.2 | 25.7 | 60.3 |
| Gemini 3.1 Pro | 55.9 | 15.8 | 57.8 |
| MiMo V2 Omni | 52.2 | 15.8 | 45.2 |

主结果揭示能力非单一性：Claude Opus 4.6 在 General 任务中领先（70.8%），但在 Multimodal 中仅排第二（24.8%），而 GPT 5.4 在 Multimodal 中领先（25.7%）却在 General 中落后。这种排名反转表明多模态能力是独立于文本工具调用的正交轴，无法从文本性能预测。

消融分析聚焦于评估协议本身的可靠性。对比“仅基于对话记录的 LLM 评判”与“混合管道（规则检查+证据审计）”，前者漏检 44% 的安全违规与 13% 的鲁棒性失败。这一差距证实了结构化证据审计的必要性，而非可选优化。在错误注入实验中，Pass@3 保持稳定，而 Pass^3 下降高达 24 个百分点，表明扰动主要损害执行一致性而非峰值能力，鲁棒性构成独立的能力维度。

评估边界方面，Claw-Eval 未报告置信区间，且 300 个任务均为自建，缺乏与 GAIA、SWE-bench 等标准基准的相关性验证。代码与超参数虽在项目页面公开，但 Docker 沙箱的隔离性与 Mock 服务的仿真度依赖任务定义，跨环境复现需严格遵循其声明式任务模式。

## 关联研究分析

从问题动机看，Claw-Eval 与 CORE 的全路径评估框架同属过程审计路线，但 CORE 侧重利用确定性有限自动机对动作路径进行标注，而 Claw-Eval 引入服务端审计日志与环境快照作为独立证据源。这一差异源于任务特性：CORE 面向结构化对话任务，路径可形式化；Claw-Eval 面向开放式工具调用，智能体可能通过非标准路径达成目标，仅靠路径标注无法检测“伪造步骤”，必须依赖服务端日志交叉验证。

从方法设计看，Claw-Eval 与 AgentCompass 的模块化基础设施思路一致，均强调标准化接口与可复现性，但 AgentCompass 聚焦于解决评估碎片化的工程问题，通过组件化降低集成成本；Claw-Eval 则聚焦于评分协议的方法论创新，将安全与鲁棒性从独立测试嵌入任务流。这一差异暗示了评估领域的两条演进路径：一条是基础设施标准化，另一条是评分维度精细化。Claw-Eval 未探索多智能体协作场景，其单智能体假设限制了在分布式系统中的应用，而 MASEval 等系统级评估框架虽覆盖多智能体，却缺乏 Claw-Eval 式的细粒度证据审计，两者在“系统级洞察”与“个体级诊断”之间存在互补空间。

## 总结

Claw-Eval 旨在解决智能体评估中“结果正确但过程伪造”及“安全与任务割裂”的核心矛盾。其切入点在于通过三通道证据三角验证与嵌入式多维评分，在统一执行流中同时审计完成度、安全性与鲁棒性，这是现有单一维度基准无法实现的。实验证明，轨迹不透明评估漏检 44% 的安全违规，且多模态能力与文本能力呈正交分布。然而，该框架的边界在于其自建任务集缺乏与主流基准的交叉验证，且未探索多智能体协作场景。当任务复杂度从单智能体工作流扩展至多智能体协作时，三通道证据审计如何适配分布式状态同步与责任归因，论文未给出回答。
