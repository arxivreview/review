# HuggingFace最新推荐论文 ｜GUI vs. CLI: Execution Bottlenecks in Screen-Only and Skill-Mediated Computer-Use Agents ｜GUI与CLI执行瓶颈的受控对比基准

研究机构：美国纽约大学、新加坡南洋理工大学

作者：Xiao Zhou、Siyue Zhang、Yilun Zhao 等 7 人

论文原文见 [arXiv](https://arxiv.org/abs/2606.24551)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2606.24551)

> 计算机使用智能体（Computer-Use Agent）可通过图形界面（GUI）或程序化命令行（CLI）执行桌面任务，但现有评估混杂了任务、状态与验证器差异，无法隔离交互模态本身的影响。本文通过构建440个任务的匹配执行层基准，固定目标、初始状态与验证器，强制各模态使用原生动作空间，以量化模态对性能的真实贡献。该设计揭示了CLI性能缺口主要源于技能覆盖度不足而非模型能力，为混合模态系统的设计提供了诊断依据，但受限于单一模态约束，未评估真实部署中混合策略的上限。

## 研究背景

当智能体执行“在Audacity中重命名三个音轨”这类任务时，GUI路径依赖截图定位与鼠标点击，CLI路径则调用预定义的技能接口。两种路径的差异不仅在于操作方式，更在于应用能力的表示形式：GUI将工作流嵌入可见界面，CLI则将能力封装为离散命令。这种表示差异导致现有基准无法公平对比——GUI基准（如OSWorld）与程序化基准（如CLI-Anything）同时改变应用、初始状态与验证器，使得性能差异无法归因于模态本身。

领域共识认为视觉输入具有跨平台泛化优势，但这一结论基于单一模态评估，未考虑程序化接口在结构化任务上的潜力。主流GUI Agent研究聚焦于视觉定位与长程任务错误累积，而CLI Agent研究则关注技能层的质量与覆盖度，两者缺乏受控对比。本文的切入点在于：通过固定任务目标、初始状态与最终状态验证器，仅改变动作空间（GUI屏幕操作 vs CLI技能调用），从而隔离模态效应，并诊断技能覆盖度对CLI性能的贡献。

## 核心方法

### 匹配执行层协议

现有基准评估GUI与CLI时，通常允许混合动作或改变任务设置，导致模态效应被任务差异掩盖。本文的关键差异在于强制“模态原生动作空间”：GUI Agent仅能通过截图与屏幕操作（点击、拖拽、输入）交互，禁止代码执行或文件直接修改；CLI Agent仅能调用CLI-Anything技能层，禁止直接编辑文件或数据库。这一约束确保了性能差异仅源于模态本身，而非通用编程能力。

### 技能覆盖度诊断

CLI Agent的性能瓶颈常被归因于模型能力，但本文发现其根源在于技能接口对验证器检查点的覆盖不足。设计动机是：若技能层未暴露验证器所需的应用状态，即使模型完美执行命令，任务仍会失败。本文通过四阶段验证器覆盖流水线量化这一缺口：首先，将验证器检查点映射到现有技能实现，标记为“通过”、“部分”或“失败”；其次，计算技能级验证器覆盖率，定义为标记为“通过”的检查点比例。原始CLI-Anything技能的覆盖率仅为37.6%，表明大部分验证器要求无法通过现有技能满足。

$$
\text{Coverage} = \frac{|\{c \in C \mid \text{label}(c) = \text{Pass}\}|}{|C|}
$$

其中 $C$ 为验证器检查点集合，$\text{label}(c)$ 为技能实现对该检查点的满足状态。该公式量化了技能接口对任务目标的表达能力，覆盖率越低，CLI Agent的潜在性能损失越大。

### 验证器引导技能修补

为诊断技能覆盖度对CLI性能的影响，本文引入验证器引导的技能修补设置。设计动机是：若原始技能缺失某些操作路径，修补后应能恢复大部分性能，从而区分“模型能力不足”与“技能接口不完整”。修补过程使用验证器信息修复标记为“部分”或“失败”的技能路径，并通过应用级测试套件验证。修补后，CLI Agent的成功率从48.2%提升至69.3%，覆盖率达到100%。这一结果被解释为覆盖度受控的诊断上限，而非开箱即用的基线，因为修补过程依赖验证器信息，无法泛化到未见任务。

$$
\Delta_{\text{CLI}} = \text{PassRate}_{\text{patched}} - \text{PassRate}_{\text{original}} = 69.3\% - 48.2\% = 21.1\%
$$

该差值量化了因技能覆盖度不足而损失的CLI性能，表明超过40%的原始CLI缺口可由技能修补恢复。

## 实验评估

实验在440个桌面任务上进行，覆盖18个应用与12个工作流类别，GUI与CLI Agent接收相同的目标、初始状态与验证器。基线包括GPT-5.4、Claude Opus 4.7等前沿模型，但未包含MobileRL、UI-S1等专用GUI Agent，可能低估了GUI模态的上限。主结果显示，最强GUI Agent（GPT-5.4）的全通过率59.1%高于最强原始技能CLI Agent（Codex GPT-5.5）的48.2%，但修补技能后CLI成功率升至69.3%，超过GUI。

| 设置 | 全通过率 (%) | 平均奖励 | 时间 (s) |
| :--- | :--- | :--- | :--- |
| GUI GPT-5.4 | 59.1 | — | 455.8 |
| CLI 原始技能 | 48.2 | — | 188.1 |
| CLI 修补技能 | 69.3 | — | 162.6 |

消融实验聚焦于程序化接地对GUI性能的影响。在176个依赖GUI工作流的任务上，提供显式步骤提示后，全通过率从59.7%微升至60.2%，但平均运行时间从397.0s降至314.8s。这表明程序化线索主要减少无效探索，而非消除失败，GUI Agent仍需解决视觉定位与状态跟踪问题。

评估边界方面，本文未报告置信区间，且修补技能设置依赖验证器信息，无法作为部署基线。代码未公开，但CLI-Anything有开源仓库，可复现技能覆盖度计算。评估协议未包含混合模态策略，限制了结果对真实部署场景的适用性。

## 关联研究分析

从问题动机看，本文与OSWorld等GUI基准的核心差异在于评估目标：OSWorld聚焦单一GUI模态的鲁棒性，本文则隔离模态效应。这一差异源于任务特性：GUI任务依赖视觉定位，而CLI任务依赖技能覆盖度，两者瓶颈不同。若将本文协议应用于OSWorld，需为每个任务构建对应的CLI技能层，但OSWorld未提供此类接口，导致无法直接对比。

从方法设计看，本文与ToolCUA等混合模态框架的差异在于约束强度：ToolCUA允许Agent动态选择GUI或CLI路径，本文则强制单一模态。这一选择牺牲了真实场景的灵活性，但换取了模态效应的清晰归因。技能覆盖度诊断是本文独有贡献，ToolCUA未量化技能层对性能的影响，可能高估了CLI模态的潜力。

## 总结

本文要解决的核心矛盾是现有基准无法隔离GUI与CLI模态对任务性能的影响。通过固定任务目标、初始状态与验证器，并强制模态原生动作空间，本文构建了首个匹配执行层基准，量化了技能覆盖度对CLI性能的贡献。实验证明，原始CLI Agent的48.2%成功率中，21.1%的缺口源于技能覆盖度不足，修补后CLI性能反超GUI。本文的边界在于未评估混合模态策略，且修补技能设置依赖验证器信息，无法作为部署基线。当技能覆盖度达到100%时，CLI Agent在结构化任务上的优势是否可持续，论文未给出回答。
