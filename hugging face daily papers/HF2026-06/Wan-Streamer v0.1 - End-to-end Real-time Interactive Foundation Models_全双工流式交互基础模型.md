> 实时音视频交互要求感知与生成在毫秒级时间尺度上重叠，而非交替执行。现有级联系统因模块边界等待和误差累积，无法实现真正的低延迟全双工行为。Wan-Streamer 通过单一 Transformer 统一处理文本、音频和视频的输入输出，将流式因果性从服务优化提升为建模约束。该架构实现了约 200 ms 模型侧延迟，但缺乏对语义理解准确率的量化验证，其长时程一致性仍存疑。

## 研究背景

实时交互的核心困境在于多模态信号的异步性：用户说话时，智能体需同时产生可见的倾听行为；智能体响应时，仍需感知用户反馈以处理打断。这种全双工特性要求不同模态在单一持续过程中因果对齐，而传统级联架构将感知、语言建模、语音合成和视觉生成拆分为独立模块，导致模块边界产生等待时间，且识别与同步误差逐级累积。流式因果性（Streaming Causality）在此场景下不仅是时间约束，更是架构约束：任何基于离线编码器或双向解码器的设计，都无法通过工程优化恢复真正的低延迟全双工行为。

早期全双工研究如 Moshi 仅处理语音流，未涉及视觉智能体生成；交互式数字人系统如 StreamAvatar 虽能实时渲染，但依赖外部对话和语音模块，其运行时指标不包含完整交互路径。Wan-Streamer 的切入点在于消除模块边界，将感知、推理、生成、响应时机和轮次管理联合优化于单一持久交互状态中，使流式能力成为模型内在属性而非外部调度结果。

## 核心方法

### 全模态因果序列建模

Wan-Streamer 将语言、音频和视频在输入输出两侧均表示为交错因果序列，由单一 Transformer 处理。设计动机在于解决级联系统中文本作为隐藏中间表示导致的同步误差累积。模型不依赖外部 VAD、ASR 或 TTS 模块，而是通过块因果注意力（Block-Causal Attention）协调增量流式生成，确保每个新生成单元立即提交至交互历史。

### 条件流匹配联合生成

音频和视频响应在连续潜空间中表示，采用条件流匹配（Conditional Flow Matching）联合生成。对于模态 $m \in \{a, v\}$，干净目标潜变量 $z_0^{[m]}$ 与高斯噪声 $\epsilon^{[m]} \sim \mathcal{N}(0, I)$ 在流时间 $\tau$ 构造噪声潜变量 $z_\tau^{[m]}$。模型估计速度场：

$$ v_\theta(z_\tau^{[m]}, \tau, c_k) \approx \frac{dz_\tau^{[m]}}{d\tau} $$

其中 $c_k$ 为包含用户观测和已提交智能体响应的干净流式上下文。该公式的物理含义是：同一干净上下文同时条件化音频和视频的速度预测，使语音、运动、外观和场景演化作为耦合响应共同优化，避免后处理对齐。

### Thinker-Performer 异步推理

推理阶段部署为 Thinker-Performer 流水线以最大化重叠。Thinker 负责编码、KV 缓存更新和解码，Performer 仅运行流匹配求解器生成下一潜变量。在流式步 $k$，Thinker 消费当前用户观测并生成 KV 切片，同时接收 Performer 返回的上一步潜变量进行解码输出；Performer 接收新 KV 切片并生成下一步潜变量。该设计将昂贵的潜变量生成与感知状态更新解耦，使当前帧感知、上一帧解码、下一帧去噪和 KV 通信在相邻流式单元间重叠，系统实时性仅要求 Performer 时间加通信开销低于 160 ms 流式单元时长。

## 实验评估

实验设置聚焦延迟指标，对比对象包括 Moshi、GPT-4o、Qwen3-Omni 等语音或全模态系统。基线覆盖审计显示，论文未对比流式视频理解专用方法如 VST 或 ThinkStream，也未在 OVO-Bench 等标准基准上报告准确率，导致语义有效性无法在领域坐标系中量化。

| 系统 | 交互类型 | 用户可见响应延迟 | 其他报告指标 |
| :--- | :--- | :--- | :--- |
| Moshi [12] | 语音到语音 | N/R 产品路径 | 160 ms 理论；200 ms 实际模型延迟 |
| GPT-4o / Realtime API [18, 20, 26] | 语音到语音，音频/视觉输入 | 协议依赖 | 232/320 ms 官方音频响应；~500 ms API TTFB |
| Qwen3/3.5-Omni [29, 30] | 音视频文本输入，语音/文本输出 | N/R 交互循环 | 首包：234/547 ms；Qwen3.5 Flash 235/426 ms |
| **Wan-Streamer (ours)** | 文本/音频/视频输入输出 | **~550 ms 总延迟**（含 350 ms 网络） | **~200 ms 模型侧**；25 FPS 视频输出 |

Wan-Streamer 的 200 ms 模型侧延迟低于 Moshi 的 200 ms 实际延迟和 GPT-4o 的 232 ms 音频响应，但总延迟 550 ms 高于部分语音系统的模型侧指标，差异源于 Wan-Streamer 包含视频生成和完整交互路径。

消融数据不可得，论文未报告各组件对延迟或质量的独立贡献。设计决策验证方面，蒸馏阶段采用自强制策略（Self-forcing）缓解长时程退化，但具体性能提升数值未公开。评估边界存在显著局限：指标仅覆盖延迟，未报告 TTFT、MaxFPS 等系统级细粒度指标；评估协议未包含打断鲁棒性或长时程身份一致性测试；代码未开源，超参数和 GPU 配置细节有限，可复现性受限。

## 关联研究分析

从问题动机看，Wan-Streamer 与 Moshi 的核心差异在于模态覆盖范围。Moshi 将用户和助手语音建模为并行流，移除显式轮次分割，但仅处理语音模态，无法学习视觉倾听行为或音视频响应时机。Wan-Streamer 将视频纳入同一因果流，使智能体在非说话间隔保持身份、注视和呼吸等可见行为，这一扩展源于具身智能对视觉反馈的需求，而非单纯的技术升级。根源在于任务特性：语音交互可容忍视觉缺失，但具身助手必须通过视觉通道传递状态。

从方法设计看，Wan-Streamer 与 StreamingVLM 在因果架构上同源，但应用目标不同。StreamingVLM 采用注意力沉没和连续 RoPE 解决无限流上下文断裂，聚焦于理解任务；Wan-Streamer 将因果性扩展至生成侧，通过流匹配联合生成音视频潜变量。关键差异在于记忆管理：StreamingVLM 依赖 KV 缓存压缩，Wan-Streamer 通过 Thinker-Performer 分离实现异步 KV 交换，后者更侧重计算重叠而非存储优化。这种设计选择暗示，当生成计算量远超感知更新时，分离部署比统一推理更具延迟优势，但可能引入状态同步开销，论文未量化该开销对长时程一致性的影响。

## 总结

Wan-Streamer 解决的核心矛盾是全双工交互中感知与生成的时间重叠需求与级联系统模块边界延迟的冲突。其切入点在于将流式因果性从服务优化提升为建模约束，通过单一 Transformer 统一处理多模态输入输出，消除外部模块依赖。方法上，采用块因果注意力协调交错序列，条件流匹配联合生成音视频潜变量，Thinker-Performer 异步推理实现计算重叠。实验证明其模型侧延迟约 200 ms，总延迟约 550 ms，在包含视频生成的完整交互路径上具备竞争力。边界在于缺乏语义准确率基准，无法验证视频理解能力是否优于级联系统；长时程一致性仅通过自强制蒸馏缓解，未提供量化证据。当流式单元时长从 160 ms 缩短至 100 ms 时，Performer 的流匹配求解器时间是否仍能低于该阈值，论文未给出回答。
