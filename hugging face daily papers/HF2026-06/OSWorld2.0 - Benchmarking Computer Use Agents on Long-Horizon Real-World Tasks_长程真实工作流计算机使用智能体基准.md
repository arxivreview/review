# HuggingFace最新推荐论文 ｜OSWorld2.0: Benchmarking Computer Use Agents on Long-Horizon Real-World Tasks ｜长程真实工作流计算机使用智能体基准

研究机构：MiniMax

论文原文见 [arXiv](https://arxiv.org/abs/2606.29537)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2606.29537)

> 计算机使用智能体（Computer-Use Agent）旨在通过像素级截图理解并操作数字设备，其核心价值在于摆脱对HTML或Accessibility Tree等结构化数据的依赖，实现跨平台的通用交互。现有基准如OSWorld 1.0任务短小且孤立，无法反映真实专业场景中跨应用、长时程的工作流需求，导致高准确率掩盖了智能体在复杂任务中的系统性失效。OSWORLD 2.0通过构建108个中位耗时1.6小时的真实工作流任务，结合自托管动态环境与细粒度部分奖励机制，重新定义了长程计算机使用的评测标准。该基准揭示了前沿模型在维持任务级状态一致性上的根本局限，但部分奖励分数是否高估了实际可用性仍存疑。

## 研究背景

当智能体执行跨应用工作流时，早期微小错误会导致后续步骤偏离，这一现象称为错误累积。错误累积源于GUI环境的部分可观测性与动态变化，单步错误易导致轨迹偏离，而现有方法缺乏有效的自我反思与回溯机制。解决此类问题的经典框架是强化学习（RL），它通过在线或半在线训练提升智能体在动态环境中的自主决策能力，但训练复杂度增加且样本效率低。

GUI智能体的兴起源于多模态大语言模型在视觉感知与推理能力上的突破，使得AI能够直接通过像素级截图理解并操作图形用户界面。早期研究主要依赖基于提示工程的模块化框架，如ReAct和Reflexion，通过组合通用LLM与外部工具实现任务执行。然而，这种“框架驱动”范式受限于推理延迟和错误累积，难以处理需要多步规划的复杂工作流，确立了以单步视觉定位（Grounding）为核心的初始问题边界。随着2024年至2025年UI-TARS、SeeClick等工作的出现，领域经历了从“框架驱动”向“原生模型驱动”的关键转折，问题定义已从单纯的定位精度，演变为长程任务中的错误累积与恢复困难。

OSWORLD 2.0的切入点在于现有基准无法同时满足长时程、真实操作环境及复杂现象覆盖三个维度。OSWorld 1.0中Claude Opus 4.8达到83.5%的成功率，暗示桌面计算机使用已“基本解决”，但其任务中位耗时仅约2分钟，且极少跨越两个以上应用。这种高准确率掩盖了智能体在端到端专业工作流中的真实能力缺口。OSWORLD 2.0通过引入中位耗时1.6小时的任务、自托管动态Web服务及细粒度部分奖励，将评测从“能否操作”转向“能否完成复杂专业工作”，直接回应了长程任务错误累积与评估标准主观性两大痛点。

## 核心方法

### 方法参照系

OSWORLD 2.0属于基准评测体系类别，其标准流程包括任务收集、环境构建、评估协议定义及质量保证。与OSWorld 1.0等静态基准的关键差异在于，OSWORLD 2.0将评测单元从孤立界面操作扩展为端到端专业工作流，强调跨应用信息依赖、动态状态变化及隐性状态恢复，而非单步动作匹配。

### 长时程工作流任务构建

任务构建的核心改动发生在任务收集与环境实例化环节。传统基准多采用合成数据或短小任务，导致智能体可通过模式匹配而非真实推理完成任务。OSWORLD 2.0通过团队头脑风暴与专家标注生成约90%的任务，确保任务源自真实专业场景，输入工件从真实材料收集或改编。每个任务定义为自包含的端到端工作流，其难度来自跨多个应用的相互依赖步骤，而非重复或无关子任务的拼接。任务中位人类操作时间约为1.6小时，是OSWorld 1.0的48倍，69.6%的任务预计耗时超过1小时。这种设计强制智能体在长时程中维持任务级模型，直接测试其在跨应用、动态环境中保持状态一致性的能力。

### 动态环境与细粒度评估

评估协议的核心改动发生在最终状态评分环节。OSWorld 1.0使用二元通过/失败评分，对长时程工作流过于粗糙，无法区分无进展与接近完成的状态。OSWORLD 2.0引入细粒度部分奖励，每个任务平均包含27.25个检查点，评分基于最终环境状态而非固定检查点顺序，以支持不同有效解决路径。模型评估仅作为有限补充，占总分的11.53%，且无任务依赖其超过50%。每个判断提示在标注的正确与易混淆错误状态上验证，仅在一致准确时接受。此外，OSWORLD 2.0自托管31个Web服务，注入任务中途消息以改变环境状态，并暴露具有有限知识的模拟用户，测试智能体在动态环境中的适应力与主动交互能力。

## 实验评估

实验在AWS CPU实例上无头运行，评估七个模型家族：Claude Opus 4.8、4.7、Sonnet 4.6、GPT-5.5、Qwen 3.7-Plus、MiniMax M3、Kimi 2.6。所有模型使用截图观察，步数预算500，生成上限16K输出令牌（MiniMax M3为8K）。基线覆盖前沿商用模型与开源模型，但缺失UI-TARS等专用GUI模型在长程任务上的表现。

Claude Opus 4.8在批量工具调用配置下取得最高二元完成率20.6%与部分得分54.8%，但GPT-5.5以约37.1K输出令牌达到13.0%完成率，显示其更高的令牌效率。然而，GPT-5.5在150、300、500步预算下均收敛于约14%，表明其性能平台期，而Claude模型通过增加令牌消耗持续提升得分。

消融分析显示，批量工具调用对Claude模型性能有显著影响：Opus 4.8在批量模式下二元完成率20.6%，单步模式下降至18.5%；Opus 4.7从18.2%降至13.9%。GPT-5.5始终批量调用工具，其每任务工具调用149.8次远低于Claude模型的481.8至597.1次，但完成率较低，表明工具调用频率与完成率并非线性相关。行为标注显示，GPT-5.5在71.3%的任务中采用直接代码/API/文件策略，而Claude Opus 4.7在37%的任务中采用该策略，37%采用人类GUI策略，显示不同模型在解决长程任务时的策略偏好差异。

评估边界方面，模型评估占总分的11.53%，虽经验证但可能引入偏差；安全审计包含8项诊断检查，但未覆盖所有潜在副作用；代码与轨迹数据已发布，但自托管Web服务的部署复杂度可能限制复现性。

## 关联研究分析

从问题动机看，OSWORLD 2.0与MyPCBench均关注真实环境中的计算机使用，但MyPCBench侧重个性化桌面状态，其报告轨迹平均45.8步，而OSWORLD 2.0中Claude Opus 4.7平均318.4步，显示长时程工作流对智能体持续执行能力的更高要求。OSWORLD 2.0通过动态环境注入与跨应用依赖，将评测从状态检索转向工作流维持，这一差异源于任务特性：真实专业工作流要求智能体在数百步中保持任务级模型一致，而个性化状态任务更侧重短期记忆与检索。

从方法设计看，OSWORLD 2.0与Agents' Last Exam均针对专业任务，但ALE将GUI交互作为广义智能体工具集的一部分，仅34%的任务指定图形软件为主要工具，而OSWORLD 2.0将GUI操作本身作为评测核心对象。这一差异源于评测目标：ALE测试通用智能体在多种工具下的能力，而OSWORLD 2.0专门测试GUI智能体在长时程、多应用环境中的表现。OSWORLD 2.0引入的细粒度部分奖励与动态环境注入，是应对长程任务错误累积与评估主观性的具体设计，而ALE未采用此类机制，可能因其任务集更短且工具多样性更高。

## 总结

OSWORLD 2.0要解决的核心矛盾是现有基准高准确率掩盖智能体在真实专业工作流中的系统性失效。其切入点在于构建长时程、跨应用、动态环境的工作流任务，结合细粒度部分奖励，直接测试智能体维持任务级状态一致性的能力。该基准通过108个中位耗时1.6小时的任务，揭示前沿模型在二元完成率上仅达20.6%（Claude Opus 4.8），部分得分54.8%，显示当前智能体在长程任务中丢失约束、跳过验证、无法恢复隐性状态的根本局限。其边界在于部分奖励分数可能高估实际可用性，且模型评估占比11.53%仍依赖MLLM判断。当部分奖励分数与二元完成率差距扩大时，智能体是否真正完成了用户意图，还是仅满足了检查点形式，论文未给出回答。
