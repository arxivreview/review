> 导读 现有形式化验证基准多源自竞赛数学或专家编写的 ITP 代码，无法反映普通软件工程中的验证难度，导致 AI 模型在真实软件验证任务上的能力评估存在盲区。本文从 333 个开源 Python 仓库抓取 11,039 个属性测试（PBT），通过智能体流水线将其转译为 9,415 个 Lean 4 证明挑战，构建了首个源自真实工程实践的大规模软件验证基准。该工作填补了“非专家代码”验证数据的空白，但转译过程中的语义保真度损失（中位数 0.65）及基线模型在困难任务上仅 49% 的成功率，揭示了当前 LLM 处理复杂软件语义的局限。

## 研究背景

属性测试（Property-Based Testing, PBT）通过随机生成输入验证软件属性，是轻量级形式方法的代表。然而，PBT 仅提供统计保证，无法像交互式定理证明器（ITP）那样提供数学上无懈可击的正确性证明。当 AI 生成的代码量激增，安全关键系统要求从“随机测试通过”升级为“形式化证明”，但 ITP 验证依赖高度专业化的证明工程，人力成本极高，形成了 AI 代码生成速度与人工验证速度之间的瓶颈。

主流 LLM 定理证明研究长期聚焦于数学竞赛题（如 MiniF2F、PutnamBench）或专家编写的 Lean 库代码（如 Mathlib）。这些基准存在两个根本缺陷：一是任务对象为抽象数学命题，缺乏对具体代码语义、API 依赖及黑盒外部系统交互的建模；二是数据源多为竞赛题或学术项目，分布与真实工业软件差异巨大，导致模型在训练数据中可能已记忆相关模式。现有基准无法评估 AI 在“普通软件”——即包含前端后端、数据库依赖及复杂依赖树的系统——上进行形式化验证的能力。

本文切入点在于利用 PBT 作为“桥梁”。PBT 在工业界已有广泛采用，且其断言逻辑天然对应形式化验证中的规格说明（Specification）。通过从真实仓库抓取 PBT 并自动转译为 Lean 定理，本文构建了 FVSpec 基准，其核心差异在于：问题源自无形式化验证意图的普通工程师代码，迫使模型处理真实世界的代码复杂性，而非竞赛题的数学技巧。

## 核心方法

### 方法参照系

本文任务属于“自动形式化”与“证明生成”的交叉领域。标准流程通常假设输入为自然语言数学陈述，输出为 Lean 代码。本文的关键差异在于输入为 Python 代码及其 PBT，任务不仅是生成证明，更包含从命令式代码到依赖类型语言的语义转译。

### 智能体转译流水线

针对 Python 到 Lean 的语义鸿沟，本文设计了三阶段智能体流水线。首先，使用 tree-sitter 提取被测函数（FUT）及其局部依赖闭包，解决动态语言中依赖关系难以静态分析的问题。其次，单一形式化智能体生成 `Impl.lean`（函数实现）与 `Spec.lean`（定理声明），并通过 Lean LSP 进行迭代修复。该环节的设计动机是解决单次生成中常见的类型不匹配与未定义符号错误，通过编译器反馈闭环提升转译成功率。

转译质量通过结构忠实度评分量化，定义为五个子分数的加权平均：

$$
S_{faith} = \frac{1}{5} \sum_{i \in \{param, type, strat, assert, dep\}} S_i
$$

其中 $S_{param}$ 衡量参数覆盖，$S_{type}$ 验证类型对应，$S_{strat}$ 追踪策略覆盖，$S_{assert}$ 确保断言对应，$S_{dep}$ 检查依赖保留。该公式旨在量化 Lean 定理与原始 Python PBT 的语义对齐程度，而非仅检查语法正确性。

### 难度标签与数据清洗

为区分任务复杂度，本文引入基于 LLM 的难度标签机制。使用 `claude-haiku-4-5` 作为裁判，结合结构忠实度、定理数量等指标，将样本标记为“Easy”或“Hard”。该设计解决了传统基准缺乏细粒度难度分层的问题，使得评估能区分模型在简单逻辑与复杂依赖推理上的表现差异。数据清洗阶段通过正则表达式过滤平凡定理（如 Unit 类型恒等式），并通过命名空间过滤器移除 `Impl.lean` 中泄漏的定理声明，确保每个样本仅包含有效的证明义务。

## 实验评估

实验在 FVSpec:FV 基准上进行，选取 100 个 Easy 和 100 个 Hard 样本，评估 Claude Sonnet 4.6、Claude Opus 4.7 和 GPT 5.4 三个前沿模型。基线仅包含通用 LLM，未对比 DeepSeek-Prover 等专用证明器，这限制了与数学证明 SOTA 的直接可比性，但符合本文“软件验证”而非“数学竞赛”的定位。

| 模型 | Easy 成功率 (%) | Hard 成功率 (%) | 总体成功率 (%) |
| :--- | :--- | :--- | :--- |
| GPT 5.4 (k=5) | 73 | 59 | 66 |
| Claude Opus 4.7 (k=5) | 70 | 55 | 62 |
| Claude Sonnet 4.6 (k=5) | 67 | 43 | 55 |

*注：数值取自论文 Figure 5 及正文描述，k=5 表示最佳 5 次尝试中的成功率。*

数据显示，模型在 Easy 任务上表现尚可（67-73%），但在 Hard 任务上显著下降（43-59%）。GPT 5.4 在 Hard 任务上领先，但整体成功率仅 66%，远低于数学基准上 90%+ 的表现。这一差距表明，真实软件验证中的依赖推理与语义映射是当前 LLM 的薄弱环节。

消融分析显示，结构忠实度中位数仅为 0.65，其中参数覆盖（0.24）和依赖覆盖（0.48）是主要短板。这意味着近半数的转译未能完整保留原始代码的参数或依赖结构，可能导致 Lean 定理与 Python 语义存在偏差。尽管类型对应（1.00）和断言覆盖（0.97）接近饱和，但参数与依赖的损失削弱了基准的严格性。

评估边界方面，本文未报告计算资源消耗，且 41% 的样本使用存根实现（Stub），其证明义务弱于完整实现。此外，难度标签由 LLM 生成，校准度约 70%，存在主观性风险。代码与数据已开源，但转译流水线的 LSP 迭代次数上限（16 次）可能影响复杂函数的转译成功率。

## 关联研究分析

从问题动机看，FVSpec 与 FVAPPS 同属“代码到定理”路线，但 FVAPPS 源自 APPS 竞赛题，其代码逻辑相对独立且数学化；FVSpec 源自真实仓库，代码包含复杂的局部依赖与外部 API 调用。这一差异导致 FVSpec 的 Hard 任务成功率显著低于数学基准，根源在于真实软件验证需处理“黑盒外部系统”的语义不确定性，而竞赛题通常假设封闭环境。

从方法设计看，本文与 LeanSearch v2 等检索增强方法形成对比。LeanSearch 通过迭代草图优化前提选择，适用于大型数学库；而 FVSpec 的依赖规模较小（中位数 2 个局部依赖），主要挑战在于 Python 到 Lean 的语义转译而非大规模检索。本文未采用检索增强，而是依赖 LSP 迭代修复，这暗示在中小规模依赖场景下，编译器反馈比外部检索更有效。然而，当依赖树扩展至数百个函数时，LSP 修复是否仍具效率，论文未给出回答。

## 总结

本文旨在解决 AI 形式化验证在真实软件工程中的基准缺失问题。现有数学基准无法反映普通代码的验证难度，而专家 ITP 代码分布与工业实践脱节。FVSpec 通过抓取真实 PBT 并智能体转译，构建了 9,415 个 Lean 挑战，填补了这一空白。实验表明，前沿模型在 Hard 任务上成功率仅 49-59%，暴露了 LLM 处理复杂软件语义的局限。本文的边界在于转译保真度中位数仅 0.65，且 41% 样本依赖存根实现，削弱了证明义务的严格性。当依赖树规模扩大至工业级复杂度时，LSP 迭代修复的效率与结构忠实度评分的稳定性是否仍能维持，是后续研究需验证的关键问题。
