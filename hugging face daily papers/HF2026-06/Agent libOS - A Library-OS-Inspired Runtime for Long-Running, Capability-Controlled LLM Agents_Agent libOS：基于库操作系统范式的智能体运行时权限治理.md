> 导读 LLM智能体从静态文本生成转向具备自主规划与工具调用能力的动态执行者，其核心安全矛盾在于模型可见的动作接口与底层资源访问权限的边界模糊。现有框架多将工具分发作为安全边界，导致间接提示注入等攻击可轻易绕过语义层防御直达宿主资源。本文提出Agent libOS，借鉴库操作系统（Library OS）理念，将智能体建模为具备身份、能力与命名空间的进程，在运行时原语层实施细粒度权限检查与审计。该架构在语义正确性上提供了可执行的权限隔离机制，但缺乏与主流护栏方法在攻击成功率上的横向对比，其实际防御效能仍存疑。

## 研究背景

当智能体执行`write_file`操作时，模型层面的工具调用与运行时层面的文件写入权限往往仅由代码封装约定隔离，这种“可见即可用”的假设构成了间接提示注入（Indirect Prompt Injection, IPI）攻击的结构性漏洞。IPI利用大语言模型无法区分数据与控制指令的特性，使外部恶意内容劫持智能体行为，而传统基于输入过滤或语义分类的防御机制在开放环境中面临系统性失效。解决这一问题的关键在于将安全边界从模型可见的工具层下沉至运行时资源访问层，引入能力系统（Capability System）实现最小权限原则，即主体仅持有执行特定操作所需的最小权限集合，且权限可随进程生命周期动态衰减与撤销。

当前LLM智能体安全研究主要沿两条路线展开：一是运行时防护架构，如GuardAgent将自然语言约束转化为可执行逻辑进行行为监控，Spider-Sense引入内在风险感知实现主动防御；二是形式化验证路线，如VeriGuard通过生成可验证代码提供数学正确性保证。前者在通用开放环境中泛化性较好但缺乏强保证，后者在安全关键场景提供强保证但扩展性差且依赖规范精确性。这两条路线均假设工具调用是受控的，未深入解决工具可见性与资源权威性混淆的根本架构问题。Agent libOS的切入点在于不改变上层规划器或工具选择逻辑，而是在运行时边界建立独立的权限治理层，将智能体视为具备身份、调度与资源权限的软件行为者，通过操作系统原语实现权限隔离与审计。

## 核心方法

### 方法参照系

本文问题归属于运行时防护架构中的系统级隔离路线。与GuardAgent等外部监控器不同，Agent libOS不依赖额外的LLM判断或语义分析，而是将安全边界内化于运行时原语层。其核心差异在于将智能体执行抽象为操作系统进程模型，通过能力系统而非逻辑规则实施权限控制，实现了从“内容安全”向“资源权威性安全”的范式转移。

### 进程模型与权限衰减

传统智能体框架中，子任务或工具调用往往继承父进程的完整权限，导致权限泄漏风险。Agent libOS引入`AgentProcess`作为执行主体，其权限通过能力（Capability）绑定，能力包含主体、资源、权利、约束、颁发者、生命周期与撤销状态。在`fork`或`spawn`操作时，子进程不自动继承父进程的文件系统写入权限，除非显式授予。这一设计动机在于解决长时程智能体中权限随时间累积导致的越界操作问题。权限衰减机制可形式化为：

$$
Cap_{child} = Cap_{parent} \setminus \{c \mid c \in Cap_{parent} \land \text{attenuate}(c) = true\}
$$

其中$\text{attenuate}(c)$表示能力$c$在进程派生时是否被标记为需衰减。该公式确保子进程仅保留必要权限，防止通过进程派生实现权限提升。

### 原语层权限检查与审计

模型可见的工具（Visibility）与运行时原语（Authority）被严格解耦。工具表仅决定模型能否看到工具模式，而实际资源访问由原语管理器在每次调用时检查。这一设计动机在于解决工具输出注入（Tool-Output Injection）问题，即恶意工具输出可能改变后续决策，但原语层检查确保即使模型被诱导，恶意动作仍受控。权限检查过程可表示为：

$$
\text{Allow}(p, r, a) = \exists c \in Cap(p) \text{ s.t. } c.r = r \land c.a \supseteq a \land \text{valid}(c)
$$

其中$p$为进程，$r$为资源，$a$为操作，$Cap(p)$为进程$p$的能力集合。该公式确保每次资源访问都需显式能力支持，且能力在撤销后立即失效。审计记录在权限变更与副作用边界生成，记录进程、原语、资源、权限与时间，实现可追溯性。

## 实验评估

实验设置采用123项回归测试套件，覆盖权限衰减、命名空间隔离、工具表拒绝等属性，未使用AgentDojo、ASB等标准基准，也未对比GuardAgent、DreamGuard等主流护栏方法。基线覆盖审计显示，本文缺乏与现有SOTA方法在攻击成功率（ASR）或F1分数上的横向对比，仅验证架构语义正确性。

| 属性 | 回归证据 | 状态 |
|---|---|---|
| 工具可见性非权威性 | 可见`write_text_file`但无写入能力被拒绝 | Pass |
| 工作区包含 | 路径逃逸工作区根目录被文件系统原语拒绝 | Pass |
| Fork/Spawn衰减 | Fork子进程不继承父进程文件系统写入权限 | Pass |
| 命名空间隔离 | 不同进程命名空间中相同本地对象名独立解析 | Pass |
| 每次使用审批 | `ask_each_time`在原始语内阻塞，授予一次，消耗后再次提示 | Pass |
| 人类与等待恢复 | 人类审批与子进程等待恢复待处理运行时动作 | Pass |
| 异步睡眠 | 两个进程在协作睡眠时交替时钟输出 | Pass |
| Deno JIT系统调用隔离 | TypeScript工具可调用`libos.syscall`但无法绕过原语能力 | Pass |
| 镜像注册权限 | YAML加载与镜像注册需要文件系统与镜像注册表能力 | Pass |
| 资源提供者基底 | 文件系统、时钟/睡眠与shell提供者可注入而不改变工具模式 | Pass |
| 封装纯度 | 内置LLM面向工具不直接调用宿主边界API | Pass |

消融与设计决策验证方面，权限衰减机制在Fork/Spawn测试中表现关键，子进程不继承父进程写入权限确保了权限隔离。命名空间隔离测试表明，对象名在进程私有命名空间内独立解析，防止跨进程对象访问。评估边界与可复现性方面，本文未报告计算开销、延迟或成本指标，评估协议局限于架构语义正确性，缺乏动态轨迹评估。代码提供Python原型与确定性Demo，可复现性较高，但缺乏大规模防御效能验证。

## 关联研究分析

从问题动机看，Agent libOS与GuardAgent均针对IPI防御，但GuardAgent依赖LLM将自然语言约束转化为可执行逻辑，易被语义逃避绕过；Agent libOS通过确定性原语检查实现权限隔离，不依赖LLM判断，在已知攻击上更具鲁棒性。这一差异根源在于任务特性：GuardAgent面向通用开放环境，需处理未知攻击向量；Agent libOS面向安全关键场景，需强权限保证。从方法设计看，Agent libOS与MemGPT均借鉴操作系统概念，但MemGPT聚焦上下文分页，Agent libOS扩展为带权限的对象内存与能力系统。MemGPT的虚拟内存框架解决上下文管理问题，Agent libOS的能力系统解决权限治理问题，两者互补而非竞争。

## 总结

Agent libOS要解决的核心矛盾是LLM智能体中工具可见性与资源权威性混淆导致的权限泄漏与IPI攻击。其切入点在于将安全边界从模型层下沉至运行时原语层，通过能力系统实现细粒度权限隔离与审计，这是现有护栏方法未深入解决的架构问题。本文提出了Agent libOS运行时，将智能体建模为具备身份、能力与命名空间的进程，通过原语层权限检查确保资源访问受控。实验验证了123项回归测试全部通过，涵盖权限衰减、命名空间隔离等属性，证明了架构语义正确性。本文的边界在于缺乏与主流护栏方法在ASR/F1分数上的横向对比，未量化运行时原语检查的性能开销，且未解决语义层面的IPI。当智能体在分布式环境中运行时，跨节点的能力撤销与审计如何保证一致性，论文未给出回答。
