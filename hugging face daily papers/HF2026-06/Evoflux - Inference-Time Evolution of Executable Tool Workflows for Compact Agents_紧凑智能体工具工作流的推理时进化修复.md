> 紧凑语言模型在 Model Context Protocol (MCP) 环境下常生成看似合理但无法执行的工具调用图，导致任务失败。现有小语料监督微调（SFT）难以覆盖错误恢复行为，而大规模蒸馏成本过高。本文提出 Evoflux，将工具使用重构为推理时的可执行工作流进化搜索问题，通过类型化编辑与执行反馈迭代修复候选图。该范式在数据稀缺时显著优于权重更新，但受限于初始规划质量，且未验证大规模数据下的训练反超可能性。

## 研究背景

紧凑语言模型（1.5B-4B 参数）因低延迟、低成本及隐私优势，成为本地部署工具智能体的首选。然而，MCP 环境要求智能体从动态目录中发现工具、满足严格模式（Schema）、维持跨步骤依赖，并基于执行证据生成响应。紧凑模型常生成格式正确但逻辑断裂的工作流图，例如选择不可用工具、遗漏必需参数或破坏依赖链。这种“表面合理但执行失败”的模式，使得传统基于文本相似度的评估失效，必须引入执行层面的验证机制。

工具增强大语言模型的主流训练路线正从行为克隆转向基于可验证奖励的强化学习（RLVR）。然而，RLVR 及大规模蒸馏（如 ToolLLM 使用约 12,000 条轨迹）依赖海量高质量标注数据，这在需要实时工具执行与裁判评估的 MCP 场景中难以复现。当教师轨迹预算仅几百条时，SFT 仅能学习表面格式，无法覆盖错误恢复过程，甚至导致灾难性遗忘。本文切入点在于：在数据极度稀缺时，计算资源应分配给模型权重更新，还是推理时的在线修复？

## 核心方法

### 方法参照系

本文问题属于工具编排与规划范畴，但区别于传统的静态 DAG 规划或线性 ReAct 序列。标准流程通常假设工具集静态且规划一次性完成，而本文将规划视为动态的“生成-执行-修复”闭环，核心差异在于引入类型化编辑语言限制变异空间，并以执行可行性而非语法正确性作为优化目标。

### 类型化工作流图与执行评分

Evoflux 将工具调用表示为类型化工作流图 $g$，包含工具节点、依赖边及验证器节点。设计动机在于解决紧凑模型生成的图在工具解析或参数验证阶段静默失败的问题。候选图 $c$ 需通过编译、静态检查及实际执行，其评分函数 $f(c)$ 定义为六个子维度（任务完成、接地、工具适当性、参数准确性、依赖意识、并行效率）的算术均值，每个子维度由 LLM-Judge 独立评分（1-10 分）：

$$ f(c) = \frac{1}{6} \sum_{i=1}^{6} s_i(c) $$

该公式确保评分基于执行结果而非文本相似度，使搜索过程能精准定位具体失效环节（如参数错误 vs. 依赖断裂）。

### 自适应进化搜索与元引导

在初始候选生成后，Evoflux 通过类型化编辑（工具交换、参数修正、步骤重排等）变异工作流。设计动机在于避免无约束图重写导致的结构崩溃，同时平衡探索与利用。算法维护增长统计量 $G$，当 $G$ 低于阈值 $\tau_m$ 时触发元引导（Meta-guidance），由规划器对最弱候选进行高层重设计：

$$ G_{t+1} = \alpha G_t + (1-\alpha) \max(0, f(c') - f^*)^2 $$

此机制使搜索在局部停滞时能跳出局部最优，通过跨服务器工作流重组或引入缺失证据阶段实现结构跃迁，而非仅依赖局部参数微调。

## 实验评估

实验在 MCP-Bench 上进行，该基准包含 28 个实时 MCP 服务器和 250 个工具，任务涵盖金融、旅行及科学计算。基线包括 Zero-shot、SFT、SFT+DPO 及 ReAct，所有训练基线使用相同的几百条教师轨迹。Evoflux 在保留集上将执行可行性从约 3% 提升至 17-24%，而 SFT 和 SFT+DPO 在相同数据下表现持平或低于 Zero-shot 基线。ReAct 虽能达到更高峰值，但方差更大且 Token 成本更高。

| 模型 | 初始可行性 (%) | Evoflux 最佳可行性 (%) | 相对提升 |
| :--- | :--- | :--- | :--- |
| Llama-3.2-3B | ~3 | ~17 | 显著 |
| Qwen3.5-4B | ~14 | ~58 | 最高 |
| SmolLM3-3B | - | - | 74% |
| DeepSeek-R1-Qwen-1.5B | - | 1.27 (分数) | 最低 |

注：表中“相对提升”指分数相对提升百分比，可行性数据取自验证集。Qwen3.5-4B 在验证集上从约 3% 提升至 24%，而 Llama-3.2-3B 从约 3% 提升至 17%。SFT 后的 Llama-3.2-3B 执行成功率降至约 5%，SFT+DPO 降至约 3%，证明小语料微调不仅无效，反而损害了模型的执行能力。

评估边界方面，论文未报告置信区间，且 LLM-Judge 评分存在主观性风险。代码已开源，但超参数（如预算 $B$、种群上限 $K$）对结果的影响未做详细消融。评估协议依赖实时服务器状态，可能导致结果随时间波动，缺乏静态快照对比。

## 关联研究分析

从问题动机看，Evoflux 与 FlowEvo 同属自进化智能体路线，但 FlowEvo 侧重技能库的共进化，而 Evoflux 聚焦单任务内的图结构修复。这一差异源于任务特性：MCP 任务强调实时依赖与参数精确性，需要细粒度的执行反馈，而非宏观技能积累。Evoflux 的类型化编辑语言正是为了适应这种细粒度修复需求，而 FlowEvo 的通用技能进化在此场景下可能缺乏针对性。

从方法设计看，Evoflux 与 Tool-R1 等 RLVR 方法形成鲜明对比。Tool-R1 通过损失掩码区分模型生成与工具返回 Token，在训练时优化策略；Evoflux 则在推理时通过执行反馈优化候选图。这种差异揭示了数据稀缺下的权衡：RLVR 需要大量环境交互以稳定训练，而 Evoflux 将计算成本转移至推理时，避免了训练不稳定性。然而，Evoflux 未验证当训练数据充足时，RLVR 是否仍优于推理时搜索，这一盲区限制了其结论的普适性。

## 总结

本文核心矛盾在于紧凑模型在 MCP 环境下的执行脆弱性与数据稀缺性的冲突。现有 SFT 无法覆盖错误恢复，RLVR 数据成本过高，Evoflux 通过推理时进化搜索将计算资源从权重更新转向在线修复，证明了在几百条轨迹预算下，执行反馈驱动的搜索比小语料微调更可靠。实验显示，Evoflux 将可行性从 3% 提升至 17-24%，而 SFT 导致性能崩溃。其边界在于依赖初始规划的可修复结构，且未探索大规模数据下的训练反超可能性。当教师轨迹增加至万级时，SFT 是否可能通过覆盖更多恢复模式而超越 Evoflux 的推理时搜索，论文未给出回答。
