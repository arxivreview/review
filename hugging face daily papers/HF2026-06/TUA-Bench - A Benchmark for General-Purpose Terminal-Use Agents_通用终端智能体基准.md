# HuggingFace最新推荐论文 ｜TUA-Bench: A Benchmark for General-Purpose Terminal-Use Agents ｜通用终端智能体基准

研究机构：Meta AI、美国杜克大学

论文原文见 [arXiv](https://arxiv.org/abs/2606.28480)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2606.28480)

> 计算机使用智能体（Computer-Use Agent）的评估长期被图形用户界面（GUI）基准垄断，导致对智能体核心规划与工具调用能力的测量被视觉感知噪声所污染。现有终端基准又局限于编程工作流，无法覆盖日常办公与专业科学场景。TUA-Bench 通过构建包含 120 个非编程通用任务的 CLI 执行环境，剥离了视觉接地干扰，直接测量文本原生交互下的任务完成能力。该基准揭示了当前最强智能体在长程规划与错误恢复上的显著短板，但其难度筛选机制可能引入对特定模型弱点的偏向。

## 研究背景

当智能体执行“将 PDF 表格数据提取并生成 Excel 图表”这类任务时，GUI 路径要求模型先通过截图定位“文件”菜单，再识别“另存为”按钮的像素坐标，最后处理弹窗遮挡。这一过程将大量计算资源消耗在视觉接地（Visual Grounding）与布局鲁棒性上，而非任务逻辑本身。相比之下，命令行界面（CLI）以文本为原生介质，指令显式、反馈即时，且可通过管道（Pipes）组合复杂工作流，这与大语言模型（LLM）的序列生成优势天然契合。然而，CLI 长期被视为编程专用工具，其作为通用计算机操作接口的潜力未被充分评估。

现有 GUI 基准如 OSWorld 和 WebArena 虽覆盖了桌面与网页操作，但其评估指标混杂了视觉理解与规划推理，且随着模型进步迅速饱和——OSWorld 发布时最佳成功率为 12.24%，而 GPT-5.5 已达 78.7%。与此同时，Terminal-Bench 等终端基准聚焦于 Shell 编程与环境配置，缺乏对文档编辑、邮件管理、科学仿真等非技术场景的覆盖。TUA-Bench 的切入点在于填补这一空白：它不测试智能体能否“看”懂屏幕，而是测试其能否通过纯文本交互完成从日常办公到博士级专业仿真的全谱系任务，从而隔离并量化智能体的核心认知能力。

## 核心方法

### 基准架构参照系

TUA-Bench 遵循执行接地（Execution-Grounded）评估范式，即通过自动验证器检查最终环境状态而非轨迹匹配。与 GUI 基准依赖截图与坐标不同，本文任务在隔离的 Linux 容器中运行，智能体仅通过 CLI 与文件系统进行交互。关键差异在于任务来源：日常任务由 OSWorld 的 GUI 任务转化而来，保留任务意图但移除工具约束；专业任务则由领域专家协同设计，确保工作流的真实性与可验证性。

### 难度感知任务筛选

传统基准常因模型进步而快速饱和，导致区分度下降。TUA-Bench 引入难度感知筛选机制，从 394 个候选任务中剔除易解项。具体而言，使用 GPT-5.5、Claude Opus 4.7 和 Gemini 3.1 Pro 三个前沿模型在 Terminus-2 框架下对每个任务进行 5 次独立试验，计算平均奖励作为可解性指标。保留可解性最低的 100 个日常任务与 20 个专业任务。该机制的数学表达为：

$$
S_{task} = \frac{1}{N_{models} \times N_{trials}} \sum_{m=1}^{N_{models}} \sum_{t=1}^{N_{trials}} R_{m,t}
$$

其中 $R_{m,t}$ 为模型 $m$ 在第 $t$ 次试验中的奖励。选择 $S_{task}$ 最小的任务集，旨在确保基准在前沿模型上仍具挑战性。这一设计解决了静态基准因模型能力提升而失效的问题，但隐含假设是“当前模型难以解决的任务”等同于“具有通用区分度的任务”，可能偏向特定模型的弱点而非通用能力缺陷。

### 多模态任务转化与验证

日常任务的 GUI-to-CLI 转化并非简单替换界面，而是重写指令以适配终端语境。例如，OSWorld 中“使用 LibreOffice 编辑电子表格”被转化为“通过命令行工具修改 CSV 文件并生成指定格式的 PDF”。验证器采用确定性脚本检查输出文件的存在性、格式合规性及数值准确性。对于专业任务，如医学影像分割，验证器结合程序化检查与专家制定的评分标准。这种混合验证策略解决了纯程序化验证无法覆盖复杂专业输出的局限，但引入了评分标准的主观性风险，尽管论文声称已通过专家协同设计最小化此偏差。

## 实验评估

实验覆盖 5 种智能体框架（Claude Code, Codex, OpenHands, Mini-SWE-Agent, Terminus-2）与 12 种前沿模型，每配置运行 5 次独立试验。基线审计显示，评估涵盖了主流商业与开源模型，但缺失 GUI 专用模型（如 UI-TARS）作为跨模态对照，无法直接比较 CLI 与 GUI 路径的效率差异。主结果如下：

| 智能体框架 | 最佳模型 | 成功率 (%) | Pass@1 | All-5 |
| :--- | :--- | :--- | :--- | :--- |
| Claude Code | Claude Opus 4.8 | 65.8 ± 0.7 | 58.8% | 51.7% |
| Codex | GPT-5.5 | 64.7 ± 0.7 | 57.7% | 42.5% |
| OpenHands | Claude Opus 4.8 | 63.4 ± 0.6 | 57.3% | 45.0% |
| Mini-SWE-Agent | GPT-5.5 | 62.4 ± 0.8 | 54.2% | 40.0% |
| Terminus-2 | GPT-5.5 | 60.1 ± 0.6 | 52.3% | 31.7% |

Claude Code 搭配 Claude Opus 4.8 以 65.8% 的成功率领先，但其 All-5 指标（51.7%）显著高于 GPT-5.5 的 31.7%，表明前者在重复试验中更具稳定性。消融实验揭示，推理努力（Reasoning Effort）的提升并非单调收益：从 high 到 xhigh，Codex/GPT-5.5 的成功率提升不足 1 个百分点，但成本增加约 $33/次。此外，智能体框架的选择对性能的影响与模型选择相当，例如 Claude Opus 4.7 在 Terminus-2 下的表现优于其在 Claude Code 下的表现，说明框架编排与模型能力的耦合效应不可忽略。

评估边界方面，TUA-Bench 依赖确定性验证器，但部分专业任务采用 LLM-as-a-judge，可能引入评估噪声。代码已开源，但任务集基于特定模型版本筛选，随着新模型发布，基准难度可能再次饱和。可复现性受限于容器环境的一致性，网络依赖任务可能因外部服务变化而产生偏差。

## 关联研究分析

从问题动机看，TUA-Bench 与 OSWorld 共享“通用计算机使用”的目标，但根本分歧在于对“通用性”的定义。OSWorld 认为 GUI 是人类交互的自然延伸，因此智能体必须具备视觉感知能力；TUA-Bench 则主张 CLI 是 LLM 的原生语言，视觉感知是额外负担而非核心能力。这一分歧源于任务特性：GUI 任务中视觉接地是必要步骤，而 CLI 任务中文本解析已内化于 LLM 架构。TUA-Bench 的 65.8% 成功率低于 OSWorld 上 GPT-5.5 的 78.7%，但这并非直接可比，因为前者剥离了视觉优势，后者利用了视觉捷径。这种差异暗示，当前智能体的“通用性”可能部分依赖于对特定接口模态的适配，而非跨模态的抽象规划能力。

从方法设计看，TUA-Bench 与 Terminal-Bench 共享 Harbor 执行框架，但任务范围存在显著差异。Terminal-Bench 聚焦于 Shell 编程与环境配置，其任务可解性主要取决于代码生成能力；TUA-Bench 扩展至文档编辑、科学仿真等领域，要求智能体具备工具组合与状态监控能力。例如，TUA-Bench 中的“建筑能源仿真”任务需要智能体调用 OpenStudio 和 EnergyPlus 等专用软件，并处理复杂的输入参数与输出验证，这超出了 Terminal-Bench 的编程范畴。这种扩展揭示了当前智能体在非编程专业工作流中的脆弱性，但也引入了新风险：专业任务的验证标准高度依赖领域知识，可能限制基准的通用适用性。

## 总结

TUA-Bench 旨在解决 GUI 基准中视觉感知噪声对智能体核心规划能力评估的干扰，以及现有终端基准局限于编程工作流的空白。其切入点在于利用 CLI 的文本原生特性，构建覆盖日常办公与专业科学场景的通用任务集，并通过难度感知筛选确保基准的前沿区分度。实验表明，最强智能体 Claude Code + Claude Opus 4.8 仅达 65.8% 成功率，且推理努力提升的边际收益迅速递减，暴露了长程规划与错误恢复的瓶颈。该基准的边界在于其难度筛选机制可能偏向特定模型弱点，且专业任务的验证标准依赖领域专家，限制了跨领域泛化性。当新模型发布导致当前任务集再次饱和时，难度感知筛选机制能否持续保持基准的区分度，而非仅反映特定模型的缺陷，是后续研究需验证的关键问题。
