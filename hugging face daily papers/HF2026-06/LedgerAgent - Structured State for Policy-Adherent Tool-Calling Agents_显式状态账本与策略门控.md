> 客服领域工具调用智能体面临的核心矛盾是：模型能检索到正确记录，却在后续决策中基于陈旧或错误的状态执行违反领域策略的动作。现有推理时脚手架（如反思、规划）仅改变生成流程，未改变状态表示方式，导致状态仍隐式埋藏于不断增长的对话转录中。LedgerAgent 通过引入确定性类型化账本存储观测状态，并在环境变更动作执行前进行谓词级策略校验，将状态管理从模型内部推理外化为系统级机制。该方法在不修改模型权重的前提下提升了多试验一致性，但其有效性高度依赖领域模式图的预定义质量，对未见工具结构的泛化能力存疑。

## 研究背景

当智能体在客服场景中执行退款或改签操作时，它必须同时追踪用户身份、订单状态、支付方式和领域规则。这些事实分散在多轮对话的工具返回中，若仅靠提示词中的线性转录来维持，模型需在每次行动前从冗长历史中重新定位关键标识符。这种隐式状态管理导致两个典型失效：一是状态接地失败，即模型检索了正确记录但后续动作基于过时或错误重构的信息；二是策略边界失效，即工具调用在语法上有效，却因未校验当前状态而违反领域政策（如向非交付订单发起退款）。

长程任务中的错误累积是代理系统的主要失败模式，现有推理时脚手架如 ReAct 和 Reflexion 通过交错推理与行动或引入自我反思来缓解，但它们均保留“状态仅存在于提示词”这一根本假设。IRMA 等上下文工程方法虽通过重写输入增强规则可见性，但仍依赖语言模型从转录中恢复精确状态，且引入额外代理导致 Token 开销激增。LedgerAgent 的切入点在于改变状态表示本身：将观测到的工具返回投影为显式类型化字典，并在动作执行边界插入确定性策略检查，从而将状态管理从模型认知负担转化为系统级确定性操作。

## 核心方法

### 标准工具调用循环

标准策略遵循型工具调用智能体遵循 ReAct 范式，每轮将用户消息、历史转录、策略文本和工具模式输入模型，生成响应或工具调用。该流程的关键差异在于：状态完全隐式存在于转录中，模型需在每次生成时自行从历史 JSON 中检索相关事实，且无独立机制在动作执行前校验策略合规性。

### 模式锚定账本

账本（Ledger）是一个类型化字典 $L: P \rightarrow V$，其中 $P$ 为规范模式路径集合，$V$ 为工具返回值集合。其设计动机是解决转录中状态检索噪声问题：通过固定工具路径映射，将成功读取工具返回确定性存储于稳定地址（如 `orders.1234`），使模型可通过路径查找而非全文搜索获取当前状态。

$$
L \leftarrow \text{Absorb}(L, m) \quad \text{if } m \text{ is a successful read-tool return}
$$

该公式表示仅当消息 $m$ 为成功读取工具返回时，才更新账本状态。写入工具返回不更新账本，遵循“观测而非假设”原则，确保账本始终反映外部系统真实状态。账本在每轮生成前渲染为提示词块，与对话历史、策略文本并列提供，而非替代它们。

### 执行前策略门控

策略门控（Policy Gate）在环境变更工具调用执行前运行，评估拟议调用是否满足账本字段上的可执行谓词 $\Pi$。其设计动机是解决策略边界失效：将策略合规从模型内部推理外化为确定性代码检查，防止语法有效但策略违规的动作被执行。

$$
(a', g) \leftarrow \text{GateFilter}(a, L, \Pi) \quad \text{where } g \in \{\text{ALLOW}, \text{REVISE}, \text{BLOCK}\}
$$

该公式表示门控函数接收拟议动作 $a$、当前账本 $L$ 和谓词集 $\Pi$，返回修正后动作 $a'$ 和判定结果 $g$。若 $g=\text{REVISE}$，被拒调用被移除并添加违规反馈至下一轮；若 $g=\text{BLOCK}$，直接拒绝该环境变更动作。门控仅作为验证器，不选择工具、修复参数或规划新轨迹，模型仍负责任务推进。

## 实验评估

实验在 $\tau_2$-bench 和 $\tau$-Trait 的四个客服领域（航空、零售、电信、远程医疗）上进行，对比标准函数调用（FC）基线与 LedgerAgent，使用六个骨干模型（GPT-5.2、GPT-4.1、Kimi K2.5、GLM-5、MiniMax M2.5、Qwen330B），每任务运行四次独立试验，报告 pass^1（主成功率）和 pass^4（一致性指标）。基线覆盖标准 FC 和 IRMA（上下文工程方法），但缺失 RL 微调类基线（如 Tool-R0）和纯提示工程变体（如 Reflexion），无法隔离状态表示改进与训练式改进的贡献。

| 骨干模型 | 领域 | FC pass^1 | Ledger pass^1 | FC pass^4 | Ledger pass^4 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Kimi K2.5 | 航空 | 54.4% | 62.3% | 38.3% | 53.9% |
| Kimi K2.5 | 零售 | 57.5% | 70.6% | 24.6% | 41.2% |
| GLM-5 | 航空 | 51.3% | 64.6% | 40.9% | 48.5% |
| MiniMax M2.5 | 电信 | 66.1% | 66.3% | 81.8% | 74.8% |

Kimi K2.5 在航空和零售领域的 pass^1 分别提升 7.9 和 13.1 个百分点，pass^4 提升 15.6 和 16.6 个百分点，表明显式状态表示对一致性指标的增益大于单次成功率。MiniMax M2.5 在电信领域的 pass^4 下降 7.0 个百分点，提示双控制场景下账本机制可能引入状态同步冲突。与 IRMA 相比，Ledger 在 pass^1 上领先 3.7 个百分点，pass^4 领先 7.4 个百分点，且 Token 开销为 0.0%，而 IRMA 因使用三个辅助代理产生 53.1% 的 Token 开销。

消融分析显示，Ledger 的改进主要来自类型化账本和策略门控两个组件的协同作用。失败轨迹分析表明，Ledger 智能体的失败中 70.3% 为遗漏必需动作，20.4% 为错误动作参数，合计占 90.7%，说明状态表示改进未能完全解决动作规划问题。电信领域失败中 98.7% 为遗漏动作，提示双控制场景下用户侧状态变更可能超出账本观测范围。

评估协议使用固定用户模拟器（GPT-5-mini）和温度 0.0，确保可比性，但未报告置信区间或统计显著性检验。代码未公开，工具路径映射和谓词定义需领域专家手动指定，限制了跨域迁移的可复现性。pass^k 指标仅衡量一致性，未评估计算延迟或 Token 消耗对部署可行性的影响。

## 关联研究分析

从问题动机看，LedgerAgent 与 Reflexion 均针对长程任务中的错误累积，但 Reflexion 依赖语言模型自我反思生成改进策略，属于模型内部优化；LedgerAgent 将状态管理外化为确定性系统机制，属于系统级增强。这一差异源于任务特性：客服领域策略合规依赖精确状态校验，模型反思难以保证确定性，而代码谓词检查可提供可审计的合规保障。然而，LedgerAgent 的谓词需预定义，无法处理未编码的策略规则，而 Reflexion 的反思机制理论上可适应新规则，但缺乏确定性保证。

从方法设计看，LedgerAgent 与 IRMA 同为推理时上下文增强，但 IRMA 通过多代理重写输入增强规则可见性，引入额外 Token 开销；LedgerAgent 通过确定性账本渲染提供状态视图，零额外调用。这一差异反映了对“状态可见性”的不同理解：IRMA 假设模型需要更多规则上下文，LedgerAgent 假设模型需要更精确的状态地址。在工具调用准确性上，LedgerAgent 的账本路径映射直接解决参数接地问题，而 IRMA 的规则重写可能引入语义歧义。但 LedgerAgent 依赖固定工具路径映射，面对未见工具结构时需重新定义映射，而 IRMA 的多代理机制理论上可动态适应新工具，论文未探索这一泛化边界。

## 总结

LedgerAgent 要解决的核心矛盾是工具调用智能体在长程交互中状态隐式化导致的接地失败与策略违规。现有推理时脚手架仅改变生成流程，未改变状态表示，而 LedgerAgent 通过显式类型化账本和确定性策略门控，将状态管理从模型认知负担转化为系统级确定性操作，在不修改模型权重的前提下实现一致性提升。实验证明其在 Kimi K2.5 骨干下航空领域 pass^1 提升 7.9 个百分点，pass^4 提升 15.6 个百分点，且零 Token 开销。其边界在于：谓词和路径映射需领域专家预定义，双控制场景下状态同步冲突导致性能下降，且失败分析显示 70.3% 的失败仍为遗漏动作，说明状态表示改进未解决动作规划问题。当工具结构动态变化或策略规则未完全编码时，账本机制的泛化能力是否仍能维持，论文未给出回答。
