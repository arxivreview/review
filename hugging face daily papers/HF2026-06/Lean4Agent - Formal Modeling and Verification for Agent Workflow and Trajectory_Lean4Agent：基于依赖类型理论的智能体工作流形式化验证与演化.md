LLM 智能体工作流在长程任务中面临执行轨迹不可控与语义一致性缺失的难题，传统基于启发式或统计的鲁棒性测试无法提供数学层面的正确性保证。现有形式化方法受限于表达力，难以统一建模数据依赖属性与高阶推理，导致验证碎片化。本文提出 Lean4Agent，利用 Lean4 依赖类型语言构建三层验证库 FormalAgentLib，并设计 LeanEvolve 机制实现验证反馈驱动的工作流自动演化。该框架在 SWE-Bench 等基准上验证了形式化约束对任务成功率的提升，但其性能增益中模型能力与形式化逻辑的贡献占比仍存疑。

## 研究背景

当 LLM 智能体执行多步复杂任务时，自然语言指令的歧义性会导致中间状态漂移，进而引发最终结果错误。这种错误往往难以通过简单的输出检查发现，因为单步执行可能看似合理，但组合后的语义逻辑存在断裂。为捕捉这种深层一致性，需要引入形式化语言（Formal Language, FL）对智能体行为进行精确建模。依赖类型理论（Dependent Type Theory）作为现代数学证明的基础，允许类型依赖于值，从而能表达数据相关的属性，这为建模智能体工作流中变量状态随执行步骤变化的动态过程提供了理论支撑。

LLM 智能体工作流编排领域长期依赖人工设计的静态模板或基于搜索的动态生成，前者泛化能力差，后者缺乏对执行过程正确性的数学保证。虽然 RobustFlow 等工作通过统计测试揭示了工作流对查询扰动的脆弱性，AgenTracer 利用反事实重放定位故障，但这些方法均属于“事后诊断”，无法在部署前提供可证明的安全性边界。现有形式化尝试如 Hoare 逻辑契约或 SMT 检查，受限于底层语言表达力，无法统一处理数据依赖与高阶推理。Lean4Agent 的切入点在于利用依赖类型 FL 的统一表达力，将工作流的结构、语义与轨迹纳入同一形式化框架，实现从“统计鲁棒性”向“可证明正确性”的范式转移。

## 核心方法

### 方法参照系

本文问题可置于“程序验证”的通用框架下，但关键差异在于被验证对象是黑盒 LLM 的执行轨迹而非确定性代码。传统程序验证假设指令执行结果确定，而 LLM 智能体需引入局部正确性假设，将非确定性推理过程转化为可验证的逻辑命题。

### 三层形式化验证架构

FormalAgentLib 的核心创新在于构建分层验证体系，解决了单一形式化语言无法覆盖结构、语义与运行时轨迹的问题。Layer 1 通过类型系统检查工作流图的结构性良构性，如节点可达性与读写一致性，类比编译器检查。Layer 2 引入谓词系统（Predicate System），将自然语言指令转化为 Hoare 风格的前置与后置条件。其关键假设 $LLMExec$ 定义为：若执行前状态 $\Pi$ 满足前置条件 $\rho_{pre}$，则执行后状态 $\Pi'$ 满足后置条件 $\rho_{post}$。

$$
LLMExec: \quad \Pi \models \rho_{pre} \implies \Pi' \models \rho_{post}
$$

该假设将 LLM 的局部正确性形式化，使得静态语义验证可在部署前完成，支持“正确性由构造保证”（Correct-by-Construction）的设计模式。Layer 3 则针对特定执行轨迹，结合 Lean 逻辑、外部工具与 LLM-as-judge，验证 $LLMExec$ 假设在实际运行中是否成立，并定位违反条件的具体步骤。

### 验证反馈驱动的工作流演化

LeanEvolve 机制利用 Layer 3 的验证结果驱动工作流修订，解决了传统自动优化方法缺乏精确故障定位的问题。在正式引导演化（Formal-Guided Evolve）模式下，系统提取违反的谓词与局部化故障步骤，提供给 LLM 进行针对性修改。相比纯 LLM 演化（Pure-LLM Evolve）的盲目试错，形式化引导提供了细粒度的修改依据。

$$
W_{new} = \text{LLM}(W_{old}, \text{Error}_{loc}, \text{ViolatedPreds})
$$

其中 $W_{old}$ 为原工作流，$\text{Error}_{loc}$ 为定位的故障节点，$\text{ViolatedPreds}$ 为违反的谓词集合。该机制将验证从“静态检查”扩展为“动态优化闭环”，使工作流具备自我修复能力。

## 实验评估

实验在 SWE-Bench-Verified 的 50 题高难度子集与 ELAIP-Bench 的 100 题子集上进行，使用 GPT-5.2、GLM-5 等 5 个前沿 LLM 作为执行引擎。基线审计显示，本文未与 DAAO、A2Flow 等主流自动编排方法在统一骨干下直接对比，而是对比“验证通过”与“验证失败”的工作流组，这限制了横向可比性。

| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| GPT-5.2 | 62.67% | 50.00% | 12.67% | 32.00% | 20.33% | 11.67% |
| GLM-5 | 58.00% | 50.67% | 7.33% | 37.33% | 25.00% | 10.83% |
| Kimi-K2.5 | 61.33% | 46.00% | 15.33% | 36.00% | 28.33% | 7.67% |
| Gemma-4-31B | 60.00% | 32.67% | 27.33% | 35.67% | 27.33% | 8.34% |
| Qwen-3.5-27B | 49.33% | 38.00% | 11.33% | 42.00% | 36.67% | 5.33% |
| **Average** | **58.27%** | **43.47%** | **14.80%** | **36.60%** | **27.53%** | **9.07%** |

验证通过的工作流在 SWE 任务上平均提升 14.80%，在 ELAIP-Bench 上提升 9.07%。消融实验表明，移除纯 LLM 演化模块后，LeanEvolve 仍带来 5.07% 的提升，但比完整系统低 2.40%，说明形式化引导是主要驱动力，而纯 LLM 探索提供补充性广度。

评估边界方面，论文未报告 Token 成本或延迟，仅关注正确性，这与领域内“成本-性能联合优化”的共识存在偏差。代码尚未开源，但提供了详细的 Lean 代码示例与实验设置（Lean v4.20.0, AgentSPEX 引擎, 温度 1.0）。统计显著性通过 95% 配对 Bootstrap 置信区间验证，除 Qwen-3.5-27B 在 ELAIP-Bench 上外，其余模型-任务组合均显著。

## 关联研究分析

从方法设计看，Lean4Agent 与 RobustFlow 代表了鲁棒性保障的两种对立路径。RobustFlow 通过构建 31,889 个工作流的测试集，利用同义变换与噪声注入进行统计鲁棒性评估，揭示了现有方法在微小扰动下的不稳定性，但其本质是“黑盒测试”，无法解释失败原因。Lean4Agent 则通过依赖类型逻辑提供“白盒验证”，不仅能判断正确性，还能定位违反的具体谓词。这种差异源于任务特性：RobustFlow 关注开放域泛化，而 Lean4Agent 聚焦高利害场景下的可证明安全性。然而，形式化验证的高计算开销与 RobustFlow 强调的低成本测试之间如何平衡，论文未给出量化对比。

从问题动机看，Lean4Agent 与 AgenTracer 均致力于故障定位，但机制截然不同。AgenTracer 利用反事实重放，通过注入错误并观察输出变化计算代理贡献度，属于“动态扰动”方法，依赖大量执行开销。Lean4Agent 的 Layer 3 则基于静态语义推导与轨迹状态检查，属于“逻辑推导”方法，无需重复执行即可定位故障。这种差异暗示了两种故障定位范式的适用边界：AgenTracer 更适合黑盒、无形式化规范的系统，而 Lean4Agent 要求工作流具备可形式化的结构。若工作流缺乏清晰的类型定义，Lean4Agent 的验证优势将大幅削弱，这一局限性在论文中未充分讨论。

## 总结

Lean4Agent 旨在解决 LLM 智能体工作流缺乏数学可证明安全性的核心矛盾，其切入点在于利用依赖类型 FL 的统一表达力，克服了传统 Hoare 逻辑与 SMT 检查在数据依赖属性建模上的局限。通过构建 FormalAgentLib 三层验证库与 LeanEvolve 演化机制，该框架实现了从静态验证到动态优化的闭环。实验证明，验证通过的工作流在 SWE-Bench 上平均提升 14.80%，LeanEvolve 进一步带来 7.47% 的增益。然而，论文未报告计算成本，且未与 DAAO 等主流编排方法在统一骨干下对比，导致无法区分性能提升中形式化逻辑与模型能力的各自贡献。当骨干模型能力极强时，形式化验证的边际收益是否递减，论文未给出回答。
