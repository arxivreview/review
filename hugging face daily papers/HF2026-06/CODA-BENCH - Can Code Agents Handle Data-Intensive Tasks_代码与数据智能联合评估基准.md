# HuggingFace最新推荐论文 ｜CODA-BENCH: Can Code Agents Handle Data-Intensive Tasks? ｜代码与数据智能联合评估基准

研究机构：中国人民大学

作者：Yuxin Zhang、Ju Fan、Meihao Fan 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2606.15300)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2606.15300)

> 数据科学智能体（DSA）在真实开发场景中需同时具备代码生成能力与数据发现能力，但现有基准孤立评估二者，导致模型在隔离测试中的高分无法转化为实际生产力。CODA-BENCH 通过构建基于 Kaggle 生态的大规模数据密集环境，强制智能体在数百个语义相似文件中自主定位目标数据并执行代码，填补了联合评估的空白。该基准揭示了当前顶级智能体在数据发现环节的显著短板，为评估智能体从“代码助手”向“自主工程师”的演进提供了关键坐标，但其任务难度由对抗演化机制控制，是否完全映射真实业务噪声分布仍存疑。

## 研究背景

数据科学智能体（DSA）的核心困境在于环境感知的缺失。当智能体面对包含数百个文件的文件系统时，它无法直接感知哪些文件包含任务所需的数据，这种状态不可见性导致智能体可能基于错误假设执行代码，或陷入对无关数据的无效探索。解决此问题需要智能体具备数据智能（Data Intelligence），即在复杂数据景观中定位并利用正确信息源的能力，这与代码智能（Code Intelligence，即生成语法正确且逻辑合理的程序）共同构成自主数据科学家的双核心能力。

现有评估体系存在结构性割裂。代码中心基准（如 SWE-bench）假设数据已预置，仅评估代码修复或生成能力；数据中心基准（如 DA-Code、DS-1000）提供预清洗数据，仅评估数据处理逻辑，且多依赖独立 Python 脚本而非终端交互。这种孤立评估范式掩盖了真实开发中“数据发现”与“代码执行”的耦合依赖：一个无法在噪声中定位数据的智能体，其代码能力再强也无效。CODA-BENCH 的切入点正是打破这种割裂，通过构建包含大规模无关数据的环境，强制智能体在探索与执行之间建立闭环，从而评估其作为自主工程师的综合能力。

## 核心方法

### 方法参照系

本文问题属于智能体评估基准构建，但与传统基准的关键差异在于环境复杂度。传统基准（如 MLE-bench）提供最小必要数据集，而 CODA-BENCH 要求智能体在包含大量语义相似干扰项（Distractors）的环境中自主发现目标数据。这要求基准不仅评估代码正确性，还需评估数据定位的准确性，从而将评估维度从单一代码逻辑扩展至“发现-执行”双阶段。

### 基于共现图的数据密集环境构建

环境构建的核心挑战在于生成“分布内噪声”（In-distribution Noise），即干扰项需与目标数据共享主题和结构特征，使智能体无法通过关键词匹配或格式过滤轻松区分。本文利用 Kaggle 生态中数据集的自然共现模式解决此问题。设数据集集合 $D = \{d_1, \dots, d_n\}$，笔记本集合 $N = \{n_1, \dots, n_m\}$，构建无向加权图 $G = (D, E, w)$，边权重定义为共现频率：

$$ w(d_i, d_k) = \sum_{j=1}^{m} \mathbb{1}[d_i \in D_j \land d_k \in D_j] $$

该公式量化了两个数据集在人类工作流中同时被使用的频率，高权重边表示语义强关联。通过 Leiden 算法（$\gamma=1.0$）将图划分为 323 个社区，每个社区内的数据集构成一个语义连贯的环境。对于目标数据 $D^* \subset C_k$，环境包含 $C_k$ 中所有数据，其中 $C_k \setminus D^*$ 作为干扰项。这一设计确保了干扰项与目标数据在主题上高度相似，迫使智能体进行细粒度语义推理而非表面匹配，从而真实模拟了企业环境中“数据在噪声中”的困境。

### 对抗性任务演化与验证

初始任务可能过于简单，无法区分顶级智能体。本文引入对抗性演化框架，将任务难度提升建模为生成器 $G$ 与判别器集合 $F$ 的博弈。判别器集合由 $K$ 个随机采样的 LLM 组成，计算求解率：

$$ r_t = \frac{1}{K} \sum_{i=1}^{K} \mathbb{1}[F_i \text{ solves } q_{t-1}] $$

当 $r_t > \tau$（阈值 0.667）时，任务过易，$G$ 分析成功轨迹并增加难度；当 $r_t = 0$ 时，$G$ 诊断失败原因，若为任务缺陷（如歧义）则修复，若为真实难度则进入人工验证。这一机制动态平衡了任务难度与可解性，避免了静态任务集因模型进步而失效的问题，确保了基准对当前 SOTA 模型的区分度。

## 实验评估

实验在 Docker 沙箱中进行，环境包含 Python 3.11 及 pandas、numpy 等库，资源限制为 4GB 内存、2 CPU 核心、600 秒超时，数据目录只读。基线覆盖 Codex CLI、Claude Code、OpenHands 等主流框架，但缺失 VDSAgents、Tree-Notebook 等专用 DSA 方法，限制了与领域内最新架构的直接对比。

| 系统 | 模型 | CODA-BENCH DA (%) | CODA-BENCH EA (%) | CODA-HARD DA (%) | CODA-HARD EA (%) |
|---|---|---|---|---|---|
| Mini-SWE-agent | GPT-5.5 | **83.0** | **61.1** | 67.5 | **49.6** |
| OpenHands | GPT-5.5 | 82.1 | 59.7 | 63.2 | 44.5 |
| Claude Code | Opus-4.7 | 77.3 | 51.9 | 61.4 | 45.4 |
| Codex CLI | GPT-5.5 | 74.9 | 60.3 | 61.4 | 47.9 |

Mini-SWE-Agent 在 CODA-BENCH 上取得最高执行准确率（EA）61.1%，但发现准确率（DA）仅 83.0%，表明近 17% 的任务中智能体未能定位所有目标文件。在更难的 CODA-HARD 子集上，所有模型性能显著下降，Mini-SWE-Agent 的 EA 降至 49.6%，证实多源数据整合是核心瓶颈。模型-框架对齐影响显著：GPT 系列在 Mini-SWE-agent 中比原生 CLI 高 0.8% EA，而 Claude 系列在原生环境中表现更优（51.9% vs 49.3% EA），提示智能体脚手架与骨干模型的兼容性至关重要。

评估边界受限于任务来源。CODA-BENCH 任务源自 Kaggle 笔记本，其数据分布偏向数据科学竞赛场景，可能未覆盖企业级数据治理中的复杂合规约束或实时数据流处理。代码已开源，但沙箱环境配置（如 600 秒超时）可能影响长程任务的评估公平性，且未报告置信区间，数值比较需谨慎。

## 关联研究分析

从问题动机看，CODA-BENCH 与 DA-Code 均关注数据科学代码生成，但 DA-Code 提供预清洗数据，仅评估代码逻辑，而 CODA-BENCH 强制数据发现，暴露了智能体在环境探索中的短板。这一差异源于任务定义：DA-Code 假设数据已就绪，CODA-BENCH 模拟真实开发中数据需自主发现的场景。根源在于评估目标的差异——前者关注“能否写对代码”，后者关注“能否找到数据并写对代码”。

从方法设计看，CODA-BENCH 与 SWE-bench 同属真实环境评估，但 SWE-bench 聚焦代码修复，数据预置；CODA-BENCH 聚焦数据探索，数据需发现。SWE-bench 的仓库级评估思路被 CODA-BENCH 借鉴，但数据密集环境的构建方法（共现图+对抗演化）是本文独有。与 Tree-Notebook 相比，后者关注内部状态管理（数据影子），CODA-BENCH 关注外部环境噪声，二者互补：Tree-Notebook 解决“执行中状态不可见”，CODA-BENCH 解决“执行前数据不可见”。

## 总结

CODA-BENCH 旨在解决代码智能与数据智能孤立评估导致的基准-现实脱节问题。其切入点在于利用 Kaggle 生态的自然共现模式构建语义连贯的噪声环境，并通过对抗演化机制动态控制任务难度，从而强制智能体在发现与执行间建立闭环。实验表明，即使顶级智能体在 CODA-BENCH 上 EA 仅 61.1%，在 CODA-HARD 上降至 49.6%，数据发现仍是主要瓶颈。本文的边界在于任务源自 Kaggle 竞赛场景，可能未覆盖企业级数据治理的复杂约束，且缺乏与专用 DSA 架构的横向对比。当智能体在语义高度相似的干扰项中频繁误定位时，其代码能力的上限是否被数据发现能力所锁死，论文未给出回答。
