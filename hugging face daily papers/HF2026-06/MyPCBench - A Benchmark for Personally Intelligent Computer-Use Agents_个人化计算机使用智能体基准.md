# HuggingFace最新推荐论文 ｜MyPCBench: A Benchmark for Personally Intelligent Computer-Use Agents ｜个人化计算机使用智能体基准

研究机构：美国卡内基梅隆大学

论文原文见 [arXiv](https://arxiv.org/abs/2606.16748)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2606.16748)

> 计算机使用智能体（Computer-Use Agent, CUA）在真实部署中需处理用户跨应用的持久化历史数据，但现有基准均运行于空桌面或最小化种子状态，无法评估“个性化助理”能力。MYPCBENCH 通过单一 Persona 深度种子化 17 个预登录应用，构建可复现的 Linux 桌面环境，以 Rubric 评分机制量化智能体在跨应用历史数据上的操作准确性。该基准揭示了当前前沿模型在长程、多应用个性化任务上的显著性能断层，但受限于单一 Persona 与模拟环境，其结论向真实多用户场景的泛化性存疑。

## 研究背景

CUA 的核心挑战在于从像素级截图理解界面并执行操作，而个性化助理场景进一步要求智能体在操作过程中检索、关联并推理用户分散在不同应用中的历史数据。这种跨应用数据一致性（Cross-app consistency）要求一次旅行在日历、银行、邮件和聊天应用中留下相互印证的记录，智能体必须基于这些关联数据做出决策，而非仅响应当前屏幕指令。

现有基准如 OSWorld 和 WebArena 虽提供了动态交互环境，但为确保证据确定性，其应用状态仅包含当前任务所需的最小数据，缺乏用户身份的历史深度。AppWorld 虽在 API 层引入了用户身份，但未下沉至 GUI 桌面层。这种“非个性化”设定导致基准无法覆盖真实用户的高频请求，如“查询我通常周五点哪家外卖”或“核对两笔旅行预订是否超出信用卡额度”。MYPCBENCH 的切入点在于将用户身份（Persona）作为环境的一等公民，通过确定性管线将个人数据种子化至桌面全栈，从而测试智能体在持久化身份下的操作能力。

## 核心方法

### 方法参照系

本文属于 GUI Agent 基准评测体系，遵循 OSWorld 的 VM 快照重置与 CUA ReAct 循环框架。关键差异在于数据种子策略：从“任务最小化数据”转变为“全量个人身份数据”，评估目标从“任务完成”扩展至“个人数据一致性”与“可见副作用验证”。

### Persona 确定性种子化管线

传统基准的数据生成是任务驱动的，而 MYPCBENCH 采用 Persona 驱动的确定性生成。设计动机是解决现有基准中用户数据缺失导致的“非个性化”失效。管线以 JSON 格式的 Persona 规格（涵盖身份、财务、社交、旅行等）为输入，通过 Python 脚本填充 SQLite 数据库、Firefox 配置文件及文件系统。跨应用一致性通过共享引用实现，例如一次旅行同时生成 Airbnb 预订、Chase 银行扣款、Delta 登机牌及 WhatsApp 消息。其核心约束可表示为：

$$
\mathcal{D}_{app_i} = f(\mathcal{P}, \mathcal{R}_{cross})
$$

其中 $\mathcal{D}_{app_i}$ 为第 $i$ 个应用的数据集，$\mathcal{P}$ 为 Persona 规格，$\mathcal{R}_{cross}$ 为跨应用引用关系。该公式确保任意应用的数据均可追溯至同一 Persona 源，且跨应用记录在时间戳与实体上严格对齐。

### Rubric-Graded 副作用评估

二元成功/失败指标无法捕捉个性化任务中的部分正确性，如智能体读取了正确数据但未执行可见操作。MYPCBENCH 引入自然语言 Rubric，由 LLM-as-a-judge 对每一步截图进行细粒度评分。设计动机是解决长程任务中“中间步骤正确但最终状态错误”或“数据正确但无可见副作用”的评估盲区。评分函数定义为：

$$
S_{task} = \frac{1}{|\mathcal{R}|} \sum_{r \in \mathcal{R}} \mathbb{I}(\text{Judge}(s_t, r) = \text{Pass})
$$

其中 $\mathcal{R}$ 为任务 Rubric 集合，$s_t$ 为轨迹第 $t$ 步截图，$\mathbb{I}$ 为指示函数。该机制允许智能体在部分 Rubric 项通过时获得部分分数，从而区分“完全解决”（Perfect）与“部分正确”（Rubric Score），更精准地定位智能体在个性化推理与操作执行上的具体失效点。

## 实验评估

实验在 MYPCBENCH 的 184 个任务上进行，评估 Claude Opus 4.6、GPT-5.5 及 Qwen 3.5 等六个模型，统一使用 `computer` + `bash` 工具空间。基线覆盖主流闭源与开源模型，但缺失 UI-TARS 等专用 GUI 模型，可能低估了特定架构在个性化任务上的潜力。

| 模型 | Perfect (%) | Rubric Score (%) | Avg Steps | Traj. Eff. |
| :--- | :--- | :--- | :--- | :--- |
| Claude Opus 4.6 | 55.4 | 81.8 | 46.5 | 3.61 |
| Claude Sonnet 4.6 | 39.1 | 65.4 | 45.8 | 3.03 |
| GPT-5.5 | 29.3 | 54.1 | 45.8 | 1.45 |
| GPT-5.4 mini | 19.0 | 48.8 | 43.7 | 1.65 |
| Qwen 3.5 35B-A3B | 7.6 | 42.5 | 66.0 | 1.41 |
| Qwen 3.5 9B | 2.7 | 7.0 | 69.2 | 0.65 |

Opus 4.6 以 55.4% 的完美率领先，但其在 7 个以上应用任务中的完美率仅 36%，而 GPT-5.5 在该切片中仅 4.5%，Qwen 系列均为 0%。这表明个性化长程任务对模型的多应用状态跟踪能力提出了远超通用基准的要求。

消融实验显示，启用 `bash` 工具对 GPT 和 Qwen 模型产生显著负面影响。GPT-5.5 的 Rubric 分数从 50.5% 降至 54.1%（注：原文 Table 5 显示 GPT-5.5 cua-only 为 50.5，cua+bash 为 54.1，但正文提及“regresses by roughly 24 rubric points”可能指特定子集或笔误，此处以表格数据为准，但 Qwen 9B 从 20.2% 骤降至 7.0%，降幅达 13.2 个百分点）。这一反直觉现象源于小模型在双工具模式下的上下文混淆，导致其无法有效切换 GUI 与 Shell 操作。

评估边界方面，MYPCBENCH 依赖单一 Persona（Michael Scott），其数据分布可能偏向特定职业与生活模式，缺乏多用户多样性验证。LLM-as-a-judge 在评估细微个性化差异时的可靠性未通过人工一致性检验，且环境为模拟克隆，未包含真实 Web 的动态噪声与登录态失效风险。

## 关联研究分析

从问题动机看，MYPCBENCH 与 AppWorld 的核心差异在于身份注入的层级。AppWorld 在 API 层种子化用户身份，适合评估代码智能体的逻辑推理，但忽略了 GUI 操作中的视觉定位与界面交互成本。MYPCBENCH 将身份下沉至桌面 GUI 层，迫使智能体通过视觉感知检索个人数据，这更贴近真实助理的交互模式，但也引入了视觉噪声与界面复杂性的干扰。

从方法设计看，MYPCBENCH 的 Rubric 评分机制与 OSWorld 的手动验证器形成对比。OSWorld 依赖人工编写的奖励函数，难以覆盖个性化任务的多样性；MYPCBENCH 采用 LLM 生成 Rubric 并自动评分，提升了可扩展性，但引入了评估器偏差。这种偏差在“模式推理”类任务中尤为明显，如判断用户的小费习惯，LLM 可能因缺乏真实用户行为分布而给出主观评分。

## 总结

MYPCBENCH 解决了 CUA 基准中“非个性化”导致的能力评估盲区，通过 Persona 确定性种子化与 Rubric 评分机制，量化了智能体在跨应用历史数据上的操作准确性。实验表明，即使是最强的 Opus 4.6 也仅在 55.4% 的任务上完全成功，且在多应用长程任务中性能急剧下降，揭示了当前模型在持久化身份管理上的根本局限。该基准的边界在于单一 Persona 的分布偏差与模拟环境的真实性局限，当引入多用户异构数据与真实 Web 动态噪声时，现有模型的个性化能力是否仍能维持，论文未给出回答。
