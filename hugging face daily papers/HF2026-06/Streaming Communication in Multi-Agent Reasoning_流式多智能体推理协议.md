> 多智能体系统长期受困于“生成-传输”串行瓶颈，导致延迟随管道深度线性增长且下游智能体被迫等待完整响应。现有拓扑优化与强化学习路线聚焦于结构或策略，却忽视了通信时序对推理质量的潜在影响。本文提出STREAMMA，将传输单元从完整响应细化为推理步，实现流水线并行。该协议在降低延迟的同时意外提升了准确率，但其在动态拓扑下的泛化性及步级质量分布的在线估计机制仍存疑。

## 研究背景

多智能体大语言模型系统（Multi-Agent LLM Systems, MAS）通常将智能体组织为有向无环图（DAG），通过角色分工与交叉验证提升复杂任务性能。然而，主流框架普遍采用“生成-传输”（Serial）协议，即上游智能体必须完成全部响应后，下游智能体方可开始执行。这种阻塞式通信导致端到端延迟与管道深度成正比，且下游智能体在等待期间处于空闲状态，无法利用上游已生成的部分信息进行并行处理。

在单模型内部，流式推理（Streaming Inference）已成为标准配置，允许逐token或逐块输出。但在多智能体间，传输单元始终被锁定为完整响应，其对流式推理质量的影响未被充分探索。传统直觉认为“信息越多决策越好”，但多步推理中存在步级质量非均匀性：早期步骤通常可靠，而后期步骤因误差累积而质量下降（Wu et al., 2025）。这一特性意味着，强制下游智能体接收包含错误后期步骤的完整响应，可能反而引入噪声。本文切入点在于：能否通过改变通信粒度，让下游智能体仅接收早期可靠步骤，从而在降低延迟的同时提升推理质量？

## 核心方法

### 通信协议参照系

现有MAS通信协议以Serial为基线，其核心特征是阻塞式消息传递：上游智能体调用LLM生成完整响应后，才将结果推送至下游队列。该流程确保了下游智能体拥有完整上下文，但牺牲了并行性。本文问题与该通用流程的关键差异在于传输时序：Serial关注“何时传输完整结果”，而STREAMMA关注“何时传输部分结果”。

### 步级流式传输机制

STREAMMA将传输单元从完整响应细化为推理步（Reasoning Step）。在算法执行中，上游智能体发起流式调用，每生成一个步骤立即推送至下游队列，无需等待后续步骤。下游智能体在接收到早期步骤后即刻开始推理，形成流水线并行。这一设计利用了步级质量的非均匀性：下游智能体从最可靠的前缀开始构建独立推理轨迹，当后期低质量步骤到达时，其影响已被稀释。

$$
\mu_j = p_j \delta - (1 - p_j) \epsilon
$$

其中 $\mu_j$ 为第 $j$ 步对下游步级正确率的期望变化，$p_j$ 为第 $j$ 步正确概率，$\delta$ 和 $\epsilon$ 分别为正确与错误步骤的影响幅度。该公式表明，当 $p_j$ 高于阈值 $p^* = \epsilon/(\delta+\epsilon)$ 时，该步骤对下游有益；反之则有害。Stream协议通过优先传递高 $p_j$ 的早期步骤，最大化了 $\mu_j$ 的正向累积。

### 理论边界与效率分析

STREAMMA的有效性依赖于步级正确率分布。定理1给出了Stream、Serial、Single三种模式在六种步级正确率分布下的有效性排序。当早期步骤可靠而后期步骤退化时（Case I），Stream最优；当所有步骤均可靠时（Case II），Serial最优；当所有步骤均不可靠时（Case III），Single最优。

$$
\text{Speedup} = \frac{A(S + r_{po})}{(S + A - 1)(1 + \alpha r_{vdp} + \beta r_{vdc})}
$$

该公式给出了Stream相对于Serial的延迟加速上界，其中 $A$ 为智能体数量，$S$ 为每智能体步数，$r_{vdp}$ 和 $r_{vdc}$ 分别为解码与预填充、解码与缓存读取的速度比。当缓存读取速度远大于预填充和解码速度时，加速比趋近于 $AS/(S+A-1)$，表明Stream在理想服务条件下可实现接近线性的加速。

## 实验评估

实验在AIME 2025/26、HMMT 2026、GPQA-Diamond、HLE及LiveCodeBench等八个基准上进行，使用Claude Opus 4.6和GPT-5.4两个前沿模型，评估Chain、Tree、Graph三种拓扑。基线包括Single（单智能体）和Serial（串行多智能体）。STREAMMA在Claude Opus 4.6上平均提升+7.3 pp，峰值+22.4 pp（HMMT 2026, Chain）；在GPT-5.4上平均提升+1.5 pp。

| 基准 | 模型 | 拓扑 | Single | Serial | STREAMMA |
| :--- | :--- | :--- | :--- | :--- | :--- |
| HMMT 2026 | Claude Opus 4.6 | Chain | - | 61.75 | 84.10 |
| HMMT 2026 | Claude Opus 4.6 | Tree | - | 75.00 | 82.20 |
| HMMT 2026 | GPT-5.4 | Chain | - | - | 73.50 |

注：表中数值仅展示部分关键结果，完整数据见原文Table 1。STREAMMA在HMMT 2026 Chain拓扑下，Claude Opus 4.6的准确率从Serial的61.75%提升至84.10%，验证了步级流式传输在复杂数学推理中的有效性。

消融实验通过步级扰动验证了机制：仅破坏上游轨迹的尾部步骤，Stream仍领先Serial +24.0 pp；仅破坏头部步骤，Stream落后Serial -36.0 pp。这证实了Stream的优势源于对早期可靠步骤的利用，而非单纯的信息量增加。

评估边界方面，实验未报告置信区间，且仅对比了Serial和Single，未与GPTSwarm、G-Designer等动态拓扑优化方法直接对比。代码已开源，但步级质量分布的在线估计机制未在实验中实现，依赖离线假设。

## 关联研究分析

从问题动机看，STREAMMA与GPTSwarm等动态拓扑优化方法形成互补。GPTSwarm聚焦于优化DAG结构本身，通过强化学习调整连接权重，解决固定拓扑无法适应任务复杂度的问题；而STREAMMA固定拓扑，仅优化边上的信息传输时序。两者正交：GPTSwarm决定“谁与谁通信”，STREAMMA决定“何时通信”。STREAMMA的发现挑战了“更多智能体必然提升性能”的共识，指出在固定智能体数量下，增加每智能体步数（Step-level Scaling）是另一条正交扩展轴，且能同时提升效果与速度。

从方法设计看，STREAMMA与KVCOMM等利用KV-cache优化通信效率的方法有相似之处，均旨在降低重复计算成本。但KVCOMM侧重跨上下文缓存复用，而STREAMMA侧重步级流式传输带来的推理质量提升。STREAMMA的步级流式机制依赖于LLM服务端的流式API支持，这在当前前沿模型中已普及，但其对步级质量分布的假设（早期可靠、后期退化）在特定任务（如自我修正任务）下可能失效，此时Serial可能更优。

## 总结

STREAMMA解决了多智能体系统中通信时序与推理质量的矛盾，通过步级流式传输利用早期步骤的可靠性，在降低延迟的同时提升准确率。其核心贡献在于揭示了“何时传输”比“传输多少”对推理质量影响更大，并提供了理论边界与效率分析。实验证明在Claude Opus 4.6上平均提升+7.3 pp，峰值+22.4 pp。然而，该协议的有效性依赖于步级质量分布的特定模式，且在动态拓扑下的表现未经验证。当任务特性导致步级质量分布非单调（如后期步骤自我修正）时，Stream协议是否仍优于Serial，论文未给出回答。
