# HuggingFace最新推荐论文 ｜Socratic-SWE: Self-Evolving Coding Agents via Trace-Derived Agent Skills ｜轨迹驱动的技能自进化软件工程智能体

研究机构：阿里巴巴集团、上海交通大学

作者：Chuan Xiao、Zhengbo Jiao、Shaobo Wang 等 8 人

论文原文见 [arXiv](https://arxiv.org/abs/2606.07412)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2606.07412)

> 软件工程智能体训练长期受限于高质量任务数据的稀缺与静态分布的僵化，现有合成方法生成的任务往往与模型当前的能力边界脱节，导致训练信号迅速稀疏化。Socratic-SWE 的切入点在于将智能体自身产生的解题轨迹转化为结构化的“技能”，并以此动态指导下一轮任务的生成，从而构建一个闭环的自进化系统。该方法通过技能引导的任务生成与执行接地验证，在固定计算预算下显著提升了小模型在仓库级修复任务上的表现。其核心贡献在于证明了内生轨迹比外部静态规则更能有效驱动模型能力的持续迭代，但其在大规模仓库池耗尽后的扩展性仍存疑。

## 研究背景

当智能体在真实代码仓库中执行修复任务时，其交互轨迹记录了从代码搜索、文件编辑到测试运行的完整过程。这些轨迹不仅包含最终结果，更暴露了模型在特定仓库模式下的反复失败点与有效修复策略。然而，传统强化学习范式（如 GRPO）通常将轨迹压缩为标量奖励用于信用分配，一旦监督信号计算完毕，轨迹即被丢弃。这种处理方式忽略了轨迹中蕴含的关于模型能力边界的丰富信息，导致随着模型能力提升，固定任务分布中仍能提供有效训练信号的比例急剧下降，学习过程陷入停滞。

软件工程智能体的训练数据构建长期依赖 AST 变异、LM 重写或固定 Bug 注入等静态合成管线。这些方法生成的任务分布独立于智能体的训练经验，往往过于简单或与模型弱点不对齐。SWE-RL 和 SWE-Gym 等先驱工作确立了执行接地验证的重要性，但未能解决数据分布与模型能力动态演进之间的错位问题。Socratic-SWE 针对这一瓶颈，提出将历史轨迹蒸馏为可检索的技能注册表，使任务生成过程能够感知并针对模型当前的能力缺口，从而在有限数据预算下实现更高效的自进化。

## 核心方法

### 方法参照系

Socratic-SWE 属于自我进化智能体框架，其核心差异在于摒弃了依赖外部教师模型或固定规则的任务生成机制，转而利用智能体自身的解题轨迹作为课程设计的唯一信号源。与 Socratic-Zero 等使用外部 Teacher 的方法不同，该框架通过内部闭环实现技能提取与任务生成的协同优化，避免了外部知识蒸馏中的信息损失。

### 技能注册表与轨迹蒸馏

该模块解决了静态任务分布无法适应模型能力演进的问题。系统首先收集智能体在种子任务上的解题轨迹，将其分为成功与失败两类。随后，利用蒸馏模型 $M_{distill}$ 从轨迹中提取结构化技能 $S$，每个技能包含名称、描述、适用条件及操作序列。技能注册表通过语义去重与覆盖率过滤构建，确保技能既具备泛化性又扎根于真实行为。这一设计使得 Generator 能够基于具体的行为模式（如“迭代 grep-then-edit”）而非抽象规则来生成任务，从而精准定位模型的能力缺口。

$$ S = \text{Dedup}(\{s_i \mid s_i \sim M_{distill}(T), \text{Coverage}(s_i) > \delta\}) $$

该公式表明，最终技能集 $S$ 是通过筛选那些在轨迹中具备足够覆盖度且语义不重复的候选技能得到的，确保了技能库的紧凑性与代表性。

### 梯度对齐的任务生成与验证

在技能引导任务生成后，系统引入执行接地验证与梯度对齐奖励，以确保生成任务的有效性与训练价值。Generator 基于技能 $s$ 和仓库 $r$ 生成候选任务 $(\tau, v)$，该任务需通过格式、接地、执行及语义四重验证。验证通过后，系统计算 Solver 在该任务上的策略梯度 $g_\tau$，并与保留验证集上的目标梯度 $G_v$ 进行余弦相似度对齐。这一机制确保生成的任务不仅可解，而且其引发的模型更新方向与整体优化目标一致，避免了无效或负向的任务进入训练集。

$$ R_G(\tau, v) = \mathbb{1}[\text{Valid}(\tau, v)] \cdot \cos(g_\tau, G_v) $$

该奖励函数通过验证门控与梯度对齐项的乘积，强制 Generator 优先产生那些既能通过执行验证，又能引导 Solver 向正确方向更新的任务，实现了任务质量与训练效用的双重约束。

## 实验评估

实验在 SWE-bench Verified、Lite、Pro 及 Terminal-Bench 2.0 上进行，基线包括 R-Zero、SPIRAL、Absolute-Zero、Socratic-Zero 和 SSR。所有方法使用相同的 Qwen3.5-9B 骨干、36k 实例预算及 mini-swe-agent 执行框架。Socratic-SWE 在三个迭代后于 SWE-bench Verified 上达到 50.40%，较基线提升 7.80 个百分点，显著优于最强基线 SSR 的 47.00%。

| 方法 | SWE-bench Verified | SWE-bench Lite | SWE-bench Pro | Terminal-Bench 2.0 |
|---|---|---|---|---|
| Base Agent | 42.60 | 29.67 | 17.24 | 10.11 |
| SSR (Iter 3) | 47.00 | 34.00 | 20.66 | 12.36 |
| Socratic-SWE (Iter 3) | 50.40 | 36.67 | 22.85 | 14.61 |

消融实验显示，移除技能注册表导致性能下降 4.20 个百分点，是各组件中影响最大的因素，证实了课程设计的核心驱动作用。将轨迹蒸馏替换为手动技能导致下降 2.40 个百分点，表明手写分类法无法捕捉如“迭代搜索-编辑”等细微行为模式。将 GDPO 替换为 GRPO 导致下降 1.80 个百分点，说明分解奖励学习在处理部分正确补丁时优于二元通过/失败信号。

评估边界方面，实验仅使用 9B 小模型，未验证大模型下的扩展性；技能提取依赖 Qwen3.6-27B，其成本与延迟未详细报告；代码未开源，超参数细节缺失，限制了可复现性。此外，实验未涵盖多语言或跨域泛化的深度分析，Terminal-Bench 2.0 的结果虽显示正向迁移，但样本量有限。

## 关联研究分析

从问题动机看，Socratic-SWE 与 SSR 的核心差异在于任务生成的自适应机制。SSR 依赖固定 Bug 注入规则，其生成的任务分布静态且独立于模型状态，导致在迭代后期迅速耗尽“低垂果实”，性能增长趋于平缓。Socratic-SWE 通过技能注册表动态调整任务难度与类型，使训练信号始终针对模型当前的能力边界，从而在相同预算下实现更持续的增益。这一差异源于对“数据-模型”耦合关系的处理：SSR 视数据为独立资源，而 Socratic-SWE 视数据为模型状态的函数。

从方法设计看，Socratic-SWE 与 Socratic-Zero 均采用师生协同框架，但知识来源截然不同。Socratic-Zero 依赖 397B 参数外部 Teacher 生成任务，其上限受限于 Teacher 的领域理解，且在蒸馏过程中可能丢失细粒度行为信息。Socratic-SWE 摒弃外部 Teacher，转而利用自身轨迹蒸馏技能，实现了完全内生闭环。这种设计降低了对外部大模型的依赖，但引入了技能提取的准确性风险。实验表明，即使使用较小的 Qwen3.5-9B 进行自我提取，性能仅下降 0.60 个百分点，说明框架对提取器规模的鲁棒性较强，核心优势源于闭环机制而非提取器能力。

## 总结

Socratic-SWE 旨在解决软件工程智能体训练中数据分布与模型能力动态脱节的核心矛盾。现有静态合成方法无法感知模型弱点，导致训练信号稀疏化；本文通过轨迹蒸馏为技能、技能引导任务生成及梯度对齐验证，构建了内生自进化闭环。在 36k 实例预算下，该方法在 SWE-bench Verified 上取得 50.40% 的准确率，较基线提升 7.80 个百分点，显著优于 SSR 等静态基线。然而，实验仅验证了 9B 小模型在有限仓库池上的表现，未探讨当仓库池耗尽或任务复杂度急剧增加时，技能注册表的泛化能力是否依然有效。当训练迭代超过 5 轮后，技能库的语义漂移是否会导致任务生成质量下降，论文未给出回答。
