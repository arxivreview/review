> 工业级数据工程要求工作流资产具备可视化、可编辑与可复用特性，而当前编码智能体仅能生成一次性脚本，导致生产环境中的审计与治理失效。DataFlow-Harness 通过引入“NL2Pipeline Gap”概念，指出自然语言意图与持久化平台资产间的断层是核心瓶颈。该系统结合程序性技能、实时模型上下文协议接地与类型化突变机制，引导智能体构建原生有向无环图。其价值在于以显著降低的成本实现了接近脚本生成的可靠性，但语义正确性的验证仍依赖外部人工干预。

## 研究背景

当大语言模型被部署于合成数据生成或检索增强等场景时，其输出的代码往往以孤立脚本形式存在。这种“一次性”产物无法被图形化工作流接口解析，导致依赖关系不可见，且常因幻觉调用不存在的算子而失败。这一现象揭示了自然语言指令与结构化执行环境之间的语义鸿沟，即模型缺乏对平台特定算子注册表与当前管道状态的实时感知能力。

数据科学智能体领域长期关注从数据清洗到洞察生成的全生命周期自动化，主流路线多聚焦于单体智能体的代码生成能力或多智能体协作的任务分解。然而，这些方案普遍将工作流视为静态代码片段，忽视了工业部署中对资产持久化、版本控制及交互式编辑的刚性需求。现有基准如 DS-1000 主要评估代码片段正确性，缺乏对完整工作流可治理性的考察。DataFlow-Harness 的切入点在于将工作流构建视为一个受平台语义约束的状态转换过程，而非单纯的代码生成任务，从而解决脚本无法集成至宿主平台的问题。

## 核心方法

### 平台接地与类型化突变

传统编码智能体依赖参数化记忆生成代码，其动作空间为任意 Python 语句，缺乏对执行环境的实时反馈。DataFlow-Harness 将动作空间限制为平台原生的类型化突变操作，通过模型上下文协议（MCP）实时获取算子注册表与管道状态。管道被形式化为五元组 $P = (D, O, E, S, R)$，其中 $D$ 为数据源，$O$ 为算子实例，$E \subseteq O \times O$ 为依赖边，$S$ 为字段模式，$R$ 为运行时状态。智能体不直接生成代码，而是通过 MCP 工具调用发出结构化突变请求，如添加算子或更新参数。这种设计动机在于消除脚本生成中常见的依赖幻觉，确保每个操作都基于真实的平台元数据。

### 程序性技能注入与验证闭环

仅暴露算子元数据不足以指导复杂组装，智能体可能选择结构有效但语义错误的算子组合。DataFlow-Skills 注入两类程序性知识：定义推荐构建序列的“程序性蓝图”和捕捉算子兼容性的“组合约束”。在每次突变提交前，系统执行双重验证：检查更新后的图是否保持无环，以及相邻算子的输入输出模式是否兼容。验证公式可表示为：

$$ V(P') = \mathbb{I}[\text{Acyclic}(P')] \cdot \mathbb{I}[\forall (u,v) \in E', S_u^{out} \subseteq S_v^{in}] $$

其中 $P'$ 为突变后的管道，$S_u^{out}$ 与 $S_v^{in}$ 分别为算子 $u$ 的输出与算子 $v$ 的输入模式。该机制解决了纯工具接地（MCP-only）在复杂任务中成功率骤降的问题，通过显式程序性指导弥补了元数据在策略层面的缺失，实现了从“能执行”到“正确执行”的跨越。

## 实验评估

实验在包含 12 个工业数据工程任务的基准上进行，涵盖问答生成、文档处理等场景，所有配置均使用 Claude Opus 4.7 作为底层模型，每个任务重复 10 次。基线包括无约束的 Vanilla CC、提供代码库的 Context-Aware CC 及仅使用 MCP 的 MCP-only。

| 方法 | 产物类型 | E2E Pass (%) | Tokens (In/Out) | Cost ($) | Latency (s) |
|---|---|---|---|---|---|
| Vanilla CC | Disposable Script | 91.7 | 153,584 / 2,474 | 0.950 | 190.7 |
| Context-Aware CC | Disposable Script | **94.2** | 185,626 / 1,140 | 0.456 | 115.9 |
| MCP-only | Native DAG | 83.3 | 100,607 / 1,273 | 0.321 | 105.5 |
| DataFlow-Harness | Native DAG | 93.3 | **74,958 / 891** | **0.261** | **95.5** |

DataFlow-Harness 的端到端通过率（93.3%）与最强的脚本基线 Context-Aware CC（94.2%）仅差 0.9 个百分点，但成本降低 42.8%，延迟降低 17.6%。相比之下，MCP-only 基线在缺乏程序性指导时通过率降至 83.3%，表明单纯的平台接地不足以应对复杂组装，Skills 的引入恢复了 10.0 个百分点的性能。

消融分析显示，Skills 在依赖隐式程序性知识的任务中收益最大。在下游训练效用评估中，DataFlow-Harness 构建的数学数据管道在微调 Qwen2.5-32B-Instruct 后，AIME24@32 准确率从 25.1% 提升至 35.9%，表明接地机制不仅提升了构建可靠性，还通过更有效的验证与去重产生了更高质量的训练数据。

评估边界方面，实验仅使用单一模型家族（Claude Opus 4.7）和平台特定基准，未报告任务聚类置信区间。代码已开源，但缺乏对并发编辑、持久化恢复等治理特性的直接测试。成本计算未区分提示缓存的影响，需独立重算。

## 关联研究分析

从问题动机看，Tree-Notebook 聚焦于交互式数据科学中的状态不可见性与静默失败，通过树搜索和熵感知数据影子重建 DataFrame 状态，其核心是解决“分析过程中的状态漂移”。DataFlow-Harness 则关注“构建过程中的资产持久化”，其状态管理针对的是管道结构而非数据内容。两者的差异源于任务阶段的不同：Tree-Notebook 处于分析执行阶段，需动态适应数据变化；DataFlow-Harness 处于工作流设计阶段，需静态保证结构合法性。这种差异暗示，状态感知机制在构建阶段可简化为结构验证，而在分析阶段则需复杂的语义探针。

从方法设计看，VDSAgents 采用多智能体协作，通过角色分工缓解长上下文注意力稀释，适用于复杂多步分析任务。DataFlow-Harness 坚持单体智能体架构，依赖 MCP 实时接地与 Skills 程序性指导来维持上下文聚焦。这一选择与领域共识中“多智能体优于单体”的观点相悖，但论文实验表明，在受平台约束的构建任务中，单体架构配合强接地机制足以达到高可靠性，且避免了多智能体通信开销。这提示我们，架构选择应取决于任务的状态空间复杂度：当动作空间被严格限制（如仅允许类型化突变）时，单体智能体的上下文瓶颈可能不再是主要矛盾。

## 总结

DataFlow-Harness 旨在解决自然语言意图与工业级持久化工作流资产之间的断层，即 NL2Pipeline Gap。现有编码智能体生成的脚本缺乏可审计性与可复用性，无法集成至平台治理机制。本文通过结合程序性 Skills、实时 MCP 接地与类型化突变验证，引导智能体构建原生 DAG，在 12 任务基准上实现了 93.3% 的端到端通过率，成本较脚本基线降低 72.5%。该结果证明了结构化编排在保证可靠性的同时能显著降低计算成本。然而，实验仅覆盖单一模型家族与平台特定场景，且未对语义正确性进行独立验证，结构验证无法保证输出质量。当任务涉及高度非标准化的算子组合时，程序性 Skills 的泛化边界是否会导致智能体陷入局部最优，论文未给出回答。
