研究机构：美国威斯康星大学麦迪逊分校

作者：Tzu-Heng Huang、Shengqi Qiu、Frederic Sala

论文原文见 [arXiv](https://arxiv.org/abs/2607.22561)

> 大语言模型评估者（LLM-as-a-Judge）在规模化部署中面临高昂的推理成本与决策逻辑不透明两大瓶颈，导致其在大规模对齐流水线中难以扩展。现有方法依赖每次评估时的模型前向传播，无法消除对专有API的依赖，且难以审计内部判断依据。PAJAMA通过一次性将LLM的评判逻辑蒸馏为可执行的Python程序，以本地代码执行替代实时模型推理，实现了成本与透明度的解耦。该范式在特定任务上以极低成本匹配了中等规模LLM的性能，但其对复杂语义推理的覆盖能力仍存疑。

## 研究背景

当评估者需要处理数百万条样本时，每次调用GPT-4或开源大模型进行推理产生的API费用与GPU延迟构成了不可接受的开销。这种成本随数据量线性增长的特性，使得基于模型的评估在大规模奖励模型蒸馏中变得昂贵。同时，模型内部的决策过程是黑盒，即使生成了解释文本，也无法验证其是否真正遵循了预设的评分标准，这种不透明性阻碍了对评估偏差的系统性审计。

LLM-as-a-Judge的主流路线通过提示工程或微调专用模型（如Prometheus）来提升评估准确性，但均保留了“每次评估需调用模型”的核心架构。这导致两个固有缺陷：一是计算成本无法通过优化模型结构来根本性降低，二是评估逻辑难以被外部干预或形式化验证。现有偏差缓解方法（如位置交换、集成投票）仅能校正模型输出的统计偏差，无法消除模型内部对冗长或格式特征的隐性偏好。PAJAMA的切入点在于改变评估的执行载体：不再让模型在推理时做判断，而是让模型在合成时生成判断逻辑，将评估过程转化为确定性的程序执行。

## 核心方法

### 方法参照系

本文问题属于自动化评估中的“标签生成”环节，但与传统弱监督（Weak Supervision）框架存在关键差异。标准弱监督依赖启发式规则或预训练模型生成噪声标签，而PAJAMA利用LLM合成具有复杂语义理解能力的程序作为标签函数，并将程序输出视为噪声源进行聚合。

### 程序化评判合成与校准

传统LLM评判在每次评估时重新执行推理，导致成本随样本数线性增加。PAJAMA将这一过程前置为一次性的程序合成：通过提示LLM生成Python函数，该函数接收查询与响应，返回标量分数。为解决单一程序泛化不足的问题，系统引入10种预设评估标准（Rubric）引导合成，并通过文本相似度过滤重复逻辑。程序输出需经过校准以消除尺度差异，其核心公式为：

$$ d_{ij} = \hat{s}^{(1)}_{ij} - \hat{s}^{(2)}_{ij} $$

其中 $\hat{s}$ 为经过Min-Max归一化后的分数，$d_{ij}$ 表示程序 $j$ 对样本 $i$ 两个响应的质量差。该差值通过与阈值 $\tau_j$ 比较转化为离散投票 $v_{ij} \in \{-1, 0, +1\}$，阈值通过验证集最大化准确率确定，允许程序在信号弱时弃权，从而提升单票可靠性。

### 弱监督聚合与置信度路由

单个程序的投票存在噪声且可能冲突，直接多数投票无法利用程序间的互补性。PAJAMA借鉴Snorkel框架，将Top-k程序的投票矩阵 $L \in \{-1, 0, +1\}^{N \times k}$ 输入标签模型，学习每个程序的聚合权重，最终输出联合偏好概率。这一设计解决了程序间评分标准不一致导致的冲突问题。对于程序委员会弃权或后验概率接近0.5的低置信样本，系统利用投票方差或聚合后验作为路由信号，将其升级至LLM评判。该机制实现了“程序处理简单样本，LLM处理复杂样本”的混合架构，在保持高吞吐的同时提升了整体准确率。

## 实验评估

实验在JudgeLM、PandaLM等5个偏好数据集上验证，基线覆盖GPT-4.1、GPT-5 Thinking、OLMO-2、GEMMA-3及QWEN2.5系列，但未包含Prometheus 2等专用微调裁判模型。主结果显示，PAJAMA平均准确率为78.11%，与OLMO-2-13B-INSTRUCT持平，比GPT-5 Thinking低8个百分点，但吞吐量比GEMMA-3-270M-IT快2.12倍，比QWEN2.5-14B-INSTRUCT快约50倍。

| 评估维度 | PAJAMA | 对比基线 | 关键指标 |
| :--- | :--- | :--- | :--- |
| 平均准确率 | 78.11% | OLMO-2-13B-INSTRUCT | 持平 |
| 吞吐量 | - | GEMMA-3-270M-IT | 2.12× faster |
| 吞吐量 | - | QWEN2.5-14B-INSTRUCT | ~50× faster |

在奖励模型蒸馏任务中，PAJAMA标签训练出的QWEN2.5-3B-INSTRUCT在RewardBench上平均得分56.65%（Prometheus数据集），高于GPT-4标签训练的54.98%，且API成本从$363.97降至$7.21，降低50倍。消融实验表明，使用聚合后验作为路由信号时，混合系统比纯LLM评估在OLMO-2-7B-INSTRUCT上提升5%准确率，同时吞吐量提高2.9倍。

评估边界方面，论文未报告置信区间，且程序合成依赖Claude Opus 4.6，存在对特定LLM能力的依赖。代码已开源，但程序库的构建依赖人工设计的10种Rubric，自动化程度有限。

## 关联研究分析

从问题动机看，PAJAMA与TrustJudge等偏差缓解方法存在根本差异。TrustJudge通过困惑度（PPL）打破平局并转换评分，仍依赖LLM的实时推理，其目标是校正模型输出的统计偏差；PAJAMA则通过程序执行彻底移除推理环节，其鲁棒性源于代码逻辑的确定性而非模型校准。这种差异源于任务特性：当评估标准可形式化（如逻辑连贯性、格式规范）时，程序执行优于模型推理；但在主观性极强的创意任务中，程序逻辑的表达力可能不足，论文未对此进行验证。

从方法设计看，PAJAMA与Prometheus等专用裁判模型形成互补。Prometheus通过指令微调内化评估标准，适合固定任务的长期部署，但训练成本高且缺乏灵活性；PAJAMA通过程序合成实现零训练成本，且可通过编辑代码快速调整评估标准，适合动态变化的评估场景。然而，PAJAMA的程序多样性受限于预设Rubric，若评估维度超出这10种标准，程序库的覆盖能力将受限，而Prometheus可通过微调适应新标准。

## 总结

PAJAMA解决了LLM评估中成本与透明度的核心矛盾，通过程序蒸馏将评估从“每次推理”转变为“一次合成+本地执行”，在RewardBench蒸馏任务中以50倍成本优势超越GPT-4标签，并在混合路由下推进了准确率-吞吐量帕累托前沿。其边界在于程序逻辑的表达力受限于预设Rubric，且对复杂语义推理的覆盖能力未充分验证。当评估任务涉及高度抽象或跨领域推理时，程序化评判的准确率是否仍能维持与中等规模LLM的持平，论文未给出回答。
