# HuggingFace最新推荐论文 ｜DocOps: A Verifiable Benchmark for Autonomous Agents in Complex Document Operations ｜文档操作智能体评估基准

研究机构：中国科学院、中国科学院大学

论文原文见 [arXiv](https://arxiv.org/abs/2607.19865)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2607.19865)

> 现有文档智能体评估基准将文档视为只读知识库或应用间传递的被动数据，无法量化智能体在长程操作中维持文档原生状态一致性的能力。DocOps 通过构建包含原子操作与跨文档工作流的分层分类法，并引入基于原生文档库的确定性验证器，系统性地暴露了当前前沿模型在复杂文档操作中的状态追踪崩溃与破坏性编辑瓶颈。该框架将评估焦点从“任务完成”转向“状态保持”，为文档智能体的可靠性诊断提供了可复现的实证基础，但其合成任务构造与固定执行框架的设定限制了结论向开放域真实场景的直接外推。

## 研究背景

当智能体执行多步文档编辑时，局部操作的正确性并不保证全局文档结构的完整性。这种局部与全局状态的脱节源于文档作为“有状态计算对象”的特性：每个编辑操作不仅是内容变更，更是对底层结构（如公式引用、层级大纲、工作表依赖）的状态转移。若智能体缺乏对文档原生状态的持续追踪，早期错误将沿工作流传播，导致最终产物在表面可读但结构失效。

文档智能体评估长期存在范式割裂：静态框架（如 DocBench）仅测试信息提取，而工作流基准（如 OfficeBench）侧重应用导航，均将文档降维为被动数据负载。这种评估盲区导致无法区分智能体是“完成了操作”还是“破坏了文档”。DocOps 的切入点在于将文档操作形式化为状态转移过程，通过确定性验证器直接检查最终产物的原生状态，从而量化智能体在保持文档有效性与非破坏性编辑方面的真实能力边界。

## 核心方法

### 评估协议参照系

文档操作评估的通用流程通常依赖任务级成功信号或 LLM-as-a-Judge 进行间接验证。DocOps 的关键差异在于摒弃了基于文本输出的模糊匹配，转而采用针对原生文档格式（XLSX, DOCX, PPTX, PDF）的确定性程序化验证，将评估粒度从“任务完成”下沉至“状态保持”。

### 双轴任务分类法

为解耦操作能力与工作流深度，DocOps 构建了正交的双轴分类体系。操作轴将编辑原语划分为内容（语义处理）、格式（呈现状态）与结构（原生对象组织）三个维度；难度轴则建立从 L1 原子编辑到 L4 跨文档工作流的四级梯度。该设计动机在于隔离失败根源：L1/L2 测试局部执行与短程规划，而 L3/L4 强制智能体维持全局一致性。任务难度 $D$ 由操作耦合度 $C$ 与状态追踪深度 $S$ 共同决定：

$$ D = f(C, S) $$

其中 $C$ 量化操作间对文档原生状态的依赖强度（如 Excel 公式引用），$S$ 表征跨步骤状态保持的规划深度。这一分类法使研究者能精确定位失败是源于局部结构破坏还是长程状态追踪崩溃。

### 确定性状态验证器

针对传统验证器无法检测“表面正确但结构损坏”产物的问题，DocOps 为每个任务部署基于原生文档库的确定性验证器。验证器通过三类谓词直接检查最终产物：结构谓词验证可执行公式与层级完整性，语言锚点校验关键文本内容，保持谓词确保范围外元素未被破坏。验证得分 $V$ 定义为三类谓词同时满足的布尔结果：

$$ V = P_{struct} \land P_{ling} \land P_{pres} $$

该公式的物理含义是：仅当文档结构未损坏、内容准确且无关状态被完整保留时，任务才被视为成功。这种设计消除了 LLM 评估的幻觉偏差，直接暴露了智能体在破坏性编辑与语义验证缺口上的失效模式。

## 实验评估

实验在 210 个任务上评估了 GPT-5.5、Claude Sonnet 4.6 等前沿模型及 DeepSeek-V4-Pro 等开源模型，覆盖 DocTools、Terminus-2、Codex 与 Claude Code 四种执行框架。基线审计显示，本文未对比 AFlow、DAAO 等专用工作流优化算法，因其评估对象是基础模型加固定框架的组合能力，而非动态结构生成。

| 模型/框架组合 | 整体通过率 | L1 通过率 | L3 通过率 |
| :--- | :--- | :--- | :--- |
| GPT-5.5 + Codex (w/ Skill) | 0.671 | 0.725 | 0.237 |
| Claude Sonnet 4.6 + Claude Code (w/o Skill) | 0.552 | — | — |
| Qwen3.6-27B + Terminus-2 | 0.476 | — | — |

GPT-5.5 在 L1 原子任务上达到 0.725 的通过率，但在 L3 工作流任务中骤降至 0.237，表明性能瓶颈不在局部操作，而在长程状态维持。Excel 格式在 L3 任务中成功率接近零，而 PDF 保持相对鲁棒，证实操作耦合度而非操作数量是工作流难度的核心来源。

消融分析揭示执行框架对性能的显著影响：开放编程环境（如 Codex）大幅优于静态 RPC 工具调用（DocTools）。技能注入对中等规模开源模型（如 Qwen3.6-27B）有显著增益，但对具备零样本编排能力的前沿模型边际效用极低。失败模式分布显示，长期状态追踪失败（42.43%）与破坏性编辑（25.77%）占主导，语义验证缺口（21.84%）次之，三者共同构成复杂文档任务的主要失效源。

评估边界方面，DocOps 任务为合成构造，虽经人工审核但可能未覆盖工业级 SOP 的极端复杂度；确定性验证器虽保真度高（95.31% 人工审计一致率），但可能限制开放式任务的评估灵活性。代码与数据集已公开，支持复现，但缺乏计算效率维度的报告。

## 关联研究分析

从问题动机看，DocOps 与 OfficeBench 均关注办公自动化，但前者将文档视为需维持状态一致性的计算对象，后者仅评估应用导航效率。这一差异源于任务特性的根本不同：OfficeBench 的成功信号是“应用间数据传递完成”，而 DocOps 要求“文档原生结构在编辑后保持有效”。这种评估协议的转变揭示了现有基准在“非破坏性编辑”维度上的系统性缺失，而非单纯的任务覆盖不足。

从方法设计看，DocOps 的确定性验证器与 Lean4Agent 的形式化验证均追求可证明的正确性，但前者针对文档格式的结构谓词，后者针对代码逻辑的数学证明。DocOps 未采用动态工作流生成算法（如 AFlow），而是固定框架评估模型能力，这暗示当前研究重心正从“如何生成最优工作流”转向“如何确保执行过程的状态安全”。查询侧增强在数据充足时是否仍有增益，论文未给出回答，但固定框架设定可能掩盖了动态编排对状态追踪的潜在缓解作用。

## 总结

DocOps 旨在解决文档智能体评估中“任务完成”与“状态保持”脱节的核心矛盾。现有基准将文档降维为被动数据，无法量化长程操作中的状态一致性，而 DocOps 凭借双轴分类法与确定性验证器，将评估下沉至原生文档结构层面。实验证明，即便 GPT-5.5 在 L1 任务上达 0.725，其在 L3 工作流中仍骤降至 0.237，暴露了当前模型在维持全局文档状态上的根本局限。该框架的边界在于合成任务构造与固定执行框架，未涵盖动态工作流生成对状态追踪的潜在影响。当执行框架从静态工具调用转向开放编程环境时，状态追踪失败的边际改善是否足以抵消资源开销，论文未给出回答。
