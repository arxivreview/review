# HuggingFace最新推荐论文 ｜How Fast Can Reward Models Score? A Systems Study of C++ and PyTorch Inference Runtimes for RLHF ｜RLHF奖励模型推理运行时基准测试

论文原文见 [arXiv](https://arxiv.org/abs/2607.19712)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2607.19712)

> 强化学习人类反馈（RLHF）训练循环中，奖励模型（Reward Model）的推理延迟直接决定策略更新的阻塞时间，但现有研究几乎完全聚焦于奖励信号的算法鲁棒性，忽视了推理引擎的性能瓶颈。本文切入点在于揭示“计算速度”这一被忽略的系统层变量，通过构建基于ONNX Runtime的C++推理引擎，量化其与PyTorch默认运行时在CPU和GPU上的延迟差异。该工作提供了首个针对RLHF奖励模型推理的严格系统基准，但其结论受限于单一硬件配置，且未探讨推理加速对奖励黑客检测灵敏度的潜在影响。

## 研究背景

RLHF训练循环包含三个串行阶段：策略模型生成候选响应、奖励模型对响应进行评分、策略模型基于奖励信号更新参数。其中，奖励模型评分是阻塞性步骤，若其推理延迟过高，整个训练循环的墙钟时间将线性增加。这一过程涉及两个关键概念：推理运行时（Inference Runtime）与批处理策略（Batching Strategy）。推理运行时决定了模型前向传播的执行效率，而批处理策略则影响GPU/CPU资源的利用率。在标准RLHF流程中，团队通常默认使用PyTorch eager模式或torch.compile，缺乏对替代推理后端（如ONNX Runtime）的系统性评估，导致潜在的性能优化空间被忽视。

现有RLHF研究主要聚焦于奖励模型的算法鲁棒性，如CausalRM通过因果分解阻断虚假相关，PRISM通过概率建模处理不确定性。这些方法关注“奖励信号质量”，假设推理速度不是瓶颈。然而，当训练规模扩大至数千步时，奖励模型推理的累积延迟成为显著开销。DeepSpeed Chat等系统研究指出生成阶段占步时长的85%以上，但未隔离奖励评分的独立延迟贡献。本文切入点在于填补这一系统层空白：不改变奖励模型内部结构，仅优化其执行环境，量化不同推理运行时在RLHF特定负载下的性能差异。

## 核心方法

### 方法参照系

本文问题属于推理引擎选型与基准测试，而非奖励模型算法设计。通用流程为：导出模型至中间表示（如ONNX）→ 选择推理运行时（如ONNX Runtime、PyTorch）→ 配置批处理与并发策略 → 测量延迟。本文与通用流程的关键差异在于：针对RLHF奖励模型的短序列、高频率评分负载，而非生成式模型的长序列解码负载，且强调独立进程启动以消除系统噪声。

### 基于ONNX Runtime的C++推理引擎

本文构建的C++引擎接管了原本由Python处理的分词、批处理和后处理任务，核心创新在于将推理完全迁移至ONNX Runtime图执行模式。设计动机是消除PyTorch eager模式的Python解释器开销和动态图调度成本。引擎通过原生实现SentencePiece和WordPiece分词器，避免跨语言调用。其性能增益并非来自C++语言本身，而是源于图执行模式对算子融合的优化。具体而言，ONNX Runtime将Transformer前向传播编译为静态计算图，消除逐算子调度开销。该引擎在CPU上达到335.9ms的p50延迟，显著优于PyTorch eager的602.4ms，验证了图执行模式在短序列负载下的优势。

### 长度感知批处理与并发控制

在引擎选型之外，本文发现批处理策略对吞吐量影响远超运行时选择。设计动机是解决朴素批处理（Naive Batching）中固定长度填充导致的计算浪费。本文提出长度感知分组（Length-aware Grouping），将相似长度的请求优先分组，减少填充token数量。其吞吐量提升机制可表示为：

$$
T_{bucketed} = \frac{N_{rows}}{\sum_{i=1}^{B} L_{max}(i)}
$$

其中$T_{bucketed}$为分组后吞吐量，$N_{rows}$为总行数，$L_{max}(i)$为第$i$个批次中的最大序列长度。该策略在GPU上将吞吐量从10.0 rows/sec提升至53.7 rows/sec，但在CPU上因缺乏并行计算能力，分组后吞吐量（2.43 rows/sec）仍低于单行基线（3.10 rows/sec）。此外，本文发现共享引擎实例在并发请求下完全串行化，多实例部署因线程池过度订阅导致性能急剧下降，GPU上8个独立实例甚至触发内存溢出。

## 实验评估

实验基于Anthropic的hh-rlhf数据集，使用60行固定种子样本，覆盖不同响应长度。基线包括PyTorch eager、torch.compile和FastAPI，缺失vLLM等专用推理框架对比。主实验结果显示，C++引擎在CPU上全面优于所有基线，置信区间无重叠；在GPU上，C++引擎优于PyTorch和FastAPI，但torch.compile在p50延迟（19.0ms vs 27.4ms）和p95延迟（25.6ms vs 116.2ms）上均显著占优。

| 系统 | CPU p50 (ms) | GPU p50 (ms) | GPU p95 (ms) |
|---|---|---|---|
| C++ engine | 335.9 [297.7, 374.0] | 27.4 [24.3, 30.5] | 116.2 [109.7, 122.8] |
| HF eager (PyTorch) | 602.4 [551.3, 653.4] | 57.2 [50.0, 64.4] | 148.2 [133.0, 163.5] |
| FastAPI | 581.6 [570.4, 592.9] | 62.8 [52.8, 72.9] | 140.8 [119.3, 162.3] |
| torch.compile | 628.8 [613.7, 644.0] | 19.0 [17.6, 20.3] | 25.6 [18.4, 32.9] |

消融实验揭示两个反直觉发现：第一，C++语言本身并非性能增益来源，Python调用ONNX Runtime的延迟（349.0ms）与C++引擎（335.9ms）几乎相同，证明增益源于运行时而非语言；第二，朴素批处理在CPU上不仅无益反而有害，batch=8时吞吐量从3.10降至0.40 rows/sec，因ONNX Runtime CPU后端将批维度折叠为串行矩阵乘法。评估边界方面，实验仅在单台AMD Ryzen 7 5800H + RTX 3060 Laptop GPU上运行，未测试多机分布式场景；所有基准使用fp32精度，未探索混合精度对延迟和精度的权衡；代码未公开，但论文提供了详细的软件版本（ONNX Runtime 1.26.0, PyTorch 2.10.0）和硬件配置，支持复现。

## 关联研究分析

从问题动机看，本文与CausalRM、PRISM等算法鲁棒性研究形成互补而非竞争关系。CausalRM通过潜在变量瓶颈阻断虚假相关，关注奖励信号的因果有效性；本文则假设奖励模型输出正确，仅优化其执行速度。这一差异源于任务特性：算法鲁棒性研究针对“奖励信号质量”的内在缺陷，而系统优化研究针对“计算资源利用率”的外部约束。两者在RLHF流程中处于不同层级，前者决定策略更新的方向正确性，后者决定策略更新的频率上限。

从方法设计看，本文与DeepSpeed Chat等系统研究存在关键差异。DeepSpeed Chat将生成阶段视为主要瓶颈，提出混合引擎设计；本文则隔离奖励评分延迟，证明其在特定硬件和负载下可成为独立瓶颈。这一差异暗示，当生成阶段通过专用硬件（如H100）加速后，奖励评分的相对开销可能上升，使系统优化研究更具紧迫性。然而，本文未探讨推理加速对奖励黑客检测灵敏度的影响：GPU上4.2e-3的浮点误差是否足以改变奖励模型的决策边界，进而影响策略对虚假相关的敏感度，论文未给出回答。

## 总结

本文核心矛盾在于RLHF训练循环中奖励模型推理延迟被系统性忽视，导致计算资源浪费。现有算法鲁棒性研究假设推理速度非瓶颈，而系统研究又未隔离奖励评分的独立贡献。本文通过构建ONNX Runtime C++引擎，证明图执行模式在CPU上可带来1.7-1.9倍加速，但在GPU上torch.compile更优。其边界在于单一硬件配置和fp32精度假设，未探索混合精度或分布式场景。当GPU浮点误差达到4.2e-3时，奖励模型对长度偏差等虚假相关的检测灵敏度是否发生显著变化，论文未给出回答。
