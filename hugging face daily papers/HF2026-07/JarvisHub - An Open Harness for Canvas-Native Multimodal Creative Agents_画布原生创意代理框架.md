> 长程多模态创作面临的核心挑战并非单次生成质量，而是如何在非线性、多分支的工作流中维持项目状态的一致性与可追溯性。现有提示词工具、聊天代理及节点式工作流均无法在长时程任务中保留中间决策、版本分支与依赖关系，导致创意过程不可审计。JarvisHub 将可编辑画布定义为智能体的外部记忆与动作空间，通过协议桥验证所有状态变更，实现了从“单次输出”到“持续项目状态”的范式转换。该框架在架构层面解决了状态管理问题，但缺乏量化基准验证其相对于线性对话在生成质量上的具体增益。

## 研究背景

当创意代理执行“生成科幻预告片”这类任务时，它需要同时管理角色参考图、分镜草稿、音频片段及用户反馈。若仅依赖线性对话历史，代理无法区分“已接受的候选”与“被拒绝的草稿”，也无法追溯某张图像是由哪个提示词和哪版参考图生成的。这种状态丢失导致长程任务中的上下文污染，即早期错误决策在后续步骤中被反复引用，形成累积性偏差。解决此问题需引入显式的项目状态表示，将非结构化的对话流转化为结构化的依赖图，使中间产物成为可寻址、可复用的实体。

统一多模态生成领域已确立架构统一与推理增强的共识，如 Chameleon 和 Transfusion 解决了模态对齐，ThinkMorph 通过交错推理提升了逻辑一致性。然而，这些工作聚焦于单次生成的内部机制，假设输入是静态的、输出是终态的。实际创意工作流是动态演化的，涉及多次迭代、局部修改与分支探索。现有智能体框架如 ToolArtist 依赖工具调用解决知识缺口，但其状态仍隐含在对话上下文中，缺乏对空间布局、版本血缘及依赖关系的显式建模。JarvisHub 的切入点在于将“画布”从用户界面提升为智能体的核心状态空间，通过形式化的图结构管理创意资产的生命周期，填补了长程创意代理在状态持久化与可追溯性上的空白。

## 核心方法

### 方法参照系

本文问题属于智能体生成框架范畴，但与传统基于对话历史的智能体存在关键差异。通用流程中，智能体状态由对话上下文隐式维护，动作空间由工具列表定义。JarvisHub 将状态显式化为画布节点图，动作空间受协议桥约束，要求所有状态变更必须通过验证后写入画布，而非仅记录在日志中。

### 画布状态形式化

画布状态层将创意项目建模为类型化工件图，解决了线性对话无法表示空间布局与版本分支的问题。在回合 $t$，项目状态定义为 $C_t = (G_t, X_t, M_t, U_t, L_t)$，其中 $G_t = (V_t, E_t)$ 为工件图，$V_t$ 为节点集合，$E_t \subseteq V_t \times \mathcal{R} \times V_t$ 为带类型关系的有向边。每个节点 $v_i = (id_i, k_i, p_i, x_i, y_i, m_i, s_i)$ 包含稳定标识符、节点类型、位置、可编辑输入、生成输出、溯源元数据及运行时状态。该设计使工件具备可寻址性、可复用性与依赖可追溯性，代理可精确引用特定候选图像或视频片段，而非依赖模糊的对话短语。

### 协议约束的状态转移

协议桥通过执行授权 $\Omega_t$ 限制代理在当前回合的合法动作空间，确保状态变更的显式性与可恢复性。给定用户查询 $q_t$、画布状态 $C_t$、能力清单 $\Gamma_t$ 及执行授权 $\Omega_t$，代理提出动作 $a_t$，仅当该动作可编码为经过检查的工具调用、画布变更或评估请求时，才由状态转移算子 $F$ 执行：

$$
C_{t+1} = F(C_t, a_t, o_t, f_t, r_t)
$$

其中 $o_t$ 为工具观察，$f_t$ 为反馈信号，$r_t$ 为修复决策。该公式的物理含义是：画布状态仅通过经过验证的动作与观察更新，任何未通过协议桥验证的操作均被拒绝，从而保证画布作为唯一事实来源的一致性。轨迹 $\tau = \{(q_t, C_t, \Gamma_t, \Omega_t, a_t, o_t, f_t, r_t, C_{t+1})\}_{t=1}^T$ 完整记录状态演化过程，使创意过程可审计而非隐藏在语言生成内部。

## 实验评估

该论文实验数据不可得，未提供实验表格。实验设置采用 GPT-5.5 作为主代理后端，GPT Image 2 作为图像生成后端，Seedance 2.0 作为视频生成后端，Gemini 3.1 Pro 作为多模态评估后端。基线审计显示，论文未对比任何具体的生成模型算法（如 UniGRPO、AlphaGRPO 或 BAGEL），仅对比了“提示词到输出”、“聊天代理”、“节点式工作流”三类系统范式。这种对比方式无法量化画布机制对生成质量的具体贡献，因为后端模型能力差异可能掩盖或放大架构优势。

消融实验缺失，无法验证画布状态层、协议桥、代理运行时各组件的独立贡献。设计决策讨论显示，协议桥的引入增加了状态变更的验证开销，但论文未报告该开销对长程任务延迟的影响。反馈机制支持人类或模型批评者介入，但论文未区分不同反馈来源对状态修复效果的差异。

评估边界存在显著局限：实验仅展示定性案例（叙事媒体、Web 开发、PPT 生成），未报告准确率、F1 等量化指标。评估协议依赖 Gemini 3.1 Pro 作为评估器，存在评估器偏差风险。可复现性方面，论文提供 GitHub 链接，但未公开超参数配置、GPU 资源需求及训练细节，仅说明后端模型配置详见代码仓库。

## 关联研究分析

从问题动机看，JarvisHub 与 ToolArtist 同属智能体生成框架，但解决的核心矛盾不同。ToolArtist 聚焦于通过工具调用弥补世界知识缺口，其状态管理隐含在对话上下文中，适用于知识密集型单次生成任务。JarvisHub 聚焦于长程创意过程中的状态一致性与可追溯性，通过画布节点显式化中间产物，适用于多分支、多迭代的复杂工作流。这一差异源于任务特性：知识缺口可通过检索解决，而状态丢失无法通过事后检索恢复，必须通过实时状态管理预防。

从方法设计看，JarvisHub 与 ThinkMorph 在推理机制上存在互补性。ThinkMorph 通过交错推理提升单次生成的逻辑一致性，其推理过程是瞬时的、不可编辑的。JarvisHub 通过画布节点实现推理的持久化与可编辑性，允许用户或代理在任意时刻修改中间状态并重新执行后续步骤。这种设计使创意过程从“黑盒生成”转变为“白盒编排”，但引入了状态同步开销。查询侧增强在数据充足时是否仍有增益，论文未给出回答，因为画布机制的优势在长程任务中才显著，短程任务中可能因验证开销而劣于直接生成。

## 总结

JarvisHub 要解决的核心矛盾是长程多模态创作中项目状态的一致性与可追溯性缺失。现有方法依赖线性对话或固定管道，无法表示空间布局、版本分支与依赖关系，导致中间决策丢失与累积性偏差。JarvisHub 抓住画布作为共享工作区的潜力，将其形式化为类型化工件图，通过协议桥验证所有状态变更，实现了创意过程的可审计性。实验证明了架构在叙事媒体、Web 开发、PPT 生成三类任务中的可行性，但未提供量化指标验证其相对于线性对话的性能优势。论文边界在于缺乏标准基准对比与消融实验，无法区分画布机制与后端模型能力的贡献。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
