> 导读 大语言模型（LLM）在生成具有强静态语义约束的代码（如 Rust）时，常因违反借用检查等规则导致编译失败，而传统的生成后反馈机制存在延迟高、错误累积的问题，约束解码则依赖白盒访问且缺乏解释性。本文提出生成式编译（Generative Compilation），通过引入“密封器”（Sealor）将部分程序转化为完整程序以触发现有编译器诊断，实现了生成过程中的实时反馈。该方法在七个前沿模型上验证了降低编译错误率并提升功能正确性的能力，但其对复杂语义错误的覆盖边界及跨语言泛化性仍存疑。

## 研究背景

当 LLM 自回归生成 Rust 代码时，其输出序列可能违反所有权与借用纪律，例如在不可变借用存活期间尝试可变借用。这种静态语义违规无法通过简单的语法检查发现，必须依赖类型系统与借用检查器。然而，LLM 的自回归特性意味着一旦生成错误前缀，后续 token 往往基于无效假设继续生成，导致错误级联。

现有解决路径分为两类：生成后编译器反馈（Post-Generation Feedback）与约束解码（Constrained Decoding）。前者在完整文件生成后运行编译器，虽兼容黑盒模型，但反馈延迟导致早期错误无法及时修正，且批量诊断信息过载；后者在解码阶段过滤无效 token，虽能保证输出有效性，但需白盒访问模型分布，且对复杂静态语义需重新实现语言前端，实施成本极高。本文切入点在于利用现有编译器基础设施，在生成过程中对部分程序进行“密封”并检查，从而在黑盒条件下实现早期、聚焦的语义反馈。

## 核心方法

### 方法参照系

本文问题属于代码生成中的静态语义验证环节。通用流程为“生成-检查-修正”，关键差异在于检查时机：传统方法在生成完整程序后检查，本文在生成部分程序时即介入，且无需修改模型采样过程。

### 密封器（Sealor）定义与性质

密封器 $S: \Sigma^* \rightarrow \Sigma^*$ 是一个轻量级转换，将部分程序 $c$ 补全为完整程序 $S(c)$，使其可被标准编译器 $C$ 处理。生成式编译器 $G_{C,S}(c) \triangleq C(S(c))$ 的判定依赖于 $S$ 的完备性与健全性。

$$
\text{Completeness: } \forall c \in X, \exists w. c \circ w \in L \implies S(c) \in L
$$

$$
\text{Soundness: } \forall c \in X, S(c) \in L \implies \exists w. c \circ w \in L
$$

设计动机在于解决约束解码的“静默过滤”缺陷：密封器不仅拒绝无效前缀，还通过编译器诊断提供错误解释，允许模型修正已生成代码。完备性保证不拒绝可完成的前缀，避免误导模型；健全性保证不将死胡同前缀误判为有效，确保早期错误捕获。

### 基于语法引导的密封实现

针对 Featherweight Rust (FR) 和真实 Rust，密封器采用语法引导策略，保留生成语法，插入类型正确的占位符（如 `holeval()`）并闭合缺失结构。

$$
S(c) = \text{Parse}(c) \oplus \text{Placeholders}(\text{Types}(c)) \oplus \text{Close}(\text{Syntax}(c))
$$

该公式表示密封过程包含解析部分 AST、根据类型上下文插入占位符、闭合语法结构三步。设计动机在于避免重新实现类型系统：密封器仅处理语法补全，将类型、借用、生命周期推理委托给 `rustc`。这解决了约束解码需重新实现语言语义的高成本问题，同时通过诊断映射（将密封程序错误映射回部分程序）确保反馈聚焦于原始代码错误，而非密封引入的伪错误。

## 实验评估

实验在 CRUST-Bench（C-to-Rust 翻译）和自构建 UpdatedAPI（更新 API 适配）两个仓库级任务上进行，对比无反馈（LLM）、生成后反馈（PC）和生成式编译（GC）三种策略，覆盖 Claude Opus 4.8、GPT 5.3 Codex 等七个模型。

| 模型 | 任务 | 策略 | 编译错误率 (↓) | 功能正确率 (↑) |
|---|---|---|---|---|
| GLM 5.2 | UpdatedAPI | PC | 45.0% | 53.3% |
| GLM 5.2 | UpdatedAPI | GC | 16.7% | 71.7% |
| Kimi K2.7 | Translation | PC | 38.6% | 39.9% |
| Kimi K2.7 | Translation | GC | 11.0% | 53.9% |
| Opus 4.8 | Translation | PC | 7.5% | 61.0% |
| Opus 4.8 | Translation | GC | 2.6% | 62.3% |

GC 在 14 个模型-任务配置中的 11 个上取得最佳功能正确率，GLM 5.2 在 UpdatedAPI 上功能正确率从 53.3% 提升至 71.7%，Kimi K2.7 在 Translation 上从 39.9% 提升至 53.9%。编译错误率显著降低，如 Opus 4.8 在 Translation 上从 7.5% 降至 2.6%。

消融分析显示，GC 的平均运行时开销（135 秒）低于 PC（233 秒），主要因 GC 在首个不可恢复错误处中断生成，避免完成无法编译的文件。Qwen 9B 在 Translation 上运行时从 879 秒降至 357 秒。然而，对 Opus 4.8 等高频反馈需求低的模型，运行时变化微小（+2 秒）。

评估边界方面，实验仅覆盖 Rust 语言，未验证 Haskell 等其他强静态语义语言；指标聚焦编译错误率与功能正确率，未量化误报率或诊断质量；代码已开源，但密封器实现依赖 `rust-analyzer` 补丁，跨编译器版本兼容性未充分测试。

## 关联研究分析

从问题动机看，本文与约束解码（Constrained Decoding）形成互补而非替代。约束解码通过白盒过滤保证输出有效性，但缺乏解释性且实施成本高；本文通过黑盒反馈提供诊断，允许模型修正，但无法保证最终输出绝对有效（依赖后续编译）。差异根源在于任务特性：约束解码适用于语法严格且语义简单的语言，本文适用于语义复杂且需迭代修正的场景。

从方法设计看，本文与生成后反馈（Post-Generation Feedback）共享“编译器作为检查器”的基础设施，但介入时机不同。生成后反馈在完整程序生成后介入，错误累积导致修复困难；本文在部分程序生成时介入，通过密封器实现早期反馈。与检索增强生成（RAG）方法（如 RESCUE）相比，本文不依赖外部知识库，而是依赖语言本身的静态语义，因此无需训练或数据策展，但受限于编译器覆盖的语义范围。

## 总结

本文核心矛盾在于黑盒 LLM 生成强静态语义代码时，实时反馈与实施成本的权衡。现有方法要么延迟反馈（生成后），要么高成本实施（约束解码），本文通过密封器复用现有编译器，实现低成本实时反馈。实验证明 GC 在 Rust 任务上显著降低编译错误率并提升功能正确率，如 GLM 5.2 功能正确率提升 18.4 个百分点。边界在于密封器仅处理语法补全，复杂语义错误依赖 `rustc` 覆盖，且未验证跨语言泛化性。当密封器面对非局部语义约束（如跨模块借用）时，其健全性保证是否仍成立，论文未给出回答。
