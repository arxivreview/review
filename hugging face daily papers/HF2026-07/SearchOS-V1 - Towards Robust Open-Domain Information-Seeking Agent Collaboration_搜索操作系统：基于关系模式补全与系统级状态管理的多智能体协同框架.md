> 导读
> 长程开放域信息获取面临的核心困境是智能体在交互历史增长后丢失任务进度，导致证据遗漏、重复搜索与执行停滞。现有单体或同步批次多智能体架构将搜索状态视为瞬态对话内容，无法在系统层面维持全局一致性，致使并行工作流出现资源闲置与冲突。本文提出 SearchOS，通过将搜索任务形式化为带引用溯源的关系模式补全，并引入系统级中间件与流水线并行调度，将状态管理从智能体提示词下沉至操作系统层。该框架在 WideSearch 与 GISA 基准上取得了领先的 F1 分数，但其性能提升是否完全归因于架构设计而非底层模型能力，仍需进一步解耦验证。

## 研究背景

当智能体执行多跳推理任务时，上下文窗口迅速被检索到的噪声文本填满，导致关键证据被淹没，智能体难以区分已确认事实与未解决缺口。这种状态丢失迫使智能体反复发起相似查询，陷入局部最优或死循环。为解决此问题，多智能体架构通过角色分工并行处理子任务，但传统同步批次调度存在严重的 Straggler 效应，即系统需等待最慢任务完成才能进入下一轮，造成大量执行槽位闲置。

长程搜索任务要求系统不仅具备强大的检索能力，更需具备对执行进度的全局感知与控制能力。主流路线如 ReAct 和 Plan-and-Solve 依赖单体智能体在对话历史中推断状态，而 A-MapReduce 等早期多智能体系统虽引入并行，但缺乏对证据覆盖率和失败模式的显式追踪。这些方法共同忽略了搜索状态应由系统而非智能体推断这一原则，导致在复杂开放域任务中，智能体无法有效协调工作流或从失败中恢复。本文切入点在于将搜索过程重构为系统级状态管理问题，通过外化执行状态和引入中间件干预，实现可观测、可控制的长程信息获取。

## 核心方法

### 关系模式补全形式化

本文解决的问题可置于表格补全与知识图谱构建的通用流程中，但关键差异在于其强调“带引用溯源的关系模式补全”。给定自然语言请求 $q$，系统构建关系搜索模式 $S = \{T_m\}_{m=1}^M$，其中 $T_m$ 定义包含属性 $A_m$ 和主键 $P_m$ 的表格，$R$ 包含表间外键关系。任务目标不仅是填充值矩阵 $\mathbf{Y}_m \in \mathcal{V}^{[N_m] \times |A_m|}$，还需维护同形状的引用矩阵 $\mathbf{C}_m$，将每个值链接至源 URL 和锚定摘录。这一形式化将开放式请求转化为具体的搜索目标，使进度可在实体和属性层面度量，解决了传统方法中证据不可验证的问题。

### 搜索导向上下文管理（SOCM）

传统多智能体系统通过智能体间对话共享信息，但对话历史是瞬态且易失的，无法保证状态一致性。SOCM 将执行状态外化为持久化共享结构 $\mathbf{M}_t = (F_t, G_t, C_t, W_t)$，包含前沿任务、证据图、覆盖图和失败记忆。智能体接收的是状态的角色特定投影 $\phi_r(\mathbf{M}_t)$，而非完整状态，这避免了上下文过载。覆盖图通过计算已填充单元格比例来量化进度：

$$ \text{Cov}(C_t) = \frac{|\{c \in \Omega_t \mid s_c = \text{filled}\}|}{|\Omega_t|} $$

该公式物理含义是衡量当前已知实体行中属性填充的完整性，分母保留声明的空表未完成状态，确保在开放集任务中，实体发现能动态扩展分母，从而准确反映搜索的广度与深度。

### 流水线并行调度与中间件治理

同步批次调度导致 Straggler 效应，本文借鉴 GPU 训练中的流水线并行思想，采用事件驱动的连续调度策略。当执行槽位释放时，立即分配新的未解决模式缺口，而非等待批次结束。为应对模型级失败（如状态丢失）和系统级中断（如工具错误），引入搜索工具中间件框架，在模型与工具边界拦截交互。中间件在每次模型调用前注入相关状态和技能，在工具执行后提取并锚定证据，同时检测停滞轨迹。停滞检测基于窗口 $w$ 内覆盖率和证据增长量：

$$ \text{Stall}_t = \mathbb{I}[\Delta \text{Cov}(C_t) < \epsilon \land \Delta |G_t| < \epsilon] $$

该公式通过监测覆盖率和证据图节点数的增量是否低于阈值 $\epsilon$ 来判定停滞，触发中间件注入纠正指令或强制停止，解决了智能体在长程任务中因上下文噪声导致的盲目重复搜索问题。

## 实验评估

实验在 WideSearch（200 个手动策划问题）和 GISA（373 个人工构建查询）上进行，基线覆盖单体方法（ReAct, Plan-and-Solve）和多智能体系统（A-MapReduce, Web2BigTable, Table-as-Search）。值得注意的是，基线中缺失基于强化学习优化的单体智能体（如 Search-R1），这可能影响对架构贡献与策略优化贡献的区分。

| 基准 | 指标 | ReAct | A-MapReduce | Web2BigTable | SearchOS |
| :--- | :--- | :--- | :--- | :--- | :--- |
| WideSearch | Item_F1 | 70.2 | 76.0 | 73.8 | **80.3** |
| WideSearch | Row_F1 | 75.2 | 76.0 | 51.4 | **56.5** |
| GISA | Set_F1 | 58.1 | 67.1 | 56.7 | **76.5** |
| GISA | Table_Item_F1 | 74.8 | 73.4 | 68.1 | **76.9** |

SearchOS 在 WideSearch Item_F1 上超越最强基线 A-MapReduce 4.3 点，在 GISA Set_F1 上超越最强基线 13.4 点。消融实验显示，连续调度相比批次调度将 Item_F1 从 79.66 提升至 86.75，同时减少 LLM 调用次数 13.1%，验证了流水线并行在提升吞吐量与质量上的双重收益。

评估边界方面，论文使用 GLM-5 作为骨干，Qwen3.5-35B-A3B 用于证据提取，报告 Max@3 结果。指标涵盖 Item/Row 级 F1 和 EM，但未报告计算效率的具体 GPU 小时数或延迟分布。代码已开源，但缺乏不同骨干模型下的对比实验，难以完全剥离底层 LLM 推理能力对最终性能的贡献。

## 关联研究分析

从问题动机看，SearchOS 与 M-ASK 均聚焦多智能体协同解决长程任务，但 M-ASK 侧重于通过角色分工解决信用分配，而 SearchOS 侧重于通过系统级状态管理解决执行可靠性。M-ASK 依赖智能体间通信协调，而 SearchOS 通过 SOCM 外化状态，避免了通信中的信息丢失与不一致。这一差异源于任务特性：M-ASK 针对多跳推理中的逻辑链条，而 SearchOS 针对广度搜索中的覆盖率与完整性，后者对状态一致性的要求更高。

从方法设计看，SearchOS 与 Web2BigTable 同属表格填充范式，但 Web2BigTable 将检索视为黑盒，而 SearchOS 通过中间件和层级技能库增强检索行为。Web2BigTable 的 Item_Recall 为 83.9%，但 Row_F1 仅 51.4%，表明其在细粒度提取上强但整体一致性弱。SearchOS 通过覆盖图驱动的任务分配，在保持高 Item_F1 的同时提升了 Row_F1，证明了显式状态管理对整体一致性的关键作用。然而，SearchOS 未采用强化学习训练智能体，这与领域共识中“RL 是优化搜索策略关键技术”的观点存在潜在冲突，其性能提升是否完全归因于架构而非策略优化，论文未给出回答。

## 总结

SearchOS 旨在解决长程开放域搜索中因状态丢失导致的执行不可靠问题。现有方法将状态视为瞬态对话内容，无法在系统层面维持全局一致性，而 SearchOS 通过关系模式补全形式化、SOCM 状态外化及流水线并行调度，将状态管理下沉至系统层。实验表明，该框架在 WideSearch Item_F1 上达到 80.3，在 GISA Set_F1 上达到 76.5，显著优于现有基线。其边界在于缺乏不同骨干模型的对比实验，且未使用强化学习优化智能体策略，使得架构贡献与模型能力贡献难以完全解耦。当骨干模型推理能力增强时，系统级状态管理的边际收益是否递减，论文未给出回答。
