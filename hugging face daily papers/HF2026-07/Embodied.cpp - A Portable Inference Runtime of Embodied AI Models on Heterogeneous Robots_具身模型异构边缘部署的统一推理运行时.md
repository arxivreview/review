# HuggingFace最新推荐论文 ｜Embodied.cpp: A Portable Inference Runtime of Embodied AI Models on Heterogeneous Robots ｜具身模型异构边缘部署的统一推理运行时

研究机构：东南大学、南京大学

论文原文见 [arXiv](https://arxiv.org/abs/2607.02501)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2607.02501)

> 具身智能体从算法原型走向机器人实体时，面临软件栈碎片化与硬件异构性的双重壁垒，现有通用推理引擎无法适配闭环控制下的多速率执行与低延迟约束。本文切入点在于识别视觉-语言-动作模型（Vision-Language-Action, VLA）与世界-动作模型（World-Action Model, WAM）在底层执行路径上的共性，将其抽象为可插拔的模块化组件。通过构建五层 C++ 推理架构，实现了跨硬件后端的统一调度与算子融合。该工作填补了具身模型部署基础设施的空白，但当前验证局限于单任务闭环与单算子量化，全模型闭环稳定性仍存疑。

## 研究背景

具身智能体的实时执行依赖于感知、规划与控制模块在毫秒级时间窗口内的协同。传统大语言模型（Large Language Model, LLM）推理运行时针对请求-响应模式优化，假设输入为均匀 Token 流且追求吞吐量，这与机器人控制中 Batch-1 低延迟、低抖动及多模块异步刷新的需求存在根本冲突。当模型架构从单体式向分层或异步式演进时，感知编码器、Transformer 骨干与动作头往往运行在不同频率，通用运行时缺乏对这种“多速率执行”的原生支持，导致部署时需为每个模型重写胶水代码。

具身模型生态正快速扩张，VLA 与 WAM 成为两大主流范式。VLA 侧重感知到动作的直接映射，而 WAM 将未来预测纳入在线控制循环。现有推理系统如 llama.cpp 或 ONNX Runtime 虽具备跨平台能力，但缺乏对具身多模态输入（如力触觉、本体感觉）及异构输出（动作块、预测未来）的一等支持；最近的 vla.cpp 虽实现了 VLA 的 C++ 部署，却未覆盖 WAM 及模块化多组件调度。这种基础设施的缺失使得高性能模型难以在 Jetson、RK 等边缘设备上稳定运行，成为制约具身智能体从仿真走向真实部署的关键瓶颈。

## 核心方法

### 方法参照系

本文问题可置于通用 AI 推理运行时类别下，但其核心差异在于运行时契约从“Token 服务”转变为“具身控制”。通用运行时假设同步前向传播与均匀接口，而具身部署要求运行时显式管理中间状态（如子目标、缓冲上下文），并支持不同模块以不同频率刷新。本文未沿用通用运行时的黑盒执行模式，而是将模型内部结构显式暴露为运行时对象。

### 五层模块化架构

针对多速率执行与接口扩展性挑战，本文提出五层架构：输入适配器、序列构建器、骨干执行、头插件与部署适配器。该设计将模型特定的头与后端转化为可插拔模块，而非一次性胶水代码。其核心调度逻辑可形式化为多速率执行策略：

$$
\mathcal{S} = \{ (M_i, f_i, D_i) \mid i \in \{1, \dots, N\} \}
$$

其中 $M_i$ 为第 $i$ 个模块（如感知编码器、动作头），$f_i$ 为其刷新频率，$D_i$ 为依赖关系图。运行时根据 $f_i$ 独立调度各模块，通过共享状态池（Shared State Pool）同步中间表示，避免了强制所有模块同步执行带来的延迟浪费。这一设计解决了单体式运行时在分层 VLA 中因感知模块低频刷新而被迫等待高频动作头的问题，实现了控制循环内的时间解耦。

### 延迟优先的融合执行

在异构边缘设备上，Batch-1 推理的延迟敏感性远高于吞吐量。本文引入延迟优先的融合执行策略，通过图重放、缓冲复用与算子融合优化小批量推理。针对 WAM 中的 Transformer 块，采用 GGUF Q4_K 量化替代 BF16，其内存占用与精度权衡可表示为：

$$
\Delta M = M_{BF16} - M_{Q4_K}, \quad \epsilon = \frac{1}{N} \sum_{j=1}^{N} |x_j^{BF16} - x_j^{Q4_K}|
$$

其中 $\Delta M$ 为内存节省量，$\epsilon$ 为平均绝对误差（MAE）。该策略通过牺牲极小的精度（MAE < $3.3 \times 10^{-2}$）换取显著的内存压缩，使得在资源受限的边缘设备上运行大型 WAM 组件成为可能。这一创新直接回应了边缘部署中内存带宽瓶颈导致的延迟抖动问题，确保了闭环控制的时序稳定性。

## 实验评估

实验在 RoboTwin 与 LingBot-VA 基准上进行，对比 Python 原版与 C++ 部署路径。基线覆盖审计显示，本文仅对比了 Python 原生实现，未与 ONNX Runtime 或 vla.cpp 进行直接性能对比，缺乏与其他 C++ 运行时的横向参照。

| 部署模型 | 骨干网络 | 动作块长度 | 成功率 (%) | 步延迟 (ms) | 推理延迟 (ms) | 显存 (MiB) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| HY-VLA | Hunyuan-VL | 20 | 100.0 | 735.9 | 1340.3 | 6850 |
| pi0.5 | PaliGemma | 50 | 91.0 | 56.85 | 266.6 | 6546 |

| 推理运行时 | 模型量化 | 单块延迟 (ms) | 单块内存 (MiB) | MAE | 余弦相似度 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Python 原版 | BF16 | 3.236 | 312.2 | 0 | 1 |
| Embodied.cpp | Q4_K | 3.171 | 88.1 | <3.3×10⁻² | >9.997×10⁻¹ |

HY-VLA 在 RoboTwin `place_empty_cup` 任务中达到 100.0% 成功率，但步延迟高达 735.9 ms，远高于 pi0.5 的 56.85 ms，这主要源于其更大的骨干网络与三视图输入。LingBot-VA 单块量化测试显示，Q4_K 量化将内存从 312.2 MiB 降至 88.1 MiB，延迟仅微降 0.065 ms，表明内存节省是主要收益，而计算加速有限。

评估边界存在明显局限：WAM 部分仅测试了单个 Transformer 块，未进行全模型闭环验证，作者承认完整模型在受限边缘设备上尚不稳定。此外，实验未报告置信区间，且缺乏在真实机器人硬件上的长期稳定性测试。代码已开源，但超参数配置与后端具体实现细节在论文中披露有限，复现需依赖 GitHub 仓库。

## 关联研究分析

从问题动机看，本文与 vla.cpp 同属具身推理运行时路线，但本文将支持范围从 VLA 扩展至 WAM，并强调多速率调度。vla.cpp 聚焦于 VLA 架构的 C++ 移植，而本文识别出 WAM 中预测分支与动作生成的异步特性，将其纳入统一调度框架。这一差异源于模型架构的演进：WAM 的引入使得“单一同步前向传播”假设失效，迫使运行时必须处理预测状态与动作生成的时序耦合。

从方法设计看，本文与通用推理运行时（如 SGLang）形成鲜明对比。SGLang 针对大规模并发优化，采用 PagedAttention 等技术提升吞吐量；而 Embodied.cpp 针对 Batch-1 低延迟优化，采用算子融合与内存复用。这种差异并非技术优劣，而是任务特性决定：具身控制对延迟抖动的容忍度极低，且并发需求低。然而，本文未探讨在混合负载（如多机器人协作）下，延迟优先策略是否会导致吞吐量瓶颈，这一盲区在单机器人场景中不显现，但在多智能体部署中可能成为关键限制。

## 总结

本文核心矛盾在于具身模型架构多样化与部署基础设施碎片化之间的冲突。现有通用运行时无法适配闭环控制下的多速率执行与异构硬件约束，而本文通过识别 VLA/WAM 的共享执行路径，将其抽象为五层模块化架构，实现了跨硬件的统一调度。实验证明该运行时在单任务闭环中保持了高成功率（100.0% 与 91.0%），并通过量化显著降低了 WAM 组件的内存占用（312.2 MiB 至 88.1 MiB）。然而，WAM 全模型闭环的不稳定性与缺乏跨运行时性能对比，暴露了当前验证的局限性。当模型规模进一步扩大或引入更复杂的预测分支时，多速率调度策略在极端延迟约束下的鲁棒性如何，论文未给出回答。
