# HuggingFace最新推荐论文 ｜ICAE-Bench: Evaluating Coding Agents as Interactive Project Builders ｜交互式编码智能体评估基准

研究机构：复旦大学、美团

论文原文见 [arXiv](https://arxiv.org/abs/2607.21217)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2607.21217)

> 现有编码基准假设任务目标静态且明确，无法评估智能体将模糊产品意图转化为可运行软件的能力。ICAE-Bench 通过从精确开源仓库反向生成模糊需求，并引入接地的用户智能体（User Agent）进行多轮澄清，构建了交互式项目构建的评估框架。该基准揭示了当前模型在需求保持与实现转化上的显著瓶颈，但其预置环境设计可能掩盖了真实部署中的依赖解析难点。

## 研究背景

当编码智能体面对“构建一个配置解析器”这类模糊指令时，它必须主动澄清重复项是否合法、支持哪些格式等缺失约束。这一过程涉及需求澄清（Requirement Clarification），即通过交互获取未显式指定的接口与边界条件。然而，若基准直接编写模糊需求，任务可能因定义不足而变得不可解，失败可能源于提示词歧义而非智能体能力缺陷。因此，评估必须建立在可验证的行为目标之上，同时保留意图的模糊性。

软件工程智能体评估已从函数级补全（HumanEval）演进至仓库级 Issue 修复（SWE-bench），核心范式是执行接地验证（Execution-Grounded Verification）。然而，SWE-bench 等基准假设代码库已存在，智能体仅需生成补丁；而“Vibe Coding”工作流要求智能体从零构建项目，涉及规划、澄清、工具使用与迭代调试的耦合。现有 0-to-1 生成基准（如 Commit0、ProgramBench）虽接近项目构建，但仍提供固定脚手架或静态可执行文件，未评估智能体在需求不完整时的交互式发现能力。ICAE-Bench 的切入点在于：将模糊性从精确行为中反向推导，通过接地交互控制信息暴露，从而分离“需求获取”与“代码实现”两个维度的能力。

## 核心方法

### 基准实例形式化

ICAE-Bench 将任务定义为五元组 $T = (D_f, E, P, U, B)$，其中 $D_f$ 为模糊产品需求文档（Fuzzy PRD），$E$ 为终极镜像（Ultimate Image）执行环境，$P$ 为公开测试用例，$U$ 为用户智能体数据，$B$ 为权威黑盒行为用例集。该形式化的关键差异在于：智能体仅初始可见 $(D_f, E)$，需通过查询 $U$ 恢复 $P$ 及隐藏约束，最终生成的仓库 $R$ 仅对 $B$ 负责。这种设计确保了评估目标固定，而初始信息量可控。

### 模糊性接地与层级控制

为解决“模糊需求可能导致任务不可解”的问题，ICAE-Bench 采用“从精确到模糊”的反向构建策略。首先从真实开源仓库合成 GroundPRD（完整规格）及黑盒用例，再通过 Fuzzification 隐藏部分约束生成 Fuzzy PRD。模糊层级定义为信息暴露的操作性梯度：

$$
\text{Info}(L_i) = \text{GroundPRD} \setminus \mathcal{H}_i, \quad i \in \{1, 2, 3\}
$$

其中 $\mathcal{H}_i$ 为第 $i$ 层级隐藏约束集合，满足 $\mathcal{H}_1 \supset \mathcal{H}_2 \supset \mathcal{H}_3$。L1 隐藏最多 API、边界及架构约束，L3 仅移除少量细节。隐藏约束存储于 $U$ 中，包含触发关键词与接地响应，确保智能体可通过针对性提问恢复信息。该设计动机在于：避免自由形式模糊需求导致的评估噪声，同时通过层级对比量化智能体对信息密度的敏感度。

### 接地交互与多维评估

为防止用户智能体引入新需求或泄露实现细节，ICAE-Bench 限制 User Agent 仅返回基准预制的 $U$ 记录，且智能体在移除黄金代码的终极镜像中运行。评估采用黑盒功能测试与静态诊断结合的多维协议：

$$
\text{Score}(R) = \alpha \cdot \frac{|\{c \in B \mid c(R) = \text{pass}\}|}{|B|} + \beta \cdot \text{Agentic}(R, R_{\text{golden}})
$$

其中第一项为功能通过率，第二项为代理评估（Agentic Evaluation），包含语义相似度、API 相似度与设计质量。该公式的物理含义是：功能正确性是基础，但代码结构与接口保真度决定了仓库的可维护性，二者需加权综合。此设计解决了单一通过率无法区分“硬编码通过”与“高质量实现”的问题。

## 实验评估

实验在 ICAE-Bench（480 任务，12 语言）及 Lite 子集（50 任务）上进行，评估 GPT-5.5、Claude-Opus-4.8 等 6 个模型在 Claude Code 框架下的表现。基线覆盖主流闭源与开源编码模型，但缺失 SWE-agent 等专用 Issue 修复智能体，因任务范式不同（0-to-1 构建 vs. 补丁生成），直接对比受限。

| 模型 | Overall (%) | Public (%) | Enhanced (%) | Sem. (%) | API (%) | Design (%) |
|---|---|---|---|---|---|---|
| Claude-Opus-4.8 | 38.2 | 48.5 | 35.5 | 22.6 | 12.1 | 44.4 |
| GPT-5.5 | 37.2 | 50.3 | 32.8 | 21.5 | 9.3 | 36.5 |
| Gemini-3.1-Pro | 27.0 | 37.0 | 23.5 | 18.9 | 8.9 | 28.6 |
| GLM-5.1 | 26.6 | 36.8 | 23.7 | 21.1 | 10.0 | 37.1 |
| Claude-Sonnet-4.6 | 21.8 | 29.0 | 19.4 | 22.9 | 10.1 | 37.5 |
| MiniMax-M2.5 | 0.8 | 1.5 | 0.6 | 11.8 | 5.5 | 23.1 |

最佳 Overall 率为 38.2%（Claude-Opus-4.8），Public 通过率（48.5%）显著高于 Enhanced（35.5%），表明可见示例的复现不等于鲁棒行为。消融实验显示，将 Public 用例文件直接放入工作区使 GLM-5.1 的 Overall 从 37.4% 升至 61.8%，但约束覆盖率从 63.8% 降至 61.2%，说明可执行用例比交互澄清更有效。交互预算从 8 增至 24 时，Overall 从 22.9% 升至 37.4% 后回落至 34.4%，表明过量查询引入冗余信息反而增加集成负担。

评估边界方面，ICAE-Bench 通过预置终极镜像规避了环境配置瓶颈，这可能高估智能体在真实异构环境中的鲁棒性。代码已开源，但 User Agent 的接地设计依赖基准预制的约束记录，无法模拟真实用户的非理性反馈或错误信息，交互的真实性存在局限。

## 关联研究分析

从问题动机看，ICAE-Bench 与 ProgramBench 同属黑盒行为评估，但 ProgramBench 提供静态可执行文件作为目标接口，而 ICAE-Bench 将目标行为隐藏在交互背后。这一差异源于任务特性：ProgramBench 评估“重建”能力，ICAE-Bench 评估“发现+构建”能力。然而，ICAE-Bench 的 User Agent 仅返回预制记录，未模拟真实用户可能提供的错误约束或矛盾信息，这使得其“交互”更接近信息检索而非真正的需求协商。

从方法设计看，ICAE-Bench 与 SWE-bench 共享执行接地验证范式，但 SWE-bench 评估补丁对现有代码库的修复，ICAE-Bench 评估从零构建的仓库。SWE-bench 的 SOTA 解决率（如 SWE-Universe 75.3%）远高于 ICAE-Bench 的 38.2%，但这并非模型能力退化，而是任务复杂度跃升：0-to-1 构建涉及架构设计、依赖管理等多维决策，而 Issue 修复仅需局部修改。ICAE-Bench 未采用 SWE-bench 的多智能体协作架构，而是聚焦单智能体+User Agent 交互，这限制了其对复杂协调能力的评估。

## 总结

ICAE-Bench 解决了模糊意图下交互式项目构建的评估难题，通过从精确仓库反向生成模糊需求并接地交互，实现了需求获取与代码实现的解耦评估。实验表明，当前最佳模型 Overall 率仅 38.2%，且可见示例通过率远高于隐藏约束，揭示智能体在需求保持与实现转化上的瓶颈。该基准的边界在于预置环境掩盖了依赖解析的真实难度，且 User Agent 的接地设计限制了交互的真实性。当智能体面对真实用户提供的矛盾或错误约束时，其澄清策略的鲁棒性如何，论文未给出回答。
