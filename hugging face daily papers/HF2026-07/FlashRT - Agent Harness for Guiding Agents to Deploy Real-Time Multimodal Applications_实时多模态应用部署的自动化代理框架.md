> 实时多模态应用由异构模型组成复杂流水线，其高效部署需针对每个应用定制放置、流式与并行策略，而现有系统仅支持静态策略或固定工作负载，无法泛化。FlashRT 通过引导编码代理执行“链式编程”范式，将用户参考实现转化为中间表示（IR），再经自驱动验证循环生成跨硬件的高效部署。该方法在 NVIDIA B200 上实现约 70 倍延迟降低与 2.8 倍吞吐提升，在 AMD MI355X 上达 3.6 倍吞吐增益，但缺乏对精度损失的量化评估，且依赖代理对应用结构的正确解析。

## 研究背景

实时多模态应用（如语音代理、视频世界模型）将自动语音识别（ASR）、大语言模型（LLM）、文本转语音（TTS）及声转视频（S2V）等异构模块串联成流水线。这类流水线的计算特性高度异质：ASR 与 LLM 为内存带宽密集，而 S2V 中的 DiT 与 VAE 为计算密集，且各模块间存在数据依赖与持久状态（如 KV 缓存）。传统部署需人工设计每个应用的 GPU 放置、流式切分与并行策略，但应用数量激增使手工工程不可扩展。

现有自动化方案存在三重局限：多模态服务框架（如 vLLM-Omni）仅支持静态解耦或共置策略，无法灵活权衡延迟与吞吐；自动并行框架（如 FlexFlow、Alpa）针对单一固定工作负载优化，无法泛化到异构推理流水线；编译器（如 TVM）仅优化算子级性能，不涉及设备放置与阶段重叠。FlashRT 的切入点在于利用编码代理的高层推理能力，以自适应粒度组织流水线，将 NP-hard 的部署问题转化为可搜索的代码生成任务。

## 核心方法

### 方法参照系

本文问题属于多模态推理部署优化，但区别于静态规则系统或固定图优化器，其核心差异在于部署策略需针对任意用户编写的单 GPU 参考实现动态生成，且优化粒度（如流式、并行）在不同组件间异构。

### 链式编程范式与中间表示

设计动机：直接提示代理优化基线代码时，代理常遗漏应用级流式机会或模型级并行策略，且无法组合多种优化。FlashRT 引入链式编程范式，要求代理先将参考实现 $P_{ref}$ 转化为结构化中间表示（IR）。IR 建模为任务图 $G=(V,E)$，其中边 $(u,v,\lambda)$ 表示依赖，$\lambda=0$ 为批内数据依赖，$\lambda=1$ 为跨批状态依赖（如 KV 缓存）。该表示显式捕获数据流与持久状态作用域，使代理能进行静态分析以识别候选变换（如解耦、序列并行）。

### 自驱动验证循环

设计动机：代理可能生成错误部署或未能充分探索搜索空间。FlashRT 实施应用接地验证循环，代理自主设计测试基准，模拟用户输入驱动后端实现，并测量延迟与吞吐。部署 $\rho$ 需满足约束：

$$ S_{j,v} \ge S_{j-\lambda,u} + \tau_u(\rho) + \kappa_{u,v}(\rho) $$

其中 $S_{j,v}$ 为实例 $(j,v)$ 的启动时间，$\tau_u(\rho)$ 为放置依赖的执行时间，$\kappa_{u,v}(\rho)$ 为同步或传输成本。该循环强制代理在实现、验证、基准测试间迭代，确保部署正确性并发现高效策略组合。

## 实验评估

实验在单节点 8 块 NVIDIA B200 或 AMD MI355X GPU 上进行，评估五个实时多模态应用。基线包括顺序执行基线与专家系统 vLLM-Omni，但未对比 FlexFlow 等自动并行框架。在面对面对话代理应用中，FlashRT 在 1 GPU 上实现 27.4 倍 TTFO 延迟降低，3 GPU 上达 1.57 秒延迟与 40.88 FPS，8 GPU 上达 173.67 FPS。

| 部署策略 | GPU 数 | 延迟 (s) ↓ | 帧率 (FPS) ↑ |
| :--- | :--- | :--- | :--- |
| 顺序基线 | 1 | 107.92 | – |
| FlashRT (流式) | 1 | 3.94 | 16.26 |
| FlashRT (流式+解耦) | 3 | 1.57 | 40.88 |
| FlashRT (流式+解耦+S2V PP) | 8 | 1.66 | 173.67 |

消融显示，从 1 GPU 到 3 GPU，延迟降低 2.5 倍，帧率提升 2.5 倍，主要源于 TTS 与 S2V 解耦后的并行执行；从 3 GPU 到 8 GPU，帧率再提升 4.2 倍，延迟微增，源于 S2V 的流水线并行。在 AMD MI355X 上，FlashRT 在 Qwen3-Omni 上比 vLLM-Omni 延迟降低 65%，且所有应用恢复与 B200 相同的部署族，验证了跨硬件泛化能力。

评估边界：指标仅关注系统效率（TTFO、FPS），未量化精度损失；评估协议依赖代理生成的测试基准，缺乏标准化基准；代码开源但超参数与代理提示未完全公开，可复现性依赖代理模型版本。

## 关联研究分析

从问题动机看，FlashRT 与 vLLM-Omni 均解决多模态服务部署，但 vLLM-Omni 采用固定阶段解耦策略，而 FlashRT 通过 IR 分析实现动态粒度选择。这一差异源于任务特性：vLLM-Omni 针对 LLM 推理优化，而 FlashRT 需处理 DiT/VAE 等生成模型的异构计算特性，静态策略无法捕捉其延迟-吞吐权衡。

从方法设计看，FlashRT 借鉴 FlexFlow 的自动并行思想，但 FlexFlow 的搜索空间校准于密集 DNN 训练，无法泛化到异构推理流水线。FlashRT 利用代理的高层推理能力，在 IR 层面进行静态分析，避免了 FlexFlow 对固定工作负载的依赖。然而，FlashRT 未涉及 MoE 架构，而领域共识认为 MoE 是高效 MLLM 的主流选择，这暗示 FlashRT 在 MoE 模型上的部署策略可能需额外适配。

## 总结

FlashRT 解决的核心矛盾是实时多模态应用部署的 NP-hard 性与手工工程不可扩展性。其切入点在于利用编码代理的高层推理能力，通过链式编程范式与自驱动验证循环，将部署问题转化为可搜索的代码生成任务。实验证明其在 B200 上实现约 70 倍延迟降低与 2.8 倍吞吐提升，在 MI355X 上达 3.6 倍吞吐增益。边界在于缺乏精度量化评估，且依赖代理对应用结构的正确解析。当应用包含 MoE 架构或复杂状态依赖时，IR 表示是否仍能有效捕获优化机会，论文未给出回答。
