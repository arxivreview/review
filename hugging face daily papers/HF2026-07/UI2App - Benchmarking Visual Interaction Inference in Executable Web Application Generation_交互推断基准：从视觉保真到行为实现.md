作者：Grace Man Chen、Litao Guo、Yifan Wu 等 8 人

论文原文见 [arXiv](https://arxiv.org/abs/2607.06306)

> 现有图像驱动网页生成基准仅评估渲染输出的像素级相似度，导致模型生成的“冻结外观”——视觉正确但交互失效——无法被识别。UI2App 通过引入交互推断（Interaction Inference, IIS）维度，首次量化了模型从静态截图恢复应用行为逻辑的能力。该基准构建了包含 45 个状态一致截图集的测试集，并设计了基于功能正确性而非单一参考匹配的评估协议。实验揭示了视觉保真度与交互实现能力之间的显著解耦，但 IIS 对人工标注的依赖及跨模型公平性仍存疑。

## 研究背景

当多模态大语言模型（MLLMs）接收 UI 截图时，其视觉编码器能精确捕捉布局与色彩，但无法直接读取隐含在界面元素背后的状态机逻辑。这种视觉-行为鸿沟导致生成的网页往往呈现为“冻结外观”：界面元素位置、样式与参考图高度一致，但点击、拖拽或跨页面状态同步等交互行为完全缺失或错误。要解决这一问题，需区分“规格遵循”（Specification-Following）与“交互推断”（Interaction Inference）：前者基于明确的文本或视频指令实现已知目标，后者则要求模型仅凭静态视觉证据，推断出未显式声明的行为逻辑，如购物车状态在路由切换后的持久化或音频合成器的信号链构建。

现有图像到代码生成基准（如 Design2Code、WebGen-Bench）主要关注视觉保真度，通过像素相似度或 DOM 结构匹配评估生成质量，却忽略了应用是否“可用”。这种评估盲区使得高视觉保真度的模型（如 Gemini 3.1 Pro Preview）可能因缺乏交互逻辑而被评为高分，尽管其生成的应用在实际使用中毫无功能。UI2App 的切入点在于将评估重心从“长得像”转向“用得对”，通过构建状态一致的截图集，迫使模型推断跨路由的状态管理、事件绑定及数据同步逻辑，从而揭示 MLLMs 在从静态视觉证据恢复动态应用行为方面的真实能力边界。

## 核心方法

### 方法参照系

本文问题属于“图像驱动代码生成”范畴，但与传统 Screenshot-to-Code 流程的关键差异在于输入模态的纯粹性与评估维度的行为化。传统流程依赖文本提示或单页截图，输出单页 HTML；UI2App 仅输入多路由截图集，要求生成可执行的多页面框架应用，并引入交互推断作为核心评估指标，突破了仅关注视觉重建的局限。

### 状态一致截图集构建

设计动机在于解决单页截图无法提供跨路由状态线索的问题，导致模型无法推断全局状态管理逻辑。UI2App 构建了 45 个状态一致截图集，每个集包含同一应用在不同路由下的截图，且截图间隐含一致的状态变化（如购物车数量、表单输入值）。这种设计迫使模型在生成代码时，不仅需还原单页布局，还需推断路由间的数据流动与状态同步机制。

$$
S_{set} = \{ (s_i, r_i, \sigma_i) \}_{i=1}^{n}
$$

其中 $s_i$ 为路由 $r_i$ 的截图，$\sigma_i$ 为隐含的状态向量。模型需从 $\{s_i\}$ 中推断出统一的状态容器（如 Context 或 Store）及其更新规则，而非独立生成各路由的静态组件。

### 交互推断评估协议（IIS）

设计动机在于解决静态截图对行为的不确定性，即同一视觉状态可能对应多种有效交互实现（如搜索框可通过 Enter、点击或实时查询触发）。IIS 采用分类法驱动评估，将交互分为 7 类，每类配备基于功能正确性的评分标准，而非匹配单一参考代码。

$$
IIS = \frac{1}{|C|} \sum_{c \in C} \frac{1}{|I_c|} \sum_{i \in I_c} \mathbb{1}[\text{func}(i) = \text{true}]
$$

其中 $C$ 为交互类别集合，$I_c$ 为类别 $c$ 中的交互实例，$\mathbb{1}[\text{func}(i)]$ 为功能正确性指示函数，检查触发器、状态转换及界面行为是否符合预期。该公式通过功能等价性而非代码相似度评估，允许模型采用任意有效实现（如 localStorage 或内存状态），只要其行为符合截图隐含的逻辑。

## 实验评估

实验在 45 个应用上评估 6 个前沿 VLM（Claude Sonnet 4.6, Gemini 3.1 Pro Preview, Kimi K2.5, GPT-5.4, Qwen3.5-397B-A17B, GLM-4.6V）及 Qwen2.5-VL 缩放阶梯。基线覆盖当前主流多模态模型，但缺乏专用 GUI 定位模型（如 UI-TARS），因任务目标不同。主结果显示，视觉保真度（VFS）领导者 Gemini 3.1 Pro Preview（78.1）在交互推断（IIS）上仅排第四（7.5），落后于 IIS 领导者 Claude Sonnet 4.6（39.3）5.2 倍，证实视觉保真与交互实现能力解耦。

| 模型 | EXEC@1 (%) | EXEC@3 (%) | VFS | IIS |
| :--- | :--- | :--- | :--- | :--- |
| Claude Sonnet 4.6 | 95.6 | 100.0 | 75.7 | 39.3 |
| Gemini 3.1 Pro Preview | 87.3 | 100.0 | 78.1 | 7.5 |
| Kimi K2.5 | 78.2 | 86.7 | 65.3 | 20.7 |
| GPT-5.4 | 64.4 | 82.2 | 65.0 | 6.7 |
| Qwen3.5-397B-A17B | 66.6 | 77.8 | 56.0 | 13.2 |
| GLM-4.6V | 55.7 | 35.6 | 22.6 | 4.5 |

消融分析显示，IIS 对状态管理复杂度权重不敏感（Kendall $\tau$=1.0），但跨路由状态（S3）是普遍瓶颈：6 个模型中 3 个得分为 0，最高仅 21.6。构建失败（EXEC@3）主要源于脚手架违规（如 GLM-4.6V 的 35% 失败因覆盖 package.json），而非模型能力不足，表明评估协议对指令遵循的严格性可能掩盖了部分模型的交互推断潜力。

评估边界方面，IIS 依赖人工标注（Fleiss $\kappa$=0.73-0.84），存在主观偏差风险；VFS 仅评估 DOM 文本块对齐，忽略视觉细节如字体渲染；代码开源但超参数（如匈牙利算法阈值 $\theta_{DOM}=0.20$）固定，未报告 GPU 资源消耗，可复现性受限于模型 API 版本。

## 关联研究分析

从问题动机看，UI2App 与 Design2Code 的核心差异在于输入模态与评估目标。Design2Code 依赖单页截图与文本提示，评估视觉相似度；UI2App 仅用多路由截图，评估行为正确性。这一差异源于任务特性：单页生成无需跨路由状态推断，而多路由应用要求模型从视觉线索中恢复全局状态机。UI2App 的交互推断维度揭示了 MLLMs 在“视觉-行为”映射上的盲区，而 Design2Code 的视觉保真度指标无法捕捉此类失效。

从方法设计看，UI2App 与 WebGen-Bench 同属图像驱动生成，但 WebGen-Bench 依赖文本提示辅助布局，UI2App 完全依赖视觉证据。这一差异导致 UI2App 对模型的语义推理能力要求更高，如从“$0.00”子标题推断购物车状态，或从 MIDI 标签推断音频合成逻辑。WebGen-Bench 的文本提示降低了推断难度，但偏离了真实设计工作流（设计师仅提供 mockup）。UI2App 的纯视觉输入更贴近实际场景，但也暴露了模型在缺乏文本锚点时的行为推断局限。

## 总结

UI2App 解决了图像驱动网页生成中“视觉保真”与“功能正确”脱节的核心矛盾，通过状态一致截图集与功能正确性评估协议，首次量化了交互推断能力。实验证明，视觉保真度领导者 Gemini 3.1 Pro Preview 在 IIS 上仅得 7.5，而 Claude Sonnet 4.6 以 39.3 领先，证实两者能力解耦。本文边界在于 IIS 依赖人工标注且跨路由状态推断仍是普遍瓶颈，最高分仅 21.6。当模型规模从 3B 扩展到 72B 时，交互推断能力的边际收益是否递减，论文未给出回答。
