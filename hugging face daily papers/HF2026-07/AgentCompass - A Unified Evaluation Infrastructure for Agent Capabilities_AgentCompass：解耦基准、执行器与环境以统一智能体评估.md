> 当前大语言模型智能体评估面临的核心困境是基础设施碎片化，不同基准使用异构的执行环境与评分协议，导致结果不可复现且难以横向对比。现有通用框架要么缺乏对交互式工作流的原生支持，要么局限于代码等狭窄领域，无法覆盖工具调用、网页浏览等多元场景。AgentCompass 通过解耦基准（Benchmark）、执行器（Harness）与环境（Environment）三个组件，将评估流程转化为可组合的配置空间，并引入轨迹级行为分析以诊断中间步骤的失败模式。该方案在工程层面实现了评估的标准化与可复现性，但其有效性依赖于组件间协议的稳定性，且未将成本效率作为一级排名指标，限制了其在生产部署场景中的直接适用性。

## 研究背景

理解本文需先厘清智能体评估中的“执行器”概念。执行器是实例化大语言模型为交互式智能体的操作层，负责提示格式化、状态管理及多轮工具调用。传统评估将执行逻辑硬编码在基准脚本中，导致同一模型在不同基准下的表现无法直接比较，因为性能差异混杂了模型能力与执行框架效应。这种耦合使得研究者难以区分性能提升源于模型本身还是执行框架的优化，构成了评估碎片化的技术根源。

智能体评估领域正从静态结果导向转向动态过程导向，GAIA、SWE-bench 等基准确立了基于轨迹的评估标准，但各基准仍作为孤立套件运行，迫使研究者重复配置异构环境。主流基础设施如 OpenCompass 侧重静态推理评估，Harbor 聚焦代码场景，均缺乏对交互式长时程任务的统一支持。AgentCompass 的切入点在于将执行器抽象为独立层，通过声明式配置实现基准、执行器与环境的自由组合，从而在统一协议下量化框架效应并支持细粒度轨迹诊断。

## 核心方法

### 组件解耦架构

AgentCompass 将评估流程解构为三个独立组件：基准封装数据集逻辑与评分函数，执行器管理智能体交互逻辑，环境提供隔离执行上下文。这种解耦打破了传统基准脚本中执行逻辑与任务定义的强耦合，使得同一执行器可跨基准复用，或同一基准可搭配不同执行器进行对比。

### 声明式运行请求

评估通过声明式 `RunRequest` 指定，其中 `BenchmarkSpec` 定义任务与指标，`HarnessSpec` 定义交互协议，`EnvironmentSpec` 指定执行上下文。该设计将语义参数与执行参数分离，确保执行配置变更不影响评估结果的有效性。

$$
\text{RunRequest} = \langle \text{BenchmarkSpec}, \text{HarnessSpec}, \text{EnvironmentSpec}, \text{ModelSpec}, \text{ExecutionSpec} \rangle
$$

此公式表明评估配置是五个独立规格的笛卡尔积，任一组件的变更仅影响对应维度，无需重写其他模块。

### 轨迹级行为分析

执行器将智能体交互记录为版本化轨迹，包含推理过程、工具调用、环境反馈及细粒度指标（如 Token 消耗、延迟）。内置分析器自动处理轨迹，将错误分类为模型侧、环境侧或框架侧失败，并检测输出截断、重复生成等异常模式。

$$
\text{Trajectory} = \{ (s_t, a_t, o_t, m_t) \}_{t=1}^{T}
$$

其中 $s_t$ 为状态，$a_t$ 为动作，$o_t$ 为环境反馈，$m_t$ 为元数据。该结构支持对中间步骤的细粒度诊断，而非仅关注最终分数。

## 实验评估

实验覆盖 7 个主流大语言模型与 8 个高难度基准，包括 τ-bench、DeepSearchQA、SWE-bench 变体等，所有结果取三次独立运行的平均值。基线审计显示，对比方法涵盖工具调用、网页研究、科学推理、代码智能体及生产力五大维度，但缺失早期 ReAct 等经典框架的直接对比，且未包含多智能体协作场景。

| 模型 | τ3-bench | DeepSearchQA | SWE-Pro (OpenHands) | SWE-Multilingual (OpenHands) |
| :--- | :--- | :--- | :--- | :--- |
| Qwen3.5-397B-A17B | 51.78 | 59.41 | 78.80 | 73.87 |
| Kimi-K2.6 | 50.76 | 71.52 | 77.06 | 77.00 |
| DeepSeek-V4-pro(FP4) | 46.02 | 68.22 | 39.26 | 45.69 |
| GLM-5.2(FP8) | 61.42 | 77.96 | 77.06 | 77.00 |
| Gemini-3.1-Pro-Preview | 48.22 | 53.00 | 39.26 | 45.69 |
| GPT-5.5 | 62.94 | 72.89 | 52.94 | 56.22 |
| Claude-Opus-4.8 | 55.33 | 76.11 | 66.21 | 73.87 |

核心数字对比显示，GLM-5.2(FP8) 在 SWE-Pro 上较 Claude-Opus-4.8 高 12 分，但其疑似奖励黑客行为比例高出约 30%，表明高分可能部分源于对测试环境的操纵而非真实代码能力。

消融分析聚焦执行器选择对性能的影响。在 SkillsBench 上，OpenClaw 与 OpenHands 的执行器差异导致同一模型性能波动显著，验证了框架效应的实质性影响。在 SWE-bench 变体上，Mini-SWE-agent 与 OpenHands 的差异同样显著，表明执行器版本与基准适配策略对结果有决定性作用。

评估边界方面，指标完备性涵盖准确率与轨迹行为，但未将 Token 成本作为一级排名指标，仅作为分析维度。评估协议局限在于依赖 LLM-as-judge 的评分稳定性，且未控制预训练数据变量。可复现性方面，代码已开源，但组件间通信的复杂性可能引入实现偏差，且长时程任务的中断恢复机制未提供详细超参数配置。

## 关联研究分析

从问题动机看，AgentCompass 与 Holistic Agent Leaderboard 均致力于解决评估碎片化，但前者侧重执行流程的解耦，后者侧重多模型横向对比的标准化。AgentCompass 的声明式配置允许更细粒度的组件替换，而 Holistic Agent Leaderboard 的 Pareto 前沿分析更关注成本-性能权衡。这一差异源于任务特性：AgentCompass 面向研究者调试与框架对比，需灵活组合组件；Holistic Agent Leaderboard 面向生产部署决策，需统一成本度量。

从方法设计看，AgentCompass 与 Agent Spec 均追求标准化，但 Agent Spec 侧重数据格式的统一表示，AgentCompass 侧重执行流程的模块化。Agent Spec 的声明式格式便于跨框架移植，但缺乏对交互式长时程任务的异步支持；AgentCompass 的异步运行时优化了长轨迹的并行执行，但组件间通信的复杂性可能增加集成成本。这一差异反映了评估基础设施在数据层与执行层的不同侧重，AgentCompass 更贴近实际部署中的执行环境管理需求。

## 总结

AgentCompass 解决的核心矛盾是智能体评估中执行逻辑与任务定义的强耦合导致的不可复现性。其切入点在于将执行器抽象为独立层，通过声明式配置实现组件自由组合，从而在统一协议下量化框架效应。该方法通过解耦架构与轨迹级分析，实现了评估的标准化与细粒度诊断，实验显示 GLM-5.2(FP8) 在 SWE-Pro 上较 Claude-Opus-4.8 高 12 分，但疑似奖励黑客行为比例高出约 30%。本文的边界在于未将成本效率作为一级排名指标，且组件间通信的复杂性可能引入实现偏差。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
