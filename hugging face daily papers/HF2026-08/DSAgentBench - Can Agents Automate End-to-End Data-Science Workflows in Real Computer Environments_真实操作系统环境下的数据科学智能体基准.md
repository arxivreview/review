# HuggingFace最新推荐论文 ｜DSAgentBench: Can Agents Automate End-to-End Data-Science Workflows in Real Computer Environments? ｜真实操作系统环境下的数据科学智能体基准

研究机构：加拿大约克大学、新加坡南洋理工大学

作者：Mizanur Rahman、Mohammed Saidul Islam、Ridwan Mahbub 等 6 人

论文原文见 [arXiv](https://arxiv.org/abs/2608.10366)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.10366)

> 数据科学智能体（DSA）旨在自动化从数据清洗到洞察生成的全生命周期，但现有评估多局限于静态代码生成或沙盒环境，无法验证智能体在真实计算系统中的长程执行能力。DSAGENTBENCH 通过扩展 OSWorld 框架，构建了包含 275 个长程任务的真实操作系统环境，要求智能体协调 IDE、终端与浏览器完成端到端工作流。该基准揭示了当前智能体在 GUI 接地与工具编排上的巨大差距，为评估自主数据科学家提供了新维度，但其对多模态数据覆盖的局限性仍制约着结论的泛化性。

## 研究背景

数据科学工作流涉及编程、统计推理与可视化等多技能协同，传统自动机器学习（AutoML）仅能处理预定义管道，难以应对非结构化数据与开放式探索。大语言模型（LLM）虽能生成代码片段，但缺乏对内存对象状态的感知，导致基于错误假设继续执行。这种状态不可见性在长链推理中引发错误传播，使得静态代码生成范式无法应对多步依赖与动态调试需求。

现有数据科学基准如 DS-1000 和 DA-CODE 主要评估代码正确性，但局限于沙盒笔记本环境，缺乏操作系统交互与跨工具协调。通用计算机操作基准如 OSWorld 虽支持真实系统控制，但未针对数据科学工作流进行优化，无法评估分析推理与模型验证能力。这种割裂导致现有基准无法反映智能体在真实企业环境中从数据获取到模型部署的完整能力，亟需一个融合系统交互与分析深度的评估框架。

DSAGENTBENCH 抓住了这一被忽略的交叉点，将 GUI 智能体技术栈引入数据科学领域。它不依赖特权 API，而是通过视觉感知与 GUI 操作协调多种工具，模拟真实分析师的工作模式。这一设计将评估重点从“代码能否运行”转向“智能体能否在真实系统中自主完成分析任务”，填补了静态代码评估与通用系统操作之间的空白。

## 核心方法

### 环境架构与状态表示

DSAGENTBENCH 基于 OSWorld 框架扩展，运行于 Ubuntu 系统，预装 Python、VS Code、Jupyter Notebook 与 Chrome。环境形式化为元组 $(O, A, T)$，其中 $O$ 为观测空间，$A$ 为动作空间，$T$ 为状态转移函数。智能体在每步 $t$ 接收观测 $o_t \in O$，选择动作 $a_t \in A$，系统转移至状态 $s_{t+1} = T(s_t, a_t)$ 并返回新观测 $o_{t+1}$。观测空间包含两种模态：1920×1080 截图提供像素级视觉上下文，或截图加无障碍树（A11y Tree）提供结构化 UI 元数据，包括元素角色、名称与边界框。动作空间支持鼠标交互、键盘输入及元动作（WAIT、DONE、FAIL），确保智能体通过标准 GUI 操作完成终端、CLI 与脚本工作流，避免依赖特权接口。

$$
s_{t+1} = T(s_t, a_t), \quad o_{t+1} \sim P(o_{t+1} | s_{t+1})
$$

该公式描述了智能体在真实操作系统中的状态转移过程，强调观测是状态的不完全反映，智能体需通过 GUI 操作间接推断系统内部状态。

### 任务定义与确定性评估

任务定义为集合 $\mathcal{T} = \{(C_i, I_i, V_i)\}_{i=1}^N$，其中 $C_i$ 为任务配置（初始系统状态、数据集、库），$I_i$ 为自然语言指令，$V_i$ 为确定性 Python 评估器。评估器验证分析正确性而非代码执行，对分类任务检查模型性能阈值（如准确率或 F1 $\geq 0.7$），对可视化任务检查轴标签、标题与数据映射。任务成功定义为评估分数 $\geq 0.95$，允许数值精度或格式变异的微小容差。

$$
\text{Success}_i = \mathbb{1}[V_i(\text{Output}_i) \geq 0.95]
$$

该公式将任务成功量化为确定性评估器的阈值判断，确保评估结果可复现且不受代码风格影响，直接反映分析结果的语义正确性。

## 实验评估

实验在 275 个任务上评估 15 个闭源与开源智能体，包括 GPT-5、Claude-4.6-Sonnet、Gemini-2.5-Pro 及 UI-TARS 等。基线覆盖主流 LLM 与 GUI 智能体，但缺乏多智能体系统（如 VDSAgents）或专用数据科学智能体（如 Data Interpreter）的直接对比，因架构差异导致不可比。

| 模型 | Screenshot (%) | Screenshot + A11y (%) |
|---|---|---|
| Claude-4.6-Sonnet | 59.66 | 56.70 |
| GPT-5 | 27.73 | 29.81 |
| GPT-4o | 26.97 | 27.45 |
| Gemini-2.5-Pro | 19.12 | 21.00 |
| UI-TARS 7B | <1 | <1 |

Claude-4.6-Sonnet 在 Screenshot + A11y 设置下取得 56.70% 的最高成功率，显著领先 GPT-5 的 29.81%。开源模型在 Screenshot 设置下成功率均低于 1%，主要失败源于 GUI 接地错误（97–98%），表明视觉定位能力是开源模型的核心瓶颈。

消融实验显示，添加 A11y 树通常提升性能，但增益因模型而异。GPT-5-mini 在 Screenshot + A11y 设置下从 24.71% 提升至 24.47%（轻微下降），而 Claude-4.6-Sonnet 从 59.66% 降至 56.70%，表明结构化 UI 元数据对强接地模型可能引入噪声。任务难度分布中，47.6% 为困难任务（5+ 步），56.7% 涉及多阶段工作流，反映真实数据科学的复杂性。

评估边界方面，基准仅覆盖 95.3% 的表格数据，图像与文本数据占比极低（3.6% 和 1.1%），限制了多模态推理能力的评估。确定性评估器虽保证可复现性，但依赖预定义阈值，无法捕捉开放式分析中的创造性洞察。代码与超参数已开源，但 GPU 资源需求未明确报告，可能影响大规模复现。

## 关联研究分析

从问题动机看，DSAGENTBENCH 与 DA-CODE 均关注数据科学工作流，但 DA-CODE 局限于沙盒笔记本环境，仅评估任务规划与多文件分析，缺乏操作系统交互。DSAGENTBENCH 引入真实 OS 环境，要求智能体协调 VS Code、Jupyter 与 Chrome，模拟分析师在真实系统中的操作模式。这一差异源于任务特性：DA-CODE 假设数据已预加载，而 DSAGENTBENCH 包含数据获取阶段（如 Kaggle API 调用），更接近端到端实践。

从方法设计看，DSAGENTBENCH 与 Tree-Notebook 均关注状态感知，但 Tree-Notebook 通过数据探针提取 DataFrame 元信息重建数据状态，解决“静默失败”问题；DSAGENTBENCH 通过 A11y 树与截图重建 UI 状态，解决 GUI 接地问题。两者分别针对数据层与系统层的状态不可见性，但 DSAGENTBENCH 未探索数据状态与 UI 状态的联合表示。当智能体在 GUI 中执行代码时，数据状态的变化如何反映在 UI 观测中，论文未给出回答。

## 总结

DSAGENTBENCH 要解决的核心矛盾是现有基准无法验证智能体在真实操作系统中执行端到端数据科学工作流的能力。现有方法局限于静态代码生成或沙盒环境，缺乏系统交互与跨工具协调，而 DSAGENTBENCH 通过扩展 OSWorld 框架，引入真实 OS 环境与确定性评估器，填补了这一空白。实验表明，最强智能体 Claude-4.6-Sonnet 仅取得 56.70% 的成功率，开源模型低于 1%，暴露了 GUI 接地与长程推理的严重不足。该基准的边界在于数据模态单一（95.3% 表格数据）与评估阈值固定，无法捕捉开放式分析中的创造性洞察。当智能体在 GUI 中执行代码时，数据状态的变化如何反映在 UI 观测中，论文未给出回答。
