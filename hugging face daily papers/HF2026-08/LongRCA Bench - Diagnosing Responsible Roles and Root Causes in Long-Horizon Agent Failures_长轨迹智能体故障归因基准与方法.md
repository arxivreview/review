# HuggingFace最新推荐论文 ｜LongRCA Bench: Diagnosing Responsible Roles and Root Causes in Long-Horizon Agent Failures ｜长轨迹智能体故障归因基准与方法

研究机构：美国普林斯顿高等研究院、中国科学院大学

作者：Yunfei Zhang、Boyu Feng、Changhua Pei 等 17 人

论文原文见 [arXiv](https://arxiv.org/abs/2608.15242)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.15242)

> 长时程智能体执行失败时，仅报告最终结果无法定位决定性错误进入轨迹的具体位置及责任角色，导致开发者需人工审查数百步日志。现有评估基准多聚焦短轨迹或仅关注任务成功率，缺乏对“最早决定性根因步”与“责任角色”的独立、细粒度诊断。本文提出 LongRCA Bench 基准与 RCTA 无训练诊断方法，通过分段召回与上游指令回溯实现长轨迹中的精确归因。该工作填补了长时程故障诊断的空白，但 24.1% 的精确根因定位准确率表明自动诊断仍远未达到生产级可靠性，其诊断边界与在线检测能力的缺失值得深思。

## 研究背景

当智能体在复杂任务中执行失败，结果级评估器只能确认“任务未成功”，却无法揭示导致失败的决定性错误是在哪一步引入的，也无法判定是哪个工作流角色（如规划器、执行器）对此负责。这种诊断缺口在长轨迹中尤为严重：当初始错误与最终失败之间相隔数百个记录步骤时，后续步骤可能执行、传播或暴露已有错误，但并非错误源头。准确区分“引入决定性错误的步骤”与“传播错误的步骤”，是长时程智能体可靠性的核心前提。

当前轨迹级故障分析基准存在显著局限。Who&When 等基准平均轨迹长度仅 22.2 步，且多依赖人工注入错误或受控条件，难以反映真实执行中的自然失败模式。RootSE 虽提供自然失败轨迹，但平均长度仅 50.9 步，且未独立评估责任角色。这些资源无法覆盖“根因步后跟随数百步执行”的诊断场景，导致现有方法在长轨迹上的表现未被充分检验。本文切入点在于构建一个包含 1,140 条自然失败长轨迹的基准，并设计能处理长上下文与错误传播的诊断方法，将故障归因从短轨迹扩展至长时程场景。

## 核心方法

### 方法参照系

轨迹诊断方法通常直接在日志文本或紧凑表示上操作，通过提示工程或结构感知搜索定位错误步。本文问题与通用流程的关键差异在于：轨迹长度达 156.3 步平均，且根因步与终点距离中位数为 48 步，要求方法在长上下文中区分“引入错误”与“传播错误”，并独立预测责任角色而非从错误步发射者推导。

### 分段候选召回

长轨迹中故障相关证据分散于大量步骤，直接全上下文输入超出模型有效预算。RCTA 将轨迹划分为连续分段，每段包含最多 5 个前置重叠步骤以保留边界信息，分段边界由字符与步数限制规则确定，不使用语言模型。对每段生成摘要，基于摘要召回少量候选错误步。该设计将宽泛轨迹搜索与聚焦文本比较解耦，避免长上下文导致的注意力稀释。分段摘要召回的候选集 $C$ 满足：

$$
C = \{s_i \mid \text{summary}(s_i) \text{ matches fault pattern}\}
$$

其中 $s_i$ 为分段内步骤，匹配基于摘要与故障模式的语义一致性。此机制解决了全上下文提示在长轨迹中因信息过载导致的召回率下降问题。

### 上游指令回溯

候选错误步可能源自更早的交接指令（handoff instruction），即角色 X 向角色 Y 发出的标记为 $X \to Y$ 的日志消息。RCTA 对每个候选步 $s_i$，检索其角色对应的最近上游交接指令 $h_j$（若 $s_i$ 为执行器或验证器，则 $h_j$ 必须指向 $s_i$ 的角色；否则取最近可用交接指令作为计划上下文）。最终归因基于原始日志文本比较 $s_i$ 与 $h_j$，独立预测责任角色 $\hat{\rho}$ 与根因步 $\hat{r}$。回溯机制的决策规则为：

$$
\hat{r} = \arg\min_{s_i \in C} \text{distance}(s_i, h_j) \cdot \mathbb{I}[\text{error in } h_j]
$$

其中 $\mathbb{I}[\text{error in } h_j]$ 为交接指令包含决定性错误的指示函数。该设计解决了候选步本身看似正确但实为执行上游错误指令的情况，将归因从局部步骤扩展至因果链上游，提升了根因定位的准确性。

## 实验评估

实验在 LongRCA Bench 上进行，包含 1,140 条来自 SWE-bench Pro、Terminal Bench 2、TravelPlanner、VitaBench 和 WebArena Verified 的自然失败轨迹，由 22 名计算机科学研究生标注。基线覆盖提示工程（Who&When）、层次上下文（ECHO）、依赖搜索（FAMAS）等路线，但缺失基于因果图反事实推理的强基线。RCTA 使用相同推理骨干，在责任角色准确率、根因步精确准确率、根因步 ±5 准确率上分别达到 51.1%、24.1%、37.4%，超越最强基线 23.6、10.9、12.7 个百分点。

| 方法 | 责任角色准确率 (%) | 根因步精确准确率 (%) | 根因步 ±5 准确率 (%) |
| :--- | :--- | :--- | :--- |
| RCTA | 51.1 | 24.1 | 37.4 |
| 最强基线 | 27.5 | 13.2 | 24.7 |

消融实验未提供详细数据，但 RCTA 相比基线的显著提升表明分段召回与上游回溯的组合有效。根因步 ±5 准确率（37.4%）高于精确准确率（24.1%），说明方法能定位到错误步附近，但精确到步仍具挑战。

评估边界方面，LongRCA Bench 仅包含离线已完成轨迹，未评估在线故障检测能力；标注由 22 名研究生完成，未报告标注者间一致性（Inter-annotator agreement）；代码未公开，超参数与 GPU 配置未详细说明，可复现性受限。

## 关联研究分析

从问题动机看，本文与 Who&When 的核心差异在于轨迹长度与失败来源。Who&When 平均轨迹 22.2 步，多依赖人工注入错误，而 LongRCA Bench 平均 156.3 步，全部为自然失败。这一差异源于任务特性：长时程任务中错误传播掩盖初始故障点，短轨迹基准无法捕捉此现象。本文通过量化“根因-终点距离”（中位数 48 步，90 分位数 183 步）明确了长轨迹诊断的独特挑战，而 Who&When 未考虑此维度。

从方法设计看，本文与 FAMAS 的差异在于证据来源。FAMAS 重放失败任务并应用基于谱的定位，依赖执行依赖关系；RCTA 基于静态文本回溯，不重放任务。这一选择源于长轨迹重放的成本与复杂性，但可能牺牲了动态执行信息的利用。TraceElephant 提供组件与起源步标签，但平均长度仅 20.5–29.3 调用，未处理长轨迹中的错误传播。本文的“最早决定性”定义比 TraceElephant 的“任意起源步”更严格，但 24.1% 的精确准确率表明该严格性在长轨迹中难以实现。

## 总结

本文核心矛盾在于长轨迹中决定性错误步与责任角色的独立、精确归因。现有方法因短轨迹假设或全上下文限制无法处理数百步后的根因定位，本文通过分段召回与上游指令回溯解耦宽泛搜索与聚焦比较，在 LongRCA Bench 上实现 51.1% 责任角色准确率与 24.1% 根因步精确准确率。其边界在于仅评估离线场景，未报告标注一致性，且 24.1% 的精确准确率表明自动诊断仍不可靠。当根因-终点距离超过 200 步时，RCTA 的准确率是否进一步下降，论文未提供分层分析数据。
