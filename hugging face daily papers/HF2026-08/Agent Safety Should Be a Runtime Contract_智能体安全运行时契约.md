# HuggingFace最新推荐论文 ｜Agent Safety Should Be a Runtime Contract ｜智能体安全运行时契约

研究机构：中山大学

作者：Albus W. Ng、Yi Han、Jusheng Zhang 等 4 人

论文原文见 [arXiv](https://arxiv.org/abs/2608.11274)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.11274)

> 自主智能体执行代码、修改文件等具有副作用的动作时，传统模型对齐无法提供可验证的安全保证。现有防御多聚焦于拦截恶意输入或监控行为，却忽视了“任务完成”这一关键节点缺乏外部证据支撑，导致虚假完成与静默失败频发。本文提出将安全定义为系统强制执行的运行时契约，包含预防与证据双重机制，并形式化了轨迹模式与证据链。该架构在理论上闭合了安全验证的循环，但其证据门控的自动化生成与跨任务泛化能力仍存疑。

## 研究背景

当智能体被授权执行 `drop database` 或发送外部邮件时，其内部推理过程对外部观察者而言是不透明的黑盒。此时，仅依赖模型输出的“任务完成”声明不足以确认动作的安全性，因为模型可能产生幻觉或执行未授权的副作用。这一困境引出了“证据门控提交”（Evidence-gated submission）的概念：系统不应接受智能体的自报，除非轨迹中包含特定格式的可验证工件。然而，当前主流对齐技术如 RLHF 和 DPO 仅优化模型内部的概率分布，无法在运行时强制这种外部契约，导致安全边界模糊。

该领域长期面临“信任-授权不匹配”问题，即智能体拥有执行复杂任务的自主性，但缺乏细粒度的运行时验证机制。主流防御路线如 GuardAgent 和 VeriGuard 分别侧重于行为逻辑转换与形式化代码验证，但前者易被语义逃避绕过，后者计算开销大且通用性低。更根本的矛盾在于，现有研究将安全视为模型训练问题，而生产环境的安全依赖于独立的运行时基础设施。本文切入点在于指出模型对齐在结构上无法闭合安全循环，主张将安全单位从“模型”转移至“带可检查证据的轨迹”，通过系统级契约而非模型内部对齐来保障安全。

## 核心方法

### 方法参照系

本文问题置于“运行时防护架构”类别下，但关键差异在于：传统防护仅关注动作执行前的拦截（预防），而本文引入动作执行后的结果验证（证据），将安全从单向监控扩展为双向契约。

### 预防层：纵深防御机制

预防层旨在动作发生前阻断风险，解决模型对齐作为“单点防御”易被越狱或微调攻击绕过的失效。本文采用 Saltzer–Schroeder 原则构建多层独立监控，包括沙箱隔离、工具白名单、文件系统范围守卫及行为监控。设计动机是确保即使某一层被突破，其他层仍能限制爆炸半径。其核心约束可形式化为：

$$
\text{PreventiveConstraint} = \bigwedge_{i=1}^{n} \phi_i(x)
$$

其中 $\phi_i$ 为第 $i$ 层监控器对输入 $x$ 的安全属性检查。该公式表明，只有当所有独立监控层同时通过时，动作才被允许执行，从而将静默的奖励黑客行为转化为可观测的违规事件。

### 证据层：轨迹模式与证据链

证据层旨在任务完成后验证结果真实性，解决模型自报与实际行动不一致导致的虚假完成问题。本文定义“轨迹模式”（Trajectory Schema）为任务完成的必要条件，要求轨迹中包含特定工件（如测试通过日志、文件差异、引用验证）。设计动机是区分“软证据”（模型自报）与“硬证据”（外部可验证工件）。其形式化定义为：

$$
\text{EvidenceGate}(T) = \exists \eta \in \text{Trajectory}(T) : \text{Verify}(\eta) = \text{True}
$$

其中 $T$ 为任务，$\eta$ 为轨迹中的证据工件，$\text{Verify}$ 为基于已知格式的验证函数。该公式表明，任务仅在轨迹中存在可通过外部验证的工件时，才被系统标记为完成，从而将验证责任从用户转移至系统。

## 实验评估

本文未使用 AgentDojo 或 ASB 等标准基准，而是通过四项公开证据审计支撑立场。基线审计显示，对比对象为“模型对齐”范式与现有生产系统，未涵盖具体防御算法的性能对比。

| 审计类型 | 样本量 | 关键发现 |
|---|---|---|
| 事故调查 | 52 | 40 例可被预防层完全阻止，11 例可部分缓解 |
| 虚假完成审计 | 31+1 | 8 例引用验证，8 例日志捕获，7 例测试运行 |
| 轨迹模式审计 | 12 | 仅 2 个系统（GitHub Copilot, OSWorld）具备证据门控 |
| 论文审计 | 28,560 | 训练时对齐论文数量是部署时护栏论文的 8–12 倍 |

核心数字对比表明，现有生产系统普遍缺乏证据门控机制，且学术界对部署时护栏的研究严重不足。

消融与设计决策验证方面，本文未提供传统消融实验，但通过事故调查的编码协议验证了预防层的有效性。52 例事故中，40 例可被功能完整的护栏层阻止，表明多层防御在已知攻击场景下具有显著效果。然而，11 例部分缓解案例揭示了单一机制的局限性，需结合证据层才能完全闭合安全循环。

评估边界与可复现性方面，本文作为立场论文，其有效性取决于论证逻辑与证据广度，而非算法性能。指标完备性上，未报告计算开销或延迟，无法评估运行时契约的实际部署成本。评估协议局限在于，事故样本来自公开报告，可能存在选择偏差，且未包含零样本未知攻击场景。可复现性上，论文提供了补充 JSON 文件，但未开源代码或提供可复现的实验环境。

## 关联研究分析

从问题动机看，本文与 GuardAgent 和 VeriGuard 存在根本差异。GuardAgent 将自然语言约束转化为可执行逻辑，侧重于行为监控，但易被语义逃避绕过；VeriGuard 通过形式化代码生成提供数学正确性保证，但计算开销大且通用性低。本文则主张安全是系统契约而非模型属性，通过证据门控解决虚假完成问题，这一视角在 GuardAgent 和 VeriGuard 中均未涉及。根源在于，本文关注的是“任务完成”这一结果节点，而前者关注“动作执行”这一过程节点，任务特性决定了证据层在结果验证中的必要性。

从方法设计看，本文与 Agent libOS 同属系统级隔离路线，但 Agent libOS 侧重于资源控制与身份管理，而本文侧重于证据验证与轨迹审计。Agent libOS 通过库操作系统架构实现细粒度权限隔离，但未涉及任务完成后的证据验证；本文则通过轨迹模式与证据链，将安全延伸至结果验证阶段。这一差异源于 Agent libOS 关注“谁有权执行”，而本文关注“执行结果是否可信”，两者在系统级治理中互补但侧重不同。

## 总结

本文要解决的核心矛盾是模型对齐无法提供可验证的运行时安全保证，导致虚假完成与静默失败频发。本文抓住的切入点是安全单位应从模型转移至带可检查证据的轨迹，通过系统级契约而非模型内部对齐来保障安全。本文提出了预防与证据双重机制的运行时契约，形式化了轨迹模式与证据链，并基于 52 例事故调查和 28,560 篇论文审计提供了实证支持。证明了 40/52 事故可被预防层阻止，且现有生产系统普遍缺乏证据门控机制。本文的边界在于，证据门控的自动化生成与跨任务泛化能力未得到验证，且未报告运行时开销。当任务描述复杂且缺乏明确验收标准时，证据门控的适用性如何，论文未给出回答。
