# HuggingFace最新推荐论文 ｜ExtractBench: A Benchmark for Schema-Guided Enterprise Document Extraction ｜面向企业级动态 Schema 的文档抽取基准

作者：Boyang Zhang、Adrian Lyjak、Eli Stewart 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2607.29677)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2607.29677)

> 企业级文档抽取的核心矛盾在于：用户定义的 Schema 是动态且多样的，而现有基准多针对固定模板或通用解析，无法同时评估系统在长文档完整性、视觉溯源与处理成本上的表现。本文提出 ExtractBench，通过 370 份真实企业文档与 5 维挑战标签，首次将值准确率、词级/页级溯源 F1 与每页成本纳入统一评估框架。实验表明，专用 API 在长列表与溯源任务上显著优于通用 VLM 与编码智能体，但词级溯源准确率仍低于 50%。该基准填补了生产环境评估空白，但其对“成本-质量”权衡的量化是否足以指导实际部署，仍需更多垂直领域验证。

## 研究背景

企业文档抽取任务中，Schema 定义了抽取目标，但不同供应商的发票、保险理赔单在布局与长度上差异巨大。传统固定模板方法无法适应这种动态性，而通用视觉-语言模型（VLM）虽能直接生成结构化输出，却常在长文档中截断记录列表，且默认不返回证据位置。这导致两个关键问题：一是长列表完整性无法保证，二是抽取结果缺乏可审计性，人工复核成本高昂。

现有基准如 SROIE、DocILE 聚焦固定本体，而 Contextual EB、LongArray 等虽引入动态 Schema，但分别缺失真实扫描件、长记录完整性或成本评估。例如，Contextual EB 仅评估 5 个共享 Schema，未覆盖手写或扫描噪声；LongExtract-50 使用合成数据，无法反映真实企业文档的视觉多样性。这些碎片化覆盖使得系统失败原因难以诊断：是模型能力不足，还是文档感知挑战（如旋转、手写）导致？

本文切入点在于构建一个多维诊断基准，将任务挑战（长列表、密集表单）、感知挑战（扫描、手写）、表格结构、长度与业务域作为独立标签轴，使低分可追溯至具体原因。同时，首次将每页成本纳入评估，回应企业级部署中“1 美分/页”可能决定项目可行性的现实约束。

## 核心方法

### 方法参照系

本文问题属于“Schema 引导的文档抽取”类别，其标准流程为：输入文档与用户定义的 JSON Schema，输出符合 Schema 的 JSON 对象及证据。与通用文档解析（如 Markdown 生成）的关键差异在于：Schema 是动态的、任务特定的，且要求输出严格符合类型约束与空值处理，而非自由文本。

### 多维挑战标签体系

传统基准仅报告单一聚合分数，无法区分系统失败源于任务难度（如长列表截断）还是感知噪声（如手写识别）。本文设计 5 个独立标签轴：任务挑战（T1-T3）、感知挑战（P1-P3）、表格结构（S1-S5）、长度（L1-L3）与业务域（D1-D8）。每个文档沿这些轴独立标注，使同一任务可在不同感知条件下出现。例如，T1（长列表完整性）在 L3（>50 页）文档中更易失败，而 P3（手写）在 T3（密集表单）中加剧过抽取风险。这种解耦设计允许诊断“系统在长文档上截断记录”与“在手写文档上误读值”是不同失效模式。

### 可扩展的 Schema 与真值构建

人工标注所有字段在 4,869 页规模下不可行，且单一抽取器输出作为真值会引入偏差。本文采用三源混合策略：真实文档使用前沿模型集成（GPT、Claude Code、Codex、Gemini）投票，分歧由人工裁决；合成长列表通过程序化生成，值与边界框由渲染代码直接确定；扫描表单由人工验证每个值与边界框。该策略确保真值质量：真实文档依赖跨模型一致性，合成列表依赖构造正确性，扫描表单依赖人工校验。

$$
\text{Grounding F1} = \frac{2 \cdot \text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}
$$

其中，Precision 为正确值且边界框 IoU≥0.5 的字段比例，Recall 为所有应抽取字段中被正确溯源的比例。该公式量化了“值正确”与“位置正确”的联合满足度，是审计可追溯性的核心指标。

## 实验评估

实验在 ExtractBench 上进行，覆盖 14 个系统：商业 VLM（GPT-5.4 Nano、Gemini 3.5 Flash）、开源 VLM（Lift 9B、Qwen3.6 35B-A3B）、编码智能体（Claude Code Opus 4.8、Codex GPT-5.5）与专用 API（LlamaExtract、Reducto、Extend、Datalab）。基线覆盖三类主流路线，但缺失知识库中提到的 LayoutLM 系列小模型，可能低估了轻量级模型在特定垂直领域的表现。

| 系统 | 整体值 F1 (%) | 短文档 F1 (%) | 长文档 F1 (%) | 词级溯源 F1 (%) | 页级溯源 F1 (%) | 每页成本 (¢) |
|---|---|---|---|---|---|---|
| LlamaExtract Agentic Plus | 95.6 | 96.6 | 94.4 | 46.4 | 84.9 | 8.1 |
| Codex GPT-5.5 | 95.4 | 93.6 | 93.6 | 0.0 | 0.0 | 27.8 |
| Reducto Deep Extract | 95.3 | 95.3 | 95.3 | 43.3 | 71.7 | — |
| Gemini 3.5 Flash | 87.9 | 87.9 | 27.9 | 0.0 | 0.0 | ≤1.0 |
| Datalab A+B | 54.4 | 54.4 | 0.0 | 2.0 | 48.5 | — |

LlamaExtract Agentic Plus 在整体值 F1、长文档 F1 与页级溯源 F1 上均领先，且成本仅为 Codex GPT-5.5 的 29%。Gemini 3.5 Flash 在长文档上 F1 从 87.9% 骤降至 27.9%，暴露了通用 VLM 在长列表完整性上的严重缺陷。Datalab 在长文档上 F1 为 0.0%，表明其架构无法处理跨页结构。

消融分析显示，感知挑战对系统表现影响显著：Codex GPT-5.5 在旋转/图像捕获（P1）上 F1 从 93% 降至 80%，而 Reducto 在扫描页（P2）上 F1 从 90% 降至 81%。表格结构挑战中，超大表格（S4，>1000 行）导致所有 VLM F1 低于 10%，而 LlamaExtract Agentic Plus 仍达 95.9%，表明其迭代工具循环在长列表处理上具有独特优势。

评估边界方面，词级溯源 F1 最高仅 46.4%，表明即使值正确，精确定位证据仍是开放问题。成本数据仅覆盖有 API 定价的系统，开源模型被排除，可能影响成本-质量权衡的完整性。代码与数据集已开源，但 Schema 构建依赖前沿模型集成，复现时需考虑模型版本差异。

## 关联研究分析

从问题动机看，本文与 FireRed-OCR、Qianfan-OCR 等端到端解析方法存在根本差异：后者聚焦通用 Markdown 生成，而本文强调动态 Schema 遵循与证据溯源。FireRed-OCR 通过几何驱动特征提取提升表格解析精度，但未评估成本或溯源；Qianfan-OCR 引入 Layout-as-Thought 机制生成布局表示，但输出仍为自由文本，无法保证 Schema 合规性。本文的 Schema 引导范式要求输出严格符合 JSON Schema 类型约束，这是通用解析方法未覆盖的维度。

从方法设计看，本文与 Logics-Parsing 的 RL 优化路线形成对比：Logics-Parsing 通过强化学习优化阅读顺序，而本文通过编码智能体的迭代工具循环（检查、编码、验证、修订）实现长列表完整性。实验显示，Codex GPT-5.5 在长文档上 F1 93.6%，高于 Gemini 3.5 Flash 的 27.9%，但成本高达 27.8¢/页。这暗示 RL 优化可能以更低成本实现类似效果，但本文未对比 RL 微调的 VLM，无法判断编码智能体的高成本是否必要。

## 总结

本文核心矛盾在于动态 Schema 抽取中值准确率、溯源可审计性与处理成本的三元权衡。现有基准缺失成本与溯源评估，而通用 VLM 在长文档上截断记录且默认不返回证据。本文通过 5 维挑战标签与三源真值构建，首次量化了这些维度，证明专用 API（LlamaExtract Agentic Plus）在长列表与溯源上优于通用 VLM 与编码智能体，但词级溯源 F1 仍低于 50%。其边界在于：词级溯源的精确性不足，且成本-质量权衡未覆盖开源模型。当企业部署中“1 美分/页”的成本差异决定项目可行性时，如何在不牺牲溯源精度的前提下进一步降低专用 API 的成本，本文未给出回答。
