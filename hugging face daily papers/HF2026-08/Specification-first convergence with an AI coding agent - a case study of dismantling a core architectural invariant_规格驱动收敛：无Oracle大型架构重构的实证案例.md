> 大语言模型软件工程智能体（LLM Agents for Software Engineering）在仓库级Issue修复上依赖预存测试套件作为执行接地验证的基准，但真实工程中大量维护任务的目标行为在变更前并不存在，导致测试Oracle缺失。现有方法在此类无Oracle场景下缺乏收敛机制，本文提出以“冻结规格书”替代测试套件作为验证基准，通过多轮迭代审计实现架构一致性收敛。该协议在189文件、717k行代码库中完成核心不变量拆除，3天内修正201个缺陷，成本2,430美元，但单案例、闭源且无对照组的局限使其结论外推性存疑。

## 研究背景

当智能体面对跨百文件依赖的架构重构时，传统“生成-测试”范式失效，因为目标行为未存在于历史数据中，无法构建测试Oracle。这一困境源于执行接地验证（Execution-Grounded Verification）对预存测试套件的依赖：SWE-bench等基准假设正确行为已编码在测试中，智能体仅需寻找满足测试的代码。然而，当变更涉及拆除核心不变量（如UI面板生命周期保证）时，新行为需从需求推导而非转录，测试Oracle无法覆盖。

主流路线聚焦于通过强化学习（RL）或记忆机制提升长程推理稳定性，但均假设存在可验证的奖励信号。SWE-RL利用执行反馈作为奖励，SWE-MeM通过记忆缓解上下文遗忘，但这些方法在“无测试Oracle”场景下缺乏收敛判据。本文切入点在于将验证基准从“结果正确性”前移至“意图一致性”，通过规格书的迭代细化与代码的迭代审计，构建无Oracle条件下的收敛协议。

## 核心方法

### 方法参照系

本文任务属于智能体架构设计中的工作流导向路线，但关键差异在于验证机制：标准流程依赖测试通过作为奖励，本文依赖“规格书零发现”作为收敛条件。SWE-agent确立的Agent-Computer Interface（ACI）交互模式被继承，但工具调用扩展为规格审计，单智能体多轮自我审计替代多智能体角色分工。

### 规格细化循环

规格细化（Refine）阶段解决初始规划的盲区问题。通常做法是单次生成规格书，但本文引入14轮迭代审计：智能体重新分析规格书与真实源代码，报告缺陷并重写。每轮独立会话，平均35分钟，产生约85处修正，将文件范围从110扩展至160。收敛判据为连续两轮零发现，第14轮无发现后冻结第13轮规格书。该循环的数学表达为：

$$
S_{t+1} = \text{Audit}(S_t, C) \quad \text{until} \quad \text{Findings}(S_t, C) = 0 \land \text{Findings}(S_{t-1}, C) = 0
$$

其中 $S_t$ 为第 $t$ 轮规格书，$C$ 为源代码，$\text{Audit}$ 为审计函数。物理含义：规格书通过反复对照源代码消除歧义，直至稳定。

### 代码验证循环

代码验证（Verify）阶段解决生成代码与冻结规格书的架构一致性。通常做法是编译/测试反馈，但本文引入17轮独立审计：智能体分析当前源代码与冻结规格书，报告架构缺陷并修正。每轮审计7-45分钟，修正生成15-60分钟，共116处代码修正。收敛判据同为连续两轮零发现，第16、17轮满足。该循环的数学表达为：

$$
P_{t+1} = \text{Audit}(P_t, S_{\text{frozen}}) \quad \text{until} \quad \text{Findings}(P_t, S_{\text{frozen}}) = 0 \land \text{Findings}(P_{t-1}, S_{\text{frozen}}) = 0
$$

其中 $P_t$ 为第 $t$ 轮代码状态，$S_{\text{frozen}}$ 为冻结规格书。物理含义：代码通过反复对照固定基准消除偏差，直至符合架构意图。

## 实验评估

实验在717,725行TypeScript代码库（3,648文件）上执行，任务为拆除UI面板生命周期不变量。基线覆盖审计：本文未对比任何SWE-bench SOTA方法（如SWE-Universe 75.3%），因任务无Oracle且不可比；未对比多智能体架构（如AgentForge），因采用单智能体多轮审计。主结果：189文件变更（31新增），201缺陷修正（85规格书+116代码），3天完成，成本2,430美元。首次手动执行无缺陷，后续约30次会话无Bug，预存单元测试套件无回归。

| 指标 | 数值 |
|---|---|
| 文件变更数 | 189 |
| 新增文件数 | 31 |
| 规格书修正数 | ≈85 |
| 代码修正数 | 116 |
| 总缺陷数 | 201 |
| 耗时 | 3天 |
| 成本 | USD 2,430 |

消融与设计决策验证：规格细化14轮与代码验证17轮的收敛判据均为连续两轮零发现，而非固定轮数。边际收益递减体现在后期修正数减少（如验证第16、17轮零发现），但论文未量化每轮修正的架构影响权重。设计决策中，智能体拒绝部分实现以维护原子性，3步分解替代10步，反映对仓库一致性的优先考量。

评估边界与可复现性：指标完备性限于“无Bug观察”，非缺陷存在性证明；评估协议依赖作者自报，无独立第三方验证；可复现性受限于闭源代码库，仅版本2.3.0可下载验证行为，过程不可复现。

## 关联研究分析

从问题动机看，本文与SWE-RL（Wei et al., 2025）同属长程推理稳定性路线，但SWE-RL依赖执行反馈作为RL奖励，本文依赖规格书零发现作为收敛判据。差异根源在于任务特性：SWE-bench任务有预存测试Oracle，本文任务无Oracle。SWE-RL的奖励信号在本文场景中不可用，因为目标行为未编码在测试中。本文的规格书收敛是否比测试通过更能保证架构一致性，论文未给出量化对比。

从方法设计看，本文与AgentForge（Kumar et al., 2026）同属多阶段工作流，但AgentForge依赖Planner-Coder-Tester-Debugger-Critic角色分工与Docker沙箱执行，本文依赖单智能体多轮自我审计。差异根源在于验证机制：AgentForge的执行验证是编译/测试通过，本文的验证是架构一致性审计。AgentForge的验证针对功能正确性，本文的验证针对意图一致性。单智能体多轮审计在计算成本上低于多智能体协调，但缺乏角色分工带来的视角互补，是否导致盲区，论文未探索。

## 总结

本文要解决的核心矛盾是无Oracle大型架构重构缺乏收敛机制。现有方法依赖测试Oracle或RL奖励，在目标行为不存在于历史数据时失效；本文凭借“冻结规格书”作为固定基准，通过迭代审计实现意图一致性收敛。协议在189文件、717k行代码库中完成核心不变量拆除，3天内修正201个缺陷，成本2,430美元。边界在于单案例、闭源、无对照组，且“无Bug观察”非缺陷存在性证明。当规格书本身存在初始偏差时，14轮细化是否足以消除所有架构歧义，论文未给出回答。
