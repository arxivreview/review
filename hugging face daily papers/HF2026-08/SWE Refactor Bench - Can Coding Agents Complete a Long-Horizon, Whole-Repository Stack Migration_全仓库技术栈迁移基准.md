# HuggingFace最新推荐论文 ｜SWE Refactor Bench: Can Coding Agents Complete a Long-Horizon, Whole-Repository Stack Migration? ｜全仓库技术栈迁移基准

研究机构：清华大学

论文原文见 [arXiv](https://arxiv.org/abs/2608.23564)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.23564)

> 软件工程智能体在仓库级 Issue 修复上已具备较高可靠性，但面对全仓库技术栈迁移这一长程、全局性任务时，现有评估范式因缺乏“迁移发生”的验证机制而失效。本文指出行为测试无法区分“未迁移”与“正确迁移”，提出 SWE Refactor Bench，通过三阶段协议（迁移审计、行为测试、智能体验证）解耦迁移完整性与行为保持。实验显示当前前沿模型仅 5.4% 的运行通过全部阶段，揭示了智能体在长程重构中的关键能力缺口。该基准为评估迁移能力提供了新标准，但其任务集规模与模型覆盖范围是否足以代表工业级迁移的普遍难度，仍需后续验证。

## 研究背景

当智能体面对一个运行正常的代码库时，其任务不再是修复缺陷，而是将底层技术栈（如语言、框架、构建工具）整体替换，同时保持外部行为不变。这一过程称为行为保持迁移（Behaviour-Preserving Migration）。迁移的难点在于，原始代码库本身是行为参考，无需额外规格说明，但智能体必须确保新栈完全替代旧栈，而非仅做表面修改。

现有仓库级基准（如 SWE-bench）依赖“红转绿”信号，即测试在补丁前失败、补丁后通过，这一范式适用于 Bug 修复，但迁移任务起始状态即为“绿”，导致固定测试套件无法区分“未迁移”与“正确迁移”。主流路线如 SWE-EVO 关注长程功能演化，但未解决迁移完整性验证问题。本文切入点在于识别“Blindness”（盲目性）：行为测试可能奖励未执行迁移的提交，因此需引入独立于行为测试的迁移审计机制。

## 核心方法

### 任务形式化与三阶段协议

本文任务定义为元组 $\tau = (R_A, \Sigma_A \to \Sigma_B, O, I, E, B)$，其中 $R_A$ 为原始仓库，$\Sigma_A \to \Sigma_B$ 为栈迁移方向，$O$ 为可观察接口，$I$ 为指令，$E$ 为离线环境，$B$ 为时间预算。智能体输出 $R_S$，需满足迁移条件 $\Sigma_B$ 构建产物且 $\Sigma_A$ 不存在，以及保持条件 $O(R_S) = O(R_A)$。

### 迁移审计（Migration Audit）

设计动机：固定行为测试无法验证迁移是否发生，智能体可能通过保留原始代码或包装层通过测试。迁移审计作为硬门槛，通过 5-8 个标准（如“Rust 是否为实现而非 FFI 包装”）否决未迁移提交。该阶段不依赖行为测试，而是检查代码结构与构建闭包，确保目标栈真正替代旧栈。

### 行为测试（Behavioural Tests）

设计动机：迁移审计仅验证“迁移发生”，无法保证行为保持。行为测试使用 130,118 个固定检查，记录自原始系统，要求所有检查通过。该阶段继承 SWE-bench 的执行接地验证，但针对迁移任务，测试覆盖范围更广，包括 API 响应、构建产物、安装树等。

### 智能体验证（Agentic Verification）

设计动机：固定测试套件可能遗漏隐藏行为差异，智能体可能通过测试但行为不一致。智能体验证引入 6 个独立编码智能体，每个运行 1 小时，生成差异测试。验证者仅能通过可执行反例（在原始系统通过、在迁移系统失败）否决提交。该阶段借鉴编译器验证中的差异测试思想，但由智能体驱动，覆盖固定测试未预见的行为差异。

## 实验评估

实验在 SWE Refactor Bench 上进行，包含 20 个全仓库迁移任务，覆盖语言、框架、平台、构建工具链四类技术债。对比 8 个前沿模型（Claude Opus 5、GPT-5.6 Sol、Kimi K3 等）在 26 种模型-努力配置下的 520 次运行。基线覆盖当前主流编码智能体，但未对比 SWE-agent 等特定架构，因任务性质不同（迁移 vs 修复），直接对比意义有限。

| 模型 | 最佳配置 | 行为通过率 (%) | 得分 (/100) | 成本 (USD/任务) |
|---|---|---|---|---|
| Claude Opus 5 | xhigh | 92.8 | 47.0 | 74.9 |
| GPT-5.6 Sol | max | 84.1 | 28.5 | 143.5 |
| Kimi K3 | max | 93.9 | 19.5 | 28.9 |
| Claude Sonnet 5 | max | 84.3 | 8.5 | 27.5 |

核心数字对比：Claude Opus 5 在 xhigh 配置下得分 47.0/100，行为通过率 92.8%，但仅 5 次运行通过全部三阶段。GPT-5.6 Sol 行为通过率 84.1%，得分 28.5，成本高达 143.5 USD/任务。Kimi K3 行为通过率最高（93.9%），但得分仅 19.5，表明行为保持与迁移完整性存在显著差距。

消融分析显示，迁移类别对性能影响显著：构建工具链重写得分 31.4，语言重写仅 5.6。智能体验证阶段中，Claude Opus 5 作为验证者时，否决率 55.7% 和 53.4%，远高于其他验证者（21.6%-26.1%），表明验证者模型能力对结果影响显著。此外，智能体未对同族模型提交表现出偏袒：Claude Opus 5 验证者否决同族提交 33.9%，其他提交 34.3%，差异源于提交质量而非偏见。

评估边界：指标完备性方面，三阶段协议覆盖迁移完整性、行为保持、隐藏差异，但未量化代码可维护性。评估协议局限：20 个任务规模较小，可能无法代表工业级迁移的多样性。可复现性：论文提供 Homepage 链接，但未公开代码与超参数，复现需依赖作者实现。

## 关联研究分析

从问题动机看，SWE Refactor Bench 与 SWE-bench 的核心差异在于任务本质：SWE-bench 评估 Bug 修复，依赖“红转绿”信号；SWE Refactor Bench 评估迁移，需验证“绿转绿”且栈替换。这一差异源于迁移任务的起始状态即为正确，导致固定测试无法区分未迁移与正确迁移。SWE-bench 的评估范式在迁移任务中失效，本文通过引入迁移审计解决此问题，但迁移审计的标准设计（如 5-8 个标准）是否足够覆盖所有迁移类型，论文未给出系统性分析。

从方法设计看，SWE Refactor Bench 的智能体验证阶段与 SWE-EVO 的长程任务设计有相似性，均关注长程依赖，但 SWE-EVO 聚焦功能演化，SWE Refactor Bench 聚焦栈替换。智能体验证阶段借鉴差异测试思想，但由智能体驱动，覆盖固定测试未预见的行为差异。这一设计是否可泛化为通用代码重构评估协议，论文未探索。此外，智能体验证阶段的计算成本（6 个智能体 × 1 小时）较高，是否在实际部署中可行，论文未讨论。

## 总结

SWE Refactor Bench 要解决的核心矛盾是现有评估范式无法区分“未迁移”与“正确迁移”，导致行为测试可能奖励未执行迁移的提交。本文抓住的切入点是识别“Blindness”，通过三阶段协议解耦迁移完整性与行为保持，其中迁移审计作为硬门槛，智能体验证覆盖隐藏差异。实验证明当前前沿模型仅 5.4% 的运行通过全部阶段，最佳模型得分 47.0/100，揭示了智能体在长程重构中的关键能力缺口。本文的边界在于任务集规模较小（20 个任务），且未量化代码可维护性。当任务集扩展到 100 个以上时，三阶段协议的评估成本与智能体性能是否呈现线性关系，论文未给出回答。
