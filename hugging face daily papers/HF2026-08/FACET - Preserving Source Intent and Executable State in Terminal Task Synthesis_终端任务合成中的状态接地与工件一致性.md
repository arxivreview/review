# HuggingFace最新推荐论文 ｜FACET: Preserving Source Intent and Executable State in Terminal Task Synthesis ｜终端任务合成中的状态接地与工件一致性

研究机构：OpenAI、Anthropic

论文原文见 [arXiv](https://arxiv.org/abs/2608.18580)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.18580)

> 终端代理训练依赖可执行监督，但现有合成管线常因多阶段生成导致指令、环境、解法与验证器相互脱节，产生不可解或误判任务。FACET 通过先构建并修复共享执行环境，再基于真实容器状态生成任务工件，解决了信息丢失与工件漂移问题。该方法在 1.2K 成功轨迹上微调 Qwen3.5 系列模型，在 Terminal-Bench 2.1 上实现跨尺度性能提升。其核心贡献在于确立了“执行状态接地”作为任务有效性的前提，但仅验证了数据效率，未评估合成任务对技能泛化性的直接增益。

## 研究背景

终端代理需在动态执行环境中操作文件、安装依赖并恢复故障，其成功不仅依赖文本生成，更取决于对变化执行状态的正确交互。这一特性使得终端任务成为评估代理能力的理想载体，但高质量训练数据的获取面临瓶颈：每个任务需耦合指令、初始化环境、参考解法与可执行验证器，若这些组件基于不一致假设生成，任务将变得不可解或评估失效。

现有合成管线多从领域规范或技能分类直接生成任务描述，虽能扩大数据规模，却难以保证工件间的一致性。指令可能引用环境中不存在的文件，解法可能假设错误的依赖关系，验证器可能测试无法产生的状态。这种“工件漂移”源于多阶段生成中信息的逐步压缩与隔离，导致最终任务仅保留源材料的部分结构。FACET 的切入点在于将“环境构建”前置为共享接地接口，确保所有工件基于同一真实状态生成，从而从根源上消除跨组件不一致。

## 核心方法

### 方法参照系

传统终端任务合成遵循“采样技能-生成描述-独立构建组件”的流程，各工件由不同模型调用独立生成，仅通过文本规范传递上下文。本文的关键差异在于引入“执行状态接地”范式：环境先于指令、解法与验证器构建并修复，其真实容器状态作为共享上下文暴露给后续生成器，将任务合成从“独立生成合理组件”转变为“构建连贯可执行整体”。

### 场景重构与参考对齐

为避免直接转换技能组合导致的信息压缩，FACET 首先通过代理式场景重构恢复跨技能依赖与中间状态。该过程将技能对 $p_c = (c, X_c)$ 转化为五维场景表示 $D_c = \{d_{goal}, d_{context}, d_{capability}, d_{state}, d_{io-tool}\}$，其中 $d_{state}$ 记录初始、中间与目标状态，$d_{io-tool}$ 指定文件、格式与依赖。设计动机在于解决直接生成任务时遗漏程序性约束的问题，通过显式建模状态转移保留源技能的丰富性。随后，基于场景描述 $C$ 生成解法参考 $R_S = f_S(C)$ 与指令参考 $R_I = f_I(C, R_S)$，一致性对齐模型检查两者共享相同初始状态与目标结果，确保每个指令需求均有解法支持，每个预期效果均可在最终状态观测。

### 执行状态接地与定向修复

环境构建阶段分离规划与资产实体化，代理生成环境清单并在受限基础镜像中实现文件、服务与依赖，允许网络访问以本地化公共资源。构建失败时，基于失败轨迹与重构规范 $Z$ 进行最多三次定向修复，防止为通过构建而移除任务需求。环境有效后，其真实状态 $e_0$ 作为共享接地接口，指令 $I$、解法 $S$ 与验证器 $V$ 依次生成，每个生成器均读取同一容器状态。解法执行产生最终状态 $e_T$，验证器基于 $I, R_S, e_0, e_T$ 生成，偏好行为与状态检查而非精确命令匹配。任务包 $T$ 通过四项验证：环境可构建、初始状态验证器不通过、解法可执行、最终状态验证器通过。失败时，约束路由器从执行轨迹识别责任工件，仅修复该组件，最多五次迭代。该机制解决了独立生成导致的工件漂移，通过共享状态确保指令、解法与验证器基于同一环境版本，减少跨组件不一致。

## 实验评估

实验在 Terminal-Bench 2.1 上进行，使用 Terminus-2 脚手架，每任务三次尝试报告平均通过率。基线覆盖 Qwen3.5 系列基础模型及 GPT-5.5、Claude Opus 4.7 等参考模型，但缺失 SkillOpt、Skill1 等技能进化方法基线，因本文聚焦数据合成而非技能优化。

| 模型 | 规模 | Terminal-Bench 2.1 |
| :--- | :--- | :--- |
| Qwen3.5-4B | 4B | 17.60 |
| FACET-Terminal-Qwen3.5-4B | 4B | 24.72 (+7.12) |
| Qwen3.5-9B | 9B | 27.34 |
| FACET-Terminal-Qwen3.5-9B | 9B | 35.58 (+8.24) |
| Qwen3.5-27B | 27B | 40.82 |
| FACET-Terminal-Qwen3.5-27B | 27B | 47.57 (+6.75) |

微调 1.2K 成功轨迹后，4B、9B、27B 模型分别提升 7.12、8.24、6.75 点，9B 绝对增益最大，4B 相对提升 40.5%。27B 模型达到 47.57，仅比 Qwen3.5-397B 的 49.06 低 1.49 点，表明小模型经数据高效监督可接近大模型性能。

任务分析显示，89.40% 的单项检查被满足，但仅 20.94% 的轨迹实现完全成功，54.00% 的失败轨迹仅有一两项验证器检查未通过。这表明失败多源于残余需求未满足而非完全无法解题，密集可执行验证使近成功轨迹可观测。FACET 数据集含 6,078 个验证任务，平均 22.77 个可执行测试，高于 Terminal-Lego 的 16.60 与 Nemotron-Terminal 的 6.18，但 P@1 为 27.00，低于其他数据集，反映更严格的完成标准。

评估边界方面，论文未报告置信区间，仅基于三次尝试平均；未提供代码与超参数细节，可复现性依赖附录；未评估合成任务对技能泛化性的影响，仅验证数据效率。

## 关联研究分析

从问题动机看，FACET 与 Trace2Skill 均从技能/轨迹提取知识，但 Trace2Skill 生成声明式 SOP 用于代理执行，FACET 生成可执行任务用于模型训练。差异根源在于任务特性：SOP 需保持架构无关以跨模型共享，任务需绑定具体环境状态以确保可验证性。FACET 的环境接地策略是否适用于生成通用 SOP，论文未探索。

从方法设计看，FACET 与 SkillOpt 均使用验证门控，但 SkillOpt 优化技能文档以冻结模型，FACET 优化任务工件以生成训练数据。SkillOpt 的验证集性能提升作为编辑接受标准，FACET 的执行验证作为任务有效性标准。差异源于目标不同：技能优化追求代理性能提升，任务合成追求数据质量保障。FACET 的定向修复机制是否可迁移至技能文档优化，以解决 SkillOpt 中全局重构导致的信息丢失问题，论文未给出回答。

## 总结

FACET 解决的核心矛盾是终端任务合成中多工件不一致导致的数据无效性。现有方法因独立生成组件而难以保证一致性，FACET 通过执行状态接地将环境构建前置，确保指令、解法与验证器基于同一真实状态生成。该方法在 1.2K 轨迹上微调 Qwen3.5 系列，27B 模型在 Terminal-Bench 2.1 上达到 47.57，较基础模型提升 6.75 点。其边界在于仅验证数据效率，未评估合成任务对技能泛化性的直接增益，且未与技能进化方法对比。当合成任务规模扩大至数万级时，环境接地策略的计算成本是否成为瓶颈，论文未给出回答。
