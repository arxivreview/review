# HuggingFace最新推荐论文 ｜SWE-Touch: Benchmarking Coding Agents When Users Touch the Code ｜共享工作区鲁棒性基准

研究机构：中国科学院、中国科学院大学

论文原文见 [arXiv](https://arxiv.org/abs/2608.02499)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.02499)

> 软件工程智能体在真实开发中需应对用户实时修改代码的共享工作区场景，但现有基准仅评估静态自主修复或消息交互，无法量化智能体对代码状态变化的感知与调和能力。SWE-Touch 通过注入与任务冲突的“反向编辑”（Counter-Edit），系统测试智能体在动态状态漂移下的表现。该框架揭示了自主高分模型在协作鲁棒性上的系统性缺陷，为动态交互评估提供了新维度，但其对“冲突”类型的单一限定是否足以代表真实协作复杂度，仍存疑。

## 研究背景

仓库级代码修复任务通常形式化为：给定代码库 $C$、问题描述 $I$ 和测试套件 $T$，智能体生成补丁 $P$ 使得 $T(P(C))$ 全部通过。这一执行接地验证范式确立了代码正确性由沙箱运行结果判定的标准，但隐含假设是工作区状态在智能体执行期间保持静态。当引入人类开发者时，这一假设失效：用户在智能体工作过程中可能直接修改代码，导致智能体观察到的状态与其内部信念产生漂移。这种状态漂移不同于消息反馈，它直接改变了后续动作的操作对象，要求智能体具备重新检查、调和冲突并验证受影响行为的能力。

现有交互式基准（如 SWE-Interact、HiL-Bench）仅通过消息传递模拟用户参与，忽略了代码编辑这一关键交互通道。对 SWE-chat 数据的分析显示，59.0% 的会话包含用户归因的仓库变更，表明代码编辑是普遍存在的交互形式。然而，缺乏基准评估智能体在用户修改共享代码库时的响应能力。SWE-Touch 的切入点在于：不改变智能体架构或训练方法，而是通过受控注入与任务冲突的代码编辑，暴露现有模型在状态感知与动态调和上的脆弱性，从而将评估维度从“静态解决率”扩展至“动态协作鲁棒性”。

## 核心方法

### 方法参照系

SWE-Touch 基于 SWE-bench Verified 的仓库级修复任务，沿用 Mini-SWE-Agent 接口与执行接地验证协议。其核心差异在于：标准流程中智能体在静态工作区上执行轨迹 $\tau = ((a_1, o_1), \dots, (a_T, o_T))$，而 SWE-Touch 在轨迹执行过程中动态注入用户补丁 $p_i^-$，改变后续动作观察到的仓库状态 $R_t$，迫使智能体从修改后的状态继续修复。

### 任务关键区域挖掘

**设计动机**：随机注入编辑可能落在无关代码上，无法有效测试智能体对任务相关状态变化的响应。需精确定位智能体实际依赖的代码区域，确保编辑具有任务相关性。

SWE-Touch 从三个不同模型家族（GPT 5.5、GLM 5.1、MiniMax M2.7）的完整轨迹中挖掘任务关键区域。对每个任务 $i$，定义区域 $r = (p, s, e)$，其中 $p$ 为文件路径，$[s, e]$ 为行区间。对轨迹集 $Z_i$，计算读区域核心 $C_i^{Read}$ 和编辑区域核心 $C_i^{Edit}$：

$$
C_i^X = \bigcap_{\tau \in Z_i, X(\tau) \neq \emptyset} L(X(\tau)), \quad X \in \{Read, Edit\}
$$

该公式取所有产生该类型证据的轨迹的区域交集，确保所选区域被多个独立智能体共同关注，从而反映任务的真实关键性。最终按“编辑证据优先于读证据、实现文件优先于测试文件”的优先级选择至多 8 个区域 $C_i$，作为后续编辑的锚点。

### 冲突编辑生成与注入

**设计动机**：编辑必须既“局部合理”（用户可能做出）又“任务冲突”（阻碍解决），才能测试智能体是否盲目接受用户代码还是主动调和。

User Patch Generator 是一个独立的 GPT 5.5 驱动智能体，基于关键区域 $C_i$、参考补丁 $p_i^\star$ 和测试命令生成候选编辑 $p_i^-$。每个候选编辑需通过三重验证：单独应用时 $V_i(R_i^-) = 0$（不解决任务）、与参考补丁组合时 $V_i(R_i^{-\star}) = 0$（不意外解决）、且编辑非平凡（非空且非注释）。注入时，当智能体动作 $a_t$ 访问的区域与编辑目标区域 $U_i$ 重叠（$L(Scope(a_t)) \cap L(U_i) \neq \emptyset$），运行时应用补丁并发送上下文消息：

$$
R'_{t_j} = \begin{cases} Apply(R_{t_j}, p_i^-), & \text{if patch applies uniquely and changes state} \\ R_{t_j}, & \text{otherwise} \end{cases}, \quad m_j = User(H_{t_j}, p_i^-, j)
$$

该机制确保编辑在智能体“到达”相关代码时生效，模拟真实场景中用户修改后智能体继续工作的状态。消息由独立模拟器生成，不接收参考补丁信息，避免泄露答案。

## 实验评估

实验在 SWE-bench Verified（200 任务）、SWE-Bench Pro（25 任务）和 DeepSWE（25 任务）上进行，评估 9 个前沿模型。基线覆盖闭源（Claude Opus 4.8、GPT 5.5）与开源（GLM 5.1、MiniMax M2.7 等）模型，但未对比特定 SWE 智能体框架（如 SWE-agent），而是测试模型原生能力。主结果显示，Counter-Edit 在 SWE-bench Verified 上使平均解决率下降 7.7 点，模型级损失范围为 1.3 至 16.5 点，并显著洗牌排名（如 MiniMax M2.7 从第 3 跌至第 8）。

| 模型 | Vanilla 解决率 (%) | Counter-Edit 解决率 (%) | ∆解决率 (点) | 保留率 (%) |
|---|---|---|---|---|
| Claude Opus 4.8 | 85.2 | 83.3 | -1.8 | 96.0 |
| GPT 5.5 | 80.5 | 79.2 | -1.3 | 95.0 |
| MiniMax M2.7 | 76.5 | 62.7 | -13.8 | 78.1 |
| Qwen3-Coder-480B | 57.2 | 40.7 | -16.5 | 60.8 |

消融实验揭示关键设计决策的影响：仅发送消息（无代码编辑）对解决率影响有限（-2.0 至 +3.0 点），而静默应用代码编辑（无消息）导致所有模型一致下降（-1.0 至 -9.5 点），表明智能体需从代码本身检测冲突，而非依赖消息提示。Co-Edit 对照实验（非冲突编辑）显示平均解决率仅变化 -0.1 点，证实性能下降源于语义冲突而非任意外部修改。长程基准上，SWE-Bench Pro 的损失随编辑频率 $K$ 从 1 增至 5 而加深（-3.9 至 -6.7 点），DeepSWE 则在 $K \geq 3$ 时趋于平稳，表明重复干扰在长程任务中累积效应因任务复杂度而异。

评估边界方面，SWE-Touch 仅测试“任务冲突”型编辑，未覆盖“任务辅助”或“中性”编辑；保留率指标未区分“正确调和”与“错误保留”，需结合轨迹分析（如 63.3% 失败运行保留冲突代码）才能诊断失败机制。可复现性上，论文提供代码与数据集，但 User Patch Generator 的提示工程细节仅在附录中给出，且编辑生成依赖 GPT 5.5，可能引入模型偏差。

## 关联研究分析

从问题动机看，SWE-Touch 与 SWE-Interact 同属交互式编码基准，但 SWE-Interact 仅通过消息传递模拟用户澄清或纠正，而 SWE-Touch 直接改变可执行代码状态。这一差异源于任务特性：消息反馈不改变操作对象，智能体仅需更新信念；代码编辑则改变操作对象，智能体必须重新检查状态。SWE-Interact 未探索代码编辑场景，可能因其假设用户影响限于语义层面，而 SWE-Touch 揭示了语义层面之外的状态层面挑战。

从方法设计看，SWE-Touch 与 SWE-agent 等智能体框架的关系是“测试床”而非“改进对象”。SWE-agent 通过 Agent-Computer Interface 实现静态工作区上的迭代交互，而 SWE-Touch 在其接口上注入动态干扰，暴露其在状态感知上的局限。SWE-agent 未设计状态变化检测机制，其 ACI 假设工作区状态由智能体自身维护，而 SWE-Touch 证明这一假设在共享工作区中失效。这种差异暗示，现有智能体架构的“静态状态假设”是其在动态协作中表现不佳的根本原因，而非提示工程或模型能力不足。

## 总结

SWE-Touch 要解决的核心矛盾是：静态基准的高解决率无法预测智能体在共享工作区中处理用户代码编辑的鲁棒性。其切入点在于：不改变智能体架构，而是通过受控注入任务冲突编辑，暴露现有模型在状态感知与动态调和上的系统性缺陷。该框架通过区域挖掘、冲突编辑生成与动态注入，实现了从静态评估到动态鲁棒性测试的扩展。实验证明，Counter-Edit 使平均解决率下降 7.7 点，且开源模型退化更显著（如 Qwen3-Coder-480B 损失 16.5 点），表明自主性能不等于协作鲁棒性。其边界在于：仅测试“冲突”型编辑，未覆盖其他编辑类型；保留率指标需结合轨迹分析才能诊断失败机制。当编辑类型从“冲突”扩展至“辅助”或“中性”时，智能体的响应策略是否会发生质变，论文未给出回答。
