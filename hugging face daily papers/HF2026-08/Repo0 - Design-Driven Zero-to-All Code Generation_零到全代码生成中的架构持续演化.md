作者：Silin Chen、Haoyi Teng、Xiaodong Gu 等 8 人

论文原文见 [arXiv](https://arxiv.org/abs/2608.19854)

> 零到全代码生成要求智能体仅凭自然语言需求构建完整软件仓库，现有方法普遍假设架构已预先设计好，导致生成代码在复杂仓库上出现组件边界模糊与依赖混乱。Repo0 指出仓库模块化属性无法在初始规划阶段完全确定，必须随开发过程动态演化。该框架通过维护需求与组件双层有向无环图（Dual-DAG），利用内聚与耦合指标驱动结构动作直至收敛，再引导测试驱动开发。这一范式在六个真实仓库上显著提升了功能覆盖与通过率，但其模块化阈值对仓库规模的敏感性尚未得到充分验证。

## 研究背景

当智能体尝试从零构建一个包含数十个模块的 Python 仓库时，它面临的首要困境并非代码语法错误，而是组件边界的模糊性。这种模糊性源于软件工程中“高内聚低耦合”原则与初始需求描述的粒度不匹配：需求文档通常描述功能目标，而非具体的类或包结构。若强行将功能目标映射为静态架构蓝图，往往导致某些组件职责过载（低内聚）或模块间依赖过度纠缠（高耦合），进而引发跨文件协调失败。

仓库级代码生成领域的主流路线长期依赖“一次性规划”范式。以 RPG 为代表的图规划方法在初始阶段生成固定的仓库结构，随后执行代码生成。然而，这种静态假设忽略了开发过程中的反馈机制：代码执行失败或测试未通过往往暴露出架构层面的缺陷，如冗余组件或职责重叠。现有方法将架构视为不可变的蓝图，无法在生成过程中修正这些结构性错误。Repo0 的切入点在于将仓库生成重构为持续结构演化问题，主张架构应在需求分解、组件构建与验证反馈中不断调整，直至满足模块化约束。

## 核心方法

### 方法参照系

本文问题属于仓库级代码生成，但区别于 SWE-bench 等“解决 Issue”任务，Repo0 面对的是无预定义架构的“零到全”场景。通用流程通常包含需求解析、架构规划、代码生成与验证四个阶段，关键差异在于 Repo0 将架构规划从一次性步骤扩展为贯穿生成过程的动态演化循环，而非固定蓝图。

### 双层有向无环图状态表示

Repo0 的核心创新在于引入 Dual-DAG 作为持久化架构状态，将需求层面的功能协调与实现层面的组件依赖解耦。传统方法常将需求与组件混在同一图中，导致功能逻辑与实现细节相互干扰。Repo0 定义架构状态 $S_t = (G^R_t, G^C_t, A_t)$，其中 $G^R_t = (V^R_t, E^R_t)$ 为需求级 DAG，边表示功能协调关系；$G^C_t = (V^C_t, E^C_t)$ 为组件级 DAG，边表示实现依赖；$A_t \subseteq V^R_t \times V^C_t$ 为多对多对齐关系，确保从需求到代码的可追溯性。这种解耦允许功能需求稳定后，组件结构仍可独立演化，避免了单一静态图在结构更新时的语义混淆。

### 模块化指标驱动的结构收敛

在初始架构构建后，Repo0 通过显式结构动作（add, split, merge, revise, save）动态调整组件边界。设计动机在于解决 LLM 自反思缺乏收敛判据的问题：无约束的结构调整易导致过度分解，降低下游正确性。Repo0 引入内聚阈值 $\gamma_{split} = 2/3$ 与耦合阈值 $\theta_{merge} = 0.7$，当组件内聚度低于阈值时触发 split，当耦合度高于阈值时触发 merge。演化过程持续直至无指标触发的重构需求，即达到结构收敛。该机制确保组件边界在代码生成前已优化，使后续生成基于更稳定的架构表示，而非依赖 LLM 的随机判断。

## 实验评估

实验在 RepoCraft 基准上进行，包含六个真实 Python 仓库，使用 GPT-5 mini 和 DeepSeek V3.2 作为骨干模型。基线包括 mini-SWE-agent、Paper2Code 和 RPG，其中 RPG 是最强的仓库规划基线。Repo0 在所有设置下均取得最高的功能覆盖率（Functionality Coverage）和通过率（Pass Rate）。

| 仓库 | 方法 | 功能覆盖率 (%) | 通过率 (%) | 投票率 (%) |
|---|---|---|---|---|
| requests | RPG | 90.91 | 31.51 | 95.89 |
| requests | Repo0 | 100.00 | 50.98 | 100.00 |
| statsmodels | RPG | 70.40 | 77.90 | 92.00 |
| statsmodels | Repo0 | 80.68 | 85.51 | 98.65 |
| django | RPG | 60.42 | 47.33 | 74.07 |
| django | Repo0 | 80.50 | 74.36 | 97.12 |

Repo0 相比 RPG 在功能覆盖率上提升 4.55–20.08 个百分点，通过率提升 7.61–29.74 个百分点。在 django 仓库上，通过率提升最为显著，表明结构演化在复杂仓库中收益更大。

消融实验显示，移除结构演化导致性能下降最大，在 requests 上通过率降低 8.47 个百分点，投票率降低 17.86 个百分点。移除需求上下文主要影响实现正确性，在 django 上通过率降低 10.00 个百分点。组件图排序对复杂仓库影响显著，在 statsmodels 上移除后通过率降低 30.00 个百分点。这些结果验证了 Dual-DAG 解耦、需求上下文与依赖感知生成顺序的必要性。

评估边界方面，Repo0 仅使用六个仓库，样本量较小，且模块化阈值 $\gamma_{split}$ 和 $\theta_{merge}$ 在 Commit0 Lite 上选定，未验证其对不同规模仓库的鲁棒性。代码已开源，但实验仅报告平均值，未提供置信区间，数值比较需谨慎。

## 关联研究分析

从问题动机看，Repo0 与 SWE-bench 系列方法存在根本差异。SWE-bench 假设仓库架构已存在，智能体仅需解决特定 Issue，而 Repo0 面对的是无架构约束的从零构建。这一差异源于任务特性：SWE-bench 的评估焦点是局部修复能力，而 Repo0 关注全局架构合理性。Repo0 的 Dual-DAG 设计正是为了在无先验架构的情况下建立可追溯的结构演化路径，而 SWE-bench 方法无需此机制。

从方法设计看，Repo0 与 RPG 共享图规划思路，但关键差异在于架构的静态性与动态性。RPG 在初始阶段生成固定图，而 Repo0 通过模块化指标驱动图演化。这一差异的根源在于对仓库模块化属性的理解：RPG 假设模块化可从需求中完全推导，而 Repo0 认为模块化是开发过程中涌现的属性。Repo0 的收敛机制解决了 RPG 在复杂仓库上因架构僵化导致的性能退化问题，但引入了额外的计算开销与阈值调参需求。

## 总结

Repo0 解决了零到全代码生成中架构静态假设导致的模块化失效问题，其切入点在于将架构视为动态演化过程而非固定蓝图。通过 Dual-DAG 解耦需求与组件依赖，并利用内聚与耦合指标驱动结构收敛，Repo0 在六个真实仓库上实现了功能覆盖率与通过率的双重提升，相比最强基线 RPG 在通过率上最高提升 29.74 个百分点。然而，实验仅覆盖六个仓库，且模块化阈值在特定数据集上选定，未验证其对更大规模或不同领域仓库的泛化能力。当仓库规模扩大至数百个组件时，结构演化循环的收敛速度与阈值敏感性是否会成为瓶颈，论文未给出回答。
