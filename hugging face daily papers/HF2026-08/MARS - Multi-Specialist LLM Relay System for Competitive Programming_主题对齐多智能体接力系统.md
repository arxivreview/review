# HuggingFace最新推荐论文 ｜MARS: Multi-Specialist LLM Relay System for Competitive Programming ｜主题对齐多智能体接力系统

作者：Andrei Mikhailov、Mikhail Burtsev、Alsu Sagirova

论文原文见 [arXiv](https://arxiv.org/abs/2608.23918)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.23918)

> 导读 竞赛编程任务要求模型同时具备算法理论深度与代码实现精度，而现有通用多智能体流水线将算法选择权完全委托给基础模型，导致在复杂逻辑上频繁失效。MARS 通过构建基于检索增强生成（RAG）的主题专家池，将“规划-编码-调试”的通用角色分工替换为“主题专家接力”，并在每一步引入公开测试执行作为确定性反馈信号。该方法在 CodeContests 测试集上以 Gemma 4 为骨干，实现了 0.624 的通过率，显著优于直接提示基线，但在绝对性能上仍低于重型搜索系统 CodeSIM。其价值在于以更低成本实现了专家知识注入，但测试反馈能否替代形式化验证的逻辑完备性保证，仍是核心存疑点。

## 研究背景

竞赛编程是评估大语言模型（LLM）代码生成能力的极端压力测试，其核心难点在于稀疏的正确性信号与深层算法内容的耦合。解决此类问题通常依赖检索增强生成（RAG）来补充模型缺失的领域知识，以及多智能体系统（MAS）来分解复杂任务。然而，传统 RAG 多检索代码片段或 API 文档，缺乏对算法理论结构的针对性；而现有 MAS 往往采用规划者、编码者、调试者等通用角色，假设基础模型具备广泛的算法专长，这种“内容无关”的流水线无法为特定算法问题提供必要的理论支撑。

该领域的主流路线存在两个瓶颈：一是知识注入的粒度不足，通用检索无法区分动态规划与图论等具体算法领域的细微差异；二是反馈机制的滞后性，多数系统仅在最终阶段进行验证，导致中间步骤的逻辑错误无法被及时纠正。MARS 的切入点在于将智能体专业化与任务主题结构对齐，每个智能体仅负责单一算法领域，并通过 RAG 锚定该领域的理论语料。同时，它将公开测试执行嵌入到接力的每一步，使当前专家在移交前即可看到代码的执行报告，从而在错误扩散前进行修复或决策移交。

## 核心方法

### 方法参照系

MARS 属于端到端验证代码生成的变体，其标准流程为“生成-验证-修复”。与依赖形式化证明器的传统验证范式不同，MARS 将“验证”具体化为沙箱内的公开测试执行，形成“生成-测试-修复/移交”闭环。其关键差异在于，验证信号不仅用于最终裁决，更作为多智能体接力过程中的实时路由与决策依据。

### 主题专家自评估与团队组建

在通用 MAS 中，团队构成通常由静态角色或通用能力描述决定。MARS 引入基于主题标签的自评估机制，每个专家智能体针对共享的 cp-algorithms 语料库进行自我评估，判断任务是否在其专长范围内。团队组建过程可形式化为：

$$
T = \text{TopK}(\{a_i \mid s_i = \text{assess}(a_i, \text{task}, \text{corpus}_i)\}, k=3)
$$

其中 $s_i$ 为专家 $a_i$ 的置信度评分，$T$ 为选出的最多 3 个专家组成的团队。这一设计解决了通用角色无法匹配特定算法需求的问题，确保只有具备相关理论知识的专家参与解题，避免了无关智能体的干扰。

### 带执行反馈的接力协议

在团队组建后，MARS 执行接力协议。每个回合包含两次 LLM 调用：首次生成代码草案，随后在沙箱中执行公开测试。第二次调用基于执行报告决定“保留”、“修复”或“移交”。修复候选仅当编译通过且不降低当前回合的通过测试数时才被接受，否则回滚至草案。这一确定性本地门控机制可表示为：

$$
\text{Accept}(r) = \mathbb{1}[\text{Compile}(r) \land \text{Pass}(r) \ge \text{Pass}(d)]
$$

其中 $r$ 为修复代码，$d$ 为当前草案。该设计将执行反馈转化为即时决策信号，使得专家能在错误累积前进行修正，显著提升了复杂任务的处理稳定性。

## 实验评估

| 方法 | 骨干模型 | 语言 | 通过率 | 平均耗时 (s) | 平均 Token 数 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Direct | Gemma 4 | C++17 | 0.48 ± 0.02 | 34.9 ± 49.6 | 1.8 ± 1.2 |
| Single-RAG | Gemma 4 | C++17 | 0.53 ± 0.01 | 59.8 ± 21.2 | 25.0 ± 3.2 |
| MARS | Gemma 4 | C++17 | 0.62 ± 0.01 | 244.3 ± 154.4 | 40.3 ± 8.1 |
| CodeSIM* | Gemma 4 | C++17 | 0.73 ± 0.01 | 817.5 ± 1358.5 | 32.2 ± 54.8 |
| MARS | Gemma 4 | Python | 0.622 ± 0.015 | 307.6 ± 215.7 | 42.9 ± 9.1 |
| PairCoder | Gemma 4 | Python | 0.705 ± 0.009 | 426.7 ± 451.7 | 27.6 ± 20.9 |

实验在 CodeContests 测试集的 165 个任务上进行，基线覆盖了直接提示、单智能体 RAG、并行集成、基础接力以及重型搜索系统 CodeSIM 和 PairCoder。MARS 在 Gemma 4 骨干下达到 0.624 的通过率，比直接提示高 14.4 个百分点，比单智能体 RAG 高 9.5 个百分点。尽管 CodeSIM 以 0.731 的通过率领先，但 MARS 的耗时仅为 CodeSIM 的 3.3 倍倒数，且在 Token 消耗的标准差上更小，表明其在效率与稳定性之间取得了更好的平衡。

消融实验显示，移除 RAG 导致通过率下降 2.0 个百分点，而通用智能体（无 RAG）比 MARS 低 0.9 个百分点但耗时增加 31%。这表明主题专家与 RAG 的结合不仅提升了准确性，还优化了计算效率。在难度分层上，MARS 在 Hard 任务上的通过率（0.40）是 Direct（0.18）的两倍以上，验证了专家知识注入在复杂逻辑推理中的关键作用。

评估边界方面，实验仅覆盖 C++17 和 Python 两种语言，且依赖 Codeforces 标签进行路由，未测试其他编程语言或无标签任务。代码已开源，但超参数设置（如温度 0.0，top-p 0.95）固定，未探索不同解码策略对结果的影响。此外，测试反馈仅基于公开示例，无法保证隐藏测试的通过，存在过拟合风险。

## 关联研究分析

从问题动机看，MARS 与 CodeSIM 均致力于解决竞赛编程中的算法逻辑错误，但 CodeSIM 依赖模拟驱动的规划与调试，通过多达 45 次迭代来修复错误，而 MARS 通过主题专家接力将错误修正前置。CodeSIM 的高通过率源于其重型搜索能力，但代价是极高的计算成本；MARS 则通过知识注入减少搜索空间，以较低成本实现接近的性能。这一差异源于任务特性：竞赛编程问题往往具有明确的算法主题，MARS 的主题对齐策略能更精准地定位错误根源，而 CodeSIM 的通用调试策略在缺乏主题引导时效率较低。

从方法设计看，MARS 与 PairCoder 同属多智能体系统，但 PairCoder 采用导航者-驾驶员架构进行多计划搜索，依赖专有嵌入模型进行计划聚类，而 MARS 采用开源组件并基于主题标签进行路由。PairCoder 在 Python 上达到 0.705 的通过率，高于 MARS 的 0.622，但其耗时是 MARS 的 1.4 倍。这一差异表明，多计划搜索在复杂任务上具有优势，但 MARS 的主题专家策略在特定算法领域可能更高效。查询侧增强在数据充足时是否仍有增益，论文未给出回答，但 MARS 的结果暗示，在算法理论明确的领域，知识注入比盲目搜索更具性价比。

## 总结

MARS 旨在解决通用多智能体系统在竞赛编程中因缺乏算法理论支撑而导致的逻辑错误问题。其切入点在于将智能体专业化与任务主题结构对齐，并通过 RAG 注入领域知识，同时利用公开测试执行作为实时反馈信号。该方法在 CodeContests 测试集上实现了 0.624 的通过率，比直接提示高 14.4 个百分点，且计算成本显著低于重型搜索系统。然而，其边界在于测试反馈仅基于公开示例，无法保证隐藏测试的通过，且未探索不同解码策略的影响。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
