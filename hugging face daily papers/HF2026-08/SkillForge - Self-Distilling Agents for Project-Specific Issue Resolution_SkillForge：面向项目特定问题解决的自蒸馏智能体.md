> 软件工程智能体在部署到具体仓库时面临冷启动困境，即缺乏该项目的特定知识导致重复踩坑。现有方法依赖历史轨迹或在线探索，前者受限于数据覆盖度，后者消耗高昂的测试时成本。SkillForge 通过重写核心功能代码合成项目特定问题，将解决轨迹蒸馏为双层技能库，实现知识的前置获取。该框架在 SWE-bench Verified 上显著超越基线，但技能库的静态性与模型依赖性限制了其跨模型迁移能力。

## 研究背景

当智能体面对一个陌生仓库时，它必须从零开始理解代码结构、API 契约及隐含的执行路径。这种缺乏项目特定知识的状态被称为冷启动问题，导致智能体在解决不同 Issue 时反复陷入相同的局部陷阱，如误用特定模块的接口或忽略边界条件。解决此问题的关键在于将项目知识从隐式的代码结构中显式提取，并转化为可检索、可注入的上下文信息。

主流路线分为历史驱动与在线探索两类。历史驱动方法如 SWE-Exp 和 EvoCoder 从过往 Issue 解决轨迹中蒸馏知识，但受限于历史数据的覆盖范围，未出现在历史轨迹中的长尾组件或 API 组合无法提供学习信号。在线方法如 Live-SWE-agent 和 SWE-Debate 在当前 Issue 解决过程中通过额外轨迹探索获取知识，虽然不依赖历史数据，但每个 Issue 都需支付高昂的 Token 和时间成本，且知识获取滞后于问题发生。SkillForge 的切入点在于打破这种被动获取模式，通过主动合成项目特定问题，在真实 Issue 到来之前完成知识积累，将知识获取从“反应式”转变为“预防式”。

## 核心方法

### 方法参照系

本文问题属于自我进化与优化路线，但偏离了标准的在线或历史驱动流程。通用流程通常依赖已有的执行轨迹（历史或当前）作为知识来源，而 SkillForge 的关键差异在于引入离线合成阶段，通过功能级代码重写生成自监督任务，将知识获取与真实 Issue 解决解耦。

### 功能级问题合成

传统合成方法如 SWE-Smith 采用单函数重写，仅暴露局部逻辑错误，难以捕捉跨组件依赖。SkillForge 在问题合成阶段引入覆盖率引导的功能级重写，针对测试覆盖的核心功能区域，选择多个协同工作的代码段进行重写。设仓库为 $R$，测试用例 $t$ 的执行轨迹为 $Tr(t)$，SkillForge 从 $Tr(t)$ 中提取关键代码段集合 $S = \{s_1, ..., s_k\}$，其中每个 $s_i$ 为连续代码片段。重写过程定义为：

$$
s_i' = \text{LLM}_{\text{rewrite}}(s_i, \text{ctx}(s_i), \text{desc}(t))
$$

其中 $\text{ctx}(s_i)$ 为上下文行，$\text{desc}(t)$ 为测试目标描述。该设计动机在于，单函数重写无法暴露 API 耦合与跨函数交互中的项目特定陷阱，而功能级重写迫使模型在缺乏原始实现的情况下重构协同逻辑，自然暴露其通用编码知识与仓库特定行为之间的差距。

### 双层技能蒸馏与即时注入

合成问题的解决轨迹 $T = \{(a_1, o_1), ..., (a_n, o_n)\}$ 被蒸馏为双层技能库。全局诊断技能集 $M_{\text{ext}}$ 捕获项目级知识，包括实体角色、推理策略及相关 API；局部干预技能集 $M_{\text{int}}$ 记录实体特定指导。对于候选实体 $\alpha \in E_{\text{cand}}$，技能记录定义为：

$$
\text{Skill}(\alpha) = \langle \text{purpose}(\alpha), \text{playbook}(\alpha), \text{related\_apis}(\alpha) \rangle
$$

其中 $\text{purpose}$ 标识实体在问题解决中的角色，$\text{playbook}$ 记录验证过的推理模式，$\text{related\_apis}$ 列出共现 API。该设计动机在于，单一粒度的知识表示无法同时满足宏观导航与微观调试需求，双层结构实现了从仓库级诊断到实体级干预的粒度覆盖。在下游解决过程中，$M_{\text{ext}}$ 作为初始上下文注入，$M_{\text{int}}$ 则在智能体访问对应实体时即时触发，确保知识注入与代码交互上下文对齐。

## 实验评估

| 方法 | 骨干模型 | SWE-bench Verified Pass@1 | SWE-bench Pro Pass@1 | 平均成本 |
| :--- | :--- | :--- | :--- | :--- |
| Mini-SWE-Agent | DeepSeek-V3.2 | 66.4% | 28.3% | $0.049 |
| Mini-SWE-Agent | GPT-5-mini | 55.0% | 47.6% | $0.031 |
| SWE-Exp | DeepSeek-V3.2 | 69.0% | 29.4% | $0.090 |
| Live-SWE-agent | DeepSeek-V3.2 | 67.0% | 32.4% | $0.050 |
| SkillForge | DeepSeek-V3.2 | 72.2% | 34.1% | $0.074 |
| SkillForge | GPT-5-mini | 60.6% | 51.7% | $0.066 |

实验在 SWE-bench Verified 和 Pro 上进行，基线覆盖历史驱动（SWE-Exp, EvoCoder, MemGovern）和在线方法（SAGE, SWE-Debate, Live-SWE-agent），但缺失纯监督微调基线。SkillForge 在 Verified 上以 72.2% 超越 Mini-SWE-Agent 5.8 个百分点，在 Pro 上以 34.1% 超越 5.8 个百分点，均达到统计显著性。与最强在线基线 Live-SWE-agent 相比，SkillForge 在 Pro 上高出 1.7 个百分点，且避免了其高昂的每问题探索成本。

| 消融变体 | DeepSeek-V3.2 Pass@1 | GPT-5-mini Pass@1 | 变化幅度 |
| :--- | :--- | :--- | :--- |
| 完整 SkillForge | 72.2% | 60.6% | - |
| 移除全局诊断技能 | 68.4% | 57.6% | -3.8% / -3.0% |
| 移除局部干预技能 | 67.8% | 57.2% | -4.4% / -3.4% |
| SkillForge w/ SWE-Smith | 68.0% | 56.4% | -4.2% / -4.2% |
| SkillForge w/ LLM Summary | 68.7% | 54.4% | -3.5% / -6.2% |

消融实验显示，移除局部干预技能导致最大性能下降（-4.4%），表明实体级即时指导比全局诊断知识更具边际价值。功能级重写（SkillForge）显著优于单函数重写（SWE-Smith 变体）和静态摘要（LLM Summary 变体），验证了跨组件交互知识的重要性。跨模型迁移实验揭示，DeepSeek-V3.2 使用自身蒸馏技能时达到 72.2%，使用 GPT-5-mini 技能时降至 65.2%，表明技能库具有模型特异性，无法跨骨干模型通用迁移。

评估协议采用 Pass@1 指标，未报告置信区间，且合成问题与真实 Issue 的分布差异未量化。代码已开源，超参数包括温度 0、动作预算 250 步、BM25 检索 top-5，但 GPU 资源需求未明确说明。

## 关联研究分析

从问题动机看，SkillForge 与 Live-SWE-agent 均解决项目知识获取问题，但前者采用离线合成，后者采用在线探索。Live-SWE-agent 在每个 Issue 解决过程中动态更新脚手架，知识获取与问题解决耦合，导致高延迟和高成本；SkillForge 将知识获取前置到离线阶段，通过合成问题暴露模型偏差，实现了知识获取的解耦。这一差异源于对“知识何时可用”的不同假设：Live-SWE-agent 假设知识必须在当前问题上下文中生成，而 SkillForge 假设项目知识可通过主动探测提前获取。

从方法设计看，SkillForge 与 SWE-Exp 均使用轨迹蒸馏，但知识来源不同。SWE-Exp 依赖历史 Issue 解决轨迹，知识覆盖受限于历史数据分布；SkillForge 依赖合成问题轨迹，通过功能级重写主动暴露未覆盖的 API 组合和边界条件。SWE-Exp 在 Matplotlib 和 Astropy 仓库上出现性能回归（-11.8% 和 -4.5%），而 SkillForge 在所有七个仓库上均无回归，表明合成问题在捕捉长尾项目知识方面更具鲁棒性。然而，SkillForge 的技能库是静态的，无法适应仓库代码的快速迭代，而 SWE-Exp 可通过持续积累历史轨迹实现知识更新，这一动态性差异在长期维护场景中可能成为关键瓶颈。

## 总结

SkillForge 针对软件工程智能体的冷启动问题，通过功能级代码重写合成项目特定问题，将解决轨迹蒸馏为双层技能库，实现了知识的前置获取。在 SWE-bench Verified 上，DeepSeek-V3.2 骨干模型达到 72.2% Pass@1，较基线提升 5.8 个百分点；在 SWE-bench Pro 上达到 34.1%，提升 5.8 个百分点。实验证实了功能级重写和双层技能结构的必要性，但跨模型迁移实验显示技能库具有模型特异性，DeepSeek-V3.2 使用 GPT-5-mini 蒸馏的技能时性能下降 7.0 个百分点。技能库的静态性与模型依赖性限制了其在快速迭代仓库和跨模型部署中的适用性。当仓库代码结构发生显著变更时，预蒸馏的技能库是否仍能保持有效性，论文未给出回答。
