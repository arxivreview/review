# HuggingFace最新推荐论文 ｜CalibForge: Adversarial Solver Calibration for Scaling Learnable Terminal Tasks ｜基于对抗性求解者校准的终端任务合成

研究机构：中国人民大学

论文原文见 [arXiv](https://arxiv.org/abs/2608.06352)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.06352)

> 导读 终端智能体训练依赖可执行且可验证的任务，但现有合成系统仅确保任务“可解”，无法区分任务对特定模型是“过易”还是“过难”，导致训练数据分布偏差。CalibForge 将任务构造转化为受限的对抗性作者-求解者循环，利用多模型求解行为作为构造时反馈，通过多求解者分歧与对比式强弱关系筛选出位于“可学习区间”的任务。该方法在 Terminal-Bench 2.0 上使 35B 模型达到 47.57% 准确率，较最强基线提升 6.75 个百分点，并验证了向软件工程基准的迁移能力。其价值在于将“可解性”升级为“相对可学习性”，但校准循环的终止条件对任务多样性的影响尚未充分量化。

## 研究背景

终端智能体在 Docker 沙箱中执行代码、调试依赖并验证状态，其训练数据必须同时满足环境可构建、指令无歧义及验证测试可执行。然而，仅通过结构检查与自求解验证的任务，可能因存在浅层捷径而过于简单，或因规格描述模糊而实际不可解，这种“可解但不可学”的数据质量缺陷直接限制了模型在长时程任务中的规划能力。

现有终端任务合成路线（如 TermiGen、CLI-Gym）主要依赖软件工件逆向或能力分类学生成任务，其验证流程止步于“存在至少一个解”。这一流程忽略了任务难度相对于特定求解者能力的分布位置，导致训练数据中混杂大量对目标模型无信息量的样本。CalibForge 的切入点在于引入“环境级行为校准”，将求解者的验证结果与交互轨迹作为构造时的反馈信号，通过多轮修订将任务难度锚定在指定求解者设置的能力区间内。

## 核心方法

### 方法参照系

标准终端任务合成流程包含任务规格生成、环境构建（Dockerfile/初始文件）、验证测试编写及结构验证。本文的关键差异在于，在结构验证通过后，不直接保留任务，而是引入一个由外部求解者驱动的校准循环，将任务保留标准从“可解”扩展为“相对可学习”。

### 对抗性求解者校准机制

校准循环的核心是定义保留准则 $C_\gamma$，该准则基于求解者的验证结果 $y_i \in \{0, 1\}$ 判断任务是否位于目标能力区间。对于多求解者校准，保留准则要求求解者池内出现分歧，即至少一个成功且至少一个失败：

$$ C_{multi}(y) = 1 \left[ 0 < \sum_{i=1}^{K} y_i < K \right] $$

此公式的物理含义是，全通过表明任务过易（存在浅层解），全失败表明任务过难或存在缺陷，唯有分歧状态才表明任务处于不同能力模型之间的“可学习区间”。对于对比式校准，保留准则强制指定强求解者 $y_s$ 与弱求解者 $y_w$ 满足特定关系：

$$ C_{con}(y_s, y_w) = 1 \left[ y_s = 1 \land y_w = 0 \right] $$

该设计动机在于，单一求解者的通过/失败信号无法区分“任务太难”与“任务有缺陷”，而强-弱对比能明确界定任务位于弱模型能力上限之上、强模型能力下限之下。当结果不满足 $C_\gamma$ 时，作者智能体利用反馈摘要与完整轨迹诊断失败原因（如捷径、规格模糊），修订任务后重新验证，直至满足准则或达到最大轮数 $R_{max}$。

## 实验评估

实验在 Terminal-Bench 2.0、SWE-bench Pro 和 Doc2Repo 上进行，基线包括 TermiGen、TerminalTraj 等开源合成集，所有数据源使用相同的 DeepSeek-V4-Pro 蒸馏协议与 SFT 训练配方，确保差异仅源于任务构造策略。

| 训练数据源 | TB2 Acc. (%) | SWE-Pro Resolved (%) | Doc2Repo Pass Rate (%) |
| :--- | :--- | :--- | :--- |
| Base Model (30B) | 7.87 ± 0.00 | 3.26 | 5.94 ± 0.88 |
| TermiGen | 23.60 ± 1.12 | 27.77 | 34.11 ± 2.64 |
| TerminalTraj | 26.22 ± 0.75 | 26.28 | 24.36 ± 0.96 |
| CalibForge (30B) | 32.58 ± 1.12 | 30.94 | 35.98 ± 1.82 |
| Base Model (35B) | 39.10 ± 1.09 | 41.29 | 44.92 ± 1.14 |
| CalibForge (35B) | 47.57 ± 0.99 | 44.32 | 48.77 ± 0.90 |

CalibForge-35B 在 TB2 上达到 47.57%，较最强基线 TerminalTraj 提升 6.75 个百分点；在 OOD 基准 SWE-bench Pro 上，30B 模型较基线提升 27.68 个百分点，表明终端任务训练能力向软件工程领域迁移。

| 校准变体 | SFT Trajectories | TB2 Acc. (%) | Δ vs. No Solver |
| :--- | :--- | :--- | :--- |
| No Solver | 2,466 | 22.47 | – |
| Single Solver | 2,493 | 24.34 | +1.87 |
| Multi Solver | 2,425 | 29.21 | +6.74 |
| Contrast Solver | 2,561 | 31.09 | +8.62 |

消融实验显示，多求解者校准产生的 SFT 轨迹数量（2,425）少于无求解者变体（2,466），但准确率提升 6.74 个百分点，证明增益源于难度定位而非轨迹数量增加。对比式校准中，初始仅 19% 候选满足强-弱关系，经修订后累计接受率达 96%，表明多数“不匹配”是可修正的规格缺陷而非任务固有缺陷。

评估协议使用 500 步限制与 1 小时超时，TB2 与 Doc2Repo 报告三次运行的均值±标准误，SWE-bench Pro 仅单次评估。代码与数据已开源，但校准循环的 $R_{max}$ 设置对最终任务集多样性的具体影响未单独消融，且未报告不同求解者组合对保留率的影响。

## 关联研究分析

从问题动机看，CalibForge 与 Reflexion 共享“轨迹反馈”机制，但 Reflexion 用于智能体自我修正以重试同一任务，而 CalibForge 将反馈用于修订任务本身以适配求解者能力。这一差异源于任务特性：Reflexion 假设任务固定且可解，而终端任务合成中任务规格本身可能是失败根源，因此必须允许作者智能体修改指令、环境或测试。

从方法设计看，CalibForge 与 TermiGen 等合成系统均依赖 Docker 环境构建，但 TermiGen 止步于“自求解通过”，CalibForge 引入外部异构求解者池。这种设计选择解决了单一模型自验证的盲区：自求解通过仅证明任务对作者模型可解，无法证明其对其他模型具有区分度。对比式校准中强-弱求解者的选择（DeepSeek-V4-Pro vs. Flash）隐含了能力层级的假设，若两个模型能力差距过小，可能导致“全通过”比例过高，校准效率下降，论文未探讨求解者能力差距对校准收敛速度的影响。

## 总结

CalibForge 解决的核心矛盾是终端任务“可解性”与“可学习性”的脱节，现有合成系统无法量化任务相对于特定模型的能力位置。通过引入对抗性求解者校准，利用多模型分歧与强-弱对比作为保留准则，CalibForge 将任务构造从静态验证转变为动态行为校准。实验证明，该策略在 Terminal-Bench 2.0 上使 35B 模型达到 47.57%，较最强基线提升 6.75 个百分点，并显著提升了向 SWE-bench Pro 的迁移能力。其边界在于，校准循环依赖求解者池的能力分布，若求解者能力过于接近或差距过大，可能影响“可学习区间”的界定精度。当求解者池从异构模型扩展至同一模型的不同推理努力设置时，对比式校准的保留率是否仍能达到 96%，论文未给出回答。
