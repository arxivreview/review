# HuggingFace最新推荐论文 ｜StarHarness: Evolving Harnesses with Stratified Search for Enterprise Environments ｜企业级智能体脚手架演化

研究机构：加拿大蒙特利尔大学

作者：Esakkivel Esakkiraja、Denis Akhiyarov、Vikas Yadav 等 7 人

论文原文见 [arXiv](https://arxiv.org/abs/2608.24804)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.24804)

> 企业级智能体在操作有状态后端时，常因工具接口不匹配或环境约定缺失导致任务失败，而现有方法或依赖模型微调、或仅优化提示词，难以在不改变权重的前提下解决此类环境特异性问题。StarHarness 提出了一种冻结模型权重、仅演化外部执行脚手架（Harness）的框架，通过分层任务划分与受控搜索，使智能体适配特定企业环境。该方法在三个企业基准上实现了 20–35 个百分点的性能提升，并验证了跨模型迁移能力，但其效果高度依赖基准任务的可复现性与护栏设计的严密性。

## 研究背景

企业智能体执行任务时，需通过工具接口（如 MCP providers）与有状态后端交互。工具 Schema 往往省略领域约定（如日期锚定、字段关联），导致模型在调用时产生无效参数或状态不一致。这种模型-环境不匹配（Model-Environment Mismatch）是长程任务失败的主因，而传统强化学习（RL）或微调方法需更新模型权重，成本高且难以快速适配新环境。

主流解决方案分为两类：提示优化（如 GEPA）仅调整指令，无法修复接口缺陷；多智能体框架（如 AutoGen）侧重协作，未解决单智能体与环境交互的鲁棒性。现有 Harness 演化方法（如 Meta-Harness）虽可编辑脚手架，但评估协议常混淆搜索性能与泛化能力，缺乏对过拟合的严格隔离。StarHarness 的切入点在于：将 Harness 演化视为外层优化问题，在冻结权重约束下，通过分层任务划分与隐藏选择集，实现环境特异性适配与跨模型泛化的解耦。

## 核心方法

### 方法参照系

本文问题可归入 Agent 框架优化范畴，但区别于多智能体协作或 RL 策略优化，其核心差异在于：优化对象是外部执行脚手架（Harness）而非模型权重，且评估协议强制隔离搜索集与泛化集，以验证环境适配的泛化性。

### 分层任务划分与隐藏选择集

传统 Harness 演化直接在全部任务上搜索，易过拟合特定任务。StarHarness 在演化前将基准任务 $N'$ 划分为三部分：搜索集 $D_{search}$（Proposer 可见）、选择集 $D_{select}$（Proposer 隐藏）与保留集 $D_{holdout}$（仅用于最终评估）。划分依据基线运行的三个描述符：失败模式（如 wrong_tool）、任务得分与验证器通过率。Proposer 仅访问 $D_{search}$ 的轨迹，候选补丁需在 $D_{select}$ 上严格提升平均分方可接受，公式为：

$$
h_{t+1} = h_t \oplus \Delta_t \quad \text{if} \quad J(h_t \oplus \Delta_t; D_{select}) > J(h_t; D_{select})
$$

该设计确保演化过程不接触泛化任务，直接量化环境适配的泛化能力，解决了传统方法中搜索性能与泛化能力混淆的问题。

### 受控搜索与护栏隔离

Proposer 基于当前 Harness 与搜索集轨迹生成候选补丁 $\Delta_t$，但受护栏约束：禁止硬编码任务 ID、访问验证器内容或映射特定答案。补丁通过范围检查、导入验证与单任务冒烟测试后，进入选择集评估。演化循环采用爬山法（Hill Climbing）或树搜索（Tree Search）：前者维护单一前沿，后者保留多个候选节点以探索替代假设。持久化记忆账本（Ledger）记录补丁、评估结果与失败状态，指导后续迭代。该机制将环境知识（如接口修复、操作约定）编码为可测试、可回滚的代码变更，而非嵌入模型权重，实现了环境特异性与模型通用性的解耦。

## 实验评估

实验在 ITBench SRE（40 任务）、EnterpriseOps-Gym ITSM（103 任务）与 AutomationBench Finance（100 任务）上进行，基线包括默认 Stirrup 框架、GEPA (Pi) 与 Codex。StarHarness 在三个基准上均显著优于 GEPA (Pi)，增益分别为 +13.8、+22.3 与 +17.6 个百分点，且推理成本降低 17%–53%。

| 基准 | 基线 (Stirrup) | StarHarness | 增益 (pp) |
| :--- | :--- | :--- | :--- |
| ITBench | 40.0% | 75.0% | +35.0 |
| EnterpriseOps-Gym | 23.3% | 43.7% | +20.4 |
| AutomationBench | 57.1% | 83.2% | +26.1 |

消融分析显示，树搜索阶段贡献了 8 个接受补丁，主要修复 Schema 与提示交互缺陷；爬山阶段贡献 4 个补丁，聚焦链接与接地修复。跨模型迁移实验中，同一 Harness 在 Qwen3.6-27B 与 GPT-5.4-mini 上均提升 17.5–46.3 个百分点，验证了环境适配的模型无关性。

评估边界方面，论文未报告置信区间，且 AutomationBench 分数因使用 Finance-100 子集与 Stirrup 框架，无法与原始基准直接比较。代码已开源，但演化预算 $B$ 与 Proposer 超参数未详细披露，可复现性依赖特定模型版本（GPT-5.4）。

## 关联研究分析

从问题动机看，StarHarness 与 Meta-Harness 同属 Harness 演化路线，但后者在 TerminalBench-2 上搜索与报告同一基准，混淆了发现与泛化；StarHarness 通过隐藏选择集与保留集分离，提供了更严格的泛化度量。这一差异源于企业环境对过拟合的敏感性：企业任务常含领域约定，过拟合特定任务会导致部署失败，而通用基准（如 TerminalBench）更关注能力上限。

从方法设计看，StarHarness 与 GEPA 等提示优化方法形成互补：GEPA 仅调整指令，无法修复接口缺陷；StarHarness 通过代码级补丁修复工具 Schema 与执行逻辑，解决了提示优化在状态依赖任务中的失效。然而，StarHarness 未探索多智能体场景，其单智能体假设在企业协作任务中可能受限，论文未提供证据支持其在多智能体环境中的适用性。

## 总结

StarHarness 解决了企业智能体在冻结权重约束下的环境适配问题，通过分层任务划分与受控搜索，将环境知识编码为可测试的代码变更。该方法在三个企业基准上实现 20–35 个百分点的性能提升，并验证了跨模型迁移能力，证明了 Harness 演化是模型扩展的实用补充。其边界在于：演化效果依赖基准任务的可复现性，且未探索多智能体场景或联合权重优化。当企业环境引入动态状态变化或跨域任务时，静态 Harness 演化的泛化能力是否仍可持续，论文未给出回答。
