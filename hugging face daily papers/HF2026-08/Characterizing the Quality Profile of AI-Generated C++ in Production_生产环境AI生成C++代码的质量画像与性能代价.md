> 导读 大语言模型（LLM）在软件开发中的大规模应用，使其生成的代码安全性成为软件工程领域的核心关切。早期研究聚焦于代码生成的功能正确性，但 Pearce 等人（2022）揭示的约 40% 漏洞率，将研究重心从“能否生成”转向“是否安全”。这一发现确立了安全作为独立评估维度的必要性，并引发了从静态模式匹配向动态执行与形式化验证的范式转移。随着代码代理（Code Agents）的兴起，问题边界进一步扩展至多轮交互中的安全退化、间接提示注入及供应链依赖风险。各技术路线在表示质量、适应效率与计算成本之间做出了不同取舍，由此形成当前涵盖评估、生成、修复及攻防对抗的多元方法格局。本综述梳理这条从功能正确到安全可信的因果演进链条，为读者提供一张领域认知地图。全文按问题演化与路线取舍组织，覆盖该领域从奠基到当前的主要工作。

## 研究背景

在大型企业的单仓库（Monorepo）开发环境中，代码质量评估面临归因难题：最终提交的代码往往混合了人类编写与AI生成的片段，且经过多轮审查与修改。传统的基于最终代码快照的静态分析无法区分缺陷的来源，导致无法量化AI工具对生产环境代码库的真实影响。为了解决这一归因问题，需要引入作者级溯源（Authoring-time Provenance）技术，即在代码编写阶段记录每个字节或行的生成来源，从而将后续的静态分析警告、审查摩擦及运行时计算成本精确映射到特定的作者类型上。

现有针对LLM生成代码的研究多局限于受控基准测试（如HumanEval、CodeLMSec）或独立的非功能性任务，这些研究假设作者身份由实验设计固定，忽略了生产环境中代码被编辑、混合及审查的生命周期。这种“生成前/中”的评估视角无法捕捉代码在落地后（Landed）的真实质量表现，例如静态警告在审查中是否被消除，或性能反模式在部署后是否转化为实际的计算开销。主流的安全对齐方法（如SafeCoder、SecCoderX）侧重于通过微调或强化学习在生成阶段内化安全知识，但缺乏对生成代码在长期维护与运行时效率维度的实证追踪。

本文的切入点在于将评估视角从“生成时刻”转移至“生产全生命周期”。通过利用字节级溯源数据，本文追踪AI生成的C++代码从编写、提交、审查到部署后的完整路径，旨在回答一个被现有基准测试忽略的问题：在真实的工业级工作流中，AI生成的C++代码是否呈现出可识别的质量缺陷画像，以及这些上游的代码属性如何转化为下游的审查成本与计算资源消耗。

## 核心方法

### 方法参照系

本文属于实证软件工程（Empirical SE）路线，而非生成模型优化路线。其核心流程是：基于作者溯源数据构建AI/人类代码队列，利用静态分析工具（SAST）提取代码属性，并关联下游的审查与计算指标。与知识库中SafeCoder等侧重“生成前安全对齐”的方法不同，本文关注“生成后”的生产环境表现，其关键差异在于引入了函数级的运行时计算资源归因，将静态代码特征与动态性能开销建立因果联系。

### 字节级溯源与队列构建

设计动机在于解决混合作者身份下的归因模糊性。传统方法难以区分AI生成代码中哪些部分被人类修改，导致质量评估失真。本文在编写阶段记录每个变更字节的来源，将内联补全、对话生成、代理编辑等工具信号聚合为单一的AI生成信号。对于每一行代码 $\ell$，定义其AI生成份额为：

$$ AIShare(\ell) = \frac{\text{AI-generated informative bytes in } \ell}{\text{Total informative bytes in } \ell} $$

静态分析警告继承其所在行或行范围的 $AIShare$，若警告跨越多行，则使用长度加权平均值。这种细粒度的溯源机制使得后续分析能够精确地将静态发现、审查评论及计算成本分配至AI或人类作者，避免了基于最终代码快照的粗糙归因。

### 分类法引导的静态画像与性能关联

设计动机在于将杂乱的静态分析警告转化为可解释的质量属性，并验证其与运行时性能的关联。本文构建了一个三级分类法（Taxonomy），将原始检查项映射为“效率与资源使用”、“正确性与安全”等质量属性。在效率维度，本文特别关注“接口与耦合负担”（Interface and Coupling Burden）和“拷贝与分配开销”（Copy and Allocation Overhead）。为了量化这些静态属性对运行时性能的影响，本文引入了CPU执行剖面分析，将总计算周期划分为命令式信号（如直接CPU处理、构造函数）和声明式信号（如调用优化库）。通过比较AI密集队列与人类队列在研究窗口首尾的CPU周期分布变化，计算相对偏移量：

$$ \text{Relative Shift} = \text{AI Shift (\%)} - \text{Human Shift (\%)} $$

这一指标揭示了静态代码模式（如显式循环 vs. 标准API调用）如何转化为动态的执行开销差异，从而将上游的代码风格问题与下游的计算成本建立量化联系。

## 实验评估

实验基于一家大型科技公司2025年4月至2026年4月的生产数据，涵盖352万次提交变更及1046万行C++代码。基线对比为人类编写的代码，未对比知识库中的SafeCoder或SecCoderX等安全生成方法，因为本文关注的是非功能性质量而非安全漏洞消除。在静态分析层面，AI生成代码在“接口与耦合负担”和“拷贝与分配开销”类别上表现出显著高于人类代码的比率，这两类问题占据了AI代码总正向绝对率差距的82.21%。在下游结果方面，AI生成代码的审查摩擦显著增加，阻塞线程（Blocking Threads）数量是人类的1.92倍，总评论数增加1.39倍。

| 指标类别 | 具体指标 | AI生成代码表现 | 人类代码表现 | 相对比率/差异 |
| :--- | :--- | :--- | :--- | :--- |
| 审查摩擦 | 阻塞线程 (Blocking Threads) | - | - | 1.92x |
| 审查摩擦 | 总评论数 (Total Comments) | - | - | 1.39x |
| 审查摩擦 | 合并时间 (Time to Merge) | - | - | 1.19x |
| 可靠性 | 构建失败率 (Build Failure Rate) | - | - | ~1.3x (Median) |
| 可靠性 | 回滚率 (Revert Rate) | - | - | ~0.9x (Median) |
| 计算性能 | CPU命令式信号偏移 | +0.88% | -2.57% | +3.46% |
| 计算性能 | 声明式库调用偏移 | -2.34% | -1.27% | -1.08% |

在干预实验（RQ4）中，本文测试了分类法知情反馈（Taxonomy-informed feedback）对50个C++函数的效果。结果显示，引入特定类别反馈（Stage 3）后，目标静态发现数量从基线的1.28降至1.12，减少了12.50%；同时，基准效率分数 $R_{eff}$ 从Stage 1的0.294提升至0.385，提升了31%。这表明上游识别出的质量属性画像可以作为有效的反馈信号，引导LLM生成更符合性能要求的代码。

评估边界方面，本文未报告置信区间，且数据来自单一企业内部，外部可复现性受限。指标完备性上，虽然覆盖了审查、可靠性及计算成本，但未直接量化安全漏洞率，因此无法评估安全与性能的联合权衡。代码与超参数未公开，干预实验的提示工程细节（Figure 5）虽在文中描述，但缺乏开源实现供第三方验证。

## 关联研究分析

从问题动机看，本文与SafeCoder、SecCoderX等安全对齐方法存在根本差异。SafeCoder通过安全指令微调提升代码的安全性，其评估指标为SecurePass@1，关注的是代码是否包含可利用漏洞。而本文关注的是代码的“非功能性质量”，即性能效率与维护成本，其核心发现是AI代码在“接口耦合”和“拷贝开销”上的系统性偏差。这种差异源于任务特性的不同：安全漏洞是二元的（有或无），而性能开销是连续的且依赖于运行时环境。本文揭示的“速度-质量权衡”与知识库中的“功能-安全权衡”共同指向多目标优化的必要性，但本文未验证安全机制的缺失是否导致了性能开销的增加，二者之间的因果联系尚不明确。

从方法设计看，本文与ContraFix等漏洞修复方法在“反馈干预”机制上有相似之处，但应用对象不同。ContraFix利用差分运行时证据修复漏洞，而本文利用静态分类法反馈优化性能反模式。本文的创新在于将生产环境的遥测数据（如CPU周期分布）转化为生成阶段的反馈信号，这是一种基于结果（Outcome-based）的反馈机制，而非基于规则（Rule-based）的静态检查。然而，本文的干预实验仅在50个函数上进行，且未对比使用RL（如SecCoderX）或RAG（如RESCUE）等更复杂的生成优化方法，因此无法判断分类法反馈在大规模场景下的泛化能力。

## 总结

本文要解决的核心矛盾是AI生成代码在提升开发速度的同时，其长期维护成本与运行时性能代价在生产环境中缺乏量化证据。本文抓住的切入点是字节级作者溯源与生产全生命周期追踪，这是受控基准测试无法实现的。通过构建静态分类法画像并关联下游计算指标，本文证明了AI生成的C++代码存在显著的“接口耦合”与“拷贝开销”缺陷，导致审查摩擦增加1.92倍及计算资源消耗增加5-8%。本文的边界在于其评估局限于单一企业的C++代码库，且干预实验规模较小，未涉及安全维度的联合优化。当支持集增大到大规模真实场景时，分类法反馈的边际收益是否递减，论文未给出回答。
