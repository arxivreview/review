> 多智能体代码生成长期受限于串行执行或无协调并行，导致单智能体“Stub-and-exit”失败模式频发且运行方差大。现有方案要么依赖顺序角色交接，要么简单合并独立样本，均无法在并发写入时保证语义一致性。AgentRoom通过CRDT底层合并与MCP工具层显式协调，将文件所有权分配从文本协商转为原子状态操作。该设计在匹配算力下显著降低失败率并提升质量，但其收益高度依赖N=2的特定配置，且缺乏与动态拓扑学习方法的横向对比。

## 研究背景

当多个LLM智能体同时编辑同一代码库时，字符级并发写入必然引发冲突。传统CRDT（Conflict-free Replicated Data Types）通过Lamport时间戳保证字节级强最终一致性（SEC），但SEC仅消除数据丢失，无法解决两个智能体在同一偏移量插入不兼容函数签名导致的编译错误。这一底层缺陷使得单纯的CRDT合并不足以支撑多智能体协作，必须引入上层协调机制来约束写入意图。

多智能体代码生成系统（Multi-Agent Coding Systems）的主流路线分为顺序流水线与无协调并行。顺序范式如ChatDev通过“需求-设计-实现”阶段交接，但每个阶段边界都放大了单智能体放弃任务的风险；无协调并行则让智能体独立工作后合并文件，但缺乏冲突检测导致覆盖错误。这两种模式均未解决并发场景下的状态同步与所有权分配问题，导致系统在复杂任务上表现不稳定。

AgentRoom的切入点在于将协调从提示词层下沉至运行时状态管理层。它不依赖智能体解析文本声明来分配文件，而是通过MCP（Model Context Protocol）工具接口提供原子性的文件Claim操作，从架构上杜绝了并发写入冲突。这一设计将多智能体协作的核心矛盾从“如何沟通”转化为“如何管理共享状态”，为并发代码生成提供了新的基础设施视角。

## 核心方法

### 方法参照系

本文问题可归类于通信拓扑优化中的动态资源分配，但关键差异在于操作粒度。通用MAS拓扑优化关注智能体间的连接权重或信息流路径，而AgentRoom聚焦于代码文件级的所有权分配。其核心差异在于：不学习拓扑结构，而是通过预定义的CRDT+MCP架构，在运行时动态管理文件独占权，以状态一致性替代策略优化。

### CRDT底层合并与字符级一致性

CRDT合并层解决了并发写入的数据丢失问题，但无法处理语义冲突。AgentRoom采用基于Yrs的pycrdt实现，在$\Delta_{crdt}=2s$窗口内对字符级编辑进行合并。其核心公式为碰撞概率估计：

$$p_{collision}(N, K_t) = 1 - \sum_{k=0}^{N-1} \left(1 - \frac{k}{K_t}\right)$$

该公式量化了$N$个智能体从$K_t$个候选文件中同时选中同一文件的概率。在$N=2, K_t \approx 5$的操作点，碰撞概率约为0.20。CRDT层保证字节级SEC，但语义冲突仍需上层协调解决，这构成了MCP工具层的设计动机。

### MCP工具层显式协调与互斥锁

MCP工具层通过原子操作抑制语义冲突，解决了CRDT层无法处理的意图冲突。`room_claim(path)`提供互斥锁，确保$\forall f, \forall t : |\{i : (f, i) \in C_t\}| \le 1$，即同一文件在同一时刻仅被一个智能体持有。该机制将碰撞概率降至零，且每次编辑开销为$O(1)$。协调协议包含六步工作流：读取状态、Claim文件、冲突重选、写入、轮询更新、广播完成。这一设计将协调从依赖智能体智能的文本解析，转变为依赖系统保证的状态管理，从根本上消除了“Stub-and-exit”失败模式的传播路径。

## 实验评估

| 条件 | 均值 | n | σ | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| ChatDev-style (sequential) | 0.333 | 6 | 0.197 | 顺序范式基线 |
| Parallel merge | 0.456 | 12 | 0.178 | 无协调并发 |
| Solo | 0.544 | 32 | 0.222 | 单智能体基线 |
| Shared only | 0.575 | 11 | 0.155 | CRDT无MCP |
| Shared + collab, noMCP | 0.588 | 7 | 0.188 | 提示词无MCP |
| AgentRoom | 0.669 | 14 | 0.140 | 完整协调 |

实验设置基于T4金融账本任务，对比了顺序、无协调并发、单智能体及AgentRoom变体。基线覆盖ChatDev顺序范式与Parallel-merge无协调并发，但缺失GPTSwarm等动态拓扑学习方法的对比。AgentRoom在LLM-judge复合得分上领先Parallel-merge 0.213（Welch t=3.35, p=0.003），且方差从0.222降至0.140。

消融实验显示，协调机制的贡献大于并发本身。Parallel-merge（0.456）低于Solo（0.544），表明无协调并发因文件覆盖错误而劣化性能。Shared-only（0.575）介于两者之间，证明CRDT底层合并有基础收益，但MCP协调层（0.669）带来显著增量。N=2时质量峰值，N=3、N=4时质量分别降至0.553、0.489，广播流量超线性增长，暗示单通道协调存在瓶颈。

评估边界受限于Express.js/TypeScript任务，缺乏跨语言泛化验证。可复现性受限于专有模型CLI版本锁定，未提供代码开源。LLM-judge与regex/AST评分器相关性为0.67-0.79，存在评分器偏差风险。

## 关联研究分析

从问题动机看，AgentRoom与GPTSwarm均解决动态拓扑问题，但路径截然不同。GPTSwarm通过强化学习优化智能体间连接权重，属于策略优化路线；AgentRoom通过CRDT+MCP管理文件所有权，属于状态管理路线。这一差异源于任务特性：代码生成具有明确的文件粒度与编译约束，适合状态管理；而通用推理任务缺乏此类结构化约束，更适合策略优化。AgentRoom未对比GPTSwarm，可能因其架构差异过大，无法在相同算力下公平比较。

从方法设计看，AgentRoom与CodeCRDT同属CRDT应用，但协调机制相反。CodeCRDT采用隐式协调，预分配Outliner与Implementer角色；AgentRoom采用显式协调，通过MCP工具动态分配文件所有权。CodeCRDT的隐式协调在21%任务中加速，39%任务中减速，表明角色预分配缺乏灵活性。AgentRoom的显式协调通过原子Claim操作消除了角色冲突，但引入了MCP工具调用开销。这一设计选择反映了代码生成任务对确定性的要求高于通用协作任务。

## 总结

AgentRoom解决的核心矛盾是并发代码生成中CRDT字节级一致性与语义冲突的脱节。其切入点在于将协调从提示词层下沉至运行时状态管理层，通过MCP工具提供原子文件Claim操作，从架构上杜绝并发写入冲突。实验证明，在匹配算力下，AgentRoom将单智能体放弃率从31%降至5%（CMH OR=13.7），且T4任务质量提升0.125。其边界在于N=2时质量峰值，N>3时性能下降，且缺乏与动态拓扑学习方法的横向对比。当智能体数量增加至4时，广播流量超线性增长导致质量下降，这一现象是否源于单通道协调瓶颈而非协调机制本身，论文未给出回答。
