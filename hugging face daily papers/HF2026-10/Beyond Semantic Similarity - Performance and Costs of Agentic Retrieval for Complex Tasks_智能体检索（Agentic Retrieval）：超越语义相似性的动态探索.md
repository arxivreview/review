> 导读 现代信息检索正从精确查询转向抽象任务描述，传统密集检索仅依赖表面语义相似性，无法处理需要推理与迭代探索的复杂场景。本文提出 NeMo Retriever Agent，通过 ReAct 循环让 LLM 动态调用密集检索器，以推理能力弥补嵌入模型的局限。该方法在 ViDoRe v3 和 BRIGHT 上显著优于标准检索，但单查询耗时达 107.4 秒，暴露了推理时优化的效率瓶颈。其价值在于验证了检索环节智能化的可行性，但高成本限制了大规模部署。

## 研究背景

当智能体面对“根据数学题描述检索相关定理”这类任务时，查询与文档间缺乏表面语义重叠，传统密集检索基于余弦相似度的匹配机制失效。这种失效源于检索任务性质的转变：从静态的查询-文档匹配，演变为需要中间推理步骤的动态信息探索过程。密集检索器虽能高效处理百万级语料，但缺乏推理能力；LLM 具备推理与世界知识，却无法直接遍历海量文档。

现有方案多采用静态管道，如查询重写（Query Rewriting），由 LLM 一次性改写查询后送入检索器。这种设计限制了智能体的自主性，LLM 无法基于检索器返回的新信息调整后续策略。Search-o1 等工作尝试引入强化学习训练搜索智能体，但训练成本高且依赖稀疏奖励。本文切入点在于摒弃训练阶段优化，转而利用 LLM 原生推理能力在推理时（Inference-time）动态规划检索策略，将检索任务本身转化为智能体任务。

## 核心方法

### 方法参照系

标准密集检索流程为：查询嵌入 → 余弦相似度计算 → Top-k 文档返回。本文问题与该流程的关键差异在于：查询意图抽象且复杂，需多次迭代探索，且检索器能力有限，需 LLM 介入进行策略规划与结果筛选。

### ReAct 循环与工具定义

设计动机：静态查询重写无法应对检索过程中发现的新信息，导致后续查询盲目。本文在 ReAct 框架下定义三个工具：Retrieve、Think 与 Final_Results。Retrieve 工具接收查询 $q$ 与整数 $k$，调用密集检索器返回 Top-k 文档及其 ID；Think 工具允许 LLM 生成推理 token 以规划策略，不改变环境状态；Final_Results 要求 LLM 输出 $k$ 个文档 ID 及选择理由，若数量错误则返回错误提示。该循环使 LLM 能动态决定何时检索、检索什么，解决了静态管道中 LLM 与检索器信息隔离的问题。

$$
\text{Score}(d) = \cos(\mathbf{e}_q, \mathbf{e}_d)
$$

此公式表示密集检索器基于查询嵌入 $\mathbf{e}_q$ 与文档嵌入 $\mathbf{e}_d$ 的余弦相似度计算文档得分，是 Retrieve 工具的底层机制。

### 失败回退与基础设施优化

设计动机：智能体可能因上下文溢出或内容违规而失败，导致无结果返回；标准 MCP 协议在高频工具调用下产生显著延迟。本文引入 Reciprocal Rank Fusion (RRF) 作为回退机制，当智能体失败时，合并所有成功检索尝试的排名列表，计算最终得分。同时，将 MCP 服务器替换为进程内线程安全单例检索器，消除网络往返延迟，提升 GPU 利用率。

$$
\text{RRF}(d) = \sum_{i \in R} \frac{1}{k + \text{rank}_i(d)}
$$

此公式表示 RRF 通过累加各排名列表中文档 $d$ 的倒数排名（$k$ 为常数，通常取 60）来融合多路检索结果，确保即使智能体中途失败，仍能基于已获取信息返回合理结果。

## 实验评估

实验在 ViDoRe v3（企业文档检索）与 BRIGHT（推理密集型检索）上进行，基线包括标准密集检索与 INF-X-Retriever。本文方法在 ViDoRe v3 上取得 69.22 nDCG@10，BRIGHT 上取得 50.90 nDCG@10，均优于同嵌入模型的标准检索基线。

| 方法 | LLM | 嵌入模型 | ViDoRe v3 nDCG@10 | BRIGHT nDCG@10 |
| :--- | :--- | :--- | :--- | :--- |
| NeMo Retriever Agent | Opus 4.5 | colembed-vl-8b-v2 | 69.22 | 50.79 |
| NeMo Retriever Agent | gpt-oss-120b | colembed-vl-8b-v2 | 66.38 | 41.27 |
| Standard Retrieval | - | colembed-vl-8b-v2 | 64.36 | - |
| Standard Retrieval | - | llama-nv-reasoning-3b | - | 38.28 |

Opus 4.5 比 gpt-oss-120b 平均高 6.2 点，在 BRIGHT 上差距达 9.5 点，主要因 Opus 4.5 平均每次查询调用 9.2 次检索，而 gpt-oss-120b 仅 2.4 次，表明探索深度影响性能。智能体将不同能力嵌入模型的性能差距缩小 57%，部分补偿了嵌入模型局限。

| 模型 | 平均延迟 (sec.) | 输入 Tokens | 输出 Tokens |
| :--- | :--- | :--- | :--- |
| Opus 4.5 | 136.3 | 759.4k | 6.2k |
| gpt-oss-120b | 78.6 | 768.9k | 5.4k |

智能体检索平均耗时 107.45 秒，远超标准检索的 0.67 秒，且消耗大量 token。这一成本结构表明，当前智能体检索的效率瓶颈在于 LLM 推理开销，而非检索器本身。

评估边界方面，论文未报告置信区间，且未与 GrepSeek 等命令行交互方法对比。代码已开源，但超参数细节有限，可复现性依赖特定 LLM 版本。

## 关联研究分析

从方法设计看，本文与 CoSearch 均涉及 LLM 与检索器协同，但 CoSearch 通过联合优化训练检索器与智能体，而本文固定检索器，仅优化智能体策略。这一差异源于任务特性：CoSearch 针对特定领域优化，而本文追求跨域通用性，固定检索器避免了领域适配成本。然而，本文未探索检索器与智能体联合训练是否能在保持通用性的同时进一步提升性能，这一盲区可能限制了其在特定领域的上限。

从问题动机看，GrepSeek 同样挑战传统向量检索，但采用命令行工具直接操作语料库，而本文保留密集检索器作为底层工具。GrepSeek 的优势在于非结构化语料上的灵活性，本文的优势在于利用嵌入模型的高效索引能力。两者差异反映了检索接口设计的不同取舍：GrepSeek 牺牲索引效率换取交互灵活性，本文牺牲交互灵活性换取检索效率。本文未评估在何种语料特性下，密集检索器优于直接文本操作，这一边界条件未明确。

## 总结

本文核心矛盾是密集检索的语义局限与复杂任务推理需求之间的冲突。切入点在于利用 LLM 原生推理能力在推理时动态规划检索策略，避免了强化学习训练的高成本。方法通过 ReAct 循环与 RRF 回退机制，实现了检索过程的智能化。实验证明其在 ViDoRe v3 上取得 69.22 nDCG@10，比标准检索高 8.7 点，但单查询耗时 107.45 秒。边界在于高推理成本限制了大规模部署，且未探索检索器与智能体联合优化的潜力。当语料规模扩大至十亿级文档时，密集检索器的索引效率优势是否足以抵消 LLM 推理的延迟开销，论文未给出回答。
