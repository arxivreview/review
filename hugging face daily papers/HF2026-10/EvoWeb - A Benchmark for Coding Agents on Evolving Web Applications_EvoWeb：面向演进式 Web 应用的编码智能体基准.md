> 导读 编码智能体在真实开发场景中需通过多轮请求持续扩展应用，但现有基准多评估单轮生成或独立任务，无法衡量跨请求的功能集成与回归稳定性。EvoWeb 通过构建基于真实产品特征的依赖有向无环图（DAG），强制智能体在持久化代码库上执行累积修改，并引入容差阈值积分指标量化轨迹鲁棒性。该基准揭示了跨请求集成是当前模型的核心瓶颈，且运行时错误随应用演进显著增加。EvoWeb 填补了“构建型”Web 智能体在长程迭代评估上的空白，但其依赖显式 DAG 结构，可能低估了真实开发中隐式架构耦合带来的挑战。

## 研究背景

当编码智能体面对用户“添加购物车功能”的后续请求时，其操作对象不再是空白仓库，而是前序请求生成的包含状态管理、路由配置与组件结构的复杂代码库。这种从“从零生成”到“增量演进”的转变，要求智能体不仅实现新功能，还需复用既有接口并避免破坏已验证行为。然而，LLM 的上下文窗口限制与代码库的指数级增长，使得智能体在多步迭代中极易出现状态漂移——即新代码与旧代码在数据流或组件引用上产生断裂，导致应用崩溃或功能失效。

现有评估体系难以捕捉这一失效模式。WebGen-Bench 等基准聚焦单轮请求的端到端生成，SWE-bench 等软件工程基准则侧重单点 Bug 修复，二者均未建模“功能演进”这一核心属性。即便 EvoCode-Bench 等研究引入了多轮交互，其任务序列仍多为线性或独立，缺乏对功能间显式依赖关系的结构化约束。这导致模型可能在独立子任务上表现优异，却在需要组合多个早期功能的集成任务上系统性失败。EvoWeb 正是针对这一评估盲区，将 Web 应用生成基准与长程软件工程范式结合，确立了“持久化状态+依赖感知+容差评估”的新坐标。

## 核心方法

### 方法参照系

EvoWeb 将编码智能体评估置于“多轮交互式软件工程”框架下，但区别于 SWE-bench 的“修复导向”与 WebGen-Bench 的“生成导向”，其核心差异在于任务序列的**累积依赖性**与**回归敏感性**。标准流程中，智能体接收自然语言指令并修改代码，评估仅关注最终产物是否满足当前指令；EvoWeb 则要求评估覆盖“新功能实现”“跨请求集成”与“旧功能保持”三个维度，且任务序列由显式依赖图驱动，迫使智能体在每一步都处理历史状态的继承与冲突。

### 依赖 DAG 构建与请求生成

传统基准的任务序列往往隐含或忽略功能间的逻辑耦合，导致评估无法区分“独立实现”与“集成实现”的难度差异。EvoWeb 在数据构建阶段引入依赖有向无环图（Directed Acyclic Graph, DAG）作为任务序列的骨架。对于每个种子应用，系统检索两个真实网站的扩展特征，由生成模型构建 DAG，其中节点对应请求，边 $i \to j$ 表示请求 $j$ 的实现必须依赖请求 $i$ 引入的功能。该 DAG 需满足深度 $\ge 3$ 且至少三个后续请求依赖早期功能，以确保长程依赖的存在。

$$
\mathcal{G} = (\mathcal{V}, \mathcal{E}), \quad \text{s.t.} \quad \max_{v \in \mathcal{V}} \text{depth}(v) \ge 3, \quad |\{v \in \mathcal{V} : \text{in-degree}(v) > 0\}| \ge 3
$$

该公式定义了 DAG 的拓扑约束，物理含义是强制任务序列包含足够深度的依赖链与足够广度的集成点。这一设计解决了此前基准中“任务独立性假设”导致的评估失真，使集成难度成为可量化、可追踪的变量，而非模型能力的隐性副产品。

### 容差阈值积分评估指标

在顺序执行任务时，单一成功率指标无法反映用户在不同失败容忍度下的真实体验：严格用户可能在首次失败后放弃，宽松用户则可能容忍中间错误。EvoWeb 引入容差阈值 $t \in [0,1]$ 建模用户行为，定义门控分数 $g_r(t)$ 指示请求 $r$ 是否被“到达”（即前序请求均满足阈值），进而计算交付功能 $Q(t)$ 与请求存活 $S(t)$。

$$
Q(t) = \frac{1}{R} \sum_{r=1}^{R} g_r(t) a_r, \quad S(t) = \sum_{r=1}^{R} g_r(t) \mathbb{I}[a_r \ge t]
$$

其中 $a_r$ 为请求 $r$ 的测试准确率。最终指标 Grade 与 Survival 通过对 $t$ 积分获得：

$$
\text{Grade} = \int_0^1 Q(t) dt, \quad \text{Survival} = \int_0^1 S(t) dt
$$

该积分设计将离散的成功/失败二元判断转化为连续的轨迹鲁棒性度量，避免了固定停止规则（如 Fail-stop 或 Independent）带来的评估偏差。它使评估结果能够区分“偶尔失败但可恢复”与“持续劣化”两种截然不同的智能体行为模式，为长程任务评估提供了更贴合实际部署的量化标准。

## 实验评估

EvoWeb 在 32 个应用、320 个累积请求上评估了 14 个前沿模型，采用 OpenHands 脚手架与 WebVoyager 浏览器代理进行端到端验证。基线覆盖包括 Fable 5、Kimi K3、GPT 5.6 Sol 等闭源模型及 Qwen3.5、DeepSeek V4 等开源模型，但未包含专用 Web Agent 架构（如 ReAct 变体），因任务本质为代码生成而非网页操作。主实验显示，Fable 5 以 Grade 0.694 领先，但最强模型也仅存活 7.32/10 个请求，表明长程集成仍是普遍瓶颈。

| Model | Grade ↑ | Survival ↑ | Turns / request ↓ | Runtime Err. % ↓ |
| :--- | :--- | :--- | :--- | :--- |
| Fable 5 | 0.694 | 7.32 | 4.7 | 0.5 |
| Kimi K3 | 0.684 | 7.31 | 7.6 | 0.9 |
| GPT 5.6 Sol | 0.622 | 6.72 | 9.0 | 3.6 |
| Sonnet 4.6 | 0.607 | 6.55 | 10.1 | 0.8 |
| Haiku 4.5 | 0.377 | 4.43 | 13.1 | 1.6 |

消融分析揭示了三个关键发现：其一，集成测试（Integration）得分始终低于功能测试（Functional）与回归测试（Backward），平均 Grade 分别为 0.510、0.550 与 0.580，证实跨请求组合是核心难点；其二，请求在 DAG 中的深度与入度与准确率呈负相关，依赖越复杂失败率越高；其三，运行时错误率与 Grade 的相关性（Spearman $\rho = -0.72$）远高于构建错误（$\rho = -0.52$），且随请求序号递增，表明模型更擅长维持可构建性而非可执行性。

评估协议存在两点局限：一是依赖 DAG 为人工/LLM 构建，可能无法完全捕捉真实代码库中的隐式耦合；二是 WebVoyager 评估器虽经人工审计（86-94% 一致性），但仍属 LLM-as-a-Judge 范式，对复杂交互的判定可能存在系统性偏差。此外，论文未报告计算成本与推理延迟，限制了实际部署参考。

## 关联研究分析

从问题动机看，EvoWeb 与 SWE-bench 均关注代码库的持久化状态，但 SWE-bench 的“修复”范式假设代码库已存在且目标明确，智能体只需定位并修改特定片段；EvoWeb 的“演进”范式则要求智能体在无显式 Bug 报告的情况下，主动维护架构一致性并扩展功能。这一差异导致 SWE-bench 上的高分模型在 EvoWeb 上未必领先，因为后者额外惩罚了“能修复但会破坏”的行为模式。EvoWeb 未对比 SWE-bench 专用微调模型，无法判断领域适配是否足以弥补通用模型在集成能力上的不足。

从评估框架看，EvoWeb 与 WebGen-Bench 共享浏览器验证协议，但 WebGen-Bench 的评估是“快照式”的，仅检查最终应用是否满足单轮需求；EvoWeb 的评估是“轨迹式”的，通过回归测试与容差积分捕捉中间状态的质量衰减。这一设计使 EvoWeb 能够识别 WebGen-Bench 无法发现的“隐性回归”——即新功能实现正确但旧功能被意外破坏的情况。然而，EvoWeb 的回归测试仅覆盖 1/5 的测试用例，对回归问题的检测粒度仍显粗糙，是否足以代表完整回归测试套件的效果，论文未给出回答。

## 总结

EvoWeb 针对编码智能体在持久化 Web 应用开发中“能生成但难集成”的核心矛盾，通过依赖 DAG 与容差积分指标，将评估从单轮功能正确性扩展至长程轨迹鲁棒性。其实验证明，即便最强模型 Grade 也仅 0.694，且集成测试得分系统性低于功能测试，运行时错误随应用演进持续累积。该基准的边界在于其依赖显式 DAG 结构建模功能依赖，而真实开发中的耦合往往隐式且动态变化，DAG 是否足以代表真实架构复杂度尚存疑问。当依赖关系从显式 DAG 转向隐式代码耦合时，当前评估框架能否保持区分度，仍有待验证。
