# HuggingFace最新推荐论文 ｜CheckerBench: Can Long-Horizon Agents Synthesize Static-Analysis Checkers? ｜长程代理静态分析检查器合成基准

作者：Hang He、Li Wang、Hao Chen 等 12 人

论文原文见 [arXiv](https://arxiv.org/abs/2610.07557)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2610.07557)

> 静态分析检查器依赖专家手工编码缺陷模式，而大语言模型（LLM）直接处理代码片段时受限于推理成本与上下文缺失，难以独立完成从漏洞规范到可复用规则的转化。现有仓库级基准聚焦补丁生成或漏洞检测，缺乏对“检查器复用性”与“分析器集成”的评估维度。本文构建 CheckerBench，通过 300 个源自真实 CVE 的任务，要求代理在隔离环境中迭代开发并验证静态分析检查器。该基准揭示了当前代理在长程检查器合成上的显著局限，但评估结果受限于特定分析器环境与时间预算，其泛化性尚存疑。

## 研究背景

静态分析工具通过预定义的检查器（Checker）检测程序缺陷，传统流程依赖专家将缺陷模式编码为特定分析器（如 Clang Static Analyzer, CSA 或 CodeQL）的规则。当 LLM 介入代码理解时，直接生成检查器面临两大障碍：一是缺乏仓库级上下文导致推理不完整，二是无法通过编译与扫描反馈迭代修正逻辑。这要求代理具备长程交互能力，即在观察-工具调用-编辑-执行的循环中，自主导航分析器基础设施并调试检查器行为。

当前仓库级软件工程基准（如 SWE-bench）主要评估代理解决 GitHub Issue 或生成补丁的能力，其核心假设是“修复单个缺陷”等价于“理解代码逻辑”。然而，检查器合成要求输出可复用的静态分析规则，而非一次性补丁，且需满足低误报率与诊断定位准确性。现有漏洞检测基准（如 ReposVul）仅关注漏洞识别，未涉及检查器的构建与验证。这种评估范式的缺失，导致无法量化代理将漏洞规范转化为可靠静态分析工具的能力，而该能力是自动化安全分析的关键环节。

## 核心方法

### 任务形式化与参照系

本文任务定义为长程代理静态分析检查器合成，区别于通用代码生成基准的单函数输出，其核心差异在于输出物为可执行、可复用的分析器规则，且需通过独立验证器的诊断对比与误报控制。参照系为仓库级代理编码流程，但本文将目标从“代码修复”转向“工具开发”，引入分析器环境约束与长程迭代调试机制。

### 基准构建与独立验证

CheckerBench 的构建核心在于将真实漏洞修复实例转化为可执行的检查器合成任务。每个任务 $x_i = (p_i, \ell_i, \alpha_i, E_i, Q_i)$ 包含漏洞修复实例 $p_i$（仓库、漏洞/修复版本、补丁）、语言 $\ell_i$、分析器 $\alpha_i$、固定环境 $E_i$ 及合成指令 $Q_i$。代理在 50 分钟预算内生成轨迹 $\tau_i^{(h,\theta)}$ 与候选检查器 $q_i^{(h,\theta)}$，其中 $h$ 为代理框架，$\theta$ 为模型参数。

$$
\text{Pass@1} = \frac{1}{N} \sum_{i=1}^{N} \mathbb{I}\left[ V_i(q_i^{(h,\theta)}) \land \text{FP}_i(q_i^{(h,\theta)}) \leq \tau_{\text{FP}} \right]
$$

该公式表明，任务通过需同时满足独立验证器 $V_i$ 的诊断对比要求（漏洞版本报告消失、修复版本无报告）及误报率阈值 $\tau_{\text{FP}}$。设计动机在于解决现有基准中“补丁正确性”无法证明“检查器正确性”的问题，通过冻结验证器与主分支扫描，确保评估的独立性与防污染性。

### 评估框架与指标体系

CheckerLab 框架引入多维评估指标，超越单一 Pass@1。过程质量（Process）由 LLM 裁判评估代理的推理与调试逻辑，语义质量（Semantic）检查检查器是否捕捉漏洞机制，误报率（FPpass）通过主分支扫描量化过度报告。

$$
\text{Score} = w_1 \cdot \text{Process} + w_2 \cdot \text{Semantic} + w_3 \cdot (1 - \text{FPpass})
$$

该加权评分旨在平衡代理的行为质量与检查器的技术性能。设计动机在于揭示“高过程分但低通过率”的矛盾现象（如 Qwen3.8-Max 在 Hermes Agent 中 Process 达 90.92 但 Pass@1 仅 25.00%），从而区分代理的“理解能力”与“执行能力”。

## 实验评估

实验在 21 种模型-框架配置上进行，涵盖 GPT-5.6、Claude Opus 4.8 等 7 个模型与 OpenCode、Claude Code、Hermes Agent 3 个框架。基线对比包括 KNighter（67.2% 有效检查器率），但缺乏通用代码生成 SOTA 基线，因任务性质不同。

| 配置 | Pass@1 (%) | Process (/100) | Semantic (/10) | FPpass (%) |
|---|---|---|---|---|
| Claude Opus 4.8 / OpenCode | 45.33 | 81.00 | 8.32 | 13.79 |
| DeepSeek-V4-Pro / OpenCode | 39.67 | 90.67 | 8.12 | 2.56 |
| Qwen3.8-Max / Hermes Agent | 25.00 | 90.92 | 8.53 | 11.11 |
| 平均 (21 配置) | 32.30 | 73.65 | 8.17 | 3.88 |

最佳配置 Claude Opus 4.8 / OpenCode 的 Pass@1 为 45.33%，显著低于静态基准上的表现，表明长程检查器合成的挑战性。DeepSeek-V4-Pro 在 OpenCode 中 FPpass 仅 2.56%，显示其在误报控制上的优势，但 Pass@1 低于 Claude Opus 4.8。

消融实验显示，移除技能库使 Pass@1 从 39.67% 降至 8.33%，隐藏执行反馈降至 13.33%，一次性生成仅 0.33%。这表明迭代反馈与技能引导是成功的关键，而非模型本身的代码生成能力。FP 阈值敏感性分析显示，阈值从 10% 升至 50% 时，平均接受率仅增加 0.78 个百分点，表明误报控制并非主要瓶颈，诊断对比才是核心挑战。

评估边界受限于 50 分钟时间预算与特定分析器环境（CSA/CodeQL），未覆盖其他分析器或更长程任务。可复现性方面，论文提供 GitHub 与 HuggingFace 链接，但验证器细节与主分支扫描数据未完全公开，可能影响结果复现。

## 关联研究分析

从问题动机看，CheckerBench 与 SWE-bench 同属仓库级代理评估，但 SWE-bench 聚焦“修复缺陷”，而本文聚焦“开发检测工具”。这一差异源于任务输出的本质不同：补丁是一次性代码修改，检查器是持久化分析规则。SWE-bench 的评估协议（测试用例通过）无法捕捉检查器的复用性与误报特性，导致其无法评估代理的工具开发能力。本文通过引入独立验证器与主分支扫描，填补了这一评估空白，但代价是任务复杂度显著增加，导致 Pass@1 远低于 SWE-bench 上的表现。

从方法设计看，CheckerBench 与 KNighter 同属检查器合成路线，但 KNighter 仅针对 Linux 内核与 CSA，而本文扩展至 5 种语言与 2 种分析器。KNighter 使用阶段特定提示与模板，本文则采用共享技能库与长程迭代。实验显示，本文方法在 KNighter 任务上达 80.3% 有效检查器率，优于 KNighter 的 67.2%，表明技能引导工作流具有跨任务迁移性。然而，本文未探索多分析器协同或检查器组合优化，这在真实安全分析场景中可能是关键需求。

## 总结

CheckerBench 解决了长程代理静态分析检查器合成缺乏统一评估基准的问题，通过真实 CVE 任务与独立验证器，量化了代理在工具开发上的能力局限。实验表明，最佳配置 Pass@1 仅 45.33%，且过程质量与通过率存在显著脱节，揭示当前代理在长程迭代调试与误报控制上的不足。本文边界在于评估局限于特定分析器与时间预算，未覆盖更复杂的多分析器场景或更长程任务。当代理在 50 分钟预算内无法完成检查器合成时，延长预算或引入多代理协作是否能显著提升通过率，论文未给出回答。
