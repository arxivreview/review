# HuggingFace最新推荐论文 ｜Learning Meta-Skills for Agent Harness Design in Test-Time AI4AI ｜元技能驱动的智能体环境构建

作者：Cheng Qian、Kunlun Zhu、Beibin Li 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2609.38143)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.38143)

> 现有代理技能研究聚焦于直接优化执行者（Target）的任务执行能力，但忽略了环境支持（Harness）对性能的关键制约，导致模型在复杂长程任务中因缺乏协调机制而失效。本文提出“元技能”（Meta-Skill）概念，将优化目标从Target的执行技能转移至构建者（Builder）的环境设计能力，通过从Target执行反馈中蒸馏支持原则，指导Builder构建可执行的支持环境。实验表明，在Harness-Bench和NewtonBench上，全库元技能使宏平均性能较无技能构建提升8.95个百分点，较直接传递技能给Target提升12.02点。这一结果验证了“支持设计”优于“知识灌输”的有效性，但元技能库规模较小且跨Builder迁移效果不稳定，其通用性仍存疑。

## 研究背景

当大语言模型代理执行多步科学发现或复杂工作流时，其性能不仅取决于推理能力，更受限于执行环境中的状态跟踪、工具调用协调及验证反馈机制。这种环境依赖导致即使具备强推理能力的模型，在缺乏外部支持时仍频繁出现提交无效或逻辑断裂，这一现象称为“协调瓶颈”。解决该瓶颈的传统路径是优化Target的执行技能，但技能往往过拟合于特定任务，难以泛化到需要频繁切换支持策略的异构场景。

代理技能学习的主流路线假设技能是Target可直接复用的程序性知识，通过轨迹蒸馏或强化学习优化技能库。然而，当技能库规模扩大或任务复杂度增加时，直接传递技能给Target面临两个瓶颈：一是技能解释与执行分离，Target需消耗大量推理预算理解并应用技能；二是技能缺乏对执行环境的动态适配，无法根据Target的实时状态调整支持粒度。本文的切入点在于区分“任务技能”与“元技能”，前者描述如何执行任务，后者描述如何设计支持环境，将优化对象从Target的执行层提升至Builder的环境设计层。

## 核心方法

### 方法参照系

本文问题属于代理技能生成与优化范畴，但关键差异在于优化目标从Target的技能库转移至Builder的Harness构建策略。标准流程中，技能学习直接更新Target的执行知识，而本文通过Builder-Target双模型交互，将技能学习解耦为环境设计原则的积累与执行。

### 元技能定义与学习机制

元技能定义为三元组 $s = (when, provide, use)$，其中 $when$ 标识触发支持的可观测条件，$provide$ 指定环境应提供的能力或资源，$use$ 说明Target如何使用该支持并保留哪些判断责任。设计动机在于解决直接技能传递中Target需自行解释并应用技能的认知负荷问题，通过将支持原则抽象为环境设计指令，Builder可将其转化为可执行组件。学习过程从空技能库 $S_0 = \emptyset$ 开始，Builder为开发任务构建Harness，Target执行后产生反馈 $F(e)$，Builder基于反馈更新技能库：

$$S_{j+1} = \text{Revise}_B(S_j, \{ (H_x^j, F(e_x^j)) \}_{x \in G_j})$$

该公式表示Builder根据当前技能库 $S_j$、生成的Harness $H_x^j$ 及执行反馈 $F(e_x^j)$ 修订技能库，每次更新仅允许一次增删改操作，确保技能基于观测证据而非假设。

### 测试时Harness构建

测试阶段冻结技能库 $S^* = S_J$，Builder为每个测试任务 $x$ 构建新Harness：

$$H_x^* = B(H_0, x, K(x, S^*))$$

其中 $K(x, S^*)$ 提供全库或检索的元技能，$H_0$ 为中性环境。设计动机在于解决开发时学习的环境与测试时任务不匹配问题，通过为每个任务动态构建支持环境，元技能从静态知识转化为动态支持策略。Builder可选择实现指令、记忆、上下文组织、组合工具、执行控制、验证恢复及工作区准备七类组件，将元技能中的 $provide$ 字段转化为具体环境机制，如将“版本跟踪”原则实现为文件版本记忆与验证工具。

## 实验评估

实验在Harness-Bench（95个测试任务）和NewtonBench（292个测试任务）上进行，Builder为GPT-5.6-Sol，Target包括Gemini-3.6-Flash、Qwen3.8-Flash和GPT-OSS-120B。基线覆盖无技能Builder、直接传递Builder技能、独立结构化Target技能及挖掘自由形式Target技能，但缺失图结构检索（如SkillDAG）或强化学习驱动（如Skill1）方法的对比，可能低估元技能在大规模技能库场景下的相对优势。

| 方法 | Harness-Bench Macro Avg. | NewtonBench Macro Avg. |
| :--- | :--- | :--- |
| Native environment | 51.40 | 49.66 |
| Builder, no skills | 56.36 | 50.34 |
| Direct Builder skills, all | 53.29 | 55.82 |
| Builder meta-skills, all | 65.31 | 63.70 |

全库元技能在两个基准上均显著优于无技能Builder和直接技能传递，其中NewtonBench提升10.96点，Harness-Bench提升6.95点，表明元技能在协调密集型任务中收益更大。消融实验显示，移除执行控制器导致Gemini性能下降13.36点，而移除记忆与上下文对GPT-OSS产生3.42点正向影响，说明支持组件的价值依赖Target特性，全库访问优于BM25检索（平均提升7.19点），但Qwen在Harness-Bench上从第一遍峰值下降4.06点，揭示技能精炼的非单调性。

评估边界方面，论文未报告计算效率指标（如Token成本、延迟），且元技能库规模较小（未明确数量），全库优势可能源于小规模互补性而非检索瓶颈。代码已开源，但超参数（如开发集通过次数）固定为2遍，未探索更多迭代对性能的影响。

## 关联研究分析

从问题动机看，本文与SkillOpt同属技能自动优化路线，但SkillOpt优化Target的提示词或技能文档，而本文优化Builder的环境构建策略。这一差异源于任务特性：SkillOpt假设技能可直接指导执行，而本文发现复杂任务中执行失败主要源于环境协调而非知识缺失，因此将优化目标转移至环境层。从方法设计看，本文与Voyager共享可执行技能库思想，但Voyager的技能是Target的代码资产，本文的元技能是Builder的设计原则，前者直接复用，后者需Builder转化为环境组件。这种解耦使元技能具有跨Builder迁移潜力，但实验显示迁移效果不稳定（如Sol-to-Qwen库在Gemini-Pro上下降4.45点），根源在于不同Builder对同一元技能的实现差异，论文未探索如何通过执行反馈细化迁移后的Harness。

## 总结

本文要解决的核心矛盾是代理技能直接传递中Target执行负荷与环境适配不足的问题。现有方法聚焦优化Target技能，但无法解决协调瓶颈，本文通过引入元技能概念，将优化目标转移至Builder的环境设计能力，从Target执行反馈中蒸馏支持原则，指导Builder构建动态Harness。实验证明全库元技能在Harness-Bench和NewtonBench上分别提升6.95和10.96点，验证了支持设计优于知识灌输的有效性。本文的边界在于元技能库规模较小，全库优势可能源于小规模互补性，且跨Builder迁移效果不稳定，根源在于Builder实现差异。当元技能库规模扩大至数百条时，全库访问是否仍优于检索，以及如何通过执行反馈细化迁移后的Harness实现，论文未给出回答。
