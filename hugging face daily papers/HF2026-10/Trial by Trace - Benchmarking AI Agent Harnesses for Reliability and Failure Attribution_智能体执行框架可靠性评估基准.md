> 导读：智能体在真实部署中的表现不仅取决于底层大语言模型，更受执行框架（Harness）对上下文、工具调用及状态管理的编排控制影响。现有评估基准多聚焦于最终任务成功率，将模型决策与框架执行混为一谈，无法定位导致任务失败的具体机制缺陷。TraceTrial-Bench 将评估对象从“智能体整体”解耦为“模型+Harness”，通过双层评估框架与多源证据获取机制，分别量化 Agent 任务表现与 Harness 可靠性。该基准揭示了任务成功与框架合规性之间的显著背离，为智能体系统的生产级审计提供了细粒度诊断工具，但其失败归因的因果验证仍依赖人工审查。

## 研究背景

当智能体执行复杂任务时，其最终输出是模型推理与执行框架（Harness）协同作用的结果。Harness 负责构建上下文、暴露工具接口、传输调用结果并维护持久化状态。若仅关注最终任务成功率，无法区分模型决策错误与框架执行缺陷。例如，框架可能因上下文压缩丢失关键信息，或因工具返回截断导致模型误判，但最终仍可能生成正确结果。这种“结果掩盖过程”的现象，使得传统评估无法识别框架层面的可靠性隐患。

智能体评估领域正从静态基准向动态轨迹评估演进。早期工作如 AgentBench 确立了多环境交互基线，MASEval 揭示了框架选择对性能的显著影响，但多停留在系统级黑盒对比。当前领域共识认为，框架实现差异对性能有实质性影响，需解耦模型能力与框架效应。然而，现有方法缺乏针对 Harness 内部机制（如状态隔离、工具传输忠实度）的白盒诊断能力。TraceTrial-Bench 针对这一空白，提出机制导向的评估范式，将 Harness 视为被测系统（SUT），通过原生执行轨迹与外部状态验证，实现框架可靠性的独立度量。

## 核心方法

### 双层评估框架与系统边界定义

传统评估将智能体视为黑盒，仅验证最终交付物。TraceTrial-Bench 将系统边界明确划分为模型、Harness、环境与测量装置，其中 Harness 为被测系统。评估框架分为 Agent 层与 Harness 层：Agent 层检查任务动作、工作区状态及交付物是否符合权威状态；Harness 层检查原生系统是否履行了信息传递与执行语义义务。

该设计解决了“正确结果伴随框架缺陷”的评估盲区。例如，模型可能通过非预期路径完成任务，但 Harness 未正确记录状态转换。双层评估确保框架缺陷即使未导致任务失败，也能被独立捕获。

### 七类可靠性组件与机制导向任务

Harness 可靠性被分解为七个组件：Context（上下文）、Execution（执行）、Governance（治理）、Lifecycle（生命周期）、Observability（可观测性）、Tools（工具）与 Verification（验证）。基准构建 95 个机制导向任务，每个任务绑定特定 Harness 义务与 Agent 交付物，并配备可执行或基于状态的 Ground Truth。

任务设计强调“机制可达性”，即任务触发条件必须在资源预算内激活目标机制。例如，通过超大输出触发上下文压缩，或通过跨会话事实传递测试状态隔离。这种设计确保评估聚焦于框架行为，而非模型能力上限。

### 多源证据获取与失败归因机制

评估依赖多源证据获取（MEA）模块，整合轨迹追踪（TT）重构的 Trace IR、工作区工件及权威环境状态。证据包（Evidence Packet）通过声明式选择器提取特定事件，确保评估可审计。

失败归因（FA）模块通过预声明的机制链连接 Harness 失败与 Agent 失败。候选链接（Candidate Link）的激活条件为：

$$
L_{act} = \{ (h_i, a_j) \mid V_H(h_i) = 0 \land V_A(a_j) = 0 \land C_{h_i \to a_j} = \text{True} \}
$$

其中 $V_H$ 与 $V_A$ 分别为 Harness 与 Agent 层判定，$C$ 为预声明的因果条件。该公式定义了候选链接的自动激活逻辑，但强调“候选”不等于“确认”，传播验证需人工审查事件顺序与中间失真，避免将相关性误判为因果性。

## 实验评估

实验在 4 种 Harness（Claude Code, Codex, DeepSeek Harness, OpenClaw）、9 种模型及 95 个任务上执行 3,420 次运行。评估使用固定 Judge（deepseek-v4-flash）进行语义评分，所有运行均通过装置完整性检查。

| Harness | Agent Pass (%) | Harness Macro (%) | Clean (%) | Overall (%) |
| :--- | :--- | :--- | :--- | :--- |
| Claude Code | 44.0 | 71.2 | 9.1 | 73.5 |
| Codex | 35.8 | 59.8 | 2.8 | 65.2 |
| DeepSeek Harness | 40.0 | 68.8 | 9.8 | 71.0 |
| OpenClaw | 38.2 | 72.0 | 11.7 | 71.8 |

主结果显示，任务成功率与框架可靠性排名不一致。Claude Code 拥有最高 Agent 任务成功率（44.0%），但 OpenClaw 在 Harness 宏观得分（72.0%）与联合清洁率（11.7%）上领先。Codex 在所有模型组中 Harness 宏观得分最低（59.8%），表明其执行语义忠实度存在系统性短板。

| Dimension | Tasks | Claude Code (%) | Codex (%) | DeepSeek H (%) | OpenClaw (%) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Context | 15 | 74.5 | 62.0 | 64.3 | 61.6 |
| Execution | 27 | 64.7 | 51.5 | 65.3 | 77.1 |
| Lifecycle | 19 | 71.3 | 53.0 | 71.7 | 65.9 |
| Tools | 17 | 71.5 | 65.6 | 71.5 | 70.2 |

维度分析揭示框架能力的异质性。Execution 维度整体得分最低（64.6%），但 OpenClaw 在该维度表现最佳（77.1%），而 Codex 仅 51.5%。Context 维度则呈现相反趋势，Claude Code 领先（74.5%）。这种跨维度的性能反转表明，框架选择需匹配任务可靠性需求，单一综合得分无法指导部署决策。

评估边界方面，基准未覆盖计算效率与成本权衡，且失败归因的因果验证依赖人工，自动化程度有限。

## 关联研究分析

从评估对象看，TraceTrial-Bench 与 MASEval 均关注框架影响，但 MASEval 侧重多智能体系统的消息历史追踪，属于系统级黑盒评估；TraceTrial-Bench 深入 Harness 内部机制（如上下文压缩、工具传输），属于组件级白盒诊断。这一差异源于任务特性：MASEval 评估协作效率，而 TraceTrial-Bench 评估执行忠实度。

从评估协议看，AgentCompass 提供统一基础设施以解决碎片化，但未深入框架内部行为审计。TraceTrial-Bench 的七类组件分类法与机制导向任务设计，填补了从“框架影响存在”到“框架缺陷定位”的空白。然而，其自建基准缺乏外部 SOTA 对照，评估协议本身引入的偏差（如任务难度分布）尚未通过跨基准验证排除。

## 总结

TraceTrial-Bench 针对智能体评估中模型能力与框架效应混淆的核心矛盾，提出将 Harness 作为独立被测系统的评估范式。通过双层评估框架与机制导向任务，该基准量化了框架可靠性，并揭示了 31.1% 的任务成功伴随框架缺陷。实验表明，任务成功率与框架合规性排名不一致，且框架能力在不同可靠性维度上存在显著异质性。该基准的边界在于其自建任务集缺乏外部验证，且失败归因的因果链验证仍需人工介入。当候选机制链接的自动激活率与人工验证的传播率存在偏差时，如何构建更鲁棒的自动化因果推断算法，以替代当前的人工审查环节，是该方法走向规模化部署前必须解决的问题。
