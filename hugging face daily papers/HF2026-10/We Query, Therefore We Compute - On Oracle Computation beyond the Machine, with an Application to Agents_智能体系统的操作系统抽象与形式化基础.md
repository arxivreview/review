## 研究背景

当开发者构建 LLM 智能体时，常面临一个根本性困境：如何定义模型输出与程序控制之间的边界？在 Agent 形态中，模型动态决定动作；在 Workflow 形态中，模型调用遵循预设代码路径。这两种形态在实现上日益交织，但缺乏统一的理论框架来解释其交互机制。传统方法将 LLM 视为黑盒，仅通过提示工程或外部编排器进行控制，导致缓存管理、任务调度与安全隔离等机制各自为政，无法形成系统级的不变量。

领域内主流研究集中于工作流的自动优化与鲁棒性提升，如通过强化学习动态调整代理拓扑或引入形式化验证确保轨迹正确性。然而，这些方法均建立在“执行环境已存在”的假设之上，未触及执行环境本身的语义定义。当系统需要处理多智能体并发状态一致性或实时故障预警时，缺乏底层抽象使得上层策略难以保证全局安全性。本文切入点在于构建一个抽象机器，将 LLM 推理过程形式化为 Oracle 计算，从而从架构层面推导出 Agent 与 Workflow 的统一视图及操作系统级保障。

## 核心方法

### 方法参照系：Oracle 计算与双栈自动机

本文问题不属于传统的工作流搜索或提示优化，而是系统架构设计。其参照系为可计算性理论中的 Oracle 机器与图灵完备的双栈下推自动机（Two-Stack Pushdown Automaton, 2-PDA）。2-PDA 通过两个栈模拟图灵机磁带，具备图灵完备性。本文的关键差异在于引入一个 Oracle 指令，将 LLM 的自回归生成过程映射为栈上的追加操作，从而将模型推理与程序控制解耦为两个同步的计算流。

### 核心创新：对称性破缺与内核契约推导

在基础 O-2-PDA 中，两个栈是对称的，无法区分操作系统与用户程序。本文通过两次对称性破缺（Symmetry Breaking）打破这种对称性，从而推导出操作系统抽象。

第一次破缺发生在存储层（S-breaking）。通过 Call-by-Push-Value (CBPV) 类型系统，规定 Oracle 仅在标记为 O 的栈上执行代码，而在标记为 P 的栈上，Oracle 的输出仅被视为数据。这一设计确保了模型生成的文本不会意外被解释为可执行指令，从架构上预防了提示注入导致的代码执行漏洞。

第二次破缺发生在转移层（T-breaking）。引入 O-mode 与 P-mode 两种特权级。在 O-mode 下，机器反复查询 Oracle 并追加答案，直到遇到特定的 yield 符号（如工具调用请求）；此时控制流陷阱至 P-mode 的固定入口，由 Priestess（即操作系统内核）处理工具调用并返回结果。这一机制将模型生成限制在用户态，将工具执行与状态管理限制在内核态。

$$
\text{Oracle}(s) \rightarrow \begin{cases}
\sigma(s) \cdot r & \text{if } \sigma(s) \in \text{dom}(E) \\
\text{jump to } l_e & \text{otherwise}
\end{cases}
$$

上述公式定义了 Oracle 指令的转移规则：若栈内容可被编码器接受，则追加解码后的答案 $r$；否则跳转至错误处理标签。这一看似简单的追加操作，结合两次破缺，使得 Priestess 程序成为 Oracle 运行程序的操作系统。内核契约（Kernel Contract）由此推导而出：Oracle 操作仅在其窗口内追加，控制流仅在固定入口返回，且 Oracle 无法直接修改程序计数器。

### 核心创新：缓存层级与调度同步

基于上述架构，本文统一了 Agent 上下文缓存与模型 KV Cache 的视角。对于内部自回归的 Oracle，一次 Oracle 调用对应一个从历史栈到 KV Cache 的缓存层级。

$$
C(k) = \begin{cases}
W_C(k) & \text{if } k \in \text{dom}(W_C) \\
f(k) & \text{otherwise}
\end{cases}
$$

该公式描述了缓存层级中存储 $C$ 对函数 $f$ 的覆盖关系。在 O-2-PDA 中，历史栈的增长对应于缓存键的追加。若 Oracle 内部自回归且编码器保持前缀一致性，则私有缓存可确保每个 token 仅计算一次。这一模型揭示了调度成本的关键：Priestess 侧知道下一个任务的历史前缀，而 Oracle 侧知道其缓存状态。若缺乏任务返回时间的信息，确定性策略在保留或丢弃任务状态时的最坏情况成本将是已知信息策略的两倍。

## 实验评估

该论文实验数据不可得，未提供实验表格。

本文未提供传统意义上的基准测试数值对比，其有效性验证侧重于架构可实现性与理论完备性。实验设置方面，作者构建了 ArchNights-SE 原型，基于 gem5 模拟器扩展 RISC-V ISA，实现 Oracle 模式与 PRTS 内核。基线审计显示，本文未与 DAAO、AFlow 等主流工作流编排方法进行对比，而是与 miniswe-agent 和 Terminus 2 等参考 harness 在 Terminal-Bench 2.1 上进行定性比较，声称表现相当。

评估边界方面，本文未量化 ArchNights 在复杂多智能体协作任务中的性能开销，也未验证形式化约束对动态工作流生成算法（如基于 RL 的拓扑搜索）的兼容性。可复现性方面，ArchNights-SE 承诺开源，但 ArchNights-FS 仅为设计文档，缺乏硬件级验证数据。

## 关联研究分析

从问题动机看，本文与 Lean4Agent 均关注形式化验证，但路径截然不同。Lean4Agent 针对具体工作流轨迹进行事后验证，属于应用层保障；本文通过 O-2-PDA 从底层执行机器推导不变量，属于系统层预防。Lean4Agent 的验证依赖于工作流结构的静态定义，而本文的架构允许动态生成，只要生成过程遵循 Oracle 指令的追加语义，即可保证内核契约成立。这一差异暗示了形式化验证的两种范式：轨迹级验证与架构级不变量。

从方法设计看，本文与 Sherlock 均涉及执行可靠性，但机制互补。Sherlock 通过选择性验证与推测执行平衡可靠性与效率，属于运行时优化策略；本文通过存储与转移的对称性破缺，从源头隔离了 Oracle 与 Priestess 的权限。Sherlock 的节点重要性评估依赖于执行反馈，而本文的安全边界不依赖 Oracle 内部状态，仅依赖调用接口。查询侧增强在数据充足时是否仍有增益，论文未给出回答，但本文的架构为这类增强提供了安全的执行沙箱。

## 总结

本文要解决的核心矛盾是 LLM 智能体系统缺乏统一的底层语义基础，导致 Agent 与 Workflow 形态割裂且安全机制零散。本文抓住的切入点是将 LLM 抽象为 Oracle，通过双栈自动机与对称性破缺从第一性原理推导操作系统抽象。本文构建了 O-2-PDA 机器与 ArchNights 原型，证明了该架构在 gem5 上的可实现性，并推导出内核契约与缓存模型。本文的边界在于未验证该架构对上层动态编排算法的兼容性，且缺乏与主流编排方法在相同任务上的量化性能对比。当形式化约束限制了 Oracle 模式的自由度时，基于强化学习的动态工作流搜索是否仍能保持其探索效率，论文未给出回答。
