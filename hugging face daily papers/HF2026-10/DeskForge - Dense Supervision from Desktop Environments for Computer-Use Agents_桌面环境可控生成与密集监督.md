# HuggingFace最新推荐论文 ｜DeskForge: Dense Supervision from Desktop Environments for Computer-Use Agents ｜桌面环境可控生成与密集监督

作者：A. Said Gurbuz、Ahmed Nassar、Sunghwan Hong 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2610.02320)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2610.02320)

> 计算机使用智能体（Computer-Use Agent）在复杂桌面场景中定位动作目标时，常因多应用窗口重叠、视觉相似控件干扰而失效。现有训练数据多为静态截图或单应用记录，缺乏对多窗口布局、遮挡关系及动作后果的系统性控制，导致模型难以泛化至未见过的桌面配置。DeskForge 通过构建可控 Linux 桌面环境，程序化组合真实应用并记录密集标注与状态转换，生成 1.2M 观测样本。该工作验证了环境生成数据对定位精度与长程任务完成率的提升，但其 Linux 后端限制及未覆盖原生 Windows/macOS 的局限，使其跨平台泛化能力存疑。

## 研究背景

当智能体需在多窗口共存的桌面中执行点击操作时，其核心挑战在于区分目标控件与跨应用干扰项。这一过程依赖于视觉-空间映射机制，即从自然语言指令与截图中预测目标像素坐标。然而，多模态大语言模型（MLLMs）缺乏原生空间感知能力，且真实桌面场景中无障碍树（Accessibility Tree, AT）常缺失或噪声大，导致依赖结构化元数据的方法失效。纯视觉驱动范式虽解决了平台兼容性问题，但静态截图数据无法反映窗口堆叠、部分遮挡等动态空间关系，模型在高分辨率密集布局下的小目标定位精度显著退化。

GUI 定位研究已从单应用定位转向多应用组合场景，但现有数据资源存在结构性缺陷：Rico、WebUI 等静态语料仅标注孤立应用，GUIrilla 虽能自动化探索但处理单应用状态图，ScreenParse 侧重网页解析。这些资源无法同时提供密集元素标注、多应用场景组合、可控视觉多样性及动作-状态转换记录。DeskForge 的切入点在于将桌面环境本身作为可控生成源，通过程序化配置应用状态、窗口布局与外观，系统性地生成具备复杂空间关系的监督数据，从而解决静态数据缺乏动态上下文的问题。

## 核心方法

### 方法参照系

本文问题属于 GUI 定位的数据构建路线，但区别于 SeeClick 等基于静态截图的预训练范式。关键差异在于：DeskForge 不记录真实用户行为，而是通过可控环境主动生成场景，将界面结构、窗口几何与动作后果融合为密集标注，实现从“被动记录”到“主动合成”的转变。

### 可控场景组合与密集标注流水线

场景组合模块通过规范文件（Scene Specification）控制应用选择、初始状态、内容、窗口布局、外观预设与分辨率。设计动机在于解决静态数据无法系统变化桌面配置的问题，使同一应用在不同上下文（如竞争控件、部分重叠窗口）中呈现，暴露模型在复杂空间关系下的定位弱点。密集标注流水线融合截图、AT 与窗口几何，输出元素类型、文本、几何、交互属性及父子结构。其核心创新在于几何细化与遮挡解析：对部分覆盖元素，可见支持表示为矩形并集，保留控件暴露部分而非整个范围作为有效点击区域。该机制解决了 AT 单独无法确定可见性的问题，确保标注反映实际渲染状态。

$$
V_{element} = \bigcup_{i=1}^{n} R_i \cap V_{viewport}
$$

其中 $V_{element}$ 为元素可见区域，$R_i$ 为元素被遮挡后剩余的矩形片段，$V_{viewport}$ 为视口限制。该公式确保点击目标仅包含实际可见像素，避免模型学习无效区域。

### 指令合成与状态转换记录

指令合成模块利用 Qwen3.6-27B 从记录的点击、目标上下文及前后截图生成自然语言指令。设计动机在于引入语言多样性，同时保留动作-状态转换记录以支持下游任务。每条转换 $(S_t, a_t, S_{t+1})$ 链接前后观测与执行动作，记录界面变化摘要。该机制使数据不仅支持单步定位，还为长程任务提供状态依赖监督。指令经人工审计，97.8% 被判定为合理，确保语义准确性。

$$
I_t = \text{VLM}(S_t, S_{t+1}, C_t)
$$

其中 $I_t$ 为合成指令，$C_t$ 为目标上下文。该公式表明指令生成依赖前后状态对比，确保目标可从 $S_t$ 中唯一识别，避免坐标或标注标记引用。

## 实验评估

实验在 200K 单目标定位视图上微调 Qwen3.5-4B、Gemma4-E4B、InternVL3.5-8B 及 UI-R1-3B，使用 LoRA 在 8 块 H100 GPU 上训练 1 个 epoch。基线覆盖通用 VLM 与 GUI 专用模型，但缺失 GUI-AIMA-3B 等最新 SOTA 的直接对比。主结果显示，所有模型在保留桌面条件及五个外部基准上均提升，Qwen3.5-4B 在 ScreenSpot-Pro 上从 30.17% 升至 41.68%，OSWorld-G 从 51.24% 升至 61.35%。

| 模型 | 训练 | SS-Pro | SS-v2 | OSWorld-G | UI-Vision | MMB-GUI |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Qwen3.5-4B | Base | 30.17 | 80.11 | 51.24 | 17.24 | 61.83 |
| Qwen3.5-4B | +DeskForge-1M | 41.68 | 90.33 | 61.35 | 28.77 | 76.82 |
| UI-R1-3B | Base | 14.48 | 81.92 | 34.04 | 12.09 | 56.84 |
| UI-R1-3B | +DeskForge-1M | 27.20 | 83.96 | 43.97 | 15.15 | 65.41 |

Qwen 的提升幅度最大，尤其在多应用场景（应用数从 1 增至 4+）中，微调模型仅损失少量精度，而基线模型持续退化，差距从 9.7 点扩大至 14.3 点。UI-R1 作为 GUI 专用模型，在 ScreenSpot-Pro 上从 14.48% 升至 27.20%，表明数据对已有专用模型仍有增益。长程任务实验中，固定 Qwen3.6-27B 规划器，仅更换动作模型，Qwen 在 WebArena-Infinity 上从 31 题升至 50 题，OpenApps 从 3 题升至 15 题，验证了定位精度对任务完成率的直接影响。

评估边界方面，DeskForge 仅使用 Linux 后端，未覆盖 Windows/macOS 原生环境，跨平台泛化能力未验证。代码与数据集已开源，但训练超参数细节仅在附录中提供，复现需依赖完整配置。外部基准中，ScreenSpot-v2 包含移动与 Web 界面，而 DeskForge 无移动屏幕，Qwen 在移动子集上仍提升 10.77 点，暗示桌面监督的迁移性，但具体机制未深入分析。

## 关联研究分析

从问题动机看，DeskForge 与 GUIrilla 均基于自动化桌面探索，但 GUIrilla 侧重单应用状态图构建，而 DeskForge 聚焦多应用组合场景。这一差异源于任务特性：GUIrilla 旨在解决桌面 UI 数据收集困难，而 DeskForge 针对多窗口干扰下的定位泛化。根源在于 GUIrilla 未考虑窗口堆叠与遮挡对定位的影响，而 DeskForge 通过几何细化显式建模可见性，解决了静态数据无法反映动态空间关系的问题。

从方法设计看，DeskForge 与 ScreenParse 均使用 ScreenTag 表示，但 ScreenParse 侧重网页解析，DeskForge 扩展至桌面多窗口。关键差异在于标注来源：ScreenParse 依赖人工密集标注，DeskForge 通过环境生成自动获取。这一选择源于数据规模需求：人工标注成本高且难以覆盖多配置组合，而环境生成可系统变化布局与外观，实现大规模密集标注。然而，程序化生成的场景分布是否覆盖真实用户操作的长尾分布，论文未给出回答，可能限制模型在罕见配置下的泛化能力。

## 总结

DeskForge 解决的核心矛盾是静态 GUI 数据缺乏多应用组合场景下的密集空间关系标注。其切入点在于将桌面环境作为可控生成源，通过程序化配置与密集标注流水线，系统性地生成具备遮挡、多窗口及状态转换的监督数据。该方法在 4B 模型规模下，将 ScreenSpot-Pro 定位精度从 30.17% 提升至 41.68%，并在长程任务中显著增加完成数量。然而，其 Linux 后端限制及未覆盖原生 Windows/macOS 的局限，暴露了跨平台泛化的边界。当模型在 Linux 生成的视觉特征上训练后，迁移至 Windows 或 macOS 界面时，因控件样式、窗口装饰差异导致的定位精度衰减幅度，论文未提供实验数据，这一迁移性验证仍是关键待解问题。
