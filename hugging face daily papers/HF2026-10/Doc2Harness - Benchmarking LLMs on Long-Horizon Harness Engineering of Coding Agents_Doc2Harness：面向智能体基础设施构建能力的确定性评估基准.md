> 导读 智能体在长时程任务中的表现高度依赖其外部执行框架（Harness）的质量，但现有评估体系仅关注固定框架下的任务成功率，无法衡量模型构建或优化框架本身的“元能力”。传统软件工程基准依赖单元测试验证代码补丁，而框架具有实现多样性且需动态驱动，导致静态测试失效。本文提出 Doc2Harness 基准，通过两阶段流程：先让模型在隔离环境中根据文档构建完整框架，再用脚本化模拟模型驱动该框架进行黑盒测试，并引入正向控制机制排除假阳性。该基准首次将评估对象从“使用工具”延伸至“制造工具”，填补了智能体自改进能力评估的空白，但其固定构建框架与消除噪声的设计是否偏离真实部署场景，仍需进一步验证。

## 研究背景

当智能体执行复杂任务时，其能力不仅取决于底层大语言模型（Large Language Model, LLM），更受制于管理交互循环、工具执行及状态管理的代码框架（Harness）。框架质量决定了模型能力向环境转化的效率。然而，现有评估基准如 SWE-bench 仅测试模型在固定框架下修复代码补丁的能力，无法反映模型构建或重构框架本身的泛化能力。框架实现具有高度多样性，且其正确性需通过动态交互验证，传统基于固定接口的单元测试无法直接迁移至框架评估场景。

智能体评估领域正从静态结果导向转向基于轨迹（Trajectory-based）的过程审计，但这一转变仍局限于评估智能体在既定框架内的行为合规性。随着递归自我改进（Recursive Self-Improvement）概念的兴起，智能体修改自身基础设施的能力成为关键瓶颈。现有方法要么依赖下游任务成功率间接推断框架质量，要么受限于模型驱动评估时的随机性干扰。如何构建一套确定性、可复现且能解耦模型能力与框架效应的评估体系，以量化 LLM 构建复杂软件基础设施的能力，成为当前领域亟待解决的核心问题。

## 核心方法

### 两阶段解耦评估架构

Doc2Harness 将评估流程解耦为构建与测试两个独立阶段，以消除评估过程中的混淆变量。在 Stage 1 构建阶段，待评估模型在固定的构建框架（OpenCode）内，依据开发文档和仅声明接口的契约骨架（Contract Skeleton），在隔离容器中生成候选框架。契约骨架源自 mini-swe-agent，仅保留 CLI、无头入口及自动化评估 API 三个不可变接口，确保候选框架中约 99.6% 的代码由模型自主编写。在 Stage 2 评估阶段，候选框架被移至独立容器，由预设脚本驱动的模拟模型（Mock Model）进行端到端黑盒测试。该架构通过固定构建工具与测试驱动源，将评估焦点严格锁定在模型生成框架代码的质量上，避免了构建工具差异或真实 LLM 随机性对结果的干扰。

### 基于正向控制的假阳性排除机制

在动态执行评估中，测试用例可能因观测机制失效而非框架功能正确导致通过，即“空洞通过”（Vacuous Pass）。为排除此类假阳性，本文引入正向控制（Positive Control）机制。每个测试用例 $t$ 关联一组正向控制 $C_t$，测试通过状态 $S_t$ 定义为：

$$
S_t = \begin{cases}
\text{PASS} & \text{if } \text{Test}(t) = \text{PASS} \land \forall c \in C_t, \text{Control}(c) = \text{PASS} \\
\text{FAIL} & \text{otherwise}
\end{cases}
$$

正向控制复用测试场景与初始状态，但改变输入或访问路径，断言在观测前提成立时必然发生的结果。例如，若测试用例验证路径逃逸拦截，正向控制则通过 Bash 工具访问同一符号链接，确认文件确实可读。若正向控制失败，说明观测通道本身失效，测试用例无论自身状态如何均记为 FAIL。该机制从通道可达性、同形访问及反向验证三个维度，确保评估结果仅反映框架对规范条款的实际执行能力。

### 多源驱动的测试用例合成策略

测试用例的判别力直接决定基准的有效性。本文采用三种互补方法合成测试用例：公开问题挖掘、跨框架对比及单变量扩展。公开问题挖掘从成熟框架的 Issue 记录中提取缺陷模式，假设 LLM 生成的框架会复现人类开发者的常见错误。跨框架对比将候选框架与成熟框架按功能模块划分，追踪实现差异并归因至开发文档条款。单变量扩展以已知判别性测试为种子，仅改变工具、输入形式、错误参数或返回位置中的一个变量，生成新候选。三种方法交替使用，确保测试用例覆盖从基础功能到边界条件的广泛场景，并通过聚类与过滤机制消除冗余，保证每个保留用例均能锚定至文档条款并具备确定性断言。

## 实验评估

实验在 328 个测试用例上评估了 19 个前沿模型，每个模型生成三个候选框架并取平均通过率。主结果显示，GPT-6 Astra 以 53.05% 的通过率领先，最弱模型 Hy3 仅为 27.44%，26 个百分点的差距表明基准未饱和且具备良好区分度。

| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| GPT-6 Astra | 71.6 | 46.7 | 44.0 | 39.4 | 45.0 | 91.7 | 53.05 ± 0.25 |
| Opus 5 | 63.4 | 39.6 | 38.1 | 17.2 | 43.3 | 91.7 | 46.65 ± 1.80 |
| Qwen3.8 Max | 61.2 | 38.2 | 43.3 | 15.2 | 32.5 | 93.3 | 45.83 ± 0.14 |
| Hy3 | 28.4 | 31.1 | 19.4 | 13.1 | 9.2 | 65.0 | 27.44 ± 0.43 |

*注：数据逐字取自论文 Table 2，正向控制不计入分母。*

消融分析揭示，权限类别具有最强判别力，平均通过率 43.7% 且强弱差距达 50.8 个百分点，而交互终端类别接近饱和。架构分析显示，代码行数与通过率呈正相关（$r=0.614$），但模块数量与通过率呈负相关（偏相关系数 $-0.423$），表明过度碎片化的模块设计损害框架质量。评估协议通过隔离容器与 Mock Model 确保了确定性，但未覆盖真实网络延迟或 UI 变化等噪声，可能高估框架在动态环境中的鲁棒性。

## 关联研究分析

从评估对象看，Doc2Harness 与 SWE-bench 存在本质差异。SWE-bench 评估模型在固定框架下修复特定 Issue 的能力，测试的是“补丁”的正确性；Doc2Harness 评估模型从零构建完整框架的能力，测试的是“系统”的合规性。SWE-bench 依赖单元测试验证行为，而框架实现多样性使得固定接口测试失效，Doc2Harness 通过黑盒驱动与正向控制解决了这一验证难题。然而，Doc2Harness 未对比传统 SWE-bench 基线，因任务定义不同导致直接数值比较无意义，但其 53.05% 的最高通过率远低于 SWE-bench Verified 的 SOTA（62.5%），暗示框架构建任务的复杂度与泛化要求更高。

从评估方法论看，Doc2Harness 与 AgentBench 等通用智能体基准形成互补。AgentBench 评估智能体在既定环境中的任务表现，关注行为轨迹；Doc2Harness 评估智能体构建环境（框架）的能力，关注代码生成质量。两者均强调过程评估，但 Doc2Harness 通过消除 LLM 随机性（使用 Mock Model）追求确定性，这与领域共识中强调“真实世界噪声”评估的路线存在张力。消除噪声虽提升了可复现性，但可能掩盖框架在异常处理与状态恢复方面的真实缺陷，导致评估结果偏离生产环境需求。

## 总结

本文针对智能体评估中“框架构建能力”缺失的盲区，提出 Doc2Harness 基准，通过两阶段解耦架构与正向控制机制，实现了对 LLM 构建智能体基础设施能力的确定性评估。实验证明，最强模型 GPT-6 Astra 通过率仅为 53.05%，表明当前模型在长时程框架工程上仍存在显著局限，且过度模块化设计会损害框架质量。该基准填补了从“使用工具”到“制造工具”的评估空白，但其固定构建框架与噪声消除设计限制了评估结果向真实部署场景的迁移。当模型在 Doc2Harness 中表现出高通过率时，其在真实网络延迟与动态 UI 变化下的框架鲁棒性是否同步提升，论文未给出回答。
