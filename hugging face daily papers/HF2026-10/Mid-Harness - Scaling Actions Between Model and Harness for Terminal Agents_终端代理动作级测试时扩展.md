# HuggingFace最新推荐论文 ｜Mid-Harness: Scaling Actions Between Model and Harness for Terminal Agents ｜终端代理动作级测试时扩展

研究机构：韩国科学技术院

作者：Minki Kang、Ryo Hachiuma、Shaokun Zhang 等 11 人

论文原文见 [arXiv](https://arxiv.org/abs/2609.39982)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.39982)

> 终端代理在长程任务中因单次动作执行改变环境状态，导致后续决策依赖被破坏，传统轨迹级扩展无法在动作执行前拦截错误。现有方法聚焦于完整轨迹的并行采样或序列精炼，忽略了模型-框架边界处动作候选的验证潜力。本文提出 Mid-Harness，在动作执行前采样并验证候选动作，以固定生成器和框架为前提提升轨迹成功率。该方法揭示了验证器质量是动作扩展收益的决定因素，但自验证在命令语义判断上仍存在显著分歧。

## 研究背景

终端代理通过执行命令与软件环境交互，每个动作（如代码编辑、包安装）都会改变环境状态，进而影响后续决策的上下文。这种状态依赖性意味着一个错误动作不仅导致当前步骤失败，还会污染后续所有步骤的输入，使得模型即使具备生成正确动作的能力，也可能因早期错误而无法完成任务。这一特性将动作可靠性定义为在长程序列中持续生成支持任务完成动作的能力，其评估需通过轨迹级任务成功率而非单步准确率来体现。

测试时计算扩展（Test-Time Scaling, TTS）旨在通过分配额外推理资源提升模型性能，主流路线包括并行采样多轨迹并聚合（如 Best-of-T）或序列精炼（如 Sequential Refine, SR）。然而，这些方法在轨迹完成后才进行验证或修正，无法在动作执行前拦截错误，导致环境状态被不可逆地改变。此外，现有研究多关注推理任务中的答案级验证，缺乏对代理任务中动作级验证机制的系统研究，特别是当验证器与生成器为同一模型时，验证机制的形式如何影响候选动作的利用效率。

本文切入点在于模型-框架边界处的动作级计算扩展。通过固定生成器和执行框架，仅在该边界插入候选动作采样与验证模块，研究何种验证机制能有效利用生成器产生的多样候选。这一设计隔离了动作扩展与轨迹扩展的贡献，揭示了验证器能力是动作采样收益的前提条件，而非采样宽度本身。

## 核心方法

### 方法参照系

本文问题属于 TTS 中验证器与奖励模型类别，但验证对象从最终答案或推理步骤迁移至环境交互动作。与标准流程的关键差异在于：验证发生在动作执行前，且候选动作来自同一交互历史下的并行采样，验证结果直接决定环境状态演化路径。

### 动作候选采样与验证机制

在交互历史 $h_t$ 下，生成器 $\pi$ 采样 $N$ 个候选动作 $\mathcal{A}_t = (a_t^1, \dots, a_t^N)$，验证器 $\psi$ 从中选择单一动作 $a_t^* = \text{Verify}_\psi(h_t, \mathcal{A}_t)$ 执行。该设计动机在于解决弱验证下增加采样宽度无效的问题：当验证器无法区分候选时，更多候选仅增加冗余计算而非成功率。

$$
a_t^* = \text{Verify}_\psi(h_t, \mathcal{A}_t) \in \mathcal{A}_t
$$

公式表明验证器输出必须是候选集的子集，确保执行动作来自生成器已产生的选项，避免引入未经验证的新动作。本文对比三种验证机制：Listwise（单次调用比较全部候选）、Pointwise（独立评分后取最大值）、Pairwise（两两比较后聚合胜率）。Pairwise 机制通过聚焦两个候选间的差异，为验证器提供共享参照，解决了 Pointwise 中独立评分难以比较不同目的动作的问题。

### 验证器蒸馏与成本优化

针对自验证能力不足，本文使用 GPT-5.6 Sol 的 117k 对比较响应，通过 LoRA 微调 TMAX-9B 作为验证器，仅激活于验证阶段而不改变生成器权重。该设计动机在于弥合前沿验证器与生成器模型间的验证能力差距，同时避免推理时调用前沿模型的高成本。

$$
\mathcal{L}_{\text{distill}} = \sum_{(i,j) \in \mathcal{C}} \left[ \log P_{\psi_{\text{dist}}}(J_{ij} | h_t, a_t^i, a_t^j) \right]
$$

公式表示蒸馏损失最小化验证器对教师模型偏好标签的预测误差。实验显示，蒸馏将 Pairwise 验证的 Pass@1 从 54.76% 提升至 57.14%，且决策-only 变体（仅输出 A/B 偏好）在 9B 模型上降低 20.9% 的 token 成本，表明有效验证不一定需要显式推理生成。

## 实验评估

| 配置 | Pass@1 (%) | Pass@3 (%) |
|---|---|---|
| Base agent | 50.00 | 69.39 |
| Mid-Harness (GPT-5.6 Sol, N=8) | 68.03 | – |
| Zero-shot Listwise (N=8) | 51.02 | 67.35 |
| Zero-shot Pairwise (N=8) | 54.76 | 71.43 |
| Distilled Pairwise (N=8) | 57.14 | 75.51 |
| Best-of-T (T=3) | 55.10 | – |
| Distilled MH + Best-of-T (T=3) | 66.33 | – |
| Distilled MH + SR (R=1) | 60.20 | 75.51 |

实验在 TerminalBench-Lite 上进行，使用 TMAX-9B 生成器与 Vanillux2 框架。基线覆盖轨迹级扩展（Best-of-T, SR）但缺失过程奖励模型（PRM）类方法，可能低估了动作级验证与 PRM 的协同潜力。核心发现是验证器质量决定采样收益：GPT-5.6 Sol 验证器将 Pass@1 从 50.00% 提升至 68.03%，而零样本 Listwise 验证下 $N=4$ 到 $N=8$ 仅提升 1.70 个百分点。

消融显示 Pairwise 机制优于 Listwise 和 Pointwise，蒸馏进一步提升 Pairwise 性能。反直觉发现是决策-only 验证在 9B 模型上优于推理验证，但在 4B 和 27B 模型上性能下降，表明验证器能力与任务复杂度存在交互效应。Mid-Harness 与轨迹扩展组合后，Distilled MH + Best-of-T (T=3) 达到 66.33% Pass@1，超过 Best-of-T (T=7) 且 token 成本约为其三分之一。

评估边界包括：仅使用 TerminalBench-Lite 单一基准，未覆盖更广泛的终端任务类型；Pass@3 在 Best-of-T 中未定义，限制了并行扩展的完整评估；代码未公开，LoRA 超参数与训练细节仅在附录中提供，可复现性受限。

## 关联研究分析

从问题动机看，本文与 Best-of-T 和 SR 的核心差异在于验证时机。Best-of-T 在轨迹完成后选择最优输出，SR 在轨迹间传递经验，两者均无法在动作执行前拦截错误。本文在模型-框架边界插入验证，使错误动作在执行前被替换，避免了环境状态的不可逆污染。这一差异源于代理任务的状态依赖性：推理任务中错误答案不影响后续计算，而代理任务中错误动作改变后续所有步骤的输入。

从方法设计看，本文 Pairwise 验证与过程奖励模型（PRM）的步骤评分相似，但验证对象是动作而非推理步。PRM 通常独立评分每个步骤，而 Pairwise 通过两两比较提供共享参照，解决了不同目的动作难以在统一尺度上比较的问题。然而，本文未探索 Pairwise 验证与 PRM 的融合，也未分析自验证偏差是否随任务复杂度增加而恶化。在 4B 和 27B 模型上决策-only 验证性能下降，暗示验证器能力与模型规模存在非线性关系，这一现象在 PRM 文献中未被充分讨论。

## 总结

本文核心矛盾是代理任务中动作执行的环境状态依赖性与现有 TTS 方法在轨迹完成后才验证的滞后性。Mid-Harness 通过固定生成器和框架，在模型-框架边界插入动作级采样与验证，揭示了验证器质量是动作扩展收益的决定因素。实验证明 GPT-5.6 Sol 验证器将 Pass@1 从 50.00% 提升至 68.03%，Distilled MH + Best-of-T (T=3) 达到 66.33% 且成本更低。边界在于自验证在命令语义和执行可行性判断上仍有 67.4% 的分歧，且仅在 TerminalBench-Lite 单一基准上验证。当任务复杂度增加或环境状态空间扩大时，Pairwise 自验证的偏差是否随轨迹长度增加而累积，论文未给出回答。
