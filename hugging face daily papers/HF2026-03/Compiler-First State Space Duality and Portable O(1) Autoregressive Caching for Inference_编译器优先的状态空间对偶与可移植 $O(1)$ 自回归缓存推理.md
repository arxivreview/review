> 导读 状态空间模型（State Space Models, SSMs）的发布通常与特定硬件的手写内核深度绑定，导致跨平台部署成本高昂。现有编译器路线受限于搜索空间爆炸与动态形状处理瓶颈，难以直接替代专家级 CUDA/Triton 内核。本文切入点在于利用状态空间对偶（State Space Duality, SSD）算法的代数性质，使其直接适配 XLA 编译器的融合与平铺通道。通过构建无手写内核的 JAX 实现并引入设备端缓存，本文在 TPU 上实现了接近带宽上限的推理性能。该工作验证了“算法适配编译器”路线在特定代数结构下的可行性，但其对静态控制流的依赖限制了向动态负载的扩展。

## 研究背景

当开发者试图将高性能 SSM 部署到非 NVIDIA 硬件时，往往面临内核移植的困境。SSM 的推理性能高度依赖融合 CUDA 或 Triton 内核，这些内核针对特定硬件的内存层级与并行模型进行了极致优化。然而，这种优化引入了硬性的硬件依赖，使得代码难以迁移至 AMD NPU 或 Google Cloud TPU 等异构加速器。传统编译器如 TVM 试图通过自动调度解决这一问题，但其搜索空间随硬件复杂度指数级增长，且难以处理运行时动态形状，导致生成的代码性能往往不及手写库。

这一矛盾在 Mamba-2 等现代 SSM 中尤为突出。Mamba-2 的 SSD 算法虽然具备可分块递归特性，但其参考实现仍依赖 Triton 内核。社区尝试将 Mamba-2 移植到 JAX/XLA 时，若不使用自定义内核，纯 JAX 实现因缺乏细粒度内存控制而性能低下。现有编译器基础设施如 PolyBlocks 或 Nova 虽在通用张量程序上表现优异，但未能针对 SSM 特有的对角状态结构与静态控制流进行专门适配。因此，如何在不编写底层内核的前提下，利用编译器自动优化实现接近手写库的 SSM 推理性能，成为跨硬件部署的关键瓶颈。

## 核心方法

### 方法参照系：编译器优先的代码生成范式

本文采用编译器优先（Compiler-First）范式，区别于 TVM 等基于搜索的自动调度路线。该范式不依赖启发式搜索或强化学习来探索调度空间，而是通过调整高层算法的代数结构，使其直接映射到编译器（如 XLA）已优化的标准原语序列上。本文问题与通用编译器流程的关键差异在于：通用流程需处理任意张量操作，而本文针对 SSD 算法的特定代数性质（对角状态、可分块递归、einsum 主导计算）进行定向适配，从而规避了搜索开销。

### 算法-编译器协同设计：Einsum 布局与静态掩码

在通用编译器流程中，张量操作通常被分解为独立的元素级运算与矩阵乘法，导致中间结果频繁写入内存。本文通过 Einsum 布局优化，将 SSD 的块内计算重构为批量收缩操作。设计动机在于消除元素级操作链的内存访问开销。具体而言，块内输出 $Y_{\text{diag}}$ 被表达为对轴 `(batch, chunk, seq, head, state)` 的单一 einsum 运算：

$$
Y_{\text{diag}} = (L \odot C_t B_t^\top) X_{\text{proj}}
$$

其中 $L$ 为下三角衰减矩阵，$C_t, B_t$ 为输入依赖的投影矩阵。该公式将原本分散的乘加操作合并为一次矩阵乘法，使 XLA 能够将其直接平铺到硬件矩阵单元上。同时，针对因果掩码，本文采用静态常量 `jnp.tril` 而非动态循环。这一选择使 XLA 能将掩码操作折叠进周围的融合链（如 `cumsum` $\rightarrow$ `exp`），避免了运行时分支破坏融合图，从而将多个内存遍历合并为单次访问。

### 设备端 $O(1)$ 缓存与编译时控制流

在自回归解码阶段，传统实现常使用主机端 Python 循环，导致每步生成产生主机-设备同步开销。本文设计动机在于消除这一同步瓶颈，实现真正的 $O(1)$ 状态更新。通过将缓存状态 `Mamba2Cache` 注册为 JAX PyTree 节点，本文利用 `jax.lax.fori_loop` 将解码循环完全编译至设备端。该结构允许 XLA 在编译时确定控制流，将状态更新操作（如卷积状态滚动与 SSM 状态递推）融合进单一内核。这一创新使得缓存状态在设备内存中保持恒定，无需主机干预，从而在序列长度增加时保持恒定的每步延迟。

## 实验评估

实验在 Google Cloud TPU v6e 上进行，评估了 130M 至 2.7B 参数规模的 Mamba-2 模型。基线对比包括非缓存 JAX 实现及 PyTorch/CUDA 参考实现。由于知识库中缺乏 TPU 上的直接可比 SOTA，本文主要评估硬件利用率与正确性。

| 模型规模 | Prefill MFU (%) @ 4096 tokens | Decode HBU (%) @ 4096 tokens |
| :--- | :--- | :--- |
| 130M | 11.33 | 53.32 |
| 780M | 11.67 | 62.99 |
| 2.7B | 12.96 | 64.08 |

在 2.7B 模型上，Prefill 阶段达到 12.96% 的模型浮点运算利用率（Model FLOPs Utilization, MFU），Decode 阶段达到 64.08% 的硬件带宽利用率（Hardware Bandwidth Utilization, HBU）。15% 左右的 MFU 符合单序列预填的 Roofline 上限，因为饱和计算需约 574 FLOPs/byte，而 batch size 1 未达到该阈值。64% 的 HBU 表明解码路径已接近带宽饱和。

消融实验揭示了关键设计决策的影响。将静态掩码替换为动态行掩码导致 Prefill 吞吐量从 42,631 tokens/s 下降至 7,330 tokens/s，降幅达 82.8%，证实了静态掩码对保持融合链完整性的必要性。此外，将衰减指数计算从 `float32` 降级为 `bfloat16` 导致最大绝对误差达到 0.013，足以影响下游采样，验证了高精度数值控制的必要性。

评估边界方面，本文仅报告了 TPU v6e 上的利用率，未覆盖 GPU 或 CPU 的细粒度性能差异。此外，实验固定块大小 $L=256$ 且 batch size 为 1，未评估动态形状或高吞吐批量服务场景下的性能扩展性。

## 关联研究分析

从问题动机看，本文与 Nova（Suresh et al., 2026）均关注编译器优化，但 Nova 侧重动态形状与数据并行同步，通过结构哈希缓解重编译开销；本文则通过固定块大小和静态控制流规避动态形状问题，侧重静态图下的极致融合。这一差异源于任务特性：SSM 的递归结构允许通过分块将动态序列转化为静态矩阵运算，而 Nova 处理的通用训练负载难以完全静态化。

从方法设计看，本文与 Triton（Tillet et al., 2019）路线形成对比。Triton 通过 Tile 抽象降低编程门槛，但仍需开发者显式定义 Tile 大小与内存布局；本文则完全消除 Tile 抽象，依赖 XLA 自动平铺。这一策略在 SSD 的代数结构下有效，因为 einsum 主导的计算模式天然适配矩阵单元。然而，对于非对角状态或数据依赖控制流的 SSM 变体，该策略是否仍有效，论文未给出回答。

## 总结

本文针对 SSM 部署中的硬件锁定问题，提出了一种编译器优先的实现范式。通过利用 SSD 算法的对角状态与可分块特性，本文将其映射为 XLA 友好的标准原语，并实现了设备端 $O(1)$ 缓存。实验表明，该实现在 TPU 上达到了 64% 的解码带宽利用率，且贪心解码与 CUDA 参考实现逐 token 匹配。然而，该方法依赖静态控制流与固定块大小，限制了其在动态形状或高吞吐批量服务场景下的适用性。当序列长度或 batch size 显著增加时，静态编译的灵活性不足是否会成为新的性能瓶颈，仍有待验证。
