# HuggingFace最新推荐论文 ｜s2n-bignum-bench: A practical benchmark for evaluating low-level code reasoning of LLMs ｜工业级底层代码形式化验证基准

研究机构：美国史蒂文斯理工学院

作者：Balaji Rao、John Harrison、Soonho Kong 等 5 人

论文原文见 [arXiv](https://arxiv.org/abs/2603.14628)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2603.14628)

> 现有 LLM 定理证明基准集中于数学竞赛题，无法评估模型对真实工业代码的验证能力，且面临基准饱和与数据污染风险。本文从 AWS 生产级加密库 s2n-bignum 中提取 2,284 个 HOL Light 证明义务，构建了首个针对底层汇编代码的机器可验证基准。通过内联上下文隔离、类型注解混淆及防作弊机制，该基准提供了离线、可复现的评估管道。其价值在于填补了 ISA 感知推理的评测空白，但当前仅以单轮生成模型为基线，缺乏与智能体框架及强化学习方法的对比，导致其作为能力上限探针的有效性尚存疑。

## 研究背景

交互式定理证明器（ITP）如 Lean 4 和 HOL Light 通过小型可信内核验证逻辑推导，确保证明的机器可验证性。在安全关键领域，自然语言推理的幻觉不可接受，因此 ITP 内核成为正确性的唯一标准。然而，LLM 在 ITP 中的表现长期受限于基准任务域：主流基准如 MiniF2F 和 PutnamBench 聚焦于抽象数学定理，其解题过程不涉及架构状态、别名或字节序等底层代码特有的语义约束。

该领域正经历从“竞赛数学”向“研究级验证”的范式转移。早期工作将证明生成视为序列建模，但长程依赖导致的幻觉使其在复杂结构上失效；随后引入强化学习（RL）与智能体框架，通过验证器反馈和多轮工具调用提升鲁棒性。然而，这些进展主要发生在 Lean 4 生态中，且任务对象多为高层软件验证条件或数学命题。VeriSoftBench 等基准虽拓展至仓库级验证，但仍缺乏对底层汇编指令序列的覆盖。s2n-bignum-bench 的切入点在于：现有基准无法区分模型是掌握了通用逻辑推理，还是仅能处理抽象数学符号，它通过引入部署级加密库的汇编证明，测试 LLM 在位精确、ISA 感知环境下的形式化推理能力。

## 核心方法

### 基准构建与任务隔离

本文基准构建流程区别于传统数学基准的“陈述-证明”对，而是从生产代码库中提取“上下文-查询”任务。s2n-bignum 库包含 x86/ARM 汇编子程序及其 HOL Light 证明，每个证明义务被封装为独立的 OCaml/HOL Light 环境。

$$
\text{Task}_i = (\mathcal{C}_i, q_i, \text{id}_i)
$$

其中 $\mathcal{C}_i$ 为内联的自包含上下文（包含定义、常量及已证引理），$q_i$ 为待证目标，$\text{id}_i$ 为形如 `arch.filename.thm.N` 的唯一标识符。该设计动机在于解决底层代码证明中依赖关系复杂的问题：通过内联相关 OCaml 模块并移除原始证明体（替换为 `CHEAT TAC` 占位符），模型必须在隔离环境中重新推导证明，避免了直接记忆或检索原始证明体的捷径，确保了评估的是合成能力而非检索能力。

### 完整性与抗污染机制

针对 LLM 可能通过引入公理或记忆化答案作弊的问题，本文设计了多层防御机制。首先，评估脚本检查 HOL Light 的 `axioms()` 函数输出，若提交前后公理列表发生变化，则判定为“CHEATING”。其次，为防止类似 SQL 注入的语法攻击，系统调用 OCaml 解析器验证提交表达式是否为单一有效表达式。

$$
\text{Verdict} = \begin{cases}
\text{OK} & \text{if } \text{kernel}(\mathcal{C}_i, p_i) = \text{thm} \land \Delta \text{axioms} = \emptyset \\
\text{CHEATING} & \text{if } \Delta \text{axioms} \neq \emptyset \lor p_i \text{ contains } \text{CHEAT TAC} \\
\text{FAIL} & \text{otherwise}
\end{cases}
$$

该机制解决了传统基准中“看似正确但逻辑无效”的提交难以自动检测的问题。此外，为缓解数据污染，本文采用类型注解混淆（Type-Annotation Obfuscation），将 HOL Light 子项打印模式设为最详细级别并重新打印查询。虽然该机制仅对约 70% 的问题集有效（受限于 HOL Light 打印器与解析器的 Pollack 一致性），但它显著增加了模型直接匹配训练数据中定理陈述的难度，迫使模型依赖语义理解而非模式匹配。

## 实验评估

实验设置采用 GPT-5.3-Codex 通过 codex-cli 进行单轮生成，分为 medium-effort 和 high-effort 两种配置。基线审计显示，本文仅测试了单一商业模型，未包含知识库中 SOTA 的智能体框架（如 Hilbert、OProver）或经过 RL 微调的开源模型（如 DeepSeek-Prover-V2），这限制了结果的可比性。

| 模型 | 配置 | 证明完成率 (%) |
| :--- | :--- | :--- |
| GPT-5.3-Codex | Medium-effort | 4.4 |
| GPT-5.3-Codex | High-effort | 5.3 |

GPT-5.3-Codex 在完整基准上的二进制证明完成率仅为 4.4%（medium）和 5.3%（high），这一极低数值表明当前 LLM 在底层汇编验证任务上存在显著能力缺口。与 MiniF2F 上 Hilbert 达到的 99.2% 准确率相比，s2n-bignum-bench 的难度呈数量级差异，主要源于 ISA 语义的复杂性和证明步骤的位精确要求。

消融方面，high-effort 配置较 medium-effort 仅提升 0.9 个百分点，边际收益递减，暗示单纯增加推理预算无法解决底层代码证明的结构复杂性。设计决策上，类型注解混淆机制虽仅覆盖 70% 问题，但论文未报告混淆前后基线性能的对比数据，无法量化该机制对防止记忆化作弊的实际贡献。

评估边界方面，本文未报告置信区间，且仅基于单一模型单轮生成，缺乏统计显著性检验。可复现性上，论文提供了离线评估管道和独立工件，但 HOL Light 环境的版本锁定（commit 9912d17...）可能限制其他 ITP 用户的迁移性。

## 关联研究分析

从问题动机看，s2n-bignum-bench 与 VeriSoftBench 均旨在突破数学基准的饱和，但任务域存在本质差异。VeriSoftBench 聚焦于 Lean 4 仓库级软件验证，其证明对象多为高层 API 或模块接口，依赖 Lean 强大的类型系统和自动化战术；而 s2n-bignum-bench 下沉至汇编指令序列，要求模型处理寄存器状态、内存别名和字节序等底层语义。这种差异源于任务特性：底层代码验证需要 ISA 感知的符号执行能力，而高层验证更依赖类型推断和抽象解释。论文未探索智能体框架在此任务中的表现，这可能是一个盲区，因为底层证明往往需要多轮状态查询和错误修正，单轮生成难以应对。

从方法设计看，本文的上下文隔离策略与 LeanSearch v2 的迭代检索形成对比。LeanSearch v2 通过动态检索 Mathlib 中的引理来降低搜索空间，适用于大规模库环境；而 s2n-bignum-bench 采用静态内联上下文，牺牲了检索灵活性以换取环境隔离和可复现性。这种设计选择反映了底层代码验证中依赖关系相对封闭的特点：汇编证明通常仅依赖少量 ISA 定义和局部引理，无需大规模库检索。然而，静态上下文可能限制了模型利用全局库知识的能力，查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

本文旨在解决 LLM 定理证明评估中“数学能力”与“工程验证能力”脱节的核心矛盾。现有基准如 MiniF2F 已饱和且无法反映工业场景，而 VeriSoftBench 等虽拓展至软件验证，但未覆盖底层汇编。s2n-bignum-bench 通过从生产级加密库提取 2,284 个 HOL Light 证明义务，构建了首个针对 ISA 感知、位精确推理的机器可验证基准。实验显示 GPT-5.3-Codex 在该基准上的完成率仅为 4.4%-5.3%，揭示了当前 LLM 在底层代码验证上的巨大能力缺口。然而，本文的边界在于仅以单轮生成模型为基线，缺乏与智能体框架及 RL 方法的对比，且类型注解混淆机制的有效性未量化。当引入多轮工具调用和迭代修正机制时，该基准上的性能提升幅度是否足以证明智能体框架在底层代码验证中的必要性，论文未给出回答。
