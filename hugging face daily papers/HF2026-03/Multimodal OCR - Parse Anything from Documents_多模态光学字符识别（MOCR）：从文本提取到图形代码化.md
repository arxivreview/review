# HuggingFace最新推荐论文 ｜Multimodal OCR: Parse Anything from Documents ｜多模态光学字符识别（MOCR）：从文本提取到图形代码化

研究机构：华中科技大学

作者：Handong Zheng、Yumeng Li、Kaile Zhang 等 25 人

论文原文见 [arXiv](https://arxiv.org/abs/2603.13032)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2603.13032)

> 文档解析长期面临“文本中心”的局限，即图形元素被裁剪为像素而非结构化数据，导致语义信息丢失。现有端到端视觉语言模型（VLM）虽解决了文本识别的误差累积，但仍未将图表、图标等视觉符号视为一等解析目标，限制了多模态预训练监督信号的规模与质量。MOCR 提出将文档中所有信息承载元素（含图形）统一解析为可执行代码（如 SVG），通过 3B 参数模型实现文本与图形的联合结构化输出。该范式在 olmOCR-Bench 上刷新了开源模型 SOTA，但在通用 VLM 对比中仍落后于 Gemini 3 Pro，其核心价值在于解锁了图形代码作为新数据源的可能性，而非单纯提升解析精度。

## 研究背景

文档解析的核心困境在于视觉信息的“有损压缩”。传统流水线将版面分析、OCR 与阅读顺序预测串联，虽便于调试，但模块间误差累积导致复杂布局解析失败。随着视觉 Transformer 的成熟，Donut 等模型确立了端到端范式，直接映射图像到文本，消除了中间模块的误差传递。然而，这一范式仍隐含“文本中心”假设：非文本元素（图表、流程图、UI 组件）被视为“图形区域”，仅被裁剪为像素或简单描述，其内部的空间结构、数值关系与几何语义在文本化过程中被丢弃。这种有损性使得文档中蕴含的大量结构化监督信号（如图表中的坐标轴、图标中的矢量路径）无法被下游任务复用。

领域共识认为，端到端 VLM 在单页解析上已超越模块化流水线，尤其在保留布局语义方面具有优势。但现有方法（如 MinerU2.5、PaddleOCR-VL）主要优化文本与表格的识别精度，对图形的处理仍停留在“检测-裁剪”层面，缺乏将图形转化为可编辑、可执行代码的能力。MOCR 的切入点在于重新定义解析目标：不仅提取文本，还将图形解析为可渲染的 SVG 代码。这一转变将文档解析从“信息读取”升级为“结构重建”，使得图形元素成为可复用的代码级监督信号，为多模态预训练提供了新的数据引擎。

## 核心方法

### 方法参照系

MOCR 延续了端到端 VLM 的架构范式，即“视觉编码器-连接器-语言解码器”的三段式结构。与 MinerU2.5 等仅输出 Markdown 文本的方法不同，MOCR 的关键差异在于解码目标：语言模型需生成包含文本转录与图形代码（SVG）的统一序列，而非仅处理文本 token。

### 统一解析任务定义

MOCR 将文档解析建模为有序元素序列生成问题。给定输入图像 $I$，模型生成序列 $S = \{(B_k, c_k, p_k)\}_{k=1}^N$，其中 $B_k$ 为边界框，$c_k$ 为语义类别，$p_k$ 为内容载荷。对于文本区域，$p_k$ 为转录文本；对于图形区域，$p_k$ 为可渲染的 SVG 代码。

$$
S = \text{Decode}(I, \text{task}) = \bigcup_{k=1}^N \left( \text{Box}(B_k), \text{Type}(c_k), \text{Payload}(p_k) \right)
$$

该公式的物理含义是：模型通过自回归解码，将视觉输入转化为结构化的“框-类型-内容”三元组序列。设计动机在于解决传统 OCR 中图形信息丢失的问题——通过将图形编码为 SVG，模型不仅识别了“这是什么图”，还重建了“图长什么样”，从而保留了空间与数值语义。

### 图形代码化训练策略

针对 SVG 代码的非唯一性（不同代码可渲染相同图像）与监督数据稀缺问题，MOCR 采用分阶段训练与数据引擎策略。训练分为三阶段：第一阶段建立视觉-语言接口；第二阶段混合通用视觉与文本解析数据；第三阶段增加图形解析权重，强化图像到 SVG 的映射。

$$
\mathcal{L}_{\text{total}} = \sum_{i=1}^{3} \lambda_i \mathcal{L}_{\text{stage}_i} + \mu \mathcal{L}_{\text{svg\_norm}}
$$

其中 $\mathcal{L}_{\text{svg\_norm}}$ 为 SVG 规范化损失，通过 `svgo` 工具对代码进行元数据清理、数值精度标准化与去重，确保训练目标的一致性。该设计解决了图形监督数据稀疏且非唯一的难题，使 3B 参数模型能在有限数据下稳定学习复杂的图形结构生成。

## 实验评估

实验在 olmOCR-Bench、OmniDocBench 1.5 与 XDocParse 上进行，基线涵盖 Gemini 3 Pro、MinerU2.5、PaddleOCR-VL 等主流模型。MOCR 在 olmOCR-Bench 上取得 83.9 的 Overall 分数，超越 olmOCR v0.4.0 的 82.4 与 MinerU2.5 的 75.2，但在 OmniDocBench 1.5 的 Elo 评分（1059.0）上低于 Gemini 3 Pro（1128.0）。

| 模型 | olmOCR-Bench Overall | OmniDocBench 1.5 Elo | XDocParse Elo |
| :--- | :--- | :--- | :--- |
| Gemini 3 Pro | - | 1128.0 | 1323.7 |
| dots.mocr | 83.9 | 1059.0 | 1210.7 |
| olmOCR v0.4.0 | 82.4 | - | - |
| MinerU2.5 | 75.2 | - | - |

在图形解析任务上，dots.mocr-svg 在 UniSVG 基准上取得 0.902 的 Score，显著高于 Gemini 3 Pro 的 0.735，验证了专用训练在图形代码生成上的优势。消融实验显示，增加 SVG 数据权重（dots.mocr-svg）提升了图形解析性能，但对文本解析影响较小，表明多任务学习中存在良好的任务解耦性。

评估边界方面，OCR Arena 采用 LLM-as-a-Judge 范式，虽解决了 NED 对非唯一序列化的敏感性问题，但依赖 Gemini 3 Flash 作为裁判，存在裁判模型偏差风险。代码已开源，但 1.2B 视觉编码器从头训练的计算成本未在论文中详细披露，限制了复现性。

## 关联研究分析

从问题动机看，MOCR 与 OCRVerse 均试图统一多任务解析，但 OCRVerse 依赖提示工程在单一 VLM 中切换任务，而 MOCR 通过专用训练将图形解析内化为模型能力。这一差异源于任务特性：图形代码生成需要精确的视觉定位与长序列结构化输出，提示工程难以提供足够的监督信号，而 MOCR 的数据引擎通过大规模 SVG 对提供了显式监督。

从方法设计看，MOCR 与 StarVector 同属图像到 SVG 方向，但 StarVector 聚焦图标等简单图形，MOCR 扩展至复杂图表与文档布局。MOCR 的 3B 参数规模挑战了“大模型必要论”，证明在专用任务上，小模型配合高质量数据引擎可超越通用大模型。然而，MOCR 未解决长文档跨页推理问题，其单页解析结果如何整合至 RAG 系统，论文未给出回答。

## 总结

MOCR 的核心矛盾在于文档图形信息的有损压缩与多模态预训练对结构化监督的需求。现有端到端 VLM 仅处理文本，丢弃图形语义，而 MOCR 通过生成 SVG 代码将图形转化为可复用数据，凭借 3B 参数模型与专用数据引擎实现了这一转变。实验证明其在 olmOCR-Bench 上达到 83.9 的 SOTA，图形解析性能超越 Gemini 3 Pro。其边界在于单页解析假设，未涉及长文档跨页证据聚合，且依赖 LLM 裁判的评估协议存在潜在偏差。当文档规模扩展至数百页时，MOCR 的图形代码如何与文本检索协同工作，以解决证据稀疏问题，仍是待验证的关键问题。
