> 软件工程智能体（SWE Agent）在推理时注入结构化技能文档（Agent Skills）已成为提升任务解决率的主流手段，但现有基准无法量化这种“上下文增强”的边际贡献。SWE-Skills-Bench 通过构建需求驱动的配对评估框架，将技能注入视为独立变量，在固定智能体配置下隔离其效用。该基准揭示了技能效用的极端异质性：多数技能仅改变推理路径而不改变结果，少数技能甚至因版本冲突导致性能退化。这一发现挑战了“技能即增益”的默认假设，但受限于单一模型配置，其结论对多智能体架构的泛化性存疑。

## 研究背景

当智能体面对复杂仓库级任务时，仅依赖模型参数内的知识往往不足以覆盖特定领域的工程惯例。Agent Skills 作为推理时注入的结构化 Markdown 包，编码了标准操作流程、代码模板及领域约定，旨在弥补模型在特定技术栈上的知识缺口。然而，技能注入并非无成本：它占用有限的上下文窗口，可能引入与当前任务不匹配的约束，甚至干扰模型原有的推理逻辑。这种“增强”与“干扰”的潜在冲突，使得技能的实际效用难以通过简单的端到端性能提升来评估。

现有 SWE 基准如 SWE-bench 和 TerminalBench 聚焦于评估智能体在真实仓库中的补丁生成能力，但均未将“技能文档”作为受控变量纳入评估体系。SkillsBench 虽引入了技能条件，但其任务集仅 16% 涉及软件工程，且缺乏针对需求满足度的细粒度验证。这导致领域内缺乏一个能够回答“技能是否真正帮助智能体满足任务需求”的专用基准。SWE-Skills-Bench 的切入点在于将评估对象从“智能体能力”转向“技能效用”，通过需求驱动的确定性验证，建立从需求文档到测试判定的完整追溯链，从而在控制变量下量化技能注入的边际贡献。

## 核心方法

### 需求驱动验证框架

SWE-Skills-Bench 的核心创新在于将软件工程任务重构为需求满足问题，而非单纯的代码生成问题。传统基准依赖预定义的测试套件，而本文要求每个任务实例锚定于一份包含明确验收标准（Acceptance Criteria）的需求文档 $P$。验证器不再直接运行预置测试，而是由 LLM 基于 $P$ 中的验收标准自动生成确定性 `pytest` 单元测试。这一设计确保了测试用例与需求的一一对应，使得“通过”不仅意味着代码可运行，更意味着需求被满足。该框架解决了现有基准中测试与需求脱节、无法区分“代码正确”与“需求满足”的问题。

### 配对技能效用隔离

在固定智能体（Claude Code + Claude Haiku 4.5）和固定仓库环境 $E$ 下，本文采用配对实验设计隔离技能 $S$ 的效用。对于技能 $s$ 关联的任务集 $T_s = \{t_1, ..., t_N\}$，定义技能效用增量 $\Delta P$ 为有技能与无技能条件下的通过率之差：

$$ \Delta P(s) = \frac{1}{N} \sum_{i=1}^{N} (v_i^+ - v_i^-) $$

其中 $v_i^+, v_i^- \in \{0, 1\}$ 分别为有/无技能时任务 $t_i$ 的二值判定。该公式直接量化了技能对任务成功率的边际贡献。同时，引入成本效率指标 $CE(s)$ 联合评估性能增益与 Token 开销：

$$ CE(s) = \frac{\Delta P(s)}{\rho(s)} $$

其中 $\rho(s)$ 为 Token 开销比率。$CE$ 值揭示了技能增益是否值得其推理成本，解决了单一通过率指标无法反映计算效率的问题。

## 实验评估

实验在 Docker 容器（Ubuntu 24.04, CPU-only）中进行，智能体固定为 Claude Code 搭配 Claude Haiku 4.5。基线为“无技能”条件，未对比其他智能体架构或训练方法，这限制了结论对多智能体系统的泛化性。主实验结果显示，49 个技能中 39 个（约 80%）的 $\Delta P = 0$，平均通过率仅提升 +1.2%。

| 技能类型 | 代表技能 | $\Delta P$ (%) | $\rho$ (%) | 特征 |
|---|---|---|---|---|
| 零增益高开销 | `service-mesh-observability` | 0.0 | +450.8 | 推理路径改变，结果不变 |
| 零增益低开销 | `python-resilience` | 0.0 | -77.6 | 引导更直接路径 |
| 正增益 | `risk-metrics-calculation` | +30.0 | -34.8 | 提升正确性且降低成本 |
| 负增益 | `springboot-tdd` | -10.0 | -36.8 | 版本冲突导致干扰 |

消融分析揭示了 Token 开销与正确性的解耦现象：在 24 个双条件 100% 通过的技能中，$\rho$ 范围从 -77.6% 到 +450.8%。这表明技能注入重塑了推理路径，但未必改变最终结果。例如，`service-mesh-observability` 导致 Token 消耗激增 450.8%，但通过率未变；而 `python-resilience` 使 Token 消耗减少 77.6%，同样未影响通过率。这种解耦暗示技能对推理效率的影响机制独立于其对正确性的影响机制。

评估边界方面，本文仅使用单一模型配置，未探索不同 LLM 对技能效应的敏感性。代码已开源，但需求文档的生成依赖 LLM 提示工程，可能存在偏差。此外，565 个任务实例虽覆盖六个子域，但样本量相对较小，统计显著性未报告。

## 关联研究分析

从问题动机看，SWE-Skills-Bench 与 SWE-bench 存在根本差异：后者评估智能体在真实 Issue 上的端到端解决能力，前者评估技能文档对固定智能体的边际效用。SWE-bench 的“执行接地”验证关注代码是否通过测试，而本文的“需求驱动”验证关注代码是否满足需求文档中的验收标准。这一差异源于任务定义的不同：SWE-bench 假设测试套件是需求的完整编码，而本文认为需求文档是更上游的约束，测试仅是其可执行编码。这种视角转换使得本文能够识别出“代码通过测试但未满足需求”的潜在情况，尽管在本文实验中两者高度一致。

从方法设计看，SWE-Skills-Bench 与 SkillsBench 形成互补。SkillsBench 是跨域基准，旨在评估技能作为一等公民的通用效用，其 SWE 任务占比仅 16%；SWE-Skills-Bench 则是 SWE 专用基准，通过固定仓库和固定智能体，更严格地隔离技能变量。SkillsBench 未采用需求驱动的验证，而是依赖通用测试，这可能导致其无法捕捉 SWE 任务中特有的需求满足细节。本文的配对设计（With/Without Skill）比 SkillsBench 的多技能条件对比更简洁，但牺牲了对技能间交互效应的探索。

## 总结

SWE-Skills-Bench 解决了技能效用评估中“增强”与“干扰”难以区分的问题，通过需求驱动验证和配对实验设计，量化了技能注入的边际贡献。实验证明，技能效用高度依赖领域特异性：39/49 技能零增益，7 个技能带来最高 +30% 提升，3 个技能导致最高 -10% 退化。该基准的边界在于其结论基于单一模型配置（Claude Haiku 4.5），未验证技能效应在不同 LLM 或智能体架构下的稳定性。当智能体具备更强的上下文管理能力或自我修正机制时，技能注入的干扰风险是否会降低，本文未给出回答。
