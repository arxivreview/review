# HuggingFace最新推荐论文 ｜MA-EgoQA: Question Answering over Egocentric Videos from Multiple Embodied Agents ｜多智能体第一人称视频问答基准与检索基线

研究机构：韩国科学技术院、美国纽约大学

作者：Kangsan Kim、Yanlai Yang、Suji Kim 等 7 人

论文原文见 [arXiv](https://arxiv.org/abs/2603.09827)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2603.09827)

> 多智能体系统级理解要求模型在多个并行长时程第一人称视频流中定位跨智能体的关联事件，现有单智能体记忆架构无法处理这种跨视角的时间对齐与证据聚合。本文构建了首个针对该场景的基准 MA-EgoQA，并提出无训练基线 EgoMAS，通过事件基共享记忆与智能体级动态检索实现系统级推理。该方法在 Gemini-2.5-Flash 骨干下取得 41.41% 准确率，显著优于全量拼接基线，但距离 Oracle 设置仍有巨大差距，揭示了当前模型在多智能体心智理论推理上的根本局限。

## 研究背景

当多个具身智能体在共享环境中连续运行数天，每个智能体产生独立的第一人称视频流，系统需回答涉及多个智能体、多个时间戳的查询。这种场景要求模型不仅理解单个智能体的历史，还需构建跨智能体的全局时间线，并推断其他智能体的信念与意图。传统第一人称视频理解基准如 EgoLife 仅支持单智能体查询，无法评估这种系统级理解能力。

现有方法在处理多智能体长视频时面临两个瓶颈：一是上下文窗口限制，直接拼接所有智能体的视频帧或字幕会导致无关信息干扰，且计算成本过高；二是检索机制缺失，单智能体记忆架构（如 EgoRAG）无法处理跨智能体的证据链接。本文切入点在于定义多智能体第一人称视频问答任务，并验证检索机制在该场景下的必要性，而非依赖全量上下文。

## 核心方法

### 方法参照系

本文问题可视为多智能体场景下的检索增强生成（RAG）任务。标准 RAG 流程为：存储文档片段 → 根据查询检索相关片段 → 基于检索结果生成答案。本文的关键差异在于：存储单元是跨智能体的事件片段，检索需针对每个智能体生成特定查询，且答案需整合多个智能体的证据。

### 事件基共享记忆

**设计动机**：解决多智能体视频流的时间对齐与全局状态估计问题，避免直接拼接导致的无关信息干扰。

EgoMAS 将每个智能体的视频流划分为 10 分钟窗口，为每个窗口生成包含时间、地点、人物、动作、原因（4W1H）的事件摘要。所有智能体的事件摘要存入共享记忆库，形成系统级全局状态。该记忆结构支持跨智能体的时间对齐，例如查询“谁在 Day 5 最后使用纸巾”时，系统可检索所有智能体在 Day 5 的相关事件。

$$
M = \bigcup_{i=1}^{N} \{ (t_j, l_j, p_j, a_j, r_j) \mid t_j \in [t_{start}, t_{end}] \}
$$

其中 $M$ 为共享记忆库，$N$ 为智能体数量，$(t_j, l_j, p_j, a_j, r_j)$ 为第 $j$ 个事件的时间、地点、人物、动作、原因。该公式表示共享记忆是所有智能体事件摘要的并集，支持跨智能体的时间对齐与状态查询。

### 智能体级动态检索

**设计动机**：解决全局统一查询在多智能体场景下的低效问题，减少无关信息干扰。

EgoMAS 在接收查询后，首先生成全局查询，然后针对每个智能体生成特定查询。例如，查询“谁在厨房烹饪”时，系统为智能体 A1 生成“厨房烹饪”查询，为智能体 A2 生成“厨房活动”查询。检索过程使用 BM25 算法，从每个智能体的记忆中检索相关事件。

$$
R_i = \text{BM25}(q_i, M_i)
$$

其中 $R_i$ 为智能体 $i$ 的检索结果，$q_i$ 为针对智能体 $i$ 生成的查询，$M_i$ 为智能体 $i$ 的记忆片段。该公式表示每个智能体的检索是独立的，查询侧针对智能体特性进行优化，而非使用全局统一查询。

## 实验评估

实验在 MA-EgoQA 基准上进行，包含 1,741 个五选一问题，覆盖社交互动、任务协调、心智理论、时间推理、环境交互五个类别。基线包括全量拼接（Gemini-2.5-Flash、GPT-5、Qwen2.5-VL-7B）、RAG（BM25、DPR、VideoRAG）及单智能体方法（EgoRAG）。EgoMAS 使用 Gemini-2.5-Flash、Qwen3VL-8B-Thinking、Qwen3VL-8B-Instruct、Qwen2.5VL-7B-Instruct 四种骨干。

| 方法 | 骨干 | 准确率 (%) |
| :--- | :--- | :--- |
| Gemini-2.5-Flash (全量拼接) | Gemini-2.5-Flash | 36.93 |
| GPT-5 (全量拼接) | GPT-5 | 34.81 |
| BM25 (RAG) | Qwen3-VL-8B-Instruct | 36.01 |
| EgoMAS | Gemini-2.5-Flash | 41.41 |
| EgoMAS | Qwen3VL-8B-Thinking | 40.26 |
| Oracle | Gemini-2.5-Flash | 83.80 |

EgoMAS (Gemini-2.5-Flash) 比全量拼接基线高 4.48%，且 Qwen3VL-8B 骨干的 EgoMAS 性能超过 Gemini-2.5-Flash 全量拼接基线，表明检索机制比扩大上下文窗口更有效。Oracle 设置（83.80%）与 EgoMAS（41.41%）的巨大差距，主要源于检索失败而非推理能力不足，因为 Oracle 使用生成问题时的完整上下文，而 EgoMAS 仅使用检索到的片段。

消融实验显示，EgoMAS 的延迟仅为 1.3 秒/查询，远低于全量拼接基线（>10 秒），表明检索机制在效率与精度间取得平衡。BM25 在多智能体场景下优于 DPR（36.01% vs 26.19%），挑战了向量检索的优越性假设，可能因视频帧检索的高噪声所致。

评估边界：MA-EgoQA 为离线批量处理，非实时流式；未报告置信区间；代码开源（https://ma-egoqa.github.io），但超参数（n=20, k=5, τ=10）未详细讨论。

## 关联研究分析

从问题动机看，EgoLifeQA 仅支持单智能体查询，而 MA-EgoQA 要求跨智能体推理。EgoLifeQA 的局限性在于无法评估系统级理解，而 MA-EgoQA 通过多智能体查询揭示了这一差距。本文的切入点在于将单智能体记忆架构扩展至多智能体场景，但 EgoLifeQA 未提供跨智能体的时间对齐机制，导致其无法处理多智能体查询。

从方法设计看，EgoRAG 使用单智能体记忆，而 EgoMAS 使用事件基共享记忆。EgoRAG 在多智能体场景下性能下降（19.57%），因其无法处理跨智能体的证据链接。EgoMAS 的智能体级动态检索针对每个智能体生成特定查询，减少了无关信息干扰，但 BM25 的简单文本检索在多智能体场景下表现强劲，暗示视频帧检索的高噪声可能是主要瓶颈。

## 总结

本文要解决的核心矛盾是多智能体长时程视频流中的系统级理解与检索效率。现有单智能体记忆架构无法处理跨智能体的时间对齐与证据聚合，而全量拼接基线因无关信息干扰与计算成本过高而失效。本文通过事件基共享记忆与智能体级动态检索，在 Gemini-2.5-Flash 骨干下取得 41.41% 准确率，比全量拼接基线高 4.48%。本文的边界在于 Oracle 设置与 EgoMAS 的巨大差距（83.80% vs 41.41%），表明检索机制仍是主要瓶颈。当检索精度提升至 Oracle 水平时，多智能体心智理论推理的准确率是否接近 83.80%，论文未给出回答。
