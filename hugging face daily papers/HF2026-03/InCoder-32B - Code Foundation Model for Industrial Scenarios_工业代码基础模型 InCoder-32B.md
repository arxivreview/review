# HuggingFace最新推荐论文 ｜InCoder-32B: Code Foundation Model for Industrial Scenarios ｜工业代码基础模型 InCoder-32B

研究机构：北京航空航天大学、上海交通大学

论文原文见 [arXiv](https://arxiv.org/abs/2603.16790)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2603.16790)

> 工业软件开发要求代码在特定硬件约束下具备语义与性能双重正确性，而通用代码大语言模型（Large Language Models, LLMs）在此类场景下表现显著退化。现有方法依赖通用语料预训练，缺乏对硬件仿真环境的闭环验证，导致生成代码无法通过综合或执行测试。InCoder-32B 通过构建真实工业仿真环境生成执行反馈数据，并采用三阶段训练流程，实现了芯片、GPU、嵌入式等多领域工业代码的统一生成。该模型在工业基准上确立了开源最强基线，但其通用能力是否因工业数据挤占而退化，仍需进一步验证。

## 研究背景

工业代码的正确性无法仅通过静态语法检查确立，必须依赖特定硬件环境的执行验证。例如，Verilog 模块需通过 RTL 仿真与逻辑综合，CUDA 内核需在 GPU 上执行并验证数值精度。这种对执行环境的强依赖构成了工业代码生成的核心约束，使得通用代码模型因缺乏领域特定的执行反馈信号而失效。

通用代码生成领域已确立预训练-微调范式，并通过执行反馈（如单元测试）提升正确性。然而，现有方法主要面向算法实现与 Web 开发，对硬件描述语言、GPU 内核优化等工业场景覆盖不足。最强模型在 Triton 算子生成上的调用成功率仅为 28.80%，在 Verilog 形式等价检查中的准确率仅为 33.3%。InCoder-32B 的切入点在于将执行反馈源从软件单元测试扩展至真实硬件仿真环境，通过重建工业工具链生成高保真训练数据，弥合通用代码智能与工业工程需求之间的鸿沟。

## 核心方法

### 方法参照系

本文问题属于特定领域代码生成，其标准流程为：领域语料预训练、指令微调、执行反馈验证。与通用代码生成的关键差异在于，验证环节必须绑定真实硬件仿真器（如 Icarus Verilog、NVIDIA A100），而非通用解释器，且训练数据需包含硬件约束下的调试轨迹。

### 仿真环境构建与数据合成

数据合成环节通常依赖 LLM 生成指令-代码对，但缺乏真实执行验证。InCoder-32B 在四个工业领域重建了生产级工具链：芯片设计使用 Icarus Verilog 与 Yosys 进行仿真与综合；GPU 优化在 A100 节点上通过 nvcc 与 Triton 编译器执行内核；嵌入式系统使用 Renode 模拟器复现 STM32F407 外设行为；代码优化在固定 CPU 频率下执行汇编基准测试。

设计动机：通用 SFT 数据集缺乏工业执行信号，导致模型无法学习硬件约束下的错误修复模式。通过真实环境验证，确保训练信号与生产部署标准一致。

数据合成流程包含任务分解、候选生成与反馈驱动修复。对于执行失败的样本，捕获编译器错误、运行时日志与波形差异，将其附加至失败代码以生成修复轨迹。该过程形成闭环修复轨迹，模拟工程师调试工作流。

$$
\mathcal{D}_{SFT} = \{ (x_i, y_i^{fail}, f_i, y_i^{pass}) \mid f_i = \text{Exec}(y_i^{fail}, \mathcal{E}) \}
$$

其中 $\mathcal{E}$ 为特定硬件仿真环境，$f_i$ 为执行反馈，$y_i^{pass}$ 为修复后的正确代码。该公式表明 SFT 数据不仅包含正确解，还包含失败解与反馈的配对，使模型学习从错误中恢复的能力。

### 三阶段 Code-Flow 训练

预训练阶段使用 4,096 块 GPU，采用自回归语言建模与 Fill-in-the-Middle (FIM) 完成，训练数据包含经过 AST 比较与重编译验证的工业代码。Mid-training 阶段将上下文从 8K 逐步扩展至 128K tokens，引入合成工业推理 QA、Agent 轨迹与工业工件（如 SDC 时序约束、GPU 性能分析日志）。

设计动机：静态代码快照无法捕捉跨文件依赖与长程调试上下文，而 Agent 轨迹提供了工具反馈下的闭环推理能力。

Post-training 阶段使用 2.5M 执行验证样本进行 SFT，样本分为直接解、缺陷修复与性能优化三类。训练目标混合自回归、FIM 与跨文件反馈，确保模型在指令遵循与代码补全任务上均具备工业感知能力。

$$
\mathcal{L}_{total} = \lambda_1 \mathcal{L}_{AR} + \lambda_2 \mathcal{L}_{FIM} + \lambda_3 \mathcal{L}_{cross}
$$

其中 $\mathcal{L}_{AR}$ 为自回归损失，$\mathcal{L}_{FIM}$ 为中间填充损失，$\mathcal{L}_{cross}$ 为跨文件一致性损失。该公式表明训练目标并非单一指令遵循，而是多任务混合，以平衡代码生成、补全与跨文件依赖处理。

## 实验评估

实验覆盖 14 个通用基准与 9 个工业基准，基线包括 Qwen3-Coder、DeepSeek-V3.2、Kimi-K2 等开源模型及 Claude-Sonnet-4.6。在通用代码生成任务上，InCoder-32B 在 HumanEval 上取得 94.5%，在 LiveCodeBench 上取得 49.14%，低于 LPW 的 98.2% 与 59.3%，但高于多数同规模开源模型。在工业基准上，InCoder-32B 在 RealBench Module Syn@1 上取得 74.8%，在 KernelBench L2 上取得 36.0%，均领先所有开源基线。

| 基准 | InCoder-32B | 最强开源基线 | 专有模型 |
|---|---|---|---|
| HumanEval | 94.5 | 98.2 (LPW) | - |
| LiveCodeBench | 49.14 | 59.3 (LPW) | - |
| RealBench Module Syn@1 | 74.8 | 43.7 (Qwen3.5-397B) | 69.2 (Claude-Sonnet-4.6) |
| KernelBench L2 | 36.0 | 28.0 (Claude-Sonnet-4.6) | 28.0 (Claude-Sonnet-4.6) |

InCoder-32B 在工业基准上的优势显著，但在通用基准上落后于顶级开源模型，表明工业专精可能以通用能力退化为代价。消融实验显示，仓库转换数据优于静态快照，Mid-training 轨迹数据提升分布偏移下的鲁棒性，多轮反馈条件轨迹解锁了标准指令微调中不存在的能力。

评估边界方面，论文未报告计算效率指标，且工业基准的样本量较小，统计显著性未验证。代码与超参数已开源，但硬件仿真环境的构建成本较高，限制了方法在资源受限场景下的可复现性。

## 关联研究分析

从问题动机看，InCoder-32B 与 SolidCoder 均强调执行反馈，但 SolidCoder 的反馈源为软件单元测试，而 InCoder-32B 的反馈源为硬件仿真。这一差异源于任务特性：工业代码的正确性依赖于硬件行为，软件单元测试无法捕捉寄存器配置或时序约束错误。InCoder-32B 通过重建真实工具链，将硬件约束转化为训练信号，这是通用代码生成方法无法实现的。

从方法设计看，InCoder-32B 与 SCoGen 均依赖合成数据，但 SCoGen 通过知识图谱生成高保真问题，而 InCoder-32B 的合成过程绑定真实执行环境。SCoGen 的图谱构建成本较高，但无需硬件仿真；InCoder-32B 的仿真环境构建成本更高，但数据保真度更强。这一差异暗示，当任务对执行环境依赖越强时，合成数据的环境绑定必要性越高。InCoder-32B 未探索轻量化仿真环境的可能性，其方法在资源受限场景下的适用性存疑。

## 总结

InCoder-32B 要解决的核心矛盾是通用代码模型在工业场景下的性能退化，其切入点在于将执行反馈源从软件单元测试扩展至真实硬件仿真环境。通过三阶段 Code-Flow 训练，模型在 RealBench Module Syn@1 上取得 74.8%，在 KernelBench L2 上取得 36.0%，确立了开源最强基线。然而，其在 HumanEval 上 94.5% 的成绩低于 LPW 的 98.2%，表明工业数据可能挤占了通用语料的学习空间。当工业语料比例增加时，通用代码能力的退化是否不可避免，论文未给出回答。
