> 导读 GPU内核优化长期受限于专家手写库的维护成本与编译器自动调优的性能瓶颈，现有基于大语言模型（Large Language Model, LLM）的自动化方法多聚焦于深度学习框架内的算子加速，缺乏对稀疏矩阵、科学计算等不规则内存访问场景的系统性评估。本文指出将内核优化等同于LLM组件加速的评估范式存在盲区，提出MSKernelBench基准以覆盖多场景通用计算任务，并设计CUDAMaster多智能体框架，通过硬件瓶颈分类过滤Profiling数据指导代码生成。该工作验证了LLM代理在通用高性能计算（High-Performance Computing, HPC）场景下逼近甚至超越专家库的潜力，但其对底层控制权的依赖与动态形状支持的缺失，限制了其在更广泛异构硬件上的直接迁移。

## 研究背景

当开发者试图在GPU上加速科学计算或稀疏线性代数任务时，往往面临两难困境：手动编写CUDA代码能榨取硬件极限性能，但针对每个算子和硬件代际的工程成本极高；使用TVM或Triton等编译器虽提升了开发效率，却难以在复杂的不规则计算模式下匹敌专家手写库。这一矛盾催生了利用LLM自动化生成高性能内核的研究热潮。然而，现有主流评估基准如KernelBench，其任务集高度集中于PyTorch框架下的深度学习算子。这类任务通常具有计算密集和规则内存访问的特征，且优化路径在公开文献中高度透明，LLM的成功可能仅源于对已知解法的“记忆”而非真正的“创造”。

这种评估视角的局限导致了一个关键问题：现有方法未能测试自动化系统在稀疏矩阵运算、科学模拟等具有不规则内存访问模式任务上的泛化能力。稀疏计算和科学计算内核的优化模式与LLM算子截然不同，涉及复杂的内存层级交互与并行策略。若缺乏覆盖这些场景的系统性基准，LLM内核优化的真实能力边界便无法被准确界定。因此，构建一个剥离框架依赖、涵盖多场景通用计算任务的评估体系，并设计能够处理复杂硬件反馈的优化代理，成为突破当前自动化内核生成瓶颈的紧迫需求。

## 核心方法

### 方法参照系：从全量反馈到瓶颈导向的迭代优化

在LLM驱动的内核优化中，标准流程通常包含代码生成、编译执行、性能剖析（Profiling）与反馈迭代。现有方法如CudaForge直接利用NVIDIA Nsight Compute的全量Profiling数据作为反馈，但这导致LLM上下文窗口被大量冗余指标占据，且难以从海量数据中精准定位瓶颈。本文的CUDAMaster框架在此流程中引入了“硬件分析过滤器”与“多智能体分工”，将优化过程重构为基于瓶颈分类的定向迭代，旨在解决全量反馈导致的注意力分散与调试效率低下问题。

### 硬件瓶颈分类与Profiling过滤机制

传统方法向LLM提供未经筛选的硬件计数器数据，迫使模型自行诊断瓶颈，这在复杂内核中极易导致误判。CUDAMaster首先建立硬件瓶颈分类体系，利用Otsu方法对基准套件中所有关键内核的吞吐量指标分布进行阈值划分，将任务归类为计算受限（Compute Bound）、内存延迟受限（Memory Latency Bound）和内存带宽受限（Memory Bandwidth Bound）。

基于此分类，过滤器在运行时动态提取关键指标。对于计算受限任务，仅保留计算单元利用率相关指标；对于内存受限任务，则聚焦于带宽与延迟指标。这一设计动机在于通过降维减少LLM的推理噪声，使其能专注于瓶颈特定的优化策略。例如，当内核被判定为内存带宽受限时，过滤器会剔除计算单元空闲率等无关指标，仅保留DRAM吞吐量等关键数据，从而引导Planner Agent生成针对内存合并或预取策略的代码，而非无效的计算指令重排。

### 多智能体协作与工具链生成

单一LLM代理在处理代码生成、编译调试与性能分析时，常因上下文切换导致性能退化。CUDAMaster将优化流程解耦为四个专用智能体：Planner Agent负责基于过滤后的Profiling数据提出高层优化策略；Coder Agent将策略转化为符合严格C接口规范的CUDA代码；Compiler Agent管理编译命令与执行脚本，确保工具链的完整性；Debug Agent则在代码执行失败时介入，诊断并修正编译或运行时错误。

该架构的核心创新在于Compiler Agent的引入，它自动生成完整的编译与执行工具链，解决了LLM生成代码常因环境配置错误而失败的问题。在迭代过程中，系统维护最佳代码与脚本，若新代码未通过正确性检查，Debug Agent将在限定轮次内尝试修复，否则标记策略无效并回退。这种分工机制模拟了人类专家的工作流，通过隔离关注点提升了系统在复杂多场景任务中的鲁棒性。

## 实验评估

实验在MSKernelBench的50个任务（FP32与BF16各50个）上进行，基线包括cuBLAS、cuSPARSE等专家库及Astra等LLM优化框架。评估协议采用复杂度加权平均加速比，以反映不同数据规模下的优化效果。

| 任务类型 | 基线方法 | 基线加速比 (x) | CUDAMaster (o4-mini) 加速比 (x) | CUDAMaster (DeepSeek) 加速比 (x) |
| :--- | :--- | :--- | :--- | :--- |
| SpMV CSR | cuSPARSE | 2.23 | 2.96 | - |
| Conv 2D | cuDNN | 0.97 | - | 1.83 |
| Dot Product | cuBLAS | 26.09 | 46.83 | - |
| RMS Norm | Astra | 1.78 | 2.44 | - |
| Silu and Mul | Astra | 3.58 | 3.67 | - |
| Merge Attn. St. | Astra | 1.05 | - | 1.35 |

在Dot Product任务上，CUDAMaster生成的代码加速比达46.83x，显著超越cuBLAS的26.09x；在SpMV CSR上亦超越cuSPARSE。这表明在特定通用计算任务上，LLM代理已具备超越专家库的能力。然而，Dot Product的极高加速比可能源于基线实现过于朴素，而非LLM的绝对优化优势，需结合具体代码实现进一步审计。

消融实验显示，迭代轮次与调试机制对性能至关重要。在o4-mini模型下，完整配置在加速比阈值$\tau=1$时的成功率为94%，而移除调试机制（No Debug）后降至77%，单次迭代（Single Iteration）降至74%。在严格阈值$\tau \ge 8$下，完整配置保持25%成功率，而消融变体仅为17-19%。这证实了结构化调试与多轮迭代是处理复杂优化场景的必要组件，而非可选增强。

评估边界方面，实验仅在NVIDIA RTX 4090上进行，未覆盖AMD或TPU等异构硬件；任务均为静态形状，未涉及LLM推理中常见的动态序列长度。此外，基准未提供置信区间，且部分任务基线选择可能影响加速比的绝对可比性。

## 关联研究分析

从问题动机看，KernelBench将内核优化局限于LLM算子加速，其任务集高度依赖PyTorch框架抽象，导致评估偏向规则内存访问模式。MSKernelBench则剥离框架依赖，直接采用纯C/CUDA实现，强制LLM处理稀疏矩阵与科学计算中的不规则内存访问。这一差异源于对“通用性”定义的不同：KernelBench关注深度学习部署效率，而MSKernelBench关注底层计算模式的泛化能力。然而，纯C实现牺牲了可移植性，使得优化策略难以直接迁移至Triton或MLIR等中间表示层，查询侧增强在数据充足时是否仍有增益，论文未给出回答。

从方法设计看，CudaForge同样利用Profiling反馈，但采用全量数据输入，依赖LLM自行解析瓶颈。CUDAMaster引入基于Otsu方法的瓶颈分类过滤，将反馈数据降维。这一设计在稀疏计算等复杂场景中可能更有效，因为不规则访问模式的Profiling数据噪声更大。但过滤机制的阈值设定依赖静态分析，若硬件架构差异导致瓶颈特征分布偏移，该过滤策略的鲁棒性存疑。此外，CUDAMaster未与TVM或Triton等编译器自动调优方法直接对比，无法量化其相对于传统编译器在开发效率与性能之间的权衡优势。

## 总结

本文针对LLM内核优化评估场景单一的问题，提出MSKernelBench基准与CUDAMaster多智能体框架，通过硬件瓶颈过滤与分工协作机制，实现了通用CUDA内核的自动化优化。实验表明，该方法在Dot Product等任务上达到46.83x加速比，超越cuBLAS，并在RMSNorm等任务上优于Astra框架35%。然而，其性能优势部分依赖于特定基线实现，且实验局限于静态形状与单一GPU架构，未验证动态负载下的泛化能力。当优化目标从静态HPC任务转向LLM推理中的动态稀疏模式时，基于静态阈值分类的Profiling过滤机制是否仍能准确识别瓶颈，论文未给出回答。
