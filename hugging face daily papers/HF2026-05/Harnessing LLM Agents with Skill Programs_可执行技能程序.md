# HuggingFace最新推荐论文 ｜Harnessing LLM Agents with Skill Programs ｜可执行技能程序

研究机构：美国纽约大学、Salesforce AI研究院

作者：Hongjun Liu、Yifei Ming、Shafiq Joty 等 4 人

论文原文见 [arXiv](https://arxiv.org/abs/2605.17734)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2605.17734)

> 代理技能学习旨在解决大语言模型代理在长程任务中重复失败且经验难以复用的问题。现有方法多将技能编码为被动文本提示，缺乏对代理决策循环的显式运行时控制，导致模型常忽略技能建议。本文提出 HASP 框架，将技能重构为可执行的状态-动作干预函数（Program Functions, PFs），通过直接修改动作或注入上下文实现主动干预。该设计在推理、训练与进化三阶段提供了统一接口，但其在非结构化任务中的泛化能力及对教师模型的依赖仍是主要存疑点。

## 研究背景

当代理执行多步搜索或推理任务时，常陷入“过早终止”或“重复无效搜索”的局部陷阱。解决此类问题的传统路径是技能注入，即将过往成功或失败轨迹提炼为自然语言规则，作为上下文提示提供给模型。然而，文本技能本质上是“建议性”的，它仅描述了“应该做什么”，却未定义“何时激活”及“如何具体修改当前动作”。这种语义模糊性导致模型在推理过程中可能“承认”技能存在，但实际生成的动作仍偏离技能指引，形成“认知-行动”脱节。

代理技能领域的核心矛盾在于技能表示形式与策略控制力之间的错位。主流路线如 Reflexion 和 ExpeL 依赖文本记忆，虽具备可解释性，但在高噪声环境下控制力弱；而基于强化学习（RL）的方法虽能优化策略，但样本效率低且难以复用具体技能。本文切入点在于将技能从“被动知识”转化为“主动控制”，通过代码化的可执行函数直接嵌入代理循环，弥补文本技能在运行时不可靠执行的缺陷。

## 核心方法

### 方法参照系

本文问题可置于“技能表示架构”与“策略内化”的交叉领域。通用流程为：从轨迹提取技能 → 检索匹配 → 注入提示 → 执行任务。本文的关键差异在于将“注入提示”替换为“执行干预”，技能不再是静态文本，而是包含激活条件与干预逻辑的可执行模块，直接作用于动作空间。

### 可执行状态-动作干预函数

传统文本技能无法指定干预时机，导致模型在关键决策点忽略建议。HASP 引入 Program Function (PF)，每个 PF 包含 `should_activate` 和 `intervene` 两个接口。在步骤 $t$，基础策略 $\pi_\theta$ 提出动作 $a_t^{orig}$，HASP 检索相关 PF 集合 $R(s_t)$ 并评估激活条件。若激活，干预算子 $\Gamma$ 生成修正动作 $\tilde{a}_t$ 或注入上下文 $c_t$：

$$ (\tilde{a}_t, c_t, \kappa_t) = \Gamma(s_t, a_t^{orig}, R(s_t)) $$

该公式表明，PF 不仅决定“是否干预”，还显式定义“如何修改动作”或“补充何种上下文”，将技能从语义建议转化为确定性代码逻辑，解决了文本技能在复杂状态下的歧义性问题。

### 结构化信号驱动的策略内化

PF 执行产生的记录包含原始动作、修正动作及结果反馈，但传统 SFT 仅关注最终答案，忽略了中间决策的质量。HASP 定义四维信号向量 $\mathbf{z}_t = (t_t, m_t, q_t, o_t)$，分别对应干预时机、模式、正确性与结果，并加权聚合为优势函数：

$$ A_t = \lambda_t t_t + \lambda_m m_t + \lambda_q q_t + \lambda_o o_t $$

其中权重 $\lambda_o=0.50$ 最高，强调结果导向。该机制使模型不仅学习“正确答案”，更学习“在何种状态下、以何种方式修正错误”，实现了技能干预向策略权重的细粒度内化，避免了纯 RL 方法中奖励稀疏导致的训练不稳定。

## 实验评估

实验基于 Qwen2.5-7B-Instruct 骨干，在 HotpotQA、2Wiki、MuSiQue（搜索推理）、AIME24、AMC23、GameOf24（数学推理）及 HumanEval、MBPP、BigCodeBench（代码）上进行评估。基线覆盖 Search-R1、ReSearch 等 RL 方法及 SFT 基线，但缺失 SkillOpt、Skill1 等专用技能进化方法的直接对比，限制了跨方法公平性。

| 方法 | Web-Search Avg. (%) | Math Avg. (%) | Coding Avg. Pass@1 (%) |
| :--- | :--- | :--- | :--- |
| RA-Agent (Base) | 31.2 | 32.8 | 60.8 |
| HASP-Intervention (PF-only) | 51.0 | 35.9 | 63.4 |
| HASP-Intervention (w. Teacher) | 56.2 | 38.8 | 68.7 |
| HASP-Evolve + RS | 60.3 | 45.4 | 69.9 |

HASP-Evolve + RS 在搜索推理上较基线提升 29.1 个点，在代码任务上较 SFT 提升 12.4 个点，表明可执行技能在结构化任务中显著优于被动文本提示。

| 消融设置 | Web-Search Avg. (%) | $\Delta$ vs Full |
| :--- | :--- | :--- |
| Full HASP-Intervention | 56.2 | – |
| w/o Timing Signal | 52.5 | -3.7 |
| w/o Mode Signal | 44.8 | -11.4 |
| Evolution, no filtering | 36.3 | -19.9 |

消融显示，移除“模式”信号导致性能下降 11.4 个点，表明干预方式（动作修改 vs 上下文注入）的选择至关重要。更关键的是，未过滤的进化导致性能暴跌 19.9 个点，验证了“执行验证+教师审查”门控机制对防止技能库污染的决定性作用。

评估协议采用精确匹配与 GPT-4o 评判，但未报告置信区间。代码开源情况未明确，但提供了详细的 LoRA 超参数（rank 16, $\alpha=32$）及 GPU 配置（L40s），具备一定可复现性。

## 关联研究分析

从问题动机看，HASP 与 SkillOpt 均关注技能进化，但 SkillOpt 将技能视为可优化的文本参数，通过验证门控迭代修改文本内容；HASP 则坚持技能必须是可执行代码，强调运行时控制力。这一差异源于任务特性：SkillOpt 面向静态文档处理，文本修改足以提升性能；而 HASP 面向动态多步交互，文本建议易被模型忽略，必须通过代码逻辑强制干预。这种“可执行性优先”的设计是否牺牲了文本技能在开放域任务中的泛化灵活性，论文未给出充分论证。

从方法设计看，HASP 与 Skill1 均涉及技能与策略协同，但 Skill1 通过统一 RL 框架同时优化技能选择与策略，依赖大规模轨迹数据；HASP 则通过 PF 产生的结构化信号进行 SFT/RS，无需复杂奖励设计。HASP 的“信号驱动”路径在样本效率上更具优势，但其依赖教师模型进行 PF 审查，引入了外部知识依赖。当教师模型能力受限或领域知识缺失时，PF 生成的质量上限是否会被教师模型锁定，是制约其自主进化能力的关键瓶颈。

## 总结

HASP 解决了文本技能在代理决策循环中“建议性强、控制力弱”的核心矛盾，通过将技能重构为可执行的状态-动作干预函数，实现了从“被动提示”到“主动控制”的范式转变。实验证明，在搜索推理与代码任务中，该框架较基线提升约 30 个点，且无需复杂 RL 训练。然而，其性能高度依赖教师模型对 PF 的审查质量，且在非结构化、高噪声任务中的泛化能力未得到充分验证。当移除教师审查环节时，技能库性能暴跌近 20 个点，这是否意味着当前框架难以实现真正的无监督自主进化，仍是其走向实用化的关键障碍。
