# HuggingFace最新推荐论文 ｜AsyncTool: Evaluating the Asynchronous Function Calling Capability under Multi-Task Scenarios ｜异步工具调用基准

研究机构：中国科学技术大学、加拿大多伦多大学

作者：Kou Shi、Ziao Zhang、Shiting Huang 等 10 人

论文原文见 [arXiv](https://arxiv.org/abs/2605.27995)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2605.27995)

> 现有工具使用评测普遍假设工具响应即时返回，忽略了真实 API 调用中普遍存在的延迟，导致无法衡量智能体在等待期间利用空闲时间推进其他任务的能力。本文切入点在于将“时间维度”引入工具调用评测，构建首个同时考察延迟反馈、多任务并发与依赖协调的基准。通过混合数据演化策略重组单任务轨迹，并在步骤、子任务、任务三级评估准确率与效率指标。该工作填补了异步调度能力的评测空白，但其模拟延迟分布与真实生产环境的长尾特征是否一致，仍缺乏验证。

## 研究背景

当智能体调用外部 API 时，网络延迟与服务端处理时间导致工具结果无法即时返回。在同步执行范式下，智能体必须阻塞等待，造成计算资源闲置；而在真实多任务场景中，智能体本可利用这段等待时间推进其他独立任务。这种对空闲时间的利用能力，即异步工具调用（Asynchronous Tool Call），要求智能体在工具结果未返回时维持任务状态，并在依赖满足后恢复执行。

现有工具使用基准（如 BFCL、NESTFUL）均基于即时响应假设，仅评估单任务下的工具选择与参数正确性，未涉及多任务并发与时间调度。ReAct 范式确立了“推理-行动-观察”的交互架构，但其隐含假设是观察结果即时可用，当引入延迟后，该范式在任务切换与状态维护上的失效机制未被量化。本文旨在通过构建异步多任务环境，揭示当前 LLM 智能体在时间协调与依赖追踪上的具体短板。

## 核心方法

### 方法参照系

本文问题属于工具调用评测基准的构建，但与传统基准的关键差异在于引入了时间维度。传统流程关注静态轨迹的正确性，而 AsyncTool 要求智能体在动态延迟环境中协调多任务，将评测对象从“单次调用准确性”扩展为“并发调度有效性”。

### 异步多任务数据构建

数据构建环节通常直接采集真实日志或人工标注，但异步场景缺乏现成数据源。本文采用混合数据演化策略，从 NESTFUL 和 BFCLv3 中提取 358 个验证过的单任务轨迹，通过 Gemini 2.5 Pro 重构任务描述与执行路径，再经人工校验消除依赖违规与参数错误。随后，通过加权随机采样将单任务组合为双任务或三任务场景，生成 712 个多任务实例。该设计解决了真实异步日志稀缺的问题，但依赖单任务轨迹的独立性假设，未覆盖真实 API 中可能存在的跨任务资源竞争。

### 多级评估协议

传统评测仅关注最终结果，无法区分“工具调用正确但调度低效”与“调度正确但调用错误”。本文设计三级评估体系，在步骤级计算工具与参数的 F1 分数，在子任务级比较预测轨迹 $T_{i}^{pred}$ 与真值 $T_{i}^{gt}$ 的匹配度，并在任务级要求所有子任务同时满足轨迹与环境状态一致性。此外，引入 Same-task Streak 指标衡量任务交错效率，定义为同一任务连续执行回合数的平均值。该协议将效率与准确率解耦，使模型在“频繁切换但错误率高”与“稳定执行但效率低”之间的权衡变得可量化。

## 实验评估

实验在 AsyncTool 基准上评估 19 个模型，包括 GPT-4.1、Gemini 2.5 Pro 等闭源模型及 DeepSeek-V3.1-Terminus、Qwen3 等开源模型。基线覆盖主流 LLM，但缺乏针对异步调度优化的专用算法（如基于 RL 的调度器），导致无法区分模型性能差异源于基础能力还是调度策略。

| 模型 | Step Level (Func.) | Step Level (Param.) | Sub-Task Level (Acc.) | Task Level (Overall) |
| :--- | :--- | :--- | :--- | :--- |
| GPT-4.1 | 96.22 | 84.08 | 67.89 | 38.06 |
| DeepSeek-V3.1-Terminus | 86.10 | 75.32 | 59.39 | 28.93 |
| Gemini 2.5 Pro | 89.08 | 78.27 | 63.16 | 34.13 |
| Qwen3-8B | 63.05 | 53.61 | 29.88 | 10.67 |

GPT-4.1 在任务级整体得分 38.06，显著领先 DeepSeek-V3.1-Terminus 的 28.93，表明闭源模型在时间协调上具备优势。开源模型中，Qwen3-8B 得分仅 10.67，显示小模型在依赖追踪上的严重不足。

消融分析显示，准确率与效率并非严格正相关。GPT-4.1 在保持高 Overall 得分的同时维持较低的 Same-task Streak，实现了调度与准确性的平衡；而部分小模型虽切换频繁（低 Streak），但因依赖违规导致 Overall 得分极低。这证实了有效异步工具使用不仅需要频繁切换，更需依赖追踪与状态维护的协同。

评估边界方面，AsyncTool 的模拟延迟分布未与真实 API 长尾延迟进行对比验证，可能高估或低估模型在极端延迟下的表现。代码已开源，但数据构建依赖 Gemini 2.5 Pro 的重构质量，人工校验仅覆盖 358 个单任务实例，多任务组合的依赖结构合理性缺乏独立审计。

## 关联研究分析

从问题动机看，ReAct 范式（Yao et al., 2022）确立了同步交互的基础，但本文揭示了其在延迟环境下的失效机制：当工具结果未返回时，ReAct 的“观察”步骤被阻塞，导致智能体无法推进其他任务。与 Tool-R0（Acikgoz et al., 2026）相比，后者关注工具选择策略的优化，而本文聚焦工具执行后的时间管理，二者构成“选择-调度”的互补链路，但 Tool-R0 未考虑并发场景下的资源竞争。

从方法设计看，MCP 协议（Model Context Protocol）标准化了工具接口，但本文指出接口标准化并未解决调用后的时间调度问题。与 AutoGen（Wu et al., 2024）的多智能体协作框架不同，AsyncTool 强调单智能体内部的多任务并发调度，而非多智能体间的通信。这种差异源于任务特性：多智能体协作解决的是角色分工问题，而异步工具调用解决的是单智能体在时间维度上的资源利用问题。

## 总结

本文核心矛盾在于现有工具评测忽略时间维度，导致无法衡量智能体在延迟反馈下的并发调度能力。切入点在于将异步工具调用形式化为多任务依赖协调问题，通过混合数据演化构建基准。实验证明 GPT-4.1 在任务级得分 38.06，显著优于开源模型，揭示闭源模型在时间协调上的优势。边界在于模拟延迟分布未验证真实长尾特征，且缺乏专用调度算法基线。当真实 API 延迟呈现重尾分布时，当前基准中基于固定延迟的评估结论是否依然成立，论文未给出回答。
