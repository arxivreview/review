> 强化学习训练的 LLM 生成的 Lean 证明虽正确但冗长、编译慢且跨版本脆弱，现有重构方法仅针对单一目标且依赖微调，无法平衡长度、编译成本与版本兼容性的多目标冲突。本文切入点是将重构知识外化为带元数据的策略库，通过推理时检索与重排引导冻结 LLM 实现多目标控制。具体做法是构建一个包含 9K 策略的标注数据库，结合多目标检索与智能体循环，在不微调模型的前提下完成证明优化。该方法在竞赛级基准上实现了 88.40% 的证明长度压缩，但在研究级复杂证明上的泛化边界尚存疑。

## 研究背景

Lean 证明重构面临的核心困境在于目标间的内在张力：缩短证明长度往往需要调用更复杂的战术，从而增加编译时间；反之，追求低编译成本可能导致证明步骤冗余。这种多目标冲突使得传统的单目标优化失效。同时，Lean 和 Mathlib 库以周为单位快速迭代，API 频繁变更，而 LLM 的知识截止点固定，导致模型生成的代码常包含已废弃的战术或过时的 API 调用，即版本错位问题。此外，Lean 代码库规模远小于 Python 等主流语言，缺乏成对的“冗长-简洁”重构轨迹数据，使得基于监督微调的方法难以获得高质量训练样本。

主流重构路线分为两类：一类是微调专用模型，如 ProofOptimizer 通过合成数据对模型进行长度优化微调，但其目标在训练时固定，无法适应推理时的新需求；另一类是通用智能体框架，如 ImProver 利用链式状态提示和检索，但缺乏对编译成本和版本兼容性的显式控制。这些方法要么牺牲灵活性，要么忽略多目标权衡。本文的切入点在于将重构知识从模型参数中解耦，外化为一个带有编译成本、版本兼容性等元数据的策略库，通过推理时的动态检索与重排，使冻结的 LLM 能够根据用户指定的目标（如最短证明、最快编译或特定版本兼容）灵活调整重构策略，从而解决多目标冲突与版本错位问题。

## 核心方法

### 方法参照系

本文问题属于代码重构领域，但区别于通用代码重构，Lean 重构具有强形式化验证约束和多目标耦合特性。通用重构流程通常依赖测试套件验证正确性，而 Lean 重构必须通过编译器类型检查，且需同时优化长度、编译时间和版本兼容性。本文的关键差异在于不修改模型权重，而是通过外部策略库的检索与重排实现控制。

### 多目标策略库构建

设计动机在于解决 LLM 知识截止与 Lean 库快速迭代之间的错位，以及缺乏成对重构数据的问题。本文从 NuminaMath、Mathlib 等来源聚合证明，利用 Goedel-Prover-V2-32B 和 GPT-OSS-120B 合成冗长-简洁证明对，并蒸馏为 9237 个唯一重构策略。每个策略包含标题、描述、应用条件、步骤指南、示例及潜在长度减少标签。关键创新在于为每个策略标注两类元数据：一是编译时间减少率，通过 `lake env lean --profile` 测量并取中位数；二是版本兼容性，通过在不同 Lean 版本（v4.14.0, v4.16.0, v4.22.0）下重新编译验证，取交集作为兼容版本集合。这种元数据标注使得策略库具备版本感知能力，推理时可过滤不兼容策略。

### 多目标检索与智能体循环

设计动机在于实现推理时的多目标可控重构，避免重新训练。本文微调 Qwen3-Embedding-8B 作为检索模型，训练目标为对比学习，损失函数如下：

$$
\mathcal{L} = -\frac{1}{B} \sum_{i=1}^{B} \log \frac{\exp(\text{Sim}(q_i, c_i^+)/\tau)}{\sum_{j=1}^{B} \mathbb{I}(q_i, c_j) \exp(\text{Sim}(q_i, c_j)/\tau)}
$$

其中 $\mathbb{I}(q_i, c_j)$ 为假负例掩码，当 $\text{Sim}(q_i, c_j) > \text{Sim}(q_i, c_i^+) + m$ 时为 0，否则为 1。该公式通过掩码高相似度负例，提升检索精度。推理时，根据用户目标动态调整检索规则：若追求最短证明，使用余弦相似度 Top-K；若追求编译速度，按编译成本减少率重排；若指定版本，过滤不兼容策略。检索结果输入智能体循环，由 Planner 分解任务，Refactorer 重写代码，Debugger 基于编译器反馈修复错误，直至证明长度低于目标或 API 预算耗尽。

## 实验评估

实验在 Gemini 3 Flash 和 Claude Haiku 4.5 上进行，覆盖竞赛级（miniF2F, PutnamBench, Putnam2025）和研究级（Analysis, FLT, PFR, PhysLean）基准。基线包括 ProofOptimizer（微调式）和 Claude Code（通用智能体）。主结果显示，Lean Refactor 在 miniF2F 上实现 88.40% 的长度压缩，优于 ProofOptimizer 的 87.90%；在 PutnamBench 上达到 70.38%，显著高于 ProofOptimizer 的 57.20%。

| 方法 | miniF2F (%) | PutnamBench (%) | Putnam 2025 (%) |
|---|---|---|---|
| ProofOptimizer | 87.90 | 57.20 | – |
| Lean Refactor | 88.40 | 70.38 | 79.27 |

消融实验表明，检索与规划具有协同效应：移除规划器的 Base Agent 在长证明上陷入调试循环，而随机检索的收益不稳定，证明精准策略选择是关键。在编译时间优化上，Lean Refactor w/ Reranking 在 PutnamBench 上实现 42.62% 的相对减少，优于纯余弦检索的 37.11%。然而，miniF2F 上纯余弦检索导致编译时间相对增加 103.98%，表明目标错位可能引发负迁移。评估边界方面，实验未报告置信区间，且研究级基准仅采样 45 个定理，样本量较小；代码未公开，可复现性受限。

## 关联研究分析

从问题动机看，本文与 ProofOptimizer 的核心差异在于目标灵活性。ProofOptimizer 通过微调固定优化目标（长度），而本文通过元数据检索实现推理时目标切换。这一差异源于 Lean 重构的多目标本质：编译成本与长度常冲突，微调模型难以同时优化。本文的策略库设计允许用户动态指定目标，但依赖元数据标注的准确性，若编译成本测量存在噪声，可能误导重排。

从方法设计看，本文与 ImProver 同属智能体框架，但检索对象不同。ImProver 检索 Lean 文档和示例，而本文检索重构策略。这一差异源于任务特性：重构需要结构化的“何时应用”和“如何应用”指导，而非单纯代码片段。本文的策略库提供了更细粒度的控制，但构建成本高，需大量证明对和元数据标注。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

本文要解决的核心矛盾是 LLM 生成证明的多目标优化与版本错位问题。现有方法因依赖微调或单目标优化而无法灵活应对，本文通过外化策略库与多目标检索实现控制。方法上，构建带元数据的策略库，结合对比学习检索与智能体循环，在不微调模型的前提下完成重构。实验证明，该方法在竞赛级基准上实现 88.40% 的长度压缩和 42.62% 的编译时间减少，优于基线。边界在于研究级证明的泛化能力未充分验证，且元数据标注依赖编译环境稳定性。当 Lean 库版本迭代加速时，策略库的更新频率与 LLM 推理延迟之间的平衡如何维持，论文未给出回答。
