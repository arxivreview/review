# HuggingFace最新推荐论文 ｜CoSPlay: Cooperative Self-Play at Test-Time with Self-Generated Code and Unit Test ｜无真值单元测试下的代码-测试协同进化

研究机构：香港科技大学

论文原文见 [arXiv](https://arxiv.org/abs/2605.23491)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2605.23491)

> 大语言模型代码生成依赖可执行验证来确保功能正确性，但现有强化学习（RLVR）与测试时扩展（TTS）方法均受制于高质量真值单元测试（GT UTs）的稀缺与标注成本。本文切入点在于：GT-free 场景下，自生成的单元测试（UTs）往往存在噪声或与错误代码形成虚假耦合，导致单向验证失效。CoSPlay 通过构建代码-UT 执行矩阵，利用双向通过计数信号驱动代码与测试的迭代协同进化，并在最终选择阶段引入输出共识聚类打破平局。该方法在无需任何真值数据与模型权重更新的前提下，显著提升了代码与测试质量，但其性能上限仍受限于骨干模型的基础能力，且在任务过易或过难时存在负迁移风险。

## 研究背景

代码生成的核心挑战在于跨越从语法正确到语义正确的鸿沟，而单元测试（Unit Tests, UTs）提供了可执行的输入-输出检查，是验证功能正确性的关键信号。然而，GT UTs 的获取成本极高，通常由人类专家或官方出题人精心策划，难以规模化。这导致现有的 SOTA RLVR 方法（如 CURE、AceCoder）必须依赖大量 GT 数据进行昂贵的训练，而 GT-free 的 RLVR 方法（如 Absolute-Zero）虽避免了数据依赖，却仍需高昂的模型权重更新成本，且实际竞争力不足。

测试时扩展（Test-Time Scaling, TTS）方法试图通过增加推理时的计算开销来弥补训练数据的不足，避免权重更新。然而，传统 TTS 方法（如 SFS、CodeTree）在 GT-free 设置下，必须依赖自生成的 UTs 进行代码筛选与修复。这些自生成 UTs 往往存在预期输出错误、区分度不足，甚至与特定错误代码形成“虚假耦合”（Spurious Coupling），即错误代码恰好通过了错误的测试，导致验证信号失效。因此，核心问题从“如何采样更多代码”转变为“如何在推理时让代码与 UTs 协同进化，以在无 GT 条件下实现竞争性代码生成”。

## 核心方法

### 方法参照系

CoSPlay 属于 GT-free TTS 框架，其标准流程通常包含代码采样、基于执行结果的筛选与修复。与单向验证方法的关键差异在于，CoSPlay 引入了双向反馈机制：不仅用 UTs 评估代码，还用代码的通过率反向验证 UTs 的可靠性，并通过迭代自博弈（Self-Play）动态更新两个池子。

### 探索-攻击引导的代码-UT 初始化

直接提示 LLM 生成 UTs 往往产生通用或浅层的测试用例，缺乏针对特定解法假设的区分度。CoSPlay 首先探索多种高层算法策略 $H$，并针对每种策略 $s \in S$ 识别其潜在失效模式，生成攻击性 UT 想法池 $A$。基于此，代码池 $\mathcal{C}$ 由不同策略生成的候选代码组成，UT 池 $\mathcal{T}$ 则混合了随机有效输入与攻击性输入。对于每个输入 $x_j$，通过多次采样输出并保留多数一致的答案 $y_j$，利用输出自一致性（Self-Consistency）提升初始 UT 的正确性先验。这一设计动机在于，攻击性 UTs 能更好地暴露解法中的隐藏缺陷，从而为后续的协同进化提供更具区分度的初始信号。

### 执行矩阵驱动的双向协同进化

给定代码-UT 执行矩阵 $\mathbf{M} \in \{0, 1\}^{N_c \times N_t}$，其中 $M_{ij}=1$ 表示代码 $c_i$ 通过 UT $t_j$。定义代码通过率 $\alpha_i^{code} = p_i^{code}/N_t$ 和 UT 通过率 $\alpha_j^{UT} = p_j^{UT}/N_c$。协同进化通过四个步骤迭代进行：

1. **代码清洗**：移除全失败代码，因其通过正确 UT 的概率极低。

2. **打破虚假耦合**：识别低通过率但非零的“可疑”UT $t_{j_{worst}}$，利用其通过的错误代码作为负参考，重新生成 UT 以打破虚假一致。

3. **代码修复**：选择高通过率但非全通过的“非平凡最佳”UT $t_{j_{best}}$，利用其执行反馈修复失败代码。

4. **替换零区分度 UTs**：替换通过率为 0 或 1 的 UTs，以维持池子的区分度。

$$
S_{cls}(G_m) = \sum_{c_i, c_j \in G_m, i < j} \sum_{k=1}^R \mathbb{I}[\mathbf{o}_i(z_k) = \mathbf{o}_j(z_k) \neq \text{ERR}]
$$

该公式定义了输出共识簇的可靠性评分，仅统计有效且一致的对间输出，以处理执行错误。这一机制解决了传统 TTS 中自生成 UTs 噪声大、易与错误代码耦合的问题，通过双向验证逐步净化代码与 UT 池，使通过计数成为无 GT 条件下可靠的质量代理信号。

## 实验评估

实验在 LiveBench、LiveCodeBench、CodeContests 和 CodeForces 四个基准上进行，基线覆盖 SFS、CodeTree、MPSC 等 TTS 方法及 CURE、Absolute-Zero 等 RLVR 模型。CoSPlay 在 Qwen2.5-7B-Instruct 上，将平均 BoN 从 22.1% 提升至 33.2%，UT 准确率从 14.6% 提升至 78.3%，略超 CURE-7B 的 32.9% BoN。在 14B 规模上，CoSPlay 将 CURE-14B 的 BoN 从 41.8% 提升至 46.2%。

| 方法 | 7B BoN (%) | 14B BoN (%) | UT Acc (%) |
|---|---|---|---|
| Qwen2.5-7B-Instruct | 22.1 | 33.2 | 14.6 |
| CoSPlay w/ Cluster | 33.2 | 42.0 | 78.3 |
| CURE-7B | 32.9 | 41.8 | 54.9 |
| CURE-14B + CoSPlay | 38.6 | 46.2 | 80.1 |

消融实验显示，移除“探索-攻击”模块导致 BoN 下降最显著，验证了初始 UT 质量的重要性。移除自一致性或 UT 迭代步骤均导致性能下降，表明各模块对稳定改进有贡献。在计算效率上，CoSPlay 使用 682K tokens 达到 37.2% Pass@1，而 BoN (N=256) 使用 745K tokens 仅达 22.5%，表明其优势源于更有效的测试时计算利用而非暴力采样。

评估边界方面，CoSPlay 依赖可执行环境，无法直接扩展至不可执行推理任务。在任务过易（如 LiveBench 上的 Gemini-2.0-Flash）或过难（如 CodeForces 上的 Absolute-Zero-7B）时，自博弈可能引入扰动或信号噪声，导致性能低于基线。实验在 200 题子集上进行，可能影响结果泛化性。

## 关联研究分析

从问题动机看，CoSPlay 与 SFS 等单向 TTS 方法的核心差异在于验证信号的来源。SFS 依赖外部或自生成的 UTs 进行代码筛选，但无法验证 UTs 本身的可靠性，导致在 GT-free 设置下信号噪声大。CoSPlay 通过代码通过率反向验证 UTs，解决了“谁验证验证者”的循环依赖问题。这一差异源于任务特性：代码生成的可执行性允许构建双向执行矩阵，而不可执行任务缺乏此机制。

从方法设计看，CoSPlay 与 Absolute-Zero 等 GT-free RLVR 方法形成对比。Absolute-Zero 通过强化学习更新权重以优化代码生成，但计算成本高且依赖大量 RL 训练。CoSPlay 为 Training-free，仅利用推理时计算，避免了权重更新成本。然而，CoSPlay 的性能上限受限于骨干模型的基础能力，而 RLVR 方法可通过训练提升模型内在能力。CoSPlay 在 CURE-7B 上的增益（+5.7% BoN）表明其可作为 RLVR 的推理时补充，但两者在模型能力边界上的互补性仍需进一步验证。

## 总结

CoSPlay 解决了 GT-free 代码生成中自生成 UTs 噪声大、易与错误代码耦合的核心矛盾。其切入点在于利用代码-UT 执行矩阵的双向通过计数信号，驱动代码与测试的协同进化，并通过输出共识聚类打破平局。实验证明，该方法在无需真值数据与权重更新的前提下，显著提升了代码与测试质量，7B 模型 BoN 从 22.1% 提升至 33.2%。然而，其性能在任务过易或过难时存在负迁移风险，且依赖可执行环境。当骨干模型能力接近任务难度边界时，自博弈的边际收益是否递减，论文未给出明确回答。
