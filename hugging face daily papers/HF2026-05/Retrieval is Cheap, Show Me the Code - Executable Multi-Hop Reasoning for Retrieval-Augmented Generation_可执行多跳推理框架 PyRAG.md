> 多跳问答要求模型跨越多个文档链式推导答案，但现有检索增强生成（RAG）系统依赖自由文本轨迹，导致中间状态隐式化、实体漂移及错误累积。PyRAG 将多跳推理重构为 Python 程序合成与执行，通过变量绑定中间结果并利用编译器反馈实现自修复。该框架在五个基准上验证了结构化执行优于自由文本推理的有效性，但其优势高度依赖代码模型的归纳偏置，且未解决全局聚合类问题。

## 研究背景

多跳问答的核心困境在于证据分散与状态管理的矛盾。当问题需要跨越多个文档时，模型必须将复杂查询分解为子问题，逐步检索并整合中间结果。这一过程要求系统维护明确的中间状态，但传统 RAG 将推理编码为自然语言叙述，中间结果嵌入在文本流中而非作为离散对象存在，导致后续步骤无法精确引用前序结果，且检索查询易偏离目标实体。

主流迭代检索方法如 IRCoT 和 Search-R1 通过交替执行检索与推理来缓解证据分散问题，但推理状态仍隐式存在于文本中，错误检测依赖 LLM 自我判断，缺乏确定性反馈机制。程序引导推理方法如 PAL 虽利用代码结构，但假设证据在合成时已知，无法处理开放域中依赖前序检索结果的动态查询。PyRAG 的切入点在于识别任务结构与推理表示的错配：多跳问答本质是逐步计算过程，与代码模型的变量维护和控制流执行模式高度契合，因此将推理重构为可执行程序以利用代码模型的归纳偏置。

## 核心方法

### 方法参照系

PyRAG 属于迭代检索与推理路线，但将状态表示从自然语言轨迹改为可执行 Python 程序。与 IRCoT 等方法的差异在于：后者通过 LLM 生成文本形式的推理链，中间结果隐含在叙述中；PyRAG 生成包含 `retrieve()` 和 `answer()` 工具调用的程序，中间结果绑定为变量，通过数据流显式连接。

### 程序化推理表示

PyRAG 将多跳问答建模为程序合成问题，规划代理生成程序 $\pi$，其中每个步骤调用工具 API 并将结果存储为变量。给定子查询序列 $s = [s_1, \dots, s_n]$，程序定义为：

$$
\pi = \{ (v_i, op_i, args_i) \mid i=1,\dots,m \}
$$

其中 $v_i$ 为变量名，$op_i \in \{retrieve, answer\}$，$args_i$ 包含查询和依赖变量。该公式的物理含义是：推理过程被分解为原子操作序列，每个操作的结果通过变量名显式传递给后续步骤，消除了自然语言叙述中的状态模糊性。这一设计解决了自由文本推理中中间结果无法精确引用的问题，使推理轨迹可检查、可调试。

### 执行引导自修复

PyRAG 引入两种无需训练的自修复机制。编译器自修复利用运行时异常作为确定性信号：当程序执行失败时，解释器返回结构化错误（如 `SyntaxError`、`NameError`），规划代理基于错误消息修订程序。自适应检索机制在中间答案指示证据不足时，动态增加该步骤的检索预算 $k$。设步骤 $i$ 的初始检索预算为 $k_0$，当 `answer()` 返回“未知”或低置信度时，系统重新执行该步骤并设置 $k_i = 2k_0$。该机制解决了固定检索深度无法适应证据稀疏子步骤的问题，通过执行反馈实现针对性修正，而非依赖 LLM 自我反思的不确定性判断。

## 实验评估

PyRAG 在五个开放域问答基准（PopQA、HotpotQA、2WikiMultiHopQA、MuSiQue、Bamboogle）上评估，使用 Qwen2.5-7B 和 72B 作为骨干，E5-base 作为检索器。基线覆盖训练-free 方法（Vanilla RAG、IRCoT、ITER-RETGEN）和 RL 训练方法（Search-R1、StepSearch、ReSearch），但缺失图结构方法如 HippoRAG 的对比。

| 方法 | HotpotQA | 2WikiMQA | MuSiQue | Bamboogle | Avg. |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Vanilla RAG (7B) | 28.9 | 18.9 | 4.7 | 16.0 | 21.3 |
| IRCoT (7B) | 32.7 | 22.0 | 10.2 | 24.8 | 24.8 |
| PyRAG (7B) | 34.0 | 33.4 | 11.8 | 41.5 | 30.8 |
| Search-R1 (7B) | 37.0 | 41.4 | 14.6 | 36.8 | 32.4 |
| PyRAG-RL (7B) | 40.5 | 49.4 | 20.7 | 46.1 | 39.2 |

PyRAG 在训练-free 设定下平均 EM 为 30.8，较 Vanilla RAG 提升 11.8 点，在 Bamboogle 上提升 25.5 点，表明结构化执行在组合多跳任务上优势显著。PyRAG-RL 平均 EM 达 39.2，超越 ReSearch（38.9）和 Search-R1（32.4），且在 2WikiMQA 和 Bamboogle 上取得 7B 模型最高分。

消融实验显示，从 Vanilla RAG 到 PyRAG 的增益呈单调递增：仅分解带来小幅提升，添加结构化计划进一步改善，执行带来最大跃升。代码专用模型在 Vanilla RAG 下无优势，但在 PyRAG 下一致优于指令模型，差距在更难基准上扩大（2WikiMQA +6.9），证实模型能力与推理接口需协同设计。

评估边界方面，PyRAG 仅报告 EM 指标，未提供置信区间或计算效率详细数据；代码开源但超参数和 GPU 配置未在正文中完整披露；Bamboogle 数据集仅 125 个样本，统计显著性存疑。

## 关联研究分析

从问题动机看，PyRAG 与 IRCoT 均解决多跳证据分散问题，但 IRCoT 依赖 LLM 自我判断控制迭代终止，而 PyRAG 通过编译器反馈和证据充分性检查实现确定性控制。这一差异源于任务特性：多跳推理中的错误传播需要可验证的中间状态，自然语言轨迹无法提供这种验证机制。PyRAG 的程序化表示使错误检测从概率性判断转为确定性运行时异常，但代码生成的语法错误率是否随问题复杂度非线性增长，论文未给出回答。

从方法设计看，PyRAG 与 PAL 同属程序引导推理，但 PAL 假设证据预知，适用于表格或封闭语料库；PyRAG 处理开放域动态检索，中间答案在合成时未知。这一差异是任务边界决定的：开放域多跳问答要求后续查询依赖前序检索结果，PAL 的静态程序结构无法适应这种动态依赖。PyRAG 通过变量绑定和自适应检索解决了这一问题，但未探索代码结构与图结构检索的结合，实体关系密集场景下代码变量是否不如知识图谱高效，论文未提供对比证据。

## 总结

PyRAG 解决的核心矛盾是多跳问答中推理状态隐式化导致的错误累积与不可验证性。现有迭代检索方法依赖自由文本轨迹，无法提供确定性反馈；PyRAG 抓住代码模型的归纳偏置，将推理重构为可执行程序，通过变量绑定中间结果并利用编译器反馈实现自修复。实验证明该框架在训练-free 和 RL 设定下均优于强基线，7B 模型平均 EM 达 39.2，在 Bamboogle 上较 Vanilla RAG 提升 25.5 点。其边界在于：代码专用模型的优势仅在程序合成接口下显现，且未解决全局聚合类问题；当支持集增大或问题复杂度提升时，代码生成的错误率是否可控，论文未给出回答。
