> 3D室内场景生成旨在从多模态输入构建可交互、高保真的三维环境，核心矛盾在于视觉真实感与几何/语义一致性的失衡。现有文本驱动方法缺乏精确空间信息，而基于透视图像的智能体框架在处理完整房间时易陷入无限循环且细节恢复不足。Code-as-Room (CaR) 提出一种基于多模态大语言模型（MLLM）的智能体框架，通过结构化执行框架与跨阶段记忆，将俯视图解析为可执行的Blender代码，实现从全局布局到局部装饰的粗到细生成。该框架在人类评估中显著优于基线，但其依赖多阶段LLM调用带来的高延迟及自建基准的局限性，限制了其实时性与跨数据集泛化能力的验证。

## 研究背景

当用户试图通过文本描述生成3D房间时，语言模型难以精确指定物体数量、位置与朝向，导致生成结果与用户意图偏离。为弥补这一缺陷，研究者转向利用俯视图（Top-Down View）作为输入，因其天然编码了房间结构与物体布局的空间先验。然而，将视觉信息转化为3D结构需要解决几何一致性问题，即确保生成的物体在空间中无碰撞、支撑正确且符合物理规律。这要求生成模型不仅具备视觉理解能力，还需具备精确的空间推理与代码生成能力，以构建可编辑、可渲染的场景表示。

早期室内场景合成依赖程序化规则或数据回归，受限于语义僵化与数据多样性不足，难以处理复杂空间关系。随着扩散模型与MLLM的发展，研究重心转向利用大模型进行空间推理与约束求解。Holodeck、SceneWeaver等方法通过LLM规划与工具调用生成场景图或JSON布局，但文本输入仍缺乏精确的空间锚点。VIGA等基于透视图像的智能体框架尝试通过代码合成构建3D场景，但在扩展至俯视图以生成完整房间时，面临细粒度空间细节恢复困难及智能体陷入无限循环的稳定性问题。Code-as-Room针对这一瓶颈，提出以俯视图为全局空间先验，通过结构化执行框架（Structured Execution Harness）与跨阶段记忆机制，实现稳定、可控的3D房间代码合成。

## 核心方法

### 方法参照系

本文问题属于智能体驱动的场景创作路线，标准流程为LLM解析输入、生成场景图或代码、执行并反馈。与通用流程的关键差异在于：本文输入为俯视图而非文本或透视图像，输出为可执行Blender代码而非JSON或隐式场，且引入了显式的跨阶段记忆以解决长流程中的上下文遗忘问题。

### 结构化执行框架与跨阶段记忆

设计动机：现有智能体框架在长流程中易因上下文窗口限制导致早期信息丢失，引发物体遗漏或布局漂移。本文通过引入共享记忆模块 $M$，将任务分解为五个阶段，每个阶段产生类型化工件 $e_s = \langle s, \tau_s, O_s, \eta_s \rangle$ 并更新记忆：

$$ M_{s+1} = M_s \cup \{ e_s \} $$

该公式表明记忆是累积式的，下游阶段仅读取预定义的内存视图，既保证跨阶段一致性，又减少提示噪声。这种设计将全局空间对齐（布局代码）与局部细节合成（物体几何、材质）解耦，避免了单轮生成中模型需同时推断结构、几何与外观的复杂性。

### 视觉反馈布局优化与物体代码生成

设计动机：纯文本推理缺乏精确几何感知，易产生物体碰撞或悬浮。本文在布局生成阶段引入渲染-比较-修正闭环。设当前布局代码为 $C_t$，渲染图像为 $I_t$，VLM评估得分 $s_t$ 及文本反馈 $A_t$ 为：

$$ s_t, A_t = \text{Critic}(I_t, I_{\text{ref}}) $$

若 $s_t < s_{\star}$ 且迭代次数 $t < T_{\max}$，则根据 $A_t$ 修正代码。该机制利用VLM的视觉识别能力自动修正布局错误，弥补了文本推理的几何盲区。随后，基于修正后的布局，智能体生成物体几何代码，将代理包围盒替换为语义化3D基元分解，并通过资产检索处理复杂小物体，最终生成包含材质与光照的完整Blender代码。

## 实验评估

实验在自建基准上进行，包含41个涵盖卧室、厨房、实验室等类型的俯视图场景，输入包括照片、合成渲染与线稿。基线包括直接VLM生成（Gemini 3.1 Pro, GPT-5.5）及智能体框架VIGA。评估指标涵盖视觉理解、空间推理、代码生成及场景质量。

| 方法 | Obj. Recall (%) | Layout IoU (%) | Rotation Acc. (%) | Human Sim. | Human Use. | Human Accept. |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| GPT-5.5 (Direct) | 15.3 | 16.8 | 14.5 | 7.0 | 6.0 | 5.0 |
| VIGA | - | - | - | 5.5 | 4.5 | 4.0 |
| CaR w/ Gemini3.1-Pro | 88.42 | 72.0 | 93.5 | 9.0 | 8.0 | 7.5 |

CaR w/ Gemini3.1-Pro在物体召回率（88.42%）与布局IoU（72.0%）上显著优于直接生成基线，人类评估中相似度（9.0）与可用性（8.0）也最高，表明结构化执行框架有效提升了空间一致性与实用性。

消融实验显示，移除跨阶段记忆导致布局IoU从73.2%降至58.0%，物体召回率从55.5%降至48.2%，证实记忆对维持长流程一致性的关键作用。视觉反馈迭代次数对性能影响呈非单调性：从0次增至5次，布局IoU从64.0%升至66.2%，旋转准确率从71.9%升至75.4%；但增至10次时，布局IoU降至64.2%，旋转准确率降至72.6%，表明过度修正引入布局漂移。

评估边界方面，自建基准缺乏统一量化指标（如FID、Chamfer Distance），且标注依赖人工修正，可能存在偏差。论文未报告计算效率，多阶段LLM调用导致的推理延迟未量化。代码开源，但超参数与GPU配置未详细披露，可复现性受限。

## 关联研究分析

从问题动机看，Code-as-Room与SceneWeaver均属于智能体驱动路线，但SceneWeaver侧重工具调用与自反思，依赖底层生成工具，而CaR侧重代码合成，直接生成可执行Blender代码。这一差异源于任务特性：SceneWeaver处理文本驱动的开放场景，需灵活调用工具；CaR处理俯视图驱动的完整房间，需精确几何控制，代码表示更利于确定性执行与局部编辑。CaR未对比SceneWeaver，可能因输入模态（图像 vs 文本）与输出表示（代码 vs 场景图）差异导致直接比较困难。

从方法设计看，CaR与SpatialGrammar均使用结构化表示，但SpatialGrammar采用领域特定语言（DSL）编码物理先验，侧重符号推理；CaR采用可执行代码，侧重几何实现。CaR引入的跨阶段记忆机制在SpatialGrammar中未体现，后者依赖LLM一次性生成或递归规划。CaR的记忆机制解决了长流程中的上下文遗忘，但可能引入早期错误传播风险，论文未讨论如何防止错误在记忆中的累积。

## 总结

Code-as-Room旨在解决俯视图到3D房间生成中的空间一致性与稳定性矛盾，切入点在于利用代码表示的确定性执行与跨阶段记忆缓解智能体长流程中的上下文遗忘。通过结构化执行框架与视觉反馈闭环，该方法在人类评估中实现了9.0的相似度与7.5的可用性，显著优于VIGA与直接生成基线。然而，其边界在于多阶段LLM调用导致的高延迟未量化，且自建基准缺乏跨数据集的标准化验证。当支持集增大或场景复杂度提升时，跨阶段记忆中的早期错误是否会累积并导致布局漂移，论文未给出回答。
