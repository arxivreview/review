研究机构：微软研究院、美国哥伦比亚大学

作者：Baolin Peng、Wenlin Yao、Qianhui Wu 等 14 人

论文原文见 [arXiv](https://arxiv.org/abs/2605.15040)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2605.15040)

> 智能体训练依赖大规模沙箱交互，但现有基础设施将环境管理耦合于特定训练栈，导致数据与配方难以跨域复用。本文提出 Orchard Env，一个 Kubernetes 原生的薄层环境服务，通过 Pod-IP 直连与运行时注入实现低延迟、高并发的沙箱管理。基于此服务，论文构建了 SWE、GUI 与个人助理三个领域的 SFT+RL 训练配方。该框架在开源同规模模型中刷新了多项基准记录，但其性能上限仍受限于骨干模型能力，且通用服务边界是否牺牲特定领域保真度尚存疑。

## 研究背景

智能体训练的核心瓶颈在于环境交互的规模化与可复用性。当模型通过强化学习（RL）或监督微调（SFT）优化策略时，每条轨迹需经历数十次沙箱内的命令执行与状态反馈。这一过程要求环境层具备高并发吞吐与低延迟响应，否则 GPU 利用率将因等待环境反馈而大幅降低。然而，环境层的架构选择直接决定了上层训练配方的可移植性：若环境管理与特定推理后端或训练循环深度绑定，则轨迹数据、奖励计算与评估协议无法独立迁移。

现有方案在环境层定位上存在显著分歧。托管沙箱平台（如 E2B、Daytona）提供便捷运行时，但限制了研究者对基础设施配置与成本的控制；垂直集成训练栈（如 MegaFlow、ProRL Agent）将环境作为子模块嵌入，虽实现了协同优化，却牺牲了与第三方 Harness 的兼容性；通用环境框架（如 ROCK）功能丰富，但未将环境隔离为最小服务边界。这种耦合导致轨迹数据集与训练配方往往绑定于特定基础设施，难以复现或跨域比较。本文的切入点在于将环境层重构为独立的薄层服务，使其在任务域、智能体 Harness 与流水线阶段三个维度上均可复用，从而解耦基础设施约束与模型能力演进。

## 核心方法

### 环境服务架构参照系

传统智能体训练基础设施通常采用垂直集成模式，环境管理、推理调度与训练循环共享同一进程空间或紧密耦合的 API。本文问题与该通用流程的关键差异在于：环境服务需作为独立微服务存在，不依赖特定 Harness 或 Trainer，同时保持与直接 Docker 调用相当的性能。这要求控制平面（生命周期管理）与数据平面（命令执行）在架构上彻底分离。

### 控制平面与数据平面解耦

Orchard Env 采用三层架构：客户端 SDK、FastAPI 编排器与 Pod 内代理。设计动机在于消除 Kubernetes exec/WebSocket 在热路径上的开销，解决高并发下 API Server 成为瓶颈的问题。编排器负责沙箱创建、就绪跟踪与孤儿清理，而所有执行与文件请求直接路由至沙箱 Pod IP，绕过 API Server。该机制通过 Pod-IP 直连实现低延迟通信，其物理含义是将控制流与数据流分离，使生命周期决策（冷路径）与命令执行（热路径）互不阻塞。

$$
L_{exec} = \frac{1}{N} \sum_{i=1}^{N} (t_{resp,i} - t_{req,i})
$$

其中 $L_{exec}$ 为平均命令执行延迟，$N$ 为测试命令数。该公式量化了数据平面解耦后的性能收益，实验显示其达到 0.28s，与 SkyPilot Code Sandbox（0.284s）持平，显著优于 E2B（0.747s）与 Modal（2.046s）。

### 运行时注入与信用分配 SFT

为支持异构任务环境，Orchard Env 引入运行时 Agent 注入机制，将轻量级 FastAPI 代理注入用户指定的 Docker 镜像，无需修改镜像构建流程。这一设计解决了静态烘焙代理导致的镜像适配成本高问题，使任意任务镜像可零修改接入。在训练层面，针对稀疏奖励导致的信号缺失，论文提出信用分配 SFT（Credit-assignment SFT）。其核心思想是利用回顾性价值估计，从失败轨迹中提取“有效上升段”作为监督信号。

$$
V(s_t) = \mathbb{E}[R | s_t, \text{outcome}]
$$

其中 $V(s_t)$ 为状态 $s_t$ 的回顾性价值，$R$ 为最终奖励。该公式通过结果条件化校准价值曲线，在 98.9% 的标注轨迹中呈现倒 U 型分布，峰值出现在探索阶段，衰减于失败提交前。这使得未解决轨迹中的部分进展可转化为有效的 SFT 信号，弥补了仅使用解决轨迹导致的监督信号稀疏问题。

## 实验评估

实验在 SWE-bench Verified、WebVoyager、Online-Mind2Web、DeepShop 与 Claw-Eval 上进行，基线覆盖开源 SWE/GUI Agent（如 OpenSWE-32B、MolmoWeb-8B）及前沿闭源模型（如 GPT-5、Gemini 3）。

| 系统 | 骨干模型 | SWE-bench Verified (%) | WebVoyager (%) | Online-M2W (%) | DeepShop (%) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Orchard-SWE (SFT+RL) | Qwen3-30B-A3B | 67.5 | — | — | — |
| OpenSWE-32B | Qwen2.5-32B | 62.4 | — | — | — |
| Orchard-GUI (SFT+RL) | Qwen3-VL-4B | — | 74.1 | 67.0 | 64.0 |
| MolmoWeb-8B | — | — | 78.2 | 35.3 | 42.3 |

Orchard-SWE 在 SWE-bench Verified 上以 67.5% 超越 OpenSWE-32B 的 62.4%；Orchard-GUI 在 Online-Mind2Web 与 DeepShop 上分别以 67.0% 和 64.0% 大幅领先 MolmoWeb-8B 的 35.3% 和 42.3%，平均成功率 68.4% 接近 Gemini computer-use-preview 的 69.3%。

消融实验显示，数据规模对 SFT 性能的影响大于选择策略。在 $N=512$ 时，不同策略间差距为 5.5 个百分点，而在 $N=2048$ 时缩小至 2.0 个百分点。RL 阶段贡献了主要增益：Orchard-GUI 从 SFT 的 52.0% 提升至 SFT+RL 的 68.4%，绝对提升 16.4 个百分点。值得注意的是，SFT 初始化的 RL 收敛性能显著优于基础模型初始化的 RL，前者在验证集上达到 50% 以上成功率，后者低于 40%，表明监督初始化提供了稳定探索所需的行为先验。

评估边界方面，论文未报告置信区间，且部分基线数值来自原始论文而非统一复现。代码与超参数已开源，但 Spot 实例的成本优化（0.022$/sandbox-hr）依赖于特定云环境配置，跨云可复现性需进一步验证。

## 关联研究分析

从问题动机看，Orchard 与 Agent0 均关注 RL 训练中的数据稀缺问题，但 Agent0 侧重算法层面的自进化机制，而 Orchard 侧重基础设施层面的环境服务化。Agent0 通过课程 Agent 与执行 Agent 协同进化解决数据生成问题，其环境管理仍耦合于特定训练栈；Orchard 则通过解耦环境层，使同一环境服务可支撑不同算法配方的训练，其贡献在于证明了环境通用性对训练效率的支撑作用。这一差异源于任务特性：Agent0 针对单一领域的深度优化，而 Orchard 面向多领域的横向扩展。

从方法设计看，Orchard Env 与 MCP（Model Context Protocol）在接口标准化理念上一致，但 Orchard 更底层，直接操作 Kubernetes 原语，而 MCP 侧重于工具调用的语义协议。MCP 解决的是工具描述与调用的标准化，Orchard 解决的是沙箱生命周期与执行的低延迟管理。两者互补：MCP 可运行于 Orchard Env 之上，提供工具语义层，而 Orchard Env 提供执行物理层。论文未探索 MCP 与 Orchard Env 的集成，这可能限制了其在复杂工具生态中的直接适用性。

## 总结

本文核心矛盾在于智能体训练基础设施的耦合性阻碍了数据与配方的跨域复用。Orchard 通过 Kubernetes 原生薄层服务解耦环境管理，以 Pod-IP 直连实现 0.28s 低延迟，支撑了 SWE、GUI 与个人助理三个领域的 SFT+RL 训练。实验证明该架构在开源同规模模型中刷新了 SWE-bench Verified（67.5%）与 GUI 平均成功率（68.4%）的记录，且环境服务引入的性能回归可忽略。其边界在于：通用服务边界是否导致特定领域（如 GUI）的保真度下降，论文未通过对比专用环境服务与通用服务在相同骨干模型下的性能差异来验证这一点。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
