# HuggingFace最新推荐论文 ｜MemTrace: Tracing and Attributing Errors in Large Language Model Memory Systems ｜记忆系统故障归因：从线性日志到执行图

作者：Xinle Deng、Ruobin Zhong、Hujin Peng 等 18 人

论文原文见 [arXiv](https://arxiv.org/abs/2605.28732)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2605.28732)

> 大语言模型（LLM）记忆系统长期面临“黑盒”困境：当Agent回答错误时，开发者无法区分是记忆构建时的信息丢失、检索时的匹配偏差，还是生成时的推理失误。现有基准仅评估最终结果，缺乏对故障因果路径的追溯能力，导致调试依赖人工逐行检查海量日志。本文提出MemTrace框架，将记忆系统的执行流转化为操作-变量有向无环图，通过智能体图探索自动定位最早且最小的故障操作集。该工作填补了记忆系统可调试性的空白，但归因准确率仍受限于图结构稀疏性与LLM推理能力，其作为自动优化信号的可靠性有待更大规模验证。

## 研究背景

记忆增强Agent通过跨会话保留状态实现长程任务，其核心机制是非参数化记忆系统（如RAG、Mem0）对信息的提取、更新与检索。然而，这些系统内部涉及复杂的LLM调用、向量检索与状态变更操作，任何环节的微小错误都可能沿信息流传播至最终输出。传统调试依赖时间戳日志，但日志是扁平序列，无法表达变量间的依赖关系——例如，一个早期会话中错误提取的用户偏好，可能在数轮对话后才导致检索失败，线性日志难以建立这种跨时间、跨操作的因果链。

现有LLM Agent诊断工作（如AgentRacer）聚焦于无状态系统的单步推理错误，假设故障局限于当前执行轨迹。但记忆系统的故障具有“延迟显现”与“跨会话传播”特性：故障源可能位于历史轨迹的任意位置，且被大量无关交互掩盖。现有记忆基准（如LoCoMo、LongMemEval）仅报告问答准确率，无法区分“系统未存储正确信息”与“系统存储了但未检索到”，更无法定位具体是哪个操作（如事实提取、记忆更新、检索排序）导致了信息丢失。这种可追溯性缺口使得记忆系统的迭代优化缺乏精确的反馈信号，开发者只能基于最终错误进行盲目提示工程。

## 核心方法

### 执行图表示与故障定义

本文首先将记忆系统执行过程形式化为有向无环二部图 $G = (V, O, E)$，其中 $V$ 为变量节点（如原始消息、记忆单元、提示词），$O$ 为操作节点（如LLM推理、检索、解析），$E$ 为信息流边。每个操作 $o \in O$ 定义输入集 $In(o) \subset V$ 与输出集 $Out(o) \subset V$。故障归因目标被定义为寻找“决定性错误集” $O^*$，即满足以下条件的最小操作子集：

$$
O^* = \arg\min_{O_c \subseteq O} |O_c| \quad \text{s.t.} \quad Z(G_{[O_c, *]}) = 0 \land \forall o \in Anc_G(O_c): o \text{ is correct}
$$

其中 $Z(G_{[O_c, *]})$ 表示将 $O_c$ 中故障操作的输出替换为正确值后，系统是否成功回答。该定义要求 $O_c$ 是最早的因果切点，其上游操作均正确，且干预后能恢复系统功能。这一形式化将模糊的“调试”转化为可计算的图论问题，区别于传统日志分析中基于时间顺序的启发式搜索。

### 智能体图探索与上下文管理

MemTrace将故障归因建模为智能体在图 $G$ 上的探索过程。初始化时，通过混合检索（稠密+稀疏+RRF融合）从历史轨迹中选取与问题最相关的源消息作为起始变量，避免全图搜索。探索阶段，智能体维护一个大小为 $N=16$ 的待探索列表（优先队列，按时间戳排序），每次迭代选取最早时间戳的变量 $v_t$，检查其关联的所有操作 $O(v_t)$。对每个操作，智能体将其子图 $G_o$ 转化为文本表示（含操作名、输入输出变量、依赖关系），并判断其是否满足决定性错误准则。若操作正确，则将其下游变量加入待探索列表；若发现故障，则终止探索。为应对大规模执行图，MemTrace引入工作上下文管理：支持操作子图的预览模式（省略变量值）、分页与正则搜索，并在上下文超过阈值 $T=272,000$ tokens时自动摘要。这种设计解决了线性日志无法表达变量依赖、且全图加载导致上下文爆炸的双重失效。

## 实验评估

实验基于MemTraceBench构建，该基准包含160个人工标注的真实故障案例，源自LoCoMo、LongMemEval、RealMem三个数据集，覆盖Long-Context、RAG、Mem0、EverMemOS四种记忆系统。基线为MemTrace-OBS（观察式基线，允许全局操作搜索但不遵循图依赖）。主实验结果显示，图探索策略显著优于观察式基线，尤其在较小模型上：GPT-4.1 mini的整体错误类型准确率（ETA）从20.00%提升至36.46%，故障操作识别准确率（OIA）从9.38%提升至14.17%。GPT-5.4上ETA从53.75%微升至54.38%，OIA从46.25%降至38.13%，表明大模型已具备较强的全局推理能力，图结构的约束收益递减。

| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| GPT-4.1 mini | MemTrace-OBS | 9.17 / 3.33 | 25.83 / 17.50 | 33.33 / 16.67 | 11.67 / 0.00 | 20.00 / 9.38 |
| GPT-4.1 mini | MemTrace | 20.83 / 4.17 | 41.67 / 26.67 | 35.83 / 23.33 | 47.50 / 2.50 | 36.46 / 14.17 |

| GPT-5.4 | MemTrace | 20.00 / 20.00 | 72.50 / 65.83 | 70.00 / 59.17 | 55.00 / 7.50 | 54.38 / 38.13 |

消融实验表明，添加源证据与先验知识可进一步提升归因质量。GPT-4.1 mini上，同时添加两者使ETA达45.83%，OIA达29.44%，且token成本降至521.80（千tokens），低于纯MemTrace的932.14。GPT-5.4上，添加源证据使ETA从65.83%升至69.17%，OIA从44.17%升至54.17%，token成本从1,659.04降至1,036.69。这表明外部证据有效缩小了搜索空间，降低了推理成本。

评估边界方面，MemTraceBench仅包含160个案例，样本量较小，且故障类型分布不均（系统相关错误占69.57%）。归因准确率整体偏低（最佳OIA仅46.25%），表明精确定位故障操作仍具挑战性。代码已开源，但依赖人工插桩构建执行图，对闭源系统不适用。

## 关联研究分析

从问题动机看，MemTrace与AgentRacer（Zhang et al., 2025a）均针对LLM Agent故障归因，但AgentRacer聚焦无状态多Agent系统的单步推理错误，假设故障局限于当前任务实例；MemTrace则针对有状态记忆系统，处理跨会话、跨操作的故障传播。这一差异源于任务特性：记忆系统的故障源可能位于历史轨迹任意位置，且被大量无关交互掩盖，线性日志无法表达变量依赖，必须引入图结构。AgentRacer未探索记忆系统的状态演化，其方法在记忆场景下失效，因为无法区分“信息未存储”与“信息存储但未检索”。

从方法设计看，MemTrace与软件工程中的根因分析（RCA）范式相似，但RCA通常基于结构化日志与统计模型，而MemTrace依赖LLM智能体在图上的探索。这一选择源于记忆系统操作的异构性与非结构化特性：记忆单元、提示词、检索结果等实体无法用统一张量表示，传统RCA的统计方法难以适用。MemTrace通过LLM的语义理解能力判断操作正确性，但这也引入了LLM推理误差，导致OIA准确率偏低。相比之下，Mem0等记忆系统本身未提供调试接口，其故障归因完全依赖外部工具，MemTrace填补了这一空白，但图构建依赖人工插桩，限制了其在未开源系统中的通用性。

## 总结

MemTrace旨在解决LLM记忆系统故障不可追溯的核心矛盾，通过将执行流转化为操作-变量图，利用智能体图探索自动定位最早且最小的故障操作集。该方法在GPT-4.1 mini上将整体ETA从20.00%提升至36.46%，并验证了归因信号可指导提示优化，提升端到端性能7.62%。然而，实验暴露了显著局限：最佳OIA仅46.25%，表明精确定位故障操作仍具挑战性；图构建依赖人工插桩，对闭源系统不适用；MemTraceBench样本量仅160，故障类型分布不均。当记忆系统规模扩大至百万级操作时，图探索的计算成本与LLM推理误差是否会抵消其归因收益，论文未给出回答。
