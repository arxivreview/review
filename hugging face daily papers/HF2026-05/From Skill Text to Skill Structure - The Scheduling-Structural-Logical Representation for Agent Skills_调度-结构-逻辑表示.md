> 代理技能长期以自然语言文档形式存在，导致机器难以区分调用接口、执行流程与资源风险。现有检索与审计方法被迫从冗长文本中反复推断这些语义分离的属性，造成效率低下与漏检。本文提出SSL表示，将技能解耦为三层结构化JSON图，以暴露不同粒度的机器可用证据。该方案在检索与风险审计中显著优于纯文本基线，但其作为中间表示的通用性尚未在端到端任务执行中得到验证。

## 研究背景

当代理系统从单次工具调用扩展至复杂工作流时，技能（Skill）作为封装指令、控制流与资源调用的能力包成为核心资产。然而，当前技能多以SKILL.md等文本工件形式存储，机器可解析的证据（如输入输出契约、执行阶段、副作用）混杂在自然语言描述中。这种“语义坍缩”导致下游系统无法直接获取结构化信号，必须依赖大语言模型（LLM）对长文本进行重复解析与推断，既增加了计算开销，又因文本噪声导致关键信息遗漏。

技能管理面临两大瓶颈：一是大规模技能库中的检索效率，语义相似度检索难以捕捉接口级与结构级差异；二是第三方技能的安全审计，自然语言指令与可执行代码的边界模糊，使得数据外泄、权限提升等风险难以静态识别。主流方法如SkillDAG侧重执行时的动态路由，LatentSkill侧重参数化内化以提升推理效率，但均假设技能表示已具备足够的机器可读性。本文切入点在于填补原始技能工件与下游系统之间的表示层空白，通过显式结构化暴露证据，解决“相关性-效用差距”与“风险不可见”问题。

## 核心方法

### 方法参照系

技能表示通常被视为检索或优化的隐式基底，如Voyager将技能作为可执行代码库，ToolkenGPT将工具映射为嵌入向量。本文问题与通用流程的关键差异在于：不关注技能如何生成或进化，而是关注如何将已有的非结构化文本工件转化为类型化、可验证的中间表示，以支持独立的检索与审计任务。

### 三层解耦架构

SSL将技能工件 $d$ 映射为类型化表示 $R = \langle r_{sch}, G_{str}, G_{log}, R_{cont}, R_{entry} \rangle$。其中 $r_{sch}$ 为调度层记录，$G_{str}$ 与 $G_{log}$ 分别为场景图与逻辑步骤图。

$$
R = \text{Normalize}(d) = \{ r_{sch}, G_{str}, G_{log} \}
$$

该公式定义了SSL的核心映射：调度层对应Memory Organization Packets，暴露意图签名与输入输出契约；结构层对应Script Theory，将操作分组为准备、获取、行动、验证等有序场景；逻辑层对应Conceptual Dependency，分解为原子动作与资源边界。设计动机在于解决文本工件中“调用接口”与“执行细节”纠缠的问题，使检索系统可仅依赖调度层进行快速匹配，而审计系统可仅依赖逻辑层进行静态风险检查，无需解析全文。

### LLM规范化与接地验证

SSL通过基于DeepSeek-V3.2的LLM规范化器实现，其核心约束是“接地性”（Groundedness）。规范化器提示词严格限定词汇表与模式，每个填充字段必须能在源工件中找到证据。

$$
\text{Valid}(R) = \mathbb{I}[\forall f \in R, \exists e \in d \text{ s.t. } f \text{ is supported by } e]
$$

该公式表示验证函数：仅当表示中所有字段 $f$ 均被源工件证据 $e$ 支持时，输出才有效。设计动机在于防止LLM在结构化过程中产生幻觉或推断隐藏行为，确保SSL作为“证据暴露器”而非“行为推断器”的可靠性。人工审计显示，83%的SSL输出被判定为源工件支持，验证了该接地策略的有效性。

## 实验评估

| 输入表示 | MRR@50 | NDCG@5 | Recall@10 |
| :--- | :--- | :--- | :--- |
| Desc_only | 0.588 | 0.608 | 0.761 |
| Full SKILL.md | 0.645 | 0.655 | 0.821 |
| Desc + Source Outline | 0.649 | 0.670 | 0.833 |
| Desc + SSL-Rich | **0.729** | **0.748** | **0.905** |

实验在6,184个公开技能语料库上进行，Skill Discovery任务使用431个意图级查询，Risk Assessment任务使用252个带六维风险标签的技能。基线覆盖纯文本（Desc, Full MD）与压缩控制（Source Outline），但缺失SkillDAG等图结构检索或SkillOpt等优化方法的对比，限制了与主流技能管理范式的直接可比性。在Skill Discovery中，Desc + SSL-Rich的MRR@50为0.729，较最强非SSL基线Desc + Source Outline的0.649提升0.080，且超过完整源文档Full SKILL.md的0.645，表明结构化字段而非文本长度是检索增益的来源。

| 输入表示 | Macro F1 | Macro Prec. | Macro Rec. |
| :--- | :--- | :--- | :--- |
| Full MD | 0.409 | 0.828 | 0.283 |
| Full SSL | 0.422 | 0.841 | 0.315 |
| MD + SSL | **0.509** | **0.884** | **0.382** |

消融实验显示，SSL的增益依赖于与源文档的组合而非替代。Full SSL单独使用的Macro F1仅为0.422，略高于Full MD的0.409，而MD + SSL组合达到0.509，提升0.101。这一反直觉结果表明，SSL的价值在于补充源文档中隐含的结构化证据，而非独立承载所有信息。在风险维度上，数据外泄（Data Exfiltration）的F1从0.511提升至0.699，权限提升（Privilege Escalation）从0.381提升至0.455，证实逻辑层暴露的原子动作与资源边界对识别细粒度风险至关重要。

评估边界方面，实验仅使用离线检索与审计指标，未验证SSL在端到端任务执行（如ALFWorld、WebShop）中的性能影响。规范化器使用DeepSeek-V3.2，但不同LLM骨干对SSL生成质量的影响未探讨。代码与数据集已开源，但6,184技能语料库的领域分布未详细披露，可能影响结果在特定垂直领域的泛化性。

## 关联研究分析

从问题动机看，SSL与SkillDAG均关注技能依赖，但SkillDAG侧重执行时的动态路由以优化任务成功率，而SSL侧重静态的结构化暴露以支持离线管理。这一差异源于任务特性：SkillDAG假设技能表示已足够清晰，瓶颈在于选择策略；SSL则假设瓶颈在于表示本身，需先解耦证据再谈路由。SSL未探索动态路由场景，其结构化开销在高并发执行中是否抵消精度优势，论文未给出回答。

从方法设计看，SSL与LatentSkill均解决上下文预算问题，但LatentSkill通过LoRA内化牺牲可解释性以提升推理效率，SSL通过结构化保留可审计性。这一冲突暗示了技能表示架构的根本取舍：参数化技能适合资源受限的推理场景，而结构化技能适合需要人工审计与安全治理的场景。SSL的三层JSON图比扁平化JSON更利于下游任务的泛化，因为其分层设计允许不同任务仅访问相关层（如检索仅用调度层，审计仅用逻辑层），但这一假设在跨任务组合场景中是否成立，缺乏实验验证。

## 总结

本文要解决的核心矛盾是技能工件中语义分离属性的文本纠缠，导致机器难以高效检索与审计。现有方法如SkillDAG与LatentSkill分别侧重路由优化与参数化内化，均假设表示已具备机器可读性，而SSL通过三层解耦架构显式暴露证据，解决了“相关性-效用差距”与“风险不可见”问题。SSL将技能映射为调度、结构、逻辑三层JSON图，并通过LLM规范化器确保接地性。实验证明，SSL在Skill Discovery中提升MRR@50至0.729，在Risk Assessment中提升Macro F1至0.509。本文的边界在于仅验证了离线管理任务，未探索SSL在端到端执行中的影响，且规范化器对LLM骨干的依赖性未充分探讨。当技能库规模扩大至数万级时，SSL的结构化开销是否在高并发检索中抵消其精度优势，论文未给出回答。
