# HuggingFace最新推荐论文 ｜Memory-Efficient Looped Transformer: Decoupling Compute from Memory in Looped Language Models ｜内存高效循环Transformer

论文原文见 [arXiv](https://arxiv.org/abs/2605.07721)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2605.07721)

> 循环语言模型通过重复执行Transformer层来提升推理深度，但标准实现中键值缓存（KV Cache）随循环次数线性增长，导致内存消耗与计算深度绑定。现有方案要么牺牲精度以压缩缓存，要么接受内存爆炸以保留全注意力，缺乏在恒定内存下扩展推理深度的架构。本文提出MELT，通过引入可学习门控机制更新固定大小的潜状态，将推理深度与内存消耗解耦。该设计在同等内存预算下超越了标准大语言模型，但训练流程依赖复杂的分块与蒸馏策略，且未验证长上下文精确检索能力。

## 研究背景

当模型通过增加推理循环次数来提升复杂任务表现时，内部状态必须保留历史键值信息以支持注意力计算。这种保留机制导致内存占用随循环次数 $T$ 线性增加，形成“推理深度-内存”耦合困境。为打破这一耦合，需引入一种既能累积历史信息、又能控制状态规模的更新机制，同时确保该机制不破坏预训练模型已习得的注意力对齐特性。

循环Transformer（Looped Transformer）通过复用同一组参数进行多次前向传播，在不增加参数量前提下提升每Token计算量，Ouro等模型已证明其推理能力可媲美参数量近两倍的静态模型。然而，其Append-only的KV缓存策略使得内存复杂度为 $O(N \times L \times T)$，限制了长序列或深推理场景的部署可行性。现有KV压缩技术如分组查询注意力（GQA）或跨层复用虽能降低内存，但往往以牺牲长程依赖精度为代价，且未解决循环架构特有的深度维度内存增长问题。MELT的切入点在于重构KV缓存的动态更新逻辑，将“追加”改为“门控更新”，从而在架构层面实现内存恒定。

## 核心方法

### 循环架构参照系

标准循环Transformer将 $N$ 层堆叠重复执行 $T$ 次，每次循环生成新的KV条目并追加至缓存。该流程的关键差异在于：MELT不扩展缓存长度，而是通过潜状态演化动态更新每层唯一的KV条目，将内存复杂度从 $O(N \times L \times T)$ 降至 $O(N \times L)$。

### 门控潜状态更新机制

MELT的核心改动发生在KV缓存生成环节。标准做法中，每个循环步骤直接计算并追加新的Key-Value对；MELT则引入一个独立于注意力计算的潜状态 $h_t^{[l]}$，该状态通过可学习门控机制跨循环更新，再投影为当前Token的Key和Value。这一设计解决了Append-only策略中内存随深度线性增长的失效问题，使模型在增加推理循环时无需额外内存开销。潜状态更新公式为：

$$ h_t^{[l]} = z_t^{[l]} \odot h_{t-1}^{[l]} + (1 - z_t^{[l]}) \odot x_t^{[l]} $$

其中 $z_t^{[l]}$ 为门控函数输出，$x_t^{[l]}$ 为当前隐藏状态。该公式的物理含义是：门控值 $z$ 控制历史潜状态与当前信息的混合比例，实现选择性记忆保留与覆盖。随后，潜状态通过投影矩阵生成Key和Value：

$$ k_t^{[l]} = W_K^{[l]} h_t^{[l]}, \quad v_t^{[l]} = W_V^{[l]} h_t^{[l]} $$

此设计将记忆动态与注意力检索解耦，确保Query-Key对齐在递归更新中保持稳定，避免了直接更新KV缓存可能导致的语义漂移。

### 两阶段过渡训练流程

架构突变导致预训练权重初始化后输出混乱，直接微调难以收敛。MELT采用两阶段训练解决此问题：第一阶段为插值过渡，并行计算LoopLM标准KV与MELT门控KV，通过线性插值系数 $\alpha$ 从0到1平滑迁移；第二阶段为注意力对齐蒸馏，冻结LoopLM作为教师，强制MELT各层各循环的注意力后表示与教师对齐。该流程解决了架构修改引发的表示漂移问题，确保MELT在获得内存优势的同时保留原模型的推理能力。

## 实验评估

实验在AIME、MATH-500、GPQA等10个基准上评估，基线覆盖Qwen3、Gemma4、DeepSeek-R1等标准LLM及Ouro循环模型，但缺失Mamba等纯SSM基线。MELT-1.6B在AIME24 pass@1达46.7，高于Qwen3-1.7B的43.1，但低于Ouro-1.4B的50.2；在MATH-500上，MELT为93.4，Ouro为94.4，Qwen3为90.6。

| 模型 | AIME24 pass@1 | MATH-500 Acc | HumanEval Acc | 32k总内存(GB) |
| :--- | :--- | :--- | :--- | :--- |
| Ouro-1.4B | 50.2 | 94.4 | 76.8 | 27.97 |
| MELT-1.6B | 46.7 | 93.4 | 81.7 | 9.49 |
| Qwen3-1.7B | 43.1 | 90.6 | 71.3 | 7.07 |

MELT在HumanEval上超越Ouro，表明门控机制在代码生成任务上可能优于全缓存策略。消融实验显示，移除注意力对齐蒸馏导致AIME24 pass@1从46.7降至44.8，移除分块训练则性能归零，证实训练流程对架构稳定性的关键作用。

| 消融变体 | AIME24 pass@1 | AIME25 pass@1 |
| :--- | :--- | :--- |
| 完整MELT | 46.7 | 33.3 |
| 无注意力蒸馏 | 44.8 | 32.9 |
| 无插值过渡 | 35.4 | 26.9 |
| 无分块训练 | 0.0 | 0.0 |

评估边界方面，论文未报告置信区间，且未测试长上下文精确检索任务（如RULER），无法验证门控机制在远距离依赖上的表现。代码尚未公开，训练需1040 GPU小时，复现成本较高。

## 关联研究分析

从问题动机看，MELT与FlashAttention等系统级优化路线存在根本差异。FlashAttention通过IO感知分块计算优化硬件利用率，但不改变算法复杂度；MELT则通过架构重构改变内存复杂度，属于算法级优化。两者均针对内存瓶颈，但MELT的解耦设计更适用于推理深度扩展场景，而FlashAttention更适用于长序列静态推理。MELT未采用GQA，导致其32k内存（9.49GB）高于Qwen3（7.07GB），这一差距源于架构选择而非优化不足，暗示门控机制与GQA的兼容性尚未探索。

从方法设计看，MELT与NLL-Guided SWAA等动态稀疏注意力方法均旨在平衡效率与精度，但路径不同。NLL-Guided SWAA通过层选择保留部分全注意力，MELT则通过门控更新实现全注意力下的内存恒定。前者依赖数据驱动的敏感度评分，后者依赖可学习门控动态。MELT的固定循环数限制使其无法适应不同输入的计算需求，而NLL-Guided SWAA的层选择机制天然支持动态计算分配。MELT在长程依赖任务上的表现未知，门控机制是否牺牲了精确检索能力，论文未提供证据。

## 总结

MELT解决的核心矛盾是循环推理中计算深度与内存消耗的耦合。其切入点在于将KV缓存从Append-only改为门控更新，通过潜状态演化实现内存恒定，这是标准循环架构无法做到的。方法上，MELT引入可学习门控机制更新固定大小潜状态，并设计两阶段过渡训练确保稳定性。实验证明，MELT-1.6B在AIME24 pass@1达46.7，32k内存仅9.49GB，低于Ouro的27.97GB。其边界在于固定循环数限制动态计算分配，且未验证长上下文精确检索能力。当输入复杂度差异显著时，固定循环数是否导致简单任务算力浪费或复杂任务推理不足，论文未给出回答。
