> 科学智能体系统长期受限于自然语言接口，导致处理时序、表格等结构化科学数据时产生信息损失与推理瓶颈。现有方案要么将非语言数据强行文本化，要么依赖人工预定义的工具调用流程，缺乏动态协作能力。本文提出 Eywa 框架，通过 FM-LLM“Tsaheylu”接口实现语言模型与领域专用基础模型的原生协作，并构建动态编排机制。该框架在效率与效用上优于纯语言基线，但其对底层 LLM 规划能力的依赖及在部分子域的性能波动，限制了其作为通用科学推理引擎的普适性。

## 研究背景

科学任务中的核心数据形态往往是非语言的，如时间序列、分子结构或晶体学参数。当智能体系统仅以自然语言为交互媒介时，这些结构化数据必须被序列化为文本，导致数值精度丢失与语义歧义，这构成了语言中心范式在科学计算中的根本局限。领域专用基础模型（Domain-Specific Foundation Models, FMs）已在特定科学领域展现出强大的预测能力，但它们通常不具备原生语言接口，无法直接参与基于文本的多智能体协作。

当前自主科研智能体研究主要沿两条路线演进：一是将 LLM 作为通用推理引擎，通过代码解释器或 API 调用外部工具，但这要求工具接口预先定义且缺乏动态适应性；二是构建多模态基础模型，试图统一表示异构数据，但训练成本极高且垂直领域深度不足。这两条路线均未能解决“如何让非语言专家模型直接参与语言推理闭环”的接口问题。Eywa 的切入点在于不改变 LLM 的语言推理核心，而是通过标准化接口赋予 FM 语言可解释的“代理”身份，使其成为智能体系统中的原生组件。

## 核心方法

### 方法参照系

本文问题可置于多智能体系统（Multi-Agent Systems, MAS）的通信拓扑优化范畴。标准 MAS 假设所有智能体共享自然语言作为通信介质，而本文的关键差异在于引入异构模态智能体，即不具备语言接口的 FM，并解决其与 LLM 智能体之间的语义对齐与任务分配问题。

### FM-LLM “Tsaheylu” 接口

传统工具调用中，LLM 生成代码或 API 请求，但缺乏对 FM 内部状态的结构化感知。Eywa 引入双向通信接口 $(\phi_k, \psi_k)$，其中查询编译器 $\phi_k: S \to U_k$ 将 LLM 的任务状态 $S$ 转化为 FM 的结构化配置参数 $U_k$，响应适配器 $\psi_k: O_k \to Z_k$ 将 FM 的原生输出 $O_k$ 映射为 LLM 可消费的结构化上下文 $Z_k$。

$$
\hat{y} = A_{LLM}(\psi_k(F_k(\phi_k(s), x_k)), s)
$$

该公式表明，FM 的计算结果并非以文本形式返回，而是以结构化数据形式直接注入 LLM 的推理状态，避免了文本化过程中的信息熵减。这一设计解决了纯语言智能体在处理高精度数值预测时，因序列化误差导致的决策偏差问题。

### 动态编排与混合拓扑

单一 EywaAgent 仅能处理单一模态任务，复杂科学问题往往需要跨模态协作。EywaOrchestra 引入规划器 $P$，根据任务输入 $\tau$ 动态选择系统配置 $c$，实例化包含 LLM Agent 与 EywaAgent 的混合拓扑。

$$
c \leftarrow P(q, x), \quad \hat{y} = M_c(q, x)
$$

规划器不依赖固定拓扑，而是基于任务特征（如数据模态、复杂度）自动决定调用哪些 FM 及协作方式。这种动态性解决了固定多智能体拓扑在异构任务中资源浪费或能力错配的问题，使得系统能在经济类任务中仅调用 TabPFN，而在气象类任务中调用 GraphCast，实现计算资源的按需分配。

## 实验评估

实验在自建 EywaBench 上进行，覆盖物理、生命、社会科学三大领域。基线包括单 LLM Agent、同质 MAS（Refine, Debate）及异质 LLM MAS（MoA, X-MAS）。缺失符号回归专用基线（如 PTB-Search），导致无法直接对比“结构化计算”与“符号搜索”在公式发现任务上的优劣。

| 方法 | Physical (Utility) | Life (Utility) | Social (Utility) | Overall Tokens |
| :--- | :--- | :--- | :--- | :--- |
| Single-LLM-Agent | 0.5871 | 0.3718 | 0.8048 | 3137 |
| EywaAgent | 0.5616 | 0.3402 | 0.7689 | 3137 |
| EywaMAS | 0.6381 | 0.3798 | 0.7959 | 11214 |
| EywaOrchestra | 0.6249 | 0.3682 | 0.7830 | 8335 |

表格显示，EywaAgent 在 Physical 和 Life 领域的 Utility 低于 Single-LLM-Agent，仅在 Social 领域持平或略低，这与论文声称的“整体提升 6.6%”存在表面矛盾，需核实其加权计算方式。EywaMAS 在 Physical 领域显著优于基线（0.6381 vs 0.5871），但 Token 消耗激增（11214 vs 3137）。EywaOrchestra 在保持较高 Utility 的同时，将 Token 消耗降至 8335，验证了动态编排在效率上的优势。

消融实验表明，更强的 LLM 骨干（gpt-5-mini vs gpt-4.1-nano）能提升 EywaAgent 性能，但边际收益递减。在 Economy 领域，单 Agent EywaAgent 已接近最优，说明并非所有任务都需要复杂多智能体拓扑，这支持了动态编排的必要性。

评估协议缺乏置信区间报告，且 EywaBench 为自建基准，外部可比性有限。代码已开源，但 FM 部署依赖本地 MCP 服务器，复现需配置特定硬件环境。

## 关联研究分析

从问题动机看，Eywa 与 ChemCrow 均致力于解决 LLM 在特定科学领域的幻觉问题，但 ChemCrow 依赖专家预定义的工具集，而 Eywa 通过 MCP 接口实现 FM 的即插即用。这一差异源于任务特性：ChemCrow 聚焦化学反应路径，工具边界清晰；Eywa 面向通用科学数据，需要动态适配不同 FM 的输入输出格式。Eywa 的接口标准化程度更高，但牺牲了工具调用的语义深度，LLM 仅能传递配置参数，无法理解 FM 内部计算逻辑。

从方法设计看，Eywa 与 AI Scientist 共享端到端科研闭环思想，但 AI Scientist 的执行层是代码解释器，而 Eywa 的执行层是异构 FM。AI Scientist 依赖 LLM 生成代码来模拟实验，存在执行错误风险；Eywa 直接调用预训练 FM，保证了计算结果的数值可靠性。然而，Eywa 的 LLM 仅负责规划，不参与数值推导，这可能导致在需要因果推理的任务中，系统缺乏对 FM 输出结果的批判性验证能力。

## 总结

Eywa 旨在解决语言中心智能体在处理非语言科学数据时的接口瓶颈，通过 FM-LLM“Tsaheylu”接口实现原生协作。该框架在 EywaBench 上展示了动态编排的效率优势，EywaOrchestra 在保持 0.6249 Physical Utility 的同时将 Token 消耗控制在 8335。然而，实验数据显示 EywaAgent 在部分子域的 Utility 低于纯 LLM 基线，且缺乏与符号回归方法的直接对比，暴露了其在复杂推理任务中的局限性。当任务涉及跨模态因果推断而非单纯预测时，仅依赖 FM 数值输出的协作模式是否足以支撑科学发现的可证伪性，论文未给出回答。
