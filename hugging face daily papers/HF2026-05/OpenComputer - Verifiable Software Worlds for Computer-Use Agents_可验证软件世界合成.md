# HuggingFace最新推荐论文 ｜OpenComputer: Verifiable Software Worlds for Computer-Use Agents ｜可验证软件世界合成

研究机构：美国宾夕法尼亚大学、美国北卡罗来纳大学教堂山分校

论文原文见 [arXiv](https://arxiv.org/abs/2605.19769)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2605.19769)

> 计算机使用智能体的训练与评估长期受限于桌面环境构建成本高及状态验证不可靠的双重瓶颈。现有基准多依赖人工策展或LLM作为裁判，前者难以规模化，后者在细粒度应用状态判断上存在系统性偏差。OpenComputer将验证器构建前置为环境合成的组织原则，通过自动生成的硬编码检查器定义任务边界并计算奖励。该框架在33个桌面应用上实现了1000个任务的自动化合成，但开源模型在其中的表现远低于其在OSWorld上的成绩，暴露出当前智能体在异构软件环境中的泛化局限。

## 研究背景

计算机使用智能体（Computer-Use Agent, CUA）旨在通过像素级截图与GUI动作操作真实软件，其核心挑战在于环境状态的可观测性与可验证性。传统评估依赖LLM-as-a-judge，但LLM对截图的感知存在盲区，无法准确判断隐藏在应用内部状态（如文件元数据、数据库记录）中的细微错误，导致奖励信号失真。这种验证缺陷直接制约了基于强化学习（RL）的策略优化，因为不可靠的奖励会导致智能体学习错误的行为模式。

CUA基准的演进经历了从静态轨迹数据集（如Mind2Web）到交互式沙箱环境（如OSWorld、AndroidWorld）的转变。然而，这些交互式基准仍主要依赖人工构建任务实例与编写奖励检查逻辑，导致任务规模受限且难以覆盖长尾应用场景。人工构建不仅耗时，且不同开发者对“任务成功”的定义存在主观差异，使得跨基准的性能比较缺乏一致性。OpenComputer切入这一痛点，将“可验证性”作为环境合成的第一性原理，通过自动化生成应用特定的状态验证器，解决了环境构建与奖励计算解耦的问题，实现了大规模、可复现的桌面任务合成。

## 核心方法

### 验证器生成与状态检查

CUA任务合成的通用流程通常包含环境初始化、任务指令生成与奖励计算三个环节。OpenComputer的关键差异在于，它不将验证视为下游评估步骤，而是将其作为环境构建的前置约束。设计动机在于解决LLM Judge在细粒度状态判断上的不可靠性，通过程序化接口直接读取应用内部状态，确保奖励信号的客观性与可审计性。

对于每个应用 $a \in A$，OpenComputer生成一个特定的验证器模块 $V_a$，该模块暴露一组CLI子命令，通过JSON输出结构化状态。验证器覆盖的内容状态、偏好设置、历史记录、文件I/O等所有可检查的表面。例如，浏览器任务通过远程调试协议（CDP）验证，办公任务通过UNO接口或文档解析验证。验证器开发遵循严格的测试协议，包括单元测试与集成测试，失败端点进入调试-修复-重试循环，直至稳定。这一机制确保了只有当任务结果可以通过程序化方式可靠检查时，该任务才会被纳入基准，从而从源头保证了奖励信号的质量。

### 自进化验证与任务合成

初始验证器可能包含对应用架构的脆弱假设或端点覆盖不全，这些缺陷在合成测试中难以完全暴露。OpenComputer引入自进化验证层，通过执行反馈闭环修复验证器错误。设计动机在于利用真实智能体运行产生的状态差异，识别验证器与参考判断之间的不一致，从而迭代优化检查逻辑。

自进化过程首先生成约15个校准任务，由强智能体在沙箱中执行并记录轨迹。随后，LLM评估器与程序化验证器分别对最终状态进行判断，比较器识别两者间的分歧。若分歧归因于验证器错误，系统修改检查代码、端点实现或文档，并在同一缓存状态上重新执行验证，直至一致或达到迭代预算。任务合成基于验证器栈进行：生成器提出候选任务，过滤掉难度不足或数据不可生成的任务，然后匹配现有验证器端点。若目标状态可检查但未暴露，则扩展验证器。最终任务实例 $\tau = (x, e, c)$ 包含指令 $x$、环境初始化 $e$ 与机器可检查的成功标准 $c$。奖励计算采用部分信用机制：

$$ R = \frac{N_{pass}}{N_{total}} $$

其中 $N_{pass}$ 为通过检查的数量，$N_{total}$ 为总检查数。该公式允许智能体在未完成所有子任务时仍获得部分奖励，缓解了长程任务中全有全无的信用分配难题，同时保持了成功条件的精确性与机器可检查性。

## 实验评估

OpenComputer基准涵盖33个桌面应用与1000个任务，评估了GPT-5.4、Claude-Sonnet-4.6等前沿模型及Qwen-3.5、EvoCUA等开源模型。基线覆盖较广，但缺失UI-TARS等专用GUI智能体的直接对比，且未包含基于结构化数据（如HTML）的传统方法，限制了与早期范式的横向比较。

| 模型 | OSWorld (%) | Success Rate (%) | Avg. Steps | Time/Step (s) | Avg. Reward (%) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| GPT-5.4 | 75.0 | 68.3 | 19.0 | 16.5 | 88.4 |
| Claude-Sonnet-4.6 | 72.5 | 64.4 | 31.5 | 20.8 | 76.6 |
| Kimi-K2.6 | 73.1 | 58.8 | 35.7 | 33.0 | 70.7 |
| GUI-OWL-1.5-8B | 52.3 | 5.7 | 73.6 | 9.43 | 27.8 |
| EvoCUA-8B | 46.1 | 10.9 | 67.0 | 9.7 | 38.1 |

GPT-5.4以68.3%的成功率领先，但其平均步数（19.0）显著低于其他模型，表明其具备更强的动作组合能力。开源模型表现急剧下滑，GUI-OWL-1.5-8B从OSWorld的52.3%跌至5.7%，EvoCUA-8B从46.1%跌至10.9%，揭示了现有模型在异构桌面环境中的泛化瓶颈。

| 指标 | 数值 |
| :--- | :--- |
| 硬编码验证器任务级对齐率 | 97.3% |
| LLM Judge任务级对齐率 | 92.2% |
| 自进化后验证器对齐率 | 94.1% |
| 自进化修复率 | 89.4% |

验证器可靠性分析显示，硬编码验证器在120个任务上与人类判断的对齐率为97.3%，高于LLM Judge的92.2%，尤其在细粒度状态判断上优势明显。自进化层将验证器对齐率从85.2%提升至94.1%，修复了89.4%的验证器侧错误，证明了执行反馈闭环的有效性。

评估边界方面，OpenComputer依赖沙箱环境，未涵盖真实网络延迟或硬件差异的影响。部分任务（如Draw.io中的视觉连接判断）难以完全程序化验证，论文承认此类任务存在验证盲区。代码已开源，但验证器构建依赖特定应用接口，迁移至新应用需重新生成验证器，扩展成本未量化。

## 关联研究分析

从问题动机看，OpenComputer与OSWorld同属交互式基准，但OSWorld侧重人工策展的任务多样性，而OpenComputer侧重自动化合成的规模与可验证性。OSWorld的任务构建依赖专家知识，难以覆盖长尾应用，而OpenComputer通过验证器约束任务生成，确保了奖励的可靠性，但可能牺牲了任务的自然度与复杂度上限。这种差异源于任务特性：桌面软件的状态空间庞大且异构，人工编写检查逻辑的成本随应用数量线性增长，而自动化验证器生成可将边际成本降至常数。

从方法设计看，OpenComputer与AgentScaler同属环境合成框架，但AgentScaler侧重API环境的模拟，而OpenComputer侧重原生桌面应用的状态检查。AgentScaler使用数据库后端模拟API响应，适用于工具调用场景，而OpenComputer通过CDP、D-Bus等协议直接读取应用内部状态，适用于GUI操作场景。这种差异源于交互模态：GUI操作涉及视觉感知与状态变化的耦合，仅靠API模拟无法捕捉屏幕渲染与用户意图的一致性，而OpenComputer的验证器直接检查最终状态，避免了中间过程的歧义。

## 总结

OpenComputer解决了CUA基准构建中环境合成与状态验证解耦的核心矛盾，通过将验证器前置为环境构建的组织原则，实现了大规模可验证桌面任务的自动化生成。其自进化验证层通过执行反馈闭环修复验证器错误，将人类对齐率提升至94.1%，证明了程序化验证在细粒度状态判断上的可靠性。然而，开源模型在OpenComputer上的成功率（5.7%-10.9%）远低于其在OSWorld上的表现（46.1%-52.3%），暴露出当前智能体在异构软件环境中的泛化局限。当应用状态涉及视觉几何判断（如Draw.io中的箭头连接）时，硬编码验证器的覆盖率是否足以支撑有效的奖励信号，论文未给出定量回答。
