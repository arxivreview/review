> 智能体编译知识库在持续使用中会积累不完整、错误与冗余缺陷，导致检索保真度下降。现有方法多优化构建策略，但已部署知识库的重建成本高昂，缺乏后构建精炼范式。本文提出 DeepRefine，通过查询驱动的多轮交互定位缺陷，并利用强化学习优化无参考下的精炼策略。该方法在分布外设置下稳定提升了多种构建器与检索器的下游性能，但其增益是否完全归因于知识库质量而非检索器适配，论文未提供隔离验证。

## 研究背景

检索增强生成（RAG）依赖外部知识库提供事实依据，但静态知识库无法从重复查询中积累结构化经验。智能体编译知识库（Agent-Compiled Knowledge Base）通过 LLM 智能体摄入源数据、合成文章并维护交叉引用，使知识库具备可进化性。然而，这类知识库常存在系统性质量缺陷，包括证据链缺失（不完整）、低置信度断言（错误）及指代消解歧义（冗余）。这些缺陷在迭代使用中复合，直接降低检索精度与下游任务表现。

当前研究主要聚焦于优化知识库构建策略，如 AutoGraph-R1 通过强化学习微调构建器。但在实际部署中，知识库往往已构建完成，重新训练构建器并全量重编译在计算成本与运维上均不现实。这催生了后构建精炼（Post-construction Refinement）的需求，即在不重建的前提下，利用用户查询定位并修复知识库缺陷。核心难点在于：大规模关系连接的知识库难以穷举检查以定位缺陷，且真实场景缺乏黄金参考来指导精炼策略的学习。

## 核心方法

### 方法参照系

本文问题可置于智能体推理框架下，但目标从生成答案转为生成编辑动作。标准 Agentic KBQA 输出最终答案，而 DeepRefine 输出针对知识库三元组的 `insert_edge`、`delete_edge` 或 `replace_node` 操作序列。关键差异在于，DeepRefine 的推理过程不直接服务于单次查询回答，而是服务于知识库状态的增量更新。

### 查询驱动缺陷定位与溯因

传统方法遍历全库检查缺陷，计算复杂度随库规模线性增长。DeepRefine 采用查询条件化的多轮交互，仅扩展与当前查询相关的子图邻域。设计动机是避免全库遍历，将定位复杂度限制在查询相关子图内。具体流程为：首先通过密集检索获取 0 跳子图 $G_q^{(0)}$；若查询不可答，则迭代扩展子图，每次从候选三元组中选取与查询嵌入最相关的 top-M 条，合并为 $i$ 跳子图 $G_q^{(i)}$。交互终止后，基于历史 $H_q$ 进行错误溯因（Error Abduction），从不完整、错误、冗余三个维度推断潜在缺陷 $I_q$。

$$ G_q^{(i)} = G_q^{(i-1)} \cup \text{TopM}(\{ (h,r,t) \mid h \in E_q^{(i-1)} \lor t \in E_q^{(i-1)} \}, q) $$

该公式表示第 $i$ 跳子图由前一跳子图与连接其节点的新候选三元组中相关性最高的 M 条合并而成，实现了局部化缺陷定位。

### 无参考强化学习策略优化

溯因得到的缺陷 $I_q$ 需转化为具体编辑动作，但缺乏黄金参考评估动作优劣。DeepRefine 引入超越草稿增益（Gain-Beyond-Draft, GBD）奖励，量化精炼后知识库 $G_f'$ 相对于草稿 $G_f$ 在下游 RAG 任务上的准确率提升。设计动机是解决非可微奖励下的策略学习问题，使精炼动作直接对齐下游任务效用。采用组相对策略优化（GRPO）算法端到端训练，移除 KL 散度项以降低计算开销。

$$ R_{GBD} = \text{ACC}(A_{refined}, A_{golden}) - \text{ACC}(A_{draft}, A_{golden}) $$

该公式表示奖励为精炼后答案与黄金答案的匹配度减去草稿答案的匹配度，确保精炼动作带来净收益。

## 实验评估

实验在分布外（OOD）设置下进行，涵盖 SimpleQA（NQ, PopQA）、Multi-hop QA（2WikiQA, Musique）及 Conversation QA（LOCOMO）。基线包括三种构建器（Naive, AR1, Graphify）与四种检索器（Subgraph, ToG, HippoRAG, HippoRAG2）。未对比传统 KB 精炼方法如 KGRefiner，可能低估了 LLM 精炼相对于规则/模型驱动方法的相对优势。

| 构建器 | 检索器 | 2WikiQA F1 (原始) | 2WikiQA F1 (DeepRefine-8B) | Musique F1 (原始) | Musique F1 (DeepRefine-8B) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Graphify | HippoRAG2 | 13.62 | 32.91 | 8.10 | 8.45 |
| AR1 | HippoRAG2 | 37.25 | 38.60 | 27.96 | 30.30 |
| Naive | HippoRAG2 | 35.91 | 36.03 | 25.33 | 26.33 |

在 Graphify 构建器上，DeepRefine-8B 将 2WikiQA F1 从 13.62 提升至 32.91，增幅显著；而在 Naive 构建器上，2WikiQA F1 仅从 35.91 提升至 36.03，增幅微弱。这表明精炼收益高度依赖初始知识库的质量缺陷程度，高质量知识库的边际收益递减。

消融实验显示，移除 RL 训练（DeepRefine-8B w/o RL）后，性能提升幅度缩小甚至出现负迁移。例如在 Graphify+HippoRAG 设置下，2WikiQA F1 从 13.23 提升至 11.84（负迁移），而带 RL 版本提升至 13.46。这验证了 GBD 奖励对引导精炼策略避免有害编辑的关键作用。

评估边界方面，论文未报告计算效率对比（仅提及 AutoGraph-R1 重建耗时 6,782.8s，DeepRefine 精炼耗时 3,201.7s），未提供置信区间，且代码未公开。指标仅使用 RAG F1，未评估幻觉率或可执行性，无法全面反映知识库质量变化。

## 关联研究分析

从问题动机看，DeepRefine 与 AutoGraph-R1 均利用强化学习优化知识库，但前者针对后构建精炼，后者针对构建时策略。AutoGraph-R1 假设知识库尚未构建，通过 RL 学习最优构建动作；DeepRefine 假设知识库已存在，通过 RL 学习修复动作。这一差异源于部署场景的不同：AutoGraph-R1 适用于新领域知识库初始化，DeepRefine 适用于存量知识库维护。根源在于，构建时优化可全局规划结构，而精炼时优化受限于局部查询驱动，导致 DeepRefine 难以修复全局结构性缺陷。

从方法设计看，DeepRefine 与 ToG 共享图交互机制，但 ToG 用于多跳推理路径搜索，DeepRefine 用于缺陷定位。ToG 的 Beam Search 旨在找到答案路径，DeepRefine 的迭代扩展旨在暴露不可答性。差异在于，ToG 的交互目标是收敛到答案，DeepRefine 的交互目标是发散到缺陷邻域。这导致 DeepRefine 的交互历史包含更多“失败”路径，为溯因推理提供了更丰富的错误信号，但也增加了上下文长度压力。

## 总结

DeepRefine 解决了存量智能体编译知识库无法低成本重建的矛盾，通过查询驱动定位与 GBD 奖励强化学习，实现了无参考下的增量精炼。在 Graphify 构建器上，2WikiQA F1 从 13.62 提升至 32.91，证明了精炼范式的有效性。然而，实验显示精炼收益高度依赖初始知识库质量，Naive 构建器上增益微弱，且未隔离验证增益是否源于知识库质量提升还是检索器适配。当初始知识库已接近高质量阈值时，查询驱动精炼的边际收益是否持续为正，论文未给出回答。
