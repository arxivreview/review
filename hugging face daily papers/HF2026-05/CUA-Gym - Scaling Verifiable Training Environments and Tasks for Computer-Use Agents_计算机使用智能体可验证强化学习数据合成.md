> 计算机使用智能体（Computer-Use Agent, CUA）的强化学习后训练长期受制于可验证奖励数据的稀缺，人工构建任务-环境-奖励三元组成本极高且难以规模化。现有方案要么依赖视觉语言模型（VLM）评判导致奖励噪声，要么局限于单一浏览器环境，无法覆盖桌面级工作流。CUA-GYM 通过多智能体对抗协同生成机制，自动化产出大规模确定性奖励训练数据。该工作验证了数据与环境多样性对CUA性能的关键作用，但其合成环境对真实系统复杂性的覆盖仍存疑。

## 研究背景

CUA 的强化学习后训练依赖可验证奖励强化学习（Reinforcement Learning with Verifiable Rewards, RLVR）范式，其核心在于为每个任务提供确定性的奖励信号以驱动策略优化。然而，CUA 的 RLVR 实例并非简单的“问题-答案”对，而是由自然语言指令 $t$、可执行环境状态 $s$ 和奖励函数 $r$ 构成的三元组 $(t, s, r)$。这三个组件必须严格对齐：指令需与环境状态匹配，奖励函数需准确反映任务完成度。这种结构性耦合使得人工构建单个三元组需数小时专家工作，且成本随应用多样性指数级增长，导致 CUA 的 RLVR 数据集规模比数学或代码域小数个数量级。

主流数据合成路线存在根本性缺陷。监督学习数据集虽覆盖多样应用，但提供的是轨迹级模仿目标而非结果奖励，无法直接用于 RL 优化。VLM-as-a-judge 框架能评估任意任务，但引入的奖励噪声会 destabilize 策略优化，ZeroGUI 的消融实验已证实此点。代码原生管线（如 GUI-Genesis）虽能生成确定性奖励，但局限于浏览器模拟环境，无法覆盖操作系统级桌面任务或跨应用工作流。CUA-GYM 的切入点在于：将环境本身作为可扩展轴，通过自动化合成高保真模拟环境，解决“奖励可验证性”与“环境覆盖范围”之间的张力。

## 核心方法

### 方法参照系

CUA-GYM 置于 RLVR 数据合成范式下，与 SWE-smith 等代码域方法共享“程序化合成任务+确定性奖励”的核心逻辑。关键差异在于：代码域任务可简化为问题陈述与可检查答案，而 CUA 任务需同时协调指令、环境状态与奖励函数三者的一致性，且环境需支持状态注入与重置以支持分布式训练。

### 对抗式协同生成

传统方法由单一智能体同时构建环境状态与奖励函数，导致奖励倾向于复现构建过程而非测量任务完成度。CUA-GYM 引入信息隔离机制，将生成器（Generator）与判别器（Discriminator）解耦。生成器编写 `initial_setup.py` 和 `golden_patch.py` 构建初始与黄金状态，判别器在沙箱中仅基于任务指令 $t$ 和两个环境状态独立编写 `reward.py`。奖励函数定义为渐进式评分：

$$r(s, \tau) = \sum_{i=1}^{k} w_i \cdot \mathbb{I}(\text{criterion}_i \text{ satisfied})$$

其中 $w_i$ 为子标准权重，$\mathbb{I}$ 为指示函数。该设计确保奖励函数从任务意图而非构建过程推导，避免奖励作弊。

### 环境规模化合成

CUA-GYM-HUB 解决环境覆盖瓶颈。基于 O*NET 职业分类与 Anthropic Economic Index 软件使用分布，合成 94 个自包含模拟 Web 应用。每个应用暴露统一状态 API，支持状态注入与会话隔离。状态注入允许同一应用实例化不同任务初始状态，会话隔离确保分布式 RL 工作并发运行时无状态干扰。环境合成采用多智能体管线：规划智能体生成设计规范，开发智能体实现应用，Web 智能体通过 Playwright 验证交互正确性，迭代直至收敛。

## 实验评估

实验在 OSWorld-Verified 与 WebArena 上评估，基线包括 Qwen3.5 基座模型及开源 CUA 模型（EvoCUA、OpenCUA 等），但未对比 MobileRL 等在线 RL 方法。CUA-GYM-A3B 将 Qwen3.5-35B-A3B 基座从 54.5% 提升至 62.1%（+7.6 pp），CUA-GYM-A17B 将 Qwen3.5-397B-A17B 基座从 62.2% 提升至 72.6%（+10.4 pp）。在 WebArena 上，A3B 从 40.8% 提升至 44.5%，A17B 从 54.0% 提升至 56.0%，验证了合成 Web 环境到真实浏览器的迁移能力。

| 模型 | OSWorld-Verified (%) | WebArena (%) |
| :--- | :--- | :--- |
| Qwen3.5-35B-A3B (Base) | 54.5 | 40.8 |
| CUA-GYM-A3B | 62.1 | 44.5 |
| Qwen3.5-397B-A17B (Base) | 62.2 | 54.0 |
| CUA-GYM-A17B | 72.6 | 56.0 |

消融实验揭示数据与环境多样性的互补作用。固定 3K 轨迹，环境从 10 个增至 80 个，OSWorld-Verified 分数从 50% 提升至 59%；固定 80 环境，轨迹从 3K 增至 6K，分数从 59% 提升至 62%。环境多样性带来的增益（+9 pp）大于轨迹量翻倍（+3 pp），证实环境覆盖是独立缩放轴。RL 训练自发诱导多动作工具调用，轨迹长度压缩 33–45%，源于组归一化优势估计下步数预算压力，策略隐式选择打包确定性子序列。

评估边界存在局限：最大规模 RL 运行仅报告单种子，未提供置信区间；合成环境缺乏认证流程、第三方集成、网络延迟等真实系统复杂性；OSWorld-Verified 任务分布可能偏向特定应用类型。可复现性方面，论文开源了完整管线、数据集与环境，但 512 GPU 集群的 5 天训练成本（约 61,440 GPU-hours）限制了复现门槛。

## 关联研究分析

从问题动机看，CUA-GYM 与 GUI-Genesis 均致力于合成可验证环境，但 GUI-Genesis 局限于单一 Flask 应用，而 CUA-GYM 通过 O*NET 与 AEI 加权覆盖 94 个应用类别，解决环境覆盖广度问题。这一差异源于任务特性：GUI-Genesis 针对特定应用的后训练，CUA-GYM 面向通用知识工作自动化，需反映真实软件使用分布。CUA-GYM 未探索环境保真度与合成成本的权衡，91% 的模拟应用源码在 2.5K–10K LOC 区间，是否足以捕捉真实应用的长尾交互模式存疑。

从方法设计看，CUA-GYM 的信息隔离机制与 SWE-smith 的 AST 变异形成对比。SWE-smith 通过代码结构变异生成 bug，奖励由单元测试确定；CUA-GYM 通过对抗式智能体生成任务-奖励对，奖励由程序化断言确定。关键差异在于：SWE-smith 的奖励验证依赖代码执行环境，CUA-GYM 需处理 GUI 状态的视觉-结构化双重表示。CUA-GYM 的 VLM 辅助过滤阶段（教师模型 rollout + LLM 多数投票）弥补了程序化奖励对表面级失败（如 UI 主题错误）的盲区，但引入额外计算开销，其边际收益在数据充足时是否递减，论文未给出回答。

## 总结

CUA-GYM 解决的核心矛盾是 CUA RLVR 数据中“奖励可验证性”与“环境覆盖范围”的不可兼得。现有方法或因 VLM 奖励噪声无法稳定训练，或因环境局限无法覆盖桌面工作流。CUA-GYM 通过对抗式协同生成与规模化环境合成，自动化产出 32,112 个验证三元组，在 OSWorld-Verified 上将开源 CUA 性能提升至 72.6%（A17B）与 62.1%（A3B），证实数据与环境多样性是独立缩放轴。其边界在于合成环境对真实系统复杂性的近似：认证流程、网络延迟、第三方集成等长尾交互未被覆盖，且单种子实验无法排除随机性影响。当模拟环境保真度提升至何种阈值，性能增益才会饱和，论文未提供答案。
