> 导读：LLM 智能体在开放环境中执行工具调用时，常因无法区分外部数据与内部指令而违反领域策略，导致状态被非法篡改。现有运行时防护多依赖概率化检测或静态规则匹配，缺乏对复杂时序依赖的数学保证，且拒绝后难以自动恢复任务。LEANGUARD 将领域策略编译为 Lean 4 形式化代码，在工具调用边界进行确定性准入决策，并引入证明引导修复机制。该工作为形式化方法在动态智能体环境中的落地提供了新路径，但其修复搜索空间的完备性与在复杂多步任务中的泛化能力仍存疑。

## 研究背景

当智能体面对包含恶意指令的外部数据（如网页、邮件）时，其内部推理机制往往无法区分“数据”与“控制指令”，导致执行被劫持。这种间接提示注入（Indirect Prompt Injection, IPI）使得智能体在看似正常的交互中执行破坏性操作。为应对此威胁，运行时验证（Runtime Verification, RV）被引入，通过在动作执行前拦截并检查工具调用，确保行为符合安全策略。然而，传统 RV 依赖人工构建的复杂逻辑公式，难以适应动态变化的环境状态，且一旦拒绝调用，智能体往往陷入死循环或任务中断。

当前领域在“形式化保证”与“任务效用”之间存在深层矛盾。形式化方法（如 VeriGuard）能提供数学上的正确性保证，但规范构建成本高，且无法处理 LLM 输出的非确定性；概率化方法（如 GuardAgent）泛化性好，但缺乏可验证的边界保证。LEANGUARD 的切入点在于利用 Lean 4 交互式证明助手的特性，将自然语言策略转化为可执行且可证明的代码，并通过元编程实现自动修复，试图在提供强安全保证的同时，通过反馈与修复机制维持任务连续性。

## 核心方法

### 运行时策略执行与可信证据 grounding

LEANGUARD 将智能体视为状态转换控制器，在语言模型与工具之间插入一个基于 Lean 4 的运行时。与常规运行时防护直接解析模型输出不同，LEANGUARD 首先将模型提出的工具调用视为不可信数据，通过领域适配器从权威后端快照和日志中提取“可信证据”（如订单状态、用户确认记录）。这一设计解决了模型可能通过注入文本伪造授权（如声称“客户已批准”）的问题，确保策略评估仅基于系统内部真实状态。

### 带作用域的时间逻辑策略评估

策略评估是 LEANGUARD 的核心，其创新在于将策略表达为包含过去时间算子的 Lean 谓词。常规策略仅检查当前状态，而 LEANGUARD 引入了 PREVIOUS、ONCE 和 SINCE 三个过去时间算子，并支持按主体、会话或资源进行作用域限制。例如，要求“在修改订单前必须已读取该订单”这一时序依赖，可通过作用域化的时间算子精确表达。

准入决策函数 $D_P(c_t)$ 定义为：

$$ D_P(c_t) = \text{allow} \iff \bigwedge_{p \in P} p(c_t) \land \bigwedge_{r \in R} r(c_t) \land \bigwedge_{f \in F} \neg f(c_t) \land \text{ErrorFree}_P(c_t) $$

其中 $P, R, F$ 分别为适用的许可、要求和禁止规则。该公式的物理含义是：只有当所有许可满足、所有要求成立、无禁止规则触发且评估过程无错误时，调用才被允许。这种“失败即关闭”（Fail-closed）机制防止了因数据缺失导致的误授权。

### 证明引导修复与反馈恢复

当调用被拒绝时，LEANGUARD 提供两种恢复路径。一是反馈引导恢复，返回违规规则 ID 与自然语言提示，辅助模型自我修正。二是证明引导修复，利用 Lean 元编程搜索附近合规调用。修复问题被形式化为存在性证明：

$$ \exists x' \in C_t. \text{EditOK}(x_t, x') \land D_P(c_t(x')) = \text{allow} $$

其中 $C_t$ 为候选编辑集，$\text{EditOK}$ 确保编辑保留用户意图。Lean 的 `guard_repair?` 策略尝试候选项，并通过内核检查证明其合规性。这一机制解决了传统形式化方法“只拒不改”的局限，将安全拦截转化为可计算的修复过程。

## 实验评估

实验在 $\tau^2$-bench（多步工具调用合规性）和 DTap（提示注入攻击）上进行，评估了 Qwen3.5 系列（0.8B-9B）及 Qwen3.8-27B 模型。基线对比主要覆盖无防护（None）、LEANGUARD（LG）及 LEANGUARD+反馈（LG+F）三种设置。

| 模型 | $\tau^2$-bench 任务成功率 (%) | | | DTap 直接攻击成功率 (%) | |
| :--- | :---: | :---: | :---: | :---: | :---: |
| | None | LG | LG+F | None | LG+F |
| Qwen3.5-0.8B | 48.9 | 41.4 | 45.3 | 46.7 | 3.3 |
| Qwen3.5-2B | 68.3 | 66.9 | 72.7 | 53.1 | 3.4 |
| Qwen3.5-4B | 83.8 | 79.5 | 82.4 | 71.6 | 7.5 |
| Qwen3.5-9B | 84.9 | 80.9 | 83.1 | 74.4 | 11.0 |
| Qwen3.8-27B | 77.7 | 75.9 | 71.2 | 40.3 | 3.7 |
| **All models** | **72.7** | **68.9** | **70.9** | **57.9** | **5.9** |

在 $\tau^2$-bench 上，LEANGUARD 执行了 0 次被 Lean 策略禁止的调用，而无防护基线至少执行了 33 次。引入反馈后，任务成功率从 68.9% 回升至 70.9%，与无防护的 72.7% 相比无显著差异（$p=0.21$）。在 DTap 上，直接攻击成功率从 57.9% 降至 5.9%，间接攻击从 22.3% 降至 3.8%。

| 模型 | 被拦截调用数 (Blocked) | | 恢复动作数 (Recovered) | |
| :--- | :---: | :---: | :---: | :---: |
| | LG | LG+F | LG | LG+F |
| Qwen3.5-0.8B | 426 | 383 | 5 | 5 |
| Qwen3.5-2B | 271 | 144 | 8 | 13 |
| Qwen3.5-4B | 91 | 62 | 9 | 12 |

反馈机制显著降低了重复被拦截的调用数（从 983 降至 719），并提升了恢复动作数（从 34 增至 48）。证明引导修复在重放的 252 个因参数值导致的拒绝中，成功修复了 88 个（34.9%），中位耗时 2 ms。

评估边界方面，LEANGUARD 仅检查工具调用，无法拦截纯文本响应中的攻击（如医疗诊断操纵）。此外，DTap 实验采用只读部署，限制了写操作，可能高估了保护效果。代码未开源，复现依赖 Lean 4 环境。

## 关联研究分析

从方法设计看，LEANGUARD 与 VeriGuard 同属形式化路线，但 VeriGuard 侧重生成可验证代码，而 LEANGUARD 侧重运行时策略执行与修复。LEANGUARD 的“证明引导修复”是 VeriGuard 未涉及的创新，解决了形式化方法在动态环境中灵活性不足的问题。然而，LEANGUARD 未与 GuardAgent 等主流运行时防护方法直接对比，无法排除其性能提升仅源于 Lean 策略的严格性而非机制优势。

从问题动机看，LEANGUARD 与 Agent-C 均使用时间逻辑约束，但 Agent-C 的公式构建复杂且依赖人工，LEANGUARD 通过 Lean 元编程实现了自动修复。然而，LEANGUARD 的修复搜索空间 $C_t$ 是有限集，对于复杂多步任务中需要大幅重构意图的场景，其修复能力可能受限。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

LEANGUARD 针对 LLM 智能体工具调用中的策略违规问题，提出了基于 Lean 4 的运行时验证与修复框架。其核心在于将策略形式化为可执行代码，并通过证明引导修复机制在拒绝后自动寻找合规调用。实验表明，该框架在 $\tau^2$-bench 上实现了零违规执行，且在 DTap 上将直接攻击成功率从 57.9% 降至 5.9%，同时通过反馈机制保持了任务效用。然而，其修复能力依赖于有限的候选编辑集，且未覆盖纯文本攻击。当任务需要跨多步的复杂意图重构时，证明引导修复的搜索空间是否足以覆盖所有合规路径，论文未给出回答。
