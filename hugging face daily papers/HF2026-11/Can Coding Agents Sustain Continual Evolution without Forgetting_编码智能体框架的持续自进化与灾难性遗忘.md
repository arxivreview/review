# HuggingFace最新推荐论文 ｜Can Coding Agents Sustain Continual Evolution without Forgetting? ｜编码智能体框架的持续自进化与灾难性遗忘

研究机构：清华大学

作者：Shangziqi Zhao、Yitong Zhang、Jia Li

论文原文见 [arXiv](https://arxiv.org/abs/2611.03219)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2611.03219)

> 导读 编码智能体在软件工程任务中的性能提升，日益依赖于协调模型、工具与环境的运行时框架（Harness）的自进化，而非仅靠调整基础模型参数。现有自进化方法多聚焦于单一任务类型的独立优化，忽视了实际开发中智能体需跨任务序列持续适应的需求，导致在适应新任务时严重丧失旧任务能力。本文通过构建跨数据集的持续进化实验，系统评估了现有方法在跨任务场景下的表现，并深入剖析了导致性能退化的框架级冲突根源。该研究揭示了当前自进化范式在稳定性与可塑性平衡上的根本缺陷，为设计冲突感知的智能体框架提供了关键实证依据，但其结论受限于特定基础模型与单智能体架构，跨模型泛化性仍待验证。

## 研究背景

当编码智能体面对复杂的软件工程任务时，其表现不仅取决于基础模型（Foundation Model）的代码生成能力，更受制于协调模型、工具与环境的运行时框架（Harness）。框架定义了智能体如何感知任务、调用工具及执行操作，其设计差异可导致同一模型在基准测试上的性能产生巨大波动。为了在不修改模型参数的前提下提升智能体能力，框架自进化（Harness Self-Evolution）应运而生，它通过分析执行轨迹自动优化框架代码。然而，这种优化通常针对特定任务类型（如代码修复）进行，当智能体需要在不同任务类型（如从代码修复转向测试生成）间持续适应时，框架的修改往往与旧任务的需求产生冲突，引发灾难性遗忘。

在软件工程领域，智能体常被期望处理多种任务，如修复缺陷、生成测试和添加新功能。现有自进化方法如 AHE 和 Meta-Harness 虽在单任务上表现优异，但缺乏对跨任务持续进化的考量。当框架针对新任务进行优化时，其引入的验证逻辑、工作流或资源管理策略可能与旧任务不兼容，导致旧任务性能急剧下降。这一现象类似于持续学习中的稳定性-可塑性困境，但在框架层面尚未被系统研究。本文旨在填补这一空白，通过实证研究揭示持续框架进化中的灾难性遗忘现象及其成因。

## 核心方法

### 方法参照系：持续框架自进化形式化

本文研究的持续框架自进化，是将单任务自进化扩展至多任务序列的场景。在标准自进化中，给定执行轨迹 $\mathcal{T}$，进化算法 $\Omega$ 更新框架 $H$ 为 $H' = \Omega(H, \mathcal{T})$。本文将其形式化为在有序数据集序列 $\mathcal{D} = (D_0, D_1, \dots, D_K)$ 上的迭代更新：

$$H_{i+1} = \Omega(H_i, \mathcal{T}_i)$$

其中 $\mathcal{T}_i$ 是从数据集 $D_i$ 中收集的执行轨迹。理想情况下，进化后的框架 $H_{i+1}$ 应在提升当前任务 $D_i$ 性能的同时，保持对先前任务 $D_j$ ($j < i$) 的性能不退化。本文通过量化源任务在目标任务进化后的性能下降，定义灾难性遗忘为：

$$\Delta_{forget} = Eval(H_{j+1}, D_j) - Eval(H_{i+1}, D_j)$$

该公式直接衡量了框架在适应新任务后，对旧任务评估性能的绝对损失，为后续冲突分析提供了量化基准。

### 核心创新：框架级冲突分类与归因

本文的核心贡献在于识别并分类了导致灾难性遗忘的框架级冲突。通过对 520 条执行轨迹的人工分析，作者将框架修改归纳为三类冲突：验证冲突、工作流冲突和预算策略冲突。验证冲突源于框架引入的针对特定任务的检查或约束，如提交门控（Submission Gate）对交付物类型的强制要求。工作流冲突则涉及任务解决程序的差异，如系统提示中强制执行的步骤顺序。预算策略冲突关乎时间与计算资源的管理，如超时重试机制。

为验证各类冲突的影响，本文设计了消融实验，将特定冲突类型的修改引入最优框架。例如，在从 SWE-Bench 进化到 SWT-Bench 时，框架引入了仅允许测试文件修改的提交门控。这一修改在 SWT-Bench 上有效，但在 SWE-Bench 上导致性能降至 0.0%，因为 SWE-Bench 要求修改源代码。该设计动机在于隔离不同冲突类型对性能退化的具体贡献，揭示验证冲突（尤其是交付物冲突）是导致灾难性遗忘的最主要因素，占比达 87.1%。

## 实验评估

实验在 SWE-Bench Verified、SWT-Bench 和 FeatureBench 三个数据集上进行，使用 DeepSeek-V4-Flash-0731 作为基础模型，Mini-SWE-Agent 作为初始框架。评估协议包括单任务进化和跨任务持续进化，通过六组进化方向测试灾难性遗忘。基线方法为 AHE 和 Meta-Harness，未包含多智能体协作基线。

| 进化方向 | 方法 | 初始性能 (%) | 进化后性能 (%) | 相对下降 (%) |
| :--- | :--- | :--- | :--- | :--- |
| SWE → SWT | AHE | 96.0 | 0.0 | 100.0 |
| SWE → SWT | Meta-Harness | 94.0 | 1.8 | 98.0 |
| SWE → Feature | AHE | 96.0 | 68.0 | 29.0 |
| SWE → Feature | Meta-Harness | 94.0 | 32.0 | 66.0 |

单任务进化显示，AHE 在 SWE-Bench 上从 82.0% 提升至 96.0%，Meta-Harness 达到 94.0%。然而，在持续进化中，性能退化显著。例如，AHE 在 SWE-Bench 进化后转向 SWT-Bench，其 SWE-Bench 性能完全丧失（下降 100%）。Meta-Harness 在 SWE-Bench 转向 FeatureBench 时，性能下降 66%。这表明现有方法在跨任务适应时，几乎无法保留旧任务能力。

消融实验进一步量化了冲突类型的影响。引入验证冲突导致 SWE-Bench 性能从 96.0% 降至 0.0%，执行时间增加 69%。工作流冲突使性能降至 66.0%，执行时间增加 235%。预算策略冲突对性能影响较小，但显著增加执行时间。这证实了验证和工作流冲突是性能退化的主因，而预算策略主要影响效率。

评估边界方面，实验仅使用单一基础模型，未验证跨模型泛化性。此外，进化轮次和任务采样量有限，可能影响结论的统计显著性。代码已开源，但复现需依赖特定沙箱环境。

## 关联研究分析

从问题动机看，本文与 AHE 和 Meta-Harness 形成直接对比。AHE 和 Meta-Harness 均假设进化目标为单一任务类型，通过闭环或 Pareto 前沿优化框架。本文指出，这种假设在实际多任务场景中失效，因为框架修改具有任务特异性。差异根源在于任务特性：代码修复与测试生成对交付物和验证逻辑的要求截然不同，导致框架优化方向冲突。本文未探索多智能体架构是否能通过角色隔离缓解此冲突，这是一个潜在的盲区。

从方法设计看，本文与 SWE-agent 等单智能体框架研究形成互补。SWE-agent 关注框架初始设计，而本文关注框架的动态演化。与 Live-SWE-agent 等自进化方法相比，本文未引入运行时工具生成，而是聚焦于框架代码的离线修改。这种设计选择使得冲突分析更清晰，但可能低估了动态适应对遗忘的缓解作用。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

本文揭示了编码智能体框架在持续自进化中的灾难性遗忘问题，指出验证和工作流冲突是主要成因。通过跨任务实验，证明了现有方法在适应新任务时严重丧失旧任务能力，如 AHE 在 SWE-Bench 上性能下降 100%。该研究为设计冲突感知的框架提供了实证依据，但其结论受限于单基础模型和单智能体架构。当基础模型能力增强时，框架冲突是否仍会导致同等程度的遗忘，论文未给出回答。
