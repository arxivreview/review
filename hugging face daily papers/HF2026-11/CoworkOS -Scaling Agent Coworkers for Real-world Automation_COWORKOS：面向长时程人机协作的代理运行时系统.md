> 导读 代理智能体在长时程复杂任务中面临全局连贯性与局部执行效率的冲突，现有工作流编排方法多聚焦于静态结构搜索或单次任务执行，难以支撑跨会话的持续监控与动态协作。COWORKOS 提出了一种分离任务策略与执行管理的运行时架构，通过 Main Agent 自主规划与 Coordinator Runtime 状态持久化，实现了复杂生产力任务与长时程监控的统一处理。该架构引入共享应用对象与分层工作空间，将人类反馈直接嵌入执行循环，并在递归自我改进（Recursive Self-Improvement, RSI）任务中验证了运行时系统对模型能力的放大效应。其价值在于确立了从“工作流编排”向“运行时协作”的范式转移，但缺乏显式工作流结构可能增加细粒度故障归因的难度。

## 研究背景

当代理系统处理如软件交付或模型训练监控等长时程任务时，单一决策上下文难以同时容纳全局目标约束与局部工具调用的海量中间状态——这一矛盾称为全局连贯性与局部执行效率的冲突。为解决此问题，早期研究依赖 Chain-of-Thought (CoT) 或 ReAct 等静态推理轨迹，但这些方法在任务中断或环境状态变更时缺乏恢复机制。随着任务复杂度提升，多智能体协作（Multi-Agent System, MAS）成为主流，然而现有 MAS 框架如 MetaGPT 仍依赖预定义角色分工，难以适应开放域中动态变化的协作拓扑与人类实时介入需求。

当前领域重心正从“工作流结构自动优化”转向“运行时状态管理”。DAAO 等方法通过难度估计动态分配算子，解决了查询自适应问题，但其生成的结构仍是静态图，无法处理跨会话的持续监控。COWORKOS 抓住了这一被忽略的运行时维度，将优化责任从外部编排器转移至模型内部决策与运行时基础设施的协同，旨在构建一个支持人类直接编辑工件、代理异步执行且状态可恢复的 Cowork Harness。

## 核心方法

### 方法参照系：从静态图到动态运行时

在标准的工作流编排中，系统通常通过搜索算法（如蒙特卡洛树搜索）生成固定的有向无环图（DAG），执行时按图遍历。COWORKOS 的关键差异在于摒弃预定义图结构，采用 Main Agent 实时决策动态生成执行轨迹。其核心在于将任务形式化为 $T = (g, E, A, V, B)$，其中 $g$ 为目标，$E$ 为包含人类与进程的环境，$A$ 为动作空间，$V$ 为验收标准，$B$ 为资源预算。环境状态演化遵循 $s_{k+1} = F_E(s_k, a_k, u_k, \epsilon_k)$，其中 $u_k$ 代表人类直接编辑，$\epsilon_k$ 代表外部进程变化。这一形式化将人类反馈与外部事件纳入状态转移函数，而非仅作为外部输入。

### 分层代理运行时架构

COWORKOS 采用 Main Agent、Coordinator Runtime 和 Subagents 的三层架构，以解决全局上下文污染与局部执行隔离的矛盾。Main Agent 作为用户接口与全局规划者，其决策过程遵循策略 $\pi_M$：

$$ a^M_t \sim \pi_M(\cdot | g, h^M_t, F_t) $$

其中 $h^M_t$ 为 Main 保留的交互历史，$F_t$ 为新反馈。该公式表明 Main 仅基于全局目标与关键反馈决策，而非所有中间步骤。当任务需要并行或独立处理时，Main 通过 Coordinator 委派 Subagent。Subagent 的初始上下文 $c_{i,0}$ 由 Main 的有界背景 $b(h^M_{t_i})$、授权工具 $\Gamma_i$ 和技能目录 $S_i$ 构成：

$$ c_{i,0} = \Phi_S(d_i, b(h^M_{t_i}), \Gamma_i, S_i) $$

此设计动机在于防止 Subagent 的长轨迹中间步骤污染 Main 的决策上下文，同时通过 Coordinator 维护持久化状态 $\xi_k$，确保异步执行与中断恢复的可靠性。Coordinator 的状态转移逻辑 $F_C$ 保证了委派、执行更新与反馈在模型决策边界间的持久化传递。

### 共享应用生态与状态持久化

为支持人机协作，COWORKOS 构建了共享应用对象（Shared Application Object）机制，允许人类与代理直接编辑同一文档、CAD 模型或 Blender 场景。人类编辑 $u_k$ 被视为任务指导而非独立指令通道，直接改变环境状态 $s_k$。在状态管理上，系统通过检查点（Checkpointing）与恢复机制确保持续性。观察源提交游标与事件至持久化 Inbox，Main 在决策边界确认反馈后，运行时才标记事件为已处理。若发生中断，Main 可从保存的上下文快照与任务状态恢复，并检查当前进程状态以决定重试或继续。这一机制解决了长时程任务中因上下文重置或进程重启导致的状态丢失问题，实现了执行连续性。

## 实验评估

实验在 12 个通用代理基准与 6 类真实世界应用场景中进行，对比 OpenHands、Codex 与 DeepSeek Harness。基线覆盖侧重于主流开源代理框架，但未包含 DAAO 等工作流自动优化方法，因后者侧重结构搜索而非运行时执行。

| 方法 | 年份 | SkillsBench (%) | MLE-Bench (%) | Tau-3 Banking (%) |
| :--- | :--- | :--- | :--- | :--- |
| COWORKOS | 2026 | 49.48 | 51.83 | 59.88 |
| OpenHands | 2025 | 44.15 | 42.95 | 55.64 |
| Codex | 2026 | 40.71 | 39.22 | 52.50 |
| DeepSeek Harness | 2026 | 36.94 | 35.90 | 49.48 |

COWORKOS 在 SkillsBench 上达到 49.48%，较 OpenHands 的 44.15% 提升 5.33 个百分点，在 MLE-Bench 上达到 51.83%，较 DeepSeek Harness 的 35.90% 提升 15.93 个百分点。在递归自我改进（RSI）实验中，COWORKOS 使用 GLM-5.3 对 Qwen3.6-35B-A3B 进行五轮自动后训练，八项基准平均分从 33.19 提升至 42.95（+9.76），其中 AutomationBench 提升 33.15 个百分点，BFCL V4 提升 7.35 个百分点。

消融分析显示，RSI 实验中 R1 轮平均提升 3.75 点，R2 轮提升 1.04 点，表明初期数据管道优化收益显著，后期边际收益递减。评估边界方面，实验未报告置信区间，且未对比轻量级工作流方法在标准推理基准（如 GSM8K）上的开销，无法判断运行时架构在简单任务上的效率损失。代码已开源，但部分专有应用接口依赖特定环境配置。

## 关联研究分析

从问题动机看，COWORKOS 与 DAAO 均追求动态适应，但路径截然不同。DAAO 通过变分自编码器估计查询难度，动态分配算子子集，其优化发生在策略层，生成的工作流结构在执行前已确定。COWORKOS 则通过 Main Agent 实时决策动态生成执行轨迹，优化发生在执行层，无预定义图结构。这一差异源于任务特性：DAAO 针对单次查询的推理效率，COWORKOS 针对跨会话的持续协作。COWORKOS 的运行时动态决策是否牺牲了 DAAO 所强调的“可验证性”与“形式化保证”，论文未给出回答。

从方法设计看，COWORKOS 与 Lean4Agent 在可靠性保障上形成互补。Lean4Agent 利用 Lean4 形式化方法对代理工作流进行建模与验证，提供数学可证明的安全性，适用于高利害场景。COWORKOS 则通过 Checkpointing 与 Recovery 机制解决长时程任务中的中断恢复问题，侧重于执行连续性而非错误归因。COWORKOS 缺乏显式工作流结构，是否导致其在复杂任务中难以进行细粒度的故障归因，论文未给出回答。

## 总结

COWORKOS 解决了长时程任务中全局连贯性与局部执行效率的冲突，通过分离任务策略与执行管理，构建了支持人机共享工件编辑的运行时架构。其核心贡献在于将人类反馈直接嵌入环境状态转移，并通过 Coordinator Runtime 实现异步执行与状态持久化。实验证明，该架构在复杂生产力任务上优于主流开源框架，并在 RSI 任务中将模型平均分提升 9.76 点。然而，缺乏显式工作流结构可能导致细粒度故障归因困难，且运行时开销在简单推理任务上的影响尚未量化。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
