> 导读
> 文本到SQL（Text-to-SQL）任务旨在将自然语言问题转换为可执行的结构化查询，其核心价值在于消除非技术用户访问数据库的门槛。当前主流方法依赖大语言模型（LLM）Agent进行多轮工具调用与自我修正，虽在复杂查询上取得高精度，但面临推理延迟高、API成本昂贵及数据隐私泄露的三重瓶颈。本文提出LuthorSQL，一种非自回归的7B参数模型，通过单次前向传播并行填充有界语法槽位，并引入执行验证器作为置信度路由信号，构建“快-慢”级联架构。该工作证明了本地小模型可替代大部分云端Agent调用，在保持精度的同时大幅降低部署成本，但其语法覆盖率的硬约束限制了复杂嵌套查询的处理能力。

## 研究背景

当企业部署自然语言数据库接口时，需在查询准确性、响应速度与数据隐私之间做出权衡。前沿LLM Agent通过多轮工具调用探索数据库，虽能处理复杂逻辑，但每次查询需消耗数秒至数十秒，且敏感数据需发送至外部API。为解决此问题，模型级联（Model Cascade）策略被引入，即利用低成本模型处理简单输入，仅将困难样本路由至高性能模型。然而，现有级联方法多依赖模型自置信度或投票一致性作为路由信号，在Text-to-SQL任务中，由于SQL语法严格且执行结果离散，自置信度往往无法准确反映查询的语义正确性，导致路由决策失效。

领域内研究重心正从单纯提升生成准确率转向推理效率与部署经济性的优化。传统微调模型虽成本低，但泛化能力弱；LLM提示工程虽灵活，但推理成本高。LuthorSQL的切入点在于利用SQL任务特有的“可执行性”：通过确定性编译器生成候选SQL并执行，利用执行结果的一致性作为比自置信度更可靠的验证信号。这一思路将Text-to-SQL从纯语言生成问题转化为结构化计划预测与执行验证问题，旨在量化本地小模型对云端Agent的成本替代率，并验证其在分布外数据上的鲁棒性。

## 核心方法

### 方法参照系：非自回归槽位填充与级联架构

LuthorSQL属于LLM提示工程与模型训练优化的混合路线，其核心架构由System 1（LuthorSQL）和System 2（LLM Agent）组成。与端到端生成SQL的自回归模型不同，LuthorSQL采用非自回归的槽位填充范式，将SQL生成分解为离散的结构决策。该流程首先由7B模型预测查询计划（Query Plan），随后通过确定性编译器生成SQL，最后由验证器评分。这一设计的关键差异在于：标准流程依赖模型直接输出SQL字符串，而LuthorSQL输出的是抽象的槽位状态，由编译器负责语法构建，从而将语法正确性从模型能力中解耦。

### 核心创新：有界语法计划与因子化评分

传统自回归模型在生成复杂SQL时易产生语法错误或幻觉列名。LuthorSQL引入有界语法（Bounded Grammar）$G$，将SQL查询抽象为离散槽位集合。每个槽位$\sigma$对应一个有限选项集$O_\sigma(q, D)$，包括模式项、标签集或字面量候选。模型通过单次前向传播，利用LoRA适配器在OmniSQL-7B骨干网络上并行计算所有槽位的隐藏状态$h_\sigma$。

计划$p$的评分通过因子化分解实现，其总分为各活跃决策$d$的对数概率之和：

$$ score(p) = \sum_{d \in p} \log P(d | q, e, D) $$

该公式的物理含义是：由于槽位决策相互独立，模型无需进行自回归解码即可通过优先队列枚举出Top-$k$个最高分计划。这一设计消除了自回归解码的串行延迟，使得单次前向传播即可生成多达32个候选计划，显著提升了推理速度。

### 核心创新：执行验证器与置信度级联路由

由于槽位评分无法捕捉全局SQL结构的交互效应，LuthorSQL引入第二个LoRA适配器VALHARD作为验证器。验证器读取编译后的SQL字符串、模式及问题，输出标量质量分数$s(q, c)$。为提供可靠的路由信号，系统定义置信度为验证器对前两个执行结果组（Result Groups）的分数边际（Margin）。

在级联架构中，若验证器边际超过阈值$t$，System 1直接返回答案；否则，将候选计划及执行结果作为上下文传递给System 2（Claude Opus 5.5）。路由决策基于以下逻辑：

$$ \text{Route to System 2 if } \max(s(c_1)) - \max(s(c_2)) < t $$

其中$c_1$和$c_2$分别代表最高分和次高分结果组中的候选SQL。该设计利用执行反馈的离散性（结果相同或不同）作为强监督信号，解决了传统自置信度在SQL任务中噪声大、区分度低的问题，实现了基于语义等价性的精准路由。

## 实验评估

实验在BIRD、Spider、KaggleDBQA等基准上进行，重点评估执行准确率（EX）、推理延迟及API成本。基线对比涵盖了纯LLM Agent（Claude Opus 5.5）、传统微调模型及现有级联方法。

| 方法 | 数据集 | 执行准确率 (EX) | 推理延迟 (s) | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| LuthorSQL (System 1) | BIRD Hidden Test | 68.03% | 0.84 | 单GPU，k=32 |
| Claude Opus 5.5 (Agent) | BIRD Dev (796 q) | 77.26% | - | 云端API |
| LuthorSQL + Opus (Cascade) | BIRD Dev (796 q) | 77.12% | - | 成本降低24.8% |
| LuthorSQL (Zero-shot) | Snowflake | 57.1-59.3% | - | 转译执行 |

LuthorSQL在BIRD隐藏测试集上达到68.03% EX，虽低于云端Agent的77.26%，但其单次推理仅需0.84秒。在级联模式下，通过设置阈值$t=3.0$，System 1本地处理了约50%的查询，使整体API成本降低24.8%-33.3%，而精度损失控制在1.2点以内。值得注意的是，在BIRD Dev集上，LuthorSQL的EX为59.39%，显著低于领域SOTA方法（如CHESS的71.10%），这反映了其语法覆盖率（84.6%）对复杂查询的限制。

消融实验显示，验证器Margin路由显著优于投票一致性和问题长度路由。在重命名Schema和Post-cutoff数据集上的测试表明，Opus Agent的高分部分源于基准污染（复现48-92%的Gold SQL），而LuthorSQL在未见过的数据库上仍保持96.1%的本地准确率，证明了其泛化能力。然而，评估协议中未包含计算效率分数（VES），且成本计算基于列表价而非实际发票，可能低估了实际部署中的网络开销。

## 关联研究分析

从问题动机看，LuthorSQL与FrugalGPT（Chen et al., 2024）同属模型级联范式，但FrugalGPT依赖模型自置信度或外部评分器，而LuthorSQL利用SQL任务特有的执行反馈作为路由信号。这一差异源于Text-to-SQL任务的强验证性：执行结果的正确性比语言模型的困惑度更能反映查询的语义正确性。相比之下，DIN-SQL（Pourreza et al., 2023）通过任务分解提升LLM推理能力，虽精度更高，但未解决成本与隐私问题，LuthorSQL则通过牺牲部分复杂查询精度换取了部署经济性。

从方法设计看，LuthorSQL继承了SQLNet（Xu et al., 2017）的槽位填充思想，但将其扩展至多表复杂查询并引入LLM骨干网络。与SmBoP（Rubin and Berant, 2021）等基于图神经网络的解码器相比，LuthorSQL利用OmniSQL-7B的语义理解能力处理模式链接，避免了显式图构建的复杂性。然而，其有界语法设计限制了处理CTE和标量子查询的能力，这与领域内追求端到端生成复杂SQL的趋势形成张力。查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

LuthorSQL针对LLM Agent在Text-to-SQL任务中成本高、延迟大及隐私泄露的核心矛盾，提出了一种基于非自回归槽位填充与执行验证器置信度路由的级联架构。该工作证明了本地7B模型可通过单次前向传播生成高质量候选计划，并利用执行结果分组作为可靠的路由信号，在BIRD隐藏测试集上以68.03%的EX和0.84秒的延迟，实现了相比云端Agent 24.8%-33.3%的成本降低。然而，其有界语法仅覆盖84.6%的BIRD查询，导致复杂嵌套查询必须依赖Agent，且跨方言支持依赖转译而非原生生成。当语法覆盖率成为瓶颈时，如何在不牺牲推理速度的前提下动态扩展语法空间以覆盖剩余15.4%的复杂查询，是该架构走向通用部署的关键挑战。
