> 多智能体系统（Multi-Agent Systems, MAS）在复杂任务中通过角色分工与协作提升性能，但其协作规则会重塑底层大语言模型（Large Language Model, LLM）服务系统的负载特征。现有研究多聚焦于算法层面的准确率优化，忽视了协作结构对并发、计算强度及内存需求的非线性影响，导致算法优化与硬件部署之间存在评测空白。MAServeBench 将多智能体协作抽象为可配置的工作负载生成器，通过分层语义轨迹（Semantic Traces）分离工作生成与工作暴露，在固定工作负载下对比不同调度策略的硬件表现。该基准揭示了协作结构对硬件资源的非线性影响，证明了单纯优化算法而不考虑服务负载特征会导致服务等级目标（Service Level Objective, SLO）违约。

## 研究背景

当多智能体系统处理复杂任务时，单一用户请求会被拆解为多个相互依赖的模型调用与工具操作。这些操作并非独立到达，而是受协作规则约束：并行分支可能同时释放多个调用，同步机制会延迟下游调用，而迭代反馈则触发重复交换。这种依赖关系导致即使任务请求数量与 Token 长度相似，其请求就绪时间、批处理机会及内存需求也存在显著差异。传统服务系统假设请求独立到达，无法捕捉这种由协作结构引发的动态负载特征。

现有工作要么评估协作有效性，要么优化特定服务机制（如基于轮次的 KV 缓存共享），但缺乏将协作规则转化为可重放硬件负载的标准化基准。算法研究关注如何通过动态拓扑提升准确率，却未量化这些拓扑在硬件层面的调度延迟与内存开销。这种脱节导致算法设计者无法预判其协作策略在真实服务系统中的资源瓶颈，进而引发任务级 SLO 违约。MAServeBench 的切入点在于将协作规则视为服务负载的可配置维度，通过分离工作生成与工作暴露，实现对硬件效率的受控评估。

## 核心方法

### 分层协作工作负载抽象

MAServeBench 将端到端任务建模为分层工作负载模型，其核心公式为：

$$
W = (S, D, \Gamma, M), \quad s \in S \mapsto C_s
$$

其中 $S$ 包含逻辑协作阶段槽位，$D$ 定义阶段间依赖与工件接口，$\Gamma$ 控制阶段激活与组合（如序列、并行、循环），$M$ 定义逻辑内存的命名空间与生命周期。每个阶段 $s$ 映射到局部规范 $C_s$，包含参与者、执行控制与上下文构建。该抽象将协作规则与具体执行解耦，使得同一任务绑定可生成不同的工作负载实现。

### 工作生成与工作暴露的分离

传统基准将执行轨迹视为固定记录，无法区分协作规则变化与调度策略变化的影响。MAServeBench 引入分层语义轨迹，记录实现的操作图：

$$
G(r) = \left( O(r), E^{ctrl}(r) \cup E^{data}(r) \cup E^{state}(r) \right)
$$

其中 $O(r)$ 包含实现的模型、工具、转换与状态操作，三类边集分别编码控制前提、消费工件与版本化状态依赖。该设计允许在固定实现工作（即固定 $O(r)$ 与依赖）的前提下，通过改变合法释放约束（如添加屏障或调整 DAG 结构）来对比不同调度策略的硬件表现。这种解耦解决了此前方法无法隔离协作结构对批处理机会与状态生命周期影响的失效。

### 任务级硬件归因测量

为连接协作结构与硬件成本，MAServeBench 定义了任务级指标体系。根延迟（Root Latency）从任务到达延伸至终端完成，阶段时间从首个操作就绪延伸至阶段完成。完成路径会计将延迟分解为预提交、后端等待与调度驻留三个阶段。通过执行键或对齐时间戳，任务、阶段与操作 ID 被追踪至服务请求、调度器步骤与共享批次，从而将硬件成本归因至具体的协作阶段。

## 实验评估

实验在 GPU（A800, PRO 5000）与 NPU（910C, 950DT）平台上进行，使用 vLLM 与 vLLM-Ascend 后端，模型包括 Qwen3.5-4B/9B/27B 与 Qwen3-8B。评估覆盖 Spawn、Fork-Join、Refinement Loop 与 Debate 四种协作模板，以及 MetaGPT、ChatDev 等十二种文档化工作流。

| 指标 | Spawn 工作负载 | Loop 工作负载 | 普通服务 |
| :--- | :--- | :--- | :--- |
| 聚合算术强度倍数 | 1.70× | 相当 | 1.0× |
| KV 内存-时间积分倍数 | 13.85× | 较长驻留 | 1.0× |
| 执行时间（64 用户） | 580 秒 | 109 秒 | 109 秒 |

在 64 用户负载下，Spawn 工作负载的聚合算术强度为普通服务的 1.70 倍，但其 KV 内存-时间积分高达 13.85 倍，执行时间从 109 秒延长至 580 秒。这表明并行协作模板显著增加了内存驻留时间与计算强度，对硬件资源构成非线性压力。

在固定工作负载的受控对比中，DAG 调度在中等负载下实现 100% 的 SLO 达成率，而 Barrier 调度仅为 4%。在高负载下，增加 KV 预算使每秒事务数（TPS）提升 7.7%，但未改善 SLO 达成率。这一反直觉发现表明，硬件增益必须满足任务截止时间，单纯提升吞吐量无法解决依赖导致的延迟瓶颈。

评估边界方面，本文未覆盖动态拓扑优化对服务负载的实时反馈影响，仅评估了静态协作模板的硬件特征。此外，骨干网络使用 Qwen3 系列，与领域内常用 GPT-4 的绝对性能不可直接比较，但负载特征具有通用性。

## 关联研究分析

从问题动机看，MAServeBench 与 GPTSwarm 等动态拓扑优化方法存在根本差异。GPTSwarm 通过强化学习调整智能体连接权重以提升任务准确率，其优化目标为算法性能；MAServeBench 则固定协作规则，评估其在服务系统中的硬件效率。这种差异源于任务特性：算法研究假设服务资源无限，而系统研究关注资源约束下的 SLO 达成。查询侧增强在数据充足时是否仍有增益，论文未给出回答，但硬件负载特征表明，动态拓扑带来的依赖复杂性可能增加调度延迟，需权衡算法收益与系统成本。

从方法设计看，MAServeBench 与 AutoGen 等框架在协作定义上一致，但 AutoGen 关注工作流编排的灵活性，MAServeBench 将其抽象为可重放的硬件负载模型。这种抽象填补了算法设计与硬件部署间的评测空白，但未对比知识库中的算法优化方法（如 GPTSwarm）在相同硬件约束下的表现。这种缺失暗示了算法与系统研究之间的沟通障碍：算法研究者可能低估了协作结构对硬件资源的非线性影响。

## 总结

本文要解决的核心矛盾是多智能体协作规则与底层服务系统负载特征之间的脱节。现有方法要么优化算法准确率，要么优化特定服务机制，缺乏将协作规则转化为可重放硬件负载的标准化基准。MAServeBench 通过分层工作负载抽象与语义轨迹，分离工作生成与工作暴露，实现了对硬件效率的受控评估。实验证明，Spawn 工作负载的 KV 内存-时间积分是普通服务的 13.85 倍，且 DAG 调度在中等负载下 SLO 达成率为 100%，而 Barrier 仅为 4%。本文的边界在于未评估动态拓扑优化对服务负载的实时反馈影响，仅覆盖了静态协作模板。当动态拓扑优化方法（如 GPTSwarm）在真实服务系统中部署时，其拓扑变化引发的负载波动是否会导致 SLO 违约，论文未给出回答。
