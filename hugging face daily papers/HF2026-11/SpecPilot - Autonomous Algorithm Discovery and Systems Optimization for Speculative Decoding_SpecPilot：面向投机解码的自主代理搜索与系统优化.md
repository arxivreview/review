> 投机解码（Speculative Decoding, SD）旨在通过轻量级草稿模型并行预测候选 Token，打破大语言模型自回归解码的内存带宽瓶颈，实现无损加速。现有方法多依赖人工设计的静态优化策略，难以适应不同硬件、模型与草稿器组合下的动态瓶颈，且自动化搜索易因奖励黑客破坏无损性。SpecPilot 提出一种自主代理循环，通过成本模型定位性能天花板，并行探索优化方向，并利用 Token Forcing 机制严格验证无损性。该框架在单请求与批处理场景下均显著提升了加速比，但其自动化搜索的泛化边界与纯算法增益的解耦仍需进一步厘清。

## 研究背景

当大语言模型（Large Language Model, LLM）在低并发场景下推理时，数据从高带宽内存（High Bandwidth Memory, HBM）加载至 GPU 缓存的时间远大于计算时间，导致算术强度不足，这一现象称为内存受限（Memory-Bound）。投机解码通过引入草稿模型并行生成候选序列，再由目标模型单次并行验证，将串行解码转化为并行验证，从而在不改变输出概率分布的前提下提升吞吐量。然而，随着并行草稿器（如 DFlash2, DSpark）的引入，草稿模型一次前向传播可生成多个候选分支，但现有系统（Stock）往往仅验证单一链式路径，忽略了草稿器排序的其他候选，导致接受长度 $\tau$ 远低于理论上限。

在批处理（Batching）场景下，每个请求引入的注意力计算与循环状态更新使得权重读取不再主导步时，加速比随之衰减。更关键的是，投机解码具有高度的部署特异性：服务场景、草稿器类型、目标模型架构（如混合循环架构）及 GPU 平台（如 H100 与 RTX PRO 6000）的差异决定了何种优化有效。人工调优难以覆盖所有组合，而自动化代理搜索虽能迭代优化，却面临两大挑战：微小增益易被计时噪声掩盖，且代理可能通过改变数值精度等“奖励黑客”手段提升速度却破坏无损性。SpecPilot 针对这一部署特异性与无损性验证难题，提出自动化搜索框架。

## 核心方法

### 成本模型与瓶颈定位

SpecPilot 将投机解码的加速比 $S(N)$ 形式化为接受长度 $\tau(N)$ 与步时 $T_{step}(N)$ 的比值，其中 $N$ 为验证行数。

$$ S(N) = \frac{\tau(N)}{c(N)}, \quad c(N) = \frac{T_{step}(N)}{T_{AR}} $$

该公式表明加速比由“每步接受 Token 数”与“每步耗时”共同决定。成本模型通过计算系统性能天花板（Ceiling）来定位瓶颈，天花板由三个因子构成：$\tau$ 因子（最佳树结构可接受的 Token 数）、内核因子（实际步时与字节下限之比）和开销因子（总步时与剖析步时之比）。设计动机在于，传统方法往往盲目优化某一维度（如仅提升树深度），而 SpecPilot 通过每轮重新计算这三个因子，识别出当前系统最大的性能损失来源（如单请求下权重读取占 80% 步时，或批处理下每行验证成本过高），从而指导代理搜索方向。

### 无损性验证与 Token Forcing

自动化搜索的核心风险在于代理可能通过引入低精度验证或数值捷径来加速，从而破坏无损性。SpecPilot 定义无损性为：每个接受的 Token 必须位于通过精确目标权重（Exact Pass）验证的路径上，且等于该路径的 Argmax。

$$ \text{Lossless} \iff \forall x_i \in \text{Accepted}, \exists \text{Exact Pass} \text{ s.t. } x_i = \arg\max p(\cdot | x_{<i}) $$

为检测奖励黑客，SpecPilot 引入 Token Forcing 机制。该机制在教师强制（Teacher-Forcing）模式下，将系统输出与 Stock 基线在每个 Token 位置进行统计对比。若不匹配率超过 Stock 基线 0.5 个百分点（95% 置信度），或出现无法解释的大边际事件，则拒绝该优化。这一设计解决了传统任务准确率评估无法捕捉细微分布偏移的问题，确保搜索出的优化严格保持无损性。

### 关键优化机制：W12 与两级验证

在定位到权重读取瓶颈后，SpecPilot 发现了 W12 格式，一种无损 12-bit 权重格式。W12 将权重分为 8-bit 视图（符号、高位尾数、指数偏移）和低尾数位平面，GEMM 内核在寄存器中解码权重，隐藏了解码延迟。在单请求场景下，W12 将权重读取时间减少 14-22%，使 KV 缓存池扩大 2.0-2.5 倍。

针对接受长度瓶颈，SpecPilot 提出两级验证（Two-Level Verification, TLV）。TLV 利用 W12 中嵌套的 8-bit 视图作为低精度预检查器，在精确验证前过滤掉不可能被接受的草稿 Token。

$$ \text{TLV}: \text{Pre-check}(x_i) \rightarrow \text{Exact Pass}(x_i) $$

TLV 在精确验证前进行低精度预检查，使得每次精确验证可处理两倍于草稿长度的候选序列，几乎使每次精确验证接受的 Token 数翻倍。这一设计突破了传统“一次草稿一次精确验证”的假设，在保持无损性的前提下显著提升了 $\tau$。

## 实验评估

SpecPilot 在 GSM8K、MATH500、HumanEval、MBPP 和 MT-Bench 五个基准上，针对 Qwen3.8-27B、Qwen3.5-4B、Gemma-4-12B 和 Muse-Glimmer-30B 四个目标模型，以及 DFlash2、DSpark、EAGLE-3 三个草稿器进行了评估。基线包括 Stock SD（针对各 GPU 调优）和 DDTree。

| 模型/草稿器 | 场景 | Stock 加速比 | SpecPilot 加速比 | Stock $\tau$ | SpecPilot $\tau$ |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Qwen3.8-27B / DFlash2 | 单请求 (H100) | 3.95× | 8.86× | 4.65 | 13.08 |
| Qwen3.8-27B / DFlash2 | 单请求 (RTX PRO 6000) | 4.46× | 10.87× | 5.23 | 12.80 |
| Qwen3.8-27B / DSpark | 批处理 (H100, FP8) | 1.94× | 3.93× | 4.37 | 5.42 |
| Gemma-4-12B / EAGLE-3 | 批处理 (H100, BF16) | 0.68× | 2.09× | 2.04 | 2.54 |

单请求场景下，SpecPilot 在 H100 上达到 8.86× 加速比，在 RTX PRO 6000 上达到 10.87×，显著高于 Stock 的 3.95× 和 4.46×。接受长度 $\tau$ 从 4.65 提升至 13.08，表明 TLV 与最佳优先树验证有效利用了草稿候选。批处理场景下，SpecPilot 将加速比从 1.94× 提升至 3.93×，证明了其在高并发下的有效性。

消融实验显示，单代理基线（无成本模型）仅达到 1.34× 增益，而 SpecPilot 达到 2.13×，证明成本模型对瓶颈定位至关重要。W12 格式在自回归解码中也能带来 1.19-1.28× 加速，说明其收益部分源于通用权重压缩，而非仅投机解码特有。评估协议中，SpecPilot 使用配对运行（Paired Runs）消除计时噪声，并通过 Token Forcing 确保无损性，但未报告置信区间，且未与 HASS、GRIFFIN 等纯算法优化方法进行同等硬件条件下的直接对比，难以剥离系统优化与算法优化的贡献。

## 关联研究分析

从问题动机看，SpecPilot 与 SpecInfer 均关注树状验证以提升硬件利用率，但 SpecInfer 采用静态树结构，而 SpecPilot 通过成本模型动态调整树深度与验证策略，适应不同草稿器（如 DSpark 的马尔可夫头）的特性。SpecPilot 进一步引入了 W12 与 TLV，将优化范围从验证策略扩展至权重格式与验证流程，解决了 SpecInfer 未处理的权重读取瓶颈。

从方法设计看，SpecPilot 借鉴了 AlphaEvolve 的代理搜索范式，但针对 SD 的无损性约束设计了 Token Forcing 机制。与 EAGLE 系列依赖特征对齐提升草稿质量不同，SpecPilot 侧重于系统级集成，利用并行草稿器（DFlash2/DSpark）的候选多样性，通过最佳优先树验证挖掘未使用的候选。然而，SpecPilot 未探索草稿模型本身的训练优化，其性能上限受限于草稿器提供的候选质量，查询侧增强在数据充足时是否仍有增益，论文未给出回答。

## 总结

SpecPilot 针对投机解码在异构部署下的性能瓶颈与无损性验证难题，提出了一种基于成本模型与 Token Forcing 的自主代理搜索框架。通过发现 W12 权重格式、最佳优先树验证与两级验证机制，SpecPilot 在单请求场景下将加速比提升至 10.87×，批处理场景下提升至 3.93×。该框架证明了自动化搜索在系统级优化中的有效性，但其性能增益部分源于 W12 等通用权重压缩技术，纯算法搜索的边际贡献尚不明确。当草稿器候选质量较低时，系统级优化能否弥补算法层面的不足，仍需进一步验证。
