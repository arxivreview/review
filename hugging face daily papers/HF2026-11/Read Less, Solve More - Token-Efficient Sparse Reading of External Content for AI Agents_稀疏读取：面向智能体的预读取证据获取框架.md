# HuggingFace最新推荐论文 ｜Read Less, Solve More: Token-Efficient Sparse Reading of External Content for AI Agents ｜稀疏读取：面向智能体的预读取证据获取框架

研究机构：中国科学院大学、中国科学院

论文原文见 [arXiv](https://arxiv.org/abs/2608.22237)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.22237)

> 长程智能体在执行任务时反复处理外部工件，导致 Token 消耗与延迟随轨迹长度激增，且全量暴露的无关内容会稀释关键证据、引发决策漂移。现有上下文压缩方法多在内容进入模型后介入，无法挽回已发生的读取成本与轨迹偏移。本文提出 SparseRead，一种训练无关的预读取控制层，通过状态化协议与在线门控机制，在无关内容进入上下文前拦截并仅暴露任务相关证据。该框架在六个前沿模型上实现了最高 92.9% 的 Token 节省与 89.0% 的时间节省，但其收益高度依赖任务的稀疏结构，在低稀疏度场景下可能产生负收益。

## 研究背景

智能体在长程任务中需频繁访问外部工件（如文档、代码库），每次读取产生的观察结果会在后续模型调用中被重复处理。这一过程受限于上下文窗口的物理边界：当工件规模远超单次决策所需的信息量时，全量读取不仅消耗大量 Token，更因无关信息的注入导致模型注意力分散，形成“过度读取”（Over-reading）失效模式。为量化这一现象，需引入“证据稀疏度”概念，即当前决策所需的有效证据占暴露内容总量的比例。在长文档问答等高稀疏度任务中，该比例低至 6–15%，意味着绝大多数读取内容对当前步骤无贡献。

当前主流路线分为两类：一是事后压缩，如 LLMLingua 与 ACON，它们在内容进入上下文后进行摘要或掩码，但无法阻止初始全量读取带来的计算开销与轨迹漂移；二是检索增强，但检索往往与智能体动态演化的信息需求脱节。这两类方法均缺乏对“读取行为”本身的一级控制机制，即无法在读取前判断暴露多少内容、何时停止。本文的切入点在于将读取建模为部分可观测下的序贯证据获取过程，通过预读取控制替代事后压缩，解决“压缩不信任”导致的循环读取问题。

## 核心方法

### 预读取控制参照系

传统智能体框架（如 ReAct）将工具调用视为原子操作，读取工件即返回完整内容。本文问题与该通用流程的关键差异在于：读取不再是“全有或全无”，而是受控的、状态化的、可中断的证据获取过程。参照系为“读取-处理-决策”循环，本文将其改造为“预览-意图-门控-稀疏读取-验证-决策”。

### 状态化稀疏读取协议

该协议解决了“压缩不信任”问题：智能体收到压缩结果后，因缺乏来源锚点与未决需求状态，无法判断证据是否完整，从而反复重新读取。SparseRead 引入模型可见的证据状态 $E$，将读取过程形式化为序贯决策。在步骤 $t$，智能体基于当前状态 $z_t$ 与工件预览 $p$ 生成读取意图 $h_t$，并选择宏动作 $a_t \in \mathcal{A} = \{\text{scout, focus, collect, refine, verify}\}$。Reader 后端根据意图与动作返回锚定观察 $x_t$，更新证据状态：

$$
E_{t+1} = \text{Update}(E_t, x_t)
$$

当智能体判断 $E_{t+1}$ 足以支持当前决策且所有未决需求已解决时，读取终止。该状态化设计使智能体能区分“已检查区域无证据”与“未检查区域可能有证据”，从而避免盲目重读。

### 在线门控与回退机制

稀疏读取并非普适：在低稀疏度任务（如全表计算、精确扫描）中，强制稀疏读取会增加协议开销。Read Gate 在每次读取请求时执行一次路由决策，基于工件规模、意图范围与 Reader 成本等预读取信号，确定性地选择干预模式。若判定为原生路径，则直接返回完整工件 $N(o)$；若判定为稀疏路径，则进入上述协议。当路由结果为空、进度停滞或预算耗尽时，触发协议级原生回退：

$$
\text{Fallback}(N, o, E) = N(o)
$$

该机制确保稀疏读取仅在有益时激活，在边界情况下保留原生读取能力，避免了“一刀切”压缩导致的性能退化。

## 实验评估

实验在 NanoBot、OpenCode、OpenClaw 三个智能体框架上，使用 Claude Opus 5、Qwen3.6-Plus 等六个模型，覆盖长文档问答、多文件审计、结构化分析、AI for Science 及原生适配控制五类场景。基线包括 Naive 全量读取、ACON 零样本压缩器与 Complexity Trap 观察掩码。ACON 在四个设置中 Token 与时间均高于 Naive，且在 Qwen3.6-Plus 多文件诊断中损失 0.80 分，验证了事后压缩的不稳定性。

| 框架 | 模型 | Token 节省率 | 分数变化 | 时间节省率 |
| :--- | :--- | :--- | :--- | :--- |
| NanoBot | Kimi-K2.5 | 92.9% | +0.598 | 85.4% |
| NanoBot | Qwen3.6-Plus | 69.0% | +0.039 | 64.4% |
| OpenCode | DeepSeek-Flash | 71.8% | +0.143 | 64.9% |
| OpenClaw | Qwen3.6-Plus | 46.7% | +0.032 | 56.8% |

在稀疏适配场景中，SparseRead 在 30 个模型-场景单元中均降低 Token 与时间，其中 26 个单元保持或提升任务分数。最强模型 Opus 5 仍节省 59.6–89.0% Token，表明读取瓶颈非模型能力不足所致，而是架构性低效。Read Gate 在 8 个匹配任务中，38 对降低 Token 成本，39 对保持或提升分数，14 个明确获胜案例的中位 Token 节省率为 79.6%。

评估边界方面，实验未报告置信区间，分数变化在 -0.10 至 +0.598 之间波动，部分负值（如 -0.031）归因于轨迹级随机性。代码已开源，但 Reader 后端的具体实现细节（如领域本体编码）未完全披露，限制了跨领域复现性。

## 关联研究分析

从问题动机看，本文与 ACON 和 Complexity Trap 的核心差异在于干预时机。ACON 在内容进入上下文后压缩，Complexity Trap 基于固定位置掩码，两者均无法感知智能体的动态信息需求。本文的预读取控制将决策点前移至读取前，通过意图驱动的证据获取解决“压缩不信任”问题。这一差异源于任务特性：长程任务中信息需求随步骤演化，事后压缩无法适应这种动态性。

从方法设计看，本文与 ReAct 等标准智能体框架的差异在于读取接口的抽象层级。ReAct 将读取视为原子工具调用，本文引入宏动作集与 Reader 后端解耦，使读取策略与证据获取能力独立演化。这种设计允许新增 Reader 而不扩展智能体接口，但 Read Gate 的确定性路由可能限制其在高度动态环境中的适应性——当工件结构或任务意图在读取过程中发生剧烈变化时，预读取信号是否仍能有效区分稀疏与原生路径，论文未给出回答。

## 总结

本文解决的核心矛盾是智能体全量读取外部工件导致的 Token 爆炸与证据稀释。现有事后压缩方法无法挽回已发生的读取成本，本文通过预读取控制与状态化协议，在内容进入上下文前实现证据筛选。实验证明，在稀疏适配场景中，SparseRead 最高节省 92.9% Token 与 89.0% 时间，且收益随模型能力增强而持续。其边界在于 Read Gate 的确定性路由依赖预读取信号的稳定性，在低稀疏度或意图快速变化的任务中，强制稀疏读取可能增加 309.2% 的 Token 开销。当工件结构在读取过程中发生非预期变化时，预读取信号的有效性是否衰减，论文未提供实证。
