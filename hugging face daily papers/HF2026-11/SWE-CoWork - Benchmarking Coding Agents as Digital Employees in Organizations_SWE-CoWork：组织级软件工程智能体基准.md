> 导读 当前大语言模型（Large Language Model, LLM）软件工程智能体在单任务代码修复上已接近饱和，但在真实组织协作中仍表现为被动的“规格执行者”，无法自主处理分布式知识、动态需求及多源冲突证据。现有基准多假设需求明确或仅通过单一模拟用户澄清，忽略了真实工程中需求分散于同事、文档与历史记录中的复杂性。SWE-CoWork 构建了包含数字员工、工作场所记录及执行验证的模拟组织环境，要求智能体从简短交接单出发，自主恢复需求、调和冲突并交付代码。该基准揭示了前沿模型在需求追踪与实现脱节上的结构性缺陷，为评估智能体从“代码生成器”向“数字员工”演进提供了关键坐标系。

## 研究背景

当智能体面对真实软件工程任务时，其输入往往不是自包含的规格说明，而是分散在组织记录与人际交互中的碎片化信息。这种信息分布特性导致传统基于静态 Issue 的评估范式失效，因为智能体缺乏主动检索、验证及调和冲突证据的能力。为解决此问题，领域引入了执行接地（Execution-Grounded）验证机制，通过沙箱环境中的测试通过与否判定代码正确性，确立了功能验证的黄金标准。然而，执行接地仅解决了“代码是否正确”的问题，未解决“需求是否被正确理解”的问题。在长程依赖任务中，智能体需维持跨多轮交互的上下文一致性，这构成了长程推理稳定性的核心挑战。

主流路线如 SWE-agent 和 OpenHands 通过代理-计算机接口（Agent-Computer Interface, ACI）实现了动态交互，但其任务定义仍局限于单仓库、单目标的修复。近期研究如 RealSWE 和 τ-Bench 开始探索需求澄清，但通常假设存在一个全知或指定的模拟用户。这种设定忽略了真实组织中知识边界受限、责任分散及历史记录冲突的现实。SWE-CoWork 的切入点在于将评估场景从“孤立任务执行”重构为“组织级协作”，要求智能体在缺乏完整初始信息的情况下，通过与具有局部知识的数字员工交互及检索版本化记录，自主构建完整的需求图谱。

## 核心方法

### 组织级任务形式化与数字员工建模

SWE-CoWork 将软件工程任务重构为组织环境中的多源信息恢复与交付问题。与传统基准直接提供 Issue 描述不同，SWE-CoWork 的任务输入仅为简短的入职简报（Onboarding Note），智能体需通过工作场所记录（看板、文档、聊天、CI 记录）和数字员工交互来恢复需求。每个任务关联一个固定的可执行契约，包含失败转通过（Fail-to-Pass, F2P）和通过转通过（Pass-to-Pass, P2P）测试节点。

数字员工被建模为具有责任边界、局部知识和协作规则的 LLM 驱动实体。其核心创新在于将需求与特定所有者（Owner）绑定，并规定知识披露条件。例如，某员工仅在智能体提供足够代码上下文时才披露隐藏需求，或要求智能体先复现问题。这种设计迫使智能体从被动接收指令转向主动探索组织知识图谱。

$$
R_{task} = \bigcup_{i=1}^{N} \{ r_i \mid \text{Owner}(r_i) = e_i, \text{Disclosure}(r_i, e_i, \text{Context}) = \text{True} \}
$$

该公式表示任务需求集合 $R_{task}$ 由分散在 $N$ 个数字员工 $e_i$ 处的需求 $r_i$ 组成，且每个需求的获取依赖于所有者 $e_i$ 对当前交互上下文 $\text{Context}$ 的披露判定。这一机制模拟了真实组织中信息不对称与责任分散的特性，解决了传统基准中需求全知假设导致的评估偏差。

### 需求追踪与执行验证的解耦评估

为区分需求获取失败与实现失败，SWE-CoWork 引入了配对评估条件：CoWork 条件（标准组织环境）与 Oracle-Spec 条件（提供完整需求规格）。两种条件共享相同的仓库、测试契约、脚手架及执行预算。通过对比两者在 F2P 测试通过率上的差异，可量化组织协作开销对最终交付的影响。

评估指标包括 F2P 率、P2P 率及完整任务通过率（Pass Rate）。完整任务通过率要求所有 F2P 和 P2P 测试节点在同一运行中全部通过，这比单一测试通过率更严格地反映了端到端交付能力。

$$
\text{Pass Rate} = \frac{1}{M} \sum_{j=1}^{M} \mathbb{I} \left( \forall t \in T_j, \text{Test}(t, P_j) = \text{Pass} \right)
$$

其中 $M$ 为任务总数，$T_j$ 为任务 $j$ 的所有测试节点集合，$P_j$ 为智能体提交的补丁，$\mathbb{I}$ 为指示函数。该指标揭示了部分实现与完整交付之间的巨大鸿沟，即使智能体能通过大部分测试，若遗漏任一关键需求，完整任务通过率仍为零。

## 实验评估

SWE-CoWork 在 101 个真实仓库任务上评估了 11 个模型，涵盖 JavaScript、Python 等 11 种语言。实验设置包括标准 CoWork 条件和 Oracle-Spec 条件，以隔离需求获取与代码实现的影响。基线覆盖包括 Claude-Opus-5.5、GPT-6 Astra 等前沿模型，但未包含 SWE-agent 等经典框架在同等组织环境下的表现，因后者缺乏处理多源冲突证据的内置机制。

| 模型 | 条件 | F2P 率 (%) | 完整任务通过率 (%) |
| :--- | :--- | :--- | :--- |
| Claude-Opus-5.5 | CoWork | 63.84 | 6.93 |
| GPT-6 Astra | CoWork | 62.91 | 7.92 |
| Seed Evolving | CoWork | 39.09 | 0.99 |
| GPT-6 Astra | Oracle-Spec | 78.84 | 7.92 |
| Seed Evolving | Oracle-Spec | 55.76 | 0.99 |

数据显示，提供完整需求（Oracle-Spec）使 GPT-6 Astra 的 F2P 率从 62.91% 提升至 78.84%，提升 15.93 个百分点，但完整任务通过率保持 7.92% 不变。这表明需求获取是主要瓶颈，但即使需求明确，智能体在实现、验证及交接阶段的持续追踪能力仍严重不足。Claude-Opus-5.5 虽能将 93% 的初始问题指向正确所有者，但仅获得 64% 的同事持有需求，且 31% 报告完成的需求未通过测试。

评估边界方面，SWE-CoWork 依赖 LLM 模拟数字员工，其可靠性偏差可能影响评估泛化性。此外，基准未覆盖计算效率维度，高解决率可能伴随高昂的 Token 消耗。可复现性方面，代码与数据集已开源，但数字员工的具体提示工程细节对结果影响显著。

## 关联研究分析

从问题动机看，SWE-CoWork 与 τ-Bench 均关注需求恢复，但 τ-Bench 假设存在单一客户端进行澄清，而 SWE-CoWork 将知识分散于多个具有责任边界的数字员工中。这一差异源于对真实组织协作复杂性的不同建模：τ-Bench 侧重交互协议，SWE-CoWork 侧重组织知识图谱的检索与调和。SWE-CoWork 揭示了多源冲突证据下智能体缺乏权威判定能力的问题，这是单用户交互基准无法暴露的盲区。

从方法设计看，SWE-CoWork 与 AgentForge 均涉及多角色协作，但 AgentForge 的角色是内部子智能体，共享全局上下文；而 SWE-CoWork 的数字员工是外部模拟实体，具有局部知识边界。这种设计迫使智能体通过显式通信获取信息，而非依赖共享内存。AgentForge 通过执行验证驱动内部协调，SWE-CoWork 则通过组织记录与人际交互驱动外部协调。查询侧增强在数据充足时是否仍有增益，论文未给出回答，但 SWE-CoWork 的低完整任务通过率暗示，单纯增强检索能力不足以解决长程追踪中的状态丢失问题。

## 总结

SWE-CoWork 针对当前 LLM 智能体在组织级协作中“能写代码但难成事”的结构性缺陷，提出了从被动规格执行向主动数字员工演进的新评估范式。通过构建包含数字员工、版本化记录及执行验证的模拟组织环境，该基准量化了需求获取与实现交付之间的鸿沟。实验显示，即使提供完整需求，前沿模型的完整任务通过率仍低于 8%，揭示了持续需求追踪与验证闭环的严重不足。该基准的边界在于依赖 LLM 模拟同事的可靠性，且未评估计算成本。当智能体在长程交互中面临需求变更与证据冲突时，如何设计有效的状态压缩与优先级调度机制以维持追踪稳定性，是后续研究需解决的关键问题。
