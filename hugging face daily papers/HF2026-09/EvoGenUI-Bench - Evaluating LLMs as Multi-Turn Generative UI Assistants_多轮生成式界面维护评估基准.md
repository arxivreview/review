# HuggingFace最新推荐论文 ｜EvoGenUI-Bench: Evaluating LLMs as Multi-Turn Generative UI Assistants ｜多轮生成式界面维护评估基准

研究机构：美国纽约大学

作者：Yue Peng、Lanke Xia、Zihan Wang 等 6 人

论文原文见 [arXiv](https://arxiv.org/abs/2608.29387)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2608.29387)

> 大语言模型（LLM）能够生成仪表盘、表单等交互式界面，但现有评估仅关注单次生成的视觉保真度或代码可执行性，忽略了用户多轮迭代中界面状态与功能的一致性维持。本文提出 EVOGENUI-BENCH，通过浏览器执行与多表面证据收集，量化模型在累积修订中保持行为、状态与响应同步的能力。实验显示最强模型单轮通过率 74.9% 但五轮完整成功率仅 37.3%，揭示了单轮成功与长程可靠性的巨大鸿沟，但缺乏对具体修复机制的探索。

## 研究背景

当 LLM 生成一个旅行规划界面后，用户要求增加预算模块并切换深色模式，模型需同时实现新需求、保留原有行程卡片功能，并确保界面显示状态与后端数据一致。这一过程涉及**感知接地（Grounding）**，即 UI 控件必须准确映射到外部运行时状态；若接地失效，界面将显示陈旧数据。同时，多轮交互要求模型具备**长程记忆**，避免在后续修订中覆盖或丢失早期功能，即防止“回归（Regression）”错误。

现有前端生成基准如 ArtifactsBench 和 SWE-bench 侧重单次代码补丁或静态页面的执行正确性，将“构建界面”与“使用界面”割裂。WebArena 等 Agent 基准评估模型操作现有网站的能力，而非生成新界面。这些方法无法捕捉多轮修订中“行为-状态-响应”的同步失效，导致高单轮通过率掩盖了长程任务的脆弱性。本文切入点在于将生成式 UI 视为一个持续演进的执行工件，而非孤立页面，要求评估覆盖整个修订序列的一致性。

## 核心方法

### 任务形式化与证据包

本文问题区别于通用代码生成流程的关键在于：评估对象是**动态演进的执行工件**，而非静态代码片段。标准流程仅检查最终代码是否编译通过，而本文要求每一轮更新后的界面在浏览器中可执行，且其行为、可见状态与助手响应必须与对话历史保持一致。为此，本文定义了**多表面证据包（Multi-surface Evidence Bundle）**，整合渲染 UI、DOM 结构、交互轨迹、运行时日志及外部状态回读，作为评估的唯一依据。

### 可靠性指标体系

针对多轮维护特性，本文设计了层级化的可靠性指标。设第 $t$ 轮通过指示器为 $p_{T,t} \in \{0, 1\}$，当且仅当生成成功、工件可评估且呈现、执行、对齐三项得分均 $\ge 4$ 时 $p_{T,t}=1$。**相邻通过保留率（Adjacent Pass Retention, APR）** 衡量在上一轮通过且当前轮生成成功的前提下，当前轮通过的概率：

$$
\text{APR}(S) = \frac{\sum_{T \in S} \sum_{t=2}^{N} e_{T,t} p_{T,t-1} p_{T,t}}{\sum_{T \in S} \sum_{t=2}^{N} e_{T,t} p_{T,t-1}}
$$

其中 $e_{T,t}$ 指示生成调用是否返回响应。该公式物理含义是：在模型已正确维护界面的条件下，其应对新修订而不破坏旧功能的概率。APR 直接量化了“回归”风险，弥补了单轮通过率无法反映跨轮次一致性的缺陷。

### 浏览器执行与评估协议

评估流程在固定 Web 环境中构建并执行模型返回的源代码，由交互 Actor 操作界面收集行为轨迹。设计动机在于解决纯文本判断无法捕捉“构建成功但控件失效”或“状态陈旧”的问题。通过分离生成器可见的请求与私有验证需求，防止评估泄漏。每个私有需求至少关联一个可观测证据表面（如 DOM、工具日志），确保验证目标语义而非参考实现，允许功能等价解通过，同时拒绝静态壳或虚假声明。

## 实验评估

实验在 EVOGENUI-BENCH 上进行，包含 150 个任务、750 轮次，分为呈现、交互、工具接地三个套件。基线覆盖 8 个主流 LLM 模型（如 Claude-Opus-4.7, GPT-5.5），但未对比专门的 UI 生成架构或微调模型，仅评估基础模型能力。

| 模型 | 整体 TP (%) | 整体 TP@5 (%) | 工具接地 APR (%) |
| :--- | :--- | :--- | :--- |
| Claude-Opus-4.7 | 74.9 | 37.3 | 68.6 |
| GPT-5.5 | 61.7 | 21.3 | 72.7 |
| Qwen3.6-Plus | 44.0 | 7.3 | 34.6 |
| Gemini-3.1-Pro | 23.6 | 6.7 | 29.4 |

Claude-Opus-4.7 单轮通过率最高（74.9%），但五轮完整成功率仅 37.3%，且工具接地任务 APR 降至 52.4%（模型平均），表明外部状态同步是主要瓶颈。工具接地任务每轮平均 11.9 个验证需求，远高于呈现任务的 3.0 个，导致难度陡增。

消融分析显示，可靠性在第 2 轮后显著下降，第 3 轮通过率跌至 39.4%。在 110 个 APR 失败案例中，52.7% 涉及对先前行为的回归，47.3% 仅因新需求未满足。这表明模型在累积修订中更易丢失旧功能，而非无法实现新需求。Gemini-3.1-Pro 整体 TP 低（23.6%）但交互任务 APR 高（79.6%），说明一旦达到正确状态，其保持能力较强，但初始生成能力弱。

评估边界方面，自动评估器与人工标注的 Cohen’s $\kappa$ 为 0.73，Fleiss’ $\kappa$ 为 0.78，一致性良好。代码已开源，但实验未报告计算效率（如推理延迟），且工具接地任务依赖模拟环境，与真实 Web 的动态性存在差距。

## 关联研究分析

从问题动机看，本文与 WebArena 的根本差异在于任务本质：WebArena 评估 Agent 在**给定环境**中的操作能力，而本文评估模型**构建并维护环境**的能力。WebArena 的 SOTA 方法如 WebRL 关注动作序列正确性，而本文关注界面状态与代码逻辑的一致性。这种差异源于任务特性：操作任务中环境是固定的，而生成任务中环境是模型输出的，因此评估必须包含对生成工件本身的执行验证。

从方法设计看，本文借鉴了 SWE-bench 的“执行即评估”范式，但将评估对象从代码补丁扩展为交互式界面。SWE-bench 通过单元测试验证代码功能，而本文通过浏览器交互与多表面证据验证 UI 行为。关键差异在于，SWE-bench 的任务是静态的（修复 bug），而本文的任务是动态的（多轮修订），因此引入了 APR 指标以捕捉跨轮次一致性。ArtifactsBench 虽也采用浏览器执行，但侧重单次生成的视觉保真度，未涉及多轮状态维护，导致其无法检测“第 3 轮丢失第 1 轮功能”的回归错误。

## 总结

本文核心矛盾在于单轮生成成功与多轮维护可靠性的脱节。现有基准无法捕捉累积修订中的状态漂移，而本文通过浏览器执行与 APR 指标，量化了模型在保持界面一致性方面的能力。实验证明，即使最强模型在五轮任务中成功率仅 37.3%，且工具接地任务表现最差，揭示了外部状态同步是主要瓶颈。本文边界在于仅评估基础模型能力，未探索微调或架构改进对缓解回归错误的作用。当模型在工具接地任务中频繁出现状态不一致时，是否可以通过引入显式的外部状态校验机制来降低 APR 失败率，论文未给出回答。
