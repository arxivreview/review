# HuggingFace最新推荐论文 ｜ProgramDistill: From Interactive Web Apps to Verifiable Reference-Guided SWE Tasks ｜参考引导软件工程基准

研究机构：韩国科学技术院、微软研究院

作者：Jeonghye Kim、Minseon Kim、Young Jin Kim 等 8 人

论文原文见 [arXiv](https://arxiv.org/abs/2609.18805)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.18805)

> 现有软件工程智能体评估默认需求已通过文本 Issue 或测试用例明确给出，但真实开发中常需从可运行的参考应用逆向推断行为。本文提出 ProgramDistill，通过自动化流水线将交互式 Web 应用分解为可重放行为任务，构建无需人工标注的参考引导修复基准。其核心贡献在于定义了“应用到任务分解”与“参考到当前蒸馏”双轴框架，并引入恢复深度作为可控难度轴。该基准揭示了前沿模型在行为推断上的显著短板，但评估仅覆盖自包含 Web 应用，且缺乏开源小模型基线，其结论向通用仓库级任务的泛化性存疑。

## 研究背景

当智能体面对一个功能缺失的 Web 应用时，若无法获取明确的需求文档，它必须通过与一个功能完整的参考应用交互来推断预期行为。这一过程涉及两个核心概念：一是可重放行为验证，即通过重放浏览器交互轨迹并比对状态信号来判定代码正确性，而非依赖静态测试；二是前置谱系，即 Web 应用中行为间存在的状态依赖关系（如登录先于创建对象），这种依赖将离散行为组织为有向树结构。前者解决了验证的客观性问题，后者则提供了任务组合的结构基础。

仓库级软件工程评估的主流路线以 SWE-bench 为代表，其范式假设问题描述（Issue）已完整指定了修复目标，智能体仅需定位并修改代码。然而，这一假设在原型迭代、版本迁移或竞品分析等场景中失效，因为目标行为往往只存在于可运行的参考实例中，而非文本描述里。ProgramBench 虽确立了从可执行行为重构代码的思路，但将其局限于编译型语言的整程序重构，未利用交互式应用特有的状态依赖结构。本文的切入点在于：利用 Web 应用行为的前置谱系结构，将单一应用分解为不同粒度的可验证修复任务，从而构建一个难度可控、无需人工标注的参考引导评估体系。

## 核心方法

### 方法参照系

本文问题可归入合成数据生成路线，其标准流程是从代码提交或测试用例中提取任务实例。关键差异在于：本文不依赖代码变更历史，而是以浏览器交互轨迹为行为单元，通过掩码机制移除源码实现来构造修复任务，验证标准从“测试通过”变为“交互轨迹重放一致”。

### 应用-任务分解与掩码构造

在标准合成流程中，任务边界由代码提交定义，本文将其替换为行为边界。设计动机在于：代码提交往往混合多个行为变更，难以隔离单一功能的修复难度，而基于行为的掩码能精确控制任务粒度。具体而言，流水线首先挖掘可重放行为轨迹 $\tau_d$，并通过重放验证器 $V(A, L_d) \in \{0, 1\}$ 确保其在完整应用 $A$ 上成功执行。随后，Crafting 阶段生成掩码 $m_d$ 移除 $\tau_d$ 对应的源码实现，得到应用 $A[m_d]$。原子任务验证要求前置轨迹 $L_{d-1}$ 在 $A[m_d]$ 上仍通过，而目标轨迹 $\tau_d$ 失败，即：

$$V(A[m_d], L_{d-1}) = 1 \quad \text{and} \quad V(A[m_d], L_d) = 0$$

此条件确保掩码仅移除目标行为，未破坏前置依赖。通过沿前置谱系组合多个掩码，可构造恢复深度 $r_L$ 递增的累积任务，实现从原子修复到全应用重建的难度梯度。

### 参考-当前蒸馏与努力分配

在任务求解阶段，智能体需从参考应用推断行为并在当前应用中实现。设计动机在于：现有评估仅关注最终补丁正确性，忽略了智能体在信息获取与代码编辑间的努力分配策略。本文定义参考-当前蒸馏为：给定参考应用 $A_{ref}$ 和当前应用 $A_{cur}$，智能体生成补丁 $P$，使得重放轨迹 $L_d$ 在 $A_{cur}[P]$ 上的执行结果与 $A_{ref}$ 一致。轨迹分析揭示，恢复深度从 1 增至 8 时，需恢复的代码行数增长 9.3 倍，但智能体每个目标行为的参考观察步数从 34.60 降至 8.46，当前应用观察步数从 27.69 降至 6.81，降幅约 75%。这种努力与负担的错配表明，智能体在深层任务中系统性减少了对每个行为的验证投入，而非单纯实现能力不足。

## 实验评估

实验在 26 个 Web 应用上构建 4,063 个任务，评估 9 个前沿编码智能体。基线覆盖 GPT-6 Astra、Claude Opus 5 等闭源模型，但缺失开源小模型（如 Llama 3 系列）及多智能体框架（如 AgentForge）对比，无法评估架构复杂度对参考引导任务的影响。

| 模型 | 全应用重建成功率 (%) | 平均轨迹成本 ($) | 当前应用观察步数/轨迹 | 编辑/写入步数/轨迹 |
|---|---|---|---|---|
| GPT-6 Astra | 49.2 | 33.99 | 96.3 | 9.9 |
| Claude Opus 5 | 28.8 | 28.86 | — | 23.5 |
| GPT-5.6 Sol | — | 16.01 | 45.8 | — |
| Gemini 3.7 Flash | — | 3.89 | — | — |

GPT-6 Astra 以 49.2% 的全应用重建成功率领先，其当前应用观察步数（96.3）约为次高模型 Sol（45.8）的 2.1 倍，而编辑/写入步数（9.9）远低于 Opus 5（23.5）。这一组合表明，观察密集型策略在参考引导任务中优于编辑密集型策略，努力分配本身构成性能差异的关键维度。

消融分析显示，掩码范围对性能影响显著：Astra 在仅逻辑掩码任务上的链式得分为 96.2%，在逻辑+UI 掩码任务上降至 84.9%，11.3 个百分点的差距表明界面重构比纯逻辑修复更难。失败模式分析揭示，59.2% 的失败源于智能体未观察到参考应用中的行为，而非实现错误，说明探索策略的覆盖度是主要瓶颈。

评估边界存在三点局限：第一，仅使用结构化浏览器观察，未包含截图等多模态输入，可能低估视觉依赖行为的修复难度；第二，应用语料限于自包含 Web 应用，未覆盖外部服务依赖或非确定性状态场景；第三，代码未公开，且未报告置信区间，数值比较需谨慎。

## 关联研究分析

从问题动机看，SWE-bench 及其衍生基准（如 SWE-bench Verified）将需求指定为文本 Issue，而 ProgramDistill 将需求指定为可执行参考应用。这一差异源于任务场景的不同：SWE-bench 模拟 GitHub Issue 修复，需求已由报告者明确；ProgramDistill 模拟版本迁移或原型实现，需求仅存在于参考实例中。根源在于任务特性决定：当需求无法文本化时，行为推断成为必要路径，而非方法选择的偏好。

从方法设计看，SWE-RL 等强化学习方法依赖执行反馈作为奖励信号，但受限于高质量轨迹数据稀缺。ProgramDistill 生成的 4,063 个可重放任务可直接作为 RL 环境，其恢复深度轴提供了天然课程学习结构。然而，SWE-RL 的奖励信号基于测试通过，而 ProgramDistill 的验证基于交互轨迹重放一致性，后者对状态依赖行为的覆盖更细粒度。查询侧增强在数据充足时是否仍有增益，论文未给出回答，因为 ProgramDistill 未与 SWE-RL 等 RL 方法在同一数据规模下进行对比。

## 总结

本文要解决的核心矛盾是：现有 SWE 基准假设需求已文本化，但真实开发中常需从可运行参考推断行为。本文抓住的切入点是 Web 应用行为的前置谱系结构，使其能将单一应用分解为粒度可控的修复任务，而现有方法因依赖代码提交或文本 Issue 无法实现这种细粒度分解。本文通过 Mine-Craft-Patch 流水线自动构建 4,063 个可重放验证任务，并引入恢复深度作为难度轴。实验证明，GPT-6 Astra 在全应用重建中仅达 49.2% 成功率，且观察密集型策略显著优于编辑密集型。本文的边界在于：评估仅覆盖自包含 Web 应用，且未包含开源小模型基线，无法验证参考引导范式在资源受限场景下的可行性。当应用规模扩展到包含外部服务依赖时，可重放验证的确定性假设是否仍成立，论文未给出回答。
