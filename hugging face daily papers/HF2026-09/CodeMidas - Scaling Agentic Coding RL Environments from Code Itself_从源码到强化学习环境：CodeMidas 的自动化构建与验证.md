> 导读 代码智能体（Agentic Coding）的强化学习（RL）训练长期受限于任务多样性不足与奖励信号不可靠，现有方法多依赖人工编写的 Issue 或测试用例，导致任务覆盖范围受限于开发记录的完备性。CodeMidas 提出了一种仅以源码为输入的智能体流水线，通过行为规格化、执行接地测试构建及后向过滤机制，将开源代码库自动转化为可验证的 RL 环境。该工作验证了从代码本身提取训练信号的有效性，但其在任务难度分布控制及跨模型泛化边界上的表现仍存疑。

## 研究背景

当智能体在长时程任务中自主完成软件工程工作时，其能力上限取决于 RL 训练环境中任务的多样性与奖励信号的可靠性。任务多样性支撑泛化能力，而可靠的执行奖励（Execution Reward）是强化正确行为的关键。然而，现有环境构建方法通常从 Issue、Pull Request 或 Commit 等开发工件中派生任务，这种依赖导致任务范围被记录覆盖率所限制，且难以保证验证器（Verifier）对替代实现的公平性。

主流路线如 SWE-bench 确立了仓库级执行评估范式，R2E-Gym 和 SWE-smith 则分别从 Commit 和测试用例合成任务。这些方法虽解决了部分自动化问题，但仍未摆脱对人工开发记录的依赖，导致任务分布偏向已记录的历史变更，且验证器常因测试覆盖不足或过度约束而失效。CodeMidas 的切入点在于直接利用已实现的功能作为任务基础，通过移除核心实现并保留上下文，迫使智能体在真实依赖中推理，从而突破开发记录的限制。

## 核心方法

### 方法参照系

CodeMidas 属于仓库级软件工程环境的自动化构建范畴，其核心差异在于摒弃了对 Issue、Commit 或人工测试的依赖，仅以源码为唯一任务特定输入。标准流程通常是从开发记录中提取任务描述，而 CodeMidas 将任务生成转化为从代码结构中识别功能并反向推导行为规格的过程。

### 行为规格化与代码适配

任务设计阶段的核心挑战在于如何从代码中明确“需要做什么”而不泄露“怎么做”。CodeMidas 通过智能体检查代码库结构，识别具有公共入口点和可观察结果的功能，并移除核心实现以形成开发起点。任务陈述（Task Statement）定义输入、可观察行为及公共接口，但保持内部实现选择的开放性。这一设计解决了此前方法中任务描述与参考实现耦合过紧的问题，确保验证器能接受多种正确实现。

$$
\text{Task} = (S, E, V) \quad \text{s.t.} \quad S \text{ defines behavior}, E \text{ is adapted codebase}, V \text{ is hidden verifier}
$$

其中 $S$ 为行为规格，$E$ 为移除核心实现后的代码库，$V$ 为仅在评分时注入的执行验证器。该公式明确了任务三元组的独立性，确保求解器在解决过程中无法访问验证器，从而保证奖励信号的纯净性。

### 执行接地测试与后向过滤

测试构建阶段通过执行参考代码生成预期输出，确保测试断言基于实际行为而非主观假设。对于状态 API，测试涵盖调用顺序及清理行为。后向过滤（Post-rollout Filtering）是 CodeMidas 的关键创新，包含泄漏检测、验证器一致性审计及结果分布过滤。泄漏检测通过对抗性智能体搜索编译产物、缓存等残留信息，防止智能体通过捷径获取答案；验证器一致性审计通过多次智能体尝试，标记假阳性（错误实现通过测试）和假阴性（正确实现失败）。

$$
\text{Filter}(T) = \begin{cases} 1 & \text{if } \exists \text{pass} \land \exists \text{fail} \land \neg \text{Leak} \land \text{Agree}(V, S) \\ 0 & \text{otherwise} \end{cases}
$$

该过滤机制仅保留在筛选模型下既有成功又有失败尝试的任务，排除了全通过（可能过易或测试弱）或全失败（可能过难或验证器缺陷）的任务，确保训练信号的区分度。

## 实验评估

实验设置采用 MiMo-V2.5 模型，在 5,545 个 CodeMidas 任务上使用 GRPO 进行 RL 训练，批量大小为 32，每任务 32 次 rollout。基线为初始 MiMo-V2.5 策略，对比方法未涵盖 GPT-4o 或 Claude 等 SOTA 模型，主要关注 RL 训练带来的增益而非横向模型比较。

| 基准 | 初始得分 (%) | RL 后得分 (%) | 增益 (pp) |
|---|---|---|---|
| SWE-bench Pro | 54.4 | 50.3 | +4.1 |
| DeepSWE | 10.0 | 21.7 | +11.7 |
| ProgramBench | 4.5 | 21.5 | +17.0 |
| RepoZero C2Rust | 40.5 | 51.8 | +11.3 |
| Terminal-Bench v2.1 | 63.7 | 72.2 | +8.5 |

核心数字显示，ProgramBench 的 Almost Solved 分数从 4.5 提升至 21.5，增益达 17.0 个百分点，表明 CodeMidas 任务对整体程序构建能力有显著促进作用。DeepSWE 的通过率从 10.0% 提升至 21.7%，验证了任务在 Issue 修复场景下的有效性。

消融实验表明，高质量任务数量从 1k 增至 3k 再至 5,545 时，SWE-bench Pro、DeepSWE 及 CodeMidas Val 的得分逐步提升。值得注意的是，3k 子集在所有三个基准上均优于未经清洗和过滤的 8k 基线，证明后向过滤机制对任务质量的提升作用大于单纯增加任务数量。轨迹分析显示，RL 训练后智能体表现出更多的代码库探索和多样化的自我验证行为，且智能体编写的检查与更高的成功率相关，提供了行为层面的泛化证据。

评估边界方面，论文未报告置信区间，且缺乏与 SOTA 模型的直接对比，限制了结果的外部效度。代码未公开，超参数细节有限，可复现性依赖于对 GRPO 及智能体流水线的精确复现。指标完备性上，ProgramBench 使用 Almost Solved 分数，与其他基准的 Pass Rate 存在定义差异，跨基准比较需谨慎。

## 关联研究分析

从问题动机看，CodeMidas 与 R2E-Gym 和 SWE-smith 的核心差异在于任务来源的独立性。R2E-Gym 依赖 Commit 记录，SWE-smith 依赖现有测试，两者均受限于开发记录的覆盖范围，而 CodeMidas 直接从源码提取功能，理论上可覆盖更广泛的任务类型。这一差异的根源在于任务生成的自动化程度：CodeMidas 通过智能体识别功能并反向推导规格，避免了人工记录的偏差，但也引入了智能体识别错误的风险。

从方法设计看，CodeMidas 与 SWE-bench 的执行验证范式一致，但在验证器构建上更为严格。SWE-bench 依赖人工编写的测试，可能存在覆盖不足或过度约束，而 CodeMidas 通过执行参考代码生成测试，并结合后向过滤机制，确保验证器对替代实现的公平性。这一设计解决了此前方法中验证器与参考实现耦合过紧的问题，但增加了环境构建的计算成本。

## 总结

CodeMidas 解决了 RL 训练环境中任务多样性与奖励可靠性之间的矛盾，通过仅以源码为输入的智能体流水线，将已实现功能转化为可验证的训练任务。其核心创新在于行为规格化与后向过滤机制，确保了任务的质量与区分度。实验证明，在 5,545 个任务上训练 MiMo-V2.5 后，ProgramBench 的 Almost Solved 分数从 4.5 提升至 21.5，DeepSWE 的通过率从 10.0% 提升至 21.7%。然而，论文未报告与 SOTA 模型的横向对比，且缺乏对任务难度分布控制的详细分析，导致其在不同模型能力水平下的泛化边界尚不明确。当任务难度与模型能力不匹配时，后向过滤机制是否仍能保持有效的训练信号，论文未给出回答。
