# HuggingFace最新推荐论文 ｜Terminal-Universe: Turning Agent Trajectories into Scalable Terminal Environments ｜终端智能体环境逆向工程

研究机构：清华大学

论文原文见 [arXiv](https://arxiv.org/abs/2609.04148)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.04148)

> 终端代码智能体的后训练依赖可执行环境提供验证反馈，但真实环境稀缺且手动构建成本高昂。现有方法要么从仓库历史恢复状态，要么从零合成任务，均无法利用已积累的海量智能体轨迹。本文提出 Terminal-Universe，通过确定性回放与智能体补全从轨迹逆向重建可执行工作区，并沿广度与深度轴扩展任务。该方法在 Terminal-Bench 2.1 上提升 11.9 点，但其重建保真度对复杂依赖任务的泛化影响尚存疑。

## 研究背景

终端智能体在容器化环境中执行代码任务时，其工具调用历史（如 Read、Write、Edit）完整记录了文件操作序列与内容变更。这一记录构成了环境状态的“投影”：虽然未访问的文件与隐式依赖不可见，但已触及路径的初始状态与最终状态可被精确提取。这种“轨迹即环境观测”的特性，使得从轨迹逆向恢复执行上下文成为可能，区别于传统“环境生成轨迹”的前向范式。

现有环境构建路线存在结构性瓶颈。基于仓库历史的方法（如 SWE-Gym）依赖 Git 提交记录，仅能恢复特定 Bug 修复前的状态，任务类型局限于修复类；扰动方法（如 CLI-Gym）通过注入故障生成任务，但任务多样性受限于源仓库规模；任务条件合成方法（如 TMax）从零生成任务与环境，但生成的工作区往往过于整洁，缺乏真实工程的复杂性。这些方法共同忽略了已存在的智能体轨迹这一资源：轨迹不仅包含任务定义，更隐含了环境的真实结构与依赖关系。Terminal-Universe 的切入点在于将轨迹视为环境的“负片”，通过逆向工程恢复可复用的执行基底，从而突破手动构建与合成生成的规模限制。

## 核心方法

### 方法参照系

标准智能体后训练流程为“环境→轨迹→SFT”，即先构建可执行环境，再由教师模型生成轨迹进行监督微调。本文的关键差异在于逆向该映射：从“轨迹→环境→新轨迹”，将冻结的演示转化为可反复查询、验证与扩展的动态执行上下文。这一转变使得同一环境可被更强模型重新求解，并通过外部验证器筛选高质量样本，解决了原始轨迹质量受限于生成模型能力且无法验证正确性的问题。

### 两阶段环境重建

确定性回放阶段按时间顺序处理轨迹中的文件操作，恢复每个访问路径的最早可见版本，排除智能体创建的文件，形成部分工作区 $\hat{E}_0$。由于轨迹仅暴露智能体触及的路径，且文件内容可能截断，$\hat{E}_0$ 必然不完整。智能体补全阶段引入一个专用智能体，在 $\hat{E}_0$ 与恢复的任务 $q$ 条件下，创建缺失文件、补全部分文件并恢复依赖，但不实现任务本身，得到完整工作区 $\hat{E}$。该设计解决了回放后工作区任务不足的问题：在 38,294 个终端环境中，回放后充分率仅 40.2%，补全后提升至 93.5%。

$$
\hat{E} = \text{Complete}(\hat{E}_0, q) \quad \text{s.t.} \quad \hat{E} \text{ is task-sufficient for } q
$$

此公式表示补全过程以任务 $q$ 为条件，将部分工作区 $\hat{E}_0$ 转化为满足任务执行条件的完整工作区 $\hat{E}$，其核心约束是“充分性”而非“完整性”，即只需提供足够上下文使智能体可工作，无需还原所有未访问文件。

### 广度与深度任务扩展

重建后的工作区通过四种机制重新查询。Intent Recovery 恢复原始任务；Single-WS 在工作区内合成新任务；Cross-WS 挖掘工作区间方向性依赖，生成跨代码库任务，要求智能体在只读参考工作区与可写目标工作区间协调信息；Multi-Round 将单轮查询扩展为多轮会话，用户智能体根据前轮结果动态调整需求，每轮均通过验证器反馈。Cross-WS 任务显著增加复杂度：中位轮次从 15.1 增至 25.3，工具调用从 21.2 增至 39.7，教师模型 pass@1 从 72.3% 降至 49.2%。

$$
\text{Task}_{\text{cross}} = f(\hat{E}_{\text{target}}, \hat{E}_{\text{ref}}, \text{dep}) \quad \text{where} \quad \hat{E}_{\text{ref}} \text{ is read-only}
$$

此公式表示跨工作区任务由目标工作区、只读参考工作区及依赖关系共同定义，参考工作区仅提供挂载路径而非内部细节，迫使智能体自主导航、内化并适配参考实现，从而生成真实工程中常见的跨项目集成任务。

## 实验评估

| :--- | :--- | :--- | :--- | :--- |
| Qwen3.5-27B (Base) | Qwen3.5-27B | – | 46.2±3.9 | 6.3 |
| Terminal-Universe-27B | Qwen3.5-27B | 32.0k | 58.1 | 20.1 |

| RST-27B | Qwen3.5-27B | 37.5k | – | – |

Terminal-Universe 在 Terminal-Bench 2.1 上达到 58.1%，较基座模型提升 11.9 点，较 TMax-27B 高 13.2 点。EvoCode-Bench v2 MT@4 从 6.3 提升至 20.1，表明多轮扩展有效改善了持久任务性能。基线覆盖 TMax、RST、CalibForge 等合成方法，但缺失纯强化学习基线，且多数对比方法未报告 EvoCode 指标，限制了跨方法直接比较。

| 消融变体 | 数据量 | TB2.1 (Terminus2-XML) |
| :--- | :--- | :--- |
| 源轨迹 SFT | 35.8k | 36.7 |
| Intent Recovery | 35.8k | 52.1 |
| Replay only | 35.8k | 48.7±3.5 |
| Replay + Completion | 35.8k | 52.9±1.4 |
| Single-WS + Cross-WS | 28.9k | 58.4±2.1 |

消融显示，重新求解重建环境（52.1）远优于模仿源轨迹（36.7），证明环境重建本身比轨迹质量更重要。智能体补全带来 4.2 点提升（52.9 vs 48.7）且方差更小（±1.4 vs ±3.5），验证了补全对执行上下文完整性的贡献。Cross-WS 数据加入后，Single-WS 基线从 56.4 提升至 58.4，其中模型训练（+15.0）与调试（+10.0）类别增益最大，而安全（-2.1）与科学计算（-2.5）类别略有下降，降幅在 8 任务以内类别的运行间变异范围内。

评估协议使用 Terminus2-XML 与 Claude Code 两种脚手架，但多数对比方法仅报告单一脚手架结果，且未提供置信区间。代码未公开，超参数（学习率 7×10⁻⁶，批大小 256，序列长度 256k）已披露，但环境重建的随机种子与补全智能体配置未详细说明，可复现性受限。

## 关联研究分析

从问题动机看，Terminal-Universe 与 SWE-Gym 均旨在从历史数据恢复环境，但 SWE-Gym 依赖 Git 提交记录，仅能恢复特定 Bug 修复前的状态，任务类型局限于修复类；Terminal-Universe 从轨迹回放，无需原始仓库权限，且可生成非修复类任务。这一差异源于轨迹记录了智能体的完整操作序列，而 Git 仅记录最终状态，前者保留了过程信息，后者仅保留结果信息。然而，轨迹回放无法恢复未访问的文件与隐式系统依赖，这是否限制了复杂依赖任务的泛化，论文未给出量化回答。

从方法设计看，Terminal-Universe 与 RST 均采用递归扩展策略，但 RST 基于种子任务递归扩展解决方案长度，Terminal-Universe 基于重建环境扩展任务广度与深度。RST 的扩展受限于种子任务的质量与多样性，Terminal-Universe 的扩展受限于环境重建的保真度。两者均使用验证器过滤，但 Terminal-Universe 的验证器由智能体在容器内自动编写，而 RST 的验证器来自原始任务定义。这种自动化验证器是否引入新的偏差，例如验证器本身对任务理解的错误，论文未进行独立评估。

## 总结

Terminal-Universe 解决了终端智能体后训练中可执行环境稀缺与轨迹资源浪费的矛盾。其切入点在于将轨迹视为环境的逆向观测，通过确定性回放与智能体补全恢复可复用工作区，并沿广度与深度轴扩展任务。该方法在 Terminal-Bench 2.1 上提升 11.9 点，EvoCode-Bench v2 MT@4 提升 13.8 点，证明环境重建与重新求解优于源轨迹模仿。其边界在于重建过程固有的信息损失：未访问文件与隐式依赖无法恢复，导致 6.5% 的终端环境与 22.9% 的 SWE 环境在补全后仍任务不足。当环境依赖关系复杂到需要跨多个未访问模块协同时，重建工作区的充分性是否仍能支撑高质量任务生成，论文未给出回答。
