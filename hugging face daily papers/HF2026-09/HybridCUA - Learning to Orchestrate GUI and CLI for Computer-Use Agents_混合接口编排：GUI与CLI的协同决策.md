# HuggingFace最新推荐论文 ｜HybridCUA: Learning to Orchestrate GUI and CLI for Computer-Use Agents ｜混合接口编排：GUI与CLI的协同决策

作者：Tongbo Chen、Junbo Niu、Zhengxi Lu 等 11 人

论文原文见 [arXiv](https://arxiv.org/abs/2609.38008)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.38008)

> 计算机使用智能体（Computer-Use Agent, CUA）依赖图形用户界面（GUI）执行任务时，长序列点击易引发级联错误且效率低下，而应用特定API虽快却缺乏跨应用泛化性。现有模型直接接入命令行界面（CLI）后性能不升反降，暴露出“何时调用”与“如何执行”的双重决策盲区。本文通过构建GUI-CLI混合轨迹数据并引入CLI感知强化学习，使9B参数模型在OSWorld基准上取得53.6%准确率，较基线提升14.8个百分点，但其在32B级模型面前的性能差距及跨操作系统泛化边界仍存疑。

## 研究背景

CUA的核心困境在于动作空间的效率与通用性矛盾。GUI操作通过像素级截图实现跨平台通用性，但将文件操作、文本编辑等任务分解为原子点击与键入时，步骤数激增导致错误累积概率呈指数上升。CLI作为操作系统原生接口，能将长GUI序列压缩为单条命令，但其使用前提是模型具备在特定GUI上下文中判断命令适用性的能力，这构成了混合接口编排的核心挑战。

主流CUA训练范式存在两个结构性缺陷。数据层面，GUI、Shell与代码语料库各自独立，CUA数据集几乎仅含GUI动作，终端数据集则剥离了GUI上下文，导致模型从未见过混合行为样本。监督层面，步级模仿学习偏好局部合理动作，结果奖励仅校验任务完成状态，两者均无法区分“高效接口选择”与“低效但成功的路径”。这种监督盲区使得模型即便拥有Shell访问权限，也无法将其转化为有效动作——实验显示，直接为Qwen3.5-27B和EvoCUA-32B暴露CLI后，OSWorld准确率分别下降2.5至11.5个百分点，且CLI步骤占比仅为15.0%和0.15%。

本文切入点在于将接口选择显式化为训练信号。通过构建包含GUI-only、CLI-only及交错轨迹的混合数据集，并设计任务级与动作级双重CLI感知奖励，HybridCUA将“何时用CLI”与“如何可靠执行CLI”解耦为两个可独立优化的子问题，从而在统一Bash动作空间内实现GUI通用性与CLI效率的协同。

## 核心方法

### 统一Bash动作空间

CUA训练的标准流程通常将GUI操作与工具调用分离为独立动作类型，本文的关键差异在于将所有可执行交互统一为单一Bash接口。GUI操作通过PyAutoGUI代码封装在Python heredoc中，CLI操作直接调用Shell命令，两者共享同一动作格式 $A = \{bash(c, \delta) \mid c \in C_{CLI} \cup C_{GUI}\} \cup \{wait, terminate, answer\}$，其中 $c$ 为命令，$\delta$ 为超时参数。这一设计消除了接口切换的显式标记，迫使模型在单一动作空间内自主决策路由，避免了分离工具架构中常见的路径混淆问题。

### 混合轨迹数据合成

数据合成环节针对“混合行为样本缺失”问题，构建了三类互补轨迹。GUI-only轨迹从开源UI-MOPD数据集转换而来，将GUI动作重表达为PyAutoGUI代码；CLI-only轨迹由Qwen3.8-27B在Claude Code框架下解决CUA-Gym任务生成，仅保留成功执行样本；交错轨迹通过两条路径获取：一是模型自由切换接口执行，二是将GUI-only轨迹中的适用片段重写为等效CLI命令后重放，仅保留成功重放。最终5,023条轨迹覆盖11个应用领域，平均10.4步，其中LibreOffice Calc、Writer、Impress分别贡献866、818、811条。该设计确保模型同时学习GUI控制、Shell命令执行及接口路由三种能力，而非仅模仿单一接口行为。

### CLI感知强化学习

SFT阶段后，模型虽能执行混合动作，但缺乏对接口选择效率的感知。本文引入两项CLI感知奖励解决此问题。任务级奖励 $R_{CLI} = \mathbb{I}[\text{Success}(\tau)] \cdot \mathbb{I}[b(\tau) = b^*]$ 中，$b^*$ 为任务标注（CLI是否提供明确执行优势），$b(\tau)$ 为轨迹是否包含直接CLI命令，该奖励仅当任务成功且接口选择与标注一致时触发，教会模型“何时”调用CLI。动作级奖励 $r_t^{exec} = \begin{cases} -1, & \text{if shell execution failure} \\ 0, & \text{otherwise} \end{cases}$ 基于终端反馈，将Shell执行失败归因于具体CLI动作，教会模型“如何”可靠执行命令。两项奖励分别嵌入轨迹级与步级优势函数，形成对路由决策与执行可靠性的双重监督。

## 实验评估

实验在OSWorld基准上进行，对比GUI-only、GUI-API及混合接口三类基线。基线覆盖Qwen3.5系列、OpenCUA、EvoCUA等GUI-only模型，ToolCUA、AutoGLM-OS、UltraCUA等GUI-API模型，但缺失纯CLI基线及最新SOTA（如EvoCUA-32B在OSWorld的56.7%）。

| 模型 | 动作空间 | 准确率(%) | 平均步数 |
| :--- | :--- | :--- | :--- |
| Qwen3.5-9B | GUI | 38.8 | 31.6 |
| Qwen3.5-9B + SFT | GUI | 44.2 | 26.3 |
| Qwen3.5-9B + SFT + RL | GUI | 50.4 | 22.1 |
| Qwen3.5-9B | GUI+CLI | 18.4 | 22.1 |
| HybridCUA-9B-SFT | GUI+CLI | 46.0 | 19.8 |
| HybridCUA-9B | GUI+CLI | 53.6 | 14.0 |

HybridCUA-9B以53.6%准确率和14.0平均步数领先同规模模型，较基线Qwen3.5-9B提升14.8个百分点。关键对比在于：直接暴露CLI导致准确率从38.8%骤降至18.4%，步数虽减少9.5但反映早期失败而非效率；经SFT与RL训练后，GUI+CLI分支在SFT阶段（46.0% vs 44.2%）和RL阶段（53.6% vs 50.4%）均优于GUI-only分支，且步数从26.3降至19.8、从22.1降至14.0，证明混合接口在训练后同时提升准确率与效率。

| 配置 | 准确率(%) | 平均步数 |
| :--- | :--- | :--- |
| Qwen3.5-9B | 38.8 | 31.6 |
| w/ CLI only SFT | 31.7 | 19.1 |
| w/ GUI only SFT | 43.2 | 29.5 |
| w/ Hybrid only SFT | 41.0 | 22.6 |
| HybridCUA-9B-SFT | 46.0 | 19.8 |

SFT数据消融显示，混合语料（46.0%）优于单一类型，较GUI-only高2.8个百分点，较CLI-only高14.3个百分点，较Hybrid-only高5.0个百分点。值得注意的是，Hybrid-only轨迹单独使用（41.0%）低于混合语料，表明单一接口演示与混合轨迹提供互补监督。RL阶段将准确率从46.0%提升至53.6%（+7.6个百分点），步数从19.8降至14.0（-29.3%）。移除任务级 $R_{CLI}$ 后，CLI使用率仅达58.9%（vs 64.0%），步数减少18.2%（vs 29.3%），准确率损失较小；移除动作级 $r_t^{exec}$ 后，执行错误率回升至16.5%（vs 11.5%），准确率与步数基本不变，证实两项奖励分别主导路由决策与执行可靠性。

评估边界方面，OSWorld-MCP上HybridCUA-9B达47.1%，较Qwen3.5-9B高9.1个百分点，与ToolCUA-8B（46.8%）相当；WindowsAgentArena上达36.0%，较基线高4.0个百分点，但训练仅使用Linux Shell，PowerShell命令的迁移能力存疑。论文未报告置信区间、推理延迟及Token消耗，且53.6%低于EvoCUA-32B的56.7%，参数量差异对性能的影响未解耦。

## 关联研究分析

从问题动机看，ToolCUA与本文同属混合接口路线，但ToolCUA依赖应用特定API，需为每个应用单独构建接口，泛化性受限于预定义工具覆盖范围；本文采用OS原生Shell，无需逐应用工程，但牺牲了API的语义明确性，将接口选择负担转移至模型。这一差异根源在于任务特性：Shell的通用性以命令可靠性为代价，而API的特定性以工程成本为代价，两者在“通用性-可靠性”权衡上处于不同位置。

从方法设计看，UI-TARS等纯GUI模型通过大规模SFT提升视觉接地能力，但动作空间局限于原子GUI操作，无法压缩长序列；本文继承其视觉感知基础，但扩展动作空间至CLI，并引入CLI感知奖励解决混合行为监督缺失问题。UI-TARS的SFT范式在静态指令遵循任务上仍具优势（AndroidControl-High上77.99%），但本文证明在动态长程任务中，混合接口+RL的组合能更有效地平衡效率与准确率，这一优势是否源于模型规模差异（9B vs 7B）或范式本身，论文未提供控制变量实验。

## 总结

HybridCUA解决的核心矛盾是GUI通用性与CLI效率的不可兼得，现有方法因数据隔离与监督盲区无法将Shell访问转化为有效动作。本文通过混合轨迹合成与CLI感知RL，将接口选择显式化为训练信号，使9B模型在OSWorld上达53.6%准确率、14.0平均步数，较基线提升14.8个百分点。其边界在于：53.6%仍低于32B级SOTA的56.7%，且Windows泛化依赖未验证的跨OS命令迁移能力。当模型规模扩大至32B时，混合接口范式的性能增益是否被参数量优势掩盖，还是能进一步缩小与SOTA的差距，论文未给出回答。
