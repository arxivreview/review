# HuggingFace最新推荐论文 ｜Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills ｜操作性知识蒸馏

研究机构：中国科学技术大学、中国人民大学

作者：Jianlyu Chen、Yuyang Hu、Hongjin Qian 等 11 人

论文原文见 [arXiv](https://arxiv.org/abs/2609.02749)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.02749)

> 自主机器学习研究代理在模型与执行框架之外缺失领域特定的“操作性知识”，导致其在复杂任务中陷入低效的试错循环。现有基于交互轨迹的技能生成方法难以从静态代码库中直接提取可验证的领域专长，且缺乏针对大规模静态源的离线蒸馏机制。本文提出DisCo框架，通过任务无关与任务导向的双模蒸馏，将静态仓库转化为经过验证的技能图，在不改变模型权重的前提下显著提升研究代理性能。该方法在ML研究域内验证了静态源蒸馏的有效性，但其跨域泛化能力及对动态版本漂移的适应性仍存疑。

## 研究背景

当研究代理面对陌生的数据集或复杂的实验配置时，它必须决定使用何种方法、调用哪个库的API以及规避哪些常见的实现陷阱。这种将领域方法绑定到具体任务执行过程的知识被称为操作性知识（Operational Knowledge），它不同于模型参数中固有的广泛先验，也不同于执行框架（Harness）提供的通用流程控制，而是连接“知道方法”与“让方法工作”的桥梁。缺乏这一层知识，代理只能在任务预算内通过反复试错来推断包行为，导致资源浪费且无法跨任务复用已发现的解决方案。

自主研究代理的架构通常由模型骨干（Model Backbone）和执行框架（Harness）组成，前者提供推理能力，后者负责编排与验证。然而，这两者均不包含特定领域的实操细节，导致代理在处理ML研究任务时表现受限。早期工作如Voyager（Wang et al., 2024）尝试从环境交互轨迹中生成可执行技能，但这类在线蒸馏方法依赖动态反馈，难以从静态、庞大且版本漂移的代码仓库中提取结构化知识。Trace2Skill（Ni et al., 2026）等后续工作虽引入了层级整合，但仍主要聚焦于轨迹池。本文的切入点在于识别静态源（如GitHub仓库和论文）中蕴含的丰富操作性知识，并解决如何自动、大规模地将其转化为紧凑、可验证且符合代理上下文预算的技能形式这一核心问题。

## 核心方法

### 方法参照系

本文问题归属于技能生成与蒸馏路线，但区别于基于交互轨迹的在线蒸馏，其核心差异在于输入源为静态声明性材料（Declarative Sources），如代码仓库和论文。标准流程通常假设技能从代理与环境交互产生的轨迹中提取，而本文需从非交互的、面向人类读者的静态文本中推导操作性指令，这要求解决源材料漂移、缺乏任务导向组织及验证缺失的问题。

### 双模蒸馏机制

针对静态源难以直接转化为可执行技能的问题，DisCo设计了任务无关（Task-Agnostic）与任务导向（Task-Oriented）两种互补的蒸馏模式。任务无关模式离线运行，将广泛使用的ML仓库压缩为可复用技能；任务导向模式按需运行，针对具体任务探索相关领域知识。每种模式均包含验证门控（Verification Gating），确保进入技能库的每个候选技能都经过检查与修复。技能表示为三层结构：$S = (SKILL.md, references/, scripts/)$，其中$SKILL.md$作为知识接口提供使用策略，$references/$作为知识基底存储API文档，$scripts/$作为执行接口提供自动化脚本。这种结构实现了能力（Capability）与策略（Policy）的解耦，使代理能在不加载全部细节的情况下按需获取操作指引。

### 层级路由与技能图

为解决大规模技能库的检索瓶颈，AREX-Skill Library采用基于能力族（Capability Family）的层级路由而非简单的向量相似度匹配。每个仓库被蒸馏为一个技能图 $G = (S, L)$，其中 $S$ 为技能节点集合，$L \subseteq \{(S_i, S_j) \in S \times S | i \neq j\}$ 为链接集合，编码路由、依赖或组合关系。代理首先读取入口技能（Entry Skill），该技能概括了源范围并路由至组件技能。通过渐进式披露（Progressive Disclosure）原则，代理仅加载当前任务所需的技能分支，从而在保持上下文预算有限的同时访问数千个技能。这种图结构使得技能间的依赖关系显式化，避免了扁平检索中常见的依赖遗漏问题。

## 实验评估

实验在MLE-bench、PaperBench、FrontierCS和PassNet四个基准上进行，固定GPT-5.5骨干、研究框架和执行预算，仅改变是否加载蒸馏技能。基线包括无技能Codex、TorchInductor以及Claude Code等公开系统。

| 基准 | 无技能基线 | 加技能后 | 相对提升 |
| :--- | :--- | :--- | :--- |
| MLE-bench | 31.11% | 72.89% | 134.3% |
| PaperBench | 29.45% | 39.59% | 34.4% |
| FrontierCS | 70.63 | 77.14 | 9.22% |
| PassNet | 1.343 | 1.5313 | 14.0% |

在MLE-bench上，技能带来的增益在高难度任务中尤为显著，得分从13.33%提升至62.22%。PaperBench中，18/20的任务得分提升，仅在两个高基线任务上出现轻微下降，表明检索精度存在边际权衡。FrontierCS的配对bootstrap分析显示，平均提升的95%置信区间为[3.41, 9.83]分，且技能主要恢复了低分任务。PassNet中，失败样本从14个减少至5个，正确率从81.35%提升至90.76%。

消融分析显示，技能访问与额外资源消耗（Token、步骤、工具调用）几乎不相关（Spearman’s ρ < 0.02），说明性能提升源于知识引导而非资源堆砌。在PassNet构建阶段，第二版技能图将几何平均速度从0.5352提升至0.6941，匹配失败率从20%降至2%。错误分析发现，初版技能中过于绝对的“禁止重写厂商优化算子”规则阻碍了特定卷积场景的优化，修订为可证伪先验后性能恢复。

评估边界方面，所有实验均在固定GPT-5.5骨干下进行，未验证不同模型骨干下的泛化性。代码已开源，但技能库的构建依赖特定版本的仓库快照，未讨论版本漂移对技能有效性的长期影响。

## 关联研究分析

从问题动机看，本文与Voyager（Wang et al., 2024）和Trace2Skill（Ni et al., 2026）均致力于解决技能生成问题，但输入源存在根本差异。Voyager从具身环境的交互轨迹中提取可执行代码，Trace2Skill从轨迹池中并行蒸馏SOP，二者均依赖动态反馈来验证技能质量。本文则从静态代码库和论文中蒸馏，面临源材料缺乏任务导向组织且版本漂移的挑战。这种差异源于任务特性：ML研究任务高度依赖特定库的API细节和配置陷阱，这些知识在静态文档中更为丰富，而交互轨迹往往只覆盖部分执行路径。静态源蒸馏能否捕捉运行时动态依赖，是本文方法未完全解决的盲区。

从方法设计看，本文的层级路由机制与SkillDAG（Bai et al., 2026）等图结构检索方法相似，但本文的路由基于能力族分类而非语义相似度。SkillDAG在SkillsBench上的表现（27.3%）低于基于轨迹的方法，可能源于图构建的初始质量限制。本文通过验证门控确保每个技能的正确性，从而提升了图结构的可靠性。然而，本文未与SkillOpt（Yang et al., 2026）等基于验证门控的优化方法直接对比，后者优化的是技能对任务性能的边际贡献，而本文验证的是技能本身的正确性。这种验证目标的差异导致两种方法在技能更新频率和适应性上存在潜在冲突。

## 总结

本文旨在解决自主ML研究代理中操作性知识缺失导致的低效试错问题。现有基于轨迹的蒸馏方法难以从静态源中提取可验证的领域专长，而本文通过双模蒸馏和层级路由，将静态仓库转化为紧凑、可验证的技能图，在不改变模型权重的前提下实现了性能提升。实验证明，在固定骨干和预算下，技能加载使MLE-bench得分提升134.3%，PaperBench提升34.4%。然而，本文的边界在于技能库依赖特定版本快照，未验证跨版本漂移的适应性，且仅在GPT-5.5骨干下评估。当仓库版本更新导致API变更时，静态蒸馏的技能是否仍能保持有效性，论文未给出回答。
