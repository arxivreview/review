> 导读 临床计算器要求精确数值输出，但大语言模型（LLM）在算术运算上存在固有缺陷，导致单一数值错误可能改变医疗建议。现有方案依赖为每个计算器编写并维护硬编码函数，但这种方式覆盖有限且维护成本高，无法泛化到未实现的计算器。本文提出 Program-Solve 接口，让模型生成案例特定的 Python 程序，由受限执行器运行，将模型任务从“计算”降维为“决定如何使用求解器”。该方法在 32B 模型上显著优于直接算术，但在 7B 模型上优势不显著，且其性能高度依赖公式与变量的准确供给，揭示了规模效应与输入质量对确定性求解的边界约束。

## 研究背景

临床计算器（如 APACHE II、eGFR）将患者笔记中的变量代入特定公式，输出用于决策的数值。这一过程包含三个环节：公式选择、变量提取与算术执行。LLM 在基础算术任务（如多位数加法）中表现不稳定，原因在于内部数值表示缺乏精确的代数结构，导致“验证鸿沟”——模型难以区分逻辑推理错误与计算错误，无法有效自我修正。当 LLM 直接处理临床笔记时，Goodell 等人报告在 48 个计算任务中约三分之一的答案错误，暴露了端到端生成在精确计算上的脆弱性。

主流解决方案是神经符号混合架构，即通过外部工具或符号引擎保证计算确定性。MedCalc-Bench 等基准推动了计算器调用形式化，MedRaC 采用检索加 Python 执行，RiskAgent 选择验证过的工具。然而，这些方法通常依赖预定义的硬编码函数库，每个计算器需单独编写、验证和维护。这种“一计算器一函数”的模式导致覆盖度受限：评估中的 22 个计算器库仅能处理 1,100 个案例中的 440 个，其余 660 个案例因库未实现而被迫放弃回答（abstention），整体准确率被锁定在 40.0%。本文的切入点在于：能否用通用接口替代专用函数，让模型动态生成代码，由执行器确定性运行，从而突破硬编码库的覆盖瓶颈？

## 核心方法

### 方法参照系

本文问题属于神经符号求解路线，核心是将 LLM 的生成能力与外部执行器的确定性结合。标准流程是：LLM 生成代码，解释器执行，返回结果。本文的关键差异在于执行器的受限性与临床公式的版本敏感性：执行器不包含任何计算器特定函数或常量，模型必须将文本公式翻译为代码；同时，临床公式本身存在版本迭代（如 MELD 3.0 替代旧版），基准测试可能仍奖励已废弃的公式，这要求方法不仅关注计算正确性，还需考虑公式来源的时效性。

### 受限执行器与代码生成

设计动机：硬编码函数库的覆盖度是固定函数，无法扩展；而 LLM 直接算术存在精度瓶颈。本文在 LLM 与最终答案之间插入一个受限执行器，强制计算过程确定性化。执行器是一个新鲜子进程，内置允许列表仅包含 `math`、`datetime`、`time`、`calendar` 等标准模块，禁止文件访问、动态评估（`eval`/`exec`）及全局变量操作，内存限制 256 MB，墙钟时间 5 秒。模型接收笔记、公式文本和变量列表，生成一个 `solve()` 函数，执行器运行后返回数值、日期或孕周元组。该机制将 LLM 的任务从“计算数值”转变为“编写计算逻辑”，公式的物理含义由模型理解，算术精度由执行器保证。

$$
\text{Answer} = \text{Executor}(\text{LLM}(\text{Note}, \text{Formula}, \text{Variables}))
$$

此公式表明，最终答案完全由执行器对 LLM 生成代码的运行结果决定，LLM 不直接输出数值，从而隔离了算术错误。

### 输入匹配与消融设计

设计动机：此前研究常混淆“执行器优势”与“输入质量优势”。若模型获得公式和变量，其代码生成能力可能被高估；若缺乏这些输入，性能下降可能源于提取错误而非执行器失效。本文设计了严格的输入匹配协议：Program-Solve 与 Open-book arithmetic（直接算术）均读取完整笔记、给定公式和变量，确保对比仅反映“执行方式”差异。同时，Blind Program-Solve 不提供公式和变量，模型需自行提取，用于解耦“执行器”与“提取能力”的贡献。此外，Gold-Solve library 提供硬编码函数和黄金变量，作为覆盖度受限的上界参考。

$$
\Delta_{\text{exec}} = \text{Acc}(\text{Program-Solve}) - \text{Acc}(\text{Open-book arithmetic}) \quad \text{with matched inputs}
$$

该差值量化了在执行条件匹配下，代码生成相对于直接算术的净收益，排除了输入差异的干扰。

## 实验评估

实验基于 MedCalc-Bench Verified（1,100 个案例，55 个计算器），使用 Qwen2.5-7B 和 Qwen2.5-32B-AWQ，5 个种子（42-46），vLLM 服务。基线覆盖直接算术（Open-book arithmetic）、硬编码库（Gold-Solve/Extract-Solve library）及盲测程序生成（Blind Program-Solve）。缺失强基线如 CodeInterpreter 或 MedRaC 的完整复现，但 Gold-Solve library 作为硬编码上界具有代表性。

| 模型 | 方法 | 完整集准确率 (%) | 覆盖集准确率 (%) |
|---|---|---|---|
| Qwen2.5-7B | Open-book arithmetic | 72.02 | 83.64 |
| Qwen2.5-7B | Program-Solve | 75.31 | 84.18 |
| Qwen2.5-32B-AWQ | Open-book arithmetic | 83.47 | 91.45 |
| Qwen2.5-32B-AWQ | Program-Solve | 90.53 | 98.64 |
| Qwen2.5-7B | Gold-Solve library | 40.00 | 100.00 |
| Qwen2.5-32B-AWQ | Gold-Solve library | 40.00 | 100.00 |

核心对比显示：在 32B 模型上，Program-Solve 比 Open-book arithmetic 高 7.05 个百分点（95% 计算器聚类置信区间 [0.47, 14.60]，不跨零）；在 7B 模型上，差异为 3.29 个百分点（区间 [-3.49, 10.38]，跨零），统计上不显著。Gold-Solve library 在覆盖的 440 个案例上达到 100%，但因放弃其余 660 个案例，整体准确率仅为 40.00%。

消融实验揭示输入质量的决定性作用。Blind Program-Solve（无公式、无变量）在 7B 上准确率为 28.04%，比 Program-Solve 低 47.27 个百分点；在 32B 上为 44.71%，低 45.82 个百分点。这表明执行器本身无法补偿变量提取错误。笔记预算消融显示，将笔记从完整截断至 250 词，Extract-Solve library 准确率从 38.84% 降至 32.30%（7B），证实信息完整性对提取的影响。语法提示行（Program-Solve + syntax）在 7B 上提升 2.64 个百分点，但在 32B 上提升微弱，暗示小模型更依赖显式格式约束。

评估边界方面，指标仅报告准确率，未提供置信区间或过程级评估（如变量提取正确率）。可复现性良好，代码、模型 ID、执行器限制（256 MB 内存、5 秒墙钟）均公开。局限包括：执行器非沙箱（无容器或系统调用过滤），存在安全风险；基准为英文美国惯例，未评估多语言或单位转换（如 mmol/L vs mg/dL）；公式版本审计发现 16/55 个计算器存在版本或系数问题，但基准仍奖励旧版公式，导致“正确”答案可能临床无效。

## 关联研究分析

从问题动机看，本文与 MedRaC 同属神经符号路线，但 MedRaC 强调检索与执行分离，评分公式选择、提取和算术三个环节；本文则聚焦执行环节的确定性，通过受限执行器强制算术正确，但未深入评估公式选择错误的影响。差异根源在于任务特性：MedRaC 面向证据检索，需处理多源信息；本文面向单计算器执行，公式已给定，瓶颈在算术精度。本文未探索公式选择错误（如选错计算器）对最终结果的影响，而 Goodell 等人指出多数计算器选择错误是理解错误而非算术错误，这暗示 Program-Solve 在公式选择环节可能仍存在盲区。

从方法设计看，本文与 PAL（Program-Aided Language Models）共享“生成代码-执行”范式，但 PAL 面向通用数学推理，执行器无领域约束；本文引入临床公式版本敏感性与受限执行器，强调安全性与确定性。与 RiskAgent 相比，RiskAgent 选择验证过的工具，本文主张通用代码生成替代专用工具，但实验显示在 7B 模型上通用生成无优势，挑战了“代码生成必然提升算术”的共识。差异根源可能是规模效应：小模型代码生成能力不足，无法充分利用执行器；大模型则能生成更鲁棒的代码。论文未提供证据解释 7B 模型执行器失效的具体原因，是代码生成能力不足还是公式理解瓶颈，尚不明确。

## 总结

本文要解决的核心矛盾是临床计算器对算术精度的要求与 LLM 算术不可靠性之间的冲突。现有硬编码函数库覆盖有限，无法泛化；本文抓住“执行确定性”这一被忽略的点，通过受限执行器将 LLM 任务降维为代码生成，从而隔离算术错误。实验证明，在 32B 模型上，Program-Solve 比直接算术高 7.05 个百分点，显著优于硬编码库的整体覆盖率；但在 7B 模型上优势不显著，且性能高度依赖公式与变量的准确供给。本文的边界在于：执行器非沙箱，存在安全风险；基准未评估多语言与单位转换；公式版本问题未解决，导致“正确”答案可能临床无效。当模型规模缩小到 7B 时，代码生成能力是否足以支撑执行器的确定性优势，论文未给出回答。
