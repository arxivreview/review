# HuggingFace最新推荐论文 ｜Agensh: Scaling Organizational Intelligence to 1,024 Agents ｜去中心化多智能体组织扩展

研究机构：微软研究院

作者：Zhihao Zhan、Ting Song、Li Dong 等 7 人

论文原文见 [arXiv](https://arxiv.org/abs/2609.26781)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.26781)

> 多智能体系统旨在通过并行协作突破单模型在长程任务上的延迟与能力瓶颈，但现有框架普遍依赖中心编排器进行任务分配与状态同步，导致系统扩展性受限于编排器的协调容量。本文提出 Agensh，一种无中心编排器的自组织多智能体协作框架，通过共享工作区、消息接口与共享上下文三大基础设施，让智能体自主认领子任务并异步整合进度。实验表明，在 ProgramBench 最难的五个软件工程任务上，将智能体数量从 1 扩展至 128，平均最终测试通过率从 19.31% 提升至 28.78%。该框架验证了智能体数量作为新扩展维度的有效性，但其性能增益是否完全源于去中心化协作机制而非单纯的并行计算，论文未提供消融实验予以区分。

## 研究背景

单智能体系统受限于单一上下文窗口与顺序执行流，在处理复杂软件工程任务时面临高延迟与能力天花板。当任务复杂度超越单模型处理极限时，多智能体系统通过角色分工与信息交换分担认知负荷，其核心假设是集体智能能超越个体能力。然而，这一假设的成立依赖于特定的通信结构与协调机制，而非简单的模型数量叠加。

现有主流多智能体框架如 Claude Code、Codex 及 Kimi Agent Swarm 均采用编排器-工作者架构，由主智能体规划、分解任务并分配给并发工作者。这种结构通常需要一个经过训练的编排器来有效管理工作者并整合其贡献，导致系统整体扩展性从根本上受限于编排器的协调容量。当智能体数量增加时，编排器面临的任务分配、状态同步与冲突解决压力呈非线性增长，成为系统规模化的瓶颈。

Agensh 的切入点在于移除中心编排器，将任务发现、依赖协调与结果整合的责任分散给所有工作者。通过轻量级的组织基础设施，工作者在持久工作循环中自主认领子任务、交换发现并整合贡献，从而突破编排器容量限制，实现大规模智能体组织的自组织协作。

## 核心方法

### 多智能体协作循环与组织基础设施

Agensh 的核心抽象是协作循环，每个工作者并发且异步执行五个步骤：收集上下文、认领子任务、执行操作、验证结果、合并进度。该循环通过提示词中的工作流指令实现，而非硬编码在运行时基础设施中，确保了与底层单智能体框架的即插即用兼容性。

$$
\text{Loop}(w) = \text{Repeat}(\text{Gather}(w), \text{Claim}(w), \text{Act}(w), \text{Verify}(w), \text{Merge}(w)) \quad \text{until Goal Achieved}
$$

该公式描述了工作者 $w$ 的迭代过程，其物理含义是工作者通过反复执行局部行动并同步至全局状态，将个体进度转化为组织贡献。设计动机在于解决中心编排器在大规模场景下无法实时响应所有工作者状态更新的问题，通过异步执行允许每个工作者在不等待其他同伴完成迭代的情况下继续工作。

### 去中心化协调机制

Agensh 通过三个组件实现去中心化协调：共享工作区、消息接口与共享上下文。共享工作区基于 Git 平台，支持并发写入与异步读取，记录变更来源并检测文本合并冲突。消息接口包含共享任务频道与直接消息，低优先级消息在每次循环迭代开始时投递，高优先级直接消息在每次基础设施工具调用结束时投递。共享上下文保留可复用的发现与工作声明，采用追加式数据库存储近期记忆，并提供上下文 grep 工具搜索完整历史记录。

$$
\text{SharedContext} = \{ \text{OBSERVED}, \text{FACTs}, \text{FAIL}, \text{CLAIMs}, \text{PATCH\_SUMMARY} \}
$$

该集合定义了共享上下文中条目类型，其算法含义是工作者通过发布类型化条目实现组织级知识积累与状态同步。设计动机在于解决自然语言通信中语义歧义与信息丢失问题，通过结构化条目确保工作者能准确复用同伴发现、解决子任务重叠并整合贡献。

## 实验评估

实验在 ProgramBench 最难的五个任务（FFmpeg、gromacs、pandoc、PHP-src、ctags）上进行，使用 GPT-5.6-sol (high) 模型与 Copilot 单智能体框架，预算为 6 小时。基线仅对比不同智能体数量（1, 8, 32, 128, 1024），未对比 GPTSwarm、G-Designer 等拓扑优化方法或 DeLM 等去中心化框架，缺乏横向方法对比。

| 任务 | 智能体数量 | 最终测试通过率 (%) |
| :--- | :--- | :--- |
| 五任务平均 | 1 | 19.31 |
| 五任务平均 | 8 | 20.68 |
| 五任务平均 | 32 | 26.52 |
| 五任务平均 | 128 | 28.78 |
| pandoc | 1 | 33.89 |
| pandoc | 128 | 50.94 |
| pandoc | 1024 | 55.06 |

数据显示，从 1 到 128 智能体，平均测试通过率提升 9.47 个百分点，相对提升约 49%。在 pandoc 任务上，1024 智能体比 128 智能体提升 4.12 个百分点，比单智能体提升 21.17 个百分点。

论文未提供消融实验以区分性能增益来源。智能体数量增加可能同时带来并行计算加速与协作机制优化两种效应，但论文未通过固定智能体数量改变协作机制或固定协作机制改变并行度来分离变量。轨迹分析显示，随着组织规模扩大，自组织协作形式从同伴协调、多工作者整合逐步演进至标准化工作流与专业化角色，但缺乏量化指标衡量这些协作形式对最终性能的贡献度。

评估边界方面，实验仅在软件工程任务上进行，未覆盖数学推理、通用问答等其他任务类型。代码已开源，但超参数与 GPU 配置未详细披露，可复现性依赖社区复现。指标仅关注最终测试通过率，未报告 Token 消耗、延迟分布或错误级联率，无法全面评估系统经济性。

## 关联研究分析

从问题动机看，Agensh 与 Kimi Agent Swarm 均旨在降低多智能体系统延迟，但路线截然相反。Kimi Agent Swarm 通过训练编排器分解任务并调度子智能体，保留中心控制以优化调度效率；Agensh 则移除编排器，依赖基础设施实现自组织。这一差异源于对扩展性瓶颈的不同判断：Kimi 认为编排器容量可通过训练提升，Agensh 认为中心控制是根本限制。然而，Agensh 未提供证据表明自组织在任务复杂度低于编排器容量阈值时优于中心控制，其优势是否仅在超大规模场景下显现，论文未给出回答。

从方法设计看，Agensh 与 DeLM 共享异步工作者与共享上下文理念，但 Agensh 引入 Git 版本控制作为共享工作区，强化了变更溯源与冲突检测。DeLM 侧重任务队列管理，Agensh 侧重代码整合一致性。STORM 将多智能体编码重构为状态管理问题，强调本地状态一致性与陈旧编辑检测，与 Agensh 的 Git 合并冲突解决机制相似，但 STORM 未探索智能体数量扩展对协作形式涌现的影响。Agensh 的 Git 机制是否比纯内存状态管理更适合长程任务，论文未进行对比实验。

## 总结

Agensh 旨在解决中心编排器容量限制导致的多智能体系统扩展性瓶颈，通过移除编排器并构建共享工作区、消息接口与共享上下文基础设施，实现智能体自主认领任务与异步整合。实验证明，在 ProgramBench 最难的五个任务上，128 智能体平均测试通过率较单智能体提升 9.47 个百分点，pandoc 任务上 1024 智能体达到 55.06%。其边界在于缺乏消融实验区分并行计算与协作机制的贡献，且仅在软件工程任务上验证，未覆盖其他任务类型。当智能体数量继续增加至数千规模时，共享上下文的检索效率与 Git 合并冲突解决延迟是否成为新的瓶颈，论文未给出回答。
