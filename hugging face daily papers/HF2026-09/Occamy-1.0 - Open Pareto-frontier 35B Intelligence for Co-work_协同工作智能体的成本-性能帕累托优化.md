# HuggingFace最新推荐论文 ｜Occamy-1.0: Open Pareto-frontier 35B Intelligence for Co-work ｜协同工作智能体的成本-性能帕累托优化

作者：Wenhui Chen、Shiwen Cheng、Hao Dong 等 43 人

论文原文见 [arXiv](https://arxiv.org/abs/2609.11977)

深度分析原文见 [ArxivReview](https://www.arxivreview.com/papers/arxiv_2609.11977)

> 协同工作（Co-work）智能体需在长程任务中平衡执行能力与推理成本，但现有方法往往追求峰值性能而忽视累积延迟与费用。Occamy-1.0 指出，多数日常步骤依赖状态跟踪与工具恢复而非前沿推理，因此通过执行接地数据与双专家合并策略，在 35B 参数规模下实现了成本-性能帕累托前沿的低成本拐点。该方法验证了专用化训练对长程执行的有效性，但其对通用工具调用精度的潜在牺牲及合成环境与真实 API 的差距仍存疑。

## 研究背景

协同工作场景下的智能体执行面临上下文窗口限制与状态连续性的双重挑战。当任务跨越数十次模型调用时，执行框架（Harness）可能压缩或重写历史以适配上下文窗口，导致模型可见状态与实际环境状态脱节。这种脱节使得基于简单截断或摘要的传统方法难以维持长程决策的准确性，因为早期动作产生的文件写入或工具副作用在后续步骤中必须被精确追踪，而任何状态丢失都会引发错误累积。

现有 LLM 智能体研究多聚焦于提升单步推理能力或工具选择准确率，如 ReAct 范式确立了推理-行动循环，Toolformer 实现了工具调用格式的内化。然而，这些方法在长程协同任务中面临两个瓶颈：一是缺乏对多轮交互中状态连续性的精细控制，二是未将推理成本作为核心优化目标。主流强化学习（RL）方法如 Agent0 和 Tool-R0 虽解决了训练数据稀缺问题，但通常假设单一模型端到端训练，未考虑不同任务时长对模型能力的差异化需求。Occamy-1.0 的切入点在于，将协同工作定义为一种需要持续协调而非单一技能爆发的端到端工作负载，并通过分离长程与短程专家训练，再合并以平衡能力与成本。

## 核心方法

### 方法参照系

标准智能体后训练流程通常采用单一模型进行监督微调（SFT）与强化学习（RL），以最大化任务成功率。本文的关键差异在于，协同工作任务的时长分布呈双峰态，单一模型难以同时优化长程状态跟踪与短程工具调用效率，且长程任务中的历史重写机制要求轨迹捕获具备 Token 级精确性，而非仅依赖解码后的文本。

### Token-精确轨迹捕获与重放

传统方法在记录智能体轨迹时，常依赖解码后的文本日志，但解码与重新编码可能改变 Token ID，且聊天模板可能重新渲染早期消息，导致训练时无法精确复现策略采样时的上下文。Occamy-1.0 引入 Token-In-Token-Out (TiTO) 机制，通过 OpenAI 兼容代理记录每次策略调用的输入 Token ID、采样 Token ID 及对数概率。其核心不变式为：

$$ P_{t+1} = \text{Append}_h(P_t, Y_t, D_t) $$

其中 $P_t$ 为模型接收的精确 Token 前缀，$Y_t$ 为策略输出 Token，$D_t$ 为下一策略调用前引入的非策略内容（如工具结果）。该公式确保在 Token 级别而非解码文本级别维持状态连续性，使得训练时的重放能精确匹配推理时的上下文，解决了历史重写导致的轨迹保真度丢失问题。

### 双专家分离训练与模型合并

长程任务需要持续的状态跟踪，而短程任务侧重快速工具调用，单一模型在优化长程能力时可能牺牲短程效率。Occamy-1.0 训练两个专家：Marathon Expert 通过 SFT 后接分层解耦策略优化（HDPO）针对长程任务，Sprint Expert 通过 SFT 针对短程任务。两者共享架构与检查点谱系，通过均匀模型汤（Model Soup）合并：

$$ \theta_{merged} = \frac{1}{2}(\theta_{marathon} + \theta_{sprint}) $$

合并后的检查点无需推理时路由，参数数量与单个专家相同。随后应用单滚出异步优化（SAO）在协同工作混合任务上进一步精炼。这一设计解决了单一模型在长程与短程任务间的能力冲突，通过参数空间合并实现了能力的互补整合，而非简单的能力叠加。

## 实验评估

实验在 12 个基准上进行，覆盖协同工作、工具调用、编码与指令跟随。基线包括 Qwen3.6-35B-A3B（骨干）、GPT-5.6 Sol（前沿闭源）及 Nex-N2-mini（开源竞品）。在协同工作基准上，Occamy-1.0 表现领先同规模模型：

| 基准 | Occamy-1.0 | Qwen3.6-35B-A3B | Nex-N2-mini | GPT-5.6 Sol |
| :--- | :--- | :--- | :--- | :--- |
| Claw-Eval (avg) | 82.20 | 69.50 | 81.80 | 83.90 |
| WildClawBench | 49.16 | 40.40 | 67.20 | 54.42 |
| AutomationBench (Pass1) | 27.60 | 7.50 | 45.50 | 43.50 |
| BFCL v4 | 65.40 | 63.19 | 64.33 | 73.65 |

Occamy-1.0 在 Claw-Eval 上超越骨干 12.7 分，但在 WildClawBench 上低于 Nex-N2-mini 18.04 分，显示其在特定协同任务上的优势并非全面。在工具调用基准 BFCL v4 上，Occamy-1.0 仅比骨干高 2.21 分，且低于 GPT-5.6 Sol 8.25 分，表明协同工作训练未显著提升通用工具调用精度。

消融实验显示，模型合并后的检查点在 AutomationBench 上得分 29.0，高于 Marathon Expert 的 50.76 在 WildClawBench 上的表现，但低于 Sprint Expert 的 45.29。这表明合并策略在长程任务上保留了 Marathon Expert 的优势，但在短程任务上未完全继承 Sprint Expert 的能力。SAO 阶段将 Claw-Eval 从 79.2 提升至 82.2，WildClawBench 从 48.28 提升至 49.16，验证了最终 RL 阶段对协同执行能力的定向增强。

评估协议使用统一服务配置与隔离执行环境，但部分基准（如 GDPval）为复现结果。代码与权重已开源，超参数完整披露。局限在于，协同工作基准多为合成环境，与真实 API 行为的差距未量化；且未对比纯提示工程基线在相同协同任务上的表现，无法隔离 RL 训练的独立贡献。

## 关联研究分析

从问题动机看，Occamy-1.0 与 Tool-R0 均使用 RL 进行工具学习，但 Tool-R0 侧重零数据自进化，通过生成器-求解器协同解决训练数据稀缺问题，而 Occamy-1.0 侧重执行接地数据构建，通过可验证任务合同确保轨迹质量。这一差异源于任务特性：Tool-R0 面对的是工具调用格式的内化，而 Occamy-1.0 面对的是长程状态连续性，后者对轨迹保真度的要求远高于前者。从方法设计看，Occamy-1.0 与 MiroFlow 均关注长程鲁棒性，但 MiroFlow 通过分层架构解耦工作流编排与 Agent 行为，而 Occamy-1.0 通过双专家合并平衡长程与短程能力。MiroFlow 的架构复杂度更高，适合复杂研究任务，而 Occamy-1.0 的合并策略更轻量，适合成本敏感的日常协同工作。

## 总结

Occamy-1.0 旨在解决协同工作智能体中执行能力与推理成本的矛盾，通过执行接地数据与双专家合并策略，在 35B 参数规模下实现了成本-性能帕累托前沿的低成本拐点。其核心贡献在于 Token-精确轨迹捕获机制与 Marathon/Sprint 专家分离训练，证明了专用化训练对长程执行的有效性。实验显示，Occamy-1.0 在 Claw-Eval 上达到 82.20，超越骨干 12.7 分，但在 BFCL v4 上仅提升 2.21 分，表明协同工作训练未显著增强通用工具调用能力。其边界在于，合成环境与真实 API 的差距未量化，且双专家合并是否必然优于单一模型在长程任务上的直接 RL 训练，论文未给出回答。当支持集增大到 5-shot 时，查询侧增强的边际收益是否递减，论文未给出回答。
