> 自动形式化领域长期面临“生成易、维护难”的矛盾：大语言模型能快速产出 Lean 代码，但 Mathlib 等标准库因严格人工审查而线性增长，无法匹配 AI 生成速度，导致新形式化结果因依赖版本漂移而迅速失效。现有方案如 M2F 聚焦单项目生成，LeanAgent 侧重证明搜索，均缺乏对多项目长期兼容性的系统管理。本文提出 Lean Pool，一个由 AI 代理驱动维护的活档案，通过自动化依赖升级、编译优化与语义审查，将独立形式化项目整合为统一环境。其价值在于验证了 AI 代理在库级维护中的可行性，但缺乏外部基准对比，且 AI 维护决策的错误率未量化。

## 研究背景

交互式定理证明器 Lean 的核心理念是通过内核验证确保证明的绝对正确性，但这一机制要求代码与底层库版本严格同步。当 Mathlib 更新时，依赖旧版 API 的形式化项目往往出现编译失败，而人工修复成本高昂，导致大量已完成的形式化结果因版本漂移而废弃。这种“静态库”模式与 AI 快速生成新形式化的趋势形成冲突：OpenAI 等机构发布的 AI 数学成果虽附带 Lean 证明，但缺乏统一的维护机制，难以被后续研究复用。

自动形式化研究的主流路线聚焦于提升单句翻译准确率或证明搜索效率，如 DRIFT 通过分解-检索流水线处理复杂依赖，Aristotle 利用蒙特卡洛搜索实现竞赛级证明。然而，这些方法均假设形式化结果是一次性交付物，忽视了库级一致性与长期可维护性。当形式化项目数量增长至数百个时，跨项目依赖管理、版本兼容性与资源优化成为瓶颈，而现有框架未提供系统解决方案。Lean Pool 的切入点在于将形式化库视为“活档案”，引入 AI 代理作为主要维护者，通过自动化工作流处理依赖升级、编译优化与语义审查，而非仅依赖人工集成。

## 核心方法

### 方法参照系

传统数学库如 Mathlib 采用人工主导的静态维护模式，贡献者提交代码后由社区审查合并，版本更新需手动适配。本文问题与该通用流程的关键差异在于：面对 AI 生成代码的指数级增长，人工审查无法覆盖所有项目，且版本漂移导致的兼容性错误需自动化修复。

### AI 代理驱动的依赖升级与修复

依赖升级是库维护的核心环节，通常做法是人工检测 API 变更并修改代码。Lean Pool 引入自动化工作流：当 Lean/Mathlib 发布新版本时，AI 代理检测失败项目，生成修复补丁，并通过 CI 验证。该过程可形式化为：

$$
\text{Repair}(P_i, v_{new}) = \text{Agent}(\text{ErrorLog}(P_i, v_{new}))
$$

其中 $P_i$ 为项目，$v_{new}$ 为新版本，$\text{ErrorLog}$ 为编译错误日志。AI 代理根据错误类型（如 API 重命名、类型不匹配）生成最小化修复，确保项目在新环境下编译通过。这一设计解决了人工修复的延迟与不一致性问题，使库能随依赖版本同步演进。

### 编译优化与证明压缩

库规模增长导致编译时间与内存占用激增，传统做法是局部优化热点代码。Lean Pool 引入全局优化策略：AI 代理分析编译性能，执行证明压缩、战术简化与内存优化。优化效果可量化为：

$$
\Delta T = T_{before} - T_{after}, \quad \Delta M = M_{before} - M_{after}
$$

其中 $T$ 为编译时间，$M$ 为峰值内存。例如，库级压缩移除 45,217 行代码，编译时间从 16.11 分钟降至 15.59 分钟（+3.3%），内存从 26.1 GiB 降至 26.9 GiB（-2.7%）。这一设计解决了大规模库的资源瓶颈，使库在增长中保持可构建性。

## 实验评估

实验设置基于 Lean Pool 内部归档，包含 211 个已完成项目、3,228,485 行 Lean 代码，未使用 miniF2F 等外部基准。基线审计显示，本文未对比 M2F、LeanAgent 等现有框架，仅报告内部优化效果，缺乏外部参照系。

| 优化类型 | 移除行数 | 编译时间 (min) | 内存 (GiB) |
| :--- | :--- | :--- | :--- |
| 证明搜索简化 | 117 | 5.30 → 5.25 (+1.1%) | 15.6 → 15.6 |
| 库级压缩 | 45,217 | 16.11 → 15.59 (+3.3%) | 26.1 → 26.9 |
| 贡献者证明压缩 | 12,515 | 21.83 → 23.01 (-5.4%) | 25.9 → 24.6 |
| 证书简化 | 338 | 30.22 → 29.13 (+3.6%) | 21.0 → 20.9 |
| 阐述成本降低 | 54,965 | 28.46 → 26.82 (+5.8%) | 19.8 → 19.6 |

核心数字对比显示，库级压缩与阐述成本降低带来显著编译时间改善，但贡献者证明压缩导致编译时间增加 5.4%，揭示优化策略的条件依赖性：局部压缩可能增加全局编译开销。

消融分析表明，依赖升级修复的成功率未量化，仅记录历史升级事件。AI 代理的修复决策缺乏错误率评估，无法区分修复正确性与偶然编译通过。评估边界方面，本文未报告置信区间，且优化效果基于历史修订，未进行随机对照实验。可复现性上，代码与数据公开，但 AI 代理的具体模型与超参数未披露，限制了外部复现。

## 关联研究分析

从问题动机看，M2F 聚焦单项目形式化生成，通过迭代修复解决教科书级依赖，但缺乏多项目协调机制。Lean Pool 的切入点在于将维护视为持续过程，而非一次性生成，其 AI 代理驱动的升级工作流解决了 M2F 未处理的版本漂移问题。然而，M2F 的语义忠实性验证更严格，而 Lean Pool 依赖 LLM 审查，可能引入语义漂移风险。

从方法设计看，LeanAgent 利用 LLM 代理进行证明搜索，侧重单证明的优化，而 Lean Pool 将代理应用于库级维护，包括编译优化与依赖管理。两者均使用 AI 代理，但任务粒度不同：LeanAgent 的代理决策影响单证明，Lean Pool 的代理决策影响整个库的兼容性。这种差异源于任务特性：证明搜索是局部优化，库维护是全局协调。Lean Pool 未探索代理决策的错误传播机制，当修复错误时，可能影响依赖该项目的其他项目，这一风险未量化。

## 总结

Lean Pool 要解决的核心矛盾是 AI 快速生成形式化代码与人工维护库的线性增长之间的不匹配。其切入点在于将库视为活档案，引入 AI 代理自动化处理依赖升级、编译优化与语义审查，解决了人工维护的延迟与不一致性问题。本文通过内部归档验证了可行性，库级压缩移除 45,217 行代码，编译时间改善 3.3%。其边界在于缺乏外部基准对比，AI 代理的修复错误率未量化，且优化策略的条件依赖性（如贡献者压缩导致编译时间增加）未充分探索。当库规模增长至数千个项目时，AI 代理的修复决策是否会导致语义漂移的累积，论文未给出回答。
