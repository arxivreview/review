综述原文见 [ArxivReview](https://www.arxivreview.com/surveys/LLM-based%20Hardware%20Design%20and%20Verification)

## 导读

大语言模型（LLM）介入硬件设计，旨在缓解电子设计自动化（EDA）流程中人工编写代码与验证的高成本痛点，其核心价值在于将自然语言规范转化为可综合的寄存器传输级（RTL）代码。早期研究聚焦于领域特定微调，通过收集开源数据提升语法正确性，但受限于数据稀缺，模型在复杂时序逻辑上易产生功能幻觉。随着智能体（Agentic）工作流的引入，LLM 开始与仿真器、综合工具交互，通过“生成-执行-反馈”闭环修正错误，显著提升了代码可靠性。研究重心随后从单纯的功能正确性扩展至性能、功耗与面积（PPA）优化及形式化验证，以逼近工业级质量标准。各路线在数据规模、推理成本与验证深度之间做出了不同取舍，由此形成当前多元并存的方法格局。本综述梳理这条从静态生成到闭环智能体的因果演进链条，为读者提供一张领域认知地图。全文按问题演化与路线取舍组织，覆盖该领域从奠基到当前的主要工作。

## 1. 研究背景、问题结构与演进脉络

硬件设计自动化的核心矛盾，源于摩尔定律推动的芯片复杂度指数级增长与人工验证效率低下之间的失衡。在集成电路（IC）开发周期中，验证环节往往占据 70% 以上的时间，成为主要瓶颈。传统方法依赖专家经验编写硬件描述语言（HDL）代码与测试平台，不仅成本高昂，且难以应对日益复杂的系统级设计。LLM 的介入重塑了这一问题：它不再仅仅是代码补全工具，而是被期望成为能够理解设计意图、生成代码并自主调试的智能代理。这一转变的根本驱动力，在于利用 LLM 的推理能力解决传统启发式算法难以处理的复杂设计空间探索问题。

问题的形式化定义经历了从“代码翻译”到“约束下搜索”的演化。早期任务被简化为给定自然语言描述，生成符合语法且功能正确的 Verilog 代码，通常以 N-way K-shot 或零样本提示进行评估。然而，随着研究深入，问题定义扩展为在满足功能正确性、PPA 约束及安全要求的前提下，搜索最优的硬件实现。这一扩展引入了子问题间的强依赖关系：数据稀缺是基础瓶颈，制约了模型的基础生成能力；功能正确性是前提，若不解决幻觉问题，后续的 PPA 优化和安全检测均无意义；验证自动化与调试则是连接生成与优化的桥梁，提供关键的反馈信号。

在概念层面，寄存器传输级（RTL）是 LLM 生成代码的主要目标格式，其正确性直接决定电路功能。测试平台（Testbench）用于验证功能正确性，是评估生成质量的关键基础设施。断言基于验证（ABV）利用 SystemVerilog 断言（SVA）形式化描述预期行为，LLM 正被用于自动生成 SVA 以增强形式化验证能力。高层综合（HLS）将高级语言代码转换为 RTL，LLM 在此主要用于代码优化与设计空间探索（DSE）。这些概念构成了从输入到输出的因果链条，其中智能体工作流（Agentic Workflow）是解决语义鸿沟、实现闭环优化的核心机制。

约束条件的变化驱动了方法范式的演变。2016-2018 年，传统 EDA 工具主导设计流程，LLM 尚未介入。2023 年成为关键转折点，VeriGen 和 RTLCoder 等早期工作证明了通过领域特定微调，LLM 可以生成可综合的 Verilog 代码，标志着从“通用代码生成”向“硬件专用生成”的范式转变。这一阶段主要解决数据稀缺导致的泛化能力不足问题，确立了 VerilogEval 等基准。

2024-2025 年，研究重心从单纯的代码生成转向可靠性与自动化验证。VerilogEval 和 RTLLM 等基准的建立解决了评估标准缺失问题，而 Agentic AI 框架的引入使得 LLM 能够与仿真器、综合工具交互，实现闭环调试。CodeV-R1 等工作引入推理导向训练，ChIRAAG 引入检索增强生成（RAG），解决了静态微调在复杂模块生成中暴露的“功能幻觉”问题。这一阶段的核心约束是 LLM 缺乏对硬件执行状态的感知，无法自我纠错，因此引入了工具交互机制。

2025-2026 年，领域进入“智能体驱动”与“形式化验证融合”阶段。研究热点从功能正确性扩展至 PPA 优化、安全漏洞检测及 HLS 自动化。LLM4Cov、ChatHLS 等代表性工作标志着智能体闭环的成熟，通过执行感知强化学习与多智能体协作，解决了在线学习成本高与评估失真问题。当前形态下，LLM 正从辅助工具向自主设计代理演进，旨在实现硬件设计全流程的智能化与自动化。

**如果用一个核心问题概括该领域，那便是：如何克服硬件领域数据稀缺与语义复杂性的约束，通过构建 LLM 与 EDA 工具的闭环交互机制，实现从自然语言规范到具备工业级 PPA 质量、功能正确且安全可靠的硬件设计的端到端自动化生成与验证。**

## 2. 方法体系

- 2023：VeriGen——奠定领域基线，通过大规模开源数据微调提升 Verilog 生成质量

- 2024：AutoBench——开创 LLM 辅助硬件验证新范式，解决缺乏黄金参考时的验证难题

- 2025：CodeV-R1——引入推理导向训练，标志从代码补全向推理增强生成的转变

- 2025：ChIRAAG——利用 RAG 技术从自然语言规范自动生成 SVA，推动断言生成语义化

- 2026：LLM4Cov——提出执行感知智能体学习框架，实现高覆盖率测试平台高效生成

- 2026：ChatHLS——构建 HLS 双阶段工作流，解决代码错误修正与性能优化耦合难题

- 2026：ChipBench——构建涵盖生成、调试及参考模型生成的综合基准，引入工业级复杂度评估

这条时间线勾勒了该领域方法演进的代表性节点：从 2023 年的 VeriGen 奠定该领域方法基线，经 2024 年 AutoBench 的推进，到 2026 年的 LLM4Cov 代表当前前沿。各节点对应的技术路线、取舍与关联，详见后续小节。

### 2.1 RTL 代码生成

RTL 代码生成是 LLM 硬件应用的基础，其演进反映了从“依赖模型参数记忆”向“依赖工具反馈与搜索”的取舍。早期工作如 VeriGen 和 RTLCoder 基于“领域特定微调可弥补数据稀缺”的假设，通过收集开源 Verilog 数据并引入注释进行微调，建立了首个广泛采用的基准与模型基线。这一路线放弃了通用模型的灵活性，换取了对 HDL 语法的初步掌握，但在复杂时序逻辑上仍易产生功能幻觉。

为解决静态微调的语义对齐难题，QiMeng-CRUX（Huang et al., 2025, P7）引入了核心精炼理解表达（CRUX）作为中间表示。该方法通过两阶段训练框架，显式捕获核心设计意图并将自由描述重构为领域对齐的结构形式，牺牲了训练阶段的复杂性，换取了生成代码的结构正确性与功能完整性。与此同时，CorrectHDL（Xu et al., 2025, P5）提出利用高层综合（HLS）作为参考的智能体框架，通过对比 LLM 生成的 HDL 与 HLS 生成的参考 HDL 进行修正，引入了功能增强步骤，以解决 LLM 生成代码可能存在的功能缺失或低效问题。

随着对可靠性要求的提高，EvolVE（Hsin et al., 2026, P14）将 HDL 生成视为状态空间探索，利用进化算子迭代生成、评估和选择 RTL 设计变体。该方法从学习中心范式转向搜索中心范式，利用测试时计算提升性能，无需大规模重新训练即可实现 PPA 优化，但增加了推理时间。此外，Stepwise Refinement（Li et al., 2026, P36）采用自顶向下的细化策略，利用细化计算提供预定义的细化规则，确保最终代码在构造上是正确的，牺牲生成速度换取形式化的正确性保证。

| 方法路线 | 代表方法 | 核心机制 | 放弃的假设 | 换取的收益 | 典型应用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 静态微调 | VeriGen, RTLCoder | 领域特定数据微调 | 通用模型灵活性 | 基础语法正确性 | 简单模块生成 |
| 中间表示 | QiMeng-CRUX | CRUX 结构对齐 | 训练复杂度 | 语义对齐与结构正确性 | 复杂规范理解 |
| 参考引导 | CorrectHDL | HLS 参考对比 | 流程复杂度 | 功能正确性与效率 | 算法到硬件转换 |
| 进化搜索 | EvolVE | 状态空间探索 | 推理时间 | PPA 优化与数据鲁棒性 | 数据受限场景优化 |
| 形式化细化 | Stepwise Refinement | 逐步细化规则 | 生成速度 | 形式化正确性保证 | 高可靠性设计 |

RTL 生成路线与验证自动化路线存在互补关系：生成提供初始代码，验证提供反馈信号以修正错误，两者共同构成闭环系统的基础。

### 2.2 硬件验证自动化

验证自动化旨在解决手动编写测试平台耗时巨大、覆盖率不足的问题。早期工作 AutoBench 提出了无需可信参考模型的开放式测试平台生成方法，通过 LLM 合成激励和银色参考预言机，开创了 LLM 辅助硬件验证的新范式，尽管存在 DUT 与预言机同源导致的歧义问题。

CD-DPO（Nadimi et al., 2025, P4）提出覆盖率驱动的偏好优化方法，构建包含高质量和低质量测试平台配对的偏好数据集，利用覆盖率指标作为反馈信号进行直接偏好优化。该方法将量化覆盖率反馈融入 DPO 训练过程，使模型学习生成能最大化覆盖率的激励，相比传统 SFT 更有效地利用执行反馈。GRPO-StateMutations（Kochar et al., 2026, P13）结合状态突变的组相对策略优化（GRPO），将测试计划生成分解为两阶段，通过引入状态突变机制增强模型在复杂决策任务中的推理能力，缓解 SFT 在长序列推理中的失效模式。

LLM4Cov（Zhang et al., 2026, P18）提出执行感知的智能体学习框架，将昂贵的模拟器反馈转化为稳定的离线监督信号，通过分阶段 SFT 和强化学习训练验证智能体，解决了在线学习成本高且执行轨迹稀疏的问题。CHORUS（Zhang et al., 2026, P38）采用互补专家框架，通过模型汤或多教师在线策略蒸馏合并多个专家模型，利用执行引导的 RL 联合训练直接生成和智能体细化两种模式，显著提升了紧凑领域特定模型的能力上限。

UCAgent（Wang et al., 2026, P24）提出端到端智能体用于块级功能验证，在纯 Python 环境中运行，利用 Picker 将 DUT 转换为 Python 包，借助 Toffee 提供高层验证抽象。该方法绕过 SystemVerilog 数据稀缺瓶颈，利用 LLM 在 Python 上的强生成能力完成验证任务，虽然限制了在原生 SV 环境中的应用，但显著提升了验证代码的生成质量和效率。

验证自动化路线与形式化断言生成路线存在竞争与互补：前者侧重动态仿真覆盖率，后者侧重静态属性证明，两者结合可提升验证的完备性。

### 2.3 形式化断言生成

形式化断言生成旨在自动从设计规范或 RTL 代码中生成 SystemVerilog 断言（SVA），以弥补仿真验证的覆盖率不足。ChIRAAG 利用 GPT-4 结合检索增强生成技术，从自然语言规范中自动化生成 SVA，突破了传统静态分析在大规模设计中的扩展性瓶颈。

STELLAR（Rajabi et al., 2025, P15）提出结构引导的 LLM 断言检索与生成框架，通过结构指纹、检索过程、结构感知提示和 SVA 生成四个阶段，从 RTL 中检索结构匹配的模块并指导 LLM 生成断言。该方法将 RTL 模块分解为 always 块或 FSM 单元，保留局部上下文，实现大规模设计的可扩展断言生成。ChatSVA（Fu et al., 2026, P25）采用长链推理分解策略，将单体任务分解为模块化子任务管道，并合成少量样本数据进行少样本学习，通过中间推理步骤增强功能意图理解，显著提升了功能通过率。

FVRuleLearner（Wan et al., 2026, P26）提出基于操作符级推理树（OP-Tree）的规则学习框架，通过训练阶段从失败案例中蒸馏高保真推理轨迹，并在测试阶段利用混合检索机制强制结构对齐，将生成范式从单体文本翻译转向显式操作符级推理。Agentic Coverage Closure（Pothireddypalli et al., 2026, P19）利用多智能体系统（MAS）处理复杂任务，通过任务调度、分配和反馈机制确保全面覆盖，结合智能体工作流与形式化验证原理，自动化覆盖率闭合过程。

形式化断言生成路线为 RTL 生成提供了安全护栏，其生成的断言可用于验证生成代码的正确性，两者共同构成“生成-验证”闭环的关键环节。

### 2.4 性能优化与综合

性能优化与综合关注 PPA（性能、功耗、面积）优化及高层综合（HLS）指令调优，旨在生成符合工业级质量标准的硬件实现。Bench4HLS（Khan et al., 2026, P16）提出端到端评估 LLM 在 HLS 代码生成中能力的基准，利用 Vitis HLS 进行综合和评估，不仅评估语法和语义正确性，还评估硬件级指标如 PPA。

Alpha-RTL（Zhou et al., 2026, P32）提出基于测试时训练（TTT）的 RTL 硬件优化方法，利用 PUCT 引导的状态采样和强化学习，在推理时更新模型参数以最小化目标指标。该方法将 HDL 生成视为状态空间探索，利用测试时计算提升 PPA 性能，无需重新训练即可实现优化。POET（Ping et al., 2026, P23）提出功耗导向的进化调优方法，包含基于差分测试的测试平台生成流水线和功耗导向的进化优化引擎，通过迭代生成、评估和选择 RTL 变体实现优化，利用进化算子嵌入领域特定优化技术。

MPM-LLM4DSE（Xu et al., 2026, P12）结合多模态学习和 LLM 驱动探索，利用 GNN 提取代码图表示，结合 LLM 提取文本表示，形成多模态嵌入以预测 QoR，显著提升了设计空间探索的效率。ChatHLS（2026, P41）构建包含 HLS-C 生成和调试的双阶段工作流，利用多智能体协作处理代码错误并迭代优化 QoR，解决了 HLS 设计中代码错误修正与性能优化耦合的难题。HLS-Seek（Zou et al., 2026, P31）提出基于代理比较奖励强化学习的 QoR 感知代码生成方法，利用不确定性感知的代理奖励指导 LLM 生成 HLS 代码，平衡功能正确性与 QoR 优化。

性能优化路线依赖于前序路线提供的功能正确代码基座，其目标是在满足功能约束的前提下，通过搜索与优化实现物理实现层面的最优解，是 LLM 硬件应用的最终目标之一。

### 2.5 跨任务与多领域应用

除核心生成与验证任务外，LLM 在基准测试、安全检测及调试修复等领域也展现出应用潜力。NotSoTiny（Ghorab et al., 2025, P11）提出大型、活的 RTL 代码生成基准，利用基于等价检查的功能评估流水线，应用 Yosys 等开源工具进行可复现评估，解决了现有基准规模小、复杂度低的问题。ChipBench（Yu et al., 2026, P17）涵盖代码生成、调试和参考模型生成，引入工业级复杂度的测试用例，弥补了现有基准忽略调试和参考模型生成的缺陷。

SecureRAG-RTL（Hasan et al., 2026, P20）提出检索增强、多智能体、零样本 LLM 驱动框架用于硬件漏洞检测，利用 CWE 知识库进行语义相似性检索，并迭代评估 RTL 设计以识别漏洞。VeriCWEty（Basu Roy et al., 2026, P28）提出嵌入启用的行级 CWE 检测框架，利用嵌入技术捕捉代码语义，结合静态分析和 LLM 进行行级漏洞检测，提升了检测的粒度。

DUET（Smith et al., 2025, P10）提出通过实验和测试进行智能体设计理解的框架，利用 LLM 智能体调用工具进行迭代查询，执行计算和运行工具，通过实验反馈增强智能体对设计的理解。GROVE（Bai and Ren, 2025, P6）提出 LLM 组织知识树用于解决 RTL 断言失败的方法，将断言失败调试建模为两阶段学习和推理任务，通过蒸馏可复用调试知识并构建知识树，提升调试的可复用性。RefEvo（Zhang et al., 2026, P29）提出具有协同进化验证的智能体设计框架，通过多智能体协作生成并验证 SystemC 模型，引入辩证仲裁者监督模型生成器和验证器的协同进化，提升模型质量。

这些跨任务应用体现了 LLM 在硬件设计全流程中的渗透，从单一代码生成扩展至系统级评估、安全分析与自动化调试，反映了领域向综合智能体系统的演进趋势。

## 3. 关键共识、分歧与开放问题

### 3.1 领域共识

领域内已形成“Agentic Workflow 优于静态生成”的共识，证据表明，通过与 EDA 工具交互实现闭环优化，能显著提升复杂硬件任务的解决能力与鲁棒性。例如，LLM4Cov 通过执行感知强化学习，将昂贵的模拟器反馈转化为稳定的离线监督信号，解决了在线学习成本高且执行轨迹稀疏的问题，实现了高覆盖率测试平台的高效生成（支撑证据：P18、P38）。与此相关的另一个共识是，功能正确性仅是基础，基于 PPA 的优化及设计空间探索已成为 LLM 硬件研究的重要前沿。POET 在 RTL-OPT 上实现 100% 功能正确性，Alpha-RTL 通过测试时训练提升 PPA 性能，均表明研究重心正从单纯的功能正确性向工业级质量标准扩展（支撑证据：P23、P32）。

### 3.2 观点分歧

数据策略上存在“大规模微调”与“小样本+推理/RAG”的分歧。VeriGen/RTLCoder 主张通过收集大规模开源数据并微调，内化硬件领域知识，提升通用生成能力；而 CodeV-R1/ChIRAAG 主张通过推理链增强、RAG 检索及中间表示对齐，提升模型在特定任务上的语义理解与可靠性。现有证据偏向后者在复杂任务（如 ChipBench, HWE-Bench）上的表现更优，因为微调模型在长上下文与复杂交互中易出现幻觉，但前者在简单模块生成上仍具有效率优势。这一分歧的背后，是另一个更根本的争论：验证机制的选择。仿真反馈派（LLM4Cov/CHORUS）认为仿真器反馈真实且低成本，通过执行轨迹进行强化学习可高效提升覆盖率；形式化验证派（ChatSVA/HierSVA）认为仿真存在覆盖率不足问题，形式化验证能证明设计满足属性，提供更强的正确性保证。证据显示两者互补而非替代，仿真反馈在提升代码覆盖率上更有效，而形式化验证在捕捉深层逻辑错误上更可靠，但缺乏统一的、包含 PPA 与安全指标的大型抗污染基准，导致不同方法在特定场景下的优劣难以直接比较。

### 3.3 其他开放问题

最紧迫的工程问题是 LLM 推理成本与延迟高，实时硬件设计流程对响应速度要求高，大模型推理开销大。当前研究通过模型蒸馏、小模型专用化、多模型调度及测试时训练（TTT）来优化推理效率，但尚未形成标准化解决方案。最根本的研究问题是长上下文与复杂层次化设计的处理瓶颈，大型 SoC 设计涉及多模块交互，超出 LLM 上下文窗口，当前研究通过层次化中间表示（IR）、模块分解及检索增强技术来管理复杂设计的全局语义，但缺乏统一的理论框架。此外，硬件安全漏洞检测难度大，HDL 的并发语义与软件不同，传统静态分析工具误报率高，LLM 缺乏对硬件安全上下文的深度理解，需通过构建 CWE 知识库、多智能体推理及图结构表示来增强漏洞检测能力。

已知—争议—未知认知图谱显示：已知 Agentic Workflow 与 PPA 优化是提升设计质量的关键路径；争议在于数据策略与验证机制的最优组合；未知在于长上下文语义理解与系统级自主设计的理论边界。未来趋势将向系统级硬件设计助手、集成形式验证与仿真反馈的闭环优化、以及自动化硬件安全分析方向演进。

## 4. 总结与展望

LLM 驱动硬件设计已从概念验证进入工程落地前夜，其核心价值在于通过智能体闭环与形式化约束，将硬件设计从“专家经验驱动”转变为“数据与推理驱动”。当前矛盾在于数据稀缺与语义复杂性制约了模型的基础生成能力，而功能幻觉与验证成本阻碍了工业级质量的实现。尝试过的路线包括静态微调、中间表示对齐、进化搜索、执行感知强化学习及形式化断言生成，核心瓶颈在于缺乏统一的、包含 PPA 与安全指标的大型抗污染基准，导致不同方法在特定场景下的优劣难以直接比较，且长上下文与复杂层次化设计的处理仍面临理论挑战。

未来可能突破的方向包括：从实验原型向鲁棒的系统级硬件设计助手过渡，通过多智能体协作和层次化中间表示分解复杂任务并提升可扩展性；集成形式验证与仿真反馈的闭环优化，利用确定性工具反馈指导 LLM 进行迭代修正，确保生成代码的功能正确性和安全性；提升 PPA 优化能力，结合进化算法、强化学习或代理奖励模型，在保持功能正确的前提下探索设计空间，实现接近或超越人工设计的硬件效率。对进入者最值得做的一件事，是构建统一的、包含 PPA 与安全指标的大型抗污染基准，以真实反映 LLM 在硬件设计中的能力，并推动不同方法在公平条件下的比较。
