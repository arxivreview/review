# A Survey of LLM Code Evaluation and Benchmarking ｜LLM代码评估与基准测试综述 ｜arxivreview

综述原文见 [ArxivReview](https://www.arxivreview.com/surveys/LLM%20Code%20Evaluation%20and%20Benchmarking)

## 导读

大语言模型（LLM）在代码生成任务上的能力跃升，迫使评估体系从静态快照向动态生态重构。早期研究以功能正确性为核心，通过HumanEval等基准量化模型生成代码的通过率，思路简洁却受制于数据污染与任务简化。当SOTA模型在静态基准上接近满分后，研究者转向仓库级软件工程与动态更新基准，用真实GitHub Issue和时间维度换取评估的抗污染能力与工程真实性。随后，评估维度从单一正确性扩展至安全性、推理忠实度及多语言泛化，各路线在评估成本、覆盖广度与指标深度之间做出了不同取舍。由此形成当前涵盖静态分析、动态执行、人类偏好对齐及内部机制解释的综合评估格局。全文按问题演化与路线取舍组织，覆盖该领域从奠基到当前的主要工作。

## 1. 研究背景、问题结构与演进脉络

LLM代码评估领域的兴起，源于大语言模型在代码生成任务上展现出的惊人能力，以及随之而来的对代码质量、安全性和可靠性的迫切需求。早期研究主要关注功能正确性，以HumanEval和MBPP等静态基准为代表，其核心假设是代码质量等同于通过单元测试的能力，且评估数据与训练数据严格隔离。这种假设在模型能力尚弱时是合理的，但随着模型规模的扩大，静态基准迅速暴露出数据污染和任务过于简单的问题，导致评估失效。

问题定义因此经历了从“生成正确代码”到“在真实约束下解决工程问题”的深刻演化。2021年至2023年间，功能正确性（Pass@k）被确立为金标准，但静态基准的饱和迫使研究者重新审视评估的有效性。2024年成为范式转移的分水岭，SWE-bench的提出将评估重心从单函数生成推向仓库级软件工程，强调解决真实GitHub Issue的能力，标志着评估向复杂上下文和代理式（Agentic）工作流的转移。随后，LiveCodeBench等动态基准的出现解决了静态数据集的饱和与污染问题，引入了时间维度的持续评估。

子问题之间存在强依赖关系：数据污染问题若不解决，功能正确性评估即失去意义；功能正确性是基础，但无法独立支撑对安全性、可维护性和推理能力的评估；仓库级上下文理解是解决复杂工程任务的前提，但依赖于长上下文处理和多轮交互能力。2025至2026年，领域进入精细化与多维化阶段，研究重心从单一的Pass@k指标转向代码安全性、可维护性、多语言泛化能力以及推理过程的忠实度。当前，领域活跃度极高，不仅关注“代码是否正确”，更关注“代码是否安全”、“是否可维护”以及“模型是否真正理解代码逻辑”。

**如果用一个核心问题概括该领域，那便是：如何在动态演进、存在数据污染风险且充满非功能约束的真实软件工程环境中，构建能够区分LLM“记忆/模式匹配”与“深层逻辑推理/代理执行”能力的可信评估体系？**

## 2. 方法体系

- 2021：APPS——奠定该领域方法基线

- 2024：LiveCodeBench——动态基准推进

- 2024：SWE-bench——仓库级评估转折

- 2025：CoRE——细粒度代码推理

- 2025：TREAT——可信度与可靠性评估

- 2026：AutoCodeBench——自动化基准生成

- 2026：SWE-Compass——统一代理编码评估

- 2026：Gistify——代码库级执行理解

这条时间线勾勒了该领域方法演进的代表性节点：从 2021 年的 APPS 奠定该领域方法基线，经 2024 年 LiveCodeBench 的推进，到 2026 年的 SWE-Compass 代表当前前沿。各节点对应的技术路线、取舍与关联，详见后续小节。

### 2.1 通用代码生成基准

通用代码生成基准的演进始于对算法题和竞赛题的静态收集，早期工作如APPS（Hendrycks et al., 2021）通过聚合竞赛和面试风格的问题，扩展了代码生成评估的规模和难度，但其静态数据面临数据污染的风险。随着SOTA模型在HumanEval上接近满分，研究者转向动态生成或防污染基准。AutoCodeBench（Tencent Hunyuan, 2026, P31）提出了一种利用LLM自动生成代码基准的框架，通过多阶段流水线生成任务描述、参考解决方案和单元测试，并引入自动化的难度控制和多语言支持机制。该方法放弃了部分人工精心设计的边缘案例，转而依赖LLM生成的广泛场景，这可能导致某些特定领域任务的缺失，但极大地提升了基准的规模和多样性，实现了基准的持续更新和规模化。

Multi-LCB（Ivanova et al., 2026, P26）将LiveCodeBench扩展至12种编程语言，旨在评估LLM在相同编程问题上的多语言代码生成能力。该方法通过保留原始LiveCodeBench的任务定义，并为每种语言生成对应的提示和测试用例，实现了跨语言的直接比较，揭示了模型在不同编程语言间的性能差异，特别是静态类型语言或低资源语言上的显著退化现象。其代价是引入了多语言处理的复杂性，如语言特定的库依赖和编译环境配置，但这更贴近真实开发场景。CodeGolf Bench（Padwal, 2026, P25）则基于code.golf平台构建，引入了代码简洁性作为评估维度，反映了物联网等资源受限场景下的实际需求，放弃了传统基准对代码可读性的关注，转而强调代码的紧凑性。

### 2.2 仓库级软件工程评估

仓库级软件工程评估的兴起源于单函数任务无法反映LLM在复杂代码库中的导航、调试和集成能力。SWE-bench（Jimenez et al., 2024）将评估粒度从函数级提升到仓库级，引入了多文件上下文理解和跨文件依赖推理的需求，成为评估LLM代理在真实软件工程任务中表现的金标准。SWE-Bench++（Wang et al., 2025, P13）提出了一种从开源仓库可扩展生成软件工程基准的框架，通过自动化流程从3971个仓库中构建11133个仓库级实例，并引入了提示注入算法，将SOTA模型失败的实例转化为可执行训练轨迹。其代价是依赖于开源仓库的可用性和多样性，可能存在数据偏差，但极大地提升了基准的规模和覆盖范围。

SWE-Compass（Xu et al., 2025, P9）提出了一种统一的代理编码能力评估基准，覆盖10种编程场景和10种编程语言，基于真实开发者交互数据构建，每个实例都配备可执行环境和可复现测试。该方法放弃了单一任务评估的简洁性，引入了多场景和多语言的复杂性，但更贴近真实开发工作流。Gistify（Shang et al., 2026, P29）则提出了一种基于运行时执行的代码库级理解基准，要求LLM通过执行代码来验证其对整个代码库的理解，揭示了现有仓库级基准可通过启发式捷径解决的问题，强调了完整执行推理的重要性。ReCUBE（Hong et al., 2026, P22）进一步引入了上下文利用的细粒度评估，不仅关注最终代码的正确性，还关注模型如何调用和整合仓库中的现有代码。

### 2.3 代码质量与非功能评估

代码质量与非功能评估的兴起源于功能正确性与非功能质量脱节的问题，现有评估过度依赖Pass@k，忽视了代码的安全性、可维护性和效率。TREAT（Gao et al., 2025, P5）提出了一种代码LLM可信度与可靠性评估框架，涵盖通用编码任务、多模态任务和鲁棒性评估，系统性地量化了LLM在不同编程场景下的性能波动和专业化程度。PACIFIC（Dreyfuss et al., 2025, P11）提出了一种精确自动检查指令遵循基准生成框架，通过生成确定性的指令遵循任务，并使用规则基于的指标进行评估，确保了评估的快速、可复现和无歧义，解决了现有代码指令遵循基准依赖复杂评估方法的问题。

Investigating The Smells of LLM Generated Code（Ghosh Paul et al., 2025, P2）提出了一种基于代码异味检测的LLM生成代码质量评估方法，利用代码异味检测技术，识别LLM生成代码中的维护、演化和重用问题。Operational Robustness of LLMs on Code Generation（Ghosh Paul et al., 2026, P21）则区分了对抗性鲁棒性和操作性鲁棒性，提供了更细粒度的鲁棒性评估视角。Social Bias in LLM-Generated Code（Rabbi et al., 2026, P24）将社会偏见引入代码生成评估，关注代码输出对人类的潜在影响，提出了基于多智能体软件过程模型的缓解策略。

### 2.4 代码推理与执行理解

代码推理与执行理解的兴起源于LLM生成的代码可能正确但推理过程错误（幻觉），现有黑盒评估无法区分“幸运猜对”与“真正理解”。CoRE（Xie et al., 2026, P27）提出了一种细粒度代码推理基准，通过构建功能等价但结构不同的代码实现，并设计中间状态探针来评估LLM的执行模拟能力，揭示了LLM在代码推理过程中可能存在的幻觉和浅层启发式问题。Beyond Output Correctness（Li et al., 2026, P23）通过收集带有推理标注的编码任务数据集，评估模型在生成、摘要和分类三种输出模态下的推理能力，揭示了正确输出可能源于错误推理，反之亦然的现象。

Can LLMs Compress (and Decompress)?（Maveli et al., 2026, P17）提出了一种通过可逆性评估LLM代码理解和执行能力的方法，设计了四步往返程序，评估模型在代码压缩和解压缩任务中的表现。On LLMs' Internal Representation of Code Correctness（Ribeiro et al., 2025, P10）利用表示工程（RepE）技术，分析LLM隐藏状态中与代码正确性相关的模式，探索如何通过内部表示评估生成代码的正确性，推动了代码生成研究对模型内部表示的关注。

### 2.5 特定领域与场景基准

特定领域与场景基准的兴起源于通用基准无法覆盖硬件描述、科学计算、Web前端等垂直领域的实际需求。MHRC-Bench（Zou et al., 2026, P16）提出了一种多语言硬件仓库级代码补全基准，针对Verilog、VHDL等硬件描述语言，填补了现有基准在硬件导向代码补全场景中的空白。CodeClash（Yang et al., 2025, P7）提出了一种目标导向的软件工程基准，设计了6个代码竞技场，要求模型分解高层目标为可操作子任务，并通过代码实现竞争结果，关注代码在实际业务场景中的效用。

FeatBench（Chen et al., 2025, P1）提出了一种更真实的特征级代码生成评估基准，从真实软件项目中提取特征实现任务，要求模型理解目标仓库并生成满足需求的代码变更。CrossPL（ICLR 2026, P30）系统评估LLM跨编程语言互操作代码生成能力，从多语言仓库中挖掘互操作模式，构建了跨语言互操作（IPC）和外部函数接口（FFI）两类任务。AICD Bench（Orel et al., 2026, P19）则关注AI生成代码检测，评估模型区分人类编写代码和LLM生成代码的能力，贴近学术诚信和代码安全中的实际需求。

### 2.6 评估方法论与可靠性

评估方法论与可靠性的兴起源于LLM-as-a-Judge存在位置偏差、自我偏好和过度纠正问题，导致评估结果不稳定。BigCodeArena（Zhuo et al., 2025, P4）提出了一种基于执行的人类偏好评估平台，通过展示两个匿名LLM响应及其代码执行结果，让用户基于可观察行为进行判断，将评估从静态文本比较转向动态功能验证。HardTestGen（ICLR 2026, P28）提出了一种高质量RL验证器生成管道，用于算法编码问题的测试用例自动合成，解决了RL训练中验证器稀缺和覆盖不足的问题。

Designing Empirical Studies on LLM-Based Code Generation（Nascimento et al., 2025, P3）提出了一种设计LLM代码生成实证研究的参考框架，组织了评估的核心组件，包括实验目标、任务定义、指标选择和报告标准。Towards Comprehensive Benchmarking Infrastructure（Rodriguez-Cardenas et al., 2026, P18）提出了一种全面的LLM软件工程基准基础设施，包括自动化基准生成、语义去重、RL驱动机制和社区协调平台。Beyond Blind Spots（Fandina et al., 2025, P12）提出了一种通过解析提示缓解LLM评估盲点的方法，引导LLM关注代码的关键特征和潜在问题，减少评估中的偏差和错误。

## 3. 关键共识、分歧与开放问题

### 3.1 领域共识

传统静态基准（如HumanEval）已无法有效区分SOTA模型的能力，且存在严重的数据污染问题，必须转向动态、仓库级或防污染基准。这一共识在多个基准上被反复验证：LiveCodeBench上OpenAI o3的67.60%与CodeContests上的67.60%均大幅超越静态基准上的表现，而SWE-Bench++上Claude Sonnet 4.5的36.20%则远低于静态基准，表明动态和仓库级基准更能反映模型的真实能力。与此相关的另一个共识是，功能正确性（Pass@k）是必要但不充分的指标，必须结合安全性、可维护性、指令遵循等非功能属性进行综合评估。TREAT和PACIFIC等框架的提出，正是为了弥补单一Pass@k在评估代码质量和可靠性方面的不足。

### 3.2 观点分歧

LLM-as-a-Judge与确定性规则评估的可靠性之争是领域内的核心分歧。BigCodeArena（Zhuo et al., 2025, P4）主张通过执行结果提高人类偏好数据的可靠性，而PACIFIC（Dreyfuss et al., 2025, P11）则强调确定性规则评估的无歧义和可复现性。现有证据偏向混合使用：LLM Judge在开放域任务上表现更好，但存在位置偏差和自我偏好；规则评估在指令遵循上更可靠，但缺乏灵活性。这一分歧的背后，是代码质量本身的多维性和主观性，缺乏统一的“黄金标准”来裁决两种方法的优劣。

动态基准的必要性 vs. 评估成本与标准化是另一个关键分歧。LiveCodeBench等动态基准虽防污染，但构建和维护成本高，且不同时间点的题目难度不一，导致跨时间比较困难。SWE-bench等标准化基准虽静态但更稳定，却面临数据污染和饱和问题。现有证据偏向动态基准，因为静态基准的污染问题已被广泛证实，但动态基准的标准化程度较低，缺乏统一的动态基准更新协议。

### 3.3 其他开放问题

最紧迫的工程问题是自动化基准生成与更新。AutoCodeBench（Tencent Hunyuan, 2026, P31）和SWE-Bench++（Wang et al., 2025, P13）已提供了自动化生成框架，但需进一步优化以解决LLM生成任务的偏差和边缘案例缺失问题。最根本的研究问题是代码推理与执行语义对齐。CoRE（Xie et al., 2026, P27）和Gistify（Shang et al., 2026, P29）揭示了模型推理过程中的幻觉和浅层启发式，但缺乏统一的理论框架来解释模型内部代码表征。低资源编程语言支持是主要认知盲区，Multi-LCB（Ivanova et al., 2026, P26）揭示了模型在低资源语言上的显著退化，但缺乏语言无关的训练管道和评估基准。

已知—争议—未知认知图谱显示：静态基准失效和功能正确性不充分是已知共识；LLM Judge vs. 规则评估和动态基准 vs. 标准化基准是核心争议；代码推理忠实度、内部机制解释和低资源语言泛化是主要未知领域。未来趋势将向动态、仓库级、多维度的评估生态演进，核心问题是如何在真实约束下量化模型的代理能力、推理忠实度和非功能质量，同时解决评估本身的可靠性与成本问题。

## 4. 总结与展望

LLM代码评估领域的核心矛盾在于模型能力的快速迭代与静态评估基准的滞后性。早期研究通过HumanEval等静态基准量化功能正确性，但数据污染和任务简化导致评估失效。随后，研究者转向仓库级软件工程（SWE-bench）和动态基准（LiveCodeBench），用真实GitHub Issue和时间维度换取评估的抗污染能力与工程真实性。当前，评估维度从单一正确性扩展至安全性、推理忠实度及多语言泛化，各路线在评估成本、覆盖广度与指标深度之间做出了不同取舍。核心瓶颈在于如何在动态演进、存在数据污染风险且充满非功能约束的真实软件工程环境中，构建能够区分LLM“记忆/模式匹配”与“深层逻辑推理/代理执行”能力的可信评估体系。

未来可能突破的方向包括：自动化基准生成与更新（AutoCodeBench, SWE-Bench++），通过LLM自动生成和持续更新基准，解决静态基准的饱和和污染问题；代码推理与执行语义对齐（CoRE, Gistify），通过中间状态探针和运行时执行验证，揭示模型推理过程的忠实度和内部机制；多语言代码生成与评估（Multi-LCB, CrossPL），通过跨语言互操作和语言无关的训练管道，缩小语言间性能差距。对进入者最值得做的一件事是，在统一骨干与统一预训练条件下，重评测代表性方法在动态和仓库级基准上的表现，以明确区分模型架构优势与预训练数据规模优势，为评估体系的标准化提供实证基础。
