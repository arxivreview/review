## 导读

大语言模型（LLM）驱动的软件工程正经历从单点代码补全向多智能体协作及工程治理的范式跃迁，其核心张力在于模型输出的非确定性与传统工程对确定性、可追溯性的刚性需求。早期研究聚焦函数级生成，验证了自然语言到代码转换的可行性，但受限于上下文窗口与架构理解，难以应对复杂系统。随着棕地悖论的显现，即遗留系统中审查修复成本抵消生成速度优势，研究重心转向可控性与治理。当前方法在生成灵活性、适应效率与工程可靠性之间做出不同取舍，形成从自由生成到规格驱动再到外部化推理的多元格局。本综述梳理这条从能力验证到治理重构的因果演进链条，为读者提供一张领域认知地图。全文按问题演化与路线取舍组织，覆盖该领域从奠基到当前的主要工作。

## 1. 研究背景、问题结构与演进脉络

LLM 驱动软件工程领域的兴起，根植于大语言模型在代码理解与生成能力上的突破，旨在通过自然语言交互实现软件开发的自动化。早期研究以函数级代码补全为核心，如 Codex 在 HumanEval 基准上的表现，确立了 LLM 在孤立任务上的可行性，但问题边界局限于绿地（Greenfield）场景下的单一函数或短片段生成。这一阶段的核心假设是 LLM 具备足够的代码理解能力，可直接从自然语言描述生成正确代码，忽略了真实开发环境中上下文依赖与架构约束的复杂性。

随着 GitHub Copilot 等 IDE 集成工具的普及，问题定义从“代码补全”转向“结对编程”，边界扩展至实时交互与开发者体验。然而，2023-2024 年 MetaGPT、ChatDev 等多智能体框架的出现，标志着范式从“单点辅助”向“多智能体协作”的跃迁，试图通过模拟人类团队角色分工解决复杂系统构建问题。这一转变的核心动机是单轮 LLM 在处理多文件、多步骤任务时上下文窗口不足，无法维持长程一致性，因此引入角色分工以分解任务复杂度。

2025 年以来的实证研究揭示了“棕地悖论”（Brownfield Paradox），即 LLM 在复杂遗留系统中因上下文丢失、幻觉及缺乏架构约束导致效率下降甚至负向影响。这一发现迫使研究重心从单纯追求生成速度转向“可控性”与“工程治理”，核心问题演变为如何在非确定性 LLM 输出与传统工程确定性需求之间建立信任链。子问题呈现强依赖关系：上下文管理是基础，若不解决长周期任务中的上下文退化，多智能体协作将因信息丢失而失效；架构约束与治理机制依赖于对代码质量的量化评估；而可复现性问题是所有实证结论可信度的前提。

当前（2025-2026），研究热点集中在智能体编程（Agentic Coding）、规格驱动工程（Spec-Driven Engineering）及 AI 原生开发环境的架构约束对齐。领域活跃度极高，不仅涉及代码生成，还延伸至需求工程、测试、维护及教育，正从实验性工具向工业级生产力基础设施转型。核心矛盾在于 LLM 的非确定性输出与传统软件工程对确定性、可追溯性及质量保障的刚性需求之间的冲突，这一矛盾贯穿了从早期能力验证到当前治理重构的全过程。

**如果用一个核心问题概括该领域，那便是：如何在 LLM 固有的非确定性输出与传统软件工程对确定性、可追溯性及长期可维护性的刚性需求之间，构建有效的工程治理机制以平衡生成效率与系统可靠性。**

## 2. 方法体系

- 2021：Codex——基于GPT-3微调的代码生成模型，确立LLM在自动化软件工程中的基础地位

- 2022：GitHub Copilot——集成于IDE的AI结对编程助手，推动AI辅助编程在工业界的广泛普及

- 2023：MetaGPT——基于SOP的多智能体框架，提升生成代码的功能正确性和可维护性

- 2024：SWE-agent——自主软件工程智能体，实现从单行代码预测向端到端任务执行的范式转变

- 2025：D³ Framework——针对Brownfield工程的LLM辅助工作流，提升复杂环境下的代码生成可靠性

- 2025：Shift-Up——AI原生软件开发中的软件工程护栏框架，确保AI生成代码的长期可维护性

- 2026：Contract-Coding——基于结构化符号范式的仓库级代码生成框架，提升大型系统的生成一致性

- 2026：Nidus——外部化推理的AI辅助工程框架，适用于安全关键领域的软件开发

这条时间线勾勒了该领域方法演进的代表性节点：从 2021 年的 Codex 奠定该领域方法基线，经 2022 年 GitHub Copilot 的推进，到 2026 年的 Nidus 代表当前前沿。各节点对应的技术路线、取舍与关联，详见后续小节。

### 2.1 代码生成与架构

代码生成与架构路线的起源可追溯至 2021 年 Codex 的函数级生成能力，其核心假设是 LLM 能通过大规模预训练习得代码模式。2023 年，MetaGPT 等框架引入多智能体协作，通过角色分工解决复杂任务分解问题，但引入了错误传播风险与通信开销。2025 年，D³ Framework 针对棕地工程提出 Builder-Reviewer 双智能体架构，通过角色分离的提示策略处理遗留系统的模糊性，牺牲了工作流步骤以换取复杂环境下的生成可靠性。

2026 年，Contract-Coding（Lin et al., 2026, P28）提出基于结构化符号范式的仓库级生成框架，通过符号投影、拓扑编排和主动契约审计三个阶段，解决了多智能体框架在扩展性上的瓶颈。该方法将代码生成视为符号空间中的搜索过程，牺牲部分生成速度以换取更高的结构一致性和可验证性，特别适用于大型单体仓库的复杂依赖场景。与之互补的是 Spec-Driven Engineering（Feng et al., 2026, P34），它通过演化的规格指导 LLM 代理的自动化实现，强调规格的可执行性和可验证性，代表了从“代码中心”向“意图中心”范式的转变。

| 方法 | 核心决策 | 放弃什么 | 换取什么 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| Contract-Coding | 符号投影与契约审计 | 生成速度 | 结构一致性与可验证性 | 大型单体仓库 |
| D³ Framework | Builder-Reviewer 分离 | 工作流步骤 | 棕地环境可靠性 | 遗留系统现代化 |
| Spec-Driven | 规格驱动生成 | 前期规格定义开销 | 可维护性与一致性 | 复杂系统自动化构建 |

### 2.2 SE过程与治理

SE过程与治理路线的演进源于对多智能体协作中质量失控的反思。2024 年 SWE-agent 实现了端到端任务执行，但暴露了缺乏架构约束的问题。2025 年，Shift-Up（Lipsanen et al., 2026, P30）提出软件工程护栏框架，重新诠释 V 模型，通过架构漂移检测和可追溯性机制前置约束，牺牲开发速度以换取长期可维护性。2026 年，Nidus（Gorinevski, 2026, P25）进一步提出外部化推理框架，将工程不变量作为外部可判定表面，通过共演化机制维护规范与证明义务，适用于安全关键领域。

TDD Governance（Hasanli et al., 2026, P32）则通过提示工程实现多智能体代码生成中的测试驱动开发治理，将 TDD 原则编码为多智能体协议，利用测试作为行为规范约束 LLM 生成空间。与 Shift-Up 的前置治理不同，TDD Governance 强调在智能体协作中嵌入治理规则，确保每个步骤都符合质量要求。FPF（Gilda and Gilda, 2026, P18）则关注架构决策的认知状态和时间有效性，通过模糊逻辑聚合证据强度，计算决策的有效置信度，防止因信息过时导致的架构侵蚀。

### 2.3 工具交互与提示

工具交互与提示路线聚焦于提升开发者与 AI 协作的效率与可靠性。2022 年 GitHub Copilot 确立了 IDE 集成范式，但提示作为临时字符串缺乏持久性。2025 年，Prompt-with-Me（Li et al., 2025, P1）提出 IDE 内结构化提示管理方法，将提示视为一等公民，支持版本控制和协作，提高了提示管理的效率和质量。ContextBranch（Nanjundappa and Maaheshwari, 2025, P13）则基于版本控制解决多轮对话中指令累积导致的性能下降问题，通过分支机制允许开发者并行尝试不同路径，显著提升了长程交互中的代码生成质量。

Reliance-Control Framework（Ferino et al., 2026, P26）关注开发者对 AI 工具的依赖控制，通过社会技术扎根理论分析开发者经验，识别依赖水平的关键因素和控制机制。该方法将依赖视为动态过程，提供调节策略，平衡 AI 效率收益与过度依赖导致的能力退化风险。与 ContextBranch 的技术路径不同，Reliance-Control 强调人机交互的动态平衡，为 AI 工具的用户体验优化提供了新的视角。

### 2.4 实证评估与影响

实证评估与影响路线旨在量化 LLM 对开发效率、代码质量及技术债务的实际影响。2026 年，Cursor DiD Study（He et al., 2025, P7）提出基于双重差分法的因果效应评估方法，通过对比采用 Cursor 前后的开源项目数据，揭示了短期速度提升与长期复杂度增加之间的权衡关系。AI-Generated Smells Analysis（Zhu et al., 2026, P35）则通过两阶段实验评估 LLM 和代理驱动开发中的代码和架构异味，揭示了 AI 生成代码的技术债务积累模式。

Matthew Effect of AI Programming Assistants（P46）评估了 AI 编程助手在软件演化中的隐藏偏差，量化了 AI 工具对主流框架的强化作用。与 Cursor DiD 的因果推断不同，该方法强调生态多样性和架构权衡，为 AI 编程助手的公平性和多样性评估提供了新的框架。

### 2.5 教育与社会影响

教育与社会影响路线关注 LLM 对软件工程教育模式、开发者技能演变及行业生态的重塑。2025 年，Coding With AI Reflection（Chang et al., 2025, P16）通过反思工业实践，探讨 AI 如何重塑软件开发工作流和未来教育。2026 年，Vibe-Check Protocol（Aiersilan, 2026, P17）提出量化 AI 编程中认知卸载的协议，通过纵向设计和难度标准化，量化认知卸载对技能发展的影响。

AI-Assisted Code Review as Scaffold（Oliveira et al., 2026, P31）将 AI 辅助代码审查作为脚手架，促进代码质量和自我调节学习。与 Vibe-Check Protocol 的量化评估不同，该方法强调教育目标，将 AI 反馈转化为学习机会，支持自我调节学习，为 AI 辅助教育提供了新的范式。

### 2.6 可信与可复现性

可信与可复现性路线聚焦于 LLM 在 SE 应用中的可信度问题。2025 年，LLM-for-SE Reproducibility Crisis（Siddiq et al., 2025, P11）通过挖掘和分析 640 篇论文的元数据，识别可复现性缺陷和最佳实践。2026 年，FeatureSHAP（Vitale et al., 2025, P15）提出面向软件工程的自动化模型无关可解释性框架，利用 SHAP 值对 LLM 决策进行特征归因，增强了高风险领域中对 AI 输出的信任和监督能力。

SEALing the Gap（Pathania et al., 2026, P19）提出基于多基准驱动的 LLM 推理碳估算参考框架，通过非侵入式方法估算 LLM 推理的碳排放，适用于生产环境。与 FeatureSHAP 的可解释性不同，该方法强调可持续性和实用性，为 LLM 的可持续部署提供了新的视角。

## 3. 关键共识、分歧与开放问题

### 3.1 领域共识

LLM 在简单、隔离的代码生成任务上能显著提升效率，但在复杂、上下文依赖的棕地系统中效果有限甚至产生负向影响，这一共识在约 15 篇论文中得到共同支持。多智能体框架通过角色分工能处理更复杂的任务，但仍面临可扩展性瓶颈和错误传播问题，需结合反馈机制，约 10 篇论文共同支持这一观点。单纯的代码生成不足以支撑软件工程，必须整合需求、设计、测试等全生命周期环节，且需引入结构化规格或护栏机制以保证质量，约 12 篇论文共同支持。

与此相关的另一个共识是，开发者对 LLM 的过度依赖是一个普遍风险，需要通过工具设计和教育干预来维持人类的判断力与技能，约 8 篇论文共同支持。上下文管理是提升 LLM 在真实项目表现的关键，包括项目规则、代码库检索及对话历史的结构化处理，约 9 篇论文共同支持。AI 生成代码的质量评估不能仅局限于功能正确性，必须纳入代码异味、架构一致性、可维护性及安全性等工程维度，约 7 篇论文共同支持。

### 3.2 观点分歧

治理的最佳形态存在显著分歧：前置约束（Guardrails） vs 后置审查（Human-in-the-loop）。Shift-Up 和 Nidus 主张在代理执行前建立治理环境，通过架构漂移检测和可追溯性机制前置约束，防止错误累积。Orchestrated Human-AI Delivery 则主张保留人类专家在关键决策和审查中的核心作用，通过编排层平衡速度与可靠性。现有证据偏向前置约束在长期可维护性上的优势，但人类判断在架构决策中的不可替代性仍存争议，缺乏长期的、跨项目的纵向对比数据。

LLM 在复杂系统中的效率悖论也是重要分歧：速度提升 vs 认知负荷增加。Cursor DiD Study 显示 AI 工具提升短期速度，但导致长期复杂度增加，整体效率在棕地系统中可能为负。Vibe Coding 支持者则认为通过降低门槛，AI 使非专家也能参与开发，整体生产力提升。认知负荷的测量工具不统一，且不同开发者技能水平对 AI 依赖的反应差异巨大，导致结论场景依赖性强。

### 3.3 其他开放问题

当前领域处于“工程问题”与“研究问题”的交汇点。最紧迫的工程问题是架构约束对齐、技术债务预测、专用语言适配。最根本的研究问题是 LLM 决策的可解释性、认知卸载的量化、非确定性的概率建模。可复现性危机阻碍了科学结论的累积，需建立标准化的实验协议、数据共享机制及模型版本控制规范。

已知—争议—未知认知图谱显示，领域在函数级生成上已达成共识，在复杂系统治理上存在争议，在安全关键领域的可信度上仍属未知。未来趋势是建立透明、可审计、可复现的 AI 原生开发基础设施。

## 4. 总结与展望

LLM 驱动软件工程已从“生成能力竞赛”进入“工程治理竞赛”，核心任务是在非确定性中构建确定性。早期方法假设 LLM 能独立解决复杂任务，实证研究证明其在棕地系统中因上下文丢失和架构无知而失效，迫使研究重心转向“人机协作中的治理”。核心瓶颈在于如何在保持 LLM 生成灵活性的同时，通过结构化约束确保工程确定性，并解决可复现性危机。

未来可能突破的方向包括：提升 LLM 生成代码的可验证性和可审计性，开发结构化验证框架和形式化验证方法；解决 LLM 辅助开发中的技术债务积累问题，开发技术债务预测和缓解机制；增强 LLM 在专用编程语言和工业领域的应用能力，开发领域适配的提示工程和微调方法。对进入者最值得做的一件事是，在统一骨干与统一预训练条件下重评测代表性方法，建立标准化的复现框架与元数据规范。
